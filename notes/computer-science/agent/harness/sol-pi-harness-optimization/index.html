SoL-Pi

2026-09-16

#Pi#Agent

理解主线

原笔记围绕 Harness 的执行成本优化：减少无效模型回合、重复上下文和长日志阅读，同时保留完成工作需要的证据。理解每项优化时，应比较节省了什么，以及可能损失哪类信息。

SoL-Pi 是 NVIDIA 发布并维护的开源 Agent Harness 效率扩展，构建在 Pi 的公开扩展 API 之上。它不是另一套模型或独立的 Coding Agent，而是在不改动 Pi 核心的前提下，为长时间运行的 Coding Agent 减少无效模型回合、上下文重放与长日志阅读开销。

其核心目标是：在不减少有效工作、不跳过验证、不隐藏关键证据的前提下，降低 token 与推理成本。

SoL-Pi 的定位更接近“Agent 运行时优化中间件”，而非“更聪明的模型 CLI”。

定位与设计边界

SoL-Pi 以 Pi 的扩展形式安装：

pi install git:github.com/NVlabs/SoL-Pi

它遵循以下边界：

  • 不 patch Pi：仅使用 Pi 的公共 API，不 fork 或 vendor Pi 源码。
  • 不接管运行时选择：认证、模型供应商、主模型、Provider URL、Shell 行为仍由 Pi 控制。
  • 不绑定 NVIDIA 模型：可随 Pi 使用 Claude、OpenAI、Gemini、其他 API Provider 或本地模型。
  • 显式启用：所有效率机制默认关闭，必须通过配置逐项开启。
  • 保留原始证据：被打包或缩减的原始观察结果仍保存于本地，必要时可精确召回。

这种设计使 SoL-Pi 能随 Pi 升级，并避免将用户锁定到某个特定模型、供应商或 NVIDIA 自有运行时。

优化的四类浪费

长任务中的 Agent 往往重复经历如下低效路径：编辑之后再花一个模型回合决定运行验证命令；大文件和长日志在后续每轮请求里反复传入；已经完成的子任务一直占据活跃上下文；模型为找到少数关键报错而完整阅读超长日志。

SoL-Pi 将这些问题拆分为四个独立机制：

层面 机制 消除的主要浪费
工具调用 Action Fusion 编辑后再单独发起固定验证的模型回合
工具观察结果 ObservationPack 大型文本结果在后续请求中被重复重放
长日志诊断 Evidence-Preserving Reducer 模型完整阅读长日志，只为获得少量关键信息
上下文 Online Context Compact 已完成子任务长期保留在活跃上下文

四个机制可以独立开启和组合使用。

Action Fusion

Action Fusion 将“修改文件”和“执行后续验证”合并为同一个工具调用。

典型 Coding Agent 轨迹如下：

  1. 调用 edit 或 write 修改代码；
  2. 模型读取修改成功的结果；
  3. 模型进行一次额外推理；
  4. 决定运行 test、lint 或 typecheck；
  5. 调用 Shell 执行验证。

其中第 2～4 步对大量可预测修改而言，常常没有足够的增量价值。Action Fusion 允许在编辑、写入后自动运行一条预配置的验证命令，并将验证输出与编辑结果一并返回模型。

普通流程：Edit → 模型推理 → Shell 验证
融合流程：Edit + Shell 验证 → 一次返回

工程意义

  • 不是省略验证，而是保留验证并删除中间决策回合。
  • 验证命令来自显式配置，而不是机制在未知项目中自行猜测。
  • 特别适用于格式化、类型检查、单测等稳定、重复的反馈循环。
  • 可视为对 Agent 工具工作流的 macro / transaction fusion。

ObservationPack

ObservationPack 解决大型工具结果被重复塞入上下文的问题。

例如，Agent 读取一个 100 KB 文件或得到一段很长的构建日志时，首次调用可能确实需要全文；但在之后的每个模型请求中持续重放原文，会带来：

  • 输入 token 与缓存成本增加；
  • 可用 Context Window 被历史材料挤占；
  • 模型更难从噪声中定位当前需要的信息；
  • 更高的上下文传输和推理负担。

工作方式

  1. 首次出现时，正常向模型提供原始结果；
  2. SoL-Pi 将符合条件的原文按会话归档到本地；
  3. 后续请求中，将重复的大结果替换为稳定句柄；
  4. 模型需要细节时，通过分页、精确的 recall 工具重新读取原文片段。
大段原文 → 稳定句柄（obs_...） → 按需、分页、精确召回

这不是普通的有损摘要，而是将上下文改造成类似“冷热分层”的存储结构：活跃上下文只留下可寻址索引，完整原文留在本地归档，只有需要时才重新载入。

可靠性特征

  • 原始内容仍然存在，可被精确召回；
  • 句柄稳定，适合作为后续推理中的引用；
  • 分页读取避免一次性重新引入全部内容；
  • 将上下文视为昂贵缓存，而不是无限的聊天历史。

Evidence-Preserving Reducer

Evidence-Preserving Reducer 面向诊断类长日志。它的目标不是生成一般性的摘要，而是产出可验证的紧凑“回执（receipt）”。

普通 LLM 摘要可能遗漏关键报错、加入不存在的推断，或者使读者无法追溯摘要依据。SoL-Pi 采用“模型生成 + 确定性验证”的设计：

  1. 识别适合缩减的诊断类长日志；
  2. 归档原始日志；
  3. 交由配置的 reducer 模型提取紧凑回执；
  4. 对回执中保留的逐字引用，在原始内容中进行机械校验；
  5. 若任何引用无法在原文中找到，直接保留原始结果。

它无法机械证明摘要的所有语义结论都正确，但能保证保留下来的关键引用确实来自原始日志。

Fail-open 原则

Reducer 验证失败时不会继续使用可疑摘要，而是回退到原始文本。这种 fail-open 策略优先保障 Agent 的证据链完整性，而非追求压缩率。

注意：Reducer 可能将符合条件的日志发送给配置的远程模型。含有密钥、用户数据、内部路径或其他敏感内容的日志，应谨慎启用此功能。

Online Context Compact

Pi 本身提供上下文压缩能力。Online Context Compact 不重新实现压缩，而是试图选择更合理的触发时机。

其关键洞察是：计划中的一个步骤完成时，往往是压缩上下文的语义安全点。 已完成子任务的具体操作细节通常不再需要持续占据上下文，但下一阶段仍可保留必要结论。

SoL-Pi 会结合以下因素决定是否触发 Pi 原生 compact：

  • 当前计划步骤是否完成；
  • Context Window 的压力；
  • 压缩本身的额外成本；
  • 预期能减少的后续上下文重放成本。

压缩成功后，Pi 会在新的 turn 中自动继续当前任务；如果用户取消运行或退出 Pi，则不会强制继续。

从运行时角度看，它类似 Agent 上下文的“垃圾回收（GC）”：不是仅凭 token 阈值机械回收，而是在任务语义边界上清理已完成阶段的详细轨迹。

配置与启用策略

SoL-Pi 使用单一有效配置，配置优先级如下：

  1. 当前受信任项目中的 .pi/sol-pi.json；
  2. 用户级 ~/.pi/agent/sol-pi.json；
  3. 内置默认值。

项目级配置优先于用户级配置，二者不会合并。这避免了多层配置叠加后难以解释的行为。

一个保守配置示例：

{
  "version": 1,
  "actionFusion": true,
  "observationPack": true,
  "evidencePreservingReducer": false,
  "onlineContextCompact": false,
  "cacheWriteReadRatio": 12.5
}

建议的启用顺序：

  1. 先开启 Action Fusion 与 ObservationPack；它们不需要额外模型调用，也不会主动终止当前运行。
  2. 在确认日志不含敏感内容、并接受额外模型调用后，再评估 Evidence-Preserving Reducer。
  3. 对长任务和复杂计划执行进行实测后，再开启 Online Context Compact。

本地存储与安全

ObservationPack 与 Reducer 的原始资料会按照会话保存在 Pi session 目录下：

<session-directory>/sol-pi/<session-id>/
├── observation-pack/
└── evidence-preserving-reducer/

这些归档在会话结束后不会自动删除。因此需要注意：

  • 工具结果可能含有源码、日志、路径与敏感信息；
  • 本地磁盘权限、备份策略与清理周期应符合项目安全要求；
  • 禁止对必须留在本地的敏感日志启用远程 Reducer；
  • 归档的价值在于可追溯性，但也带来数据留存责任。

与 Claude Code、Codex CLI 的差异

维度 SoL-Pi Claude Code / Codex CLI
形态 Pi 的开源效率扩展 各自厂商维护的完整 CLI Agent 产品
优化重点 可组合的 Harness 效率机制 官方内置的端到端 Agent 体验
模型绑定 不绑定，继承 Pi 的多 Provider 能力 主要围绕 Claude 或 OpenAI/Codex 生态
可定制性 通过 Pi 公共扩展 API 与配置组合 受官方产品接口与工作流限制
证据策略 本地归档、按需召回、可验证缩减 具体行为由各工具内部实现决定

SoL-Pi 不直接与 Claude Code 或 Codex CLI 在“谁的模型更强”上竞争；它优化的是 Agent 在模型调用之间的执行轨迹和上下文生命周期。

总结

SoL-Pi 的工程特色可概括为：

  1. 在 Harness 层而非模型层优化：减少重复回合、重复上下文与无效长日志阅读。
  2. 四个机制分层解耦：工具、观察结果、日志缩减、上下文压缩分别治理。
  3. 以证据保留为先：原文可召回，Reducer 引用可验证，失败时回退原文。
  4. 以显式配置为先：默认不改变 Pi 行为，用户可以分阶段启用并测量收益。
  5. 不侵入上游：不修改 Pi 核心，不绑定模型、认证或 NVIDIA 运行时。
  6. 面向长任务的经济性：把 Context Window、缓存重放、模型回合都视为有成本的运行时资源。
