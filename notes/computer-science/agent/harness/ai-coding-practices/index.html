理解主线

把模糊评价改成验收条件：先说明预期行为、允许改动的范围和验证方法，再让 Agent 实现。计划与测试的价值在于可检查的工作边界，小改动可以一次完成实现、验证和总结。

你缺的不是“更会看 AI 写的代码”，而是一套让结果可验证的闭环喵：

模糊想法 → 可验收需求 → 实现 → 自动验证 → 独立 Review → 人工只看关键风险

核心原则：不要问“代码有没有问题”，要问“它是否满足哪些可验证的条件”。

先把每个需求写成这个最小模板：

目标：用户最终能看到/做到什么？
现状：现在的行为与问题是什么？
验收条件：
- 场景 A：输入……，应得到……
- 场景 B：输入……，不应发生……
- 相关测试必须通过：……
范围：允许改哪些目录/模块。
约束：不改 API / 不改数据格式 / 保持兼容……
不确定之处：不要自行猜测或静默降级；列出需要我决定的选项。

例如，不说“优化登录”，而说：

修复登录失败后页面永久 loading 的问题。

验收条件：
- 密码错误时显示服务端错误信息；
- 提交按钮恢复可点击；
- 网络异常时显示通用错误，不泄露原始异常；
- 成功登录行为不变；
- auth 相关测试通过。

范围：src/auth 与对应测试。不要修改接口返回格式。

复杂任务建议分两步，而不是直接让 AI 开写：

  1. 先让它输出计划：会改哪些文件、为什么、有哪些风险、如何测试。
  2. 你确认计划后，再让它实现并自行运行相关测试。

这一步能极大减少“它到底在干嘛”的不确定感。小改动则可以直接要求“实现、测试、总结”，不用额外来回。

完成时，不接受一句“已完成”。要求它交付验收证据：

完成后按以下格式汇报：
1. 改了什么，以及影响哪些行为；
2. 每条验收条件是否满足；
3. 运行了哪些命令，结果是什么；
4. 没有覆盖的边界、已知风险和后续建议；
5. 给出可供我人工验证的步骤。

Review 也不要让 AI 泛泛地“看看代码”。把它变成独立的、带证据的审查：

请 review 当前未提交改动。

依据：<原始目标和验收条件>
重点检查：
- 是否遗漏任一验收场景；
- 是否有空值、异常路径、边界值、并发或权限问题；
- 是否破坏兼容性或引入无关改动；
- 测试是否真的能捕获本次 bug。

只报告可证实的问题。每项必须包含：
严重程度、文件与行号、触发条件、为何会出错、修复建议。
若没有发现问题，明确说明已检查的范围和仍无法覆盖的风险。

我很推荐“实现者 + 独立审查者”两遍：第一个 AI 负责实现，第二个带着原始验收条件、但不沿用第一个的思路，专门尝试找错。这样比让实现者自己说“没问题”可靠得多喵。

最后，人类 review 不必逐行读完。优先看四件事：

  • 改动是否超出需求范围；
  • 有没有错误处理、边界条件与数据安全风险；
  • 测试是否覆盖了真正的失败路径；
  • 你能否按验收步骤亲自复现“成功”和“失败”场景。

对 UI 任务，额外要求截图、录屏或明确的手工验证步骤；对后端任务，要求请求/响应示例和自动化测试。这样“实现效果是否符合预期”就不再靠直觉判断了。

复习与应用

给一个需求写出可观察的完成条件，并检查总结中的每项证据是否真的来自运行或阅读。
