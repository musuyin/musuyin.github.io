Agent

2026-04-17

#AI#Agent

Agent 如何把一个目标转化成行动，又由谁判断任务已经完成？从模型、工具和运行时的分工入手，再看工作流、规划和验收如何约束执行。可从 智能体学习路径 找到相关主题。

Agent 如何推进目标

Agent 是能在给定目标和约束下自主决策并采取行动的 AI 系统。单次问答由用户给出输入，模型返回回答。面对需要多步完成的目标，Agent 可以拆解任务、调用工具、访问记忆、读取环境反馈，并据此调整下一步。它的核心能力包括工具调用、记忆、多步推理和自我纠错。

常见的实现由 LLM、工具、记忆与规划模块组成。LLM 提出决策，工具执行外部操作，记忆保留或补充状态，规划模块把复杂目标转化为可执行的步骤。比如写一份竞品分析报告，可以先搜索竞品资料，再整理数据、对比分析，最后撰写报告。

决策、行动与反馈

Agent 循环可以概括为 思考（Thought）→ 行动（Action）→ 观察（Observation）。模型根据当前目标和已有信息决定是否调用工具，运行时执行调用并把结果交回模型。模型用新的观察决定继续执行、调整策略还是返回最终结果。

停止条件

运行时可以同时设置以下条件，先触发的条件决定何时结束。

  • 模型给出最终答案。模型判断目标已经达成时，可以退出循环。业务步骤是否完成仍需要按约定验收。
  • 达到最大循环次数。例如最多运行 15 轮，达到上限后返回已有结果并告知用户进度。
  • 接近总 token 预算。限制整个任务的 token 消耗和成本。
  • 达到超时上限。例如运行超过 60 秒时终止任务。

模型、工具与记忆如何分工

LLM 负责理解和决策

模型根据用户指令、工具结果和检索到的记忆判断下一步动作。运行时负责组装这些输入、执行动作、保存状态与验收产物。一次模型调用如何组装消息、设置输出上限和分配上下文预算，见 S06-LLM。

工具负责访问外部系统

**工具（Tool）**把搜索、数据库查询、读文件、执行代码或发邮件等能力封装成可调用函数。工具的定义向模型描述名称、用途和参数结构。模型选择工具并给出参数，运行时负责真正执行并回传结果。

工具的设计契约

  • 职责单一。天气查询与发送邮件适合拆成不同工具，使模型容易根据当前目标选择。
  • 描述精确。模型结合名称、description、参数 schema 和上下文选择工具。「查询数据」容易和其他工具混淆。「查询公司内部销售数据库，支持按日期和产品类别筛选，返回销售额和订单数」交代了范围、筛选条件和结果。描述质量仍需用实际任务验证。
  • 参数简洁。模型只填写需要它决策的参数。可信身份与已知配置由运行时提供。默认值应写入工具契约，缺少必填参数时应明确报错。
  • 错误可处理。「参数 city 不能为空」比「Error code 400」更有助于模型修正参数后重试。

工具定义的传递、描述与参数 schema 的设计、大工具集合的筛选，以及调用结果如何回传，见 S04-Tool-Use。

记忆负责保留状态与补充上下文

短期记忆

短期记忆依赖当前任务或对话的上下文窗口（context window）。任务中间的搜索结果、工具反馈等状态可以用作下一步输入。它类似人的工作记忆，容量有限，也不承担跨任务持久化。

复杂任务积累了大量工具返回后，可以压缩早期步骤的内容，留下摘要和关键信息，也可以用滑动窗口保留最近几步的详细内容。两种方法都有信息损失，需要在上下文预算与关键事实保留之间取舍。

长期记忆

长期记忆把重要信息持久化，以便在后续任务中检索。一种常见做法是对信息生成向量表示（embedding），存入向量数据库，再通过语义检索和元数据过滤找回相关内容。

可以借用认知科学的分类来理解长期记忆存储的内容。实现时可以共享同一套检索机制。

  • **语义记忆（Semantic Memory）**保存事实，例如用户从事金融行业、某个 API 每分钟最多调用 60 次。
  • **情景记忆（Episodic Memory）**保存经历，例如上次处理某笔退款时查到订单已超过退款期。
  • **程序性记忆（Procedural Memory）**保存可复用的做事流程，例如处理退款时先查订单状态，再核实支付方式。

写入前可以评估信息的重要性。存得过多会增加检索噪音，存得过少则无法充分支持后续任务。检索时可考虑记忆衰减（Memory Decay）。一种做法是给语义相似度乘以随时间指数下降的权重，使较久远的记录在其他条件相近时排序更靠后。衰减速度取决于业务。一次性的客服对话可较快衰减，可能长期作为依据的法律合规记录需要更慢的衰减。

MCP 与 A2A 分别连接什么

**MCP（Model Context Protocol，模型上下文协议）**由 Anthropic 于 2024 年 11 月发布，使用 JSON-RPC 交换消息。它定义了三类可暴露的能力。Anthropic 发布公告

  • **Tools（工具）**是可调用的操作，例如搜索或发送邮件。发邮件等操作会产生外部副作用。
  • **Resources（资源）**提供可读取的上下文数据，例如文件内容。
  • **Prompts（提示模板）**提供预定义的提示词模板，例如代码审查模板。

Host 是用户交互的 AI 应用，例如 Claude Code CLI 或 Cursor。Client 管理与 MCP Server 的连接。Server 暴露相应的工具、资源或提示模板。统一的协议让不同 Host 可以复用按协议实现的 Server。工具是否能被当前模型看到和调用，仍取决于 Host 的接入配置和运行时权限。发现、加载与调用的过程见 MCP 基础概念 和 MCP 工具规范。

**A2A（Agent to Agent）**关注智能体之间的通信。任务状态、消息和交付物怎样表示，可参阅 A2A 通信机制。

何时使用 Workflow

区分 Tool、Agent 和 Workflow，可以看下一步由谁决定。

组成 决策方式
Tool 按已给出的参数执行一项能力，例如搜索、执行代码或发邮件。
Agent 在运行时约束下，由模型根据目标和观察决定调用哪个工具、是否继续以及何时给出结果。
Workflow 开发者预先定义节点、分支和流转规则。节点可以调用 LLM、Agent 或工具。

固定工作流如何控制分支

下面的客服流程用 LLM 识别意图，并在产品分支生成回答。开发者用 if 和 elif 定义分支，代码根据分类或订单结果选择下一节点。

def run_customer_service_workflow(user_query: str) -> str:
    # ---- 第一步：意图识别 ----
    # 这里把 LLM 当成一个分类器来用，它只负责判断这个问题属于哪个类别
    # 「下一步去哪」这个决策是下面的 if/elif 来做的，不是 LLM 自己决定的
    intent = classify_intent_with_llm(user_query)  # 返回 "product" / "refund" / "other"

    # ---- 第二步：根据意图走不同分支 ----
    # 注意：这个分支判断是开发者写的 Python 代码，不是 LLM 的决策
    if intent == "product":
        # 产品问题：去知识库检索，再生成回答
        docs = search_knowledge_base(user_query)    # 直接调 Tool，固定的检索步骤
        answer = generate_answer_with_llm(user_query, docs)  # LLM 作为节点生成回答
        return answer

    elif intent == "refund":
        # 退款问题：查订单系统，再走审核流程
        order_info = query_order_system(user_query)  # 调 Tool 查订单
        if order_info["eligible"]:
            process_refund(order_info["order_id"])   # 调 Tool 处理退款
            return "退款已受理，预计 3 个工作日到账"
        else:
            return "很抱歉，该订单不满足退款条件"

    else:
        # 其他问题：转人工
        escalate_to_human_agent(user_query)
        return "已为您转接人工客服，请稍候"

 # 整个流程的走向在代码里一目了然
 # 出了任何问题，你可以精确定位是哪一步出了错

固定工作流的优点是路径可控，出了故障可以沿节点逐步调试。相同的编排规则仍可能随分类结果或外部数据走不同分支。输入超出预设范围时，流程的灵活性取决于已有分支是否覆盖该场景。

Agentic Workflow 如何组合两者

自主 Agent 可以按反馈调整，但运行行为更难预测，故障更难复现，多轮模型调用也可能推高成本。固定工作流保留可控的主路径，处理预设范围以外的输入时弹性较小。Agentic Workflow 可以固定整体流程，在需要灵活判断的节点嵌入 Agent，其他节点直接使用 LLM 或工具。这样既能沿主流程定位问题，也能让局部节点按情况调整。

常见编排模式

  • **Prompt Chaining（提示链）**按顺序分解任务，前一步的输出成为后一步的输入。
  • **Routing（路由）**先分类，再按分类结果分发到不同分支。客服工作流是一个例子。
  • **Parallelization（并行化）**同时执行可以并行的子任务，最后汇总，例如同时从多个数据源检索信息。
  • **Orchestrator-Workers（编排者与执行者）**由中央编排者分配可独立完成的子任务，多个 Worker 分别执行。
  • **Evaluator-Optimizer（评估者与优化者）**由一个模型生成结果，由另一个模型或同一模型的评估角色检查结果。评估未通过时把反馈交给生成者，直到通过或达到重试上限。评估标准应明确，可由代码中的打分函数等机制执行。

如何选择推理与执行策略

CoT 与 ToT 如何展开推理

直接回答时，模型可以只给结论。**CoT（Chain of Thought，思维链）**是一类传统提示方法。给模型提示「让我们一步步思考」或 “Let’s think step by step”，引导它先展开中间步骤，再生成结论。语言模型顺序生成 token，已经生成的推理内容会进入上下文，供后续生成参考。这种方式在某些任务中能改善回答，但生成更多推理文字无法保证结论正确。纯文字思维链本身不能访问外部世界。

  • **Zero-shot CoT（零样本思维链）**只需在提示中要求分步思考，无需准备示例。模型自行决定步骤的格式和深度，可能详细展开，也可能跳步。
  • **Few-shot CoT（少样本思维链）**提供带推导的示例。比如给出一道数学题的逐步计算和结论，让模型按同样的格式作答。示例有助于稳定格式，也需要准备高质量样本并占用上下文 token。

一些推理模型会进行内部推理。应用可以要求可检查的结论、简洁依据和结构化计划，由运行时判断后续能否执行。

**ToT（Tree of Thoughts，思维树）**在推理节点上展开多条候选路径，评估各分支后再选取路径继续。与沿单条思维链逐步推导相比，思维树可以比较备选方案。

ReAct 如何利用工具反馈

**ReAct（Reasoning and Acting）**把推理与行动交替进行。模型每轮根据最新观察决定下一步，适合在执行中根据环境反馈调整的任务。

  1. Thought。模型根据当前状态提出下一步。例如用户想查竞品信息，先搜索竞品 A 的最新动态。文本提示实现可把这一步写在输出中。
  2. Action。模型选择工具并提供参数，运行时调用工具。
  3. Observation。运行时把工具返回值交回模型。模型根据新的观察继续推理或返回最终结果。

从文本指令到结构化工具调用

下面是由运行时代码驱动的 ReAct 示例。提示约定 Thought、Action 和 Final Answer 等标记，运行时解析模型输出、执行工具，再把结果加入历史。

def react_agent(question: str, tools: dict, max_steps: int = 10):
    # 把 ReAct 格式约束和问题拼在一起，作为初始 prompt
    prompt = build_react_prompt(question, tools)
    # 用来存每一轮的对话历史，每次调 LLM 都把完整历史带上
    history = []

    for _ in range(max_steps):
        # 调 LLM，让它输出下一步的 Thought + Action
        # 注意：每次调用都把完整历史拼进去，LLM 才知道之前做了什么
        response = llm.generate(prompt + "\n".join(history))

        if "Final Answer:" in response:
            # LLM 输出了 Final Answer，说明它判断任务完成了
            return response.split("Final Answer:")[-1].strip()

        # 从 LLM 输出里解析出 Action 名称和 Action Input
        # 例如：Action: search，Action Input: 苹果公司市值 -> ("search", "苹果公司市值")
        action, action_input = parse_action(response)

        # 执行对应的工具，拿到真实结果
        if action in tools:
            observation = tools[action](action_input)
        else:
            # 如果 LLM 填了一个不存在的工具名，给它一个错误反馈
            observation = f"工具 {action} 不存在，请选择可用工具"

        # 把这一轮的 LLM 输出（含 Thought+Action）和 Observation 都追加进历史
        # 下次调 LLM 时这些内容会成为它的「记忆」
        history.append(response)
        history.append(f"Observation: {observation}")

    return "超过最大步数，任务未完成"

支持原生 Function Calling / Tool Use 的模型接口可以返回结构化工具调用，避免依赖从自由文本解析 Action: xxx。运行时仍负责解析和校验参数、执行工具、回传观察并控制循环。

循环漂移与错误传播

  • 循环漂移。单独使用 ReAct 时，每步根据局部状态决策，缺少全局计划可能使执行偏离初始目标。
  • 错误传播。错误的工具输出或早期判断会进入历史，影响后续步骤。基础的前向循环本身不包含独立反思或验收。

可以先用粗略计划约束整体目标，再用 ReAct 执行各个子任务，根据反馈调整受影响的步骤。

Reflection 如何利用评估反馈

Reflection 在完成一步或整个任务之后，使用同一模型或专门的评估模型检查结果是否达到预期。未通过时可以重试或换策略。代码生成、文案写作等一次难以达到要求的任务可以用反馈逐轮修订。

Reflexion 会把失败原因和改进建议整理为反思总结，作为下一次尝试的额外上下文，使反馈能够跨尝试复用。

如何拆分复杂任务

大任务涉及多个目标和大量中间状态。把搜索结果、分析和未完成的文稿都放进同一上下文，会消耗有限的窗口，也让当前子目标难以追踪。拆分让每一步围绕一个可验收的子目标，只带入与当前步骤有关的输入。独立步骤还可以并行，以降低端到端延迟。

静态拆分与动态拆分

静态拆分把步骤和流转规则预先写入 Workflow。例如技术博客的固定步骤可以是搜索资料、整理大纲、逐段撰写、润色校对。固定步骤便于定位问题，灵活性则受既有流程限制。

动态拆分让模型按目标和约束提出候选步骤。Plan-and-Execute 将规划和执行分开，便于看清任务的全局结构，也可以在执行前人工审查计划。动态拆分适应新任务的能力较强，需要对候选计划和执行结果做额外检查。

Plan-and-Execute 如何分离规划与执行

  1. 规划（Planner）。模型从全局目标出发，生成包含子任务、依赖和预期产出的结构化计划。规划器可以是同一模型的单独调用，也可以使用不同模型。只生成计划、不执行工具，是一种实现方式。
  2. 执行（Executor）。运行时按依赖选择可执行步骤。执行器知道当前子任务在整体计划中的位置，可以在步骤内部用 ReAct 循环处理实际情况。
  3. 汇总。把各步骤的产出整合为最终交付物，检查各部分之间的衔接，再按整体目标验收。

规划器需要的输入

输入 用途
原始目标与交付物 明确最后需要交付什么，防止计划偏离用户要求
用户约束与授权范围 区分可以执行的动作、禁止事项和需要补充的信息
当前环境与已验证事实 让步骤建立在实际资源上，而不是编造工具或文件
可用能力与工具边界 判断哪些动作能执行、输入从哪里获得
已完成工作与操作记录 保持进度，不重复已经执行的动作
调用、时间与 token 预算 限制计划规模与执行成本
输出 schema 与验收要求 让计划能够被程序读取和检查

只要求模型「把任务拆一下」不足以获得可可靠执行的计划。模型服务支持结构化输出时可以约束字段，否则由运行时解析与校验，解析失败时明确报错。

下面是一段规划指令。

依据提供的目标、约束、已验证事实和可用能力生成候选计划。
每个步骤输出 id、action、depends_on、required_capabilities、output 和 acceptance。
每步围绕一个可验收的子目标，明确所需输入及其来源。
未知信息列为待确认条件，不编造资源、工具或执行结果。
步骤必须覆盖原始目标，遵守用户的动作范围。
仅返回符合计划 schema 的数据，当前调用不执行工具。

运行时将规划指令和任务资料一起交给模型，并负责落实「当前调用不执行工具」的配置。未知环境可以先做必要的只读发现，也可以把确认资源和输入列为最前面的步骤。

模型如何提出候选步骤

模型结合目标、上下文、训练中学到的任务模式和当前推断，逐 token 生成计划和结构化字段。例如诊断慢接口往往需要先确认慢在哪里、收集证据，再检查实现。写报告则需要收集资料、分析并组织表达。

这些模式有助于提出步骤，但无法证明模型已经正确完成调度。计划可能漏掉依赖，假设不存在的工具，把推测当作已知事实，或提出无法验收的步骤。有的推理模型会在生成结果前投入内部推理，具体机制和可配置程度取决于服务。应用可要求简洁的计划依据、输入输出和验证条件。DAG 验证、拓扑排序和资源互斥等确定性规则由运行时实现。

计划如何表示

以「只读定位接口延迟来源」为例，下面是候选计划。字段描述待执行的动作及其验收条件。

{
  "goal": "基于证据定位接口延迟来源，输出结论与不确定项",
  "constraints": ["只读分析，不修改线上配置"],
  "steps": [
    {
      "id": "observe",
      "action": "确认服务、接口、时间范围并读取延迟指标",
      "depends_on": [],
      "required_capabilities": ["读取服务指标"],
      "output": "确认后的查询范围、P95 延迟与对照数据",
      "acceptance": "每个指标都有查询范围和来源；信息缺失明确标记"
    },
    {
      "id": "trace",
      "action": "读取同一范围的请求链路，识别耗时集中的环节",
      "depends_on": ["observe"],
      "required_capabilities": ["读取请求链路"],
      "output": "链路证据与候选原因",
      "acceptance": "候选原因对应可追溯的耗时证据；未验证结论保留为假设"
    },
    {
      "id": "verify",
      "action": "核对相关代码与已有配置，验证候选原因并汇总结论",
      "depends_on": ["trace"],
      "required_capabilities": ["读取代码", "读取配置"],
      "output": "支持或排除各候选原因的证据与后续建议",
      "acceptance": "区分已证实原因、仅相关的现象和仍需验证的问题"
    }
  ]
}

运行时将 required_capabilities 映射到真实可用的工具，缺少对应能力时应明确报告。acceptance 声明验收条件，由已配置的检查逻辑、证据核对或人工判断实际验收。

计划如何进入执行循环

用户目标 + 约束 + 环境 + 能力
          ↓
LLM 提出候选计划
          ↓
程序校验格式、依赖、能力、范围与预算
          ↓
选取依赖已满足的步骤，构建局部上下文
          ↓
执行器运行 model → tool → model
          ↓
独立验收输出，保存证据与执行状态
          ↓
继续剩余步骤，必要时提出并校验新的剩余计划

运行时可以检查步骤 ID 是否唯一、依赖是否存在、图中是否有环，以及工具、权限和预算是否满足要求。目标覆盖和验收条件的含义通常还需要语义检查，结构化输出合法只能证明格式符合契约。

执行器收到当前子目标、必需的上游结果、用户约束和整体目标。局部上下文可以省去无关历史，同时保留仍然约束当前步骤的信息。

工具返回成功只说明调用的执行状态。步骤通过验收后才标记完成。如果调用超时且结果未知，应保留未知状态，先核对结果再决定是否重试。计划、操作记录与验收状态可保存在结构化任务状态或文件中。Todo 工具承担记录和更新职责，任务拆分与执行仍由规划和运行逻辑完成。

依赖与粒度如何影响并行

可将步骤及其依赖表示为有向无环图（DAG）。运行时选择依赖已满足的节点，等上游完成后再执行后续节点。没有相互依赖的步骤在其他执行条件满足时可以并行。

拆得太细会增加模型调用次数和总 token 消耗，还可能让每步丢失整体语境，造成产出衔接生硬。拆得太粗会增加单步的复杂度，故障也更难定位。按可验收的子目标划分步骤，明确职责、输入、产物和完成标准，并显式记录依赖。一个步骤内部可以包含多次模型或工具调用。

何时调整剩余计划

自适应拆分调整当前子任务的粒度。执行器先尝试完成当前任务，验收通过就继续。超过最大步数或质量未达标时，可以由规划器把该任务拆成更小的子任务，再逐个尝试和验收。

**重规划（Replan）**调整尚未执行的步骤。将当前结果和剩余计划交给规划器，后续步骤仍适用就继续执行，前提变化时则修订或插入步骤。每步检查一次会增加模型调用和 token 消耗，也可以只在执行失败、结果严重偏离预期、新证据推翻前提、资源缺失、用户修改目标或预算变化时触发。

修订后的计划仍需校验。保留已执行操作和已验收结果，只调整受影响的剩余工作。已有失败和写入都应留在记录中，供后续判断是否可以安全重试。

如何验证拆分结果

  • 完备性。将原始需求与计划逐项对照，确认所有要求都有步骤覆盖。
  • 独立性。各步职责边界清晰，避免重复工作浪费 token，或让多个产出给出相互冲突的判断。
  • 可验证性。为每步定义明确的完成标准，像为单元测试编写断言一样配对定义步骤与验收条件，为自动重试和质量控制提供依据。

如何评估 Agent 的效果

分层评估有助于判断故障出在模型调用、工具选择、上下文处理、任务规划还是最终交付。

环节 主要观察
模型调用 截断与服务错误、结构化输出合法性、时延和费用
工具调用 候选召回、工具选择、参数与业务含义是否正确
上下文管理 关键事实保留、约束违反、恢复能力与连续压缩后的质量
任务规划 目标覆盖、依赖错误、冗余步骤、重规划次数与验收通过率
整体任务 最终交付是否满足用户要求、实际副作用是否符合授权

返回了工具调用、生成了计划或成功生成摘要，都是中间结果。最终验收应检查交付产物、证据和业务条件，并统计整个任务的 token 消耗、耗时与费用。具体指标见 S04-Tool-Use#评估工具选择与描述 与 S02-Memory#如何评估压缩策略。

这些研究可作为推理与规划方法的参考。运行时仍负责状态管理和业务验收。ReAct、Plan-and-Solve Prompting
