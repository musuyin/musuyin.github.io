RAG

2026-09-07

#AI#Agent#Memory#RAG

理解主线

RAG 的检索目标是可追溯、权限正确且足够完整的证据。解析、分块、索引、召回、重排和上下文组装构成同一链路，任何一环丢掉来源或条件都可能影响回答。

RAG（检索增强生成）的完整流程

RAG 的关键不是“把文档放进向量数据库”这一步，而是构造一条能在用户提问时找回正确、完整、可追溯且能放入 Context的证据链。

离线建库：文档 → 解析与清洗 → 切分 → Embedding → 索引与存储

在线问答：问题 → 查询理解 → 检索 → 过滤/重排 → 组装 Context → 生成 → 引用与评估

离线建库：把文档变成可检索记录

文档解析、清洗与版本管理

原始资料可能是 Markdown、HTML、PDF、Word、表格、代码库或数据库记录。首先需要提取文本及其结构，并保留来源信息。

每份文档至少应保留：

  • 稳定的 document_id、来源 URI 或文件路径。
  • 标题层级、页码、段落位置、作者、创建与更新时间。
  • 权限、业务域、语言、标签等过滤条件。
  • 内容哈希（hash）与 Embedding 模型版本，用于增量更新和可复现性。

清洗不是无条件删内容。应删除网页导航、页眉页脚、重复模板和无意义空白；但表格标题、代码块、章节标题、单位、日期、权限标记往往是检索和引用所必需的结构信息。

Chunking（文档切分）

Embedding 模型通常有单次输入长度限制，且一整个长文档的单一向量会混合多个主题。因此要将文档切成 Chunk（片段）。

策略 做法 优点 风险
固定长度 按 Token 数切分，常配合重叠窗口。 实现简单、长度稳定。 可能在句子或主题中间切断。
递归结构切分 优先按标题、段落、句子逐级切。 更能保留语义边界。 格式差的文档效果不稳定。
语义切分 在主题相似度明显变化处切分。 片段主题更集中。 计算更贵，阈值难调。
父子切分 小 Chunk 用于检索，命中后返回其父段落或章节。 兼顾精确定位与上下文完整性。 需要维护父子关系。
文档类型专用切分 代码按函数/类，表格按行组，FAQ 按问答对。 符合数据结构。 需要针对格式实现解析器。

常见实践是以标题和段落为优先边界，再设定最大 Token 上限；对长段落用少量重叠保留跨边界语义。Chunk 过小会丢失上下文，过大则主题混杂、检索不精确，并挤占最终 Prompt 的空间。

一个可存储的 Chunk 可以抽象为：

{
  "id": "handbook:v3:chunk-042",
  "document_id": "handbook:v3",
  "parent_id": "handbook:v3:section-auth",
  "text": "认证令牌在过期前五分钟应主动刷新……",
  "metadata": {
    "title": "认证与会话",
    "source": "docs/handbook.md",
    "heading_path": ["开发手册", "认证与会话"],
    "updated_at": "2026-09-07",
    "access_level": "internal"
  }
}

Embedding（嵌入）如何把文本变成向量

Embedding 模型是一个编码器：输入一段 Token，经过神经网络的多层计算后，输出一个固定维度的实数数组，即向量。可写为：

v = f_embed(text)，其中 v ∈ ℝ^d

其中 d 是向量维度，例如几百到几千维。训练时，模型通过大量相似与不相似文本学习：语义相近的内容在向量空间中应更接近，语义无关的内容应更远。

“如何重置密码” ──Embedding──> [0.12, -0.03, 0.71, …]
“忘记密码怎么办” ─Embedding──> [0.10, -0.01, 0.69, …]
“本周天气” ─────Embedding──> [-0.54, 0.66, -0.18, …]

向量并不是把词逐字加密或压缩进去，通常无法从向量精确还原原文；它是为“相似性比较”学习出的数值表示。Embedding 也会丢失细节，尤其是精确编号、罕见专有名词、否定关系和复杂逻辑，因此不能只依赖向量检索。

构建索引时应固定或记录：

  • 使用的 Embedding 模型与版本；查询和文档通常应使用同一模型或明确兼容的模型。
  • 输入是否带标题、父级路径或文档类型前缀；这会改变向量语义。
  • 归一化方式、向量维度、切分版本和生成时间。
  • 失败重试、批处理、缓存和去重策略。

文档更新、切分策略变更或 Embedding 模型替换后，应按版本重新生成受影响 Chunk 的向量；不要把不同空间、不同维度的向量混在同一索引里比较。

向量数据库“长什么样”

概念上，它是“向量 + 原文或引用 + 元数据”的记录集合：

id:       handbook:v3:chunk-042
vector:   [0.12, -0.03, 0.71, ...]      # d 个浮点数
payload:  { text, source, heading_path, updated_at, access_level, ... }

真正的向量数据库通常还维护专门的近邻索引，而不只是把数组逐行存进关系数据库。常见索引思路包括：

索引 核心思想 取舍
精确搜索（Flat） 将查询向量与每个向量逐一比较。 结果精确；数据大时延迟高。
HNSW 构建多层近邻图，从少量入口跳转到接近查询的区域。 召回高、查询快；内存占用较大。
IVF 先把向量聚成簇，查询时只搜索最相关的若干簇。 节省搜索量；需调节簇数和探测数。
PQ 等量化 用更短编码近似表示向量。 节省内存与成本；会损失精度。

实际系统还需要元数据索引，例如先筛选 access_level = internal、language = zh 或某个租户，再做向量近邻搜索。先做权限过滤，再把文本送进模型，避免检索阶段发生越权泄露。

在线检索：从问题到证据

查询理解与向量化

用户问题也要用同一个或兼容的 Embedding 模型编码：

q = f_embed(query)

在此之前或之后，系统可能进行查询改写：补全省略的主语、把对话代词替换为实体、拆分多意图问题、生成同义检索词，或从用户权限中生成过滤条件。改写必须保留原意，并记录原问题，以便审计和调试。

向量相似度如何计算

设查询向量为 q，某个文档 Chunk 向量为 d。

余弦相似度（Cosine Similarity） 衡量两个方向是否接近：

cosine(q, d) = (q · d) / (||q|| × ||d||)

其中 q · d 是各维度相乘后求和，||q|| 和 ||d|| 是向量的长度。若向量已做 L2 单位归一化，余弦相似度就等于点积；此时欧氏距离与余弦排序也具有单调对应关系。

向量库通常使用近似最近邻搜索（ANN），不是与全部向量精确比较。它在很低延迟下返回“很可能最接近”的 Top-K 候选，并以少量理论精度换取速度和成本。关键调参是延迟、召回率、内存和索引构建时间之间的平衡。

稠密检索、关键词检索与混合检索

Embedding 产生的向量检索又称稠密检索（Dense Retrieval），擅长语义近义表达；传统 BM25、倒排索引等属于稀疏检索（Sparse Retrieval），擅长精确关键词、ID、错误码、函数名和罕见术语。

用户问题
 ├─ 稠密检索：理解“忘记密码”≈“重置凭证”
 ├─ BM25 检索：精确命中“ERR_AUTH_4017”
 └─ 融合排序：得到候选 Chunk 集合

生产 RAG 常使用混合检索。可用加权分数、倒数排名融合（RRF）等方法融合多个检索器，再进入重排阶段。这样既避免“只靠关键词看不懂同义表达”，也避免“只靠向量漏掉精确编号”。

过滤、重排与上下文组装

第一次召回通常取较多候选，例如 Top-20 或 Top-100；不能直接把它们全部塞入模型。后续流程通常是：

  1. 权限与元数据过滤：租户、用户角色、时间范围、文档状态、语言与业务域。
  2. 去重与多样化：避免同一段文字的重叠 Chunk 占满候选位。
  3. 重排（Reranking）：用更慢但更精确的模型同时阅读“问题 + 候选文本”，为候选重新打分。交叉编码器（Cross-encoder）常用于此处。
  4. 父级扩展：小 Chunk 命中后，取其父段、相邻段或结构化表格的必要部分，补足上下文。
  5. Context 编排：在 Token 预算内选择最相关、最新、可信且互补的证据，附上来源标识与清晰分隔。
  6. 生成与引用：要求模型仅依据提供证据回答；答案应携带文档链接、页码或 Chunk 标识，以便人复查。

“Top-K 相似”不等于“足以回答”。检索分数只是候选排序信号；重排、证据完整性与最终人工评估决定回答是否可靠。

生成阶段与拒答策略

最终 Prompt 往往包含系统规则、用户问题和检索到的资料。模型应把检索文本视为证据而非指令：资料中即使出现“忽略规则”，也不应改变 Agent 的权限或目标。

当没有检索到足够相关、可信的证据时，系统应明确说明“知识库中未找到依据”或请求补充信息，而不是编造答案或悄悄切换到不受控的数据源。对关键领域还可以设置最低相关性阈值、要求至少两个独立来源，或交由人工审批。

RAG 的效果评估与常见失败点

应将评估拆成检索与生成两层：

层次 要问的问题 常用指标或检查
切分与索引 正确答案所在片段是否被正确建库？ 覆盖率、重复率、更新延迟。
检索 正确证据是否进入 Top-K？ Recall@K 、MRR、nDCG。
重排 正确证据是否排在前面？ Precision@K 、nDCG、人工相关性标注。
生成 回答是否正确、完整且有依据？ 忠实度、引用正确率、人工评审。
端到端 用户能否完成任务？ 任务成功率、拒答正确率、延迟与成本。
现象 常见原因 优先检查
找不到明明存在的资料 切分破坏语义、未索引、查询改写错误、Embedding 不匹配。 文档版本、Chunk 文本、过滤条件、 Recall@K 。
找到的资料语义相近但答非所问 Chunk 主题过宽、向量模型不足、缺少关键词检索。 Chunk 大小、混合检索、重排。
回答引用了资料但结论仍错误 模型推理错误、证据不完整、Context 编排差。 父级扩展、提示词、答案与引用逐项对照。
回答过期 增量索引未更新、缓存未失效、旧版本未过滤。 文档哈希、更新时间、版本字段。
越权引用资料 检索后才做权限控制，或元数据错误。 查询前过滤、访问控制测试、审计日志。

RAG 复习要点

  • RAG 是“检索证据后再生成”，不是把知识永久塞进模型。
  • 文档切分应保留结构和来源；Chunk 大小、重叠和父子关系直接影响召回与答案完整性。
  • Embedding 将文本编码为向量，向量相近表示模型学习到的语义相近，但不保证精确事实或逻辑相同。
  • 向量数据库保存向量、原文/引用和元数据，并借助 ANN 索引高效近邻搜索。
  • 实用系统通常采用“稠密向量检索 + BM25 等关键词检索 + 重排”，而非单一相似度搜索。
  • 权限过滤、版本管理、引用、拒答和端到端评估是 RAG 可靠性的必要组成部分。

复习与应用

用一个跨段落问题检查分块边界；用一个已更新文档检查旧索引失效，再区分检索失败和生成忽略证据。
