Agent 工具调用

2026-10-28

#AI#Agent#Tool

理解主线

工具调用有模型契约与执行实现两部分：模型看到名称、描述和参数形状，运行时负责校验、授权、执行并回填结果。MCP 统一接入协议，不自动替 Host 完成权限控制。

从工具定义到真实执行

工具调用包含两份不同的东西：给模型看的能力契约，以及运行时真正执行的函数或远程服务。模型通常看到名称、description 和参数 schema，不会因为注册了工具就看到函数实现。

本地函数 / MCP tools/list
        ↓
运行时工具注册表：名称 → schema、实现、权限与行为属性
        ↓
按身份和当前任务筛选，适配为模型支持的工具定义
        ↓
模型请求：messages + tools
        ↓
模型响应：调用标识 + 工具名 + 参数
        ↓
运行时校验 → 调用实现 → 记录结果
        ↓
带对应调用标识的工具结果加入下一次模型请求

MCP 解决的是工具发现和远程调用协议。将 MCP schema 转换成模型输入、控制工具可见性和执行权限，仍由 Host / Agent 运行时负责。协议细节见 S00-基础概念。

工具列表如何交给模型

支持原生工具调用的模型 API 通常有与消息并列的 tools 一类字段，运行时把工具名称、description 和输入 schema 放进去。不同服务有不同包装结构，不能假设 MCP 的 inputSchema 响应可以原样直接发送。

底层服务会把这些定义转换为模型能够处理的输入表示。工具说明和 schema 消耗上下文，并非窗口之外的一本免费手册。

不支持原生工具调用的模型，可以通过文本列出工具并约定输出格式，但名称与参数解析更容易出错。支持原生接口时，应使用该接口及其校验机制。

下一次调用仍需要让模型访问当前可用的工具定义：可能由应用重新发送，也可能由服务的会话或引用机制保留。是否可以省略传输，要依据服务契约；不能假定“第一轮给过，之后就永远记住”。

工具调用与结果必须关联

一次模型响应可能含多个工具调用，运行时需要记录每个调用的 ID，并用它关联对应结果。不能只追加一段“查询成功”的普通文本，让模型猜它属于哪个调用。

压缩消息时也必须保留合法的调用与结果关系，不能留下孤立结果、遗漏需要返回的调用结果，或改变执行状态。

如果响应通过流式返回，参数可能分成多个 JSON 片段；应在调用参数完整且验证通过后才执行。多个调用能否并行，取决于是否存在数据依赖、共享状态和副作用，不是模型一次输出多个调用就一定能并行。

Description 与参数契约

描述帮助模型区分能力

Description 需要回答：工具做什么、适用于什么输入、与相似工具有何边界、返回什么，以及调用有什么副作用。写“查询数据”无法让模型区分查订单、查日志和查知识库。

例如，日志工具可以描述为：

查询指定服务在给定时间范围内的运行日志，用于定位异常和检查请求行为。仅检索日志，不查询业务订单；返回日志条目、是否截断及下一页游标，不直接给出故障根因。时间使用带时区的 ISO 8601 格式。

这一描述同时给出了适用范围、相邻能力边界、输入约定和输出含义。关键限制需要写清楚，但不应在每个工具里重复整份平台操作手册。

模型选择工具会综合名称、description、参数 schema、当前任务和历史结果，不能说它“完全只靠 description”。明确而有区分度的名称同样重要。

参数 Schema 减少含糊表达

下面是应用内部的工具目录示意，适配器会转换为所选模型服务的工具格式。其中 input_schema 不代表所有 API 使用同一个字段名。

{
  "name": "search_service_logs",
  "description": "检索指定服务与时间范围的运行日志，返回条目、截断状态和下一页游标；不查询业务订单，不修改服务。",
  "input_schema": {
    "type": "object",
    "properties": {
      "service": {
        "type": "string",
        "description": "准确的服务标识，不能用自然语言推测服务名"
      },
      "start_time": {
        "type": "string",
        "description": "包含时区的 ISO 8601 开始时间，例如 2026-10-28T09:00:00+08:00"
      },
      "end_time": {
        "type": "string",
        "description": "包含时区的 ISO 8601 结束时间，必须晚于开始时间"
      },
      "level": {
        "type": "string",
        "enum": ["all", "error", "warn", "info"]
      },
      "limit": {
        "type": "integer",
        "minimum": 1,
        "maximum": 100
      }
    },
    "required": ["service", "start_time", "end_time", "level", "limit"],
    "additionalProperties": false
  }
}

字段应说明标识符来源、单位、格式、范围及必填性。枚举比“填写适当的状态”更清楚，明确时区比“传一个时间”更清楚。

这个 schema 仍不能独自保证服务存在、时间真实合法或当前身份有访问权，运行时必须检查。不同服务支持的 JSON Schema 子集也不同，应在工具注册时验证兼容性。

能由运行时确定的租户、当前用户和认证信息，不应让模型填入；由可信身份上下文绑定。工具也应避免要求模型复制大段可以通过稳定 ID 引用的数据。

输出也是工具契约的一部分

工具结果最好明确返回数据、执行状态、数据来源及完整性，例如：

{
  "status": "ok",
  "entries": [],
  "truncated": false,
  "next_cursor": null,
  "query_id": "日志系统实际返回的查询标识"
}

这里的空数组表示检索范围内没有匹配项。它与查询失败不同；truncated: true 则表示结果不完整，不能据此判断“没有其他异常”。示例字段应按实际工具能力实现，不得编造查询标识或截断状态。

输出过大时，优先在工具设计中支持筛选、分页和按范围读取。完整结果需要留存时，可以返回持久化引用与有限预览，同时明确省略了多少内容；不能悄悄截断后伪装成完整结果。

工具过多时如何组织

工具多带来的问题有两类：schema 占用输入预算，以及相似能力增加选择混淆。没有一个适用于所有模型的固定安全数量，需要同时考察总 token、工具相似度和任务成功率。

方法 实现方式 代价与验证点
按身份过滤 先剔除当前身份不可使用的工具 可见性控制不能替代执行时鉴权
按任务范围分组 当前查日志只加载日志、指标等相关工具 范围判断错误会使需要的工具缺席
候选检索 根据工具名称、简述和 schema 建索引，为任务选候选集 必须评估需要的工具是否被召回
按需发现 常驻少量基础工具与发现工具，发现后加载完整 schema 多一次调用，还要明确加载到哪一轮生效
调整工具边界 合并重复能力，让一个工具用明确参数处理同类操作 不应合并成可任意执行的万能接口

按需发现可以这样工作：模型先调用“查找日志相关工具”，运行时返回候选名称和简述，选择后将完整 schema 注册到后续请求；或者运行时直接检索并加载候选。这是应用明确实现的流程，不是模型凭工具名字自动获得远程能力。

未进入完整可用集合的工具不能直接执行。模型提出未注册或当前不可用的名称时，应报告明确错误，而不能模糊匹配到名字相似的另一个工具。

筛选工具时不能只使用最初的用户问题。任务执行会产生新信息，应结合当前子目标、已确认事实和计划依赖决定可用工具；“查完日志后需要读代码”的能力变化要在下一次请求前反映出来。

评估工具选择与描述

用有明确正确动作的任务集比较 description 和筛选策略，任务既要包含需要调用的场景，也要包含应直接回答或信息不足的场景。

  • 候选召回率：完成当前任务需要的工具是否进入可用集合；多步骤任务应检查关键工具是否全部覆盖。
  • 工具选择正确率：模型是否选了适合当前动作的工具，而不是名称相似的工具。
  • 参数正确率：schema 校验通过之后，ID、时间、单位等业务含义是否正确。
  • 不必要调用比例、完成步数、时延、每个成功任务的费用。
  • 最终任务成功率：工具调用有效不代表故障诊断、订单查询等目标已经完成。

可以专门构造“查订单”和“查订单日志”等相邻工具的区分样例。改善描述的目标是减少真实混淆，不是单纯让 description 更长。

运行时校验与失败语义

模型提出的是调用意图，运行时负责验证名称、参数结构、业务规则、身份与权限，然后才执行工具。工具 schema 即使受到生成约束，也不能代替这些验证。

错误需要明确分类，例如无效参数、认证失败、没有权限、资源不存在、服务超时，以及执行结果未知。不得把异常转换成空结果或“成功但无数据”。

参数错误可以作为带原调用 ID 的明确错误反馈给模型，让它在允许的预算内修正；认证、权限和业务失败则按应用定义的终止或恢复协议处理。任何重试都需要明确触发条件、次数限制和可观察的结果，不应自动掩盖失败。

特别是写入类操作：超时只说明没有收到结果，不证明服务没有完成写入。重试前需要幂等键、操作记录或状态查询；不能因为模型“再试一次”就重复创建、扣款或发送。

工具返回里的指令式文本只是外部数据，不能自动变成平台规则。工具 description 也不是权限授予，真正的访问范围由运行时和服务端控制。

复习与应用

追踪一项工具从服务端 Schema 到模型 tools 字段，再到 handler 和结果消息；每个转换都应保留调用标识与错误语义。
