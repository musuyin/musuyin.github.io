Agent 模型调用

2026-10-28

#AI#Agent#LLM

理解主线

一次模型请求由消息、工具定义和生成配置共同组成。上下文由应用或服务会话机制显式维护，不能因为模型名称相同就假设它记得上一轮，也不能把输出上限当作输入窗口。

模型调用在 Agent 中的位置

Agent 的循环是：运行时组装输入 → 模型提出下一步动作或回答 → 运行时执行工具 → 将结果加入下一次输入。模型调用本身只负责一次推断，不负责持久化历史、真正执行工具或确认业务完成。

一次请求通常由三部分组成：带角色的消息、当前可用的工具定义，以及模型与生成参数。多轮状态需要通过重新传入消息，或通过服务提供的会话、响应引用机制保留；不能因为调用的是同一个模型，就认为模型自动记得上一轮。

相关内容：S01-Agent、S04-Tool-Use、S02-Memory。

上下文窗口与应用预算

模型上限不等于应用配置

上下文窗口是模型服务在某种模型和部署配置下支持的 token 上限。托管模型通常不能通过任意设置一个 context_window 参数，把服务支持的窗口扩大。自托管推理服务可能允许配置最大序列长度，但还受模型训练、位置编码、显存和服务实现约束，增大配置不保证长文本质量。

应用真正控制的是：选哪个模型、给本次输入分配多少 token、为输出留多少空间，以及达到什么预算时触发裁剪或压缩。框架里叫作 context_window 的配置，也可能只是预算计算所用的模型能力元数据，需要检查它是否真的被发给服务端。

输入不仅包含用户问题，还包括 system/developer 指令、工具 schema、历史消息、工具结果、检索片段及多模态内容。中文字符数不等于 token 数，JSON 的标点和字段名同样有成本。

每次请求如何计算预算

对于输入与输出共享窗口上限的服务，可以用以下约束做预算：

T_input + R_output + S <= C_model
T_input <= B_app

T_input = T_instructions + T_tools + T_history + T_retrieved + T_current
符号 含义 谁决定
C_model 当前模型服务支持的上下文上限 模型服务
B_app 应用允许本次输入使用的预算 应用开发者
R_output 本次输出预留量 应用配置，受服务输出上限限制
S 计数误差、封装开销等安全余量 应用开发者
T_input 实际序列化后输入的 token 数 本次请求内容

一些服务还有独立的输入上限、输出上限或不同的推理 token 计费规则，应按服务的实际契约校验，不能只套一个公式。

例如，假设服务窗口是 128,000 token，应用输入预算是 90,000，输出预留 4,000，安全余量 8,000，那么输入必须满足 T_input <= min(90,000, 116,000)。这里的 90,000 是应用主动限制输入的预算，不是把模型改成了 90,000 token 的窗口；这些数值只是演示计算，不能直接当作生产默认值。

压缩触发点应低于硬上限，还要为下一步可能返回的大工具结果留空间。输入已超限时，再把全部历史发给相同窗口的模型做摘要，摘要请求也可能失败。具体处理见 S02-Memory。

为什么不把窗口尽量填满

窗口够大只说明请求能被接收，不说明模型能够稳定利用每个细节。无关历史、重复日志和相似工具会增加干扰；某些长上下文任务还会出现中间信息利用率下降的问题。

更长的输入通常增加计算、延迟和费用，具体还受模型架构及缓存影响。因此应比较“保留了什么证据、任务是否完成”，而不只是“用了多少窗口”。

生成参数如何选择

不同服务的字段名称、支持范围和默认值不同。下面讨论的是参数的作用，不是一份可直接复制到任意 SDK 的请求。

参数类别 控制什么 Agent 中的设置依据 容易误解的地方
模型选择 能力、窗口、延迟、价格 用真实任务比较工具选择、参数正确率和最终成功率 模型更大不保证每种任务都更合适
输出 token 上限 本次最多生成多少内容 工具参数生成通常短；长报告和复杂推理需要更多空间 输出上限不等于输入窗口，也不保证模型一定用满
temperature 采样分布的尖锐程度 对结构化提取、工具参数可评估较低值；开放式创作可评估较高值 设为 0 不等于事实正确，也不保证跨服务完全确定
top_p 从累计概率达到阈值的候选 token 集合采样 通常先保留默认值，调 temperature 或 top_p 中的一项 同时调两项会让效果变化更难归因
推理强度或预算 部分模型支持的额外推理投入 对困难规划和诊断比较成功率、时延和费用 不是所有模型支持，也不等于要求输出完整思维过程
工具选择策略 可自由选择、必须调用、指定工具或禁用工具 普通执行允许选择；需要特定动作时显式限定 强制调用工具不证明业务上应该调用，也不代表参数正确
结构化输出约束 输出字段和类型 计划、分类结果等适合使用受支持的 schema 约束 结构合法不等于计划合理或事实真实
流式输出 是否分片接收响应 便于展示进度、降低首段等待时间 不完整的参数片段不能直接执行

工具 schema 的生成约束与普通文本结构化输出不是完全相同的机制，需要分别检查服务支持情况。部分推理模型不开放 temperature、top_p，不能照搬普通模型的参数。

输出上限应覆盖参数或计划的完整生成；过小可能截断 JSON。若服务返回长度截断、拒绝或错误，运行时必须识别对应状态，不能把“没有工具调用”一律视为任务成功。

从任务分布确定参数

先构造一组真实代表性任务，包含简单查询、复杂参数、长历史和多步骤任务，再固定工具和上下文策略，逐项调整参数。

观察工具选对率、参数校验通过率、业务验收通过率、平均与 P95 延迟、每个成功任务的成本。单次演示成功不足以确定配置，应重复运行观察波动。

低 temperature 的配置可以减少某些输出变化，但无法替代 schema 校验、权限校验和结果验收。参数调优解决的是模型行为分布，运行时校验解决的是可执行性与边界。

请求组装与响应处理

下面是应用自己的配置和接口示意，不对应某家模型 API 的固定字段。adapter 负责把这些概念转换成所选服务实际支持的请求格式，不能把这些配置键直接发给任意服务。

config = {
    "model_id": "应用已配置的模型标识",
    "input_budget_tokens": 90_000,
    "output_reserve_tokens": 4_000,
    "safety_margin_tokens": 8_000,
}

request = adapter.build_request(
    model_id=config["model_id"],
    messages=active_messages,
    tools=selected_tool_schemas,
    output_limit=config["output_reserve_tokens"],
)

# 必须按包含工具定义和消息封装的实际请求计数；无法满足预算则显式报错。
validate_request_budget(request, config, model_capabilities)
response = adapter.invoke(request)

# 识别完整输出、工具调用、截断、拒绝与服务错误。
validated_response = validate_complete_response(response)
event_log.append(validated_response)

这里没有直接执行工具：工具调用的名称、参数、身份与权限还需要运行时验证。模型返回最终文本后，也需要结合任务验收判断完成，而不能只检查文本里是否写了“已完成”。

Token 计数与缓存

优先使用服务提供的计数接口或适配当前模型的 tokenizer。仅按字符数估算可以作为早期预警，但不能当作精确计数；消息封装、工具格式和多模态输入可能带来额外成本。

服务返回的 usage 适合用于校准估算和统计成本，但它是在请求后拿到的，不能替代调用前的超限检查。

Prompt cache 可以在条件满足时减少重复前缀的计算或计费，但缓存命中的内容仍属于逻辑上下文，不能因此超出窗口。缓存也不是长期记忆：它不负责选择重要事实、处理记忆冲突或保证未来能召回。

复习与应用

区分窗口容量、当前输入、输出预算和缓存；用真实任务分布评价工具选择、延迟与成本，避免从一次演示推断可靠性。
