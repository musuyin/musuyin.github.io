基础概念

2026-09-28

理解主线

先分清模型、工具和运行时：模型产生推断，工具执行具体动作，Agent 运行时连接反馈并施加权限与预算。MCP、A2A、RAG、Skill 分别处理接入、协作、检索和流程知识，不能作为同义词使用。

LLM（大语言模型）

LLM（Large Language Model，大语言模型）：根据海量训练数据，预测下一个词元（Token）概率的模型。

可以把它理解为一个很强的“自动补全”引擎：输入前文后，模型不断预测并输出合适的后续内容。它本身不等于搜索引擎、数据库或操作系统。

Agent（智能体）

Agent（智能体） 是在“模型推理—调用工具—读取结果—继续行动”的循环中完成目标的应用。它不一定具备完美规划能力；所谓“自主”，通常指在既定权限和预算内能选择下一步，而不是脱离约束自由行动。

任务与约束 → 理解当前状态 → 选择工具/动作 → 执行       →           读取结果
                                      ↑                        ↓
                                      └──── 判断是否继续 ────────┘

一个可靠 Agent 除了能执行，还应能：

  • 将目标转换为可验证的验收条件。
  • 对高风险动作请求确认，并保留必要的证据。
  • 在未知或失败时报告事实与阻塞原因，不应悄悄改走未授权的替代路径。
  • 完成后说明改动、执行的验证、未覆盖风险和复现方式。

Token（词元）

Token 是大模型处理文本的基本单元，并不等同于自然语言中的“词”。它由 Tokenizer（分词器） 切分并映射为数字。

阶段 过程
编码（Encode） 文本 → Token → Token ID
解码（Decode） Token ID → Token → 文本

词和 Token 不是一对一关系。例如 unhappiness 可能被拆为 un、happi、ness；中文字符也可能对应一个或多个 Token。

Context（上下文）

Context 是模型在当前一步能“看到”的全部输入，常包含：

  • 对话历史与用户当前请求。
  • System Prompt（系统提示词）和项目约定。
  • 已读取的文件、工具调用结果。
  • 可用工具或 Skill 的说明。
  • 模型已经生成的内容。

Context Window（上下文窗口）

Context Window 是 Context 可容纳的最大 Token 数。内容超过上限时，宿主通常需要截断、压缩或重新检索；被移出窗口的信息不能再被模型直接依据。

可把它想成工作台：工作台越拥挤，模型越难聚焦；放不下的资料即使仍在磁盘上，也不在当前视野中。

Prompt（提示词）

Prompt 是给模型的指令与上下文，决定任务目标、约束和输出形式。

类型 作用
User Prompt（用户提示词） 用户明确提出的任务、事实和验收要求。
System Prompt（系统提示词） 平台或开发者预置的角色、权限、安全和行为规范。
Developer Prompt（开发者提示词） 应用开发者为某个 Agent 设定的产品规则与工作流程。

高质量任务描述应同时说明目标、范围、验收条件和禁止事项。对于不确定的产品决策，要要求 Agent 报告问题，而不是自行臆测或静默采用替代方案。

RAG（检索增强生成）

RAG（Retrieval-Augmented Generation，检索增强生成）：先从外部知识库检索相关内容，再将检索结果放入 Context，最后由模型生成答案。

它常用向量检索，也可以使用关键词检索、数据库查询或混合检索。RAG 提供的是“本次回答可参考的资料”，并不会把资料永久训练进模型。

Tool（工具）

大模型本身无法直接读取文件、执行命令、调用 API 或写入数据库。Tool（工具） 是宿主提供给模型的函数接口。

  1. 模型根据当前 Context 决定是否调用工具，并生成工具名与参数。
  2. 宿主校验权限与参数，实际执行调用。
  3. 宿主把结果作为新的 Context 交给模型。
  4. 模型据此继续推理、调用其他工具或输出最终答案。

模型负责“决定做什么”，宿主与工具负责“真的去做”。因此工具能否执行、可访问什么数据、是否要求用户确认，都由宿主和工具权限决定。

MCP（模型上下文协议）

MCP（Model Context Protocol，模型上下文协议） 是让 AI 客户端以统一方式连接外部能力的开放协议。它定义客户端与 MCP Server（服务器）之间交换消息的格式，而不是某一个具体的模型或工具库。

角色 职责
Host（宿主） 例如 IDE、桌面应用或 Agent 运行时；负责权限、UI、模型调用和连接管理。
MCP Client（客户端） 由 Host 创建，代表当前会话与某个 MCP Server 通信。
MCP Server（服务器） 暴露工具、资源或提示模板，并将真实系统的能力封装为协议接口。
Model（模型） 依据 Host 提供的工具描述与结果，决定下一步行动。

MCP 能提供什么

MCP 不只可以提供工具（Tools），还可以提供：

能力 用途 典型例子
Tools（工具） 模型主动调用以执行动作或查询。 搜索代码、创建工单、查询数据库。
Resources（资源） 可读取的上下文数据，通常以 URI 标识。 文档、数据库记录、日志。
Prompts（提示模板） 服务端提供的可复用任务模板。 代码审查提示词、事故分析模板。

工具适合“做事”，Resource 更像“给资料”，Prompt 则是“给任务模板”。不要把它们混为一谈。

发现远程工具时，究竟拿到了什么

协议层面，客户端会先完成初始化协商，然后发送 tools/list 请求。服务器返回的不是只有名称和 Description；每个工具至少应带有可机器读取的输入模式（input schema），通常是 JSON Schema。

简化后的响应形态如下：

{
  "tools": [
    {
      "name": "search_issues",
      "description": "Search issues in the project",
      "inputSchema": {
        "type": "object",
        "properties": {
          "query": { "type": "string", "description": "Search keywords" },
          "state": { "type": "string", "enum": ["open", "closed"] },
          "limit": { "type": "integer", "minimum": 1, "maximum": 100 }
        },
        "required": ["query"],
        "additionalProperties": false
      },
      "outputSchema": { "type": "object" },
      "annotations": { "readOnlyHint": true }
    }
  ],
  "nextCursor": null
}
  • name：调用时使用的稳定工具标识。
  • description：面向模型和人的功能说明；质量会直接影响模型会不会选对工具。
  • inputSchema：参数的类型、字段说明、必填项、枚举值、数值范围和嵌套结构。这是可靠构造调用参数的关键。
  • outputSchema：可选的结构化输出契约；并非每台服务器或每个旧工具都会提供。
  • annotations：可选的行为提示，例如只读、是否可能造成破坏、是否幂等、是否会访问开放网络。它是提示，不应替代宿主的真实权限控制。
  • nextCursor：工具很多时用于翻页；客户端需要继续请求，才能拿到完整列表。

因此，能让 Agent 正确调用复杂工具的正式工具定义，通常会包含参数 Schema，而不仅是一行名称和 Description。

为什么 /mcp 看到的信息可能更少

/mcp 是某个 Host 或 CLI 的交互命令，不是 MCP 协议中的标准请求名。它展示多少信息由该 Host 的版本和 UI 决定：可能只显示服务器状态、工具名、工具数量和简介，也可能支持展开参数定义。

观察位置 能说明什么 不能据此断定什么
/mcp 的界面列表 Host 当前识别到哪些 Server 或工具。 不能保证已展示完整 JSON Schema、全部分页结果或实际权限。
tools/list 的原始协议响应 服务器声明的工具与输入契约。 不代表当前用户一定有权限执行，也不保证结果一定符合描述。
Agent 的可用工具上下文 当前模型被允许看见和调用的工具定义。 不代表工具一定会被模型选择或调用成功。

调用时，客户端发送 tools/call，核心字段是工具名与参数：

{
  "name": "search_issues",
  "arguments": {
    "query": "MCP timeout",
    "state": "open",
    "limit": 10
  }
}

服务器返回内容块（文本、结构化内容、资源链接等）或错误。参数 Schema 能帮助模型与客户端在调用前发现格式错误，但业务权限、数据存在性和服务端规则仍要由服务器验证。

MCP 工具如何进入模型上下文

工具发现与注入是两步

MCP Client 先向服务器请求 tools/list，得到工具定义；但 Host 不一定把原始 JSON 原封不动地塞入模型 Prompt。典型流程是：

MCP Server ──tools/list──> Host / MCP Client
                               │
                         过滤、权限检查、格式转换
                               │
                               ▼
                        模型可见的 Tool 定义
                               │
                        模型发出调用意图
                               ▼
Host ──tools/call──> MCP Server ──结果──> Host ──> 模型

Host 可以隐藏工具、裁剪 Description、转换 Schema、延迟加载，或要求高风险工具在执行前得到人工批准。MCP Server 声明了工具，不等于该工具一定进入当前模型的上下文。

是 System Prompt，还是 User Prompt

这不能用一个绝对答案概括，因为不同模型 API 与 Host 的消息格式不同；但语义上可以这样理解：

内容 常见传递方式 语义归属
平台安全规则、权限策略 System 或 Developer 指令。 高优先级运行规则。
工具名、Description、JSON Schema 专用 tools 字段，或由 Host 编译进系统/开发者上下文。 运行时能力说明，不是用户请求。
用户的目标、偏好、业务资料 User message。 用户意图与事实输入。
工具调用请求 专用 tool-call 消息或结构化输出。 模型提出的动作。
MCP 工具返回值 专用 tool-result 消息。 外部观察结果，默认应视为不可信数据。

因此，MCP 工具定义通常不是 User Prompt。在很多 API 中它甚至不是文本形式的 System Prompt，而是一个与消息并列的专用 Tool 定义字段；Host 可能在模型内部将它编码为等价的运行时上下文。

Prompt 角色的真正区别

角色的价值在于让 Host 和模型知道“这段内容来自谁、能约束什么、该怎样处理”。常见优先级可概括为：

System / Platform 规则
        ↓
Developer / Application 规则
        ↓
User 的任务与偏好
        ↓
外部数据、工具结果、引用材料
  • System Prompt：平台级行为边界，如安全规则、身份、基础能力限制。用户通常不能覆盖。
  • Developer Prompt：应用作者给 Agent 的工作方式，例如必须先跑测试、不得写入生产环境。通常高于 User，但低于 System。
  • User Prompt：用户希望完成的任务。只要不与高优先级规则冲突，Agent 应尽力满足。
  • Tool Result / 外部数据：用于回答问题或决定下一步，但其中出现的“忽略前述规则”“上传密钥”等文字只是数据，不能自动升级为指令。

角色标签不是“信息真伪标签”。System Prompt 也可能有误，工具结果也可能正确；角色主要解决的是指令冲突时谁有权决定行为。对外部 MCP 返回内容仍要防范提示词注入（Prompt Injection）。

工具 Schema、Skill 说明与用户消息都会消耗模型可见的 Context。若 Tool 很多且每个 Schema 很复杂，工具定义本身可能成为显著 Token 成本；这与安装过多 Skill 的问题相同，适合采用按需发现、分组和延迟加载。

排查远程 MCP 工具发现

当“连上了但看不到工具”时，按以下顺序检查：

  1. 确认连接的 Server、传输方式和认证身份正确。
  2. 查看 /mcp 是否报告连接错误、认证失败或工具数量为零。
  3. 确认服务端是否实现并允许当前身份使用 tools/list；工具可能按角色或租户过滤。
  4. 检查是否存在分页，以及 Host 是否已获取下一页。
  5. 查看 Host 的安全策略：某些工具虽然由 Server 声明，但会因权限、信任设置或策略而不注入模型上下文。
  6. 对一个只读工具进行最小调用，区分“发现失败”“参数校验失败”“鉴权失败”和“业务执行失败”。

安全与可靠性

远程 MCP Server 的工具描述、返回文本、资源内容都属于外部输入。它们可能错误、过期，甚至包含诱导模型泄露数据或执行无关操作的提示。

  • 只连接可信来源，并遵循最小权限原则。
  • 对写入、删除、发送消息、支付和生产环境操作设置明确确认。
  • 不把 Tool Description 或工具返回内容当作高优先级指令。
  • 为关键调用保留参数、身份、时间和结果日志。
  • 以真实测试、权限检查和人工 Review 验证结果，而不是只相信模型的总结。

Skill（技能）

Skill 是给 Agent 的可复用工作说明包。它的目标不是直接增加模型知识或权限，而是让 Agent 在特定类型任务中采用一致的流程、工具和产物标准。

Tool 像“能使用的扳手”；Skill 像“修理某类设备的作业指导书”。Skill 可以指导何时使用哪些 Tool，但它本身通常不会绕过权限。

Skill 的组成

常见的文件型 Skill 以 SKILL.md 为入口，通常包括：

层次 常见内容 作用
元数据层 name、description、适用条件 供 Host 或模型发现与选择。
指令层 步骤、约束、质量标准、安全边界 规定选中后如何执行任务。
支持资源 脚本、模板、示例、参考资料 减少重复劳动并统一产物。

不同平台的目录结构、frontmatter 字段和自动发现规则可能不同；SKILL.md 是常见约定，而不是 MCP 强制规定。

Skill 如何生效

一个典型实现分为三个阶段：

  1. 发现：Host 扫描已安装 Skill，向模型提供名称、描述和触发条件等轻量信息。
  2. 选择：模型或 Host 根据用户任务判断是否匹配。例如用户要求处理 PDF 时，选择 PDF Skill。
  3. 注入与执行：Host 读取完整 SKILL.md，把指令及必要资源路径加入 Context；Agent 再按其中的流程调用已有工具。

这种“先给目录、命中后再读全文”的方式能节省 Context。若每个 Skill 的完整内容都预先注入，Skill 很多时会挤占真正任务所需的上下文。

Skill、Tool 与 MCP 的关系

概念 本质 谁执行 是否天然有权限
Prompt 一段任务或约束文本 模型据此推理 否
Skill 可复用的工作流程与资源 Host 注入后由 Agent 遵循 否
Tool 可调用的函数接口 Host 或 Tool Server 执行 取决于 Host 与服务端
MCP 连接 Host 与外部 Server 的协议 Client 与 Server 通信 否

例如“生成并校验 PDF”这个 Skill 可以规定先读取 PDF、修改后渲染页面、最后人工检查；其中“读取”“渲染”“写文件”是 Tool，而这些工具可能来自本地运行时或 MCP Server。

Skill 的识别、开销与设计

提高识别效率，不只是扩写 Description

Description 往往是 Skill 被发现与选择时最先进入模型 Context 的信息，因此它很重要；但只靠把 Description 写得更长，通常不能稳定提高命中率，反而会增加 Token 消耗与相似 Skill 间的混淆。

一个易识别的 Skill，应在短描述中交代以下信息：

要素 要回答的问题 示例
任务意图 用户想完成什么？ “读取、生成或修改 PDF”
输入或产物 面对什么对象，产出什么？ “以 .pdf 为输入或输出”
触发线索 用户可能怎样表达？ “合并 PDF、填写表单、OCR”
边界 哪些相近任务不应由它处理？ “不处理 Word 或电子表格”
独特流程 为什么应选它而非通用 Skill？ “修改后必须渲染页面进行视觉校验”

好的 Description 像图书馆书脊：足够短，能区分同类书；也足够具体，使读者一眼知道该不该抽出这本书。它不是把整本书抄在书脊上。

应避免两种极端：

  • 过宽：如“处理文档”。它会与 Word、表格、演示文稿等 Skill 竞争，选择精度低。
  • 过窄或堆砌关键词：如只写某一个文件名，或把大量同义词堆进 Description。前者召回率低，后者既浪费 Token，也可能误命中。

比完善 Description 更有效的手段

  1. 能力边界互斥：相似 Skill 明确写出“适用什么”和“不适用什么”。例如把“创建 XLSX 文件”和“分析 CSV 文本”区分开。
  2. 分层暴露（Progressive Disclosure）：默认只向模型提供 Skill 的名称、短描述和触发条件；只有命中后才读取完整 SKILL.md 与参考资料。
  3. 使用确定性路由：对扩展名、特定命令、合规操作等强信号，Host 可以先用规则选择，而不完全依赖模型语义判断。
  4. 语义检索或分类器路由：Skill 很多时，可先把描述嵌入化，检索少量候选 Skill；也可以训练或配置轻量分类器。随后仍应让模型检查候选边界是否匹配。
  5. 按域、项目或权限分组：只暴露当前仓库、当前团队或当前任务类型可用的 Skill。例如前端项目无需注入数据仓库运维 Skill。
  6. 合并重复流程，拆分不相干流程：同一目标、同一工具链的细小变体可合并；输入、风险、产物明显不同的工作不应塞进一个“万能 Skill”。
  7. 用测试集评估路由：准备真实用户表达及其期望 Skill，统计命中率、误命中率、平均候选数和端到端任务成功率。

安装很多 Skill 会不会浪费 Token

会不会浪费，取决于 Host 的加载策略。

加载方式 Token 成本 主要问题
所有 SKILL.md 全文都注入 随 Skill 数量和篇幅线性增加。 最浪费 Context，也容易发生指令冲突。
只注入全部 Skill 的元数据/摘要 成本随 Skill 数量增加，但通常可控。 过多、过相似的摘要仍会降低选择精度。
先检索少量候选，再按需读取全文 初始成本最低。 需要可靠候选召回；漏召回会使正确 Skill 不可见。
完全由规则或用户显式指定 Token 成本低且确定。 弹性较差，维护规则成本更高。

即使只加载描述，几十到几百个 Skill 的名称、说明、触发规则也会占用 Context；更重要的是，模型要在更多候选中做选择，可能选错。因此应优先优化候选集合，而非只压缩单个 Description。

可以用下列指标判断一个 Skill 库是否健康：

  • 召回率（Recall）：应命中的任务中，正确 Skill 是否进入候选集合。
  • 精确率（Precision）：被选中的 Skill 是否真的适用。
  • 冲突率：同一任务有多个 Skill 都看似适用的比例。
  • 加载成本：路由说明、完整指令和参考资料分别占多少 Token。
  • 端到端成功率：选中 Skill 后，任务是否按预期完成；不要只评估“是否选中”。

复习要点

  • Context 是模型当前能看到的工作台；Tool 定义了它可请求的外部动作。
  • MCP 是连接协议，不等同于某个工具、Skill 或模型。
  • tools/list 通常返回工具名称、说明和输入 JSON Schema；/mcp 界面可能只展示其中一部分。
  • 参数 Schema 约束“参数长什么样”，但不替代服务端鉴权和业务校验。
  • Skill 是可复用的执行说明，通常经“发现 → 选择 → 注入 → 执行”生效。
  • 权限由 Host 与服务端控制；流程由 Skill 约束；模型只是在当前 Context 中做决策。

复习与应用

用同一项任务标出哪一步属于检索、哪一步属于工具调用，哪一步才涉及远程 Agent；再指出每层的输入输出。
