Hello World

2026-09-18

#AI#Agent

理解主线

跨语言互操作依赖线上契约：字段、方法、状态机、错误与流事件都必须一致。SDK 是语言适配层，注册、健康与路由是控制面，两者都不能替代协议本身的兼容测试。

结论：A2A 的边界应当是“协议”，不是 SDK

一个可互操作的 A2A 系统可拆成四层：

┌─────────────────────────────────────────────────────────────┐
│  业务层：Agent runtime / LLM / tools / memory / workflow     │
│  （语言和框架可以完全不同）                                   │
├─────────────────────────────────────────────────────────────┤
│  A2A 运行时语义：任务状态机、取消、超时、幂等、流式事件、授权  │
├─────────────────────────────────────────────────────────────┤
│  A2A 规范层：Agent Card、Task、Message、Artifact、Error      │
│  （JSON Schema / OpenAPI / protobuf 等可机器校验的契约）       │
├─────────────────────────────────────────────────────────────┤
│  传输层：HTTPS + JSON-RPC/HTTP；SSE 或 WebSocket 流式传输     │
├─────────────────────────────────────────────────────────────┤
│  基础设施：发现、路由、负载均衡、健康检查、可观测、安全        │
└─────────────────────────────────────────────────────────────┘

语言无关性的关键约束：

  1. 线上只传递标准化字节序列：HTTP header、URL、JSON（或 protobuf）；绝不能把 Python dataclass、异常类型、async generator 等内部对象当作协议。
  2. 先发布 schema 再生成 SDK：JSON Schema / OpenAPI 是契约源；各语言 SDK 只是其便利封装，不能反过来定义契约。
  3. 消息字段、枚举、状态转移、错误码、版本兼容规则必须确定：否则不同实现即便都“使用 JSON”，仍然无法正确互通。
  4. 业务 Agent 是可替换适配器：A2A server 只要求它满足运行接口（执行、可选流式执行、取消、描述能力），不依赖其使用哪个模型、工具框架或编程语言。

当前实现的职责地图

文件 当前责任 可抽取的语言无关能力
models.py AgentCard、Capability、TaskCard、TaskResult、流事件及能力版本判断 规范数据模型与能力协商
server.py HTTP 服务；Agent Card、健康检查、执行入口、SSE 输出 A2A 服务端传输适配器
client.py 获取 Agent Card、调用远端 Agent、解析 SSE A2A 客户端传输适配器
discovery.py 进程内注册表、TTL、心跳、健康评分 服务发现与活性管理
router.py 按能力筛选 Agent、备选节点、路由历史 控制面路由决策
load_balancer.py 轮询、最少请求、随机、指标 候选节点选择与流量分配

这形成了合理的雏形：

调用方
  │ ① discover / 查注册表
  ▼
Router ──按 capability、status、health、load 选择──► Agent Card(url)
  │                                                        │
  │ ② HTTPS JSON-RPC                                      │
  ▼                                                        ▼
A2A Client ─────────────────────────────────────────► A2A Server
                                                         │
                                                         ▼
                                                    Agent Runtime
                                                         │
                             ③ JSON 响应或 SSE 事件 ◄─────┘

其中，AgentCard 是控制面的“服务描述”；任务调用和事件流是数据面；注册、心跳、负载指标则是可靠性基础设施。

先定义规范：跨语言互通所需的最小契约

Agent Card：发现与能力协商

仓库的 AgentCard 已包含名称、说明、版本、URL、状态、能力、并发上限和 metadata。对外应固定为 JSON 文档（如 GET /.well-known/agent.json），而不是语言对象。

建议最小格式：

{
  "protocolVersion": "1.0",
  "name": "code-reviewer",
  "description": "Reviews pull requests",
  "endpoint": "https://review.example.com/a2a",
  "supportedTransports": ["jsonrpc-http", "sse"],
  "capabilities": [
    {
      "id": "code_review",
      "version": "2.1.0",
      "description": "Review code changes",
      "inputSchema": {"$ref": "https://example.com/schema/review-input.json"},
      "outputSchema": {"$ref": "https://example.com/schema/review-output.json"}
    }
  ],
  "limits": {"maxConcurrentTasks": 4},
  "auth": {"schemes": ["oauth2", "mtls"]}
}

设计要点：

  • 统一使用 camelCase 或 snake_case，不要混用；仓库当前使用 snake_case，跨组织协议建议明确一种规范。
  • endpoint 必须是调用入口，而不能隐含“卡片 URL 即 POST URL”。这样服务可以把 discovery 与执行 API 部署在不同路径或网关后。
  • inputSchema / outputSchema 用 JSON Schema 表达，调用方可在本地校验和生成表单、类型代码。
  • metadata 可以保留扩展性，但核心控制字段不可藏在 metadata 中；扩展字段须使用命名空间，如 x-acme-region。
  • 能力版本建议使用 SemVer。约束如 code_review>=2.0.0 的解析语法应写入规范，并明确预发行版本、缺失段（2.0）等比较规则。

Task 与 Message：把“一次调用”建模成可追踪工作单元

TaskCard 当前表达了任务文本、能力要求、优先级、超时、上下文和元数据。生产协议中，Task 应有稳定 ID、状态、时间戳、调用身份与幂等键。

{
  "jsonrpc": "2.0",
  "id": "req-01J...",
  "method": "tasks/send",
  "params": {
    "task": {
      "id": "task-01J...",
      "contextId": "conversation-42",
      "requiredCapabilities": ["code_review>=2.0.0"],
      "priority": "normal",
      "deadline": "2026-09-18T12:30:00Z",
      "message": {
        "role": "user",
        "parts": [{"type": "text", "text": "Review this pull request"}]
      },
      "metadata": {"traceparent": "00-..."}
    }
  }
}

建议区分：

  • request ID：一次 HTTP / JSON-RPC 请求的关联标识；
  • task ID：可跨重试、轮询、取消和事件订阅的工作单元标识；
  • context ID：多轮会话或协作上下文标识；
  • idempotency key：网络重试时避免重复执行带副作用工具。

parts 是语言无关的多模态边界。至少应规范 text、file（URI、MIME、摘要）、data（受限内嵌数据）等类型；避免把本地文件路径、Python pickle、Java 序列化对象传给对端。

TaskResult、Artifact 与错误

TaskResult 的 status/content/error/duration 是有用起点，但协议应该能表达结构化产物和可恢复错误。

{
  "taskId": "task-01J...",
  "state": "completed",
  "artifacts": [
    {
      "id": "artifact-1",
      "name": "review.md",
      "parts": [{"type": "text", "text": "## Findings\n..."}]
    }
  ],
  "usage": {"durationMs": 1842},
  "metadata": {}
}

统一错误结构：

{
  "code": "CAPABILITY_UNAVAILABLE",
  "message": "No compatible code_review capability is available",
  "retryable": true,
  "retryAfterMs": 1000,
  "details": {"required": ["code_review>=2.0.0"]}
}

错误码必须稳定且与 HTTP 状态配合：400 参数错误、401/403 身份/授权失败、404 任务或端点不存在、409 幂等冲突、429 限流、5xx 服务故障。不要仅发送某一语言的 Exception.toString()，因为调用方无法可靠决策是否重试。

运行时语义：任务状态机比“请求—响应”更重要

Agent 工作通常长耗时、可排队、可中断、会调用工具。因此协议须明确状态机：

submitted → working → input_required → working → completed
     │          │                         │
     │          ├────→ canceled            └────→ failed
     └──────────┴────→ rejected / expired

建议状态含义：

状态 含义 终态
submitted 服务已接受任务，可能尚未开始 否
working 正在运行或等待内部步骤 否
input_required 需要调用方补充信息或确认 否
completed 已产生最终结果 是
failed 不可继续执行，携带规范错误 是
canceled 被调用方或调用方取消 是
rejected 未受理，例如无能力、策略拒绝、超载 是
expired 已超过 deadline / TTL 是

必须另行规定：

  • tasks/get(taskId)：查询最终或中间状态；
  • tasks/cancel(taskId)：取消语义（尽力取消还是强保证）；
  • tasks/input：向 input_required 的任务补充消息；
  • 幂等性：同一个 (caller identity, idempotency key) 应返回同一任务，不应二次执行；
  • deadline：以绝对 UTC 时间为准；服务端可拒绝已过期请求；
  • 重试：仅在 retryable=true、超时但未收到服务端确认等明确情形下进行，使用指数退避与抖动。

传输设计：同步 JSON 与流式 SSE 要使用同一事件信封

请求/响应

最易跨语言实现的基线是：HTTPS + UTF-8 JSON + JSON-RPC 2.0（也可采用 REST，但二者不可在字段语义上混搭）。需要明确 method 名、参数形状、成功结果和错误对象。

同步完成的任务可返回 result.task，而异步任务可立即返回 submitted 状态和 taskId，由调用方轮询或订阅。

SSE 流式事件

SSE 适用于服务端向调用方持续推送；其每条事件应具备统一 JSON envelope，不能让服务端和客户端各自猜字段位置。

event: task.status
id: evt-0007
data: {"specVersion":"1.0","eventId":"evt-0007","taskId":"task-01J...","sequence":7,"type":"status","state":"working","timestamp":"2026-09-18T10:00:02Z"}

event: task.message
data: {"specVersion":"1.0","eventId":"evt-0008","taskId":"task-01J...","sequence":8,"type":"message","message":{"role":"agent","parts":[{"type":"text","text":"Found 2 issues"}]}}

event: task.completed
data: {"specVersion":"1.0","eventId":"evt-0009","taskId":"task-01J...","sequence":9,"type":"completed","result":{"state":"completed","artifacts":[...]}}

约束：

  • type 为规范枚举：status、progress、message、artifact、tool_call（可选）、error、completed；
  • 事件包含 taskId、递增 sequence、eventId 与时间戳，供去重、排序、重连；
  • completed / error 是终止事件；
  • SSE 重连使用 Last-Event-ID，或改用 GET /tasks/{id}/events?afterSequence=N；
  • 长连接须有心跳注释（: ping\n\n）、代理超时配置和背压/最大缓冲策略；
  • 无法或不愿支持 SSE 的实现仍必须提供查询任务状态的方式。

WebSocket / gRPC streaming 可作为协商出的可选 transport，但不能改变 Task、Event、Error 的语义模型。

控制面：发现、路由、负载与健康

发现

当前 AgentRegistry 是线程安全的进程内表，适合单进程测试或嵌入式编排器。跨语言、跨进程部署时，注册表必须成为网络服务或接入一致的基础设施：DNS/服务网格、Kubernetes Service、Consul、etcd、数据库或专用 Agent Directory。

注册记录应至少包含：Agent Card、注册时间、lease/TTL、最后心跳、实例 ID、签名或服务身份。注册与续租流程为：

Agent instance ── register(card, lease) ──► Directory
Agent instance ── renew(instanceId) ──────► Directory
Router         ── query(capability, policy) ► Directory
Directory      ── candidates/cards ─────────► Router

Agent Card 是相对静态的描述；available/busy/offline、当前并发、延迟、错误率是动态遥测。不要仅信任 Agent 自报状态，路由器应结合主动健康检查和实际调用结果。

路由

TaskRouter 的基本策略是“所有 required capabilities 均匹配，优先 AVAILABLE”。把它泛化为可解释的打分模型：

score = capabilityMatch
      × compatibility(version/schema/transport/auth)
      × health
      × capacity
      × localityOrCost
      × policyPermission

路由不应只看能力名：还应检查能力版本、输入输出 schema、对方支持的传输方式、认证方案、租户/数据驻留策略以及 deadline 是否可满足。若无完整匹配，返回 CAPABILITY_UNAVAILABLE 和候选摘要，而不是悄悄降级给不兼容的 Agent。

负载与熔断

DelegationLoadBalancer 给出 round-robin、random、least-pending 三种策略。要让“least pending”有效，必须把选择和执行生命周期原子关联：选择后 record_start，终态（成功、失败、取消、超时）必定 record_end，否则计数会永久漂移。

建议增加：

  • 每实例并发上限与队列上限；
  • 请求超时、连接超时、整体 deadline；
  • 熔断器（连续失败/高延迟时暂时摘除）；
  • 半开探测恢复；
  • 指数退避、抖动和 retry budget；
  • 以任务类型或租户隔离的限流、配额与优先级队列。

心跳与健康

HeartbeatMonitor 提供心跳、漏检阈值、TTL 清扫、健康衰减，思路正确。分布式实现要注意时钟和网络分区：使用服务端收到心跳的时间作为权威；offline 更准确地表示“不可确认可达”，不等同于进程已退出；恢复后需允许实例重新注册并逐步恢复流量。

安全与可观测性是协议的一部分

安全

  • 强制 TLS；内部高信任网络仍建议 mTLS。
  • Agent Card 声明认证方式；请求携带 OAuth2 access token、mTLS 身份或签名凭证。
  • 授权同时覆盖“谁能调用此 Agent”“谁能使用某能力/工具”“谁能读取该任务和事件流”。
  • taskId 不可作为访问凭证；查询、取消、订阅都必须鉴权。
  • 限制输入大小、文件类型、URL 下载范围；防 SSRF、提示词注入导致的越权工具调用、重放攻击。
  • metadata 与日志中脱敏 token、个人数据、模型上下文和工具输出。

可观测性

建议所有请求和事件透传 W3C Trace Context（traceparent / tracestate），并记录：

  • 调用量、成功率、失败码、重试数；
  • 队列等待、端到端耗时、TTFT/流式间隔；
  • 每个 Agent 的并发、健康、熔断状态、容量拒绝；
  • taskId、requestId、agent instance id、capability id 等结构化日志字段。

load_balancer.py 的 OTel bridge 可以保留为实现示例；指标名称、标签基数限制和 trace 传播格式则应上升为跨语言运维规范。

对当前代码的互操作性审计

现有代码是良好的概念原型，但尚不能视作已经严格互通的 A2A 协议实现。关键差异如下：

  1. SSE 编解码不一致：server.py::_stream_response 发送扁平事件，如 {"type":"content","task_id":"...","content":"..."}；而 client.py::_sse_data_to_event 与 _read_sse_stream 解析的是 params.status、params.message.parts。因此客户端无法从当前服务端事件中正确得到 content / completed。
  2. 非流式响应编解码不一致：服务端成功响应是 result: {status, content, agent}；客户端 _extract_text_from_json 只从 result.message.parts（或 params.message.parts）取文字，所以会得到空字符串。
  3. JSON-RPC 只实现了外形，未实现完整语义：服务端未验证 jsonrpc、method，也没有标准 JSON-RPC error code、批处理、通知或明确的 method contract。它会从 params 或 body 宽松取字段，方便试验但降低互操作确定性。
  4. 任务没有完整生命周期 API：当前 request 内直接 agent.run()；没有持久 task、查询、取消、断线恢复、幂等键及 deadline 强制。
  5. 能力版本支持不一致：models.py 的 find_capable_agent() 可处理版本约束，但 AgentRegistry.discover()、TaskRouter 的部分匹配与 alternatives 使用 has_capability()，忽略版本约束。路由结果可能与主匹配规则不一致。
  6. 发现仅限进程内：AgentRegistry 不能被另一台机器或另一种语言直接注册/查询；需用 HTTP/gRPC Directory API 或共享服务替换/封装。
  7. 状态来源不统一：Agent Card 中的 status、心跳、health score、负载指标没有形成单一的更新和淘汰策略，分布式场景应由目录服务建立权威合成规则。
  8. 生产安全尚未接入：默认 CORS *，没有认证、授权、TLS、限流、审计和输入边界策略。

这些不是语言限制，而是“协议契约还没有被单独、严格定义”的表现。

推荐的实现路径（语言无关）

阶段 1：固化规范与契约测试

  1. 编写 a2a-spec/：JSON Schema（Card、Task、Event、Error）、OpenAPI（HTTP API）、状态机、错误码、版本策略。
  2. 选择一个规范版本（如 1.0），所有请求、响应、事件均携带或可协商 specVersion。
  3. 提供 JSON 示例与 golden fixtures：每个语言实现必须能序列化、反序列化并通过 schema validation。
  4. 提供契约测试套件：启动任意实现的 server 后，使用语言无关的 HTTP 测试用例验证 discovery、同步任务、异步任务、SSE、错误、重连、取消和鉴权。

阶段 2：把本仓库改成“规范适配器”

  1. 在 models.py 中把 dataclass 视为 schema 的 Python 映射；序列化字段名、空值、省略规则、枚举值严格对齐 schema。
  2. 在 server.py 中只接受声明的 JSON-RPC methods，验证请求 schema，输出统一 Task/Event/Error envelope。
  3. 在 client.py 中按同一个 envelope 解析；以 taskId + sequence 处理重连和去重；不要兼容性猜测多个不相关字段结构。
  4. 增加 TaskStore 抽象（内存实现用于开发、Redis/PostgreSQL 等用于生产），实现 send/get/cancel/events。
  5. 将 Agent 包在一个最小 AgentExecutor 适配接口之后：describe()、execute(task)、cancel(taskId)，流式能力为可选。

阶段 3：建设分布式控制面

  1. 将 AgentRegistry 抽象为 Directory 接口，分别实现 in-memory 和 network-backed 版本。
  2. 将健康检查、TTL、熔断、容量和负载指标汇集到 Directory / Router；路由器只消费标准候选记录。
  3. 为 Agent 实例分配唯一 instance ID；以 lease 和服务端时间处理上线、续租、下线与重启。
  4. 支持策略插件：租户隔离、区域亲和、成本上限、数据分类和能力准入。

阶段 4：多语言 SDK（最后才做）

从同一 OpenAPI/JSON Schema 生成或手写 Python、TypeScript、Go、Java SDK。SDK 只负责：

  • 类型安全模型；
  • HTTP/SSE transport；
  • 认证与 trace header；
  • 重试、超时、取消和事件订阅；
  • 本地 schema validation。

任何 SDK 特有的便利功能（Python async generator、Java reactive stream、Go channel）都必须映射到同一组网络事件，不能新增仅某语言可见的线上语义。

最小可行互操作闭环

一个真正语言无关的 MVP 应达到以下验收：

  1. Go 服务端发布 Agent Card，Python 客户端能发现并校验其 schema。
  2. TypeScript 客户端能提交 Task，服务端可返回立即完成或 submitted 任务。
  3. 任意客户端能通过 SSE 接收统一 Event，并在断线后按 eventId/sequence 恢复。
  4. 任意客户端能查询、取消同一 Task；重试同一幂等键不会导致重复执行。
  5. 路由器能基于 versioned capability、健康、并发和权限选择候选者，并在失败时执行受控切换。
  6. 无效 JSON、未知方法、无能力、超时、限流、内部错误都返回可机器处理的标准 Error。
  7. 所有实现通过同一份契约测试，而不仅仅是各自语言内的单元测试。

与 ../a2a-sdk-rust 的实现对比

路径说明：用户指定的 ../a2a-rust 在当前工作目录的父目录中不存在；实际存在且对应的 Rust 项目为 ../a2a-sdk-rust。以下比较基于该仓库的源码，而非 README 的功能宣称。

总体定位：Python 是“编排/基础设施原型”，Rust 是“协议 SDK 原型”

维度 当前 Python 实现 a2a-sdk-rust 实现 影响
主要目标 面向本地多 Agent 委派：注册、能力路由、负载均衡、心跳 面向 A2A v1 协议实现：类型、JSON-RPC、服务端 trait、Axum 适配器、客户端 两者不是同一抽象层级，不能只比较语言特性
模块组织 7 个 Python 模块，模型/传输/控制面放在同一轻量包中 workspace 分为 a2a-types、a2a-server、a2a-client、a2a-axum 四个 crate Rust 更适合作为可复用 SDK；Python 更接近应用侧编排组件
契约来源 以 dataclass 与实现逻辑为主，参考 A2A / Goose / Hermes 类型文件显式对齐 A2A v1 与 JSON-RPC binding，并固化 method/错误码 Rust 的线上协议边界更明确；Python 需要先外置 schema/fixtures
控制面 有进程内 Registry、TaskRouter、负载均衡、HeartbeatMonitor 有 Registry HTTP 自动注册 client；没有本地能力路由和负载均衡 两者能力互补；Registry API 仍需统一

Rust 的 a2a-types 是协议核心，a2a-server 以 A2AAgent trait 隔离 Agent runtime，a2a-axum 只负责 HTTP/SSE 接入。这正是本文件推荐的“规范层 → 运行时适配 → transport adapter”结构。Python 当前 server.py 则同时承担解析、协议转换、执行与流事件拼装，适合原型但边界更松。

线上契约差异（决定能否直接互通）

协议项目 Python 当前行为 Rust 当前行为 结论
JSON 字段命名 模型以 snake_case 输出，如 task_id、required_capabilities 协议对象使用 camelCase，如 taskId、contextId、statusUpdate 不能直接互通；必须以官方 schema 固定 wire format，内部可各自转换
JSON-RPC method 客户端发送 SendMessage，服务端未校验 method，默认接受宽松 body 明确常量和分派：SendMessage、SendStreamingMessage、GetTask、ListTasks、CancelTask Python 要补全 method 验证和全部操作
SendMessage 成功结果 {result: {status, content, agent}} {result: {task: ...}} 或 {result: {message: ...}} 结果结构不同；Python client 当前也无法解析自己的 server 响应
Task 模型 TaskCard 是提交参数，TaskResult 是扁平结果；无规范 Task 实体 Task{id, contextId, status, artifacts, history, metadata} Rust 更贴近长任务状态机；Python 应把 Task 设为一等资源
状态枚举 completed / 字符串 status，流式还有自定义 started/content/error submitted、working、completed、failed、cancelled、input-required、rejected、auth-required Python 的语义较简化，缺少 input/auth required 等互操作状态
Message / Part 服务端只提取 parts[].text，TaskCard 使用 task 字符串 Message 有 message/context/task ID、role、text/file/data Part、extension/reference IDs Python 当前只支持文本子集；应明确是否支持 Rust 所有 Part 变体

Agent Card name/url/status/capabilities/skills/max concurrent 等自定义字段 protocol versions、skills、capabilities、interfaces/bindings、认证等 A2A Card 两者 Card 形状和能力表述不同；应以 Card schema 为准，并把本地 status/load 移到目录遥测

因此，当前 Python server 与 Rust client、Rust server 与 Python client 都不能直接互操作。问题根源不在异步模型（asyncio 对 Tokio），而是 wire format 和状态语义未对齐。

流式传输：Rust 的服务端封装更规范，但两边都仍有缺口

Python server.py 根据 Accept: text/event-stream 在同一个 SendMessage 请求中返回 SSE，事件为扁平的：

{"type":"content","task_id":"...","content":"..."}

Rust 区分 SendMessage 与 SendStreamingMessage。后者在 a2a-axum/src/sse.rs 中把每条 SSE data: 统一包装为 JSON-RPC response：

{
  "jsonrpc": "2.0",
  "id": "request-id",
  "result": {
    "statusUpdate": {
      "taskId": "task-id",
      "status": {"state": "working"}
    }
  }
}

其 StreamResponse 明确只能承载 task、message、statusUpdate、artifactUpdate 中的一种；并通过 SSE keep-alive 支持长连接。这比 Python 当前的“服务端扁平事件、客户端却按 params.message.parts 解析”的不一致实现更接近可验证的协议。

但 Rust 也不是完整闭环：a2a-client/src/client.rs 只有同步 send_message/get_task/cancel_task，没有 send_streaming_message 或 SSE 解码 API；StreamingResponse 是同步 next_event() trait，ManualSseStream 仅持有预先填充的 Vec<Event>。它提供了正确 envelope 与 server adapter，但尚未覆盖生产所需的客户端持续消费、背压、事件序号、断线重连和 Last-Event-ID 恢复。

**统一建议：**采用 Rust 已实现的 SendStreamingMessage + JSON-RPC response + StreamResponse wire envelope；在两边补充异步事件消费接口，并扩展规范字段 eventId / sequence 以支持可恢复流。不要保留 Python 的自定义扁平 SSE 格式作为跨语言协议。

任务运行时与持久化

Rust A2AAgent trait 要求实现 agent_card、handle_message、get_task、cancel_task，并可选实现 handle_streaming_message、list_tasks；默认流式回退至少输出 working → final。TaskStore 提供 Tokio RwLock<HashMap<...>> 的内存 Task CRUD、按 context/state 查询。示例 Agent 会把完成任务存进 store，因此 GetTask 可以工作。

Python A2AServer 直接调用 agent.run(text) 或 agent.run_stream(text)，未创建可查询的 Task，也没有 cancel/list API 或 TaskStore。因此：

  • Rust 明确了任务运行时的接口形状，但 TaskStore 仍是易丢失的内存实现，且不会自动接入所有 Agent；
  • Python 更容易直接包裹既有 Agent 框架，但缺乏跨请求的任务生命周期；
  • 两边均未见持久存储、幂等键、deadline 强制、状态转移校验、取消传播和事件回放。

应定义语言无关的 TaskRepository / TaskStore 能力（create、compare-and-transition、append artifact/event、get、list、cancel-request、TTL cleanup），再分别以 PostgreSQL/Redis 等实现；不能把 Rust 的 RwLock 或 Python dict 当成分布式任务语义。

发现与控制面：Python 更完整，Rust 的注册接口更易跨进程

Python 的 AgentRegistry 支持能力筛选、状态变更监听、TTL、心跳与健康评分；TaskRouter 支持多能力匹配与备选；DelegationLoadBalancer 有轮询、随机、最少 pending 等策略。这些是 Rust SDK 当前未提供的应用编排能力。

Rust 的 RegistrationClient 则已经将注册行为落实为网络调用：POST {registry}/api/v1/agents/register，body 为 { "url": "..." }，支持环境变量 AGENT_REGISTRY_URL / AGENT_URL 和启动时自动注册。这比 Python 仅进程内注册表更接近跨语言部署，但协议仍过于薄弱：只注册 URL、没有 Card 快照或版本、实例 ID、lease/heartbeat、认证、撤销令牌和 capability query；而且该 API 不是 A2A core JSON-RPC 的组成部分。

可行的合并方向：保留 Python 侧的路由/健康/负载策略，采用 Rust 的“网络化注册 client”思路，把它们共同收敛到独立 Directory API：

POST   /v1/agents                 注册 AgentCard + instanceId + lease
PUT    /v1/agents/{instanceId}/lease  续租/心跳/容量遥测
DELETE /v1/agents/{instanceId}    注销
GET    /v1/agents?capability=...  查询兼容候选者

Directory 返回规范 Agent Card 及动态 health/capacity 摘要；路由策略可留在调用侧或独立 Router 服务，但注册 API、能力约束和淘汰语义必须跨语言一致。

类型安全与扩展边界

Rust 利用 serde 的 camelCase、enum、Option、Result 和 A2AError 将很多协议错误前置到编译期或反序列化期；四个 crate 也隔离了纯类型、Agent trait、HTTP adapter 与客户端。Python dataclass 同样便于建模，但 dict[str, Any]、字符串 status、宽松 body.get() 让非法组合更容易越过边界。

这不意味着必须在 Python 中复制 Rust trait 或使用 Rust；正确做法是：

  1. 以 JSON Schema/OpenAPI 作为两端共同真源，并为 Rust serde 类型和 Python Pydantic/dataclass adapter 生成或校验模型；
  2. 严格拒绝未知/非法核心字段（扩展只允许命名空间字段）；
  3. 在 Python 中拆分 protocol types、executor adapter、HTTP adapter、directory/router，获得与 Rust 类似的依赖方向；
  4. 用同一组 JSON fixture 和互操作测试，而非比较两种语言的内部类型系统。

合并后的优先级

  1. 先统一 v1 wire contract：字段命名、Card、Task、Message/Part、Artifact、JSON-RPC methods、错误码、SSE StreamResponse；删除 Python 的自定义响应/SSE 格式或限制其仅内部使用。
  2. 修复双向客户端闭环：Python client 按统一 envelope 解析同步与 SSE；Rust client 实现 SendStreamingMessage、SSE 解析、终态判断与取消/查询协同。
  3. 实现共享的契约测试矩阵：Python client ↔ Rust server、Rust client ↔ Python server，至少覆盖 discovery、SendMessage（Task/Message 两分支）、Get/Cancel/ListTask、文本/file/data Part、标准错误和流式状态/artifact。
  4. 将 TaskStore 与 Directory 产品化：持久任务、幂等、TTL、lease/heartbeat、熔断/容量；Python 现有 router/LB 可作为策略参考。
  5. 最后加强安全与恢复能力：TLS/mTLS/OAuth、授权、trace context、SSE sequence/replay、重试预算与审计。

一句话原则

把 Agent 当作一个有能力描述、可寻址、可鉴权、可观测、可追踪状态机的远程服务；把 SDK 当作协议的可替换实现，而不是协议本身。

按这个边界演进，当前仓库中的模型、服务端、客户端、注册表、路由和负载均衡代码可以保留为 Python 参考实现；../a2a-sdk-rust 中的 types/server/client/axum 分层则可作为协议 SDK 的模块化参考。二者只有先收敛于同一份可执行契约与互操作测试，才能建立确定、可测试的跨语言 A2A 通信。

复习与应用

分别检查同步响应、SSE、取消和重试是否使用同一套任务标识。原文的 Python/Rust 实现比较属于仓库快照，不是当前官方规范的逐条符合性声明。
