Skill

2026-09-14

#AI#Agent#Skill

理解主线

Skill 的延迟加载分开处理“发现候选流程”和“读取流程正文”。向量筛选、意图分类和任务结束后裁剪是可选设计；它们不是所有 Agent 框架都会采用的固定流水线。

Agent 系统在处理大规模组件（Tools 或 Skills）时最核心的痛点：如果列表里有几百个 Skill，哪怕只看 description，也会极大地拖慢模型响应，并导致巨大的 Token 浪费。

可以用前置路由或检索机制（Pre-routing / Retrieval-based Loading）缩小候选范围。下文列出可选择的设计方案，不描述所有框架的共同内部实现。

主要的优化手段可以分为以下三个层级：

向量检索（Embedding & RAG）分级过滤

采用这一方案时，系统可以使用成本极低、速度极快的向量模型（Embedding）进行前置筛选：

  • 离线阶段：所有的 Skill Description 会提前转化为向量，存入本地或内存向量数据库中。
  • 用户输入时：系统先用向量模型计算用户当前任务与哪些 Skill 的 Description 最相似，然后只挑出最相关的 Top 3 或 Top 5 个 Skill 的描述喂给大模型。
  • 效果：大模型实际上每次只看到了极少数的 Skill 备选，Token 消耗和思考时间被压缩到了极致。

意图分类器（Intent Classifier）

对于一些高频、核心的 Skill，系统会训练一个非常轻量、速度极快的小模型（或者一段硬编码的关键词路由规则）作为“门卫”：

  • 用户说话后，门卫先判断：“这属于“代码修改”还是“数据分析”还是“网络搜索”？
  • 如果被归类为“代码修改”，系统就只加载与代码相关的这一组 Skill 列表，其他领域的 Skill 直接被屏蔽。

按需动态卸载与上下文压缩（Context Management）

采用上下文裁剪方案时，可以在任务结束后缩减不再需要的 Skill 内容：

  • 当这一步的任务执行完毕，Agent 已经拿到了结果（例如：图表已经画好），系统在进入下一轮对话时，会启动上下文裁剪（Pruning）。
  • 它会把那个几千字的 SKILL.md 从当前的 System Prompt 中剔除（Unload），只保留该 Skill 输出的最终结论。这样可以确保后续的对话依然保持“轻量”。

对比总结

做法 Token 消耗 思考延迟（Latency） 适合场景
朴素扫描（每次都全量带上所有 description） 极高（随 Skill 数量线性暴涨） 高（大模型需要阅读长文本） 只有 10 个以内核心 Skill 的小系统
路由检索（向量筛选 / 意图分类后只带 Top-N） 极低（保持恒定，与 Skill 总数无关） 极低（大模型只读极少文本） 拥有成百上千个 Skill 的大规模 Agent

“扫描成本”在实际工程落地时，已经通过 “向量数据库检索 -> 筛选出少数 Description -> 大模型决定是否触发 -> 动态加载 SKILL.md” 这样的漏斗形架构被成功解决掉了。

复习与应用

比较三种策略的召回范围、上下文开销和误路由风险。官方 Claude Code 文档说明正文在使用时加载，但不能据此推断内部一定有 embedding 前置检索或任务结束后立即卸载。参见 官方 Skills 说明。
