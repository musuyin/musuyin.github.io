Sandbox

2026-07-22

#AI#Agent

理解主线

并行目录隔离解决覆盖冲突，操作系统沙箱解决越权访问，两者目标不同。多用户场景还需要考虑身份、凭据、共享对象库和进程资源。

Sandbox 隔离方案笔记

背景：从 worktree 到真正的 sandbox

讨论起点是 s18 worktree isolation 章节。worktree 本质上是 git 的多工作目录特性，每个目录对应一个独立分支。对于多用户 Agent 平台，可以将每个用户 session 绑定一个 worktree，实现文件写冲突隔离。

worktree 的隔离能力与限制

能做到的：

  • 文件写冲突隔离（用户 A 和用户 B 写同名文件互不覆盖）
  • 每用户独立 git 分支和历史
  • session 结束后 git worktree remove 干净清理

做不到的：

  • Agent 可以通过 bash 工具 cd 到 worktree 之外的任意目录，读写其他用户文件
  • 所有 worktree 共用同一个 .git 对象库，git refs 操作存在并发干扰风险
  • 不是真正的进程隔离，所有用户 Agent 在同一进程内运行

结论： worktree 是弱沙箱，可以通过在 bash 工具层加路径白名单增强隔离性，但仍存在绕过风险。

Docker 强沙箱方案

核心原则

隔离在 Harness 层透明实现，Agent 不需要知道 Docker 的存在。Agent 调用 bash("ls /") 时，Harness 自动将命令路由到专属容器，Agent 以为在跑普通 bash。

架构

用户请求
   ↓
Harness（持有 session → container_id 的 map）
   ↓ 工具调用时自动注入 docker exec
Agent（以为自己在跑普通 bash）
   ↓
docker exec <container_id> sh -c "<command>"

Map 管理

# session_id → container_id，由 Harness 维护，Agent 无法读写
session_containers: dict[str, str] = {}

def create_session(session_id: str) -> str:
    result = subprocess.run(
        ["docker", "run", "-d", "--rm",
         "--memory=512m", "--cpus=0.5",
         "--network=none",           # 默认无网络
         "--read-only",              # 根文件系统只读
         "--tmpfs=/tmp",             # 只有 /tmp 可写
         "sandbox-image"],
        capture_output=True, text=True
    )
    container_id = result.stdout.strip()
    session_containers[session_id] = container_id
    return container_id

def destroy_session(session_id: str):
    container_id = session_containers.pop(session_id, None)
    if container_id:
        subprocess.run(["docker", "rm", "-f", container_id])

工具层透明代理

def make_bash_tool(session_id: str):
    def bash(command: str) -> str:
        container_id = session_containers.get(session_id)
        if not container_id:
            return "Error: session has no bound container"
        result = subprocess.run(
            ["docker", "exec", container_id, "sh", "-c", command],
            capture_output=True, text=True, timeout=30
        )
        return result.stdout + result.stderr
    return bash

每个 session 启动时动态生成一套工具，bash/read/write 全部通过闭包绑定 session_id。Agent 拿到的工具签名没有任何 Docker 相关参数，无法感知也无法操控容器管理逻辑。

安全边界

攻击面 防御手段
Agent 尝试操作其他容器 Agent 工具集里根本没有 docker 命令
Agent 读其他用户文件 容器文件系统完全独立
Agent 耗尽资源 --memory / --cpus 硬限制
Agent 发起网络请求 --network=none 或白名单网络策略
容器逃逸漏洞 依赖 Docker/内核自身；可加 gVisor 加固

与 worktree 的本质区别

worktree 是共享进程内的目录切换，Agent 依然在同一进程里，只是 cwd 不同。Docker 方案是真正的进程隔离——即使 Agent 执行了 rm -rf /，删的也是容器内的文件系统，宿主机和其他用户完全不受影响。

进一步加固

对完全不受信任的用户（公共 SaaS），可以加 gVisor（--runtime=runsc）沙箱化系统调用，代价是性能损失约 10-20%。

方案对比

方案 隔离强度 实现复杂度 适用场景
worktree 弱（文件级） 低 受信任用户，防误操作
worktree + 路径白名单 中 中 受信任用户，增强防护
Docker 强（进程级） 中 多租户平台，半受信任用户
Docker + gVisor 极强 高 公共平台，完全不受信任用户

复习与应用

用“Bash 切到别人的目录”反例检查 Worktree 的边界，再说明容器化后仍需检查的挂载与权限。
