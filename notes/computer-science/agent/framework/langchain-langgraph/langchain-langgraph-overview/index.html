LangChain 与 LangGraph 学习总览

2026-09-15

#AI#Agent#LangChain#LangGraph

理解主线

按应用层与运行时层理解两套工具：LangChain 封装模型、消息、工具与常见 Agent 接口；LangGraph 表达状态、节点、路由和可恢复执行。先完成最小工具循环，再学习持久化与审批，比先记 API 名称更容易建立联系。

文档基线 本系列以 2026-09-15 的 LangChain Python v1、LangGraph Python v1 官方文档为基线。框架迭代较快，复制代码前应确认安装版本，并以官方 API Reference 为准。

一句话建立心智模型

  • LangChain 解决“怎样方便地接入模型、消息、工具、结构化输出、检索与 Agent 中间件”。
  • LangGraph 解决“怎样把多个确定性步骤与 Agent 步骤编排成有状态、可暂停、可恢复、可观测的执行图”。
  • LangSmith 解决“怎样追踪、调试、评估和监控一次 Agent 执行”。它是平台，不是构建 LangChain 或 LangGraph 应用的强制依赖。

可以用后端开发作类比：

AI 体系 后端类比 主要责任
模型 不稳定、非确定性的计算服务 理解与生成
Tool RPC/API 客户端 对外执行明确动作
LangChain SDK 与 Agent Harness 统一模型和工具接口，组织模型循环
LangGraph 工作流引擎与状态机运行时 状态、路由、持久化、恢复、人工审批
LangSmith APM、Trace 与评测平台 观测、评估、调试

两者不是竞争关系

flowchart TB
    App[业务应用]
    LC[LangChain<br/>模型、工具、Agent、中间件]
    LG[LangGraph<br/>状态、节点、边、Checkpoint、Interrupt]
    Model[模型供应商]
    Tools[业务工具与数据源]
    LS[LangSmith<br/>Trace、评估、监控]

    App --> LC
    LC --> LG
    LC --> Model
    LC --> Tools
    LG --> Model
    LG --> Tools
    LC -. 可选观测 .-> LS
    LG -. 可选观测 .-> LS

LangChain 的 create_agent 本身构建在 LangGraph 之上，因此它天然继承持久化、流式输出和 Human-in-the-loop 等能力。只有在预置 Agent 循环不能清楚表达业务流程时，才需要直接编写 LangGraph。

选择原则 从最高层且能满足需求的抽象开始。简单 Agent 先用 LangChain；复杂、长时间运行、需要严格流程控制的系统再下沉到 LangGraph。不要为了“用了图”而把一个简单调用拆成十几个节点。

什么时候使用哪一个

场景 推荐 原因
切换不同厂商的聊天模型 LangChain 提供较统一的模型接口
为模型注册几个 Python 工具 LangChain create_agent 能直接建立模型—工具循环
要求模型返回 Pydantic 结构 LangChain 结构化输出是高层能力
简单 RAG 问答 LangChain Loader、Splitter、Embedding、Retriever 生态成熟
固定的分类、检索、生成流水线 LangGraph 或普通代码 图适合显式表达阶段和路由；流程很短时普通代码更直接
Agent 中夹杂强制审批与确定性规则 LangGraph interrupt、条件边和持久化共同表达控制点
跨分钟、小时甚至更久的任务 LangGraph Checkpoint 支持暂停与恢复
多 Agent 协作、并行分派、子图 LangGraph 图结构能表达路由、并行与状态汇总
追踪耗时、Token、工具调用和失败路径 LangSmith 或其他观测系统 这是可观测性问题，不是提示词问题

核心学习顺序

    B --> C[create_agent]
    C --> D[结构化输出与中间件]
    D --> E[StateGraph]
    E --> F[State、Node、Edge、Reducer]
    F --> G[Checkpoint 与 thread_id]
    G --> H[Interrupt 与 Command]
    H --> I[Streaming、Subgraph、并行]
    I --> J[测试、观测与生产化]

推荐按以下节奏学习：

  • 先读 S01-LangChain，亲手完成一次模型调用、一次工具调用和一个 create_agent。
  • 再读 S02-LangGraph，先写完全不调用 LLM 的状态图，确保真正理解状态、节点和边。
  • 最后读 S03-工程实践，用“变更申请审批 Agent”串起结构化输出、持久化、人工审批、幂等和测试。
  • 每学一个抽象，都回答三个问题：谁拥有状态、谁决定下一步、失败后从哪里恢复。

学习验收标准

完成文档阅读不等于掌握。至少做到以下事情，才算完成本轮入门：

  • 能不用术语堆砌，解释 LangChain、LangGraph、LangSmith 的职责边界。
  • 能写出 LangChain create_agent，说明模型为什么以及何时调用工具。
  • 能画出 Agent 的模型—工具循环，并指出结束条件。
  • 能独立实现包含普通边和条件边的 StateGraph。
  • 能解释 State 更新为什么需要 Reducer，以及覆盖写和追加写的差异。
  • 能使用 Checkpointer 与 thread_id 延续同一执行线程。
  • 能使用 interrupt 暂停，并用 Command(resume=...) 恢复。
  • 能解释为什么 interrupt 前的副作用必须幂等。
  • 能为节点、路由、暂停恢复和失败重试分别设计测试。
  • 能判断一个需求该用 LangChain、LangGraph，还是普通 Python 代码。

学习时最容易混淆的概念

Chain、Agent 与 Graph

  • Chain：开发者预先规定数据按什么顺序经过哪些组件，通常更确定。
  • Agent：模型根据当前消息和工具结果，动态决定下一步调用哪个工具或结束。
  • Graph：用状态、节点和边描述执行拓扑；节点既可以是确定性代码，也可以是 Agent。

Graph 不等于 Agent。一个 Graph 可以完全没有 LLM；一个 Agent 也可以由预置 Harness 生成，不要求开发者手写 Graph。

State、Checkpoint 与 Store

  • State：某次 Graph 运行正在处理的工作数据。
  • Checkpoint：某个线程在特定执行时刻的 State 快照，用于恢复、回放和查看历史。
  • Store：跨线程共享或长期保留的数据，例如用户偏好。

不要把所有业务数据都塞进 State。订单、工单、权限等权威事实仍应由业务数据库负责；Graph State 保存编排所需的数据和引用。

Tool 与 Node

  • Tool 是暴露给模型选择调用的能力，接口描述会进入模型上下文。
  • Node 是 Graph 的执行单元，由图的边和路由调度，模型不一定知道节点存在。

同一个 Python 函数可以被包装成 Tool，也可以在 Node 内部被直接调用，但这两种方式的决策权不同：前者通常交给模型，后者属于应用程序。

版本意识

搜索资料时经常看到旧版教程中的 LLMChain、ConversationChain、initialize_agent、AgentExecutor 或 create_react_agent。这些内容能帮助理解历史，但不应直接当作 v1 新项目的默认入口。当前学习主线是：

  • LangChain：create_agent、模型、消息、工具、结构化输出、中间件。
  • LangGraph：StateGraph、State、Node、Edge、Reducer、Persistence、Interrupt、Command。

对旧教程应先核对：发布时间、包版本、导入路径，以及官方迁移指南。
