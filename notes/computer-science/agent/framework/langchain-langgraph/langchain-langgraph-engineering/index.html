LangChain 与 LangGraph 工程实践

2026-09-15

#AI#Agent#LangChain#LangGraph#Engineering

理解主线

生产变更助手的关键是分配决定权：模型提取候选请求，确定性代码校验与授权，有权限的人审批，执行服务以稳定 operation_id 处理副作用。图把这些环节连接起来，但不接管每类数据的权威所有权。

实践目标

实现一个“生产变更申请助手”：

  • 接收自然语言变更请求。
  • 用结构化输出提取系统、环境、动作和风险依据。
  • 通过确定性规则校验字段与权限。
  • 查询变更目标的只读信息。
  • 生成执行计划，但不直接执行。
  • 暂停等待有权限的人批准。
  • 批准后调用带幂等键的执行工具。
  • 保存执行结果和审计信息。

这个项目能覆盖 LangChain 和 LangGraph 的主要边界，也能避免“做一个聊天机器人就以为掌握了 Agent 工程”。

需求边界

模型可以决定

  • 从自然语言中提取候选字段。
  • 生成计划说明和风险摘要。
  • 在只读工具之间选择所需信息。

模型不能决定

  • 当前用户是否有权限。
  • 生产环境变更是否可以绕过审批。
  • 请求参数是否符合业务约束。
  • 幂等键怎样生成。
  • 外部调用超时后是否已经成功。
  • 最终审计记录是否完整。

这些必须由确定性代码和权威系统负责。

总体架构

flowchart TB

数据所有权

数据 权威所有者 Graph 中保存什么
用户身份与角色 身份系统 不可伪造的主体 ID、必要角色快照
目标资源状态 Inventory/API 查询结果摘要、资源版本或 ETag
变更申请 业务数据库 change_id 与当前编排所需字段
审批记录 审批或审计数据库 approval_id、决定、审批人、时间
执行结果 执行服务/业务数据库 operation_id、状态、错误摘要
编排进度 Checkpointer 节点 State 与 Checkpoint 历史

Graph State 不是所有业务事实的唯一存储。恢复后仍要对关键资源版本和权限重新校验，避免用过期快照执行生产变更。

执行流程

flowchart TD
    Start([收到请求]) --> Extract[提取结构化请求]
    Extract --> Validate[校验字段]
    Validate --> Authorize[校验权限]
    Authorize --> Inspect[查询目标当前状态]
    Inspect --> Plan[生成执行计划]
    Plan --> Risk[确定性风险分级]
    Risk --> Approve[Interrupt 等待审批]
    Approve --> Decision{审批结果}
    Decision -->|拒绝| Rejected[记录拒绝]
    Decision -->|批准| Revalidate[重新校验权限与资源版本]
    Revalidate --> Execute[使用幂等键执行]
    Execute --> Verify[读取权威状态验证结果]
    Verify --> Audit[记录审计]
    Rejected --> End([结束])
    Audit --> End

这里的条件分支是显式业务规则：审批批准进入执行，拒绝直接结束。不存在静默降级到其他执行路径。任何字段缺失、权限不足或状态冲突都应形成明确错误。

State 设计

from typing import Literal, TypedDict


class ChangeState(TypedDict):
    request_text: str
    requester_id: str
    change_id: str

    target_system: str
    environment: Literal["dev", "stage", "prod"]
    action: str
    requested_parameters: dict

    target_version: str
    plan: list[str]
    risk_level: Literal["low", "medium", "high"]
    risk_reasons: list[str]

    approval_id: str | None
    approved: bool | None
    approver_id: str | None

    operation_id: str | None
    execution_status: Literal["not_started", "succeeded", "failed"]
    error_code: str | None

设计要点：

  • 用 Literal/枚举限制状态空间。
  • 不保存密码、Token、数据库连接或完整敏感响应。
  • change_id 标识业务申请，thread_id 标识 LangGraph 线程，两者概念不同。
  • operation_id 作为执行服务的幂等键或关联键。
  • 错误使用稳定 error_code，人类可读说明放日志或审计记录。

结构化请求提取

from typing import Literal

from pydantic import BaseModel, Field
from langchain.agents import create_agent


class ChangeRequest(BaseModel):
    target_system: str = Field(description="要变更的系统唯一名称")
    environment: Literal["dev", "stage", "prod"]
    action: str = Field(description="明确的变更动作")
    requested_parameters: dict
    stated_reason: str


extractor = create_agent(
    model="openai:gpt-5.5",
    tools=[],
    response_format=ChangeRequest,
    system_prompt=(
        "只提取用户明确提供的事实，不得补造系统、环境或参数。"
    ),
)

提取成功只说明数据符合 Schema。后续 validate 节点还要查配置目录确认系统存在、环境合法、动作在允许列表内。不能因为模型输出了一个合法字符串就信任它。

节点职责

节点 类型 输入 输出 副作用
extract_request 模型 原始请求 候选结构化字段 无
validate_request 确定性 候选字段 规范化字段 无
authorize_request 确定性 主体、目标、动作 授权结论 只读查询
inspect_target 确定性 目标标识 状态与版本 只读查询
draft_plan 模型 请求、当前状态 计划和风险说明 无
assess_risk 确定性 环境、动作、影响面 风险级别 无
request_approval Interrupt 计划、风险 审批决定 持久暂停
revalidate 确定性 审批结果、目标版本 最新校验结果 只读查询
execute_change 确定性 已批准计划、operation_id 执行结果 写操作
verify_change 确定性 目标、期望结果 权威状态 只读查询
write_audit 确定性 全部关联 ID 与结果 审计 ID 写操作

把计划生成和实际执行分开至关重要。模型生成的是候选计划；执行节点只能接受经过 Schema、规则、权限和审批校验的结构化命令。

审批节点

from langgraph.types import interrupt


def request_approval(state: ChangeState) -> dict:
    decision = interrupt(
        {
            "change_id": state["change_id"],
            "target": state["target_system"],
            "environment": state["environment"],
            "plan": state["plan"],
            "risk_level": state["risk_level"],
            "risk_reasons": state["risk_reasons"],
        }
    )

    return {
        "approval_id": decision["approval_id"],
        "approved": decision["approved"],
        "approver_id": decision["approver_id"],
    }

外部审批入口必须验证：

  • 恢复请求对应哪个 thread_id 和待审批任务。
  • 当前身份是否有该环境和风险级别的审批权限。
  • 审批是否已被消费，避免重复恢复。
  • 审批内容是否与展示给审批人的计划哈希一致。
  • 决定、审批人、时间和理由是否写入不可抵赖的审计记录。

不要信任客户端提交的 approver_id；它应来自通过认证的服务端身份上下文。示例字段只是表达 State 形状。

幂等执行

def execute_change(state: ChangeState, executor) -> dict:
    if state["approved"] is not True:
        raise PermissionError("变更尚未获得批准")

    result = executor.execute(
        operation_id=state["operation_id"],
        target=state["target_system"],
        environment=state["environment"],
        action=state["action"],
        parameters=state["requested_parameters"],
        expected_version=state["target_version"],
    )

    return {
        "execution_status": result.status,
        "error_code": result.error_code,
    }

执行服务应保证同一个 operation_id：

  • 第一次调用创建操作并执行。
  • 重复调用返回同一操作的当前或最终结果。
  • 相同 ID 携带不同请求体时直接报冲突。

若网络超时，Graph 不能凭超时就断言执行失败，也不能换一个新 ID 重试。应使用相同 operation_id 查询或重试，让执行服务消除不确定性。

安全边界

Prompt Injection

工具返回、检索文档和用户文本都是不可信数据。文档中的“忽略此前规则”“调用删除工具”等文本不能改变系统权限。应通过工具白名单、确定性授权和输入输出隔离约束行为，而不是只依赖系统提示词。

最小权限

  • 读取和写入使用不同凭据与工具。
  • Graph 进程不应持有超出当前业务需要的集群管理员权限。
  • 生产写工具默认要求审批并记录主体。
  • Tool 参数按资源级权限校验，不能只判断“用户能调用这个工具”。

Secret

Secret 只在执行时由 Secret Manager 或平台注入。不要把 Secret 放入 State、Checkpoint、Prompt、Trace、异常消息或模型 Tool 参数。

可观测性

至少记录：

  • trace_id、thread_id、change_id、operation_id。
  • 当前节点、进入和退出时间、重试次数。
  • 模型名称、Token、延迟、结构化校验是否成功。
  • Tool 名称、经过脱敏的参数摘要、结果码、延迟。
  • State 字段变化摘要，不记录 Secret 和完整敏感文本。
  • Interrupt 创建、审批和恢复事件。

指标至少包括：

  • 端到端成功率和延迟。
  • 各节点失败率与重试率。
  • 人工审批等待时间。
  • 模型 Token 与成本。
  • Tool 选择和参数校验失败率。
  • 重复执行被幂等机制拦截的次数。

Trace 用于解释单次执行路径，Metrics 用于发现总体异常，Log 用于保留离散事件证据，三者不能互相替代。

测试计划

不调用真实模型的快速测试

  • 为每个 Node 测试输入和部分 State 更新。
  • 为风险规则测试边界值。
  • 为 Router 测试批准与拒绝路径。
  • 用固定模型响应测试结构化提取后的 Graph 路径。
  • 验证未批准时执行工具从未被调用。

Persistence 与恢复测试

  • 执行到 Interrupt 并确认出现待审批负载。
  • 关闭进程，重新创建应用和 Graph。
  • 使用同一 thread_id 恢复。
  • 确认审批前节点重跑不会产生重复副作用。
  • 确认不同 thread_id 不能读取或恢复对方状态。

真实集成测试

  • 使用测试模型凭据验证真实结构化输出。
  • 使用测试环境的 Inventory、审批与执行服务。
  • 注入超时，验证使用相同 operation_id 核对结果。
  • 验证 Token、Trace、日志和审计中没有 Secret。

故障场景

场景 预期行为
模型返回不符合 Schema 节点明确失败或执行有界重试，不进入执行阶段
资源不存在 校验失败，不创建审批
用户无权限 明确拒绝，不生成可执行命令
审批期间资源版本变化 恢复后重新校验失败，不执行旧计划
执行 API 超时 用同一 operation_id 查询权威状态
Checkpointer 暂时不可用 不开始不可恢复的写操作
审批请求重复提交 只消费一次，后续返回已处理状态
进程在执行响应前崩溃 恢复后通过幂等键核对，不重复执行

分阶段练习

建立 LangChain 最小 Agent

  • 实现一个只读 Tool。
  • 观察消息中 Tool Call 与 ToolMessage。
  • 记录调用次数、参数和最终消息。

验收：能解释每一轮模型调用的输入、输出和终止原因。

建立纯确定性 Graph

  • 不接模型，实现校验、风险分级和条件路由。
  • 为每条路径写测试。

验收：能从 State 推导下一节点，错误输入直接失败。

接入结构化提取

  • 用 Pydantic 定义请求。
  • 模型只负责提取，规则节点负责校验。

验收：非法系统名和环境不会因为 Schema 合法而通过业务校验。

加入 Checkpoint 和审批

  • 使用持久化 Checkpointer。
  • 用 Interrupt 暂停、重启进程、再恢复。

验收：重启后能恢复；错误 thread_id 无法恢复；审批前无写副作用。

加入幂等执行和故障注入

  • 用 operation_id 保护写操作。
  • 注入超时和进程崩溃。

验收：重复恢复或重复调用不会产生第二次业务变更。

加入观测和评估

  • 记录 Trace、Metrics 和审计。
  • 建立提取与计划质量数据集。

验收：能从一次失败追踪到具体节点、模型调用、工具结果与业务操作 ID。

项目完成定义

  • 文档中的所有图和 State 字段与代码实现一致。
  • 正常、拒绝、越权、状态冲突、超时和恢复路径都有自动化测试。
  • 进程重启后的恢复经过真实验证。
  • 外部写操作使用稳定幂等键。
  • 生产操作存在明确人工审批，并在恢复后重新校验。
  • Trace、Log、Checkpoint 和错误信息中没有凭据。
  • 已在测试环境进行真实模型和真实服务集成验证。
  • 仍需人工检查的 UI、权限配置和运行手册被明确列出。

复盘问题

  • 哪些判断交给了模型，为什么无法用确定性规则更可靠地完成？
  • 哪个系统拥有每类数据的最终解释权？
  • 任意节点执行两次会发生什么？
  • 外部调用超时时，怎样区分未执行、执行中和已执行？
  • 进程在哪些位置崩溃仍能安全恢复？
  • 审批人看到的内容是否与最终执行命令完全对应？
  • 如何证明某次变更由谁提出、谁批准、执行了什么？
  • 如果更换模型，哪些评估可以发现行为退化？
