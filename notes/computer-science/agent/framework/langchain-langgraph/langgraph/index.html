LangGraph 核心原理与使用

2026-09-15

#AI#Agent#LangGraph#Workflow

理解主线

把图理解为对 State 的逐步变换：Node 产生更新，Reducer 决定如何合并，Edge 决定下一步。Checkpoint 记录进度；Interrupt 恢复时节点会重新执行，因此恢复能力必须与副作用幂等一起设计。

LangGraph 解决什么问题

LangGraph 是构建长时间运行、有状态 Agent 和工作流的低层编排框架与运行时。它让应用显式定义：

  • 执行过程中保存哪些状态。
  • 每个节点读取什么、返回什么更新。
  • 节点之间怎样流转、分支、循环或并行。
  • 在哪里保存 Checkpoint。
  • 在哪里暂停等待人工输入。
  • 失败或进程重启后从哪里恢复。

它专注编排，不负责替开发者设计 Prompt 或业务架构。LangGraph 可以使用任意模型 SDK，也可以构建完全不含 LLM 的普通状态工作流。

为什么 Agent 需要 Graph

简单 Agent 只有一个模型—工具循环。真实业务往往还要求：

接收请求
  → 确定性校验权限
  → 模型分类
  → 按类别选择数据源
  → 并行检索
  → 生成方案
  → 高风险操作等待审批
  → 执行工具
  → 写审计记录

其中有些步骤必须由程序决定，有些适合交给模型。LangGraph 的关键价值是把两者放在同一张显式执行图中，并让状态转移可检查、可测试、可恢复。

核心概念

State

State 是节点之间共享的工作数据。节点不应原地修改 State，而是返回一个部分更新，由 Runtime 根据每个字段的 Reducer 合并。

import operator
from typing import Annotated, TypedDict


class WorkflowState(TypedDict):
    request: str
    category: str
    evidence: Annotated[list[str], operator.add]

这里 request 和 category 默认使用覆盖语义；evidence 使用 operator.add，多个更新会追加到列表。

State 只保存执行所需数据。数据库连接、模型 Client、Logger 等依赖不应塞进 State；大文件也应存到对象存储，只在 State 中保留 URI、哈希和元数据。

Node

Node 是接收 State 并返回 State 更新的函数。

def normalize_request(state: WorkflowState) -> dict:
    normalized = state["request"].strip()
    if not normalized:
        raise ValueError("request 不能为空")
    return {"request": normalized}

好的 Node 应职责单一、输入输出清晰。外部副作用应显式隔离，便于重试、测试和审计。

Edge

Edge 决定控制流：

  • 普通边：节点完成后固定进入下一个节点。
  • 条件边：调用路由函数，根据当前 State 选择后继。
  • START：图的虚拟入口。
  • END：图的虚拟终点。

路由函数应该是纯函数：同样的 State 应得到同样的路由结果，不应在路由函数里访问外部服务或执行副作用。

Reducer

Reducer 决定某个 State 字段如何合并更新。没有 Reducer 时通常是覆盖；有 Reducer 时按指定规则合并。

Reducer 尤其影响并行节点。如果两个并行节点同时更新同一字段，而字段没有定义可合并语义，Runtime 无法安全判断最终值。

消息列表通常使用 add_messages，它不只是简单拼接，还会按消息 ID 正确更新已有消息：

from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages


class ChatState(TypedDict):
    messages: Annotated[list, add_messages]

官方还提供 MessagesState 作为常用消息 State。

Graph 编译

先用 StateGraph 声明拓扑，再调用 compile() 生成可运行对象。编译阶段会检查部分结构问题，并注入 Checkpointer、Store 或中断配置。

最小状态图

先写一个完全不调用模型的示例：

from typing import Literal, TypedDict

from langgraph.graph import END, START, StateGraph


class ReviewState(TypedDict):
    amount: int
    risk: Literal["normal", "high"]
    result: str


def assess_risk(state: ReviewState) -> dict:
    risk = "high" if state["amount"] >= 10_000 else "normal"
    return {"risk": risk}


def route_by_risk(state: ReviewState) -> Literal["manual_review", "auto_approve"]:
    return "manual_review" if state["risk"] == "high" else "auto_approve"


def manual_review(state: ReviewState) -> dict:
    return {"result": "等待人工审核"}


def auto_approve(state: ReviewState) -> dict:
    return {"result": "自动通过"}


builder = StateGraph(ReviewState)
builder.add_node("assess_risk", assess_risk)
builder.add_node("manual_review", manual_review)
builder.add_node("auto_approve", auto_approve)

builder.add_edge(START, "assess_risk")
builder.add_conditional_edges("assess_risk", route_by_risk)
builder.add_edge("manual_review", END)
builder.add_edge("auto_approve", END)

graph = builder.compile()
result = graph.invoke({"amount": 12_000, "risk": "normal", "result": ""})
print(result)

这个例子刻意先不用 LLM，因为 Graph 的本质是状态机和数据流，不是提示词包装器。

手写模型—工具循环

LangChain create_agent 已经封装了常见循环。为了理解两层关系，可以用 LangGraph 显式写出来：

from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langgraph.graph import END, START, MessagesState, StateGraph
from langgraph.prebuilt import ToolNode, tools_condition


@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气。"""
    return f"{city}：晴，24°C"


tools = [get_weather]
model = init_chat_model("openai:gpt-5.5").bind_tools(tools)


def call_model(state: MessagesState) -> dict:
    response = model.invoke(state["messages"])
    return {"messages": [response]}


builder = StateGraph(MessagesState)
builder.add_node("agent", call_model)
builder.add_node("tools", ToolNode(tools))

builder.add_edge(START, "agent")
builder.add_conditional_edges(
    "agent",
    tools_condition,
    {"tools": "tools", END: END},
)
builder.add_edge("tools", "agent")

graph = builder.compile()

tools_condition 检查最后一条 AI 消息：存在 Tool Call 就路由到 tools，否则结束。ToolNode 执行工具并产生 ToolMessage，然后回到模型。

如果业务只需要这张标准图，使用 create_agent 更简洁；只有需要插入自定义审批、复杂路由、批处理或特殊状态时，手写图才有明显价值。

Pregel 与 Super-step 心智模型

LangGraph 的执行受到 Pregel/BSP 思想启发。可以把一次运行理解为多个 Super-step：

  • 当前可执行的一组节点在同一轮运行。
  • 节点返回 State 更新。
  • Runtime 使用 Reducer 合并更新。
  • 更新完成后，下一组节点被激活。

这个模型解释了为什么并行更新必须有明确合并规则，也解释了 Checkpoint 为什么通常围绕执行步骤保存，而不是随意保存半个函数的局部变量。

Persistence 与 Checkpoint

给图配置 Checkpointer 后，Runtime 会把每个线程的 State 按执行步骤保存。

from langgraph.checkpoint.memory import InMemorySaver


checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "ticket-2026-001"}}

first = graph.invoke(
    {"messages": [{"role": "user", "content": "查询上海天气"}]},
    config=config,
)

thread_id 是 Checkpoint 的逻辑分区键：

  • 相同 thread_id 会继续同一线程的历史。
  • 不同 thread_id 应彼此隔离。
  • 它不是用户身份，也不能替代认证授权。

生产环境不能使用 InMemorySaver 承诺持久恢复。应选择数据库支持的 Checkpointer，并考虑租户隔离、加密、保留期、迁移、清理、备份和恢复。

Checkpoint 可支持：

  • 进程失败后的恢复。
  • 查看当前和历史 State。
  • Human-in-the-loop 暂停。
  • 从旧 Checkpoint 派生新执行。
  • 调试时的时间旅行与状态回放。

Checkpoint 不是业务数据库事务 Checkpoint 保存编排状态，不能让“写业务数据库 + 写 Checkpoint”天然成为一个原子事务。跨系统副作用仍需幂等键、Outbox、状态核对或补偿机制。

Interrupt 与 Human-in-the-loop

interrupt() 可以在节点内部暂停执行，把可序列化的数据交给外部审批者；恢复时用 Command(resume=...) 提供答案。

from typing import TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt


class ApprovalState(TypedDict):
    change_id: str
    summary: str
    approved: bool | None


def request_approval(state: ApprovalState) -> dict:
    decision = interrupt(
        {
            "change_id": state["change_id"],
            "summary": state["summary"],
            "question": "是否批准执行该变更？",
        }
    )
    return {"approved": decision["approved"]}


builder = StateGraph(ApprovalState)
builder.add_node("request_approval", request_approval)
builder.add_edge(START, "request_approval")
builder.add_edge("request_approval", END)

graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "change-42"}}

paused = graph.invoke(
    {"change_id": "CHG-42", "summary": "升级 API", "approved": None},
    config=config,
)

completed = graph.invoke(
    Command(resume={"approved": True}),
    config=config,
)

Interrupt 的关键语义

恢复时，Runtime 会从包含 interrupt() 的节点开头重新执行，不是从 Python 函数中断的那一行继续。因此：

  • interrupt() 之前的代码可能再次执行。
  • 中断前的副作用必须幂等，或移到中断之后、拆到独立节点。
  • 不要用裸 try/except 包住 interrupt()；它通过特殊异常通知 Runtime 暂停。
  • 同一节点中的多个 Interrupt 依赖稳定顺序，不要在恢复时改变调用顺序。
  • 传给 Interrupt 的值应可序列化，不要传函数、数据库连接或复杂对象实例。

Human-in-the-loop 不是一个 UI 按钮，而是“持久化暂停 + 外部身份授权 + 审批数据 + 可恢复执行 + 审计”的组合。

Command

Command 可以在一个结果中同时表达 State 更新和下一跳，也用于恢复 Interrupt。概念上：

from typing import Literal
from langgraph.types import Command


def decide(state: WorkflowState) -> Command[Literal["review", "execute"]]:
    target = "review" if state["category"] == "high_risk" else "execute"
    return Command(update={"evidence": ["routing-complete"]}, goto=target)

普通条件边适合“路由与节点逻辑分离”；Command 适合节点在产生更新的同时决定下一跳。团队应选择一致风格，避免控制流隐藏在各处。

并行、Send 与 Map-Reduce

一个节点可以扇出到多个节点并行执行。动态数量的并行任务可通过 Send 表达，例如为每份文档派发摘要任务，再通过 Reducer 合并结果。

并行设计要明确：

  • 各分支是否读同一版本的 State。
  • 多分支写同一字段时使用什么 Reducer。
  • 单个分支失败是终止整轮、重试该分支，还是产生显式失败结果。
  • 外部 API 的并发、限流和成本上限。
  • 合并结果是否需要保持稳定顺序。

Subgraph

Subgraph 用于封装可复用的工作流或隔离不同 Agent 的状态。常见场景包括：

  • 主图根据任务类型调用不同领域子图。
  • 每个子 Agent 拥有自己的内部状态，只把必要结果返回主图。
  • 团队分别维护审批、检索、代码生成等子流程。

子图边界应像服务接口一样清晰：输入输出契约稳定、内部 State 不泄漏、错误语义明确。不要把每个函数都变成子图。

Streaming

图可使用 stream / astream 暴露运行中的更新。根据模式可以观察 State 更新、消息 Token、调试事件等。

for event in graph.stream(
    {"messages": [{"role": "user", "content": "你好"}]},
    stream_mode="updates",
):
    print(event)

流式输出改善用户体验，但不会让后端任务天然可靠。客户端断线后，任务是否继续、如何重连、事件是否重放，需要由部署层、持久化和 API 协议共同定义。

错误、重试与幂等

应先区分错误类型，再决定策略：

错误类型 示例 处理原则
瞬时基础设施错误 连接重置、限流、暂时超时 有界重试、退避、抖动
永久配置错误 密钥无效、模型不存在 立即失败并暴露配置问题
业务校验错误 参数非法、状态不允许变更 不重试，返回明确错误
模型质量错误 分类错误、幻觉 评估、规则约束、人工审核
副作用不确定 请求超时但不知道对方是否成功 使用幂等键并查询权威状态

Durable Execution 不等于副作用 Exactly-once。节点可能因为恢复、超时或 Interrupt 被再次执行。写操作应以业务操作 ID 作为幂等键，并让服务端能识别重复请求。

常见失败与诊断

现象 常见原因 诊断方向
State 字段被意外覆盖 没有定义 Reducer 检查并行更新和字段注解
图一直循环 路由条件永远不满足结束条件 记录 State 演进并设置递归上限
恢复后重复写数据 Interrupt 或失败导致节点重跑 拆分副作用并增加幂等键
同一用户看不到历史 每次使用了不同 thread_id 检查线程 ID 生成和传递
不同会话串数据 复用了不该共享的 thread_id 检查租户、用户、会话分区
InMemory 本地正常、重启丢失 使用了非持久 Checkpointer 换用生产持久化实现并做恢复测试
并行执行报 State 冲突 多节点写同一字段且无 Reducer 定义合并语义或拆分字段
Human-in-the-loop 无法恢复 没有 Checkpointer 或 thread_id 不一致 检查编译参数和恢复配置

测试策略

Node 单元测试

直接给函数传入 State，验证返回的部分更新；模型和外部 API 使用可控替身。

Router 单元测试

为每个边界状态验证下一跳，确保存在可达的结束路径。

Graph 路径测试

覆盖正常路径、高风险路径、循环退出和并行合并。断言最终 State 和经过的节点，而不只看最后一句模型回复。

Persistence 测试

运行到中间步骤，销毁进程或重新创建 Graph 实例，再用相同 thread_id 验证能否恢复。仅在同一进程内连续 invoke 不算完整恢复验证。

Interrupt 测试

验证暂停负载、未审批时无副作用、批准和拒绝两条路径，以及恢复时不会产生重复写。

故障注入

在模型、Tool、Checkpointer 和业务 API 的调用点注入超时、限流和未知结果，验证重试上限、幂等和审计记录。

面试问答

LangGraph 和普通 DAG 工作流有什么区别

它支持循环、有状态执行、持久化、Interrupt 和 Agentic 决策，适合非固定终止步数的 Agent；传统 DAG 通常更偏无环批处理。LangGraph 仍然可以表达确定性 DAG。

State 为什么返回部分更新而不是直接修改

部分更新让 Runtime 能通过 Reducer 统一合并、记录 Checkpoint、支持并行节点，并更清楚地观测每个节点造成了什么变化。

Checkpointer 和 Store 有什么区别

Checkpointer 保存某个 thread_id 的执行 State 和历史，用于恢复；Store 保存跨线程访问的长期数据。两者都不能自动替代业务数据库。

Interrupt 为什么要求副作用幂等

恢复时节点从开头重跑，中断前代码可能再次执行。非幂等写会产生重复记录、重复通知或重复扣款，因此要把副作用移到审批后或用幂等键保护。

LangGraph 是否保证 Exactly-once

不能把编排恢复能力等同于外部副作用 Exactly-once。跨模型、数据库和第三方 API 时，应按可能重复执行设计，并通过幂等、Outbox、核对与补偿达到业务一致性。
