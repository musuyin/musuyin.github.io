LangChain 核心原理与使用

2026-09-15

#AI#Agent#LangChain

理解主线

Tool Calling 只产生工具请求，工具是否能执行仍由运行时校验。学习 LangChain 时先观察完整消息序列，再引入 create_agent、结构化输出和中间件，避免把框架接口误当成业务正确性保证。

LangChain 解决什么问题

直接调用模型 API 并不困难，困难的是应用很快需要处理不同模型的消息格式、工具 Schema、流式输出、结构化结果、重试、动态提示词、上下文裁剪和观测。LangChain 把这些常见能力组织成较统一的接口，并提供一个可配置的 Agent Harness。

当前 LangChain v1 的核心入口是 create_agent。官方用下面的公式描述它：

Agent = Model + Harness
  • Model 提供推理和生成能力。
  • Harness 是包围模型的运行骨架，包括系统提示词、工具、模型—工具循环、状态与中间件。

LangChain 降低的是集成和编排成本，不会自动解决提示词质量、工具权限、业务幂等、检索质量和结果评估。

安装与版本管理

python -m venv .venv
source .venv/bin/activate
python -m pip install -U langchain

模型供应商通常位于独立集成包中。例如 OpenAI 集成：

python -m pip install -U langchain-openai

学习时可以使用最新版理解概念；项目中应锁定依赖并提交锁文件，避免上游升级后导入路径或行为漂移。密钥只通过环境变量或 Secret 管理系统注入，不应写进源码、笔记示例、日志或命令历史。

模型与消息

模型接收的不只是一个字符串，而是一组带角色的消息。常见角色包括：

  • system：应用给模型的长期行为约束。
  • user：用户请求。
  • assistant：模型此前的回复。
  • tool：某次工具调用的执行结果，并通过调用 ID 与请求对应。
from langchain.chat_models import init_chat_model

model = init_chat_model(
    "openai:gpt-5.5",
    temperature=0,
)

response = model.invoke(
    [
        {"role": "system", "content": "回答应简洁、可验证。"},
        {"role": "user", "content": "什么是幂等？"},
    ]
)

print(response.text)

模型标识只是示例，应替换为当前账号实际可用的模型。temperature=0 只能降低随机性，不能保证模型输出完全确定。

消息为什么比字符串重要

消息保留了角色、工具调用、图片等内容块和元数据。Agent 判断“这段文字是谁说的”“这个结果属于哪个工具调用”依赖这些结构。把所有历史拼成一个长字符串，会丢失协议语义并增加 Prompt Injection 风险。

Tool Calling

Tool 是一个带名称、说明和参数 Schema 的可执行函数。模型只负责提出调用请求，真正执行函数的是 Agent Runtime。

from langchain.tools import tool


@tool
def get_order_status(order_id: str) -> str:
    """按订单 ID 查询当前状态；仅用于读取，不修改订单。"""
    return f"订单 {order_id} 当前状态为 PAID"

工具设计应明确：

  • 名称和描述说明“什么时候用”以及“不能做什么”。
  • 参数使用明确类型与业务含义，不把整段自然语言丢给工具自行猜测。
  • 读取工具与写入工具分开，便于授权、审计和审批。
  • 返回模型可理解的业务错误，不要只返回模糊的 500。
  • 写操作必须考虑幂等键、权限、超时、重试和审计。

工具调用不是授权 模型选择了某个工具，不代表该用户有权执行。参数校验、身份认证、资源级授权和副作用确认必须由确定性代码完成。

使用 create_agent

from langchain.agents import create_agent
from langchain.tools import tool


@tool
def get_order_status(order_id: str) -> str:
    """按订单 ID 查询当前订单状态。"""
    return f"订单 {order_id} 当前状态为 PAID"


agent = create_agent(
    model="openai:gpt-5.5",
    tools=[get_order_status],
    system_prompt=(
        "你是订单助手。先确认订单 ID，再查询工具；"
        "不得编造订单状态。"
    ),
)

result = agent.invoke(
    {
        "messages": [
            {"role": "user", "content": "查询订单 A-1024"}
        ]
    }
)

print(result["messages"][-1].text)

运行过程可以抽象为：

flowchart LR
    Input[用户消息] --> Model[调用模型]
    Model --> Decision{模型输出类型}
    Decision -->|Tool Call| Runtime[校验并执行 Tool]
    Runtime --> ToolMessage[追加 ToolMessage]
    ToolMessage --> Model
    Decision -->|Final Answer| Output[返回最终消息]

这里的循环是 LangChain Agent 的核心：模型每轮只决定下一步，Runtime 执行工具后把结果追加回消息，再次调用模型，直到模型不再请求工具并给出最终回答。必须为生产应用设置最大步数、超时和成本边界，避免错误工具描述或模型判断导致无限循环。

结构化输出

业务系统通常需要稳定字段而不是一段自由文本。可以用 Pydantic 定义输出契约：

from typing import Literal

from pydantic import BaseModel, Field
from langchain.agents import create_agent


class TicketClassification(BaseModel):
    category: Literal["account", "payment", "delivery"]
    priority: Literal["low", "medium", "high"]
    reason: str = Field(description="分类依据，必须引用用户消息中的事实")


agent = create_agent(
    model="openai:gpt-5.5",
    tools=[],
    response_format=TicketClassification,
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "已经扣款但订单仍显示未支付"}]}
)

classification = result["structured_response"]
print(classification.priority)

结构化输出保证的是输出能通过 Schema 校验，不保证业务判断一定正确。仍要使用测试集评估分类准确率，并对高风险决定增加规则或人工复核。

Middleware

Middleware 在 Agent 循环的特定阶段插入控制逻辑。适合集中处理横切关注点，例如：

  • 根据用户角色动态生成系统提示词。
  • 在调用模型前裁剪或摘要上下文。
  • 根据当前状态限制可见工具。
  • 对模型或工具调用记录指标。
  • 对敏感信息做确定性脱敏。
  • 为高风险工具增加审批。
  • 统一模型重试、降载或调用预算。

Middleware 的价值不是“能写 Hook”，而是让这些规则不散落在每个 Tool 和 Prompt 中。顺序很重要：认证、授权、脱敏、模型调用、结果校验之间不能随意交换。

不要隐藏错误 重试只针对明确的瞬时错误，并设置上限。业务校验失败、权限不足、Schema 不兼容等错误应直接暴露为明确失败，不应通过静默降级掩盖。

短期记忆与线程

LangChain Agent 建立在 LangGraph 上，可以通过 Checkpointer 保存线程内状态：

from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver


checkpointer = InMemorySaver()

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[],
    checkpointer=checkpointer,
)

config = {"configurable": {"thread_id": "conversation-42"}}

agent.invoke(
    {"messages": [{"role": "user", "content": "记住项目代号是 Aurora"}]},
    config=config,
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "项目代号是什么？"}]},
    config=config,
)

InMemorySaver 只适合学习和测试，进程重启后内容会丢失。生产环境应选择持久化 Checkpointer，并设计线程 ID 的租户隔离、生命周期、清理与访问控制。

对话历史越长，模型输入越贵且注意力越分散。需要根据业务设计消息裁剪、摘要或检索，而不是无限追加全部历史。

RAG 在 LangChain 中的位置

RAG 不是单一类，而是一条数据链路：

离线：文档加载 → 清洗 → 切分 → Embedding → 索引
在线：问题理解 → 检索 → 过滤/重排 → Context 组装 → 生成 → 引用

LangChain 提供 Loader、Text Splitter、Embedding、Vector Store 和 Retriever 的集成。它能减少适配代码，但切分质量、权限过滤、召回率、重排、来源引用和评估仍由应用负责。详细原理见 RAG。

检索能力有两种常见接法：

  • 固定检索链路：每个问题都先检索再生成。路径稳定，适合知识库问答。
  • Retriever Tool：把检索暴露为 Tool，由 Agent 判断何时检索。更灵活，但也可能漏检索或重复检索。

有明确知识边界的问答系统通常应优先使用固定检索链路，避免把“是否查证”完全交给模型。

Runnable 与 LCEL

LangChain 组件通常实现 Runnable 接口，常见调用方式包括：

  • invoke：单次同步调用。
  • ainvoke：单次异步调用。
  • batch / abatch：批量调用。
  • stream / astream：流式返回。

LCEL 使用管道符组合 Runnable：

chain = prompt | model | parser
result = chain.invoke({"topic": "LangGraph"})

LCEL 适合清晰的转换流水线；如果流程包含循环、暂停恢复、复杂分支和持久状态，LangGraph 更容易表达和维护。

常见失败与诊断

现象 常见原因 诊断方向
模型不调用工具 Tool 描述模糊，Prompt 未说明证据要求 检查 Tool Schema 和 Trace
模型调用错误工具 工具职责重叠、名称相似 拆分工具并补充边界说明
工具参数经常校验失败 参数类型过宽或描述不清 收紧 Schema，增加枚举与字段说明
Agent 循环过多 工具结果不完整，模型看不懂错误 检查每轮消息和终止条件
对话越聊越差 Context 过长、旧信息污染 统计 Token，设计裁剪和摘要
结构化输出合法但判断错误 Schema 只校验格式 建立标注数据集与质量评估
本地成功、生产失败 配置、权限、超时、并发差异 对外部依赖做真实集成测试

测试重点

Tool 单元测试

不调用模型，直接测试参数校验、权限、幂等、错误语义和返回结构。

Agent 路径测试

使用可控模型或录制响应，验证特定输入是否触发预期 Tool、参数是否正确、是否在规定步数内结束。

质量评估

建立包含正常、边界、对抗和越权请求的数据集，分别度量：

  • 最终答案正确率。
  • 工具选择正确率。
  • 工具参数正确率。
  • 拒答与越权拦截率。
  • 延迟、Token 和调用成本。

真实集成测试

Mock 只能证明应用按预期发出了调用，不能证明模型供应商、凭据、网络、配额和真实业务 API 能协同工作。上线前仍需在受控环境运行真实集成测试。

面试问答

LangChain 的核心价值是什么

它提供模型和工具等组件的统一接口，以及可组合的 Agent Harness，减少供应商适配和模型—工具循环的样板代码。它不替业务系统承担授权、幂等、一致性和质量评估。

Tool Calling 和直接调用函数有什么区别

直接调用函数时，应用代码拥有决策权；Tool Calling 时，模型先根据 Schema 生成调用意图和参数，再由 Runtime 校验并执行。真正的权限控制仍在 Runtime 和业务服务。

为什么结构化输出仍可能不可靠

Schema 只保证字段、类型和枚举合法，不保证模型依据充分、分类正确。业务正确性要靠规则、数据集评估和人工审批。

什么时候不该用 Agent

当步骤、判断条件和数据来源都明确时，普通函数或确定性工作流通常成本更低、可测试性更强。只有决策空间难以用规则枚举、且错误风险可控时，才把局部决策交给模型。
