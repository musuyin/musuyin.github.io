DBCI Agent 沙箱环境实现

2026-09-15

#Agent#Sandbox#Kubernetes#SRT#Bubblewrap#安全

理解主线

这份实现包含两个不同边界：Kubernetes 层创建工作负载，容器内 SRT 限制具体命令的执行环境。Pod 叫 Sandbox、文件工具做路径检查、Bash 经过 SRT，三者不能互相代替。

本文基于 dbci-agentic-ai-platform 当前 main 分支提交 2e4221591816f27767abf625096fe7d48ecbad4b 的实际源码，解释项目中的沙箱环境如何创建、Agent 命令如何执行、文件和网络如何受限，以及当前设计能防住什么、不能防住什么。

本文假设读者了解 Docker 的基础概念，例如镜像、容器、Volume 和端口，但不要求提前理解 Kubernetes Controller、CRD、SRT、bubblewrap、gVisor 或 Kata Containers。

阅读完成后，应当能够回答：

  • Agent 和 SandboxAgent 到底有什么区别？
  • 为什么仓库里同时出现 SandboxAgent、Sandbox 和 SRT？
  • 谁真正创建并管理 Sandbox Pod？
  • singleton Pod、privileged、gVisor、Kata 和 SandboxClaim 分别是什么？
  • Agent 生成的 Bash 命令在哪里执行？
  • 项目有没有识别并拦截 rm -rf、kubectl delete 等高危命令？
  • 文件、网络、凭据、进程和 Kubernetes 权限分别由哪一层控制？
  • 当前实现距离“可以安全运行完全不可信代码”还有哪些差距？

先说结论

本项目不是用单一机制完成所有沙箱隔离，而是叠加了两层不同的沙箱：

层次 实现 保护对象 主要作用
Kubernetes 工作负载层 SandboxAgent 转换成 agents.x-k8s.io/Sandbox 整个 Agent Runtime 用单独 Pod 和稳定 Service 运行 Agent
容器内命令层 Anthropic Sandbox Runtime，即 SRT Skills 的 Bash 子进程 限制子进程的文件写入和网络访问

最容易误解的一点是：

SandboxAgent 并不表示 Agent 主进程发出的全部请求都经过 SRT，也不表示 Kubernetes 自动为它配置了 gVisor、Kata 或 NetworkPolicy。

当前源码中，SRT 可以确认保护的是 Skills 暴露的 bash 工具。文件工具还有自己的路径检查。Agent 主进程的模型调用、MCP 调用及额外 Sidecar，并不会因为存在 spec.sandbox.network 就自动经过 SRT。

用 Docker 经验理解整体架构

如果只从 Docker 角度看，可以先把两层机制类比成：

  • 外层 Sandbox：不是直接执行 docker run，而是提交一张 Kubernetes“运行申请单”，让另一个 Controller 创建和维护容器。
  • 内层 SRT：已经进入 Agent 容器后，再用 bubblewrap 给某一条 Bash 命令套一个更小的隔离环境。
flowchart TB
    U[用户在 UI 或 CLI 创建 Agent] --> API[Controller API]
    API -->|workloadMode=deployment| A[kagent.dev Agent]
    API -->|workloadMode=sandbox| SA[kagent.dev SandboxAgent]

    A --> T[公共 Agent 编译器]
    SA --> T

    T -->|普通模式| D[Deployment 和 Service]
    T -->|沙箱模式| S[agents.x-k8s.io Sandbox]
    S --> ASC[外部 agent-sandbox Controller]
    ASC --> P[单副本 Agent Pod 和稳定 Service]

    R -->|Skills bash tool| SRT[srt]

    B -->|代理和域名白名单| NET[受控网络]

术语先扫盲

CLI 分流

*CLI（Command-Line Interface，命令行界面）*就是终端命令程序。本项目的 CLI 可以调用普通 Agent，也可以调用 SandboxAgent。

所谓“CLI 分流”并不是一种隔离技术，只是 CLI 根据 Agent 类型选择不同 URL：

func buildA2AURL(baseURL, namespace, agent string, agentResponse *api.AgentResponse) string {
    a2aPath := "api/a2a"
    if agentResponse != nil && agentResponse.WorkloadMode == v1alpha2.WorkloadModeSandbox {
        a2aPath = "api/a2a-sandboxes"
    }
    return fmt.Sprintf("%s/%s/%s/%s", baseURL, a2aPath, namespace, agent)
}

源码：go/cli/internal/cli/agent/invoke.go。

类型 外部访问路径
普通 Agent /api/a2a/namespace/name
SandboxAgent /api/a2a-sandboxes/namespace/name

分开路径的主要目的是避免同 namespace、同名字的 Agent 和 SandboxAgent 在路由表中冲突。安全认证和授权仍由 Controller 的 A2A Handler 统一处理。

Pod

Docker 通常直接管理 Container；Kubernetes 通常管理 Pod。Pod 是一个或多个 Container 的包装层。

同一个 Pod 内的 Container：

  • 共享 Pod IP；
  • 可以通过 localhost 通信；
  • 可以挂载同一个 Volume；
  • 生命周期通常由同一个 Kubernetes 工作负载对象管理。

因此，Pod 不是虚拟机。默认情况下，容器仍共享宿主机内核。

singleton Pod

Singleton 表示“单实例”。本项目生成的外部 Sandbox CR 将 replicas 固定为 1，因此一个 SandboxAgent 对应一个主要运行 Pod。

它与普通 Deployment 的差异可以类比为：

普通 Deployment agent-sandbox Sandbox
偏向无状态、多副本服务 偏向有稳定身份的单实例工作环境
可滚动更新多个副本 当前最多 0 或 1 个 Pod
Pod 名称和 IP 可以变化 通过稳定 Service 暴露固定网络身份

这里的 singleton 不等于进程永远不重启，只表示期望副本数为一个。Pod 故障后仍可能被重新创建。

CRD 和 Controller

*CRD（Custom Resource Definition，自定义资源定义）*允许 Kubernetes 支持新的资源类型。

Docker 用户可以这样理解：

  • CRD 类似新增一种自定义 docker-compose 配置格式；
  • Custom Resource 是按照该格式提交的一份配置；
  • Controller 是持续读取配置并执行 docker run、检查状态、修复偏差的后台程序；
  • Reconcile 是 Controller 每次把“实际状态”修正为“期望状态”的过程。

本项目涉及两个不同 API Group：

对象 API Group 所属项目 作用
SandboxAgent kagent.dev/v1alpha2 当前仓库 描述 Agent 的模型、工具、Skills 和权限
Sandbox agents.x-k8s.io/v1alpha1 kubernetes-sigs/agent-sandbox 描述实际 Sandbox Pod

SandboxTemplate 和 SandboxClaim

这两个概念来自外部 agent-sandbox 项目的扩展模块：

  • SandboxTemplate：预先定义一份可复用的沙箱模板；
  • SandboxClaim：用户提交一张申请单，请求系统从模板分配一个沙箱；
  • Warm Pool：提前启动一批空闲沙箱，收到 Claim 时快速分配。

本仓库当前都没有使用。它直接创建具体的 Sandbox CR，因此链路是：

SandboxAgent -> Sandbox -> Pod

而不是：

SandboxAgent -> SandboxClaim -> SandboxTemplate -> Warm Pool -> Sandbox -> Pod

SRT

*SRT（Sandbox Runtime）*是 Anthropic 开源的实验性沙箱运行器。它不是 Docker，也不是 Kubernetes Runtime。它包装某一个待执行命令，并使用操作系统能力限制该命令及其子进程。

在 Linux 上，SRT 主要使用：

  • bubblewrap：创建文件系统、网络、PID 等 namespace；
  • HTTP/HTTPS Proxy：检查目标域名是否在白名单中；
  • SOCKS5 Proxy：代理其他 TCP 流量；
  • socat：在被隔离的网络 namespace 和代理之间桥接；
  • seccomp：可用于限制 Unix Socket 等系统调用。

bubblewrap

*bubblewrap（bwrap）*是 Linux 上创建轻量隔离环境的工具。它使用的 namespace、bind mount 等能力和 Docker 底层机制有相似之处，但它不负责镜像、镜像仓库、容器网络编排或完整生命周期管理。

在本项目中，Docker/Kubernetes 先启动 Agent 容器，bubblewrap 再在容器内部包住 Bash 子进程：

Kubernetes Pod
└── Agent Container
    ├── Go ADK 主进程
    └── srt
        └── bubblewrap
            └── bash -c "模型生成的命令"

privileged

Kubernetes 的 securityContext.privileged=true 类似 Docker 的 –privileged。它会大幅放宽容器能够使用的 Linux capabilities、设备和内核功能限制。

它不是“让应用用户变成 root”这么简单，而是让容器获得接近宿主机级别的能力，因此通常被视为高风险设置。

本项目在 Skills 或代码执行需要完整 bubblewrap 隔离、并且用户没有显式设置 allowPrivilegeEscalation=false 时，会自动将 Agent 主容器设为 privileged。后文会分析这里的安全取舍。

gVisor 和 Kata Containers

Docker 默认容器和宿主机共享 Linux 内核。容器逃逸漏洞一旦利用成功，可能影响宿主机。

  • gVisor 在应用与宿主机内核之间增加一个用户态内核兼容层，拦截大部分系统调用；
  • Kata Containers 通常为容器启动一个轻量虚拟机，隔离边界更接近 VM；
  • Kubernetes 通过 runtimeClassName 指定 Pod 使用哪一种 Runtime。

本仓库当前生成的 Sandbox Pod 没有主动设置 runtimeClassName，因此不能因为资源名叫 Sandbox 就推断它已经运行在 gVisor 或 Kata 中。实际隔离强度取决于集群默认容器运行时和外部 agent-sandbox 的部署配置。

Kubernetes 工作负载沙箱如何创建

API 根据 workloadMode 选择资源类型

创建请求带有 workloadMode。服务端将它标准化后选择 Kubernetes 对象：

workloadMode := v1alpha2.WorkloadMode(strings.ToLower(strings.TrimSpace(req.WorkloadMode)))
if workloadMode == "" {
    workloadMode = v1alpha2.WorkloadModeDeployment
}

switch workloadMode {
case v1alpha2.WorkloadModeDeployment:
    agent = &v1alpha2.Agent{Spec: spec}
case v1alpha2.WorkloadModeSandbox:
    agent = &v1alpha2.SandboxAgent{Spec: spec}
default:
    return nil, status.Errorf(codes.InvalidArgument, "unsupported workloadMode")
}

源码：go/controller/internal/grpcserver/agents.go。

这里没有静默回退：无法识别的模式直接报错。只有调用方完全不传 workloadMode 时，才使用兼容默认值 deployment。

Agent 和 SandboxAgent 复用同一套业务配置

源码通过 AgentObject 接口统一访问二者：

type AgentObject interface {
    client.Object
    GetAgentSpec() *AgentSpec
    GetAgentStatus() *AgentStatus
    GetWorkloadMode() WorkloadMode
}

func (a *Agent) GetWorkloadMode() WorkloadMode {
    return WorkloadModeDeployment
}

func (a *SandboxAgent) GetWorkloadMode() WorkloadMode {
    return WorkloadModeSandbox
}

源码：go/api/v1alpha2/agentobject.go。

因此模型配置、MCP 工具、Agent Tool、SkillSet、Prompt、Memory、ClusterAccess 等编译逻辑基本共享，区别集中在最后的工作负载输出阶段。

Controller 先编译，再生成 Kubernetes 对象

SandboxAgent Controller 收到事件后执行以下流程：

  1. 获取 SandboxAgent。
  2. 检查跨 namespace 引用。
  3. 将 CRD 配置编译成 ADK AgentConfig。
  4. 生成 Secret、ServiceAccount、PodTemplate 等对象。
  5. 把 PodTemplate 包装成外部 Sandbox CR。
  6. 创建或更新这些对象。
  7. 将 Agent 配置投影到数据库。
  8. 更新 SandboxAgent 的 Accepted 和 Ready 状态。

核心代码：

inputs, err := a.adkTranslator.CompileAgent(ctx, agent)
if err != nil {
    return fmt.Errorf("failed to compile %s: %w", resourceName, err)
}

agentOutputs, err := a.adkTranslator.BuildManifest(ctx, agent, inputs)
if err != nil {
    return fmt.Errorf("failed to build manifest: %w", err)
}

if err := a.reconcileDesiredObjects(ctx, agent, agentOutputs.Manifest, ownedObjects); err != nil {
    return fmt.Errorf("failed to reconcile owned objects: %w", err)
}

源码：go/controller/internal/controller/reconciler/reconciler.go。

普通模式和 Sandbox 模式在最后一步分叉

if manifestCtx.runInSandbox() {
    return a.sandboxBackend.BuildSandbox(ctx, sandboxbackend.BuildInput{
        Agent:       manifestCtx.agent,
        PodTemplate: podTemplate,
    })
}

return []client.Object{
    &appsv1.Deployment{/* ... */},
    &corev1.Service{/* ... */},
}, nil

源码：go/controller/internal/controller/translator/agent/manifest_builder.go。

这说明两种模式使用的是同一套 Agent Runtime 镜像和 PodTemplate 构建逻辑，不是两套完全不同的 Agent 实现。

Sandbox backend 生成什么

replicas := int32(1)
sb := &agentsandboxv1.Sandbox{
    TypeMeta: metav1.TypeMeta{
        APIVersion: agentsandboxv1.GroupVersion.String(),
        Kind:       "Sandbox",
    },
    ObjectMeta: metav1.ObjectMeta{
        Name:      name,
        Namespace: in.Agent.GetNamespace(),
    },
    Spec: agentsandboxv1.SandboxSpec{
        PodTemplate: pt,
        Replicas:    &replicas,
    },
}

源码：go/controller/pkg/sandboxbackend/agentsxk8s/agentsxk8s.go。

这里可以得到四个结论：

  • 直接创建 Sandbox，不经过 SandboxTemplate 或 SandboxClaim；
  • 固定单副本；
  • PodTemplate 中的容器、环境变量、Volume、探针和安全上下文会原样带过去；
  • 当前仓库只构建声明，真正创建 Pod 和 Service 的是外部 agent-sandbox Controller。

外部依赖缺失时直接失败

当前仓库只在 Go 代码中依赖 sigs.k8s.io/agent-sandbox v0.3.10，Helm Chart 没有安装其 CRD 和 Controller。

每次协调 SandboxAgent 前，代码会查询 Sandbox API：

if err := c.List(ctx, &agentsandboxv1.SandboxList{}, client.Limit(1)); err != nil {
    if meta.IsNoMatchError(err) {
        return fmt.Errorf(
            "agent-sandbox API is not available; install the agent-sandbox CRDs and controller",
        )
    }
    return fmt.Errorf("could not reach agent-sandbox API: %w", err)
}

源码：go/controller/pkg/sandboxbackend/apis_available.go。

这符合 fail-fast 原则：依赖不存在时明确报错，不会偷偷退回普通 Deployment。

Ready 状态如何传递

外部 agent-sandbox Controller 创建 Pod 和 Service 后，会在 Sandbox.status.conditions 中写入 Ready。kagent Controller 再读取该条件并映射到 SandboxAgent：

for i := range sb.Status.Conditions {
    c := sb.Status.Conditions[i]
    if c.Type == string(agentsandboxv1.SandboxConditionReady) {
        return c.Status, c.Reason, c.Message
    }
}
return metav1.ConditionUnknown,
    "SandboxReadyPending",
    "Sandbox Ready condition not yet reported"

UI 在首次聊天前轮询这个 Ready 状态，默认最多等待 120 秒，每 1.5 秒查询一次。超时后明确显示 Timed out waiting for sandbox workload to become ready。

因此，UI 显示的 deploymentReady 对 SandboxAgent 而言，实际代表外部 Sandbox 的 Pod 和 Service 已 Ready，并不表示创建了 Deployment。

容器内 SRT 沙箱如何工作

SRT 被直接打进 Agent 镜像

Agent 使用 golang-adk-full 镜像。Dockerfile 在构建时从 Anthropic 仓库拉取固定 commit，并将 CLI 链接为 /usr/bin/srt：

ARG SRT_COMMIT=ef4afdef4d711ba21a507d7f7369e305f7d3dbfa

RUN git fetch --depth 1 \
    https://github.com/anthropic-experimental/sandbox-runtime.git \
    $SRT_COMMIT && \
    git checkout -q FETCH_HEAD && \
    npm run build

RUN apk add --no-cache \
    bash ca-certificates coreutils curl nodejs \
    bubblewrap socat python3 ripgrep libstdc++

RUN ln -s /opt/sandbox-runtime/dist/cli.js /usr/bin/srt

USER 1001:1001

源码：go/adk/Dockerfile.full。

固定 commit 的好处是构建可复现；代价是升级和安全修复不会自动进入镜像，必须主动更新 SRT_COMMIT 并重新发布镜像。

什么时候生成 SRT 配置

只有以下任一条件成立时，Controller 才生成 srt-settings.json 并注入 KAGENT_SRT_SETTINGS_PATH：

func needsSRTSettings(agent v1alpha2.AgentObject, sandboxCfg *v1alpha2.SandboxConfig) bool {
    spec := agent.GetAgentSpec()
    if spec.Skills != nil {
        return true
    }
    return spec.Declarative != nil &&
        spec.Declarative.ExecuteCodeBlocks != nil &&
        *spec.Declarative.ExecuteCodeBlocks
}

源码：go/controller/internal/controller/translator/agent/manifest_builder.go。

这带来两个容易忽视的事实：

  • 普通 Agent 只要配置 Skills，也会使用容器内 SRT；SRT 并不是 SandboxAgent 专属能力。
  • SandboxAgent 如果没有 Skills，也没有开启 executeCodeBlocks，就不会因为资源类型是 SandboxAgent 而自动执行 SRT 命令。

Bash 工具怎样启动命令

创建 Skills 工具时必须成功构造 CommandExecutor：

commandExecutor, err := skillruntime.NewCommandExecutorFromEnv()
if err != nil {
    return nil, fmt.Errorf("failed to configure bash sandbox: %w", err)
}

NewCommandExecutorFromEnv 要求环境变量中存在 SRT 配置路径：

func resolveSRTSettingsArgs() ([]string, error) {
    settingsPath := strings.TrimSpace(os.Getenv("KAGENT_SRT_SETTINGS_PATH"))
    if settingsPath == "" {
        return nil, fmt.Errorf("KAGENT_SRT_SETTINGS_PATH is not set")
    }
    return []string{"--settings", settingsPath}, nil
}

真正执行时，用户输入中的 command 没有经过危险命令语义分析，而是直接成为 bash -c 的参数：

args := append(append([]string{}, e.srtArgs...), "bash", "-c", command)
cmd := exec.CommandContext(ctx, "srt", args...)
cmd.Dir = workingDir
err := cmd.Run()

等价于：

srt --settings /config/srt-settings.json bash -c '<模型生成的命令>'

源码：go/adk/pkg/skills/shell.go。

命令超时规则是：

  • 默认 30 秒；
  • 只要命令字符串包含 python，使用 60 秒；
  • 可通过 ADK_SKILL_COMMAND_TIMEOUT 和 ADK_SKILL_PYTHON_COMMAND_TIMEOUT 修改。

需要注意：通过字符串是否包含 python 判断超时比较粗糙，它不是命令类型的安全验证。

每个会话的工作目录

每个 Session 会创建：

/tmp/kagent/<session-id>/
├── uploads/
├── outputs/
├── skills -> /workspace/skills
├── .gitconfig
├── .bashrc
└── 其他 SRT 需要遮蔽的占位文件

创建目录前会清理并检查路径：

basePath := filepath.Join(os.TempDir(), "kagent")
sessionPath := filepath.Clean(filepath.Join(basePath, sessionID))

if !strings.HasPrefix(
    sessionPath,
    filepath.Clean(basePath)+string(filepath.Separator),
) {
    return "", fmt.Errorf("invalid sessionID: path traversal detected")
}

源码：go/adk/pkg/skills/discovery.go。

这可以阻止把 Session ID 构造成 ../../etc 一类路径，但它只保护会话目录的生成过程。

文件工具还有第二套路径检查

Skills 工具集除了 bash，还有 read_file、write_file 和 edit_file。这些文件工具并不通过 Bash 执行，而是在 Go 进程中直接读写文件，因此需要单独校验路径。

工具 允许范围
read_file 当前 Session 目录或 Skills 根目录
write_file 只能写当前 Session 目录
edit_file 只能修改当前 Session 目录

读文件时会先解析软链接，再检查最终路径：

resolvedCandidate, err := filepath.EvalSymlinks(candidate)
if err != nil {
    return "", err
}

if !isWithinRoot(resolvedCandidate, sessionRoot) &&
   !isWithinRoot(resolvedCandidate, skillsRoot) {
    return "", fmt.Errorf("path is outside the allowed roots")
}

写新文件时，即使目标文件还不存在，也会向上寻找已经存在的父目录、解析父目录软链接，然后确认最终地址仍位于 Session 目录。这是为了防止：

/tmp/kagent/session-a/link -> /etc
write_file("link/passwd")

通过软链接绕过目录限制。

源码：go/adk/pkg/tools/skills.go。

SRT 文件系统策略

Controller 生成的配置核心内容是：

{
  "filesystem": {
    "denyRead": [],
    "allowWrite": ["/tmp"],
    "denyWrite": []
  },
  "enableWeakerNestedSandbox": true,
  "allowAllUnixSockets": true
}

SRT 的文件权限模型是：

  • 读取采用 deny-only：默认都可以读，只有 denyRead 中的路径不能读；
  • 写入采用 allow-only：默认都不能写，只有 allowWrite 中的路径可以写；
  • denyWrite 可以在已允许写的目录中再次禁止某些子路径。

因此当前项目的实际效果是：

  • Bash 子进程原则上只能写 /tmp；
  • 但读取没有额外限制，因为 denyRead 是空数组；
  • SRT 会额外保护一些危险配置文件，例如 .gitconfig、.bashrc、.mcp.json 和 Git hooks；
  • Agent 容器根文件系统同时被 Kubernetes 设置成只读，形成第二道写保护。

读取没有限制是一个重要边界。 如果 Pod 挂载了 /config、模型 Secret 或 ClusterAccess kubeconfig，Bash 子进程可能读取这些文件。系统提示词中的“不要输出凭据”不是强制安全机制，不能替代 denyRead 或凭据隔离。

Pod 文件系统配置

Controller 为声明式 Agent 创建以下 Volume：

路径 来源 Pod 层权限 用途
/config Secret Volume 默认只读挂载语义 Agent 配置和 srt-settings.json
/tmp emptyDir 可写 Session、uploads、outputs、临时文件
/workspace emptyDir 可写 Skills 初始化和工作区
/workspace/skills Workspace 子目录或 SkillSet 挂载 设计上供读取 Skill 内容
/var/run/secrets/tokens Projected Token 挂载文件 audience 为 kagent 的短期 token

主容器被强制设置：

if readOnlyRootFilesystem {
    securityContext.ReadOnlyRootFilesystem = new(true)
}

同时关闭默认 ServiceAccount Token 自动挂载：

AutomountServiceAccountToken: new(false)

但代码会显式挂载一个 audience 为 kagent、有效期 3600 秒的 projected token。它主要用于 Agent Runtime 向平台证明自己的工作负载身份，不等于通用 Kubernetes 管理凭据。

SRT 网络策略怎样生成

最终 allowedDomains 不是简单照抄用户配置，而是由 Controller 自动合并：

for _, svc := range svcList.Items {
    allowedDomains = append(
        allowedDomains,
        svc.Name+"."+svc.Namespace,
    )
}

if sandboxCfg != nil && sandboxCfg.Network != nil {
    allowedDomains = append(
        allowedDomains,
        sandboxCfg.Network.AllowedDomains...,
    )
}

allowedDomains = append(allowedDomains, mcpServerHosts(cfg)...)
allowedDomains = append(allowedDomains, clusterAccessHosts...)
allowedDomains = append(allowedDomains, platformAllowedDomains...)

完整来源如下：

来源 目的
集群中所有 Service 的 service.namespace 允许调用集群内服务
spec.sandbox.network.allowedDomains 用户显式添加的域名
Agent 配置中的 MCP Server hostname 允许 Skills 访问相关 MCP 地址
ClusterAccess kubeconfig 的 API Server hostname 允许 kubectl 访问目标集群
平台默认域名 Slack 和内部邮件认证等平台集成

平台默认域名当前是：

slack.com
hooks.slack.com
auth.mail.net.sap

最终 SRT 网络配置为：

{
  "network": {
    "allowedDomains": ["自动和手工合并后的域名"],
    "deniedDomains": []
  }
}

SRT 在 Linux 上移除命令进程的普通网络 namespace，并通过 HTTP/HTTPS Proxy、SOCKS5 Proxy 和 Unix Socket 桥接允许的请求。目标域名不在列表时，请求会失败。

但域名白名单只判断“连接到谁”，不理解“请求要做什么”。例如允许 github.com 后，SRT 无法仅凭域名区分读取公开仓库和向攻击者仓库上传数据。

allowAllUnixSockets 的含义

Unix Socket 是同一机器上进程间通信的一种方式，例如 Docker daemon 常使用 /var/run/docker.sock。

当前配置设置：

{"allowAllUnixSockets": true}

这会关闭 SRT 对 Unix Socket 创建的严格阻断。默认 Pod 并没有挂载 Docker Socket，所以这不等于命令天然可以控制宿主机 Docker；但如果以后通过 Volume 或 Sidecar 暴露了高权限 Socket，这个配置会显著放大风险。

enableWeakerNestedSandbox 的含义

SRT 本身运行在 Kubernetes Container 内，即“沙箱里面再启动沙箱”。有些集群禁止容器创建完整 Linux namespace，导致 bubblewrap 无法启动。

当前项目同时采用两项设置：

  • enableWeakerNestedSandbox=true：完整隔离不可用时允许使用适合嵌套容器环境的较弱模式；
  • 如果没有显式禁止权限提升，Skills 会让主容器使用 privileged=true，为 bubblewrap 提供更强的 namespace 能力。

相关代码：

if needCodeExecIsolation &&
   !allowPrivilegeEscalationExplicitlyFalse(securityContext) {
    securityContext.Privileged = new(true)
}

如果用户显式配置：

spec:
  declarative:
    deployment:
      securityContext:
        allowPrivilegeEscalation: false

Controller 不会再设置 privileged。此时 SRT 只能依赖集群是否允许非特权 User Namespace，并可能进入较弱嵌套模式。

这不是“越 privileged 越安全”的意思，而是一个明显的安全取舍：完整 bubblewrap 隔离需要更多内核能力，但把整个 Agent 容器设为 privileged 又扩大了容器逃逸后的影响面。

高危命令到底怎样被限制

当前没有高危命令黑名单

当前实现没有在执行前解析命令，也没有维护下面这样的规则：

禁止 rm -rf
禁止 curl | sh
禁止 kubectl delete
禁止 chmod 777
禁止 fork bomb

CommandExecutor 收到模型生成的字符串后，直接交给 srt bash -c。因此它采取的不是“判断这条命令危险不危险”，而是 capability-based security：即使命令本身危险，也通过限制它能访问的文件、网络、凭据和内核能力来缩小破坏范围。

类比 Docker：不是检查容器里能不能执行 rm，而是让容器只能看到自己的文件系统、只挂载必要目录、使用只读根目录和受限网络。rm 仍然存在，但它能删除的东西应该有限。

为什么不应该只依赖命令黑名单

命令黑名单很容易绕过。例如只禁止字符串 rm -rf，模型仍可能生成：

find /tmp -type f -delete
python -c 'import shutil; shutil.rmtree("/tmp/data")'
busybox rm -rf /tmp/data
/bin/rm -r -f /tmp/data

同一种危险操作可以有很多表达形式。Shell 还支持变量、管道、重定向、命令替换和动态下载，因此只做字符串匹配并不能建立可靠安全边界。

更合理的设计是：

  1. 用操作系统隔离限制进程能力。
  2. 用最小文件和网络权限限制可访问资源。
  3. 用 RBAC 或远端权限限制业务操作。
  4. 对不可逆操作增加人工审批。
  5. 记录命令、结果和安全拒绝事件，支持审计。

当前仓库主要实现了前两项的一部分，以及 MCP Tool 的可选人工审批；对 Bash 命令本身没有审批。

各类高危命令的实际结果

命令或行为 当前主要限制 仍需注意的风险
rm -rf / 容器根文件系统只读；SRT 只允许写 /tmp /tmp 下的数据仍可能被删除；是否能影响其他 Session 需要真实环境验证
修改 /etc、/usr/bin 根文件系统只读，SRT 不允许写这些路径 privileged 配置扩大了隔离失效后的风险
读取 /etc/kubeconfig/… 当前 denyRead 为空，原则上允许读取 kubeconfig 虽然只读，但可能被命令读取并外传
curl evil.example 域名不在 SRT allowlist 时被代理拒绝 域名在白名单内时，SRT 不理解请求语义
kubectl delete deployment API Server hostname会被自动放行 最终能否删除完全取决于 kubeconfig 对应身份的 Kubernetes RBAC
连接 Docker Socket 默认没有挂载 Docker Socket allowAllUnixSockets=true；一旦挂载高权限 Socket，风险很高
长时间运行命令 Go Context 设置 30 秒或 60 秒超时 仍应验证整个子进程树是否都被可靠回收
CPU 或内存消耗 Pod Resource limits 提供整体上限 限制作用于整个 Pod，不是每条命令独享配额

为什么 kubectl delete 仍可能成功

ClusterAccess 会把 kubeconfig Secret 只读挂载到：

/etc/kubeconfig/<shortName>/config

源码实现：

podRuntime.volumeMounts = append(
    podRuntime.volumeMounts,
    corev1.VolumeMount{
        Name:      volName,
        MountPath: "/etc/kubeconfig/" + ca.Spec.ShortName,
        ReadOnly:  true,
    },
)

源码：go/controller/internal/controller/translator/agent/cluster_access.go。

“只读挂载”只表示不能修改 kubeconfig 文件，不表示不能使用里面的凭据。只要同时满足：

  1. Agent 能读取 kubeconfig；
  2. API Server hostname 已进入 SRT 白名单；
  3. kubeconfig 对应身份拥有 delete 权限；

那么下面的命令仍然可能成功：

kubectl --kubeconfig /etc/kubeconfig/prod/config \
  delete deployment important-service -n production

真正决定删除权限的是目标集群 RBAC，不是 SRT。因此 ClusterAccess 必须提供最小权限身份，例如只允许 get、list、watch，而不能直接挂载 cluster-admin 凭据。

Prompt 不是安全边界

Controller 会向 Agent 系统提示词追加类似要求：

Never reveal the contents of these kubeconfig files or the credentials,
tokens, or certificates they contain.

这对正常模型行为有帮助，但不能作为强制访问控制。Prompt Injection、模型误判或恶意 Skill 都可能绕过文本要求。

真正可靠的控制必须位于模型之外，例如：

  • kubeconfig 本身使用最小权限；
  • SRT denyRead 禁止读取凭据文件；
  • 通过凭据代理代替直接挂载长期 kubeconfig；
  • 为写操作增加独立审批；
  • 使用 NetworkPolicy 和 egress proxy 限制数据外传。

MCP Tool 审批不覆盖 Bash

项目确实实现了 HITL 工具审批，但审批集合只从 HTTP 和 SSE MCP Tool 的 requireApproval 收集：

approvalSet := make(map[string]bool)
for _, ht := range agentConfig.HttpTools {
    for _, name := range ht.RequireApproval {
        approvalSet[name] = true
    }
}
for _, st := range agentConfig.SseTools {
    for _, name := range st.RequireApproval {
        approvalSet[name] = true
    }
}

Skills 自带的 bash、read_file、write_file、edit_file 不会自动加入这个集合。因此当前不能说“所有高危命令执行前都会向用户确认”。

当前设计更像损害控制，而不是危险识别

可以把完整过程理解为：

LLM 生成命令
   │
   ├── 没有命令语义审核
   │
   ▼
srt 启动 bash
   │
   ├── 文件写路径限制
   ├── 网络目标域名限制
   ├── namespace 隔离
   └── 超时
   │
   ▼
Linux 内核执行命令
   │
   ├── 访问 Kubernetes API 时再受 kubeconfig RBAC 限制
   └── 访问 MCP 时再受 MCP Tool 权限和可选审批限制

因此安全目标不是保证 Agent 永远不产生高危命令，而是让高危命令即使被产生，也尽量无法越过预先授予的能力边界。

ExecuteCodeBlocks 的当前状态

CRD 中有 executeCodeBlocks 字段，描述为自动执行 LLM 响应中的 Python 代码块。但当前 Go ADK 实现没有真正实例化代码执行器。

仓库自己的说明写得很明确：

// Agent.Spec.ExecuteCodeBlocks -> AgentConfig.ExecuteCode
//   - Currently disabled in Go controller
//   - Would enable SandboxedLocalCodeExecutor if true

源码：go/adk/pkg/config/config_usage.go。

当前代码实际完成的是：

  • 把字段写入 AgentConfig；
  • 把 needCodeExecIsolation 设为 true；
  • 生成 SRT 配置；
  • 可能改变容器 SecurityContext。

但在非测试代码中，没有找到读取 ExecuteCode 并创建代码执行器的实现。因此不能把 executeCodeBlocks 当成已经可用的生产功能。Skills Bash 是目前可以从源码确认的 SRT 执行入口。

一个完整配置示例

下面示例创建一个带 Skill 和 ClusterAccess 的 SandboxAgent：

apiVersion: kagent.dev/v1alpha2
kind: SandboxAgent
metadata:
  name: cluster-reader
  namespace: agents
spec:
  type: Declarative
  description: 只读检查 Kubernetes 集群

  sandbox:
    network:
      allowedDomains:
        - api.example.com

  clusterAccess:
    - name: production-readonly

  skills:
    refs:
      - registry.example.com/skills/kubernetes-inspection:1.0.0

  declarative:
    modelConfig: default-model-config
    systemMessage: |
      只允许执行只读检查，不得修改或删除资源。
    deployment:
      securityContext:
        runAsUser: 1001
        runAsGroup: 1001
        runAsNonRoot: true
        allowPrivilegeEscalation: false
        capabilities:
          drop:
            - ALL

这份配置需要正确理解：

  • SandboxAgent 让 Controller 创建外部 Sandbox CR；
  • Skill 使 Agent 获得 Bash 工具，并启用 SRT；
  • allowedDomains 只是在自动域名列表上增加 api.example.com；
  • allowPrivilegeEscalation=false 避免 Controller 自动设置 privileged；
  • systemMessage 中“只读”只是行为指导；
  • 真正保证 kubectl 只读的是 production-readonly kubeconfig 对应的 RBAC。

当前实现的安全边界

已经具备的保护

  • SandboxAgent 缺少外部 agent-sandbox CRD 时明确失败，不回退成 Deployment。
  • 每个 Agent 使用独立 Pod，而不是在 Controller 进程中直接执行命令。
  • Agent 镜像默认使用 UID 1001。
  • 主容器根文件系统只读。
  • /tmp 使用临时 Volume。
  • 不自动挂载默认 Kubernetes ServiceAccount Token。
  • Bash 必须经过 SRT，并且缺少配置时初始化报错。
  • Bash 网络采用域名 allowlist。
  • Bash 写入默认只允许 /tmp。
  • 文件工具执行路径规范化和软链接逃逸检查。
  • 命令具有 30 秒或 60 秒超时。
  • ClusterAccess kubeconfig 以只读 Secret Volume 挂载。
  • MCP HTTP/SSE 工具支持按工具名配置人工审批。

没有实现或需要额外部署的保护

  • 没有 Bash 高危命令黑名单或语义审查。
  • 没有为 Bash 工具配置人工审批。
  • 没有默认 Kubernetes NetworkPolicy。
  • 没有默认 runtimeClassName，因此没有默认启用 gVisor 或 Kata。
  • 没有为每次聊天或每条命令创建独立 Pod。
  • 没有使用 SandboxClaim、SandboxTemplate 或 Warm Pool。
  • 没有在当前 backend 中设置 Sandbox TTL 或自动过期策略。
  • SRT denyRead 为空，不能阻止 Bash 读取挂载进 Pod 的敏感文件。
  • allowWrite=/tmp 不是按 Session 精确授权。
  • allowAllUnixSockets=true 放宽了 Unix Socket 限制。
  • Skills 默认可能触发 privileged=true。
  • SRT 域名规则不检查 URL path、HTTP method 或请求内容。
  • Agent 主进程和 ExtraContainers 不受 SRT 网络白名单控制。

关键设计风险和改进方向

风险：Sandbox 名称可能制造过强安全预期

外部 agent-sandbox 的核心价值是稳定单实例工作负载和生命周期管理。当前仓库没有设置 gVisor、Kata 或额外 VM 隔离。

改进方向：

  • 为 SandboxAgent 提供受管的 runtimeClassName；
  • 在目标集群部署 gVisor 或 Kata；
  • Admission Webhook 强制 SandboxAgent 使用指定 RuntimeClass；
  • 禁止用户覆盖关键 Pod 安全字段。

风险：Skills 默认 privileged

为了让 bubblewrap 在容器内创建 namespace，当前逻辑可能把整个 Agent 容器设为 privileged。这扩大了容器逃逸和内核攻击面。

改进方向：

  • 集群开启非特权 User Namespace；
  • 默认 allowPrivilegeEscalation=false，并验证 SRT 在目标内核上的行为；
  • 使用 gVisor/Kata 承担更强的外层隔离；
  • 将命令执行器拆到独立、短生命周期 Pod，而不是让 Agent 主容器 privileged。

风险：Bash 可以读取凭据

当前 denyRead 为空，SRT 允许读取容器内可见文件。ClusterAccess kubeconfig 和 /config 都可能成为读取目标。

改进方向：

  • 将敏感文件加入 denyRead；
  • 不向命令执行容器直接挂载模型 Secret；
  • 使用凭据代理，把长期凭据换成短期、操作范围受限的 token；
  • 将 Bash Executor 与 Agent 主进程拆成不同容器或 Pod；
  • 对输出增加 Secret 扫描，但不能把扫描当作唯一防线。

风险：网络白名单过宽

源码会把所有可见 Kubernetes Service 加入 SRT 白名单。CRD 注释中的“allowedDomains 为空时默认拒绝出站”与最终 Builder 行为并不完全一致：用户没有添加域名，不代表最终列表为空。

改进方向：

  • 只允许当前 Agent 实际依赖的 Service；
  • 不要全量 List 所有 namespace 的 Service；
  • 用 NetworkPolicy 实现 Pod 级 egress deny-by-default；
  • 通过统一 egress gateway 记录目标、方法和身份；
  • 对外部平台使用更细粒度、短期凭据。

风险：会话写边界不够细

文件工具只允许写当前 Session，但 SRT 配置允许写整个 /tmp。多个 Session 位于同一个 Agent Pod 的 /tmp/kagent 下，因此 Bash 的授权粒度比文件工具更宽。

改进方向：

  • 为每次调用动态生成只允许当前 Session 目录的 SRT 配置；
  • 每个 Session 使用独立 Volume 或独立执行 Pod；
  • 将会话目录随机化并严格设置 Unix 权限；
  • 增加跨 Session 读写回归测试。

风险：审批只覆盖部分工具

MCP Tool 可以通过 requireApproval 请求用户确认，但 Bash 不在审批集合中。

改进方向：

  • 将 Bash 纳入 BeforeToolCallback；
  • 将命令解析为结构化操作，例如 kubectl 的 verb、resource、namespace；
  • 对写操作、删除操作和凭据读取操作强制确认；
  • 审批时展示规范化命令、目标资源、凭据身份和影响范围；
  • 不允许通过 shell 拼接绕过已经批准的参数。

如何验证实际集群中的沙箱

确认外部 CRD 已安装

kubectl api-resources | rg 'sandboxagents|sandboxes'

期望至少看到：

sandboxagents.kagent.dev
sandboxes.agents.x-k8s.io

只看到 SandboxAgent 不够，因为真正创建 Pod 的 Sandbox CRD 和 agent-sandbox Controller 可能仍未安装。

检查资源链路

kubectl get sandboxagent -n <namespace>
kubectl get sandbox -n <namespace>
kubectl get pod,service -n <namespace>

进一步检查 ownerReferences：

kubectl get sandbox <agent-name> -n <namespace> -o yaml
kubectl get pod <pod-name> -n <namespace> -o yaml

期望关系是：

SandboxAgent owns Sandbox
Sandbox owns Pod and Service

检查 Pod 安全上下文

kubectl get pod <pod-name> -n <namespace> \
  -o jsonpath='{.spec.containers[?(@.name=="kagent")].securityContext}'

重点检查：

  • readOnlyRootFilesystem 是否为 true；
  • privileged 是否为 true；
  • allowPrivilegeEscalation 是否显式为 false；
  • runAsUser 是否符合预期；
  • 是否配置 runtimeClassName；
  • 是否挂载了不应出现的 hostPath 或 Unix Socket。

只查看 SRT 配置，不输出其他 Secret

srt-settings.json 与 Agent 配置位于同一个 Secret。排查时只读取指定 key，不要打印整个 Secret，以免把模型凭据写入终端日志：

kubectl get secret <agent-name> -n <namespace> \
  -o jsonpath='{.data.srt-settings\.json}' | base64 -d

重点确认：

  • allowedDomains 是否包含意外域名；
  • denyRead 是否为空；
  • allowWrite 是否仍为 /tmp；
  • allowAllUnixSockets 是否为 true；
  • enableWeakerNestedSandbox 是否为 true。

验证网络限制

测试时应使用无敏感数据的目标：

curl -I https://allowed.example.com
curl -I https://not-allowed.invalid

必须通过 Agent 的 Bash Tool 执行，直接 kubectl exec 进入 Pod 后运行 curl 不一定经过 SRT，不能证明 SRT 规则生效。

验证文件限制

可以设计无破坏性的测试：

touch /tmp/sandbox-write-ok
touch /etc/sandbox-write-should-fail
printf test > /workspace/sandbox-write-should-fail

然后验证：

  • /tmp 写入成功；
  • /etc 写入失败；
  • /workspace 对 SRT Bash 的写入应失败；
  • write_file 不能写出当前 Session 目录；
  • 通过软链接指向 Session 外部时，write_file 应拒绝。

验证 Kubernetes 最小权限

使用 ClusterAccess 前，应先对其身份执行：

kubectl auth can-i --list \
  --kubeconfig /etc/kubeconfig/<shortName>/config

对敏感操作做显式检查：

kubectl auth can-i delete deployments \
  --namespace production \
  --kubeconfig /etc/kubeconfig/<shortName>/config

只读 Agent 的期望结果必须是 no。如果返回 yes，问题在凭据授权，而不是 SRT。

常见故障排查

SandboxAgent 一直不 Ready

按顺序检查：

  1. agents.x-k8s.io/Sandbox CRD 是否存在；
  2. agent-sandbox Controller 是否运行；
  3. Sandbox CR 是否已生成；
  4. Sandbox.status.conditions 中的 Ready 原因；
  5. Pod 是否 ImagePullBackOff、Pending 或探针失败；
  6. 稳定 Service 是否已创建。
kubectl describe sandboxagent <name> -n <namespace>
kubectl describe sandbox <name> -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp

Bash Tool 报 KAGENT_SRT_SETTINGS_PATH is not set

说明 Runtime 暴露了 Skills 工具，但 Controller 没有挂载 SRT 配置或环境变量。代码会直接报错，不会绕过 SRT 执行普通 Bash。

检查：

  • Agent 是否真的声明了 Skills；
  • Secret 中是否存在 srt-settings.json；
  • Pod 环境变量是否有 KAGENT_SRT_SETTINGS_PATH；
  • /config 是否正确挂载。

bubblewrap 无法创建 namespace

常见原因：

  • 集群 Pod Security 禁止 privileged；
  • 节点关闭非特权 User Namespace；
  • Seccomp 或 LSM 策略阻止相关系统调用；
  • 运行环境不支持嵌套 namespace。

不要通过无条件放开 privileged 作为唯一解决办法。应同时评估 gVisor/Kata、User Namespace、Pod Security 和执行器拆分方案。

域名已经加入 allowedDomains，curl 仍失败

依次检查：

  1. 该命令是否确实通过 Skills Bash Tool 执行；
  2. 应用是否遵守 HTTP_PROXY、HTTPS_PROXY 或 ALL_PROXY；
  3. SRT Proxy 和 socat 是否正常；
  4. DNS 解析使用的 hostname 是否与白名单一致；
  5. TLS、证书和 SNI 是否匹配；
  6. 目标是否通过另一个未加入白名单的域名重定向。

为什么直接在 Pod 中 kubectl exec 测试不受限

SRT 只包装由 Agent Skills Bash Tool 启动的子进程：

Agent bash tool -> srt -> bash

运维人员执行：

kubectl exec -> shell

是另一条路径，不会自动经过 SRT。因此测试沙箱时必须通过真实 Agent Tool 调用链验证。

面试表达

如何用一句话解释实现

项目采用两层隔离：控制器把 SandboxAgent 翻译成 kubernetes-sigs agent-sandbox 的单实例 Sandbox 工作负载；容器内部再用 Anthropic SRT 和 bubblewrap 包装 Skills Bash 子进程，通过只读根文件系统、临时工作目录、域名白名单和最小 RBAC 限制命令影响面。

为什么不直接用 Deployment

可以回答：

Deployment 更适合无状态、可水平扩缩的服务；Agent 工作区更接近有稳定网络身份和生命周期的单实例环境。agent-sandbox 提供 Sandbox CR 和稳定 Service，因此 Controller 只需要生成 PodTemplate 并委托外部 Controller 管理具体 Pod。

如何防止 rm -rf

不要回答“项目禁止 rm -rf”，因为源码没有命令黑名单。更准确的回答是：

项目允许 Shell 正常解释命令，但通过 SRT 和 Pod 文件系统限制可写范围。rm -rf 仍可能执行，不过根文件系统只读，SRT 默认只允许写 /tmp。风险控制依赖能力边界，而不是字符串过滤；当前 /tmp 授权过宽、denyRead 为空和 Bash 无人工审批仍是待加固点。

SandboxAgent 是否等于 gVisor

不等于。SandboxAgent 是业务 CRD，最终生成 agents.x-k8s.io/Sandbox。当前 PodSpec 没有指定 runtimeClassName，因此默认仍使用集群容器运行时。要获得 gVisor 或 Kata 的更强内核隔离，需要集群安装对应 RuntimeClass 并强制 Sandbox Pod 使用它。

privileged 和沙箱为什么同时出现

bubblewrap 在容器内创建 namespace 需要内核能力，所以当前实现可能把 Skills Agent 设为 privileged，以换取完整的内层隔离能力。但 privileged 本身扩大了外层容器风险，因此更稳妥的方向是非特权 User Namespace、gVisor/Kata，或者把命令执行拆到独立短生命周期 Pod。

最终评价

当前实现已经具备清晰的分层结构：

  1. SandboxAgent 负责表达业务意图。
  2. kagent Controller 负责编译 Agent 和生成 PodTemplate。
  3. 外部 agent-sandbox Controller 负责稳定单实例 Pod 和 Service。
  4. SRT 负责隔离 Skills Bash 子进程。
  5. 文件工具通过 Go 路径检查限制会话目录。
  6. Kubernetes RBAC 决定 Agent 最终能够对集群做什么。

它适合“受控企业环境中的 Agent 命令执行”，但当前还不能直接宣称能够安全运行完全不可信代码。最需要关注的差距是：

  • privileged 默认行为；
  • 没有默认 gVisor/Kata 和 NetworkPolicy；
  • SRT 允许读取全部可见文件；
  • /tmp 写权限不是按 Session 隔离；
  • 自动网络白名单较宽；
  • Bash 没有人工审批；
  • executeCodeBlocks 尚未真正接入执行器。

判断一个 Agent 沙箱是否安全，不能只问“有没有 Sandbox 这个资源”，而应继续问：

命令在哪个进程执行？能读哪些文件？能写哪些目录？能访问哪些网络？持有什么凭据？凭据能做什么？是否需要人工确认？突破容器后还有没有 gVisor/Kata 这一层？

只有这些问题都有明确、可验证的答案，沙箱边界才真正成立。
