A2A 协议与 DBCI Agent 通信实现

2026-09-15

#Agent#A2A#JSON-RPC#Kubernetes#Google ADK

理解主线

先把编排和通信分开：模型决定是否委派，Controller 把 Agent 引用编译成工具配置，Runtime 再通过 A2A 发送请求。阅读时始终追踪请求、消息、任务和上下文四种标识，才能解释恢复、取消与持久化。

本文基于 dbci-agentic-ai-platform 当前 main 分支 0dd32d03011f8dd1609b1e262cc3fc0a8bfbd7af 的实际源码，解释项目中的 Agent 如何互相发现、发送消息、保存上下文、处理流式事件，以及如何把子 Agent 包装成父 Agent 可以调用的工具。

本文假设读者已经知道 LLM、Tool Calling、Kubernetes CRD 等基本概念，但不要求预先理解 JSON-RPC 或 A2A。

阅读完成后，应当能够回答：

  • JSON-RPC 和普通 HTTP/REST API 有什么区别？
  • A2A 在 JSON-RPC 之上又增加了什么？
  • 为什么项目中的子 Agent 会表现成一个 Function Tool？
  • messageId、taskId、contextId 和数据库 Session 分别是什么？
  • 用户到 Agent、Agent 到 Agent、Gateway 到 Agent 三条调用链有什么区别？
  • Agent Card、流式响应、HITL、认证、持久化分别在哪里实现？
  • 当前实现有哪些容易被忽略的边界和风险？

一句话理解

本项目的 Agent 间通信可以概括为：

Controller 把 Kubernetes 中引用的子 Agent 编译为父 Agent 的一个 ADK Function Tool；父 Agent 的 LLM 决定调用该工具后，Runtime 再用 A2A JSON-RPC 向子 Agent 发送消息，并把子 Agent 的结果作为 Tool Result 交回父 Agent。

flowchart LR
    U[用户] --> UI[Web UI]
    UI -->|gRPC-Web stream| C[Controller]
    C -->|A2A message/stream| P[父 Agent Pod]
    P -->|LLM 选择 Agent Tool| T[Remote A2A Tool]
    T -->|A2A message/send| S[子 Agent Pod]
    S -->|Google ADK Runner| L[子 Agent LLM 和工具]
    L -->|Message 或 Task| T
    T -->|Function Result| P
    P -->|A2A Events| C
    C -->|流式帧| UI

这里有两个不同层次：

  • 编排层：LLM 根据工具名称、description 和上下文决定是否调用子 Agent。
  • 通信层：程序使用 A2A 定义的 JSON-RPC 消息，把请求真正发送给另一个 Agent。

因此，A2A 解决的是“两个 Agent 服务如何用统一格式通信”，不负责决定“什么时候应该委派任务”。

从 JSON-RPC 开始理解

RPC 是什么

RPC（Remote Procedure Call，远程过程调用）的目标，是让调用远程服务看起来像调用一个本地函数。

本地函数调用可能是：

result, err := SendMessage(message)

如果 SendMessage 实际运行在另一台机器上，客户端需要把以下信息编码后发到网络：

  • 想调用哪个方法；
  • 方法参数是什么；
  • 这次请求的标识是什么；
  • 成功结果或错误如何返回。

RPC 框架负责完成这些工作。

可以把 RPC 理解成“跨网络函数调用的约定”。本地调用依靠函数名和参数列表，远程调用则需要把函数名和参数序列化成网络消息。

JSON-RPC 是什么

JSON-RPC 是一种很薄的 RPC 消息格式。它只规定 JSON 消息的结构，不强制使用哪个 HTTP 路径，也不定义 Agent、Tool 或 Session。

一个标准请求包含四个核心字段：

{
  "jsonrpc": "2.0",
  "id": "request-001",
  "method": "message/send",
  "params": {
    "message": {}
  }
}
字段 含义
jsonrpc 协议版本，通常固定为 2.0
id 关联请求和响应的 RPC ID
method 希望服务端执行的方法
params 方法参数

成功响应使用 result：

{
  "jsonrpc": "2.0",
  "id": "request-001",
  "result": {
    "kind": "task",
    "id": "task-001",
    "contextId": "context-001",
    "status": {
      "state": "completed"
    }
  }
}

失败响应使用 error：

{
  "jsonrpc": "2.0",
  "id": "request-001",
  "error": {
    "code": -32602,
    "message": "Invalid params"
  }
}

需要注意三个边界：

  • JSON-RPC 的 id 只负责匹配 RPC 请求和响应，不等于 A2A 的 messageId、taskId 或 contextId。
  • HTTP status 表示 HTTP 传输是否成功；JSON-RPC error 表示远程方法执行是否成功。HTTP 200 仍然可能携带 JSON-RPC error。
  • JSON-RPC method 不是 REST path。message/send 通常放在请求 body 的 method 字段中，而不是请求 /message/send 路径。

JSON-RPC 和 REST 的区别

维度 REST 风格 JSON-RPC 风格
操作表达 HTTP method 和 URL，例如 GET /tasks/123 body 中的 method，例如 tasks/get
参数位置 path、query、header、body 通常统一放在 params
结果关联 HTTP 请求本身 JSON-RPC id
错误表达 HTTP status 和业务 body JSON-RPC error.code/message/data
适合场景 面向资源的 CRUD 面向方法调用的协议

A2A 选择 JSON-RPC，是因为它要表达“发送消息”“查询任务”“取消任务”等远程操作，而不是单纯管理一组 REST 资源。

A2A 在 JSON-RPC 之上定义了什么

A2A（Agent-to-Agent Protocol）不是另一个传输协议。当前项目使用 HTTP 承载 JSON-RPC，再由 A2A 定义 Agent 领域对象、方法和状态机。

核心对象

对象 作用 在本项目中的含义
Agent Card 描述 Agent 地址、能力、输入输出模式和 skills 客户端连接前的能力发现文档
Message 一条由 user 或 agent 发送的消息 父 Agent 发给子 Agent 的任务描述
Part Message 的内容单元 TextPart、DataPart、FilePart 等
Task 可跟踪状态的执行任务 子 Agent 的一次执行
Artifact Agent 生成的结果载体 最终文本或其他输出
Event 流式执行事件 working、partial、artifact、completed 等

三类 ID

ID 生命周期 用途
JSON-RPC id 一次网络 RPC 将 JSON-RPC response 对应到 request
A2A messageId 一条消息 标识具体输入或输出消息
A2A taskId 一次任务执行 查询、取消、恢复任务
A2A contextId 多轮会话 将多条消息和多个任务放进同一个上下文

可以把它们类比为：

JSON-RPC id 是快递单号，messageId 是包裹编号，taskId 是处理工单号，contextId 是整个客户会话号。

本项目使用的 A2A 方法

Method 作用
message/send 非流式发送消息，返回 Message 或 Task
message/stream 发送消息并通过 SSE 持续返回事件
tasks/get 查询已有 Task
tasks/cancel 取消运行中的 Task
tasks/resubscribe 重新订阅已有 Task 的事件
push notification config 设置或读取任务回调配置

当前 Agent Runtime 的服务端使用 github.com/a2aproject/a2a-go v0.3.15，Controller Proxy 使用 trpc.group/trpc-go/trpc-a2a-go v0.2.5。两套库通过兼容的 A2A JSON-RPC wire format 通信。

项目中的三条 Agent 调用链

理解代码前，必须区分三条调用链。

UI 到顶层 Agent

Browser
  -> Controller MessageService gRPC-Web
  -> Controller A2A client message/stream
  -> Agent Pod :8080
  -> SSE A2A events
  -> Controller 转成 gRPC-Web stream
  -> Browser

这条链路是用户聊天的主路径，强调流式返回。

父 Agent 到子 Agent

父 Agent LLM
  -> Function Call
  -> KAgentRemoteA2ATool
  -> A2A client message/send
  -> 子 Agent Pod
  -> Message 或 Task
  -> Function Response
  -> 父 Agent LLM

这条链路是 Agent 间协作的主路径，表现为父 Agent 的一次工具调用。当前代码使用非流式 SendMessage。

Gateway 到 Agent

外部 API Client
  -> Kagent Gateway invoke endpoint
  -> invocation 持久化队列
  -> Controller A2A route
  -> 非阻塞 message/send
  -> tasks/get 轮询终态

这条链路用于异步、可轮询的外部 Agent invocation，不应与父子 Agent 的同步 Tool Call 混淆。

Agent 引用如何进入 CRD

Tool 类型

源码：go/api/v1alpha2/agent_types.go。

type ToolProviderType string

const (
    ToolProviderType_McpServer ToolProviderType = "McpServer"
    ToolProviderType_Agent     ToolProviderType = "Agent"
)

type Tool struct {
    Type       ToolProviderType `json:"type,omitempty"`
    McpServer  *McpServerTool   `json:"mcpServer,omitempty"`
    Agent      *TypedReference  `json:"agent,omitempty"`
    HeadersFrom []ValueRef      `json:"headersFrom,omitempty"`
}

一个 Agent Tool 最好显式写为：

apiVersion: kagent.dev/v1alpha2
kind: Agent
metadata:
  name: parent-agent
  namespace: team-a
spec:
  type: Declarative
  declarative:
    modelConfig: default-model-config
    systemMessage: |
      你是协调 Agent。数学问题交给 math-agent。
    tools:
      - type: Agent
        agent:
          name: math-agent
          namespace: team-a

TypedReference.NamespacedName() 会在未填写 namespace 时使用父 Agent 所在 namespace：

func (t *TypedReference) NamespacedName(defaultNamespace string) types.NamespacedName {
    namespace := t.Namespace
    if namespace == "" {
        namespace = defaultNamespace
    }
    return types.NamespacedName{Namespace: namespace, Name: t.Name}
}

a2aConfig 的真实作用

CRD 中还存在：

spec:
  declarative:
    a2aConfig:
      skills:
        - id: solve-math
          name: Solve Math
          description: Solve mathematical problems
          tags: [math]

从当前 Go 实现看，Runtime 无论是否配置 a2aConfig 都会启动 A2A Server。a2aConfig.skills 的实际作用是把 skills 写进 Agent Card，供客户端发现和理解 Agent 能力。它不是运行时 A2A Server 的启停开关。

Controller 如何编译 Agent Tool

Controller 的 translator 会把 CRD 中的 Agent 引用编译成 runtime 可以读取的 RemoteAgentConfig。

核心代码位于 go/controller/internal/controller/translator/agent/compiler.go：

case tool.Agent != nil:
    agentRef := tool.Agent.NamespacedName(agent.GetNamespace())

    if agentRef.Namespace == agent.GetNamespace() &&
        agentRef.Name == agent.GetName() {
        return nil, nil, nil, fmt.Errorf(
            "agent tool cannot be used to reference itself, %s", agentRef,
        )
    }

    toolAgent := &v1alpha2.Agent{}
    if err := a.kube.Get(ctx, agentRef, toolAgent); err != nil {
        return nil, nil, nil, err
    }

    originalURL := fmt.Sprintf(
        "http://%s.%s:8080", toolAgent.Name, toolAgent.Namespace,
    )

    cfg.RemoteAgents = append(cfg.RemoteAgents, adk.RemoteAgentConfig{
        Name:        utils.ConvertToPythonIdentifier(utils.GetObjectRef(toolAgent)),
        Url:         originalURL,
        Headers:     headers,
        Description: toolAgent.Spec.Description,
    })

假设父 Agent team-a/coordinator 引用 team-a/math-agent，生成的运行时配置近似为：

{
  "remote_agents": [
    {
      "name": "team_a__NS__math_agent",
      "url": "http://math-agent.team-a:8080",
      "description": "负责数学计算"
    }
  ]
}

这里的 URL 是 Kubernetes Service DNS：

http://<service-name>.<namespace>:8080

如果设置全局 proxy.url，Controller 会把目标 URL 改成代理地址，同时增加：

x-kagent-host: math-agent.team-a

由代理根据该 header 路由到真实 Kubernetes Service。

静态引用安全检查

Controller 在部署前检查 Agent 引用图：

if state.isVisited(agentRef) {
    return fmt.Errorf(
        "cycle detected in agent tool chain: %s -> %s",
        agentRef, agentRef,
    )
}

if state.depth > MAX_DEPTH {
    return fmt.Errorf(
        "recursion limit reached in agent tool chain: %s -> %s",
        agentRef, agentRef,
    )
}

当前 MAX_DEPTH 是 10。它可以阻止：

  • A -> A 自引用；
  • A -> B -> A 环形引用；
  • 超过限制的静态 Agent 链。

这是静态引用图检查，不等同于运行时业务级循环检测。即使 Agent 引用图无环，LLM 仍可能在一个会话内重复调用同一个合法工具。

跨 namespace 引用

同 namespace 引用默认允许。跨 namespace 引用需要同时满足：

  1. 目标 namespace 在 Controller 的 watch 范围内；
  2. 目标 Agent 的 allowedNamespaces 允许来源 namespace；
  3. 创建或更新父 Agent 的用户具有目标 Agent 的 invoke 权限。

这是一种类似 Gateway API 的双向授权：父 Agent 声明“想引用谁”，目标 Agent 声明“允许谁引用”。

Agent Pod 启动时发生什么

Controller 会为 Agent 生成 Secret、ServiceAccount、Deployment 和 Service。Secret 中包含：

  • config.json：模型、instruction、MCP tools、remote agents 等运行时配置；
  • agent-card.json：Agent 对外声明的能力。

Agent 进程启动后执行：

  1. 从 /config 读取 config.json 和 agent-card.json；
  2. 创建模型客户端和本地工具；
  3. 把每个 remote_agents 元素转成 ADK Function Tool；
  4. 创建 Google ADK Runner；
  5. 创建 A2A Executor；
  6. 在 8080 端口启动 A2A HTTP Server。

Agent Card 近似如下：

{
  "name": "parent_agent",
  "description": "负责拆解和分发任务",
  "url": "http://parent-agent.team-a:8080",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false,
    "stateTransitionHistory": true
  },
  "defaultInputModes": ["text"],
  "defaultOutputModes": ["text"],
  "preferredTransport": "JSONRPC"
}

A2A Server 路由

源码：go/adk/pkg/a2a/server/server.go。

实际接口包括：

HTTP Path 含义
GET /.well-known/agent-card.json 获取 Agent Card
POST / 发送 A2A JSON-RPC 请求
GET /health、/healthz 健康检查
GET /files、/files/download 文件访问能力

父 Agent 如何构造 Remote Agent Tool

源码：go/adk/pkg/agent/agent.go。

for _, remoteAgent := range agentConfig.RemoteAgents {
    remoteClient, err := auth.NewControllerA2AClient(
        os.Getenv("KAGENT_URL"),
        remoteAgent.Url,
        usageAgentID,
    )
    if err != nil {
        return nil, nil, nil, fmt.Errorf(
            "failed to configure authentication for remote Agent %s: %w",
            remoteAgent.Name, err,
        )
    }

    remoteTool, sessionID, err := tools.NewKAgentRemoteA2ATool(
        remoteAgent.Name,
        remoteAgent.Description,
        remoteAgent.Url,
        remoteClient,
        remoteAgent.Headers,
        propagateToken,
    )
    if err != nil {
        return nil, nil, nil, fmt.Errorf(
            "failed to create remote A2A tool for %s: %w",
            remoteAgent.Name, err,
        )
    }

    subagentSessionIDs[remoteAgent.Name] = sessionID
    remoteAgentTools = append(remoteAgentTools, remoteTool)
}

NewKAgentRemoteA2ATool 最终创建的是一个普通 ADK function tool：

type remoteA2AInput struct {
    Request string `json:"request,omitempty"`
}

ft, err := functiontool.New(functiontool.Config{
    Name:        name,
    Description: description,
}, func(ctx tool.Context, in remoteA2AInput) (map[string]any, error) {
    return state.run(ctx, strings.TrimSpace(in.Request))
})

这解释了为什么父 Agent 能像调用 MCP 工具一样调用子 Agent：在模型视角中，两者都是 Tool；区别在 Tool 的执行器。

Tool 类型 执行器 下游协议
MCP Tool MCP Toolset MCP JSON-RPC
Agent Tool KAgentRemoteA2ATool A2A JSON-RPC
本地 Tool Go function 进程内函数调用

父 Agent 如何发现子 Agent

Remote tool 不会在父 Agent 启动时立即连接所有子 Agent，而是在第一次调用时执行 lazy initialization：

resolver := agentcard.NewResolver(s.httpClient)
card, err := resolver.Resolve(ctx, s.baseURL, resolveOpts...)

client, err := a2aclient.NewFromCard(
    ctx,
    card,
    a2aclient.WithJSONRPCTransport(s.httpClient),
)

Resolver 默认请求：

GET /.well-known/agent-card.json

拿到 Card 后，客户端读取：

  • Agent 名称和 description；
  • 实际调用 URL；
  • preferredTransport；
  • streaming 等 capabilities；
  • skills。

初始化由 sync.Once 保护，因此一个 remote tool 实例只创建一次 A2A client。HTTP transport 又被 otelhttp 包装，用于传递 W3C traceparent 和 tracestate。

一次父子 Agent 调用的完整过程

构造 A2A Message

源码：go/adk/pkg/tools/remote_a2a_tool.go。

message := a2atype.NewMessage(
    a2atype.MessageRoleUser,
    a2atype.TextPart{Text: requestText},
)
message.ContextID = s.lastContextID

result, err := client.SendMessage(
    sendCtx,
    &a2atype.MessageSendParams{Message: message},
)

对应的 JSON-RPC 请求可以近似理解为：

{
  "jsonrpc": "2.0",
  "id": "rpc-001",
  "method": "message/send",
  "params": {
    "message": {
      "kind": "message",
      "messageId": "message-001",
      "contextId": "context-001",
      "role": "user",
      "parts": [
        {
          "kind": "text",
          "text": "检查集群中为什么 Pod 一直 Pending"
        }
      ]
    }
  }
}

这里的 role=user 不是说真实用户直接请求了子 Agent，而是表示这条消息是子 Agent 本轮推理的输入。真实用户身份另外通过 X-User-Id 传播。

Header 和 trace 传播

客户端 interceptor 会处理：

  • X-Kagent-Source: agent：标记这是 Agent 发起的调用；
  • X-User-Id：把父会话的用户传播给子 Agent；
  • X-MCP-Token-*：仅传播显式作用域的 MCP credential header；
  • 静态 headersFrom；
  • W3C Trace Context；
  • 在启用 KAGENT_PROPAGATE_TOKEN=true 时，传播允许的 Authorization。

X-Kagent-Source: agent 还有两个作用：

  • 子 Agent 创建 Session 时将来源记录为 agent；
  • Controller 可以把这次调用记录为 internal A2A usage。

子 Agent 返回什么

message/send 的结果不是固定字符串，而是联合类型：

SendMessageResult = Message | Task

当前父 Agent 的处理逻辑是：

返回值 处理方式
Message 提取文本，返回给父 LLM
Task(completed) 从 artifact/history 中提取文本和 usage
Task(input-required) 将子 Agent HITL 提升到父 Agent
Task(failed) 生成带 error 的 Tool Result

成功 Tool Result 近似为：

{
  "result": "目标 Pod 因为缺少匹配的 node selector 而无法调度。",
  "subagent_session_id": "context-001",
  "kagent_usage_metadata": {
    "promptTokenCount": 1200,
    "candidatesTokenCount": 220
  }
}

父 Agent 会把这个对象作为 function response 放回自己的上下文，然后由父 LLM 决定：

  • 直接向用户总结；
  • 继续询问另一个 Agent；
  • 再调用本地或 MCP Tool；
  • 根据错误调整策略。

子 Agent 的 Executor 如何执行请求

源码入口：go/adk/pkg/a2a/executor.go。

恢复用户与会话

userID := "A2A_USER_" + reqCtx.ContextID
if callCtx, ok := a2asrv.CallContextFrom(ctx); ok {
    if callCtx.User != nil && callCtx.User.Name() != "" {
        userID = callCtx.User.Name()
    }
}
sessionID := reqCtx.ContextID

如果请求带有可信的 X-User-Id，interceptor 会将其转换成 AuthenticatedUser。否则 Runtime 使用 A2A_USER_<contextId> 作为默认 user ID。

随后 Runtime 使用 contextId 查询或创建 ADK Session。A2A context 和 ADK session 在当前实现中使用同一个 ID。

A2A Part 转成模型输入

messageToGenAIContent() 负责转换：

A2A Part GenAI/ADK 表示
TextPart 文本 Part
FilePart 文件 Part
function_call DataPart GenAI FunctionCall
function_response DataPart GenAI FunctionResponse
HITL decision DataPart 由 HITL 恢复逻辑单独消费

无法识别类型的普通 DataPart 不会直接塞给 LLM，以免把协议控制数据误当成用户内容。

执行 ADK Runner

var runConfig adkagent.RunConfig
if e.stream {
    runConfig.StreamingMode = adkagent.StreamingModeSSE
}

for adkEvent, adkErr := range r.Run(
    runCtx, userID, sessionID, content, runConfig,
) {
    // 将 ADK event 转换成 A2A event
}

子 Agent 本质上仍然运行标准 Agent Loop：

输入消息
  -> 加载 session history
  -> 调用 LLM
  -> LLM 可能调用 MCP、本地工具或另一个 Agent
  -> Tool Result 回到 LLM
  -> 生成最终响应

ADK Event 转成 A2A Event

Executor 会输出：

  1. submitted；
  2. working；
  3. partial message 或 artifact update；
  4. completed、failed 或 input-required。

生成最终结果的核心逻辑近似为：

if len(hitlParts) > 0 {
    hitlMsg := a2atype.NewMessage(
        a2atype.MessageRoleAgent, hitlParts...,
    )
    inputRequired := a2atype.NewStatusUpdateEvent(
        reqCtx, a2atype.TaskStateInputRequired, hitlMsg,
    )
    inputRequired.Final = true
    return queue.Write(ctx, inputRequired)
}

if len(lastNonPartialParts) > 0 {
    finalArtifact := a2atype.NewArtifactEvent(
        reqCtx, lastNonPartialParts...,
    )
    finalArtifact.LastChunk = true
    queue.Write(ctx, finalArtifact)
}

return queue.Write(
    ctx, newCompletionStatusEvent(reqCtx, finalMeta, hadRenderableOutput),
)

为什么 Agent Tool 调用也能在 UI 展开

父 Agent 的 A2A Executor 会把 FunctionCall 转成 DataPart，并在 Agent Tool 的 function call metadata 中加入：

kagent_subagent_session_id=<child-context-id>

子 Agent 返回时，Tool Result 中也包含：

{
  "subagent_session_id": "child-context-id"
}

UI 发现工具名包含 __NS__ 时，把它识别为 Agent Call；再根据 subagent_session_id 查询子 Session 的事件，从而展示：

  • 子 Agent 正在做什么；
  • 子 Agent 调用了哪些 MCP Tool；
  • 子 Agent 的 Tool Result；
  • 子 Agent token usage；
  • 子 Agent 是否正在等待审批。

这不是前端从父 Agent 文本中猜出来的，而是后端显式写入的关联 ID。

嵌套 HITL 如何工作

*HITL（Human in the Loop，人类介入）*在多 Agent 场景中的难点是：真正需要审批的 Tool 位于子 Agent 内部，但用户连接的是父 Agent。

当前实现采用两阶段恢复。

等待审批

sequenceDiagram
    participant U as 用户
    participant P as 父 Agent
    participant S as 子 Agent
    participant M as MCP Tool

    U->>P: 发送任务
    P->>S: A2A message/send
    S->>M: 请求执行敏感工具
    M-->>S: 需要审批
    S-->>P: Task input-required
    P-->>U: 展示子 Agent 内部工具及参数

父 Agent 收到 input-required 后保存：

  • 子 Agent taskId；
  • 子 Agent contextId；
  • 子 Agent 名称；
  • 内部待审批 function calls；
  • 批量审批决定或拒绝原因。

然后调用父 Agent 的 RequestConfirmation()，把审批请求暴露给 UI。

恢复执行

sequenceDiagram
    participant U as 用户
    participant P as 父 Agent
    participant S as 子 Agent

    U->>P: approve / reject / answers
    P->>P: 恢复原 Agent Tool Call
    P->>S: 同 taskId + contextId + decision DataPart
    S->>S: 重建 FunctionResponse
    S-->>P: completed 或 failed
    P-->>U: 最终回答

恢复消息使用结构化 DataPart，而不是解析 yes、approve 等自然语言关键词。这避免了把普通文本误判成批准操作。

Session 和 Task 如何持久化

Agent Pod 中的 KAGENT_URL 指向 Controller。只要该值存在，Runtime 就会使用：

  • KAgentSessionService：保存 ADK Session 和 Event；
  • KAgentTaskStore：保存 A2A Task。

Session 持久化

子 Agent 首次处理某个 contextId 时会：

  1. 查询 Session；
  2. 不存在则创建；
  3. 将 ADK Event 持续追加到 Session；
  4. 后续相同 contextId 可以加载历史继续执行。

当请求携带 X-Kagent-Source: agent 时，Controller 将 Session 标为：

kind = sub_agent_call
source = agent

Task 持久化

KAgentTaskStore.Save() 会：

  1. 复制当前 Task；
  2. 删除只用于实时展示的 partial history/artifact；
  3. 序列化完整 Task JSON；
  4. 调用 Controller TaskService.PutTask。

这样 tasks/get 和 HITL 恢复可以在后续请求中取得任务状态。

持久化 Task 不等于父 Agent 已经成为 durable workflow。父 Agent 到子 Agent 的 Tool Call 当前仍然等待 SendMessage 返回；客户端断开、Pod 重启和跨进程恢复需要分别分析。

Controller A2A Proxy

Controller 不只是资源控制器，还暴露统一 A2A 路由：

/api/a2a/{namespace}/{name}/
/api/a2a-sandboxes/{namespace}/{name}/

动态注册

A2ARegistrar 监听：

  • Agent；
  • SandboxAgent；
  • AccessPolicy。

资源变化后，它为目标 Agent 创建内部 A2A client，并把 handler 注册进动态 mux：

client, err := a2aclient.NewA2AClient(
    card.URL,
    a2aclient.WithHTTPReqHandler(
        authimpl.A2ARequestHandler(authenticator, agentRef),
    ),
)

cardCopy := *card
cardCopy.URL = a.a2aRouteURL(agent)

a.handlerMux.SetAgentHandler(
    a2aRouteKey(agent),
    client,
    cardCopy,
    tracingMiddleware,
    resource,
    identity,
)

这里有两张 Card：

  • 原始 Card URL 指向 http://<agent>.<namespace>:8080，供 Controller 调用真实 Agent Pod；
  • 对外 Card URL 改成 Controller /api/a2a/...，避免客户端依赖集群内部 DNS。

PassthroughManager

Controller 的代理不重新执行 Agent，而是把 A2A 方法转发给 Pod：

func (m *PassthroughManager) OnSendMessage(
    ctx context.Context, request protocol.SendMessageParams,
) (*protocol.MessageResult, error) {
    return m.client.SendMessage(ctx, request)
}

func (m *PassthroughManager) OnSendMessageStream(
    ctx context.Context, request protocol.SendMessageParams,
) (<-chan protocol.StreamingMessageEvent, error) {
    return m.client.StreamMessage(ctx, request)
}

tasks/get、tasks/cancel、push notification 和 resubscribe 也采用相同方式转发。

UI 聊天为什么使用另一条链路

UI 不直接调用 Agent Pod，而是调用 Controller 的 MessageService.SendMessage。Controller 会：

  1. 根据 sessionId 查询数据库 Session；
  2. 验证当前用户就是 Session owner；
  3. 检查 Session 绑定的 Agent UID 仍然匹配；
  4. 创建 A2A message，强制 contextId=sessionId；
  5. 调用目标 Agent 的 message/stream；
  6. 将 A2A SSE event 编码成 gRPC-Web stream frame 发回浏览器。

因此 UI 的外层对话可以实时看到 partial token 和状态变化。父 Agent 调子 Agent 使用的是 message/send，所以父 Tool Call 本身是同步等待；UI 若要显示子过程，会通过 subagent_session_id 单独读取子 Session。

认证和权限边界

Controller 路由上的认证

通过 Controller /api/a2a/... 调用时会经过：

  • 用户或 workload 身份认证；
  • AccessPolicy 的 AgentInvoke 授权；
  • Agent UID 和 live Pod UID 校验；
  • nested invocation 目标约束；
  • 用户、ServiceAccount 和 group 权限处理。

Agent Pod 使用 audience 为 kagent 的 projected ServiceAccount token。专用 HTTP transport 只允许把这个 token 发送到：

同一个 KAGENT_URL origin
且 path 以 /api/a2a/ 或 /api/a2a-sandboxes/ 开头

它还禁止 redirect，避免 workload token 被重定向到其他主机。

默认父子调用的实际边界

当前 translator 默认生成：

http://child-agent.namespace:8080

也就是父 Agent 默认直接访问子 Agent Service，而不是 Controller /api/a2a/...。只有目标 URL 确实是 Controller A2A route 时，NewControllerA2AClient 才会附加 projected workload token；否则它返回 nil，remote tool 使用普通 HTTP client。

这意味着需要明确区分：

检查 CR 创建/更新 Controller A2A route 默认直连 Agent Service
引用存在 有 有 已在编译期解析
环路和深度 有 不负责 不负责
allowedNamespaces 有 依赖当前 AccessPolicy Runtime 不重新检查
用户 AgentInvoke 有 每次请求检查 Agent Server 自身不执行同等检查
workload token 不适用 校验 默认不附加
X-User-Id 不适用 由认证层建立 Runtime interceptor 会读取

因此，CRD 校验保证“配置上允许引用”，Controller route 保证“每次调用经过运行时授权”；默认 Pod-to-Pod 直连并不天然等价于后者。 如果生产环境要求所有内部调用都做强制授权，需要结合实际 proxy.url、Service 暴露范围和 NetworkPolicy 核对数据面路径。当前 Helm 目录没有为普通 Agent Pod 提供对应的 NetworkPolicy 模板。

可观测性

Agent-to-Agent 调用已经包含以下观测信息：

  • traceparent、tracestate：父子 Agent trace 关联；
  • gen_ai.operation.name=invoke_agent；
  • gen_ai.agent.name、gen_ai.agent.id；
  • kagent.user_id；
  • gen_ai.task.id；
  • gen_ai.conversation.id；
  • invocation_id；
  • LLM usage metadata；
  • internal A2A usage event。

X-Kagent-Source: agent 是 internal A2A usage 统计的重要信号。Controller 只有看到该 header 才记录 Agent 发起的调用。

当前实现中需要重点注意的行为

以下结论来自当前源码，不是 A2A 协议本身的要求。

子 Agent context 是 remote tool 实例级

NewKAgentRemoteA2ATool() 创建 tool 时执行一次：

state := &remoteA2AState{
    lastContextID: a2atype.NewContextID(),
}

后续每次调用都使用：

message.ContextID = s.lastContextID

当前文件中没有看到根据父 Session 重新生成或映射 context ID 的逻辑。因此，从代码语义看，同一父 Agent Pod 中同一个 remote tool 的多次调用会复用同一个子 Agent context。

这需要重点验证：

  • 不同父 Session 是否会共享子 Session；
  • 不同用户连续调用时，Session owner 校验如何表现；
  • 并发调用是否会把事件写入同一个子上下文；
  • Pod 重启后生成新 context 是否符合产品预期。

Remote Agent 错误被包装成 Tool Result

网络或协议错误当前不是作为 Go error 返回，而是：

return map[string]any{
    "error": fmt.Sprintf(
        "Remote agent '%s' request failed: %v", s.name, err,
    ),
}, nil

这会让 ADK 把它当成一次成功返回的 Tool Result，再交给 LLM解释。优点是 LLM 可以尝试恢复；缺点是上层错误统计和 fail-fast 行为会变弱。若业务要求错误必须显式中断，这一语义需要调整，而不是额外添加静默 fallback。

空 request 存在默认请求文本

当模型传入空 request 时，当前实现会替换成默认英文任务描述，而不是报错。这属于显式 fallback。严格调用契约下，更合理的行为通常是参数校验失败并返回错误，让问题直接暴露。

Task 状态处理比较宽松

父 Agent 当前显式处理：

  • input-required；
  • failed。

其余 Task state 进入默认结果分支。因此需要确认非流式 SendMessage 在所有部署版本中是否只会返回预期终态，尤其是：

  • submitted；
  • working；
  • canceled；
  • rejected；
  • auth-required。

更严格的实现应逐个枚举状态，未知状态直接返回错误。

两套 A2A SDK 需要持续做兼容测试

Controller 和 Agent Runtime 使用不同 A2A Go SDK。当前方法名和主要对象兼容，但升级任意一侧时都应验证：

  • Agent Card schema；
  • JSON 字段名；
  • SSE event 格式；
  • Task state；
  • streaming 和 resubscribe；
  • error code；
  • HITL DataPart metadata。

排障顺序

Agent 根本没有成为 Tool

依次检查：

  1. 父 Agent CR 的 tools[].type 是否为 Agent；
  2. tools[].agent.name/namespace 是否正确；
  3. 目标 Agent 是否存在；
  4. 跨 namespace 的 allowedNamespaces 是否允许；
  5. Controller 是否报告 cycle 或 depth 错误；
  6. 父 Agent 是否因配置变化完成 rollout；
  7. Runtime 日志是否出现 Wired remote A2A agent tool。

能看到 Tool，但调用失败

依次检查：

  1. 目标 Agent Service 是否存在；
  2. EndpointSlice 是否包含 Ready Pod；
  3. http://agent.namespace:8080/healthz 是否可达；
  4. Agent Card endpoint 是否返回合法 JSON；
  5. Card 的 preferredTransport 是否为双方支持的 transport；
  6. proxy.url 和 x-kagent-host 是否匹配实际路由；
  7. 是否把 Controller workload token 错误发送到了非 Controller origin；
  8. trace 中是否同时存在父调用、invoke_agent 和子 Agent span。

子 Agent 执行了，但父 Agent 没拿到正确结果

重点检查：

  • 返回的是 Message 还是 Task；
  • Task state 是否为 completed；
  • 最终文本是在 status message、history 还是 artifact；
  • function response 中是否有 result；
  • 是否只产生 partial artifact，持久化时又被清理；
  • subagent_session_id 是否正确；
  • 子 Agent Session 是否属于当前用户。

HITL 卡住

重点检查：

  • Task 是否进入 input-required；
  • status message 是否包含 long-running function call DataPart；
  • 父 Agent payload 是否保存 task_id 和 context_id；
  • UI 返回的是结构化 decision，而不是自然语言文本；
  • resume 消息是否使用原 task/context；
  • Task Store 中是否仍能查询到原 Task。

面试式总结

这个项目的 A2A 是怎么实现的？

Controller 把 Agent CR 中的 Agent Tool 引用编译成 RemoteAgentConfig，Go ADK Runtime 再将它包装成一个 Function Tool。父 Agent 的 LLM 选择该 Tool 后，Runtime 先通过 well-known endpoint 获取子 Agent Card，然后使用 A2A JSON-RPC message/send 发送带 contextId 的 Message。子 Agent 的 A2A Executor 将 Message 转成 GenAI Content，恢复持久化 Session，运行 Google ADK Runner，并以 Message、Task、Artifact 和状态事件返回结果。

A2A 和 MCP 有什么区别？

MCP 主要标准化 Agent 如何发现和调用工具、资源与 prompt；A2A 标准化一个 Agent 如何发现和调用另一个具备独立会话、任务状态和能力描述的 Agent。在本项目中，两者都最终表现为父 LLM 可调用的 Tool，但 MCP Tool 下游执行某个确定函数，Agent Tool 下游会启动另一个完整 Agent Loop。

为什么需要 Task，而不是只返回 Message？

Message 适合即时结果；Task 可以表达 submitted、working、completed、failed、canceled 和 input-required，支持流式事件、查询、取消、恢复和 HITL。Agent 执行通常是多阶段过程，因此 Task 比单次字符串响应更适合。

Controller 在 A2A 中负责什么？

Controller 负责 CR 编译、静态引用校验、统一 A2A route、Agent Card URL 重写、认证授权、代理转发、Session/Task 持久化 API、usage 和 trace。真正的 LLM 推理和 Tool Loop 运行在各个 Agent Pod 中。

Agent 之间是否共享上下文？

不直接共享。父 Agent 把一段任务文本作为新 Message 发给子 Agent；子 Agent 使用自己的 contextId 和持久化 Session。父 Agent只收到子 Agent 的结果与关联 metadata。若需要传递更多背景，必须显式放入请求文本、DataPart、FilePart 或其他协议字段。

当前实现最值得继续改进的地方是什么？

优先核对 remote tool 的 context 是否应按父 Session 隔离，并统一内部 A2A 是否必须经过受认证的 Controller route。随后应把 remote error 和 Task state 改成严格、穷举、fail-fast 的处理，并为两套 A2A SDK 增加协议兼容测试。
