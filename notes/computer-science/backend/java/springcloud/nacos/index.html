Nacos

2025-10-04

#后端#Java#SpringCloud#Nacos#微服务

Nacos 的注册中心管理服务实例地址，配置中心管理可发布的配置内容。学习时分别验证注册/发现和读取/刷新，再用 namespace、group 与 dataId 区分不同环境和应用。

nacos 是注册中心，服务启动时，会向 nacos 注册，nacos 会记录服务的地址，服务下线时，会从 nacos 中删除服务地址。

nacos 官网

使用的是 2.x 版本

服务发现

开启服务发现

在 Main 使用 @EnableDiscoveryClient，加了之后这个微服务才能发现其他服务（不加的话仍会注册，但不能进行发现）

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.client.discovery.EnableDiscoveryClient;

// 开启服务发现功能
@EnableDiscoveryClient
@SpringBootApplication
public class ServiceOrderApplication {
    public static void main(String[] args) {
        SpringApplication.run(ServiceOrderApplication.class, args);
    }
}

由于每个微服务之间都有可能发生相互调用，所以每个服务都要加上 @EnableDiscoveryClient

微服务 API 实现远程调用

场景描述：

抽取 model 层

由于各个微服务之间的相互调用，会导致实体类需要被多个服务依赖，而如果是按照单体项目的习惯将实体类放在项目之中，则其他项目就会无法访问。

所以需要将所有实体类单独抽离为一个 model Module

并且此时只需要给 model/pom.xml 写入 lombok 依赖

<dependencies>
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <scope>annotationProcessor</scope>
    </dependency>
</dependencies>

此时所有的微服务都要依赖这个 model Module，在 service/pom.xml 中导入依赖

<dependency>
    <groupId>com.github.musuyin</groupId>
    <artifactId>model</artifactId>
    <version>1.0-SNAPSHOT</version>
</dependency>

远程调用

public class OrderServiceImpl implements OrderService {
    @Resource
    private DiscoveryClient discoveryClient;

    @Resource
    private RestTemplate restTemplate;

    @Override
    public Order createOrder(Long userId, Long productId) {
        Order order = new Order();
        order.setUserId(userId);
        order.setNickName("Musuyin");
        order.setAddress("Home");
        // 需要远程调用来获取
        Product product = getProductFromRemote(productId);
        order.setTotalAmount(product.getPrice().multiply(new BigDecimal(product.getNum())));
        order.setProductList(Arrays.asList(product));

        return order;
    }

    private Product getProductFromRemote(Long productId) {
        // 1. 获取到商品服务所在的机器 ip + port        List<ServiceInstance> instances = discoveryClient.getInstances("service-product");

        // 2. 拼接url
        ServiceInstance serviceInstance = instances.get(0);
        String url = "http://" + serviceInstance.getHost() + ":" + serviceInstance.getPort() + "/product/" + productId;

        // 3. 使用RestTemplate发送远程请求
        log.info("Getting product from remote: " + url);
        return restTemplate.getForObject(url, Product.class);
    }
}

由于 url 是根据服务发现获取的，所以即使另外的服务集群其中部分宕机了，会在注册中心下线，仍然能正常运行

RestTemplate

其中，RestTemplate 是线程安全的，全局只需要一个，在每个服务中启动一个就好

@Configuration
public class OrderServiceConfig {
    @Bean
    public RestTemplate getRestTemplate() {
        return new RestTemplate();
    }
}

现在的调用仍然是单点调用，虽然能实现即使节点宕机也能继续进行，但是无法实现均衡地请求

负载均衡

加入依赖

services/pom.xml

<!--负载均衡-->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>

使用负载均衡

只需要使用 LoadBalancerClient.choose() 就能自动实现负载均衡

public class OrderServiceImpl implements OrderService {

    @Resource
    private LoadBalancerClient loadBalancerClient;

    @Resource
    private RestTemplate restTemplate;

    private Product getProductFromRemote(Long productId) {
        // 1. 获取到商品服务所在的机器 ip + port        // List<ServiceInstance> instances = discoveryClient.getInstances("service-product");        ServiceInstance serviceInstance = loadBalancerClient.choose("service-product");

        // 2. 拼接url
        String url = "http://" + serviceInstance.getHost() + ":" + serviceInstance.getPort() + "/product/" + productId;

        // 3. 使用RestTemplate发送远程请求
        log.info("Getting product from remote: " + url);
        return restTemplate.getForObject(url, Product.class);
    }
}

使用注解配置

给 RestTemplate 加上 @LoadBalanced 注解，就能直接实现负载均衡

@Configuration
public class OrderServiceConfig {

    @Bean
    @LoadBalanced
    public RestTemplate getRestTemplate() {
        return new RestTemplate();
    }
}

这样只需要将 url 设置为需要发现的微服务即可

private Product getProductFromRemoteWithLoadBalanceAnnotation(Long productId) {
    // 1. 拼接url，直接使用微服务名称（在nacos中注册的名字）替代ip和port
    String url = "http://service-product/product/" + productId;

    // 2. 使用RestTemplate发送远程请求
    log.info("Getting product from remote: " + url);  	// 在这里还没有替换
    // 在发送请求时会动态替代名字
    return restTemplate.getForObject(url, Product.class);
}

缓存-注册中心宕机

实际上会发起两次请求：

  • 请求注册中心
  • 给目标微服务发送请求

如果每次都要去注册中心查询，则会损耗性能。在第一次查询后，其他服务地址列表会被保存在缓存中，缓存会和注册中心实时同步（因为一般服务的 ip 和 port 不会轻易变动）

因此即使注册中心宕机了，如果有缓存，则不会影响远程调用；但是如果还没有发起过请求，在没有缓存的情况下，就无法进行远程调用了

配置中心

使用 Nacos 配置中心可以做到不停机更新, 同时也可以做到配置的版本管理。

基本使用

导入依赖

因为每个微服务都要使用，在 services/pom.xml

<!-- 配置中心 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>

导入配置

在各个微服务的配置文件中指定要读取的 Nacos 配置中心地址

spring:
  application:
    name: service-order
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
  config:
    import: nacos:service-order.yaml

但是一旦引入了 Nacos 配置中心的依赖，就必须导入

如果暂时用不到配置中心：

  • 指定 Nacos 配置为 optional
  • 禁用导入检查（在微服务配置文件）
spring:
  application:
    name: service-order
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
      config:
        import-check:
          enabled: false  # 禁用导入检查

编写 Nacos 配置

在 Nacos 端口页面创建配置

order:
	timeout: 30
	auto-confirm: 7

注意 Data Id 和在微服务配置文件中指定的文件应该相同

读取配置

使用 @Value 就可以读取

@Value("${order.timeout}")
private Integer orderTimeout;
@Value("${order.auto-confirm}")
private String autoConfirm;

动态刷新

@RefreshScope

虽然一般都会监控配置文件，但是不会自动刷新，需要在 Controller 上加上注解 @RefreshScope

@RestController()
@RequestMapping("order")
@RefreshScope
public class OrderController {

    @Value("${order.timeout}")
    private Integer orderTimeout;
    @Value("${order.auto-confirm}")
    private String autoConfirm;
}

@ConfigurationProperties 无感自动刷新

properties/OrderProperties.java

@Data
@Component
@ConfigurationProperties(prefix = "order")  // 批量绑定，无需@RefreshScope就能自动刷新
public class OrderProperties {
    private Integer timeout;

    private String autoConfirm;
}

使用

@RestController
@RequestMapping("order")
public class OrderController {

    @Resource
    private OrderService orderService;

    @Resource
    private OrderProperties orderProperties;

    @GetMapping("config")
    public String config() {
        return orderProperties.getTimeout() + ":" + orderProperties.getAutoConfirm();
    }
}

NacosConfigManager 监听配置变化

现在希望实现：

  1. 项目启动就监听配置文件变化
  2. 发生变化后拿到变化值
  3. 发送邮件

实现： 在启动类中添加 ApplicationRunner 实例，这是一个一次性任务，项目启动时就会执行

// 开启服务发现功能
@EnableDiscoveryClient
@SpringBootApplication
public class ServiceOrderApplication {
    public static void main(String[] args) {
        SpringApplication.run(ServiceOrderApplication.class, args);
    }

    // 1. 项目启动时监听配置文件变化
    // 2. 发生变化后拿到变化值
    // 3. 发送邮件
    // 使用@Bean修饰，如果参数列表中有参数，就会自动注入
    @Bean
    public ApplicationRunner applicationRunner(NacosConfigManager nacosConfigManager) {
        // 项目启动后就会执行一次
        return args -> {
            ConfigService configService = nacosConfigManager.getConfigService();
            // 添加监听器 (数据集ID, 组, 监听器)
            configService.addListener("service-order.yaml", "DEFAULT_GROUP", new Listener() {
                // 线程池
                @Override
                public Executor getExecutor() {
                    return Executors.newFixedThreadPool(4);
                }

                // 接收到数据集发生变化时，执行的回调函数
                @Override
                public void receiveConfigInfo(String configInfo) {
                    System.out.println("Receive config info: " + configInfo);
                    System.out.println("Send email");
                }
            });
        };
    }
}

测试效果：

配置优先级

当配置中心和微服务本地都有对于同一值的配置，则以配置中心为准，即外部优先，且后导入优先

启动时，会先进行配置合并，将外部配置和内部配置进行合并，并将低优先级的配置丢弃（和使用 Hexo 的主题一样），然后将合并后的配置存入本地的环境变量，之后的调用都是从环境变量中获取

数据隔离

概念

需求：项目有多套环境 test/dev/prod，每个微服务，同一种配置，在每套环境的值都不一样。项目可以通过切换环境，加载本环境的配置

难点：

  • 区分多套环境
  • 区分多种微服务
  • 区分多种配置
  • 按需加载配置

配置中心基于项目激活不同的环境标识，动态指定名称空间（Namespace），动态加载指定文件和配置

  • 名称空间（Namespace）：用于隔离不同环境的配置。名称空间可以包含多个分组
  • 分组（Group）：代表某个微服务，每个组可以有多个 data-id
  • 数据集（Data-id）：配置文件名称

实现

在 Nacos 监控页面创建名称空间

Group 不需要创建，只需要在创建配置时指定就好

然后使用克隆可以将配置复制到其他名称空间

固定名称空间和分组加载

server:
  port: 8000

spring:
  application:
    name: service-order
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
      config:
        # 指定名称空间
        namespace: dev
  config:
    import:
      # 指定分组
      - nacos:common.yaml?group=service-order
      - nacos:database.yaml?group=service-order

新增字段，自动注入

@Data
@Component
@ConfigurationProperties(prefix = "order")  // 批量绑定，无需@RefreshScope就能自动刷新
public class OrderProperties {
    private Integer timeout;

    private Integer layoff;

    private String url;

    private String port;
}

测试：

@GetMapping("config")
public String config() {
    return orderProperties.getTimeout() + ":" + orderProperties.getLayoff() + ":" + orderProperties.getUrl() + ":" + orderProperties.getPort();
}

动态加载

上面的方法适用于各个名称空间的配置结构相同的情况，如果对于不同名称空间，各个空间所拥有的配置名称、数量不一致，每次不仅要修改 namespace ，还要修改 import，所以使用 yaml 文件的多文档模式

server:
  port: 8000

spring:
  application:
    name: service-order
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
      config:
        import-check:
          # 要关闭默认的配置检查，才能获取其他的配置
          enabled: false
        # 动态名称空间取值，默认值为dev
        namespace: ${spring.config.active:dev}
  profiles:
    # 指定激活的配置环境
    active: dev

---
spring:
  config:
    activate:
      # 仅在dev环境下生效
      on-profile: dev
    import:
      # 指定分组
      - nacos:common.yaml?group=service-order
      - nacos:database.yaml?group=service-order
---
spring:
  config:
    activate:
      # 仅在test环境下生效
      on-profile: test
    import:
      # 指定分组
      - nacos:common.yaml?group=service-order
      - nacos:database.yaml?group=service-order
---
spring:
  config:
    activate:
      # 仅在prod环境下生效
      on-profile: prod
    import:
      # 指定分组
      - nacos:common-prod.yaml?group=service-order
      - nacos:database-prod.yaml?group=service-order
