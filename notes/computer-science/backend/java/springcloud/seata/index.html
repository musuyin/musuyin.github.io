Seata

2025-10-08

#后端#Java#SpringCloud#微服务#Seata#分布式事务

本地事务只覆盖一个资源管理边界，跨服务协调需要显式传播全局事务上下文。Seata 中 TM 定义全局范围，RM 管理分支，TC 协调状态；不同模式在隔离、侵入性与补偿能力上取舍。

本地事务

没有@EnableTransactionManagement，@Transactional 两注解

有异常不回滚

有@Transactional，但没有@EnableTransactionManagement

有异常会回滚，因为 SpringBoot 默认开启了事务管理。如果使用 Spring 项目，需要开启

有@EnableTransactionManagement，@Transactional两注解

有异常回滚。但是如果是分布式服务，其中一个微服务出现错误，应该是希望所有事务都能回滚，但是现在只会回滚发生错误的服务，不会回滚远程调用的其他服务，导致数据出现不同步

所以引入 Seata 实现分布式事务

分布式事务

Seata

Seata 有服务器端和客户端，客户端要连上服务器才能使用

  • TC（事务协调者）在服务器端
    • 全局事务的管理者
    • 用于维护全局和分支事务的状态，驱动 TM 的全局提交和回滚
    • TM 和 RM 通过 TC 注册分支和汇报状态
  • TM（事务管理器）在客户端：发起全局事务，定义全局事务的范围，操作全局事务的提交和回滚。
  • RM（资源管理器）在客户端：操作自己分支的事务提交和回滚。

注意：Seata 服务器的稳定性非常重要，TC 故障会影响协调与恢复，应配置高可用和持久状态；不能直接推出所有已执行分支的本地事务都失效。

环境搭建

  • 下载 seata 服务端
  • 解压并启动：seata-server.bat 访问：http://localhost:7091/ 账号密码都是 seata
    • 服务端口开启在 8091，前端页面开在 7091
  • 在微服务中导入 spring-cloud-starter-alibaba-seata 依赖
  • 在 resources 里配置 file.conf 文件，每个 seata 服务都配置

在 application.yaml 中可以指定导入的 tx_group，如果不配置则使用 default_tx_group，但是这时 default_tx_group 还是没有配置的状态，需要在 file.conf 中配置 default_tx_group

service {
  #transaction service group mapping
  vgroupMapping.default_tx_group = "default"
  #only support when registry.type=file, please don't set multiple addresses
  default.grouplist = "127.0.0.1:8091"
  #degrade, current not support
  enableDegrade = false
  #disable seata
  disableGlobalTransaction = false
}
  • default.grouplist 可以写入 Seata 集群

使用

  • 去掉 @EnableTransactionManagement（加不加都可以）
  • 在 TM 全局事务微服务中启动类上不加@EnableTransactionManagement，但在事务 service 方法上要加上@GlobalTransactional
  • 在 RM 分支事务微服务中启动类上加入@EnableTransactionManagement，在具体事务 service 方法上加@Transactional

原理

二阶提交协议

AT 模式

默认模式

  • 一阶：本地事务提交，记录业务数据镜像 undo_log
    • 为了防止并发，必须向 TC 申请全局锁
  • 二阶
    • 成功
      • 删除 undo_log
    • 失败
      • 获取前镜像
      • 恢复
      • 删除 undo_log

  • 第一阶段：本地提交
    • 生成前镜像：将要操作的数据记录下来
    • 执行 SQL 操作数据(期间启动 MySQL 的行锁，先对要操作的数据 select …for update（此时数据被锁住，普通的 select 可以读取，要看隔离级别。还有如果读操作的 select..for update 这种想加锁的读是不可以的），再执行后续 sql，执行完则释放行锁)
    • 生成后镜像：将操作后的数据记录下
    • 前镜像和后镜像等待保存到 uodo_log 日志表中
    • 向 TC 注册分支，在 TC 中申请一个全局锁，锁定操作的数据防止其他人操作，读同上，有锁才能操作。注意这里 TC 的全局锁不是 MySQL 的全局锁，MySQL 的全局锁是锁整个数据库，而 TC 的全局锁相当于 MySQL 的行级别锁，只锁操作的数据。
    • 本地事务提交；将业务数据和 uodo_log 日志表数据一起保存到当前事务的的表中
    • 和 TC 汇报事务执行状态
  • 第二阶段：
    • 若各分支事务都成功：删除 uodo_log 记录
      • TC 能感知到每个事务的状态，通知他们进行提交
      • 给异步任务对列添加异步任务，异步+批量删除对应的 uodo_log 日志表的记录
    • 若某个事务失败，TC 会通知所有分支事务回滚：拿到前镜像，数据恢复，删除 uodo_log 记录
      • 先找到 uodo_log 记录（通过 XID，BranchID）
      • 数据校验，后镜像和当前数据是否一致，一致就 ok 执行回滚；不一致说明当前数据被其他操作给篡改了，需要配置相应的策略（怎么处理这个脏数据，忽略还是人工处理？之类）
      • 若一致，则回滚数据到前镜像的内容，完成后删除 uodo_log 记录
    • 只要有分支事务没处理完，全局锁会一直存在。但是第一阶段执行事务是真正提交了的，不会在第二阶段一直阻塞数据库。

XA 模式

第一阶段不会提交数据，阻塞事务请求，在第二阶段确认提交再提交或者回滚。全局锁+MySQL 行锁在第一阶段就开启，事务一开始就用阻塞模式，性能差。AT 和 XA 区别是 AT 第一阶段执行完 SQL 释放行锁，XA 是到第二阶段才提交 SQL 导致行锁从开始到最后，阻塞时间长性能差。但二者都是一直持有 seata 的全局锁的。

TCC 模式

主要是广义上的事务，需要写侵入式的代码。举例业务需要三个事务，一个事务改数据库，一个发短信，一个发邮件，这就用 AT 和 XA 行不通了，无法回滚，如果全局事务失败，只能进行补偿性操作，例如再发邮件和短信提醒对方扣款失败或者订单失败等。

Saga 模式

用于长事务，一时半会执行不完的事务。例如请假审批，其他模式都用了锁，如果长期锁在那是对系统是非常大的阻塞。Saga 是长事务的本地提交与业务补偿模型，并非必须基于消息队列。Seata 提供状态机引擎实现；不能凭空判断“几乎不用”。见 Seata Saga 文档。
