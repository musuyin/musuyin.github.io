Sentinel

2025-10-05

#后端#Java#SpringCloud#微服务#Sentinel

Sentinel 先把调用定义为资源，再为资源设置流量、熔断、热点参数或系统规则。复习时要分清规则拒绝、业务异常与降级结果；控制台展示规则不等于规则已经可靠持久化。

概述

应用场景

Sentinel 通过流量控制、流量路由、熔断降级等多个维度保护服务的稳定性

架构原理

通过定义规则，存储规则，推送规则来实现保护资源

  • 定义资源
    • 主流框架自动适配，所有的 Web 接口均为资源
    • 编程式（不常用）
    • 声明式：@SentinelResource
  • 定义规则
    • 流量控制 FlowRule
    • 熔断降级 DegradeRule
    • 系统保护 SystemRule
    • 来源访问控制 AuthorityRule
    • 热点参数 ParamFlowRule

工作原理

整合使用

控制台启动

Sentinel 控制台包含如下功能:

  • 查看机器列表以及健康情况：收集 Sentinel 客户端发送的心跳包，用于判断机器是否在线。
  • 监控 (单机和集群聚合)：通过 Sentinel 客户端暴露的监控 API，定期拉取并且聚合应用监控信息，最终可以实现秒级的实时监控。
  • 规则管理和推送：统一管理推送规则。
  • 鉴权：生产环境中鉴权非常重要。这里每个开发者需要根据自己的实际情况进行定制。

从 release 获取 jar 包

启动：

java -Dserver.port=8080 -Dcsp.sentinel.dashboard.server=localhost:8080 -Dproject.name=sentinel-dashboard -jar sentinel-dashboard.jar

默认用户名和密码都是  sentinel

客户端接入

spring:
  cloud:
    sentinel:
      # 饥汉式启动
      eager: true
      transport:
        dashboard: localhost:8080

定义资源

声明式

将 createOrder 定义为资源，sentinel 就会对其进行监控

public class OrderServiceImpl implements OrderService {

    @SentinelResource(value = "createOrder")
    @Override
    public Order createOrder(Long userId, Long productId) {}
}

这样就能得到一个请求的完整流程中需要用到什么资源，就能进行规则的设置了

异常处理

违背了规则之后，会根据资源类型的不同，进行不同的处理

Web 接口异常处理

默认处理

默认 BlockExceptionHandler，返回 429

自定义

@Component
public class MyBlockExceptionHandler implements BlockExceptionHandler {

    private final ObjectMapper mapper = new ObjectMapper();

    @Override
    public void handle(HttpServletRequest httpServletRequest, HttpServletResponse httpServletResponse, String s, BlockException e) throws Exception {
        // 获取一个通信管道
        PrintWriter writer = httpServletResponse.getWriter();
        httpServletResponse.setContentType("application/json;charset=UTF-8");
        // 构造错误类型
        R error = R.error(s + "被 Sentinel 限制了！原因：" + e.getMessage(), e);
        // 转成字符串形式的json
        String json = mapper.writeValueAsString(error);
        // 通过管道返回
        writer.write(json);
        writer.flush();
        writer.close();
    }
}

效果

注意这个是对 Web 接口进行的配置，使用 dashboard 添加规则时，要注意添加的资源应该是路径

@SentinelResource 异常处理

@SentinelResource 多用于保护非 controller 层方法，比如 service

在 @SentinelResource 上指定 blockHandler 参数或者 fallback / defaultFallback 参数

  • 会先查询 blockHandler 是否有指定处理方法，若有则执行
  • 若无则查询 fallback
  • 如果这三个参数都没有指定，异常就会继续向上抛出

全局异常处理

使用全局异常处理器，即使没有指定参数，也可以接收到最后向上抛出的异常

// @ResponseBody
// @ControllerAdvice
// 以上两个注解合并为下面这个注解
@RestControllerAdvice   // 全局异常处理器
public class GlobalExceptionHandler {
    @ExceptionHandler(Throwable.class)
    public String error(Throwable ex) {
        return ex.getMessage();
    }
}

局部异常处理

通过在注解上指定参数，可以针对每个资源进行异常处理

@SentinelResource(value = "createOrder", blockHandler = "createOrderFallback")
@Override
public Order createOrder(Long userId, Long productId) {
    Order order = new Order();
    order.setUserId(userId);
    order.setNickName("Musuyin");
    order.setAddress("Home");
    // 需要远程调用来获取
    // 使用feign client进行远程调用
    Product product = productFeignClient.getProductNameById(productId);
    // Product product = getProductFromRemote(productId);
    order.setTotalAmount(product.getPrice().multiply(new BigDecimal(product.getNum())));
    order.setProductList(Arrays.asList(product));

    return order;
}

// 兜底回调
public Order createOrderFallback(Long userId, Long productId, BlockException ex) {
    Order order = new Order();
    order.setUserId(0L);
    order.setNickName("Unknown");
    order.setAddress("");
    order.setTotalAmount(BigDecimal.ZERO);
    order.setProductList(null);
    return order;
}

正常执行，则只会执行上面的方法，如果出现错误，则执行下面的方法

OpenFeign 调用异常处理

使用全局异常捕获（同上 GlobalExceptionHandler），或者局部异常处理

开启熔断

spring:

    openfeign:
      client:
        config:
          service-product:
            logger-level: full
            connect-timeout: 3000

            request-interceptors:

feign:

加入回调实现

注意要加入容器

@Component
public class ProductFeignClientFallback implements ProductFeignClient {
    @Override
    public Product getProductNameById(Long id) {
        System.out.println("远程调用失败-执行兜底回调");
        Product product = new Product();
        product.setId(id);
        return product;
    }
}

关联回调函数

用 fallback 指定兜底回调

// feign客户端标志, value填写要发送目的地服务名
@FeignClient(value = "service-product", fallback = ProductFeignClientFallback.class)
public interface ProductFeignClient {
    // RequestMapping, 在controller上表示接收路径, 在feignClient上表示发送路径
    @GetMapping("/product/{id}")
    Product getProductNameById(@PathVariable("id") Long id);
}

SphU 异常处理

硬编码处理

try {
    SphU.entry("resourceName");
} catch (BlockException e) {
    throw new RuntimeException(e);
}

流量控制规则

都是在创建规则时指定，不需要编码

阈值类型

  • QPS：统计每秒请求数（一般使用 QPS）
  • 并发线程数：统计并发线程数

集群模式：

  • 单机均摊：每个机器单独计算
  • 总体阈值：所有机器共享额度

流控模式

调用关系包括调用方、被调用方；一个方法也可能调用其他方法，会形成一个调用链路的层次关系

直接

默认，只对一个资源进行控制

关联

当系统里出现资源竞争的时候，使用关联策略进行限制

需要分离上下文，关闭上下文统一

spring:
  cloud:
    sentinel:
      web-context-unify: false

链路

两个请求访问一个资源，但只限制其中一个请求

流控效果

快速失败

如果超出阈值，则直接执行错误规则。只有快速失败支持上面的流控模式

Warm Up

慢慢将每秒的请求阈值达到峰值

先从低点启动，在 Period 中逐渐提升处理数量，最后达到 QPS，保持稳定。每秒多余的请求会被丢弃

匀速排队

多余的请求会排队，如果超出 timeout，则会丢弃

熔断降级规则

  • 切断不稳定调用
  • 快速返回，不积压
  • 避免雪崩效应

熔断降级用于保护自身，在客户端（调用端）配置

  • 断路器处于关闭状态，则发送请求
  • 如果请求状态满足了异常状态阈值，则将断路器切换为打开状态
  • 如果断路器处于打开状态，则不会发送请求
  • 等待熔断时长到达之后，断路器会切换为半开状态
  • 在半开状态下，只会放行一个请求，成功则切换为关闭状态，否则切换为打开状态，接着再处理后续的请求

  • 无熔断规则：是 OpenFeign 发生错误、超时，才会执行 fallback，每次都还会发送请求
  • 有熔断规则：绕过 OpenFeign，直接执行 fallback，不会再发送请求了

慢调用比例

如：统计时长 5 秒，比例阈值 70% 的请求在最大 RT（最大反应时间）1 秒以上，则触发熔断降级。

  • 熔断时长：断开时间，时间到了则会发一个请求试探，有用则通，没用则再继续熔断。
  • 最小请求数：指统计时长内最少发的请求数量。
  • RT：response time

由于是在远程调用处设置了熔断策略，所以熔断之后走 openFeign 的 fallback 处理

发生熔断后直接回调，不发远程请求

异常比例

统计时长内发生异常的比例达到比例阈值（慢调用比例是根据响应时间，异常比例是看调用是否发生异常）

发生熔断后直接回调，不发远程请求

异常数

统计时长内发生异常的数量达到设置的异常数，则发生熔断

热点参数规则

流控规则只能对某一路径（资源）进行控制，热点参数规则可以对更细节的参数进行控制，如：

  • 参数数量
  • 参数满足条件

需求：

  • 用户秒杀 QPS 不超过 1（userId 限制）
  • vip 用户不限制 QPS
  • 下架商品，不允许访问

环境搭建

Sentinel 的热点参数仅适配 Dubbo，对于 Spring 则需要自定义埋点，指定新的资源名并传入希望的参数

自定义埋点的资源名和其他资源名不可重复

热点参数限流

@GetMapping("/seckill")
@SentinelResource(value = "seckill-order", fallback = "seckillFallback") // 自定义埋点
// 默认值也算有值，相当于所有用户都会使用默认值被同一个userId限制
// public Order seckill(@RequestParam(value = "userId",defaultValue = "888") Long userId,
//                         @RequestParam(value = "productId",defaultValue = "1000") Long productId)
public Order seckill(@RequestParam(value = "userId", required = false) Long userId,
                     @RequestParam(value = "productId", required = false) Long productId) {
    Order order = orderService.createOrder(userId, productId);
    order.setId(Long.MAX_VALUE);
    return order;
}

// BlockException 改为 Throwable，从而能捕获所有的异常，都通过fallback回调
public Order seckillFallback(Long userId, Long productId, Throwable exception) {
    System.out.println("seckillFallback...");
    Order order = new Order();
    order.setId(productId);
    order.setUserId(userId);
    order.setAddress("seckillFallback异常信息" + exception.getClass());
    return order;
}

默认情况下使用 fallback，发生限流时不会调用，需要换为 blockHandler，但是 blockHandler 不能处理业务异常，使用 fallback 覆盖面更广，所以将回调函数的 BlockException 改为 Throwable，使得 fallback 也能处理限流异常

需求 1：通过 userId 限制每个用户的 QPS 为 1

  • 参数索引即控制参数的位置，0 即为 userId
  • 携带了 userId 参数就会被流控，不携带不会被流控（required）

需求 2：设置 VIP 用户不受流控

添加参数例外项即可

需求 3：下架商品不允许访问

即其他商品可被正常访问，添加例外项限流下架商品

授权规则

设置白名单或黑名单，只有指定服务才能访问

系统规则

对于整个系统的保护规则，但是精度难以控制，很少用

规则持久化

Sentinel 只把规则存储在内存，无法持久化。可以使用 Nacos 进行配置和持久化

  • QPS 限流与慢调用熔断观察的指标有什么不同？
  • 应用重启后，规则由哪里恢复？
