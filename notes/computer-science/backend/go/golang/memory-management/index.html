内存管理

2026-08-23

#Go#并发#八股

内存问题先分为分配位置、对象存活与资源生命周期。逃逸分析决定对象能否留在栈上；GC 只回收不可达对象，无法替业务解除被长期持有的引用或停止仍在等待的 goroutine。

内存分配

Go 语言的内存分配采用了TCMalloc 算法的改进版本，核心是分级分配和本地缓存。

分配器架构

分配器架构：Go 内存分配有三个层级：

  • mcache（线程缓存）：每个 P 都有独立的 mcache，避免了锁竞争
  • mcentral（中央缓存）：mcentral 按对象大小分类管理
  • mheap（页堆）：mheap 负责从操作系统申请大块内存

对象分类分配

对象分类分配：根据对象大小分为三类处理：

  • 微小对象（<16 字节）：在 mcache 的 tiny 分配器中分配，多个微小对象可以共享一个内存块
  • 小对象（16 字节-32KB）：通过 size class 机制，预定义了 67 种大小规格
    • 优先从 P 的 mcache 对应的 mspan 中分配
    • 如果 mcache 没有内存，则从 mcentral 获取
    • 如果 mcentral 也没有，则向 mheap 申请
    • 如果 mheap 也没有，则从操作系统申请内存。
  • 大对象（>32KB）：直接从 mheap 分配，跨越多个页面

channel 分配

channel 分配在堆上，Channel 被设计用来实现协程间通信的组件，其作用域和生命周期不可能仅限于某个函数内部，所以一般情况下直接将其分配在堆上

内存逃逸

内存逃逸是编译器在程序编译时期根据逃逸分析策略，将原本应该分配到栈上的对象分配到堆上的一个过程

主要逃逸场景

  • 返回局部变量指针：函数返回内部变量的地址，变量必须逃逸到堆上
  • 接口装箱：是否逃逸取决于值的使用与编译优化，不能仅由传给 interface{} 推断
  • 闭包捕获：捕获变量是否逃逸取决于闭包能否超出当前栈帧生命周期
  • 切片/map 动态扩容：当容量超出编译期确定范围时会逃逸
  • 大对象：超过栈大小限制的对象直接分配到堆上

函数参数类型选择

对于函数参数，不应机械地全部传指针。指针会扩大别名范围，使调用方和被调方可共享修改、引入数据竞争和 nil 处理，也可能让小对象逃逸到堆、增加 GC 压力并降低可读性。

  • 值传递复制的是值，编译器会优化小对象
  • slice、map、channel、interface、func 本身已是描述符/引用语义

选择依据是语义（是否允许修改/可为 nil）、对象大小、所有权和 profiling 结果，而不是“指针一定更快”。

影响

堆对象需要垃圾回收机制来释放内存，栈对象会跟随函数结束被编译器回收，所以大量的内存逃逸会给 gc 带来压力

内存泄漏

场景

  • goroutine 泄漏：这是最常见的泄漏场景。goroutine 没有正常退出会一直占用内存，比如从 channel 读取数据但 channel 永远不会有数据写入，或者死循环没有退出条件。
  • channel 与等待者：未关闭不等于泄漏；仍可达的阻塞 goroutine 及其引用可能导致对象长期保留。比如生产者已经结束但没有关闭 channel，消费者 goroutine 会一直阻塞等待，造成内存无法回收。
  • slice 引用大数组：当 slice 引用一个大数组的小部分时，整个底层数组都无法被 GC 回收。解决方法是使用 copy 创建新的 slice。
  • map 元素过多：map 中删除元素只是标记删除，底层 bucket 不会缩减。如果 map 曾经很大后来元素减少，内存占用仍然很高。
  • 定时器版本差异：Go 1.23 起，不可达且未停止的 timer/ticker 可被 GC 回收；Stop 仍用于结束不再需要的定时行为。旧版本需特别检查定时器保留问题，见 Go 1.23 发布说明。
  • 循环引用：不可达的循环引用可被追踪式 GC 回收。泄漏应检查是否仍由根对象间接持有。

定位

  • pprof：最重要的工具，通过 go tool pprof http://localhost:port/debug/pprof/heap 分析堆内存分布，go tool pprof http://localhost:port/debug/pprof/goroutine 分析 goroutine 泄漏
  • trace 工具：go tool trace 可以看到 goroutine 的生命周期和阻塞情况
  • runtime 统计：通过 runtime.ReadMemStats() 监控内存使用趋势，runtime.NumGoroutine() 监控协程数量

先看内存增长曲线，如果内存持续上涨不回收，就用 pprof 分析哪个函数分配内存最多。如果是 goroutine 泄漏，会看到 goroutine 数量异常增长，然后分析这些 goroutine 阻塞在哪里

优化

  • goroutine 泄漏：使用 context 设置超时，确保 goroutine 有退出机制，避免无限阻塞
  • channel 泄漏：及时关闭 channel，按协议提供取消或关闭路径；不要用 select+default 忙轮询掩盖生命周期问题
  • slice 引用优化：对大数组的小 slice 使用 copy 创建独立副本
  • 定时器清理：手动调用 timer.Stop() 释放资源
