07-operations-checklist

2026-10-11

运维清单围绕可恢复性验收：上线前确定契约与确认策略，运行中观察队列、消费者和业务指标，故障时先定位积压在哪一段，再限流、扩容、重试或补偿。原复选框保持未勾选。

上线、监控与故障处置清单

上线前

契约

  • 每条消息有稳定 eventId、事件类型、schema 版本、发生时间、聚合 ID、trace ID。
  • 定义向前/向后兼容策略；消费者能忽略新增字段。
  • payload 不含不必要的隐私信息；敏感数据有脱敏、加密与保留策略。
  • 定义最大消息体；大对象存对象存储，消息只传引用和校验值。

生产者

  • durable exchange/queue 与 persistent message 配套。
  • Publisher Confirm 有超时、nack 和结果未知处理。
  • mandatory + Return 可发现不可路由消息。
  • DB/MQ 双写使用 Outbox 或有明确对账补偿。
  • 重试有指数退避和抖动，不无限阻塞请求线程。
  • 日志含 eventId，但不泄露凭据/敏感 payload。

消费者

  • 手动 ACK，且在核心业务成功提交后执行。
  • 唯一索引/原子条件更新保证幂等。
  • 瞬态、永久、结果未知错误分类明确。
  • 有限退避重试与 DLQ，禁止永久立即 requeue。
  • 每个下游有 timeout；任务有总 deadline。
  • prefetch、worker 数与下游容量经过压测。
  • 优雅停机和超时后的重投经过验证。

Broker

  • 生产账号使用独立 vhost、最小权限、TLS 和密钥轮换。
  • 关键队列的副本/类型、节点和故障域满足 RPO/RTO。
  • 磁盘、内存水位和连接数容量充足。
  • 拓扑由 IaC 或可审计机制管理，参数一致。
  • 备份只是一部分，已实际演练恢复。

核心监控

Broker/队列

  • ready 消息数；
  • unacked 消息数；
  • 最老消息年龄（通常比单纯深度更重要）；
  • publish / deliver / ack / redeliver rate；
  • consumer 数和 churn；
  • connection/channel 数与关闭原因；
  • memory/disk alarm、磁盘剩余、节点/副本健康；
  • unroutable、nack、DLQ 数。

应用

  • 发布成功率、Confirm latency、outbox NEW 数及最老年龄；
  • 消费成功/重试/永久失败率；
  • 处理耗时 p50/p95/p99；
  • 幂等命中率；
  • 各错误分类数量；
  • LLM QPS、限流、超时和 token/费用；
  • 从 occurredAt 到报告成功的端到端延迟。

告警应关注持续时间和业务影响，避免瞬时波动造成告警风暴。

常见故障 Runbook

队列持续积压

  1. 判断是生产突增、消费变慢、消费者减少还是下游故障；
  2. 看最老消息年龄、unacked、处理耗时和错误分类；
  3. 若下游健康且有容量，逐步扩 worker；
  4. 若下游限流，盲目扩容只会雪崩，应降并发并修复/等待；
  5. 估算追平时间并向业务暴露延迟；
  6. 禁止直接清队列，除非业务所有者批准且有审计。

unacked 很高

检查 prefetch 是否过大、处理是否卡死、下游 timeout 是否缺失、消费者是否停止 ACK。必要时滚动重启会使未 ACK 重投，必须先确认幂等。

redelivery/retry 激增

按错误分类聚合，找共同 schema/配置/下游。若是毒消息，隔离到 DLQ；若是系统故障，启用退避和熔断，避免重试放大。

DLQ 有消息

保留原消息与失败元数据，定位根因；修复代码/数据后在隔离环境验证；按 eventId 小批重放，观察幂等和下游容量；记录操作者与结果。不要把 DLQ 原样无脑倒回主队列。

Broker 不可用

确认节点/网络/证书/磁盘水位；观察生产端 outbox 是否积压；恢复后控制 Relay 速率，避免发布洪峰；确认消费者重新声明 Channel、QoS 和订阅；核对数据而非只看进程存活。

本项目重点指标

建议按 eventType=conversation.closed 建面板：

会话关闭事件数
-> outbox 待发布/发布延迟
-> RabbitMQ ready / oldest age / redelivery
-> report PROCESSING / SUCCESS / FAILED
-> LLM 延迟/失败/费用
-> 端到端报告生成时间

对长期停留 Processing 的报告做扫描和租约恢复；扫描器同样要使用原子抢占，避免多个实例重复修复。

容量与降级

报告生成属于异步高成本任务。积压时可按业务要求：

  • 保证风险预警优先于普通摘要，使用独立队列而非滥用单队列优先级；
  • 降低 prompt/模型规格，或暂缓非关键步骤；
  • 设置租户配额和公平调度，防止单一单位占满消费者；
  • 设置最大可接受等待时间，过期任务进入补偿而非静默丢弃。

任何降级都应写入状态并可审计。

复习

  • ready 与 unacked 分别积压，排查方向为何不同？
  • DLQ 中的消息由谁判断可重放？
  • oldest message age 为什么比单纯队列长度更接近用户等待体验？
