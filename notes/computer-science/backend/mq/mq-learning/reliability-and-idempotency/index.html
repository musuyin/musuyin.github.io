03-reliability-and-idempotency

2026-10-11

可靠性要覆盖数据库、生产者、Broker、消费者和外部副作用。以“业务成功但确认未知”的窗口为主线，组合 Outbox、Confirm、手动 ACK、唯一约束与重试隔离，才能把重复收敛为一致结果。

可靠消费、幂等与宕机恢复

端到端可靠性不是一个开关

要逐段检查：

业务状态 -> 生产者本地 -> Broker 接收/复制 -> Queue 保存
         -> Consumer 获取 -> 业务副作用提交 -> ACK

任何相邻两步都可能出现“前一步成功、后一步未知/失败”。可靠设计的核心是：持久记录事实、允许重试、接受重复、用幂等收敛、让失败可观测和可补偿。

生产可靠性

Publisher Confirm

Channel 开启 confirm 模式后，Broker 对发布给出 ack/nack。批量异步 Confirm 吞吐通常优于逐条同步等待。需维护发布序号到消息/outbox 记录的映射，并处理：

  • ack：标记 outbox 已发布；
  • nack/超时/连接断开：保持待发布并重试；
  • Confirm 之前断线：结果未知，按至少一次重发。

Confirm 只证明 Broker 接受了消息（具体安全程度受队列类型和配置影响），不证明消费者业务成功。

路由失败检测

设置 mandatory=true 并监听 Return；若 exchange 存在但没有匹配队列，消息返回生产者。注意：不存在的 exchange 通常会关闭 Channel，因此拓扑也要监控。

Transactional Outbox

解决“业务数据库写入 + MQ 发布”的双写原子性：

  1. 同一数据库事务内写业务记录和 outbox；
  2. Relay 扫描/监听未发布 outbox；
  3. 发布并等 Confirm 后标记成功；
  4. 超时重发，所以仍可能重复；
  5. 定期归档，监控最老 NEW 记录年龄。

MongoDB 可在 replica set/sharded cluster 的事务条件下采用事务。若暂不能使用事务，可设计单文档原子状态机，或使用定期对账补偿，但必须明确一致性边界。

不要用进程内内存队列托底关键消息：宕机即丢；本地磁盘队列也会引入刷盘、容量、多实例和恢复复杂度。

Broker 可靠性

生产环境至少考虑：

  • durable exchange/queue；
  • persistent message；
  • quorum queue 多副本与多数派提交；
  • 合理的磁盘/内存水位、容量和告警；
  • 跨故障域部署与经过验证的恢复流程；
  • 权限、TLS、vhost 隔离。

这些降低 Broker 丢失概率，但不能替代 Confirm、Outbox 和幂等。

消费可靠性

ACK 时机

原则：所有必须成功的业务副作用提交后再 ACK。

if err := handle(msg); err != nil {
    // 分类后重试或进 DLQ
    return
}
delivery.Ack(false)

不要在耗时任务开始前 ACK；否则消费者中途宕机会丢任务。也不要把非关键副作用无限纳入同一成功条件，否则次要操作会阻塞主任务；应拆事件或设计状态机。

宕机恢复矩阵

故障时刻 结果 所需机制
收到消息、业务未写入 未 ACK，重投 手动 ACK
业务写入一半 可能脏状态 DB 事务/状态机
业务成功、ACK 前宕机 重投且可能重复 幂等
ACK 成功后进程退出 正常完成 无
Broker/网络中断 Channel 关闭、未 ACK 重投 重连并重新订阅

幂等设计

先定义幂等键

优先使用稳定 eventId。若“一次会话只能生成一份最终报告”，业务键也可为：

(event_type, conversation_id, schema_version)

不要每次消费创建随机报告 ID 后再用它去重；随机 ID 每次不同。

数据库唯一约束 + 状态机

推荐报告集合建立唯一索引，例如 (conversation_id, report_version)。处理流程：

  1. 原子插入或 upsert PENDING；
  2. 若已 SUCCEEDED，直接 ACK；
  3. 若 PROCESSING，根据租约判断另一个 worker 是否仍在处理；
  4. 以条件更新抢占：status in [PENDING, RETRYABLE] && lease_until < now；
  5. 执行业务；
  6. 条件更新为 SUCCEEDED 并保存结果。

“先 SELECT 不存在，再 INSERT”有并发竞态，必须由唯一索引兜底。

外部副作用

LLM 调用、短信、支付等不一定支持事务回滚：

  • 若供应商支持 idempotency key，传 eventId；
  • 发送前持久化调用记录和请求摘要；
  • 超时结果未知时先查询供应商状态，勿盲重试；
  • 将报告步骤拆成可恢复状态机，已完成步骤不重复执行；
  • 对不可避免的重复成本做对账和限额。

对本项目，建议先按会话唯一创建报告，再让 LLM 结果更新同一记录；不要每次 delivery 新建随机报告。若 worker 在 LLM 成功后、落库前宕机，仍可能再次调用，需要调用记录或供应商幂等能力进一步收敛。

重试不是简单 requeue

错误分类

  • 可重试瞬态错误：网络超时、限流、临时 5xx、短暂主从切换；
  • 不可重试永久错误：JSON 非法、ID 非法、schema 不支持、必要配置缺失；
  • 结果未知：请求可能已成功但响应丢失，优先查询或以幂等键重试。

延迟退避 + DLQ

不要立即永久 NACK requeue=true。常见 RabbitMQ 方案：

main queue
  --失败1--> retry.5s queue  --TTL/DLX--> main
  --失败2--> retry.30s queue --TTL/DLX--> main
  --失败3--> retry.5m queue  --TTL/DLX--> main
  --超过上限/永久错误--> dead-letter queue

可使用消息 header 记录业务 attempt，但应防伪并考虑 x-death；也可由重试服务重新发布。延迟消息插件可简化，但增加插件依赖。DLQ 不是垃圾桶：要告警、展示原因、支持修复后安全重放。

超时、并发和背压

  • 消费处理设置总超时与每个下游超时；
  • prefetch × consumer 数 是在途任务上限之一；
  • 扩容前检查 LLM QPS、Mongo 连接池和成本；
  • 优雅停机：停止接收新 delivery，等待在途任务到限时；未完成的不 ACK，让 Broker 重投；
  • 单任务过长时关注连接心跳、Kubernetes termination grace period 和业务租约。

顺序与并发

全局顺序往往代价极高。先问是否只需“同一会话有序”。可用：

  • 按 conversation ID 哈希到固定队列，每队列单消费者；
  • 每条事件携带 aggregate version，数据库只接受期望版本；
  • 可交换操作通过幂等与最终状态消除顺序要求。

RabbitMQ 多消费者 + 重投无法保证业务完成严格有序。

推荐改造优先级

  1. 先修复 WaitGroup.Add 与 goroutine 的启动顺序，并以测试约束连接/Channel 重建生命周期；
  2. 为消息增加 eventId/eventType/schemaVersion/occurredAt/traceId；
  3. 报告表加业务唯一索引，消费改为原子 upsert/状态机；
  4. 永久错误不 requeue，有限退避后 DLQ；
  5. durable 拓扑 + quorum queue + mandatory + Confirm；
  6. 业务更新与 outbox 同事务，Relay 可重试发布；
  7. 增加队列深度、最老消息年龄、失败率、DLQ、处理耗时、outbox age 告警；
  8. 做 kill -9、断网、Broker 重启、毒消息和积压恢复演练。

可靠性验收问题

上线前必须能回答：

  • 发消息超时时，如何判断是否已成功？
  • 消费业务成功但 ACK 丢失，重投会产生什么副作用？
  • 一条永久坏消息最终在哪里？谁处理？
  • 消费者停 30 分钟后恢复，容量多久追平？
  • DB 成功、MQ 失败如何自动补偿？
  • Broker 丢一个节点或重启后，哪些数据可能丢？
  • 如何从 trace/eventId 定位一条消息全链路？

复习

  • Confirm 成功能否证明报告已经生成？
  • Outbox Relay 为何仍可能重复发布？
  • 调用外部计费 API 的幂等边界应怎样定义？
