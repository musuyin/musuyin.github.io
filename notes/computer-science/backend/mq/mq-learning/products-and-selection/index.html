04-products-and-selection

2026-10-11

选型从数据消费后是否保留、是否需要回放、任务级确认和顺序范围出发。RabbitMQ、Kafka、RocketMQ、Redis Streams 与 Pub/Sub 各有不同的状态模型；吞吐数字只有在相同持久化与复制条件下才可比较。

RabbitMQ、Kafka、RocketMQ 与 Redis 消息能力选型

先看结论表

维度 RabbitMQ Kafka RocketMQ Redis Streams Redis Pub/Sub
核心抽象 Exchange + Queue 分区追加日志 Topic + Queue/日志 Redis 内的追加日志 在线频道广播
消费后数据 队列通常删除 按保留策略留存 按保留策略留存 XTRIM/策略裁剪 不留存
回放 传统队列不擅长 强，按 offset 重读 支持按位点/时间重读 可按 ID 读取 不支持
路由 direct/topic/fanout/headers 很强 通常 Topic + key 分区 Topic/tag/filter Stream key，路由较简单 channel/pattern
吞吐 高，复杂路由/逐消息状态有成本 超高吞吐强项 高吞吐业务消息 中小规模很方便 很高但无可靠保障
延迟 低 通常低毫秒，但偏批处理吞吐 低 低 极低
消费组 竞争消费者 分区分配给组成员 消费组/队列分配 Consumer Group + PEL 无可靠消费组
失败跟踪 unacked、NACK、DLX offset/重试 topic 由应用生态处理 重试/死信能力完善 PEL、XPENDING、XCLAIM 无
顺序 单队列单消费者较易 分区内有序 队列内有序，可选顺序消息 Stream ID 有序，组内并发完成可乱 仅在线到达顺序，不可靠
典型优势 任务队列、灵活路由、细粒度 ACK 事件流、日志、回放、数据平台 业务消息、延迟/事务/重试生态 已有 Redis 的轻中量可靠流 可丢的实时广播

表格是主流使用方式，不代表绝对性能边界；版本、配置、消息大小、复制和硬件会显著影响结果。

RabbitMQ

为什么适合这些场景

RabbitMQ Broker 主动把队列消息推给消费者，并跟踪每条 delivery 是否 ACK；Exchange 提供灵活路由，QoS 控制在途数。因此适合：

  • 后台任务队列：邮件、图片处理、报告生成；
  • 复杂业务路由：一个事件按 key 发往不同队列；
  • 低延迟命令和工作分发；
  • 需要细粒度 ACK、重试、DLQ 的中等吞吐业务。

短板：传统队列消息 ACK 后删除，不适合长期保留和任意回放；大量队列、超大积压或超高吞吐需要认真规划。RabbitMQ Streams 能提供日志式能力，但若核心目标本来就是大规模事件流，Kafka 通常生态更成熟。

本项目契合点：报告是离散且昂贵的任务，需要固定并发、手动 ACK、失败隔离和低延迟派发；RabbitMQ 很自然。

Kafka

Kafka 把 Topic 分成 Partition，每个分区是只追加日志。消费者拉取数据并维护 offset；数据是否保留与是否消费解耦。顺序写、批量、页缓存和零拷贝等设计偏向吞吐。

适合：

  • 埋点、日志、CDC；
  • 实时流计算、数据湖管道；
  • 事件溯源、多个下游在不同时间独立回放；
  • 超高吞吐、可接受按分区扩展和有序。

约束：同一 consumer group 中，并行度受分区数约束；只保证分区内顺序；复杂内容路由通常靠多个 topic 或消费者过滤；单条任务的延迟重试/DLQ 不如业务 MQ 原生直观。Kafka 的事务和幂等 producer 能解决 Kafka 范围内的一些重复问题，不能自动让外部 Mongo/HTTP 副作用 exactly once。

若本项目未来要把所有对话事件长期保留，供画像、审计、离线训练、实时统计多个团队反复消费，Kafka 会比传统 RabbitMQ 队列更合适；“生成一次报告任务”仍可留在 RabbitMQ，二者可共存。

RocketMQ

RocketMQ 也是基于持久化提交日志和逻辑消费队列的分布式消息系统，面向业务消息提供较完整的能力：消费组、重试、死信、延迟/定时消息、顺序消息；事务消息通过半消息与事务状态检查协调本地事务和消息提交。

适合：

  • 电商订单、支付、库存等业务事件；
  • 需要延迟/定时消息，如超时关单；
  • 需要顺序消息或成熟重试/DLQ 约定；
  • 大规模 Java/云上 RocketMQ 生态。

与 RabbitMQ 比，RocketMQ 更偏日志式高吞吐业务消息和内建延迟/事务机制；RabbitMQ 路由模型更灵活、协议/客户端生态广、任务队列心智直观。事务消息也不是分布式事务魔法：本地事务必须幂等，事务回查必须可正确判断，消费仍需幂等。

Redis Streams

Stream 是 Redis 数据结构，XADD 追加带 ID 的条目；XREAD 可按 ID 读取，XREADGROUP 支持消费组。组会维护 PEL（Pending Entries List），消息经 XACK 才从 pending 中移除；XPENDING/XAUTOCLAIM 可发现并接管超时任务。

适合：

  • 团队已有高可用 Redis、规模中小、希望少引入组件；
  • 轻量事件流、设备事件、内部任务；
  • 需要一定保留、回读和消费组，但无需 Kafka 级数据平台。

注意：

  • 必须设置合理 MAXLEN/裁剪策略，否则内存增长；
  • Redis 主要以内存为中心，持久性取决于 AOF/RDB、复制与故障转移配置；异步复制窗口可能丢数据；
  • PEL 需要主动巡检和 claim，未 ACK 消息不会自动完成；
  • 路由、DLQ、跨数据中心和海量长期保留生态弱于专业 MQ/日志平台。

不能因为“用了 XACK”就认为端到端可靠；生产确认、业务双写与幂等问题仍存在。

Redis Pub/Sub

发布者把消息发到 Channel，Redis 只转给当时在线且已订阅的客户端：不持久化、无 ACK、无消费进度、断线期间丢失、慢订阅者还可能被断开。

适合：

  • 可丢的在线通知；
  • WebSocket 节点间广播“刷新/失效”信号；
  • 临时状态更新和开发调试。

不适合订单、扣款、报告生成等必须最终处理的任务。若消费方必须离线恢复，至少考虑 Streams 或专业 MQ。

“Redis 队列”补充

若口语中的 Redis 指 Lists：可用 LPUSH/BRPOP 做简单工作队列；更可靠的模式需把处理中任务移动到 processing list，并自行实现 ACK、超时回收、重试和 DLQ。功能逐渐接近“手写半个 MQ”，复杂业务通常直接用 Streams 或专业 MQ。

按问题选型

  1. 断线期间能否丢？ 能：Pub/Sub；不能：排除它。
  2. 是否要保存数天/月并任意回放？ 是：优先 Kafka/RocketMQ；中小规模可评估 Streams。
  3. 是否需要灵活路由和经典任务队列？ 是：RabbitMQ。
  4. 是否强依赖延迟、顺序、事务消息的业务生态？ RocketMQ 常更顺手。
  5. 吞吐是百万级事件流，还是几十/几千 QPS 的昂贵任务？ 前者偏 Kafka，后者 RabbitMQ 往往更匹配。
  6. 是否已有可靠 Redis，且规模小、团队不能维护新组件？ Streams 可降低运维门槛，但要接受可靠性边界。
  7. 消息有多大、保留多久、积压峰值多少？ 用容量模型和压测决定，禁止凭印象。

场景示例

场景 首选倾向 原因
本项目会话结束生成报告 RabbitMQ 任务分发、prefetch 背压、逐条 ACK/DLQ
用户行为埋点供多团队处理 Kafka 高吞吐、长期保留、独立回放
订单 30 分钟未付自动关闭 RocketMQ / RabbitMQ 延迟方案 原生/组合式延迟投递和业务重试
缓存失效通知，可容忍偶发丢失 Redis Pub/Sub 极简低延迟
小系统可靠异步任务，已有 Redis Redis Streams PEL/ACK，较低引入成本
数据库 CDC 到数仓 Kafka 日志生态、Connector、流处理

反模式

  • “Kafka 吞吐最高，所以所有场景都用 Kafka”；
  • “Redis 已经有了，所以拿 Pub/Sub 做关键任务”；
  • “RabbitMQ 设置 persistent 就绝不会丢”；
  • “RocketMQ 事务消息等于跨系统强一致”；
  • 只比较 benchmark，不比较消息大小、保留、复制、失败恢复、团队运维能力和总成本。

复习

  • 可丢缓存通知与不能丢的报告任务为何不应共用 Pub/Sub 方案？
  • 回放需求怎样改变消息保留成本？
  • 事务消息为什么不等于任意外部系统的强一致事务？
