06-practice-labs

2026-10-11

实践按基线、最小收发、重复投递、幂等、确认故障、Outbox、毒消息与容量逐步推进。每个实验都应有可重复触发的故障、预期状态和观测记录，不能把清单中的验收目标视为已完成结果。

实践实验：从接入到故障演练

实验以独立分支进行，避免污染当前业务。每项都要记录现象、指标、日志与结论，而不只是“跑通”。示例配置不可用于生产。

建立基线

定位并画出调用链：

psych-core-api/biz/domain/engine/engine.go
 -> psych-core-api/biz/infra/mq/producer.go
 -> RabbitMQ
 -> psych-post/pkg/mq/consumer.go
 -> psych-post/biz/domain/report/report.go

回答：发布时机、消息字段、Exchange/routing key/queue 来自哪里、ACK/NACK 条件、worker 并发上限。

启动 RabbitMQ 并声明拓扑

可用 Docker：

docker run -d --name mq-learning \
  -p 5672:5672 -p 15672:15672 \
  -e RABBITMQ_DEFAULT_USER=learn \
  -e RABBITMQ_DEFAULT_PASS=learn-pass \
  rabbitmq:4-management

访问 http://localhost:15672。创建独立 vhost 和最小权限用户更接近生产。声明：

  • durable direct/topic exchange；
  • durable queue（生产可评估 quorum queue）；
  • binding key；
  • DLX、DLQ；
  • 5s/30s 重试队列，通过 TTL + DLX 返回主 exchange。

验收：能在 Management UI 看到 binding；发布正确 key 可入队，错误 key 配合 mandatory 能 Return。

最小 Go 生产与消费

使用项目已有 amqp091-go。生产者至少实现：

  1. 建立 Connection/Channel；
  2. 幂等声明拓扑；
  3. 开启 Confirm；
  4. mandatory=true；
  5. 发布 persistent 消息，包含 message ID、content type、timestamp；
  6. 等待 ack/nack/return 并记录 eventId。

消费者实现：

  1. 每个 worker 独立 Channel；
  2. Qos(1, 0, false)；
  3. autoAck=false；
  4. 成功后 ACK；
  5. 错误分类后进入 retry/DLQ，而非永久立即 requeue；
  6. SIGTERM 时停止新任务并等待在途任务。

验收：连续发送 100 条，不丢；消费者并发不超过设定值；错误路由能被生产者发现。

验证 at-least-once

处理函数按步骤记录：RECEIVED -> DB_WRITTEN -> ACKED。在 DB 写入后、ACK 前人为 kill -9。

预期：消息重投，Redelivered 可能为 true；若没有幂等，会出现重复记录。注意 Redelivered=false 不能证明从未重复，不能把它当幂等键。

验收输出：故障时间线、重复数据证据、恢复后队列状态。

实现消费幂等

为测试报告使用稳定业务键 conversationId + reportVersion，数据库建立唯一索引。实现原子 upsert/条件状态转换：

不存在 -> PENDING -> PROCESSING(lease) -> SUCCEEDED
已 SUCCEEDED -> 直接 ACK
PROCESSING 且租约未过期 -> 延迟重试
PROCESSING 且租约已过期 -> CAS 抢占并恢复

重复投递同一 eventId 10 次。验收：只有一份最终报告；可接受多次 delivery，但昂贵调用次数符合设计目标；并发消费者不会突破唯一约束。

Publisher Confirm 故障实验

批量异步发布，并保存 deliveryTag -> eventId 映射。发布过程中停止 RabbitMQ 容器或断网，观察三类消息：已 confirm、明确 nack/return、结果未知。

恢复后重发未确认消息。验收：消息不缺失；可能重复，由 Lab 4 幂等吸收；指标可显示 confirm latency 和 nack/timeout。

Transactional Outbox

设计集合：

{
  "_id": "eventId",
  "aggregateId": "conversationId",
  "type": "conversation.closed",
  "schemaVersion": 1,
  "payload": {},
  "status": "NEW",
  "attempts": 0,
  "nextAttemptAt": "...",
  "createdAt": "...",
  "publishedAt": null
}

把会话更新与 outbox insert 放在 Mongo 事务内。Relay 以租约/CAS 抢占 NEW 记录，发布后等 Confirm，再标记 PUBLISHED。Relay 在 Confirm 后、更新状态前 kill -9。

预期：恢复后重复发布，但不丢；消费幂等保证最终只产生一份业务结果。

毒消息、退避和 DLQ

发送三类消息：非法 JSON、非法 ObjectID、模拟 LLM 503。

期望策略：

  • 非法 JSON/ID：立即 DLQ；
  • 503：5s、30s、5m 等有限退避；
  • 超过最大次数：DLQ；
  • DLQ 消息保留 eventId、原 routing key、失败分类和诊断信息，避免泄露敏感 payload。

验收：没有高频 requeue；正常消息不被毒消息饿死；DLQ 有告警，修复后能按 eventId 安全重放。

连接恢复和优雅停机

测试：

  1. RabbitMQ 重启；
  2. TCP 断开；
  3. 消费者 SIGTERM；
  4. 处理超过 termination grace period；
  5. 网络恢复后生产者/消费者重新建立 Channel、Confirm、QoS 和订阅。

特别审查当前生产端重连代码：共享 producer 初始化时序、旧 Connection/Channel、NotifyClose 重新注册是否存在竞态。使用 Go race detector 做针对性测试：

cd psych-core-api && go test -race ./biz/infra/mq/...
cd ../psych-post && go test -race ./pkg/mq/...

若包无测试，先补 fake/integration test；不要以“没有 test files”作为通过。

积压与容量

暂停消费者并发送任务形成积压，再恢复不同 worker 数。记录：

  • publish/ack rate；
  • ready/unacked 数；
  • 最老消息年龄；
  • p50/p95/p99 处理耗时；
  • LLM QPS/限流率与 Mongo 压力；
  • DLQ 和重试量。

估算：

单 worker 吞吐 ≈ 1 / 平均处理秒数
总稳定吞吐 ≈ worker 数 × 单 worker 吞吐 × 有效率
追平时间 ≈ backlog / (消费速率 - 新增速率)

若消费速率不大于新增速率，永远无法追平。扩 worker 不能突破下游配额。

选型对比小实验

用相同消息和业务处理分别实现 RabbitMQ 与 Redis Streams：

  • RabbitMQ：prefetch、manual ack、DLQ；
  • Streams：consumer group、PEL、XACK、XAUTOCLAIM、XTRIM。

再用 Redis Pub/Sub 模拟消费者断线，证明消息不可恢复。比较代码量、恢复机制、积压内存、可观测性，不要只比较无持久化峰值 QPS。

最终交付物

  • 架构图和故障窗口表；
  • 可重复的 Docker/脚本；
  • 幂等索引和状态机说明；
  • 5 类故障实验报告；
  • 监控面板截图或指标样例；
  • 一页 ADR：为什么本项目继续使用 RabbitMQ，何时应重新评估 Kafka/RocketMQ/Streams。

复习

  • 业务提交后主动终止消费者，怎样验证重投没有重复副作用？
  • permanent error 与 transient error 应进入什么不同路径？
  • 消费能力高于生产速率多少时，积压才能在目标时间追平？
