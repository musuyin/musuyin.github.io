05-internals

2026-10-11

队列 Broker 跟踪待处理与未确认消息，分区日志保存数据并分离消费位置。理解状态放在哪里后，就能解释灵活路由、细粒度 ACK、保留回放与批量吞吐为何适用于不同场景。

底层实现与应用场景的因果关系

本篇关注“为何产品会有这样的应用场景”，不是源码逐行解析。

两类核心模型

队列 Broker：RabbitMQ 传统 Queue

Broker 维护“哪些消息仍在队列、哪些已投递未确认”。消费者 ACK 后消息可被删除。优点是单条任务状态、推送、路由和公平分发自然；代价是逐消息状态和复杂路由带来额外开销，历史回放不自然。

分区日志：Kafka（RocketMQ 也有日志式基础）

Broker 将记录顺序追加到日志段；消费者位置是 offset，消费不删除原记录，保留由时间/空间策略决定。顺序 IO、批量与共享日志让吞吐和回放自然；代价是路由和任务级重试通常围绕 topic/partition/offset 设计。

这不是“谁更先进”，而是状态放在哪里、为哪种访问模式优化。

RabbitMQ 内部机制

Connection / Channel 多路复用

AMQP Connection 是 TCP 连接；Channel 在其上多路复用，减少大量 TCP/TLS 连接成本。因此工程上应复用 Connection，为消费者创建独立 Channel。Connection 断开时其上所有 Channel 都失效，必须重建 Channel、QoS、Confirm 与订阅，不能只替换 Connection 指针。

Exchange 路由

消息先进入 Exchange，Broker 根据 binding 做精确、模式或广播匹配。这使 RabbitMQ 擅长复杂业务拓扑；同时绑定数量和路由复杂度不是免费的。

推送、unacked 与 prefetch

RabbitMQ 主动投递；未 ACK delivery 记录在 Channel/Consumer 相关状态中。prefetch 限制在途消息，形成显式背压。连接关闭后未 ACK 消息重新可投递，所以天然偏向 at-least-once。

持久化与 Confirm

持久消息进入 durable/quorum queue 后要经历内存、磁盘和可能的副本复制。客户端调用 write 成功只表示数据交给连接层，不等价于 Broker 安全接受。Confirm 把 Broker 处理结果反馈给生产者；断线窗口仍可能结果未知，因此重发 + 幂等是必要组合。

Quorum Queue

Quorum Queue 使用 Raft，在多个节点复制日志并由 leader 协调。多数派可用时才能继续，提升节点故障下的数据安全；代价是网络复制、磁盘和更高延迟。它适合关键队列，不意味着可以忽略容量、分区故障和客户端确认。

为什么传统 RabbitMQ 不以回放见长

ACK 后消息通常从队列生命周期中退出。要让多个独立下游消费，需要为每个订阅创建队列并复制路由，而不是让所有消费者共享同一长期日志位置。这恰好换来了直观的任务完成语义。

Kafka 内部机制

Partition append-only log

每个分区是有序追加日志，记录有单调 offset。生产者批量追加，消费者按 offset 拉取；顺序磁盘 IO、操作系统 page cache、批处理/压缩以及高效网络传输使其适合高吞吐。

Consumer Group

组内每个分区在一个时刻分配给一个消费者，因此：

  • 分区内顺序容易保持；
  • 最大有效并行度受分区数限制；
  • 成员变化触发分区再分配；
  • 不同组维护独立 offset，可重复读取同一日志。

Retention 与回放

Broker 按时间或大小保留日志，而非 ACK 后删除。消费者可重置 offset 重放，这使事件流、审计和数据管道自然，但单条失败不能简单“留住队头”：通常要暂停分区、重试，或转发 retry/DLQ topic。

复制与一致性

分区 leader 接受读写，followers 复制；acks、ISR 和副本配置决定延迟/安全权衡。幂等 producer 可避免特定重试下的日志内重复；事务可原子写多个 Kafka 分区并协调 offset，但外部数据库副作用仍需 outbox/幂等等方案。

RocketMQ 内部机制

RocketMQ 的 Broker 通常把消息顺序写入 CommitLog，再构建按 Topic/Queue 的逻辑索引 ConsumeQueue。统一顺序写有利吞吐，逻辑队列支持消费定位。NameServer 提供轻量路由发现；消费者按队列分配并维护进度。

这种“物理日志 + 逻辑队列”让它既能高吞吐持久化，又围绕业务消息提供：

  • 顺序消息：同一 sharding key 进入同一队列；
  • 延迟/定时投递：由 Broker 的定时存储/调度机制到期转投；
  • 消费失败重试与 DLQ；
  • 事务消息：先写半消息，本地事务后提交/回滚，未知时回查生产者。

事务回查要求生产者能根据业务状态作确定判断；消费者仍可能收到重复消息。

Redis Streams 内部机制

Stream 是 Redis 键空间中的有序条目集合，每条记录有 milliseconds-sequence ID。底层使用为紧凑存储和范围查询优化的数据结构（实现随版本演进，不应把应用契约绑定到具体结构名）。

Consumer Group 维护：

  • group 的 last-delivered ID；
  • 每个 consumer；
  • PEL：已投递但未 ACK 的 entry、归属、空闲时间和投递次数。

因此可以 XPENDING 检查卡住任务，并以 XAUTOCLAIM 接管。但这也意味着应用必须主动实现超时、认领、重试和 DLQ。数据通常驻内存，持久性由 AOF/RDB 和复制决定，所以成本/容量模型与磁盘日志系统不同。

Redis Pub/Sub 内部机制

Redis 维护 channel/pattern 到当前客户端的订阅关系。PUBLISH 时遍历匹配订阅并把数据写入在线客户端输出缓冲区；没有持久日志、offset、PEL 或 ACK。于是它极低延迟、简单，却无法补发断线消息。这个底层事实直接决定它只能承担可丢通知。

机制到场景的推导

RabbitMQ：逐 delivery 状态 + Exchange + push/QoS
=> 灵活路由、任务分发、细粒度确认、低延迟

Kafka：分区追加日志 + offset + retention + pull/batch
=> 高吞吐、长期保留、多下游、任意回放、流处理

RocketMQ：CommitLog + ConsumeQueue + 业务消息机制
=> 高吞吐业务事件、顺序、延迟、事务检查、重试/DLQ

Redis Streams：内存型有序流 + PEL
=> 已有 Redis 时的轻量可靠流，但需自己补齐治理

Redis Pub/Sub：只维护在线订阅关系
=> 极低延迟广播，但断线即丢、不可恢复

性能不是单一数字

压测至少固定：消息大小、生产/消费并发、持久化级别、副本数、Confirm/acks、批量大小、积压量、路由数量、失败率、磁盘与网络。只报“每秒多少条”而不报这些条件没有选型价值。
