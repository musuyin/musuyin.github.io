02-project-usage

2026-10-11

本篇以原稿记录的 psych-core-api 到 psych-post 报告链路分析 RabbitMQ。路径与已实现能力属于原记录的代码快照，本次未读取该项目代码重新验证；建议改造与现状继续分开呈现。

RabbitMQ 在本项目中的使用

业务目标

实时会话结束后，需要读取聊天历史、提取词云、调用 LLM 生成报告、更新标题并可能创建预警。这些操作耗时且受模型配额限制，不应阻塞 WebSocket 实时链路，因此拆到 psych-post 异步处理。

sequenceDiagram
    participant E as psych-core-api/Engine
    participant M as MongoDB
    participant X as RabbitMQ Exchange
    participant Q as Queue
    participant P as psych-post
    E->>M: 更新会话时间和消息数
    E->>X: Publish PostNotify
    X->>Q: routing key + binding
    Q->>P: delivery (prefetch=1)
    P->>M: 读取消息/插入 Processing 报告
    P->>P: 词云 + LLM 报告
    P->>M: 更新报告/标题/预警
    P->>Q: ACK；失败则 NACK requeue

生产端

入口与消息内容

psych-core-api/biz/domain/engine/engine.go 在 Engine.Close() 收尾阶段：

  1. 仅处理已认证连接；
  2. 创建独立的 10 秒后台 Context，避免原会话 Context 取消；
  3. 检查 MongoDB 中会话仍有效；
  4. 检查消息数确有增长；
  5. 更新会话开始/结束时间和消息数；
  6. 构造 PostNotify 并发布。

消息结构见 psych-core-api/pkg/core/post.go，包含 Session、Usage、Info、Start、End、Config 等。当前注释说明用户/单位 ID 实际从 Info 中携带。

RabbitMQ 客户端

psych-core-api/biz/infra/mq/producer.go 使用 github.com/rabbitmq/amqp091-go：

  • 单例复用 Connection 和 Channel；
  • JSON 序列化；
  • 发布到配置的 Exchange 和 RoutingKey；
  • 设置 DeliveryMode: amqp.Persistent；
  • 发布失败最多重试 5 次，采用退避；
  • 监听连接关闭并尝试重连；
  • test 状态只记录消息，不实际发布；
  • Mutex 串行保护共享 Channel。

配置结构位于 psych-core-api/biz/conf/config.go：

type RabbitMQ struct {
    URL        string
    Exchange   string
    RoutingKey string
}

消费端

启动

psych-post/main.go 根据 Consumers 创建消费管理器并启动；收到 SIGINT/SIGTERM 后调用 Close() 等待消费者结束。

psych-post/biz/domain/report/report.go 的 StartConsume() 对每个 worker 配置：

PrefetchCount = 1
AutoAck       = false
NackRequeue   = true
AckMultiple   = false
Consumers     = 配置值

含义是：每个消费者最多持有一条未确认消息；业务函数成功才 ACK，失败重新入队。这既控制了 LLM 并发，也让连接故障/进程退出时未 ACK 消息有机会重投。

连接与消费循环

  • psych-post/pkg/mq/conn.go：维护 Connection，监听关闭并重连；
  • psych-post/pkg/mq/consumer.go：每轮创建 Channel、设置 QoS、调用 Consume，Channel 关闭后等待 5 秒恢复；
  • 每个 consumer 有自己的 Channel，Connection 共享，这是合理的 AMQP 使用方式。

业务处理

DoConsume() 当前主要步骤：

  1. 反序列化 PostNotify；
  2. 从 Info 取用户/单位 ID，校验 ObjectID；
  3. 读取并整理历史消息，统计轮数和词云；
  4. 新建随机报告 ID，插入 Processing 报告；
  5. 读取配置、构造 prompt、调用 LLM；
  6. 解析结果并把报告更新为 Success；
  7. 更新会话标题，必要时创建预警；
  8. 返回成功后由通用消费者 ACK。

已具备的能力

  • 实时链路与报告链路解耦；
  • RabbitMQ 排队削峰；
  • 固定 worker 数 + prefetch=1 控制高成本调用并发；
  • 消息设置为 persistent；
  • 消费者手动 ACK/NACK；
  • 连接/Channel 中断后的基础恢复；
  • 发布和连接采用退避重试。

当前不具备或未在仓库中发现的能力

缺口 后果
代码中未声明 Exchange/Queue/Binding 依赖外部预创建；环境漂移会导致启动或路由失败
无 Publisher Confirm Publish 返回 nil 不代表 Broker 已可靠接收/复制
mandatory=false 且无 Return 无匹配绑定时消息可能被丢弃而生产者不知情
Mongo 更新与发消息无 Outbox 更新成功、发布失败时任务永久缺失
消息无稳定 eventId 难以准确去重与追踪
消费无幂等唯一约束 重投会插入新 rptID，可能重复报告/模型计费/预警
永久 NackRequeue=true 格式错误、配置错误等毒消息可能高速无限循环
无延迟重试/DLQ 故障隔离与人工补偿困难
未见积压和最老消息年龄监控 可能很晚才发现报告处理停滞
wg.Add(1) 在启动 goroutine 之后 goroutine 极快退出时可能先 Done()，触发负计数 panic
生产端重连会并发替换全局 Connection/Channel 存在初始化时序、数据竞争和旧 Channel 失效风险，应以明确生命周期管理器重构并做 race/断线测试

尤其注意：解析非法 ID 时返回 false, nil，通用消费器仍会 NACK 并重入；这类永久坏消息不会自行恢复。StartConsume() 也应先完成全部 wg.Add 再启动 goroutine，遵守 WaitGroup 的生命周期约束。

典型故障窗口

窗口 A：Mongo 更新成功，Publish 前进程退出

会话状态已写入，但报告任务不存在。仅靠发布重试无法修复，建议 Outbox。

窗口 B：Broker 收到消息，Confirm 前连接断开

生产者不知道是否成功，重发可能重复，不重发可能丢失。因此 Confirm 解决“是否被 Broker 接收”的判断，幂等解决“不确定时重发”的重复。

窗口 C：报告写入成功，ACK 前消费者退出

消息重投。当前会生成新的 rptID 并再次调用模型，存在重复副作用。手动 ACK 保障“不轻易丢”，幂等才处理“重复”。

窗口 D：某条消息永久失败

当前不断 requeue，占用 worker 和日志，形成 retry storm。应按错误分类：瞬态错误有限退避重试；永久错误直接进入 DLQ。

建议的目标链路

Mongo 业务事务
  ├─ 更新会话
  └─ 插入 outbox(eventId, payload, NEW)
             |
             v
Outbox Relay --confirm + mandatory--> durable exchange -> quorum queue
                                                     -> retry queues -> DLQ
Consumer: eventId/业务唯一键原子占位 -> 执行业务 -> 标记完成 -> ACK

若 Mongo 部署支持事务，应将业务更新和 outbox 插入放在同一事务；Relay 允许重复发布，消费者必须幂等。拓扑可由 IaC 管理，也可由应用以相同参数幂等声明，但要避免不同服务声明参数冲突。

复习

  • Mongo 更新成功到 Publish 之前退出，会漏掉哪一步？
  • 为什么重新生成随机报告 ID 不能实现消费去重？
  • 消费者重连后还需重新声明或订阅哪些对象？
