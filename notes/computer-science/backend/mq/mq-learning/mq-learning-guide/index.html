消息队列与 RabbitMQ 学习手册

这套文档以本仓库的真实链路为主线：psych-core-api 在会话结束后发布任务，RabbitMQ 排队，psych-post 限流消费并生成报告。目标不是只会调用 API，而是能解释可靠性边界、处理重复/故障，并做基本选型。

代码基线：以当前工作区为准。文档会明确区分“项目已实现”和“建议方案”，不能把建议误当现状。

一张总图

实时请求                    异步边界                    高成本后台任务
psych-core-api  --PostNotify-->  exchange -> queue  --> psych-post workers
    Mongo 更新                  RabbitMQ                  读历史/词云/LLM/报告

这条链路的主要收益：

  1. 异步解耦：实时 WebSocket 链路无需等待报告生成。
  2. 削峰填谷：集中结束的会话先排队，后台只按固定并发调用模型。
  3. 故障隔离：报告服务短暂故障不应拖垮实时服务。
  4. 可扩展：增加消费者可提高吞吐，但必须同时考虑模型配额和数据库容量。

最重要的结论

  • MQ 普遍提供的是 at-least-once（至少一次），不是“业务恰好一次”。重复是必须处理的正常情况。
  • 消息持久化 + durable queue 仍不等于发布成功；生产端还需要 Publisher Confirm。
  • 手动 ACK 只能保证失败后有机会重投，不能阻止“业务成功但 ACK 丢失”造成重复。
  • 幂等不能依赖“先查再写”；并发下要靠 唯一约束/原子条件更新。
  • DB 更新与发消息之间存在双写问题，常用 Transactional Outbox 解决。
  • 永久 NACK(requeue=true) 会制造毒消息热循环，应使用有限重试、退避和 DLQ。
  • 选型先问语义和负载，而不是品牌：需不需要回放、复杂路由、严格顺序、超高吞吐、延迟消息、运维成本？

建议学习方法

每篇先阅读，再到代码中定位对应实现；完成第 6 篇实验；最后闭卷回答 Questions.md。答案应包含故障窗口，而不只是 API 名称。例如：

消费者写库成功后宕机、尚未 ACK，会发生什么？如何避免重复报告和重复模型计费？

能完整回答这类问题，才算掌握消息队列的实际使用。
