01-basic-concepts

2026-10-11

消息队列把提交任务与完成业务解耦，也让故障窗口跨越多个系统。先建立 Producer、Broker、Consumer 与消息契约的模型，再用三种投递语义解释 ACK、重复和恢复。

消息队列与 RabbitMQ 基本概念

为什么使用消息队列

消息队列位于生产者和消费者之间，典型价值是：

  • 异步：生产者提交任务后尽快返回；
  • 解耦：双方只依赖消息契约，不直接同步调用；
  • 削峰：瞬时请求留在 Broker，消费者按能力处理；
  • 广播/分发：同一事件可触发多个下游；
  • 缓冲故障：消费者短暂不可用时暂存任务。

代价也很明确：系统变成最终一致；要处理重复、乱序、积压、消息契约演进、Broker 运维和跨系统事务。

通用术语

  • Producer：发送消息的应用。
  • Broker：接收、存储、投递消息的中间件节点/集群。
  • Consumer：处理消息的应用实例。
  • Message：载荷加元数据，如 message ID、时间、类型、版本、追踪信息。
  • Queue/Topic：消息组织与订阅单位。不同产品语义不完全相同。
  • Consumer Group：组内竞争消费，通常一条消息由组内一个成员处理；不同组各得一份。
  • ACK：消费者确认处理完成，Broker 才可删除或推进消费位置。
  • Retry / DLQ：失败重试与最终隔离。
  • Backlog/Lag：尚未消费的消息量或消费进度差。

三种投递语义

At-most-once：至多一次

可能丢，但不重投。例如收到就自动 ACK，随后业务失败。适合可丢的瞬时通知或指标。

At-least-once：至少一次

尽量不丢，但可能重复。典型流程是业务成功后手动 ACK；若成功后 ACK 前宕机，Broker 会重投。生产端超时重试也可能重复。这是业务系统最常见且可实现的语义。

Exactly-once：恰好一次

需要先定义范围。某些产品可在自身日志或事务范围内提供 exactly-once processing，但无法自动让任意数据库、HTTP 服务、邮件和扣款都只发生一次。跨系统通常仍靠：

至少一次投递 + 幂等业务处理 + 原子状态转换/事务

RabbitMQ 核心模型

RabbitMQ 常用 AMQP 0-9-1 模型：生产者一般不直接发给队列，而是发给 Exchange。

Producer -> Exchange --Binding/routing key--> Queue -> Consumer
  • Connection：TCP 长连接，创建成本较高，应复用。
  • Channel：复用在 Connection 上的轻量逻辑连接；通常每个发布单元/消费者使用自己的 Channel。多数客户端 Channel 不应被无保护地并发共享。
  • Exchange：根据类型和绑定决定消息路由。
  • Queue：保存待投递消息。
  • Binding：Exchange 到 Queue 的路由规则。
  • Routing Key：生产者发布时携带的路由键。
  • Consumer Tag：消费者在 Channel 内的标识，不等于持久消费进度。
  • Virtual Host：逻辑隔离命名空间和权限。

Exchange 类型

类型 路由方式 常见用途
direct binding key 与 routing key 精确匹配 按业务类型路由任务
topic 以 . 分段，* 匹配一段，# 匹配多段 领域事件，如 report.created.*
fanout 忽略 routing key，发往全部绑定队列 广播
headers 按消息 header 匹配 少量特殊规则，通常不作为首选
default 空名称 direct exchange，routing key 等于队列名 简单直投队列

广播需要多个队列。 多个消费者监听同一个队列是竞争消费，不是每人一份；要让报告、计费、审计都收到同一事件，应各有队列并绑定到同一 Exchange。

队列与消息生命周期

两个“持久”必须分开：

  • Queue durable=true：Broker 重启后保留队列元数据；
  • Message delivery_mode=2：消息按持久消息处理。

通常两者都需要。即便如此，从发送到安全落盘/复制仍有窗口，所以还需要 Publisher Confirm。高可用可使用 quorum queue，由 Raft 复制；它提高容灾能力，但有复制成本，且仍不能替代客户端确认和业务幂等。

常用属性：

  • exclusive：连接关闭后通常删除，仅该连接使用；
  • auto-delete：最后消费者消失等条件满足时删除；
  • TTL：消息或队列过期；
  • max-length：限制长度/字节数；
  • DLX：消息被拒绝且不重入、过期或超限时转发到死信交换机。

消费、ACK 与 QoS

  • autoAck=true：Broker 投递即视为完成，业务异常会丢消息。
  • 手动 ACK：业务完整成功后 Ack。
  • Nack(requeue=true)：重新入队；永久故障会无限循环。
  • Nack/Reject(requeue=false)：丢弃，或配置 DLX 后进入死信流程。
  • basic.qos / prefetch：一个 Channel/Consumer 最多持有多少未确认消息，用于背压和公平分配。

若任务耗时差异大，prefetch=1 公平且易控制并发，但吞吐可能偏低；短任务可提高 prefetch。应以处理耗时、内存、失败成本和下游容量压测决定。

顺序、重复和回放

RabbitMQ 队列大体按入队顺序投递，但以下行为会打乱“业务完成顺序”：多消费者并发、redelivery、优先级队列、消费者失败。若同一业务键必须有序，可让同键进入固定分片队列并单消费者处理，或在业务层做版本检查。

RabbitMQ 的传统队列偏向“消费后删除”，不是长期事件日志；虽有 Streams 功能，但产品主流心智仍与 Kafka 的可回放分区日志不同。

消息契约建议

不要只发送裸业务 JSON。推荐 envelope：

{
  "eventId": "uuid",
  "eventType": "conversation.closed",
  "schemaVersion": 1,
  "occurredAt": "2026-09-24T10:00:00Z",
  "aggregateId": "conversation-id",
  "traceId": "...",
  "payload": {}
}

eventId 用于幂等，aggregateId 用于分区/聚合，版本用于兼容演进，时间和 trace 用于排障。新增字段应保持旧消费者可忽略；破坏性变更应升版本或新事件类型。
