RabbitMQ

2025-10-12

#后端#数据库#中间件#消息队列

RabbitMQ 从同步/异步的业务差异进入，再学习 Exchange、Queue、Binding、Consumer 的路由模型。Spring AMQP 简化收发之后，仍需明确 Confirm、持久化、ACK、重试与幂等各保护哪个故障窗口。

版本边界：原稿 Lazy Queue 参数与镜像队列章节属于历史版本资料。现代 classic queue 已不再支持 lazy 模式设置，见 RabbitMQ 历史说明。高可用队列按目标版本评估 quorum queue。

同步/异步通信

同步通信

同步通讯是指发送方在发送消息后，会等待接收方的回应，直到收到回应后才会继续执行后续操作

  • 阻塞：发送方在等待回应期间会被阻塞，无法进行其他操作
  • 顺序执行：消息的处理是按照发送和接收的顺序进行的，确保了消息的时序性
  • 实时反馈：发送方可以立即得到接收方的回应，适用于需要立即确认的场景
  • 占用资源：由于需要等待，可能会造成资源的浪费，如线程阻塞

异步通信

异步通讯是指发送方在发送消息后，不需要等待接收方的立即回应，就可以继续执行其他操作。接收方在处理完消息后，可能会在未来的某个时间点给出回应

  • 非阻塞：发送方在发送消息后可以立即继续其他工作，不会因为等待回应而被阻塞
  • 解耦：发送方和接收方在时间上解耦，可以独立处理各自的任务
  • 灵活：异步通讯可以处理更复杂的通信模式，如消息队列、事件驱动等
  • 资源利用率高：更高效地利用资源，因为不需要等待，可以提高系统的吞吐量

MQ 技术选型

为什么选用消息队列

同步调用

  • 时效性强，下一步操作依赖于上一步操作

但是

  • 业务耦合，扩展性差，不符合开闭原则
  • 性能差
  • 级联失败：一个模块的故障导致整个服务的故障

异步调用

异步调用基于消息通知，一般包含三个角色消息

  1. 发送者：投递消息的人
  2. 消息代理：管理、暂存、转发消息的人
  3. 消息接收者：接收和处理消息的人

优点：

  • 接触耦合，拓展性强
  • 无需等待，性能好
  • 故障隔离
  • 削峰填谷

缺点：

  • 不能得到调用结果
  • 不能确定下游业务执行是否成功
  • 业务安全依赖于消息代理（Broker）的可靠性

启动

docker run \
 -e RABBITMQ_DEFAULT_USER=musuyin \

 --name rabbitmq \
 --hostname rabbitmq \

 -d \

指令说明：

  • docker run：基本的 Docker 命令，用于启动一个新的容器实例
  • -e RABBITMQ_DEFAULT_USER=musuyin：设置 RabbitMQ 服务的默认用户名
  • -e RABBITMQ_DEFAULT_PASS=123456：设置 RabbitMQ 服务的默认密码
  • -v rabbitmq-plugins:/plugins：将一个名为 rabbitmq-plugins 的卷映射到容器的/plugins 目录，用于存放 RabbitMQ 的插件。这里的 rabbitmq-plugins 是一个卷的名称，而不是宿主机的路径
  • --name rabbitmq：指定容器的名称为 rabbitmq
  • --hostname rabbitmq：设置容器的主机名为 rabbitmq
  • -p 15672:15672：将宿主机的端口 15672 映射到容器的端口 15672，这是 RabbitMQ 管理界面的默认端口
  • -p 5672:5672：将宿主机的端口 5672 映射到容器的端口 5672，这是 RabbitMQ 用于 AMQP 协议通信的默认端口
  • -d：在后台运行容器（守护进程）
  • rabbitmq:latest：使用最新的 RabbitMQ 官方镜像来创建容器

Java 客户端-Spring AMQP

Spring 在基础的 Java 客户端使用上进行了封装

Spring AMQP 核心组件：

  • RabbitTemplate：用于发送消息
  • @RabbitListener：用于监听队列消费消息
  • AmqpAdmin：用于声明队列、交换机、绑定关系

依赖引入：

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>

配置文件：

spring:
  rabbitmq:
    host: localhost
    port: 5672
    virtual-host: /
    username: musuyin
    password: 123456

基本使用

发送消息

@Autowired
private RabbitTemplate rabbitTemplate;

// 发送到指定队列（通过默认交换机）
rabbitTemplate.convertAndSend("queue.name", "Hello RabbitMQ");

// 发送到指定交换机和路由键
rabbitTemplate.convertAndSend("exchange.name", "routing.key", "Hello RabbitMQ");

接收消息

@RabbitListener(queues = "queue.name")
public void handleMessage(String message) {
    System.out.println("收到消息: " + message);
}

监听方法参数也可以使用 Message 类型获取原始消息：

@RabbitListener(queues = "queue.name")
public void handleMessage(Message message) {
    byte[] body = message.getBody();
    MessageProperties props = message.getMessageProperties();
}

WorkQueue

WorkQueue（工作队列）模式：多个消费者共同消费同一个队列，实现任务的负载均衡。

Publisher → Queue → Consumer1
                 → Consumer2
                 → Consumer3

默认行为（轮询）：消息会均匀分配给每个消费者，不考虑消费者的处理能力。

问题：消费能力强的消费者处理完后会空闲等待，能力弱的消费者积压大量消息。

解决：能者多劳

通过配置 prefetch 限制每次预取的消息数量，消费者处理完一条才会取下一条：

spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1  # 每次只预取1条消息

设置后，RabbitMQ 会根据消费者的实际消费速度分配消息，处理快的消费者自然会获取更多消息。

Fanout 交换机

Fanout（扇出）交换机：将消息广播给所有绑定的队列，忽略路由键。

Publisher → FanoutExchange → Queue1 → Consumer1
                           → Queue2 → Consumer2
                           → Queue3 → Consumer3

适用场景：消息需要被多个服务同时处理，如订单成功后同时通知库存服务、积分服务、通知服务。

// 发送消息到 Fanout 交换机（路由键传空字符串，会被忽略）
rabbitTemplate.convertAndSend("fanout.exchange", "", "广播消息");
// 消费者1
@RabbitListener(queues = "fanout.queue1")
public void handleMessage1(String message) { ... }

// 消费者2
@RabbitListener(queues = "fanout.queue2")
public void handleMessage2(String message) { ... }

Direct 交换机

Direct 交换机：根据消息的路由键（Routing Key）将消息路由到完全匹配的队列。

Publisher → DirectExchange → (routingKey=red)   → Queue1 → Consumer1
                           → (routingKey=blue)  → Queue2 → Consumer2
                           → (routingKey=green) → Queue1 → Consumer1（多重绑定）

特点：

  • 一个队列可以绑定多个路由键
  • 同一路由键可以绑定多个队列（此时与 Fanout 行为相同）
  • 精确匹配，不支持通配符
// 发送红色消息
rabbitTemplate.convertAndSend("direct.exchange", "red", "红色消息");

// 发送蓝色消息
rabbitTemplate.convertAndSend("direct.exchange", "blue", "蓝色消息");
@RabbitListener(queues = "direct.queue1")
public void handleQueue1(String message) { ... }  // 收到 red 和 green

@RabbitListener(queues = "direct.queue2")
public void handleQueue2(String message) { ... }  // 收到 blue 和 green

Topic 交换机

Topic 交换机：支持通配符的路由键匹配，是功能最强大的交换机类型。

通配符规则：

  • *：匹配一个单词（单词之间用 . 分隔）
  • #：匹配零个或多个单词
RoutingKey: china.weather   → 匹配 china.*、#.weather、china.#、#
RoutingKey: china.news.hot  → 匹配 china.#、#.hot、#，不匹配 china.*
Publisher → TopicExchange → (china.#)     → Queue1 → Consumer1（中国所有话题）
                          → (#.weather)   → Queue2 → Consumer2（所有天气话题）
// 发布中国天气消息
rabbitTemplate.convertAndSend("topic.exchange", "china.weather", "今日晴天");

// 发布中国新闻消息
rabbitTemplate.convertAndSend("topic.exchange", "china.news", "重大新闻");
@RabbitListener(queues = "topic.queue1")  // 绑定 china.# 
public void handleChina(String message) { ... }

@RabbitListener(queues = "topic.queue2")  // 绑定 #.weather
public void handleWeather(String message) { ... }

三种交换机对比：

交换机类型 路由规则 适用场景
Fanout 广播所有队列 日志广播、事件通知
Direct 精确匹配路由键 按类型分发任务
Topic 通配符匹配路由键 多维度灵活路由

声明队列和交换机

Spring AMQP 提供两种方式声明队列和交换机：

方式一：Bean 声明（代码配置）

@Configuration
public class RabbitMQConfig {

    // 声明 Fanout 交换机
    @Bean
    public FanoutExchange fanoutExchange() {
        return new FanoutExchange("fanout.exchange");
    }

    // 声明队列
    @Bean
    public Queue fanoutQueue1() {
        return new Queue("fanout.queue1");
    }

    @Bean
    public Queue fanoutQueue2() {
        return new Queue("fanout.queue2");
    }

    // 绑定队列到交换机
    @Bean
    public Binding bindingQueue1(FanoutExchange fanoutExchange, Queue fanoutQueue1) {
        return BindingBuilder.bind(fanoutQueue1).to(fanoutExchange);
    }

    @Bean
    public Binding bindingQueue2(FanoutExchange fanoutExchange, Queue fanoutQueue2) {
        return BindingBuilder.bind(fanoutQueue2).to(fanoutExchange);
    }

    // Direct 交换机绑定示例
    @Bean
    public DirectExchange directExchange() {
        return new DirectExchange("direct.exchange");
    }

    @Bean
    public Binding directBinding(DirectExchange directExchange, Queue fanoutQueue1) {
        return BindingBuilder.bind(fanoutQueue1).to(directExchange).with("red");
    }
}

方式二：注解声明（更简洁）

直接在 @RabbitListener 中用 @QueueBinding 声明队列、交换机和绑定关系，无需额外配置类：

@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "direct.queue1"),
    exchange = @Exchange(name = "direct.exchange", type = ExchangeTypes.DIRECT),
    key = {"red", "blue"}
))
public void handleDirectQueue1(String message) { ... }

@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "topic.queue1"),
    exchange = @Exchange(name = "topic.exchange", type = ExchangeTypes.TOPIC),
    key = "china.#"
))
public void handleTopicQueue1(String message) { ... }

消息转换器

Spring AMQP 默认使用 JDK 序列化发送对象，可读性差且安全性低，推荐替换为 JSON 序列化。

引入 Jackson 依赖：

<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
</dependency>

配置消息转换器（发送方和接收方都需要配置）：

@Bean
public MessageConverter messageConverter() {
    Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
    converter.setCreateMessageIds(true); // 为消息生成唯一 ID，方便幂等性处理
    return converter;
}

配置后，发送 Java 对象时会自动序列化为 JSON，接收时自动反序列化：

// 发送 Java 对象
rabbitTemplate.convertAndSend("exchange", "key", new User("Alice", 25));

// 接收时直接指定类型
@RabbitListener(queues = "queue.name")
public void handleMessage(User user) { ... }

可靠性机制

消息从发送到消费的完整链路：

Publisher → [生产者确认] → RabbitMQ Broker → [消息持久化] → Queue → [消费者确认] → Consumer

生产者可靠性

生产者重连

网络抖动时连接可能失败，Spring AMQP 支持自动重连：

spring:
  rabbitmq:
    connection-timeout: 1s
    template:
      retry:
        enabled: true
        initial-interval: 1000ms  # 首次重试等待
        multiplier: 1             # 等待时长倍数（1 表示等待时长不变）
        max-attempts: 3           # 最大重试次数

注意：这是阻塞式重试，会阻塞当前线程，生产环境慎用。

生产者确认（Publisher Confirms）

确认消息是否成功到达 RabbitMQ Broker，分两种情况：

  • ConfirmCallback：消息到达交换机时触发（成功或失败都会触发）
  • ReturnCallback：消息从交换机路由到队列失败时触发
spring:
  rabbitmq:
    publisher-confirm-type: correlated  # 异步确认（推荐）
    publisher-returns: true             # 开启 Return 回调
    template:
      mandatory: true                   # 消息路由失败时返回给生产者
@Autowired
private RabbitTemplate rabbitTemplate;

@PostConstruct
public void init() {
    // 设置 Return 回调（全局，每个 RabbitTemplate 只能设置一个）
    rabbitTemplate.setReturnsCallback(returned -> {
        log.error("消息路由失败，exchange={}, routingKey={}, message={}",
            returned.getExchange(), returned.getRoutingKey(), returned.getMessage());
    });
}

public void sendMessage(String exchange, String key, Object msg) {
    // 使用 CorrelationData 关联 Confirm 回调
    CorrelationData cd = new CorrelationData(UUID.randomUUID().toString());
    cd.getFuture().addCallback(
        confirm -> {
            if (confirm.isAck()) {
                log.info("消息到达交换机成功，id={}", cd.getId());
            } else {
                log.error("消息到达交换机失败，id={}，原因={}", cd.getId(), confirm.getReason());
            }
        },
        ex -> log.error("消息发送异常", ex)
    );
    rabbitTemplate.convertAndSend(exchange, key, msg, cd);
}

生产者确认会带来额外性能开销，仅在业务对消息可靠性要求极高时开启。

消息持久化

RabbitMQ 默认将消息存储在内存中，重启后会丢失。持久化分三层：

交换机持久化：durable = true（Spring AMQP 默认就是持久化）

队列持久化：

@Bean
public Queue durableQueue() {
    return QueueBuilder.durable("my.queue").build();  // 持久化队列
}

消息持久化：

Message message = MessageBuilder
    .withBody("持久化消息".getBytes())
    .setDeliveryMode(MessageDeliveryMode.PERSISTENT)  // 持久化投递模式
    .build();
rabbitTemplate.send("exchange", "key", message);

使用 RabbitTemplate.convertAndSend() 配合 JSON 转换器时，默认即为持久化消息。

Lazy Queue（惰性队列）

RabbitMQ 3.6+ 引入，消息直接写入磁盘而非内存，内存占用极低：

@Bean
public Queue lazyQueue() {
    return QueueBuilder.durable("lazy.queue")
        .lazy()  // 开启惰性模式
        .build();
}

优点：内存占用低，可存储海量消息，重启不丢失
缺点：消费速度略低于内存队列

RabbitMQ 3.12+ 所有持久化队列默认采用惰性模式。

消费者可靠性

消费者确认机制（Acknowledge）

消费者处理消息后需要向 RabbitMQ 发送确认，RabbitMQ 才会删除该消息。

三种确认模式：

模式 配置值 说明
自动确认 none 消息投递给消费者就立即确认（不安全）
手动确认 manual 代码中显式调用 ack/nack
自动确认（推荐） auto Spring 根据监听方法是否抛出异常自动确认或拒绝 
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto  # 推荐使用 auto

auto 模式下的行为：

  • 方法正常执行完毕 → 自动 ack，消息从队列删除
  • 方法抛出 AmqpRejectAndDontRequeueException → nack，消息不重新入队，直接丢弃（或进死信队列）
  • 方法抛出其他异常 → nack，消息重新入队，会被再次消费

失败重试

默认情况下消费失败会无限重新入队，导致消息风暴。建议开启本地重试：

spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto
        retry:
          enabled: true
          initial-interval: 1000ms
          multiplier: 2      # 等待时长倍增（指数退避）
          max-attempts: 3    # 最大重试3次
          stateless: true    # 无状态重试（不涉及事务时使用）

重试耗尽后，消息的处理策略由 MessageRecoverer 决定：

策略 类名 说明
丢弃（默认） RejectAndDontRequeueRecoverer 直接丢弃消息
重新入队 ImmediateRequeueMessageRecoverer 重新入队（慎用）
投递到死信 RepublishMessageRecoverer 投递到指定的死信交换机（推荐） 
@Bean
public MessageRecoverer republishMessageRecoverer(RabbitTemplate rabbitTemplate) {
    // 重试耗尽后投递到 error.direct 交换机，路由键为 error
    return new RepublishMessageRecoverer(rabbitTemplate, "error.direct", "error");
}

业务幂等性

RabbitMQ 的 at-least-once 语义意味着消息可能被重复消费，业务层需保证幂等。

方案一：唯一消息 ID

配置消息转换器生成唯一 ID（前文已配置 setCreateMessageIds(true)），消费时记录已处理的消息 ID：

@RabbitListener(queues = "queue.name")
public void handleMessage(Message message) {
    String messageId = message.getMessageProperties().getMessageId();
    // 判断 messageId 是否已处理（Redis SET NX 或数据库唯一索引）
    if (isProcessed(messageId)) return;
    // 业务处理
    process(message);
    markProcessed(messageId);
}

方案二：业务唯一标识

更常用，直接用业务字段（如订单 ID）做幂等判断，无需依赖消息 ID：

@RabbitListener(queues = "order.queue")
public void handleOrder(OrderDTO order) {
    // 查询订单状态，已处理则跳过
    Order existing = orderService.getById(order.getId());
    if (existing != null && existing.getStatus() != OrderStatus.INIT) {
        return;
    }
    orderService.process(order);
}

延迟队列

延迟队列用于处理需要延时触发的场景，如：订单超时未支付自动取消、定时提醒。

RabbitMQ 本身不直接支持延迟队列，有两种实现方式。

死信队列实现延迟

死信（Dead Letter）：消息在以下情况会成为死信：

  1. 消费者 nack 且不重新入队
  2. 消息过期（TTL 到期）
  3. 队列达到最大长度

死信会被投递到死信交换机（DLX），通过这个机制可以实现延迟：

Publisher → 普通队列(TTL=30min, DLX=dlx.exchange) → 消息过期 → 死信交换机 → 死信队列 → Consumer
@Bean
public Queue normalQueue() {
    return QueueBuilder.durable("normal.queue")
        .ttl(30 * 60 * 1000)               // 消息存活30分钟
        .deadLetterExchange("dlx.exchange") // 指定死信交换机
        .deadLetterRoutingKey("dlx.key")    // 死信路由键
        .build();
}

@Bean
public DirectExchange dlxExchange() {
    return new DirectExchange("dlx.exchange");
}

@Bean
public Queue dlxQueue() {
    return new Queue("dlx.queue");
}

@Bean
public Binding dlxBinding() {
    return BindingBuilder.bind(dlxQueue()).to(dlxExchange()).with("dlx.key");
}

消费者监听死信队列处理超时消息：

@RabbitListener(queues = "dlx.queue")
public void handleExpiredOrder(OrderDTO order) {
    // 处理30分钟未支付的订单
    orderService.cancelIfUnpaid(order);
}

缺点：TTL 固定，无法为每条消息设置不同的延迟时间；且队列头部消息未过期时，后面已过期的消息不会立刻进入死信（队列头阻塞）。

DelayExchange 插件

官方提供的 rabbitmq_delayed_message_exchange 插件，支持为每条消息设置独立的延迟时间。

安装插件：

# 进入容器
docker exec -it rabbitmq bash
# 启用插件
rabbitmq-plugins enable rabbitmq_delayed_message_exchange

声明延迟交换机：

@Bean
public DirectExchange delayExchange() {
    return ExchangeBuilder.directExchange("delay.exchange")
        .delayed()       // 声明为延迟交换机
        .durable(true)
        .build();
}

发送延迟消息：

public void sendDelayMessage(Object msg, int delayMs) {
    rabbitTemplate.convertAndSend("delay.exchange", "delay.key", msg, message -> {
        message.getMessageProperties().setDelay(delayMs);  // 设置延迟时间（毫秒）
        return message;
    });
}

// 30分钟后触发
sendDelayMessage(order, 30 * 60 * 1000);
@RabbitListener(queues = "delay.queue")
public void handleDelayMessage(OrderDTO order) {
    orderService.cancelIfUnpaid(order);
}

两种方案对比：

方案 优点 缺点
死信队列 原生支持，无需插件 队列头阻塞，延迟不精确
DelayExchange 插件 精确延迟，每条消息独立控制 需要安装插件，延迟消息存储在内存

集群与高可用

普通集群

多个 RabbitMQ 节点组成集群，队列的数据只存在于某一个节点，其他节点只存储元数据（交换机、队列定义）。

  • 优点：提高并发性能
  • 缺点：队列所在节点宕机，该队列不可用

镜像集群（Mirroring）

队列在多个节点之间同步，任意节点宕机不影响服务（RabbitMQ 3.x 推荐方案）。

# 设置镜像策略，将所有队列在所有节点同步
rabbitmqctl set_policy ha-all "^" '{"ha-mode":"all"}'

Quorum Queue（仲裁队列）

RabbitMQ 3.8+ 推荐，基于 Raft 协议，比镜像队列更可靠、更简单。

@Bean
public Queue quorumQueue() {
    return QueueBuilder.durable("quorum.queue")
        .quorum()  // 声明为仲裁队列
        .build();
}

Quorum Queue 特性：

  • 基于多数派投票，保证强一致性
  • 自动处理节点故障和数据同步
  • 不支持非持久化消息（天然持久化）
