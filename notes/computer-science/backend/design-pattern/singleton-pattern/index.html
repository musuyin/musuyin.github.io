单例模式（Singleton Pattern）

2026-08-24

#设计模式#创建型

单例约束的是实例数量，线程安全还包括安全发布与实例内部状态的并发访问。比较 Java 实现时，先看初始化时机，再看发布保障，最后看序列化、反射和测试隔离。

定义

单例模式确保一个类只有一个实例，并提供一个全局访问点来获取该实例。

问题场景

某些对象在系统中应该只存在一份，例如：

  • 配置管理器：应用配置应该只加载一次
  • 日志系统：所有日志应该写入同一个文件/流
  • 数据库连接池：连接复用，避免重复建立连接
  • 缓存管理器：全局唯一的缓存实例

如果不做控制，多个地方各自创建实例会导致资源浪费、数据不一致等问题。

实现方式

饿汉式（Eager Initialization）

类加载时立即创建实例。

public class Singleton {
    // 类加载时就创建实例
    private static final Singleton instance = new Singleton();
    
    // 私有构造器
    private Singleton() {}
    
    // 全局访问点
    public static Singleton getInstance() {
        return instance;
    }
}

优点：

  • 线程安全，无需额外同步
  • 实现简单

缺点：

  • 无法延迟初始化
  • 如果实例创建成本高但不一定用到，会浪费资源

懒汉式（Lazy Initialization）

第一次使用时才创建实例。

非线程安全版本

public class Singleton {
    private static Singleton instance;
    
    private Singleton() {}
    
    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();  // 线程不安全！
        }
        return instance;
    }
}

问题：多线程环境下可能创建多个实例。

线程安全版本 - synchronized

public class Singleton {
    private static Singleton instance;
    
    private Singleton() {}
    
    public static synchronized Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

缺点：每次调用都经过同步；实际开销需结合调用频率和 JVM 优化测量。

双重检查锁定（Double-Checked Locking）

public class Singleton {
    private static volatile Singleton instance;
    
    private Singleton() {}
    
    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查，无锁
            synchronized (Singleton.class) {       // 加锁
                if (instance == null) {            // 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

优点：

  • 延迟初始化
  • 大多数情况下无锁，性能好
  • 线程安全

关键点：

  • 第一次检查减少同步开销
  • volatile 关键字确保内存可见性，防止指令重排

静态内部类（Bill Pugh Singleton）

public class Singleton {
    private Singleton() {}
    
    private static class SingletonHolder {
        static final Singleton instance = new Singleton();
    }
    
    public static Singleton getInstance() {
        return SingletonHolder.instance;
    }
}

优点：

  • 延迟初始化（只在调用 getInstance() 时加载内部类）
  • 利用 ClassLoader 机制保证线程安全
  • 实现简洁，无需显式同步

静态内部类依赖类初始化的同步保障，可参考 JLS 类初始化过程。是否采用还取决于初始化参数、生命周期及测试需求。

枚举（Enum）

public enum Singleton {
    INSTANCE;
    
    public void doSomething() {
        // 业务逻辑
    }
}

// 使用
Singleton.INSTANCE.doSomething();

优点：

  • 线程安全
  • 天然防止反序列化创建新实例
  • 防止反射破坏单例
  • 代码最简洁

限制：

  • 枚举也是单例的实现方式，但不能像普通类那样继承其他类
  • 需要参数化初始化或复杂生命周期时应另行设计

单例的破坏与防护

反射破坏

// 破坏
Constructor<?> constructor = Singleton.class.getDeclaredConstructor();
constructor.setAccessible(true);
Singleton instance2 = (Singleton) constructor.newInstance();

有限防护：构造器中检查实例可以拦截部分重复创建，但对首次构造顺序等情形并非普遍可靠

private Singleton() {
    if (instance != null) {
        throw new RuntimeException("单例已存在");
    }
}

序列化破坏

// 破坏
ObjectInputStream.readObject() 会创建新实例

防护：实现 readResolve() 方法

private Object readResolve() {
    return getInstance();
}

对比总结

实现方式 线程安全 延迟加载 性能 代码复杂度
饿汉式 ✅ ❌ 最优 简单
懒汉式（synchronized） ✅ ✅ 一般 简单
双重检查锁定 ✅ ✅ 很好 中等
静态内部类 ✅ ✅ 很好 简单
枚举 ✅ ❌ 最优 简单

推荐方案：

  • Java：枚举 > 静态内部类 > 饿汉式
  • 其他语言：根据语言特性选择

实际应用

// 日志系统
public class Logger {
    private static volatile Logger instance;
    private PrintWriter writer;
    
    private Logger() {
        try {
            writer = new PrintWriter("app.log");
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
    
    public static Logger getInstance() {
        if (instance == null) {
            synchronized (Logger.class) {
                if (instance == null) {
                    instance = new Logger();
                }
            }
        }
        return instance;
    }
    
    public void log(String message) {
        writer.println(message);
        writer.flush();
    }
}

// 使用
Logger.getInstance().log("Application started");
Logger.getInstance().log("User logged in");

注意事项

⚠️ 单例的缺陷：

  1. 难以测试：全局状态难以在测试中隔离
  2. 隐藏依赖：不清楚类依赖了单例
  3. 线程安全复杂：多线程环境需谨慎
  4. 频繁应用会导致高耦合：应审慎使用

💡 现代替代方案：

  • 依赖注入（Dependency Injection）框架
  • 工厂模式 + 工厂管理单一实例

对比其他模式

模式 目的 区别
单例 确保一个实例 全局唯一
工厂 解耦创建逻辑 可创建多个实例
对象池 复用对象 多个实例，重复利用
