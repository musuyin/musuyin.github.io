并发互斥场景

2026-08-26

#并发#Redis#MySQL

任务分发首先要解决“谁领取任务”，随后才是“领取者失败后如何恢复”。这两个阶段分别依赖原子分配与确认/重投机制；它们都不能单独保证业务副作用只执行一次。

核心问题

多个实例并发消费同一个消息队列时，如何保证同一条消息不被多个实例同时处理？

关键认知：锁的粒度应该下沉到元素级别，而不是锁住整个队列。

错误思路：实例 A 取出消息后持有全局锁，其他实例全部等待
正确思路：原子抢占某一条消息 + 立即释放，各实例并行处理各自拿到的消息

队列: [msg1, msg2, msg3, msg4]

实例1 原子抢到 msg1 → 独立处理
实例2 原子抢到 msg2 → 独立处理  ← 不需要等实例1完成
实例3 原子抢到 msg3 → 独立处理

锁的作用范围只是确定谁负责这条消息，消息一旦分配出去就各自并行处理。

方案一：MySQL 行锁

-- 原子地抢一条待处理任务
-- 自动提交事务中，UPDATE 完成并提交后释放锁；显式事务需等提交/回滚
UPDATE tasks
SET status = 'running', worker_id = ?, started_at = NOW()
WHERE status = 'pending'
ORDER BY created_at ASC
LIMIT 1;

-- affected_rows = 1：抢到了
-- affected_rows = 0：队列为空或被别人抢走，重试或等待
  • MySQL UPDATE 是原子语句；InnoDB 锁通常持有到事务提交或回滚，不能把语句结束等同于事务结束。见 InnoDB 锁文档
  • 并发执行相同 SQL 时，MySQL 保证最多只有一个实例能把同一行从 pending 改成 running
  • 不需要额外加互斥锁，UPDATE 的原子性本身就是并发保障

宕机恢复：定时扫描 status = 'running' 且 started_at 超时的行，重置为 pending。

方案二：Redis List（LPOP）

LPOP queue_name

Redis 单线程处理命令，LPOP 天然原子。同一时刻只有一个实例能弹出同一个元素，弹出后其他实例拿到的是下一个元素。不需要额外加锁。

适合：对持久化要求不高、消息量大、需要极低延迟的场景。

方案三：Redis Stream + Consumer Group（推荐）

底层结构

Stream 底层是 Radix Tree（基数树），每个节点存储 listpack（紧凑型连续内存，类似压缩列表）。

  • 消息 ID 格式：毫秒时间戳-序号（如 1690000000000-0），天然有序
  • Radix Tree 按 ID 范围查找效率高，适合“从某个 ID 之后读取”的场景
  • Redis 单线程处理命令，所有 Stream 操作（XADD、XREAD、XACK）本身都是原子的

两种消费模式

模式一：独立消费（广播）

XREAD COUNT 1 BLOCK 30000 STREAMS mystream $

每个实例维护自己的 lastID，彼此不共享进度。同一条消息会被所有实例读到，适合广播通知，不适合任务分发。

模式二：Consumer Group（任务分发）

# 创建消费组
XGROUP CREATE mystream workers $ MKSTREAM

# 消费者拉取（> 表示"给我一条没有被任何人取走的消息"）
XREADGROUP GROUP workers instanceA COUNT 1 BLOCK 30000 STREAMS mystream >

# 处理完成后 ACK
XACK mystream workers <message-id>

PEL 机制（核心）

Consumer Group 内部维护一个 PEL（Pending Entries List），记录“已投递给某个 Consumer 但尚未 ACK 的消息”。

消息 msg1 投递给 instanceA → 进入 PEL：{msg1 → instanceA}
instanceB 执行 XREADGROUP  → 拿到 msg2，不会拿到 msg1
instanceA 处理完，XACK     → msg1 从 PEL 移除

PEL 跟踪未确认消息的归属，正常读取新消息时不会重复分配。但认领超时消息不会停止旧消费者，业务处理仍可能重叠；必须设计幂等和超时边界。见 XCLAIM 文档

宕机恢复（XCLAIM）

Consumer 宕机后消息滞留在 PEL，永远不会 ACK。需要另一个实例定期认领：

# 查看滞留超过 60s 的消息
XPENDING mystream workers - + 10

# 认领超时消息（60000ms = 60s）
XCLAIM mystream workers instanceB 60000 <message-id>

认领后重新处理，因此消费逻辑必须是幂等的（处理前检查数据库状态，避免重复执行）。

三种方案对比

Redis Stream Consumer Group MySQL UPDATE Redis LPOP
原子性来源 PEL 机制 + 单线程 UPDATE 行锁 单线程
需要额外加锁 不需要 不需要 不需要
宕机恢复 XCLAIM 认领 扫超时 running 行 需自行实现
消息持久化 取决于 Redis 持久化配置 取决于事务与落盘配置 取决于 Redis 持久化配置
消息回溯 支持（按 ID 范围） 支持 不支持
适用场景 任务队列、需要 ACK 任务队列、强一致 简单队列、低延迟

常见误区

误区：取消息时需要先加 Redis 分布式锁，再取，再释放锁

这是把锁的粒度搞错了。正确理解：LPOP / XREADGROUP 的弹出/投递操作本身就是原子的，不需要在外面再套一层锁。加额外的锁反而会引入锁竞争和死锁风险。

需要加锁的场景：多个操作组合在一起需要原子性时（如“读-判断-写”三步合一），才需要 SET NX 分布式锁或 Lua 脚本。

方案四：RabbitMQ

并发分发机制

RabbitMQ 的并发安全由 AMQP 协议的 Channel + 消息确认机制（ACK） 保证，不需要额外加锁。

Exchange → Queue → [msg1, msg2, msg3, msg4]
                        ↓       ↓
                    instanceA  instanceB   ← RabbitMQ 轮询/按权重分发，天然互斥

每条消息从 Queue 弹出并投递给某个 Consumer 后，在 Consumer 发送 ACK 之前，这条消息处于 Unacked 状态，不会再投递给其他 Consumer。

核心概念

prefetch count（流量控制）

channel.basic_qos(prefetch_count=1)  # 同一时刻每个 Consumer 最多持有 1 条未 ACK 的消息

不设置 prefetch 的话，RabbitMQ 会把大量消息预推给某个 Consumer，导致负载不均。设为 1 是任务队列场景的标准做法。

消息状态流转

Ready → Unacked（投递给 Consumer）→ 已删除（ACK）
                                  → 重新入队（NACK / 超时）

宕机恢复

Consumer 断开连接后，该 Consumer 持有的所有 Unacked 消息自动重新入队（Ready），由其他 Consumer 重新消费。不需要像 Redis Stream 那样手动 XCLAIM。

与 Redis Stream 的关键差异

RabbitMQ 消息被 ACK 后从队列删除，无法回溯历史。Redis Stream 消息 ACK 后仍保留在 Stream 中，可以按 ID 范围重放。

方案五：Kafka

并发分发机制

Kafka 的并发模型与前面几种本质不同：它不是“谁来抢”，而是静态分区分配。

Topic: okx-signals
  Partition 0: [msg1, msg4, msg7, ...]  → instanceA 负责
  Partition 1: [msg2, msg5, msg8, ...]  → instanceB 负责
  Partition 2: [msg3, msg6, msg9, ...]  → instanceC 负责

同一个 Consumer Group 内，一个 Partition 同一时刻只能被一个 Consumer 消费。这个约束由 Kafka Broker 的 Consumer Group 协调器（Group Coordinator）强制保证，不需要加锁。

Offset 机制

每个 Consumer 维护自己负责的 Partition 的消费进度（Offset），提交 Offset 相当于 ACK：

Partition 0 offset: 消费到第 100 条
instanceA 提交 offset=101 → Broker 记录
instanceA 重启后从已提交的 101 继续；业务处理与提交之间仍有失败窗口

自动提交 vs 手动提交

// 自动提交：每隔一段时间自动提交当前 offset，可能丢消息（处理中宕机）
config.Consumer.Offsets.AutoCommit.Enable = true

// 手动提交：处理完成后再提交，保证 at-least-once
session.MarkMessage(msg, "")
session.Commit()

宕机恢复（Rebalance）

某个 Consumer 宕机后，Kafka 触发 Rebalance，将该 Consumer 负责的 Partition 重新分配给组内其他 Consumer。重新分配后从上次提交的 Offset 继续消费。

Rebalance 期间整个 Consumer Group 暂停消费，这是 Kafka 的一个延迟抖动点。

Kafka 不适合“任务队列”场景的原因

Kafka 的分区数决定了最大并发度——3 个 Partition 最多 3 个 Consumer 并行，多余的 Consumer 闲置。且消息有序性只在单 Partition 内保证。

Kafka 真正擅长的是高吞吐日志流（埋点、日志收集、事件溯源），不是细粒度任务分发。

延伸：显式分布式锁的适用场景

Redis SET NX（Set if Not eXists）适合的是：不走消息队列，但多个实例可能同时触发同一个任务的场景。

// 典型场景：定时任务，多个实例同时触发，只允许一个执行
ok, _ := rdb.SetNX(ctx, "task:lock:hour:"+hourKey, instanceID, 10*time.Minute).Result()
if !ok {
    return // 其他实例已在执行，跳过
}
// 示例缺少安全解锁：须校验唯一持有者 token 后再原子删除
// 不能直接 DEL，过期后可能删除另一实例重新取得的锁

doTask()

与消息队列的区别：消息队列的“谁处理哪条消息”由队列本身决定；SET NX 锁只在有效租期内协调互斥；业务幂等仍需唯一键或状态机。安全解锁需原子比较唯一 token 后删除，见 Redis 分布式锁。
