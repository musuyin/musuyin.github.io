Kubernetes and Linux Troubleshooting Question Bank

2026-10-20

理解主线

题库训练的是排障路径：症状和范围 → 证据 → 假设 → 操作 → 验证。先用短回答说明调查逻辑，再补充命令和分支，避免把工具名堆成答案。

How to use this question bank

  • Understand the troubleshooting path instead of memorizing every command.
  • Start with a four-to-six-sentence answer.
  • Use the structure symptom → evidence → hypothesis → action → verification.
  • Explain what evidence you would collect before listing possible causes.
  • Add commands, branches, and preventive actions only after the basic answer is clear.

General troubleshooting framework

Confirm the symptom and scope

  • Capture the exact error message, status, and start time.
  • Determine whether the issue affects one instance, one node, one service, or the whole cluster.
  • Ask about recent deployments, configuration changes, certificate rotations, and infrastructure changes.

Collect evidence

  • Check status, conditions, events, logs, and metrics.
  • Compare a failing instance with a healthy one.
  • Identify the stage where the request or workload stops progressing.

Narrow down the layer

  • Application and configuration
  • Container and workload
  • Scheduling and controllers
  • Service, DNS, Ingress, and CNI networking
  • Storage and CSI
  • Node, operating system, and cloud infrastructure

Resolve and verify

  • Prefer the smallest safe and reversible change.
  • Verify both technical recovery and the end-user path.
  • Document the root cause, impact, resolution, and preventive actions.

General answer framework

First, I would confirm the exact symptom and determine the scope of the issue. Then I would collect evidence from status, events, logs, and metrics. Based on the failure stage, I would narrow the problem down to the application, Kubernetes resources, networking, storage, or the node. I would make the smallest safe change, verify recovery from the user’s perspective, and document the root cause and follow-up actions.

Kubernetes troubleshooting questions

Container

ImagePullBackOff

Question

A Pod is in ImagePullBackOff. What would you check?

What to check

  • Read the exact image pull error from the events.
  • Verify the image repository, name, and tag.
  • Check image pull secrets, registry permissions, and credential validity.
  • Check DNS, network access, proxy configuration, and image architecture from the node.

Answer starter

I would inspect the events to get the exact image pull error. Then I would verify the image name and tag, registry credentials, network access, DNS resolution, and image architecture.

CrashLoopBackOff

Question

A container keeps restarting with CrashLoopBackOff. How would you investigate it?

What to check

  • Inspect both the current logs and the logs from the previous container instance.
  • Check the exit code, last state, termination reason, and restart count.
  • Verify the startup command, environment variables, ConfigMaps, Secrets, volume mounts, and dependencies.
  • Distinguish an application crash, OOM kill, liveness probe failure, and permission problem.

Answer starter

I would inspect the current and previous container logs, the exit code, and the last termination reason. Then I would check the startup command, configuration, dependencies, resource limits, and liveness probe.

Container OOM Killed

Question

A container was OOM Killed. What would you do?

What to check

  • Confirm the last termination reason, exit code, and memory limit.
  • Review memory usage trends, working set, and node memory pressure.
  • Distinguish a memory leak, traffic spike, cache growth, and an unrealistic limit.
  • Fix the application or adjust requests and limits based on evidence, then run a load validation.

Answer starter

I would confirm the OOMKilled termination reason and compare memory usage with the configured limit. Then I would determine whether the cause is a memory leak, a traffic spike, or an unrealistic limit before changing the application or its resources.

Pod

Pod stuck in Pending

Question

A Pod has been stuck in the Pending state. How would you troubleshoot it?

What to check

  • Inspect Pod events and the scheduler message first.
  • Check insufficient CPU or memory, taints and tolerations, node selectors, affinity rules, Pod limits per node, and unbound PVCs.
  • Verify node readiness and scheduler health if the events do not explain the issue.

Answer starter

I would inspect the Pod events first because Pending usually indicates a scheduling or resource issue. Then I would check node capacity, scheduling constraints, taints and tolerations, and PVC binding.

Pod Running but not Ready

Question

A Pod is running but never becomes Ready. What would you check?

What to check

  • Inspect the Ready condition and recent readiness probe failures.
  • Verify the probe path, port, protocol, initial delay, timeout, and thresholds.
  • Confirm that the application listens on the expected port and can reach its dependencies.
  • Check application logs, container state, and restart count.

Answer starter

I would check why the Ready condition is false and inspect the readiness probe failures. Then I would verify the application port, startup state, logs, and dependencies.

Deployment

Deployment rollout stuck

Question

A Deployment rollout is stuck. How would you troubleshoot it?

What to check

  • Inspect the rollout status, Deployment conditions, and events.
  • Compare desired, updated, ready, available, and unavailable replicas.
  • Inspect the new ReplicaSet and its Pods.
  • Check images, configuration, probes, resources, quotas, and the rolling update strategy.
  • Verify the rollout and application traffic after the fix, or perform a carefully evaluated rollback.

Answer starter

I would check the rollout status and Deployment conditions, then inspect the new ReplicaSet and Pods. I would identify whether the failure comes from scheduling, startup, health checks, configuration, or the rollout strategy.

Service

Service unreachable

Question

A Service exists, but clients cannot reach the application. How would you troubleshoot it?

What to check

  • Verify that the Service selector matches the Pod labels.
  • Check whether the EndpointSlice contains the correct Ready Pod addresses and ports.
  • Verify the Service port, target port, application listener, and container port.
  • Test from the same Pod, the same node, and another node to narrow the network scope.
  • Check NetworkPolicies, kube-proxy or the equivalent data plane, and the CNI plugin.

Answer starter

I would verify that the Service selector matches the Pod labels and that the EndpointSlice contains Ready backends. Then I would check the ports, application listener, NetworkPolicies, and cluster networking.

Cluster DNS failure

Question

Pods cannot resolve a Service name. How would you investigate it?

What to check

  • Test name resolution from an affected Pod and inspect its resolver configuration.
  • Verify the Service name, namespace, and fully qualified domain name.
  • Check CoreDNS Pods, Service, configuration, and logs.
  • Verify network access and NetworkPolicies between the Pod and the DNS Service.
  • Determine whether the issue affects one Pod, one node, or the entire cluster.

Answer starter

I would test DNS resolution from the affected Pod and inspect its resolver configuration. Then I would check the Service name, namespace, CoreDNS health and logs, and network access to the DNS Service.

Ingress

Ingress returns 502 or 503

Question

An Ingress returns a 502 or 503 response. What would you check?

What to check

  • Confirm that the request reaches the Ingress Controller.
  • Verify the host, path, Service name, and backend port in the Ingress rule.
  • Check whether the backend Service has Ready endpoints.
  • Inspect the Ingress Controller logs and generated route configuration.
  • Verify the backend protocol, TLS configuration, timeouts, and health checks.

Answer starter

I would first confirm that the request reaches the Ingress Controller. Then I would verify the routing rule, backend Service and port, Ready endpoints, controller logs, protocol, and TLS configuration.

Storage

PVC Pending or volume mount failure

Question

A PVC remains Pending, or a volume cannot be mounted. How would you troubleshoot it?

What to check

  • Inspect PVC, Pod, and VolumeAttachment events.
  • Verify the StorageClass, access mode, requested capacity, selector, and binding mode.
  • Check the CSI controller and node plugin status and logs.
  • Check available volumes, topology restrictions, cloud storage quotas, and attach limits.
  • Do not delete a PVC or PV before evaluating the data risk.

Answer starter

I would inspect the PVC and Pod events, then verify the StorageClass, access mode, capacity, binding mode, and available volumes. For mount or attach failures, I would also check the CSI components, topology, and storage provider limits.

Node

Node NotReady

Question

A node becomes NotReady. How would you investigate and reduce the impact?

What to check

  • Inspect node conditions and events for network, disk, memory, PID, or kubelet problems.
  • Check node reachability, kubelet, and the container runtime.
  • Check disk space, inodes, memory pressure, and system logs.
  • Verify network access and certificates between the node and the API server.
  • Evaluate cordoning, draining, or replacing the node while considering PodDisruptionBudgets and stateful workloads.

Answer starter

I would inspect the node conditions and events, then check connectivity, kubelet, the container runtime, resource pressure, and system logs. To reduce impact, I would evaluate cordoning, draining, or replacing the node while protecting workload availability.

Linux troubleshooting questions

SSH connection failure

Question

A client cannot SSH into a Linux server. How would you troubleshoot it?

What to check

  • Identify whether the error is a timeout, connection refused, or permission denied.
  • Verify the hostname, IP address, port, username, and SSH verbose output.
  • For a timeout, check routing, firewalls, security groups, and network ACLs.
  • For connection refused, check the SSH daemon and listening port.
  • For permission denied, check the username, private key, authorized public key, file permissions, and authentication logs.

Answer starter

I would identify the exact error first. A timeout points to the network path or firewall, connection refused points to the SSH daemon or listening port, and permission denied points to authentication or authorization.

High CPU usage

Question

A Linux server has very high CPU usage. How would you investigate it?

What to check

  • Confirm the duration, user impact, load average, and CPU time categories.
  • Identify the processes and threads consuming CPU.
  • Distinguish computation, an infinite loop, traffic growth, repeated retries, and high system time.
  • Correlate the spike with application logs, monitoring, and recent changes.
  • Apply a temporary mitigation if needed, then address the application, configuration, or capacity root cause.

Answer starter

I would confirm the impact and CPU pattern, identify the processes and threads consuming CPU, and correlate the spike with traffic, logs, and recent changes. Then I would mitigate the impact and address the root cause.

Memory pressure and OOM

Question

A Linux server is running out of memory. What would you check?

What to check

  • Inspect available memory, swap, page cache, and memory pressure.
  • Identify the largest memory consumers and review their growth trends.
  • Check kernel logs for OOM killer events.
  • Distinguish a leak, traffic spike, cache growth, and insufficient capacity.
  • Handle restarts, scaling, or traffic reduction carefully and verify service recovery.

Answer starter

I would inspect available memory, swap, memory pressure, and the largest consumers. I would check the kernel logs for OOM events and determine whether the cause is a leak, a spike, cache usage, or insufficient capacity.

Disk full

Question

A server reports that the disk is full. How would you troubleshoot it safely?

What to check

  • Check both disk space and inode usage.
  • Identify the filesystem, directories, and logs that are growing.
  • Look for deleted files that are still held open by processes.
  • Avoid deleting unknown files; prefer log rotation, removal of verified disposable data, or storage expansion.
  • Investigate the growth cause and alerting threshold after recovery.

Answer starter

I would check both disk space and inode usage, then identify which filesystem and directories are growing. I would also look for deleted files that are still open before choosing a safe cleanup or expansion plan.

systemd service fails to start

Question

A systemd service fails to start. What would you check?

What to check

  • Inspect the service status, exit code, and journal logs.
  • Verify the configuration, environment variables, dependencies, user permissions, and port conflicts.
  • Check the executable path, working directory, and required mounts.
  • Restart after the fix and verify both the service and user path.

Answer starter

I would inspect the service status, exit code, and journal logs. Then I would verify the configuration, dependencies, permissions, executable path, and possible port conflicts.

Port unreachable

Question

An application is running, but clients cannot reach its port. How would you troubleshoot it?

What to check

  • Confirm that the process listens on the expected address and port.
  • Test locally, from the same network, and remotely to find the failure boundary.
  • Check the host firewall, security group, routes, and network ACLs.
  • Check whether the application listens only on the loopback address.
  • Inspect proxies, load balancers, and upstream health checks.

Answer starter

I would verify that the process is listening on the expected address and port. Then I would test locally and remotely to narrow the scope before checking firewalls, routes, security rules, and upstream components.

DNS resolution failure

Question

A Linux server cannot resolve a domain name. How would you investigate it?

What to check

  • Confirm that the failure is DNS-specific rather than general network loss.
  • Inspect resolver configuration, DNS servers, and search domains.
  • Query a specific DNS server and compare the result.
  • Check firewall rules, routes, VPNs, proxies, and local caching services.
  • Determine whether the issue affects one domain, one host, or all lookups.

Answer starter

I would confirm that the issue is DNS-specific, inspect the resolver configuration, and query the configured DNS server directly. Then I would check network access, caching, and whether the problem affects one domain or all lookups.

File permission denied

Question

A process receives Permission denied when accessing a file. What would you check?

What to check

  • Identify the process’s effective user and groups.
  • Inspect ownership, permissions, ACLs, and all parent directories.
  • Check SELinux or AppArmor policy.
  • Check read-only mounts, container mappings, and service sandbox restrictions.
  • Do not hide the root cause by assigning unnecessarily broad permissions.

Answer starter

I would identify the effective user and inspect the ownership, permissions, ACLs, and parent directories. If those are correct, I would check mandatory access control and mount or service sandbox restrictions.

High load with moderate CPU

Question

The load average is high, but CPU usage is not. What might cause this?

What to check

  • Remember that load includes runnable tasks and tasks in uninterruptible sleep.
  • Inspect process states, disk and network storage latency, and pressure metrics.
  • Check storage failures, blocked mounts, swap activity, and kernel logs.
  • Interpret load together with CPU, I/O, memory, and process state.

Answer starter

High load with moderate CPU may indicate tasks blocked on I/O rather than CPU saturation. I would inspect process states, disk and storage latency, memory pressure, mounts, and kernel logs.

Practice order

Foundation set

  • Pod stuck in Pending
    • Read Pod events and the scheduler message first.
    • Check CPU and memory requests against node allocatable capacity.
    • Check taints and tolerations, selectors, affinity, topology rules, and unbound PVCs.
    • Confirm that eligible nodes are Ready and the scheduler is healthy.
  • Pod Running but not Ready
    • Read the Ready condition and readiness probe failures.
    • Verify the probe path, port, protocol, timing, and thresholds.
    • Confirm that the application is listening and its required dependencies are available.
    • Check logs, container state, and restart count; remember that readiness removes traffic but does not restart the container.
  • CrashLoopBackOff
    • Check current and previous container logs.
    • Read the exit code, last termination reason, and restart count.
    • Verify the command, environment, ConfigMaps, Secrets, mounts, and dependencies.
    • Distinguish an application crash, OOMKilled, liveness failure, and permission problem.
  • SSH connection failure
    • Classify the error as timeout, connection refused, or permission denied.
    • Verify the hostname, IP, port, username, and verbose SSH output.
    • For a timeout, check routes and firewalls; for refusal, check the listener and SSH daemon.
    • For permission denied, check keys, authorized keys, file permissions, and authentication logs.
  • High CPU usage
    • Confirm the duration, user impact, load average, and CPU time categories.
    • Identify the processes and threads consuming CPU.
    • Correlate the spike with traffic, logs, deployments, and retry behavior.
    • Capture diagnostic evidence before restarting, then mitigate and verify performance.
  • Disk full
    • Check both filesystem space and inode usage.
    • Identify the affected filesystem and the directories or logs growing fastest.
    • Check for deleted files that are still open and for unexpected mount behavior.
    • Clean up only verified disposable data or expand storage, then fix the growth cause and alerting.

Intermediate set

  • Deployment rollout stuck
    • Check rollout status, Deployment conditions, events, and revision history.
    • Compare desired, updated, ready, available, and unavailable replicas.
    • Inspect the new ReplicaSet and classify its Pod failure as scheduling, startup, probe, resource, or configuration related.
    • Fix or carefully roll back, then verify replica health and application traffic.
  • Service unreachable
    • Compare the Service selector with Pod labels.
    • Verify that EndpointSlices contain the expected Ready Pod IPs and ports.
    • Check Service port, target port, named ports, and the application listener.
    • Test from different locations, then inspect NetworkPolicies, kube-proxy or the service data plane, and CNI networking.
  • Cluster DNS failure
    • Reproduce the lookup from an affected Pod and inspect its resolver configuration.
    • Verify the Service name, namespace, search domain, and fully qualified domain name.
    • Check CoreDNS Pods, Service, configuration, logs, and upstream resolvers.
    • Determine whether the issue affects one Pod, one node, or the cluster, and verify network access to DNS.
  • PVC Pending or volume mount failure
    • Read PVC, Pod, VolumeAttachment, and storage events first.
    • Check the StorageClass, capacity, access mode, selector, binding mode, and topology.
    • Inspect CSI controller and node plugin health, storage quotas, and attachment limits.
    • Protect existing data; do not delete a PVC or PV before evaluating reclaim and data-loss risk.
  • Node NotReady
    • Read Node conditions and events for memory, disk, PID, network, or kubelet problems.
    • Check reachability, kubelet, container runtime, resources, system logs, and API server connectivity.
    • Cordon the node to prevent new scheduling and evaluate drain or replacement.
    • Respect PodDisruptionBudgets and stateful workloads, then verify rescheduling and node recovery.
  • Linux memory pressure and OOM
    • Check available memory, swap activity, pressure, and the largest consumers over time.
    • Read kernel logs to confirm the OOM event and identify the selected victim.
    • Distinguish a leak, workload spike, cache growth, and insufficient capacity.
    • Mitigate with a safe restart, scaling, or traffic reduction, then correct the root cause and monitor recurrence.

Advanced set

  • Ingress returns 502 or 503
    • Confirm that the request reaches the correct Ingress Controller.
    • Verify host and path matching, IngressClass, backend Service, and backend port.
    • Check that the Service has Ready EndpointSlice backends and that the application is listening.
    • Inspect controller logs and generated configuration, then verify protocol, TLS, health checks, and timeouts.
  • Container OOMKilled and capacity planning
    • Confirm the termination reason, exit code, memory limit, and whether the event was container- or node-level.
    • Review working-set trends, traffic, deployments, and node memory pressure.
    • Distinguish a leak, temporary peak, cache behavior, and an unrealistic limit.
    • Tune requests and limits from measured usage, load-test the change, and verify scheduling capacity and stability.
  • Port unreachable
    • Identify whether the failure is DNS-related, a timeout, or connection refused.
    • Confirm that the process listens on the expected IP and port, not only on loopback.
    • Test locally and remotely to locate the boundary, then check routes, firewalls, security rules, and proxies.
    • Use packet capture when needed to verify whether requests arrive and responses return.
  • High load with moderate CPU
    • Remember that load includes runnable tasks and tasks in uninterruptible sleep.
    • Inspect process states and identify tasks blocked in D state.
    • Check disk or network-storage latency, queue depth, mounts, swap, and kernel logs.
    • Correlate load with CPU count, I/O, memory pressure, and historical baselines before acting.
  • Incident mitigation, verification, and follow-up
    • Confirm the symptom, scope, severity, timeline, and recent changes.
    • Preserve evidence and choose the smallest safe, reversible mitigation.
    • Verify component health and the complete end-user path, then monitor for recurrence.
    • Document impact, root cause, contributing factors, recovery actions, and preventive ownership.

Self-review checklist

  • Did I confirm the exact symptom and scope first?
  • Did I name the first evidence I would collect?
  • Did I branch based on the error instead of listing random commands?
  • Did I separate temporary mitigation from root-cause resolution?
  • Did I explain how I would verify recovery?
  • Could I deliver the first answer in four to six clear sentences?
