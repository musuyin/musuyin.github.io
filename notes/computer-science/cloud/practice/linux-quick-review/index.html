Linux 基础知识速览

2026-10-20

理解主线

Linux 排障可以按进程、服务、资源、网络、权限与日志组织。每一类工具展示一部分状态，只有把时间、对象和影响范围对应起来，才足以支持故障结论。

This note covers the Linux concepts most useful in operations and troubleshooting interviews. Each major topic includes an interview question, expected knowledge, an explanation, and a sample answer. For detailed scenarios, see Kubernetes and Linux Troubleshooting Question Bank.

Troubleshooting mental model

A Linux investigation can be organized around six areas:

  • Process: Which process or thread is involved, and what state is it in?
  • Service: How is the service started, supervised, restarted, and logged?
  • Resource: Are CPU, memory, disk space, inodes, and I/O capacity sufficient?
  • Network: Are name resolution, routing, ports, connections, and firewall rules correct?
  • Permission: Which identity is performing the operation, and what policy permits or denies it?
  • Logs: What evidence do the kernel, system, and application logs provide?

A reliable answer structure is:

symptom and scope → evidence → hypothesis → safe action → verification

Interview question: What is your general approach to troubleshooting a Linux service?

Key knowledge

  • Scope, timeline, and recent changes
  • Service and process state
  • Logs and resource evidence
  • Dependency and network validation
  • Safe mitigation and end-to-end verification

Explanation

Start from an exact symptom instead of immediately listing commands. Determine whether the failure affects one request, one host, or the whole service. Use status, logs, metrics, and comparisons with a healthy host to find the first failing layer. Separate temporary mitigation from root-cause resolution.

Sample answer

First, I confirm the exact error, start time, and impact scope and ask what changed recently. Then I check the service and process state, correlate system and application logs, and inspect the relevant resources and dependencies. I form a hypothesis from evidence and test it with the least disruptive action. After recovery, I verify the real user path, monitor for recurrence, and document the root cause and prevention work.

Filesystem

Common directories

  • /etc: System and service configuration.
  • /var/log: Traditional log file location.
  • /var/lib: Persistent service state.
  • /run: Runtime data for the current boot.
  • /proc: Virtual filesystem exposing process and kernel state.
  • /sys: Device and kernel object information.
  • /tmp: Temporary files; retention depends on system policy.
  • /home: Home directories for regular users.
  • /root: Home directory for the root user.

Linux presents regular files, directories, devices, sockets, pipes, and symbolic links through the filesystem interface.

  • An absolute path starts with /.
  • A relative path is resolved from the current working directory.
  • A symbolic link stores a reference to another path.
  • A hard link refers to the same inode and cannot cross filesystems.

Disk space and inodes

  • Free bytes do not guarantee that a filesystem can create another file; it can run out of inodes.
  • Deleting a file does not release its space while a process still holds an open file descriptor to it.
  • If a filesystem is not mounted as expected, data may be written into the underlying mount-point directory and fill the root filesystem.
  • Disk capacity, inode capacity, and storage latency are different constraints.

Interview question: A filesystem is full, but you cannot find enough large files. What would you check?

Key knowledge

  • Block usage and inode usage
  • Deleted but open files
  • Mount points and hidden underlying data
  • Sparse files, snapshots, and filesystem reservations
  • Safe cleanup and service impact

Explanation

df reports filesystem allocation, while du walks visible directory entries. Their results can differ when a deleted file remains open, when data is hidden below a mount point, or because of filesystem-specific allocation. Inode exhaustion can also prevent file creation even when bytes remain available.

Sample answer

I first confirm whether the problem is exhausted blocks or exhausted inodes using df -h and df -i. Then I compare filesystem usage with visible directory usage and check for deleted files that are still open, for example with lsof +L1. I also verify the mount table because data written below an unexpected mount can be hidden. I would not blindly delete files; I would identify the owner, release or rotate data safely, and verify both free capacity and application behavior.

Processes and signals

Each process has a PID, parent PID, user identity, environment, open file descriptors, and resource usage.

Common process states:

  • Running or runnable: Executing or waiting for CPU time.
  • Interruptible sleep: Waiting for an event and can be awakened by a signal.
  • Uninterruptible sleep: Usually waiting on I/O and often shown as D state.
  • Stopped: Suspended.
  • Zombie: Exited, but its parent has not collected the exit status.

Important signals:

  • SIGTERM: Requests graceful termination and should normally be tried first.
  • SIGKILL: Forces termination in the kernel; the process cannot catch it or clean up.
  • SIGHUP: Traditionally means terminal disconnection and is often used to request configuration reload.

Before terminating a process, confirm its identity, business impact, and whether systemd or another supervisor will restart it.

Interview question: What is the difference between SIGTERM and SIGKILL?

Key knowledge

  • Catchable graceful shutdown versus forced termination
  • Cleanup, connection draining, and data integrity
  • Supervisor restart behavior
  • Uninterruptible sleep limitations

Explanation

A process can catch SIGTERM and perform cleanup. It cannot catch SIGKILL; the kernel ends it immediately when possible. Even SIGKILL cannot make a task disappear until an uninterruptible kernel operation returns.

Sample answer

I use SIGTERM first because it lets the application stop accepting work, flush data, and release resources. If it does not exit within an appropriate timeout and the impact justifies it, I may use SIGKILL, knowing that cleanup will not run. Before either action, I check whether a supervisor will recreate the process and whether termination could corrupt state. A process in uninterruptible D state may remain until the underlying I/O operation returns, even after SIGKILL.

Interview question: What is a zombie process, and is it consuming CPU or memory?

Key knowledge

  • Child exit status awaiting parent collection
  • Process table entry rather than a running workload
  • Parent process responsibility
  • PID exhaustion risk from large accumulation

Explanation

A zombie has already exited and no longer executes application code. The kernel retains a small process table entry until the parent calls wait() or exits. A few zombies are not normally a resource emergency, but continued accumulation indicates a parent-process bug and can consume PIDs.

Sample answer

A zombie is a child process that has exited but whose parent has not collected its exit status. It does not consume normal CPU or application memory, but it keeps a process table entry and PID. I identify the parent process and investigate why it is not reaping children. Restarting or fixing the parent may be appropriate, but killing the zombie itself is not, because it has already exited.

systemd services

systemd manages services, sockets, timers, mounts, targets, and other units.

Common service unit settings:

  • ExecStart: Start command.
  • User and Group: Runtime identity.
  • Environment and EnvironmentFile: Environment sources.
  • WorkingDirectory: Process working directory.
  • Restart: Restart policy after exit.
  • After: Ordering relationship, not a strong dependency by itself.
  • Requires and Wants: Stronger and weaker dependency relationships.

A useful inspection sequence is status, exit code, journal, unit definition, configuration validation, permissions, dependencies, and port conflicts.

Interview question: A systemd service fails to start. How would you investigate it?

Key knowledge

  • Unit status and recent journal
  • Exit code and failed command
  • Effective unit configuration and overrides
  • User, environment, working directory, dependencies, and ports
  • Configuration validation before restart

Explanation

Interactive shell behavior may differ from systemd because of the runtime user, environment, current directory, resource limits, or security sandbox. Inspect the effective unit rather than only the vendor file, because drop-in overrides may change behavior.

Sample answer

I begin with systemctl status and the unit’s recent journalctl entries to find the exact exit code and failure time. Then I inspect the effective unit and its drop-ins, checking the start command, runtime user, environment, working directory, dependencies, and restart policy. I validate the application’s configuration and check permissions and port conflicts. After a minimal fix, I restart or reload as appropriate and verify both the unit state and the application’s real endpoint.

Users, groups, and permissions

  • UID identifies a user and GID identifies a group.
  • A process’s effective user and group determine most access checks.
  • Root has broad privileges but can still be constrained by SELinux, read-only mounts, namespaces, and Linux capabilities.

Traditional permissions are defined for owner, group, and others:

  • r: Read a file or list directory entries.
  • w: Modify a file or create and delete directory entries.
  • x: Execute a file or traverse a directory.

For directories, execute permission controls traversal. Access to a file therefore depends on every parent directory as well as the file itself.

Additional controls include:

  • ACLs for more granular permissions.
  • SELinux or AppArmor mandatory access control.
  • Capabilities that split root privilege into smaller units.
  • Mount options such as read-only or noexec.
  • umask, which influences default permissions for new objects.

Interview question: How would you troubleshoot Permission denied?

Key knowledge

  • Effective process identity
  • Ownership and mode of every path component
  • ACLs and mandatory access control
  • Mount options and capabilities
  • Evidence before weakening permissions

Explanation

Changing a file to mode 777 is unsafe and may not solve the problem. A denial can come from a parent directory, ACL, SELinux or AppArmor rule, read-only filesystem, missing capability, or the wrong runtime user.

Sample answer

I first identify the exact operation and the process’s effective user and groups. Then I inspect the target and every parent directory for ownership, mode, and ACLs. If traditional permissions allow the operation, I check SELinux or AppArmor denials, mount options, filesystem state, and required capabilities. I make the narrowest permission change possible and retest as the actual service identity rather than granting broad access.

CPU and load average

CPU time commonly includes:

  • user: Time running user-space code.
  • system: Time doing kernel work.
  • idle: Unused CPU time.
  • iowait: CPU idle time while tasks are waiting for I/O.
  • steal: Time a virtual CPU waits for the hypervisor to provide physical CPU.

Load average is the average number of runnable tasks and tasks in uninterruptible sleep over time. It is not a CPU percentage.

  • High load and high CPU can indicate computation, increased traffic, lock contention, or a loop.
  • High load with moderate CPU can indicate storage or network filesystem waits.
  • Interpretation must include CPU count, process state, and historical baseline.

Interview question: Can load average be high while CPU usage is low?

Key knowledge

  • Runnable and uninterruptible tasks
  • CPU core count and queueing
  • I/O wait and D state
  • Point-in-time observation versus historical trend

Explanation

Load includes tasks waiting in uninterruptible sleep, not only tasks waiting for CPU. A slow disk or network filesystem can therefore raise load while CPUs remain partly idle. A load value also has different significance on a two-core and a sixty-four-core system.

Sample answer

Yes. Load average counts runnable tasks and tasks in uninterruptible sleep, so storage or network filesystem delays can produce high load without high CPU utilization. I compare the load with the number of CPUs, review per-CPU usage and run queues, and identify tasks in D state. Then I correlate that evidence with disk latency, queue depth, and kernel or storage logs before concluding that the system is CPU-bound.

Interview question: One process uses high CPU. What would you do?

Key knowledge

  • Process and thread-level CPU usage
  • Expected workload and recent changes
  • User time versus system time
  • Profiling or stack evidence
  • Mitigation without destroying evidence

Explanation

High CPU can be legitimate demand or a defect. Identify whether one thread, many workers, kernel activity, or a dependency retry loop is responsible. Compare with traffic, deployments, and normal baselines before restarting the process.

Sample answer

I confirm whether the CPU increase is host-wide or isolated to one process and inspect its threads. I correlate the start time with traffic, deployments, and logs and distinguish user CPU from system CPU. If safe, I capture a profile, stack sample, or runtime diagnostic before restarting so I do not lose the evidence. I mitigate according to impact, then verify latency and throughput and follow up with capacity or code changes.

Memory

Important concepts:

  • Used memory includes application memory and reclaimable caches, so a high used value alone does not prove memory exhaustion.
  • Available memory estimates what the system can still provide without severe swapping.
  • Page cache uses otherwise idle memory to improve I/O and can often be reclaimed.
  • Swap can absorb some pressure, but sustained paging causes latency.
  • Memory pressure, paging rate, application growth, and OOM evidence are more useful than one snapshot.

When memory is critically low, the kernel OOM killer may terminate a process. In a cgroup, a process can be OOM-killed because it reached the cgroup limit even when the host still has available memory.

Interview question: How would you investigate an OOM kill?

Key knowledge

  • Kernel or cgroup OOM evidence
  • Victim process and memory limit
  • Resident memory, working set, and growth trend
  • Leak, traffic peak, cache, or undersized limit
  • Restart behavior and recurrence risk

Explanation

An OOM event must be classified as host-level or cgroup-level. The terminated process may be the selected victim rather than the original source of pressure. Historical metrics and workload changes help distinguish a leak from a temporary peak or incorrect capacity setting.

Sample answer

I first confirm the OOM event in kernel, system, or container runtime logs and determine whether it was a host OOM or a cgroup limit violation. I identify the killed process, its configured limit, memory trend, and recent workload or deployment changes. Then I distinguish a leak, a legitimate peak, an oversized cache, and an undersized limit. I may restart or reschedule for immediate recovery, but I also correct the application behavior or capacity and monitor for recurrence.

Storage and I/O

A simplified storage path is:

Block device → Partition or LVM → Filesystem → Mount point → File

Important terms:

  • Block device: Physical or virtual disk-like device.
  • Partition: Region of a block device.
  • LVM: Flexible logical volume management using PVs, VGs, and LVs.
  • Filesystem: Structure such as ext4 or XFS that organizes files and directories.
  • Mount point: Directory where a filesystem appears.
  • Inode: Metadata object that refers to a file’s data blocks.

I/O analysis should include throughput, IOPS, latency, queue depth, utilization, and blocked tasks. Capacity alone is not enough.

Interview question: How would you determine whether a server is suffering from disk I/O problems?

Key knowledge

  • Application latency and blocked tasks
  • Device latency, queue depth, throughput, and utilization
  • Filesystem and kernel errors
  • Local disk versus remote storage
  • Workload source and saturation versus failure

Explanation

A high utilization percentage alone does not prove a problem, especially for modern devices. Latency and queueing must be interpreted against device type and workload. Also determine whether the delay is local, in a storage network, or at a remote filesystem server.

Sample answer

I correlate the application slowdown with host I/O metrics and look for tasks blocked in uninterruptible sleep. I inspect per-device latency, queue depth, throughput, and utilization and review kernel logs for timeouts or filesystem errors. Then I identify which processes are generating I/O and whether the storage is local or remote. I mitigate only after distinguishing expected saturation from a failing path, and I verify both device metrics and application latency afterward.

Networking

A client connection normally follows this path:

Hostname resolution → Route selection → Layer 3 reachability → TCP handshake → TLS or application protocol

Important concepts:

  • Interface: Network device and its state.
  • IP address and prefix: Host address and network range.
  • Route: Decision about where traffic to a destination should go.
  • Default gateway: Route used when no more specific route matches.
  • DNS resolver: Translates hostnames into addresses.
  • Listening socket: Local address and port accepting connections.
  • Established connection: Connection whose handshake has completed.
  • Firewall: Filters traffic by protocol, address, port, state, and other properties.

Common error meanings:

  • Timeout: May indicate routing failure, packet loss, silent firewall drop, overloaded service, or no response.
  • Connection refused: The destination was reachable but nothing accepted the port, or a device actively rejected it.
  • Permission denied: Often indicates that communication reached an authentication or authorization stage.
  • Name or service not known: Usually starts with hostname spelling and resolver configuration.

Ping uses ICMP and cannot by itself prove that a TCP service port is usable.

Interview question: A remote TCP port is unreachable. How would you troubleshoot it?

Key knowledge

  • DNS result and address family
  • Route and interface state
  • Listener address and port
  • Firewall and security policy
  • Packet flow and return path
  • Timeout versus refusal

Explanation

Test from the affected source because network policy and routes can differ by location. Move layer by layer and use the exact error to decide the next branch. A service listening only on 127.0.0.1 is not reachable through the host’s external address.

Sample answer

I reproduce the problem from the affected client and record whether it is a DNS failure, timeout, or refusal. I verify the resolved IP and address family, route selection, and basic reachability. On the server, I check whether the process is listening on the expected address and port and then inspect host and network firewalls. If the path is still unclear, I capture packets on the relevant sides to see whether the SYN arrives and whether the response returns, then verify the application protocol after TCP succeeds.

Interview question: What is the difference between a timeout and connection refused?

Key knowledge

  • Silent absence of response versus active rejection
  • Listener state
  • Firewall behavior
  • Routing and packet loss
  • Need for packet-level confirmation

Explanation

A refusal commonly means the host or an intermediate device actively returned a reset or rejection. A timeout means no useful response arrived before the deadline. Neither message alone proves a single root cause, but each narrows the investigation.

Sample answer

Connection refused usually means the destination is reachable but no process is listening on that address and port, or a firewall is actively rejecting it. A timeout means the response never arrived, which can result from routing, packet loss, a silently dropping firewall, or an overloaded endpoint. I use listener checks, firewall rules, and packet capture to confirm which case applies rather than relying only on the client message.

Interview question: Why is ping not enough to prove that a service is available?

Key knowledge

  • ICMP versus TCP or UDP
  • Different firewall policies
  • Port listener and application health
  • End-to-end protocol validation

Explanation

Ping only tests a form of ICMP reachability. ICMP may be blocked while the service works, or ping may work while the service port is closed. Availability must be tested with the actual transport and application protocol.

Sample answer

Ping tests ICMP reachability, not whether the required TCP port is listening or the application can serve a valid request. Network devices can allow or block ICMP independently of application traffic. I therefore test the actual destination port and then perform a protocol-level check, such as a TLS handshake or HTTP request, from the same source as the affected client.

Logs

Common log sources:

  • systemd journal for service and system events.
  • Kernel log for drivers, devices, networking, OOM, and filesystem events.
  • Application logs for requests, errors, and business context.
  • Audit logs for security and access-control decisions.

Reading principles:

  • Limit the investigation to the failure time window.
  • Read context before and after an error rather than searching only one keyword.
  • Correlate logs with metrics, deployments, and request identifiers.
  • Account for time zones, clock synchronization, rotation, and multiple instances.
  • Remember that an error may be an effect of an upstream failure rather than the root cause.

Interview question: How do you use logs effectively during an incident?

Key knowledge

  • Time window and clock consistency
  • Correlation IDs and instance identity
  • Multi-layer correlation
  • Signal versus repeated secondary errors
  • Preservation of evidence

Explanation

Logs are most useful when tied to a known symptom and timestamp. The same request may appear in a load balancer, application, database, and kernel log, so time and request correlation are important. A flood of identical errors can hide the first causal event.

Sample answer

I start with the user’s failure time and normalize time zones and host clocks. I identify the affected instance and trace a request or correlation ID across system, application, and dependency logs. I read the context around the first error and compare it with metrics and recent changes. I preserve important evidence before rotating, restarting, or making a change that could remove it.

Software and configuration changes

  • Distinguish installed packages, running processes, and currently loaded configuration.
  • Validate syntax or configuration before reloading or restarting a service.
  • Reload usually attempts to apply configuration without recreating the process, while restart creates a new process; exact behavior depends on the service.
  • Investigate recent package upgrades, configuration edits, certificate rotation, and automation changes.

Interview question: What is the difference between reload and restart?

Key knowledge

  • In-process configuration reload versus process replacement
  • Service-specific implementation
  • Connection impact and state preservation
  • Configuration validation and rollback

Explanation

Reload is not universally supported and may not apply every setting. Restart is more complete but can interrupt connections and clear process state. The correct choice depends on documentation, availability design, and the type of change.

Sample answer

A reload asks the existing process to reread supported configuration, usually with less disruption. A restart stops and recreates the process, so it applies startup-only settings but may interrupt traffic or lose in-memory state. I validate the configuration first, confirm what the service supports, prepare a rollback, and verify that the new configuration is actually loaded after the action.

Compact command map

Commands are evidence-collection tools, not a substitute for a troubleshooting method.

  • Service: systemctl status, systemctl cat, journalctl -u
  • Process: ps, top, pidstat, pstree, /proc/<pid>
  • Open files: lsof, /proc/<pid>/fd
  • Filesystem: df -h, df -i, du, findmnt, lsblk
  • Memory: free, vmstat, sar, kernel logs
  • CPU and load: uptime, top, mpstat, pidstat
  • I/O: iostat, iotop, vmstat
  • Sockets: ss, lsof -i
  • Address and route: ip address, ip route, ip link
  • DNS: getent hosts, dig, resolvectl
  • Connectivity: nc, curl, openssl s_client, traceroute or tracepath
  • Packets: tcpdump
  • Permissions: namei -l, getfacl, id, security audit logs

Quick review questions

  • Why can disk space remain allocated after a file is deleted?
  • Why can a process remain after receiving SIGKILL?
  • Why can a command work in an interactive shell but fail under systemd?
  • Why is mode 777 not a proper response to Permission denied?
  • Why can load average be high when CPU usage is moderate?
  • Why can a cgroup OOM occur while the host still has available memory?
  • Why does a successful ping not prove that an HTTPS endpoint works?
  • What evidence would you preserve before restarting a failing process?
