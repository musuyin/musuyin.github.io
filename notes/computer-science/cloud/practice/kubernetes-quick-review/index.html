Kubernetes 基础知识速览

2026-10-20

理解主线

速览把面试问题与控制循环放在一起。复习时先解释 apply 后各组件怎样推进状态，再按对象、资源、网络和存储扩展，保留职责边界比背术语更重要。

This note summarizes core Kubernetes concepts for technical interviews. Each topic includes an interview question, the knowledge an interviewer expects, an explanation, and a sample answer. For scenario-based investigation, see Kubernetes and Linux Troubleshooting Question Bank.

User runs kubectl apply
          ↓
kube-apiserver authenticates and validates request
          ↓
Object state is stored in etcd
          ↓

          ↓

          ↓

          ↓

          ↓

          ↓

          ↓

          ↓

          ↓
Kubelet runs health probes and reports status
          ↓
EndpointSlice controller adds the Pod as a Ready endpoint
          ↓
Service data plane can forward traffic to the Pod

Mental model

Kubernetes is a declarative system. A user submits a desired state through the API, and controllers continuously compare that desired state with the observed state and reconcile any difference.

Common ownership chain:

Deployment → ReplicaSet → Pod → Container

Common traffic path:

Client → Ingress Controller → Service → EndpointSlice → Ready Pod

Common persistent storage path:

Pod → PVC → PV → Storage Provider

Common scheduling flow:

Pod requirements → Scheduler filtering and scoring → Node

Interview question: How does Kubernetes maintain the desired state?

Key knowledge

  • API server and persistent cluster state
  • Declarative spec and observed status
  • Controllers and reconciliation loops
  • Idempotent operations and eventual convergence

Explanation

A Kubernetes object declares the desired state in spec. Controllers watch relevant objects, compare the desired state with the actual state, and take corrective action. Components report observations through status, conditions, and events. Reconciliation is continuous, so Kubernetes can recover from drift after a process crash, node failure, or manual change.

Sample answer

Kubernetes uses a declarative control model. I submit the desired state through the API, for example a Deployment with three replicas. The Deployment and ReplicaSet controllers continuously compare that state with the observed state and create or remove Pods as needed. The scheduler assigns unscheduled Pods to suitable nodes, while kubelet makes sure the containers run there. This reconciliation loop drives the system toward the desired state and corrects later drift.

Kubernetes object structure

Most Kubernetes objects contain these top-level fields:

  • apiVersion: API group and version of the object.
  • kind: Object type, such as Pod, Deployment, or Service.
  • metadata: Name, namespace, labels, annotations, owner references, and other metadata.
  • spec: Desired state declared by the user.
  • status: Observed state reported by Kubernetes components.

Important metadata fields:

  • name: Object name within its scope.
  • namespace: Logical scope for a namespaced object.
  • labels: Key-value pairs used to identify, group, and select objects.
  • annotations: Non-selecting metadata used by tools and controllers.
  • ownerReferences: Ownership information used for lifecycle management and garbage collection.
  • finalizers: Cleanup requirements that must be completed before deletion finishes.

Interview question: What is the difference between spec, status, labels, and annotations?

Key knowledge

  • Desired state versus observed state
  • Selection and grouping
  • Operational metadata
  • Controller ownership of status

Explanation

Users normally define spec, while controllers and other Kubernetes components update status. Labels are designed for selection and grouping, so Services and controllers can use them in selectors. Annotations hold additional non-identifying information and cannot replace labels in selector matching.

Sample answer

The spec describes what I want, while status describes what Kubernetes currently observes. Labels are identifying metadata used by selectors, grouping, and routing. Annotations contain extra information for tools or controllers but are not used for selector matching. When troubleshooting, I compare spec with status, conditions, and events to understand why the object has not reached its desired state.

Pod and container

A Pod is the smallest deployable and schedulable Kubernetes unit. Containers in the same Pod share a network namespace, can communicate through localhost, and can share declared volumes. A Pod should usually represent one application instance, possibly with tightly coupled sidecar or helper containers.

Common Pod fields:

  • containers: Main application containers.
  • initContainers: Containers that run sequentially and complete before the main containers start.
  • volumes: Storage made available to containers in the Pod.
  • restartPolicy: Always, OnFailure, or Never.
  • serviceAccountName: Kubernetes identity used by the Pod.
  • nodeSelector and affinity: Placement constraints and preferences.
  • tolerations: Permission to schedule onto nodes with matching taints.
  • topologySpreadConstraints: Distribution across zones, nodes, or other topology domains.
  • securityContext: Pod-level security settings.
  • imagePullSecrets: Credentials for private registries.
  • terminationGracePeriodSeconds: Time allowed for graceful termination.

Common container fields:

  • image, command, and args
  • env and envFrom
  • resources.requests and resources.limits
  • volumeMounts
  • readinessProbe, livenessProbe, and startupProbe
  • securityContext

Important Pod status fields:

  • phase: Pending, Running, Succeeded, Failed, or Unknown.
  • conditions: Common examples include PodScheduled, Initialized, ContainersReady, and Ready.
  • containerStatuses: Current state, previous state, readiness, restart count, and image information.
  • podIP and hostIP: Pod and node addresses.

Interview question: Why is a Pod, rather than a container, the smallest scheduling unit?

Key knowledge

  • Shared lifecycle and scheduling
  • Shared network namespace
  • Shared volumes
  • Sidecar pattern and tightly coupled containers

Explanation

Kubernetes schedules the whole Pod to one node. All containers in that Pod therefore share placement and lifecycle boundaries. They also share the Pod IP and can use shared volumes, which supports tightly coupled helper patterns. Independently scalable services should normally be placed in separate Pods.

Sample answer

Kubernetes schedules Pods rather than individual containers because a Pod defines a shared execution context. Its containers run on the same node, share one network namespace and Pod IP, and can share volumes. This is useful for a main container and a tightly coupled sidecar. If two components need independent scaling or failure isolation, I would put them in separate Pods.

Resource requests and limits

  • CPU and memory requests are used by the scheduler to find a node with enough allocatable resources.
  • CPU limits are normally enforced through throttling.
  • Exceeding a memory limit can cause the container to be terminated with OOMKilled.
  • Requests that are too high can leave Pods Pending.
  • Requests that are too low can cause overcommitment, contention, and unstable performance.
  • Requests and limits also influence the Pod’s Quality of Service class.

Interview question: What is the difference between requests and limits?

Key knowledge

  • Scheduling versus runtime enforcement
  • CPU throttling versus memory OOM termination
  • Capacity planning and Quality of Service
  • Measurement-based tuning

Explanation

A request is the amount considered during scheduling and represents the baseline capacity reserved for placement. A limit is a runtime boundary. CPU is compressible, so excessive CPU use is throttled. Memory is not safely compressible, so exceeding the memory limit can terminate the container.

Sample answer

Requests influence scheduling because the scheduler compares them with node allocatable capacity. Limits control runtime consumption. A container that reaches its CPU limit is usually throttled, while a container that exceeds its memory limit can be OOM-killed. I set requests from normal observed usage and limits from tested peak behavior, rather than choosing arbitrary values.

Health probes

  • Readiness probe: Determines whether a container should receive Service traffic.
  • Liveness probe: Determines whether kubelet should restart the container.
  • Startup probe: Protects slow-starting applications by disabling readiness and liveness checks until startup succeeds.

A failed readiness probe normally removes the Pod from Ready Service endpoints without restarting it. A failed liveness probe causes a restart according to the Pod restart policy.

Interview question: How do readiness, liveness, and startup probes differ?

Key knowledge

  • Traffic control versus process recovery
  • Slow startup protection
  • Probe configuration risks
  • Dependency-aware health design

Explanation

Readiness answers whether the application can serve traffic now. Liveness answers whether restarting the container is likely to recover it. Startup gives an application enough time to initialize before the other probes take effect. Poorly designed liveness probes can create restart loops during temporary dependency failures.

Sample answer

Readiness controls traffic, liveness controls restarts, and startup protects slow initialization. If readiness fails, the Pod remains running but is removed from Ready endpoints. If liveness repeatedly fails, kubelet restarts the container. I keep liveness focused on unrecoverable process health and avoid making it depend on every external service, because that can turn a dependency outage into a restart storm.

Workload controllers

Deployment and ReplicaSet

A Deployment commonly manages stateless applications and creates ReplicaSets, which maintain the required number of matching Pods.

Important Deployment fields:

  • replicas
  • selector and Pod template labels
  • template
  • strategy: RollingUpdate or Recreate
  • maxUnavailable and maxSurge
  • minReadySeconds
  • progressDeadlineSeconds

Important status values include desired, updated, ready, available, and unavailable replicas, together with conditions.

StatefulSet

A StatefulSet supports workloads that need stable identities, stable network names, ordered operations, or per-Pod persistent volume claims.

Important fields include:

  • serviceName for stable network identity through a headless Service
  • volumeClaimTemplates for per-Pod PVCs
  • podManagementPolicy
  • updateStrategy
  • persistentVolumeClaimRetentionPolicy

A StatefulSet does not implement database replication, leader election, consistency, or backup. The application or an Operator must provide those capabilities.

DaemonSet

A DaemonSet ensures that every eligible node, or every node in a selected group, runs a Pod. Typical uses include logging, monitoring, networking, and storage agents.

Job and CronJob

  • A Job runs a task to successful completion.
  • A CronJob creates Jobs on a schedule.
  • Job fields include completions, parallelism, backoffLimit, and activeDeadlineSeconds.
  • CronJob fields include schedule, concurrencyPolicy, startingDeadlineSeconds, and jobTemplate.

Interview question: When would you use Deployment, StatefulSet, DaemonSet, and Job?

Key knowledge

  • Stateless replicated services
  • Stable identity and storage
  • One Pod per eligible node
  • Finite batch work

Explanation

The controller should match the workload’s lifecycle and identity requirements. A Deployment replaces interchangeable replicas. A StatefulSet preserves ordinal identity and supports stable storage. A DaemonSet follows the node population. A Job tracks completion rather than continuous availability.

Sample answer

I use a Deployment for interchangeable stateless replicas, such as an API service. I use a StatefulSet when each replica needs a stable name or its own persistent volume. A DaemonSet is appropriate for a node-level agent that should run on every eligible node. A Job is for finite work that must complete successfully, and a CronJob schedules that work repeatedly.

Nodes and scheduling

A Node represents a physical or virtual worker machine.

Important Node information:

  • metadata.labels: Role, zone, instance type, or custom placement labels.
  • spec.taints: Repel Pods without matching tolerations.
  • spec.unschedulable: Indicates that the node is cordoned.
  • status.capacity: Total resources.
  • status.allocatable: Resources available to Pods after system reservations.
  • status.conditions: Ready, MemoryPressure, DiskPressure, PIDPressure, and NetworkUnavailable.
  • status.nodeInfo: Operating system, kernel, kubelet, and container runtime details.

Scheduling concepts:

  • Node selector: Exact label matching.
  • Node affinity: Expressive required rules and preferred placement.
  • Pod affinity: Places Pods near selected Pods.
  • Pod anti-affinity: Spreads Pods apart to reduce correlated failure.
  • Taint: Repels Pods from a node.
  • Toleration: Allows, but does not require, a Pod to use a matching tainted node.
  • Topology spread: Balances replicas across topology domains.

Memory aid: selector selects, affinity attracts, taint repels, and toleration permits.

Interview question: How does Kubernetes decide where to place a Pod?

Key knowledge

  • Scheduler filtering and scoring
  • Requests versus allocatable capacity
  • Hard constraints and soft preferences
  • Taints, tolerations, affinity, and topology

Explanation

The scheduler first filters out nodes that cannot satisfy resource requests or hard constraints. It then scores the feasible nodes based on configured priorities and preferences. After binding, kubelet on the selected node starts the Pod. A toleration only makes a tainted node eligible; it does not force placement there.

Sample answer

The scheduler first filters nodes using resource requests and hard constraints such as node affinity, volume topology, and taints. It then scores the feasible nodes using preferences, spreading, and other priorities, and binds the Pod to the best candidate. Kubelet on that node creates the containers. If a Pod stays Pending, I start with scheduler events because they normally explain which constraint could not be satisfied.

Namespace and multi-tenancy controls

A namespace provides logical scope for namespaced resources. It is useful for organizing teams, environments, or applications, but it is not a complete security boundary by itself.

Common complementary controls:

  • ResourceQuota: Limits aggregate resource usage or object counts in a namespace.
  • LimitRange: Defines defaults, minimums, and maximums for containers or PVCs.
  • RBAC: Controls API permissions for users and ServiceAccounts.
  • NetworkPolicy: Controls allowed Pod ingress and egress traffic.

Nodes, PersistentVolumes, StorageClasses, and Namespaces are cluster-scoped resources.

Interview question: Does a namespace provide security isolation?

Key knowledge

  • Logical scope rather than complete isolation
  • RBAC, quotas, and NetworkPolicies
  • Namespaced and cluster-scoped resources
  • Shared cluster components and nodes

Explanation

A namespace separates names and creates a scope for policies, but workloads may still share nodes, networking infrastructure, and cluster-level components. Stronger tenant isolation requires layered controls and sometimes separate clusters.

Sample answer

A namespace provides logical isolation and a policy scope, but it is not a complete security boundary. I combine it with RBAC for API access, ResourceQuota and LimitRange for resource governance, and NetworkPolicy for traffic isolation. I also apply Pod security controls and protect cluster-scoped resources. For tenants with strict trust or compliance boundaries, separate clusters may be more appropriate.

Service and EndpointSlice

A Service provides a stable virtual endpoint for a changing set of Pods. It normally selects Pods by labels, and Kubernetes maintains EndpointSlices containing the actual backend addresses and readiness information.

Important Service fields:

  • type: ClusterIP, NodePort, LoadBalancer, or ExternalName.
  • selector: Selects backend Pods.
  • ports[].port: Port exposed by the Service.
  • ports[].targetPort: Backend port or named port.
  • ports[].nodePort: Node port when applicable.
  • clusterIP: Virtual IP; None creates a headless Service.
  • externalTrafficPolicy: Cluster or Local handling for external traffic.
  • sessionAffinity: Optional client affinity.

A Service with no Ready EndpointSlice backends cannot normally forward traffic to the application. Common causes are mismatched selectors, non-Ready Pods, or incorrect ports.

Interview question: How does a Service route traffic to Pods?

Key knowledge

  • Label selectors
  • EndpointSlice backend discovery
  • Stable virtual IP and data plane
  • Readiness and port mapping

Explanation

The Service selector identifies candidate Pods. EndpointSlice controllers publish their addresses, ports, and readiness state. The cluster data plane, implemented by kube-proxy or another networking component, forwards Service traffic to eligible endpoints.

Sample answer

A Service gives clients a stable name and virtual IP even though Pod IPs change. Its selector matches Pod labels, and the EndpointSlice objects record the actual Ready backend addresses and ports. The cluster networking data plane forwards traffic from the Service to those endpoints. If a Service is unreachable, I first compare its selector with Pod labels and verify that the EndpointSlices contain the expected Ready Pods.

Ingress

Ingress defines HTTP and HTTPS Layer 7 routing rules, but an Ingress Controller must implement them.

Important fields:

  • ingressClassName
  • rules[].host
  • rules[].http.paths[].path and pathType
  • Backend Service name and port
  • tls hostname and certificate Secret
  • defaultBackend

Interview question: What is the difference between Ingress and a Service?

Key knowledge

  • Layer 4 service exposure versus Layer 7 HTTP routing
  • Ingress resource versus Ingress Controller
  • Host, path, TLS, and backend mapping
  • End-to-end request path

Explanation

A Service provides stable access to a set of backends, usually inside the cluster, and may expose them externally depending on its type. Ingress defines HTTP routing rules across Services. The resource itself does not process traffic; the controller does.

Sample answer

A Service provides a stable endpoint and forwards traffic to Pod endpoints, mainly at Layer 4. Ingress adds Layer 7 HTTP or HTTPS routing by host and path and can terminate TLS. An Ingress object is only configuration, so an Ingress Controller must read it and handle the traffic. For a 502 or 503, I trace the path from the controller to the Service, EndpointSlice, and Ready Pod.

ConfigMap and Secret

  • ConfigMap stores non-sensitive configuration.
  • Secret stores sensitive values, but base64 encoding is not encryption.
  • Both can be exposed through environment variables or mounted volumes.
  • Environment variable updates do not modify an already running process; Pods normally need replacement.
  • Mounted projections may update eventually, but the application must reread the file.
  • Secret protection should include encryption at rest, least-privilege RBAC, and possibly an external secret manager.

Interview question: How do you manage application configuration and secrets in Kubernetes?

Key knowledge

  • Separation of image and environment-specific configuration
  • Environment variables versus mounted files
  • Secret security limitations
  • Rollout and configuration reload behavior

Explanation

ConfigMaps and Secrets decouple configuration from container images. The injection method affects update behavior, and a production design should define how configuration changes trigger safe rollouts. Secrets require protection beyond simply creating a Secret object.

Sample answer

I use ConfigMaps for non-sensitive settings and Secrets for credentials or keys. I grant the workload access only to the values it needs and enable appropriate encryption and audit controls. I also define how updates reach the application: environment variables usually require a Pod rollout, while mounted files may update but still require the application to reload them. I avoid storing secrets directly in images or Deployment manifests.

Persistent storage

A PersistentVolume is cluster-scoped storage made available to the cluster. A PersistentVolumeClaim is a namespaced request for storage. A StorageClass defines how dynamic provisioning is performed.

Important PV fields:

  • capacity
  • accessModes
  • persistentVolumeReclaimPolicy
  • storageClassName
  • volumeMode
  • nodeAffinity

Important PVC fields:

  • resources.requests.storage
  • accessModes
  • storageClassName
  • volumeMode
  • Optional selector
  • Bound volumeName

Important StorageClass fields:

  • provisioner
  • parameters
  • reclaimPolicy
  • volumeBindingMode
  • allowVolumeExpansion

Interview question: How do PVC, PV, StorageClass, and CSI work together?

Key knowledge

  • Storage request, storage resource, and provisioning policy
  • Static versus dynamic provisioning
  • CSI controller and node components
  • Topology, access mode, binding, attachment, and mounting

Explanation

A Pod references a PVC. The PVC either binds to a suitable existing PV or triggers dynamic provisioning through a StorageClass and CSI driver. The volume may then be attached to a node and mounted into the Pod. WaitForFirstConsumer delays binding so storage topology can follow Pod scheduling.

Sample answer

A PVC expresses a workload’s storage requirement, while a PV represents the actual storage resource. A StorageClass defines how a CSI provisioner should create storage dynamically. After binding, the CSI components handle operations such as provisioning, attachment, and mounting. When a PVC is Pending, I check its events, StorageClass, access mode, capacity, binding mode, topology, and CSI health before changing or deleting anything.

Identity, authorization, and security context

A ServiceAccount is the workload identity a Pod uses when calling the Kubernetes API.

RBAC objects:

  • Role: Permissions within a namespace.
  • ClusterRole: Cluster-wide rule definition, also reusable in a namespace.
  • RoleBinding: Grants a Role or ClusterRole within one namespace.
  • ClusterRoleBinding: Grants a ClusterRole across the cluster.

RBAC rules use apiGroups, resources, optional resourceNames, and verbs.

Common security context fields include runAsUser, runAsGroup, runAsNonRoot, fsGroup, allowPrivilegeEscalation, capabilities, privileged, and readOnlyRootFilesystem.

Interview question: How would you apply least privilege to a Kubernetes workload?

Key knowledge

  • Dedicated ServiceAccount
  • Minimal RBAC verbs and resources
  • Non-root execution and reduced Linux capabilities
  • Read-only filesystem and privilege escalation controls
  • Network and secret access restrictions

Explanation

Least privilege must cover both the Kubernetes API and the container runtime environment. A workload should receive only the API permissions, secrets, filesystem access, Linux capabilities, and network paths that it requires.

Sample answer

I give the workload a dedicated ServiceAccount and bind only the required API verbs and resources, preferably within its namespace. At runtime, I run the container as a non-root user, disable privilege escalation, drop unnecessary capabilities, and use a read-only root filesystem when possible. I also restrict secret access and network traffic. Finally, I validate the effective permissions instead of assuming the manifest is sufficient.

Object inspection order

When examining an object, use this sequence:

  1. Identify its kind, name, namespace, and owner.
  2. Compare labels with selectors.
  3. Read the desired state in spec.
  4. Read status, conditions, and events for observed state and failure evidence.
  5. Follow dependencies and managed objects.
  6. Compare the failing object with a healthy equivalent.

Interview question: What is your general Kubernetes troubleshooting approach?

Key knowledge

  • Symptom and scope before commands
  • Desired state versus observed state
  • Events, logs, metrics, and dependency tracing
  • Smallest safe change and end-to-end verification

Explanation

A structured investigation avoids random command lists. Start from the user-visible failure, locate the first broken layer, and use Kubernetes ownership and traffic relationships to move through the system.

Sample answer

First, I confirm the exact symptom, start time, and impact scope. Then I inspect the relevant object’s spec, status, conditions, and events and compare a failing instance with a healthy one. I trace the ownership or request path through controllers, Pods, Services, networking, storage, and nodes until I find the first failing layer. I make the smallest safe and reversible change, verify the complete user path, and document the root cause and preventive action.

Quick review questions

  • Why can a Pod be Running but not Ready?
  • Why can a Service exist but have no usable endpoints?
  • Why does a toleration not guarantee placement on a tainted node?
  • Why can an application be OOM-killed even when the node still has free memory?
  • Why is a StatefulSet not a complete database high-availability solution?
  • Why does changing a ConfigMap not always update a running application?
  • What evidence distinguishes a scheduling failure from a container startup failure?
  • How would you verify recovery from the end user’s perspective?
