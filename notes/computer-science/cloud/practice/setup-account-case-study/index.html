DBaaS setup-account 多云基础设施实践

2026-08-12

#Cloud#Terraform

理解主线

这个案例展示多云基础设施的职责拆分：模块表达可复用资源，Landscape 组织具体环境，CI/CD 产生受审阅的变更。它与集群内 Helm 应用发布处在不同管理层。

这是 SAP 内部真实使用 Terraform 管理多云账号的项目，是上述所有概念在生产环境的完整体现。

仓库整体职责

setup-account 负责为 SAP HANA Cloud（DBaaS）在各云上创建和维护基础设施账号——包括网络（VPC/子网/防火墙）、IAM 权限、密钥管理（Vault）、DNS（Route53）、容器仓库（ECR）等，但不管理 K8s 集群内的应用（那是 Helm 的职责）。

目录结构——体现 Terraform Module 模式

setup-account/
├── _modules/                  # 可复用 Terraform Module（按云厂商分类）
│   ├── Aws/                   # AWS 专用模块
│   │   ├── hana/              # HANA Cloud 相关资源
│   │   ├── csi/               # CSI（Cloud Service Infrastructure）
│   │   └── _create_aws_key/   # IAM Key 创建模块
│   ├── Azure/                 # Azure 专用模块
│   ├── Gcp/                   # GCP 专用模块
│   └── AliCloud/              # 阿里云模块
│
├── HanaCloud/                 # 具体 Landscape 配置（调用 _modules）
│   ├── Aws/
│   │   ├── Landscapes/        # 每个具体的 AWS 环境（如 hc-ap11、hc-eu10）
│   │   ├── Vault/             # HashiCorp Vault 配置
│   │   ├── Route53/           # DNS 配置
│   │   └── ECR/               # 容器镜像仓库
│   ├── Azure/
│   ├── Gcp/
│   └── AliCloud/
│
├── stencils/                  # Landscape 元数据（账号/凭证/后端配置的单一来源）
│   ├── cca-dev-aws.yaml       # AWS dev 环境的 stencil
│   ├── azure/
│   │   ├── hc-eu20.yaml       # Azure 欧洲生产环境 stencil
│   │   └── ...
│   └── ...
│
├── scripts/                   # 运维脚本（初始化 IAM Key / Service Principal / Vault 密钥）
├── Jenkinsfile                # CI/CD Pipeline（PR → plan，merge → apply）
└── cfg/                       # 全局配置

核心设计：_modules/ 是可复用模板（类比 Helm Chart），HanaCloud/Aws/Landscapes/hc-ap11/ 是具体的 Values（类比 values-prod.yaml），调用模块并传入该 Landscape 的参数。

Stencil：Landscape 的元数据单一来源

Stencil 是什么？

stencils/ 下的每个 YAML 文件描述的是一个 Landscape 的身份信息，不是 Terraform HCL，也不是 Helm values——它是比 Terraform 更底层的一层：告诉所有工具“这个环境长什么样”。

以 stencils/cca-dev-aws.yaml 为例：

hyperscaler: aws
region: eu-central-1
stage: dev
area: hc
vault:
  instance: dev
  project: hc-dev
  secrets_vault_storage_path: cca/aws/dev
accounts:
  cca:
    profile: cca-dev
    id: '895633207865'           # AWS 账号 ID
    credentials:
      vault:
        path: cca/aws/dev/automator  # 凭证在 Vault 中的路径
terraform:
  project_path: HanaCloud/Aws/CCA/cca-dev   # 对应的 Terraform 项目目录
  backend:
    account: cca
    type: s3
    params:
      bucket: terraform-state.895633207865.eu-central-1  # Terraform State 存储位置
      key: terraform.tfstate
      region: eu-central-1

Azure 的 stencil（如 stencils/azure/hc-eu20.yaml）更复杂，还包含：

account:
  orchestration:
    subscription_id: eebe3b6f-...   # 各子账号的 Azure Subscription ID
  hana:
    subscription_id: ea6a9e60-...
  sgw0 ~ sgw26:                    # 每个 SGW 子账号
    subscription_id: ...

service_account:
  gardener:                        # Gardener 专用 Service Principal
    account:
      hana:
        app_id: 64448613-...       # 各账号下的 Azure App ID
  automator:
    ...
  deployment:
    ...

Stencil 解决的核心问题：

同一个 Landscape 的账号信息会被多个工具引用——Terraform 需要知道用哪个账号、State 存哪里；scripts/ 里的 Python 脚本需要知道要创建哪些 Service Principal 并把密钥存到 Vault 的哪个路径。如果每个工具各自维护一份，很容易不一致。

Stencil 把这些信息集中在一个 YAML 里，充当所有工具的共同配置来源：

stencil.yaml（单一来源）
    │
    ├──→ Terraform Pipeline（读取 project_path、backend config）
    │        → 知道去哪个账号、State 存哪
    │
    ├──→ scripts/create_azure_key.py（读取 account、service_account）
    │        → 知道要为哪些账号创建 App Registration，密钥存 Vault 哪条路径
    │
    └──→ scripts/create_aws_key.py（读取 accounts.cca.id）
             → 知道要在哪个 AWS 账号下创建 IAM Key

与 Terraform Module 的关系：

层次 文件 内容
元数据层 stencils/azure/hc-eu20.yaml 账号 ID、Vault 路径、State 后端
配置层 HanaCloud/Aws/Landscapes/hc-ap11/ Terraform HCL，调用 Module，传参数
模块层 _modules/Aws/hana/ 可复用 Terraform Module

Stencil 不参与 terraform apply 的渲染过程，但它是整个 Pipeline 启动前的准备工作的数据来源——凭证初始化、State 位置配置，都先从 stencil 读取。

CI/CD 流程——GitOps 思想的体现

Jenkinsfile 实现了一套智能 Pipeline，完整体现了 Terraform 的生产实践：

开发者提 PR
    │
    ▼
Jenkins 自动检测变更文件
（只对受影响的 Landscape 运行，不跑全量）
    │
    ▼
PR 阶段：terraform plan（预览，不执行）
→ 结果作为 Comment 发回 PR
    │
    ▼
Code Review + 合并到 master
    │
    ▼
master Pipeline：terraform apply（真正执行变更）
→ 最多 20 个 Landscape 并行执行
→ 结果上传 Sirius（合规审计）
→ 失败发 Slack 告警

智能 Pipeline 选择机制：不是每次 PR 都跑所有 Landscape（那样太慢）。Jenkins 分析变更文件路径，只触发受影响的 Lane（hc / di / monitor / cca 等）和具体 Landscape，大幅缩短 CI 时间。

多云 + 多环境的层次结构

HanaCloud/Aws/Landscapes/
├── hc-ap11/    # AWS 亚太（日本）生产环境
├── hc-eu10/    # AWS 欧洲生产环境
├── hc-us10/    # AWS 美国生产环境
└── hc-dev/     # 开发/测试环境

每个 Landscape 目录下是调用 _modules 的 Terraform 配置，传入该环境的具体参数（region、账号、网络 CIDR、资源规格等）。同一套模块代码，通过不同参数部署到 10+ 个云环境，零代码重复。

与其他工具的分工（在此项目中）

setup-account（Terraform）
    管：AWS/Azure/GCP 账号级基础设施
    → VPC、子网、IAM Role、Security Group
    → Vault（密钥管理）、Route53（DNS）、ECR（镜像仓库）
    → 为 Gardener 创建 Shoot 提供云账号凭证

Gardener（另一套系统）
    管：在上述账号内创建/维护 K8s 集群（Shoot）

Helm（再上一层）
    管：往 K8s 集群内部署 HANA Cloud 的服务

这三层正好对应了 Cloud Native 的完整基础设施栈：账号/网络层 → 集群层 → 应用层。

复习与应用

沿一项账号变更追踪元数据、模块、计划与流水线；指出 Terraform、Vault、DNS 和 Helm 各自管理什么。案例中的内部结构是记录快照，未在本轮连接系统验证。
