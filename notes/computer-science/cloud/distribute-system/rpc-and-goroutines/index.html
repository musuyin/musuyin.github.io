RPC and Threads

2026-05-14

#分布式#RPC#线程

理解主线

RPC 让远端操作形成调用接口，goroutine 让一个进程同时处理多项等待与计算。并发程序必须明确共享状态、同步和失败返回，不能把远端调用理解成本地函数一样可靠。

Why Use Go

  • Good support for threads
  • Convenient RPC
  • Type- and memory-safe
  • Garbage-collected (no use-after-free problems)
  • Threads + GC is particularly attractive
  • Not too complex
  • Widely used in distributed systems

Threads

A thread (“thread of execution”) is a useful structuring tool, though tricky to use correctly. Go calls them goroutines.

  • Threads allow one program to do many things at once
  • Each thread executes serially, just like a non-threaded program
  • Threads share memory
  • Each thread has its own per-thread state: program counter, registers, stack

Why Threads

  • I/O concurrency — while waiting for disk/network for client X, process a request from client Y
    • Client sends requests to many servers in parallel and waits for replies
    • Server processes many simultaneous client requests, each of which may block
  • Multicore performance — execute code in parallel on several cores
  • Convenience — e.g., once per second in the background, check whether each worker is still alive

Event-driven: The Alternative to Threads

Event-driven is an alternative concurrency model that uses a single thread with a single event loop.

The loop:

  1. Waits for any input or event that might trigger processing
  2. Does the next step for each activity
  3. Updates per-activity state (e.g., a table keyed by client request)
Threads Event-driven
I/O concurrency ✓ ✓
Multi-core speedup ✓ ✗
Programming complexity Medium High (explicit interleaving)
Thread overhead Yes No

Threading Challenges

Shared Data Safety

Race condition: two threads access the same memory concurrently, and at least one writes.

Solutions:

  • Use locks: Go’s sync.Mutex
  • Avoid sharing mutable data altogether

Coordination Between Threads

One thread produces data, another consumes it. How does the consumer wait (releasing the CPU), and how does the producer wake it up?

Go primitives:

  • chan — Go channels
  • sync.Cond — condition variable
  • sync.WaitGroup — wait for a group of goroutines to finish

Deadlock

A cycle of threads waiting for each other — can happen via locks, channels, or RPC.

Web Crawler

Goal: given a starting URL, recursively fetch all reachable web pages (a DAG).

Constraints:

  • Don’t fetch a given page more than once
  • Don’t get stuck in cycles

Challenges

  • I/O concurrency: network latency (~0.1s) dominates throughput → fetch many pages in parallel
  • Deduplication: remember which URLs have been visited
  • Termination: know when all pages are fetched

Solution 1: Serial

func Serial(url string, fetcher Fetcher, fetched map[string]bool) {
	if fetched[url] {
		return
	}
	fetched[url] = true
	urls, err := fetcher.Fetch(url)
	if err != nil {
		return
	}
	for _, u := range urls {
		Serial(u, fetcher, fetched)
	}
}
  • Depth-first traversal via recursion
  • fetched map (passed by reference) avoids repeats and breaks cycles
  • Problem: fetches one page at a time — slow

Note: simply adding go before Serial() breaks correctness — when main() exits, spawned goroutines may be killed before finishing.

Solution 2: Concurrent Mutex (Shared State)

type fetchState struct {
	mu      sync.Mutex
	fetched map[string]bool
}

func (fs *fetchState) testAndSet(url string) bool {
	fs.mu.Lock()
	defer fs.mu.Unlock()
	r := fs.fetched[url]
	fs.fetched[url] = true
	return r
}

func ConcurrentMutex(url string, fetcher Fetcher, fs *fetchState) {
	if fs.testAndSet(url) {
		return
	}
	urls, err := fetcher.Fetch(url)
	if err != nil {
		return
	}
	var done sync.WaitGroup
	for _, u := range urls {
		done.Add(1)
		go func(u string) {
			ConcurrentMutex(u, fetcher, fs)
			done.Done()
		}(u)
	}
	done.Wait()
}
  • Spawns a goroutine for each page fetch → many concurrent fetches
  • fs.fetched is shared across goroutines; the mutex protects it

Why the mutex in testAndSet()?

Without it: T1 and T2 both read fetched[url] == false simultaneously (because two different pages link to the same URL), and both proceed to fetch — duplicate fetch.

With the mutex: one thread waits while the other atomically checks-and-sets, so only one sees false.

The code between Lock() and Unlock() is called a critical section. Note: Go does not enforce any relationship between locks and data — it’s the programmer’s responsibility.

WaitGroup: done.Wait() blocks until all Add(1) calls are balanced by Done() calls, i.e., all child goroutines finish.

Detecting Races

go run --race crawler.go

Go’s race detector instruments memory accesses at runtime and reports concurrent unsynchronized accesses — even when the output happens to be correct. It only detects races on the specific execution path that was run, so it may miss races that require a different scheduling.

Solution 3: Concurrent Channels

func worker(url string, ch chan []string, fetcher Fetcher) {
	urls, err := fetcher.Fetch(url)
	if err != nil {
		ch <- []string{}
	} else {
		ch <- urls
	}
}

func coordinator(ch chan []string, fetcher Fetcher) {
	n := 1
	fetched := make(map[string]bool)
	for urls := range ch {
		for _, u := range urls {
			if fetched[u] == false {
				fetched[u] = true
				n += 1
				go worker(u, ch, fetcher)
			}
		}
		n -= 1
		if n == 0 {
			break
		}
	}
}

func ConcurrentChannel(url string, fetcher Fetcher) {
	ch := make(chan []string)
	go func() {
		ch <- []string{url}
	}()
	coordinator(ch, fetcher)
}

Channel basics:

ch := make(chan int)
ch <- x      // sender blocks until a receiver is ready
y := <-ch    // receiver blocks until a sender sends
for y := range ch  // receive until channel is closed
  • A channel both communicates values and synchronizes goroutines
  • Send + receive costs less than a microsecond — fairly cheap
  • Multiple goroutines can send/receive on the same channel safely

How coordinator() works:

  • coordinator creates a worker goroutine for each new URL
  • Each worker sends exactly one []string (the fetched URLs) back on the channel
  • coordinator tracks in-flight workers with counter n; when n == 0, all work is done
  • The fetched map is not shared — only coordinator uses it, so no lock needed

Is there a race between worker writing the URL slice and coordinator reading it?

No — the worker writes the slice before sending, and the coordinator reads it after receiving. The channel send/receive enforces the happens-before relationship.

Why does ConcurrentChannel wrap the first send in a goroutine?

Because ch <- []string{url} would block (unbuffered channel) until coordinator is ready to receive. Without the goroutine, it would deadlock.

Shared State vs. Channels

Scenario Preferred approach
Protecting shared state sync.Mutex / sync.Cond
Communicating between goroutines Channels

Most problems can be solved either way — choose based on how you think about the problem. For the 6.824 labs, sync.Mutex / sync.Cond is recommended for shared state.

Remote Procedure Call (RPC)

RPC is a key mechanism in distributed systems. The goal: make client/server communication as easy as a local function call.

RPC handles:

  • Hiding network protocol details
  • Marshalling: converting data (strings, arrays, maps, etc.) into wire format
  • Portability and interoperability

Message Flow

Client              Server
  |  --- request --> |
  |  <-- response -- |

Software layers:

client app         handler fns
stub fns           dispatcher
RPC lib            RPC lib
net -------------- net

Go RPC Example (key/value store)

A toy key/value server supporting Put(key, value) and Get(key) → value.

Common: declare Args and Reply structs for each handler.

Client side:

  • Dial() creates a TCP connection to the server
  • get() / put() are client stubs
  • Call() asks the RPC library to perform the call — marshalls args, sends request, waits, unmarshalls reply
  • Return value of Call() indicates whether a reply was received; reply.Err indicates service-level failure

Server side:

  • Declare an object with methods as RPC handlers, register it with the RPC library
  • Server accepts TCP connections and hands them to the RPC library
  • For each request, the RPC library:
    1. Creates a new goroutine
    2. Unmarshalls the request
    3. Looks up the named object (via Register())
    4. Calls the named method (dispatch)
    5. Marshalls the reply and writes it back

The Get() and Put() handlers must lock, because the RPC library creates a new goroutine per request.

Marshalling Details

  • Go RPC can pass strings, arrays, objects, maps, etc.
  • Pointers are passed by copying the pointed-to data
  • Cannot pass channels or functions
  • Only exported fields (capitalized) are marshalled

RPC Failure Handling

What failures look like to the client: Call() never gets a response. The client cannot tell:

  • Whether the server received the request at all
  • Whether the server executed and crashed before replying
  • Whether the reply was lost in transit

This is a fundamental difference from local procedure calls.

Failure Semantics

Best-effort RPC:

  • Call() waits for a response; if none arrives, re-sends a few times, then returns an error
  • Simple, but dangerous for non-idempotent operations

Bad scenario: two Put("k", 10) / Put("k", 20) calls, a timeout on the first, re-send — server may execute Put("k", 10) twice. Get("k") could yield 10 instead of 20.

Best-effort is acceptable only for read-only or idempotent operations (e.g., DB checks whether a record already exists).

At-most-once RPC (Go’s default):

  • Uses a single TCP connection; never re-sends a request
  • Server won’t see duplicate requests
  • If no reply arrives (timeout, server crash, network failure), Call() returns an error
  • Drawback: too restrictive for replicated servers — ideally, retry at another replica if the first fails
