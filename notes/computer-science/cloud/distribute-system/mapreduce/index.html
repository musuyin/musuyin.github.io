MapReduce

2026-05-06

#分布式#MIT6824#MapReduce

理解主线

MapReduce 将计算分为 Map 生成中间键值、按键分组与 Reduce 聚合。框架负责任务分配、数据路由与失败重试，用户函数则需符合输入输出契约。

Introduction

MapReduce is a programming model for processing and generating large data sets. The computations can be distributed across multiple machines.

Analogy: Think of a library doing a word count across thousands of books. MapReduce is like hiring many workers (Map) to each count words in one book, then having a smaller team (Reduce) tally the totals across all books — automatically parallelized and fault-tolerant.

Programming Model

Two computations:

  • Takes a set of input key/value pairs
  • Produces a set of output key/value pairs

The MapReduce library expresses the computations as Map and Reduce:

  • Map: takes an input pair and produces a set of intermediate key/value pairs
  • MapReduce groups all intermediate values together with the same intermediate key and passes them to the Reduce function
  • Reduce: accepts an intermediate key and a set of values for that key. Merges together the values to form a possibly smaller set of values
map(k1, v1)        -> list(k2, v2)
reduce(k2, list(v2)) -> list(v2)

Examples

Application Map Reduce
Count words Emits each word plus an associated count of occurrences Sums together all counts emitted for a particular word
Distributed grep Emits a line if it matches a supplied pattern Copies the supplied intermediate data to the output
Count of URL access frequency Processes logs of web page requests and outputs <URL, 1> Adds together all values for the same URL and emits <URL, total count>
Reverse Web-Link graph Outputs <target, source> pairs for each link to a target URL found in a page named source Concatenates the list of all source URLs associated with a given target URL and emits the pair <target, list(source)>
Distributed sort Extracts the key from each record, and emits a <key, record> pair Emits all pairs unchanged

Implementation

Execution

  • Map invocations are distributed across multiple machines by automatically partitioning the input data into a set of MMM splits
    • The input splits can be processed in parallel by different machines
  • Reduce invocations are distributed by partitioning the intermediate key space into RRR pieces using a partitioning function
    • e.g., hash(key) % R

The execution proceeds in 7 steps:

  1. Split: Divide input files into MMM pieces (typically 16 MB to 64 MB per piece). Start up many copies of the program on a cluster of machines.
  2. Assign: One copy becomes the master; the rest are workers. Master picks idle workers and assigns map or reduce tasks. (Total: MMM map tasks and RRR reduce tasks.)
  3. Map: Each Map worker reads its input split, parses key/value pairs, passes them to the user Map function, and buffers the intermediate key/value pairs in memory.
  4. Spill to disk: Buffered pairs are periodically written to local disk, partitioned into RRR regions by the partitioning function. The locations are reported back to the master, which forwards them to reduce workers.
  5. Shuffle & Sort: Each Reduce worker uses remote procedure calls (RPC) to fetch intermediate data from Map workers’ local disks. Once all data is fetched, it sorts by key so that the same key is grouped together.
  6. Reduce: The Reduce worker iterates over the sorted data. For each unique key, it passes the key and its list of values to the Reduce function. Output is appended to a final output file for this partition.
  7. Complete: When all tasks finish, the master wakes up the user program. The MapReduce call returns to user code.

The output is available in RRR output files. These are often piped as input to another MapReduce call or another distributed application — no need to merge them into a single file.

Master Data Structures

The master stores two things for each map/reduce task:

  • State: idle, in-progress, or completed
  • Worker identity: which machine is running it (for non-idle tasks)

The master is the conduit for propagating intermediate file locations from Map tasks to Reduce tasks:

  • Stores the locations and sizes of the RRR intermediate file regions produced by each map task
  • Receives location updates as map tasks complete
  • Pushes this information incrementally to in-progress reduce workers

Fault Tolerance

MapReduce is resilient to large-scale worker failures.

Worker Failure

The master pings every worker periodically.

  • If no response within a timeout, the master marks the worker as failed

Task re-execution rules:

  • Completed map tasks are re-executed — their output is on the failed machine’s local disk, now inaccessible
  • In-progress map or reduce tasks are re-executed — they never finished
  • Completed reduce tasks are NOT re-executed — their output is in the global file system (e.g., GFS)

When a map task is re-executed (e.g., worker A fails, worker B re-runs it), all Reduce workers are notified. Any Reduce worker that hasn’t yet read from A will now read from B.

Master Failure

The master writes periodic checkpoints of its data structures. A new master can resume from the last checkpoint.

Current limitation: only one master exists. If it fails, the entire MapReduce computation is aborted. Clients must check for this condition and retry.

Semantics in the Presence of Failures

When Map and Reduce operators are deterministic, the distributed output is identical to a non-faulting sequential execution.

This guarantee is achieved via atomic commits. Each in-progress task writes to private temporary files:

  • A Map task produces RRR temporary files.
    • On completion, sends the RRR filenames to the master.
    • If the master already received this message (duplicate), it ignores it.
    • Otherwise, it records the filenames.
  • A Reduce task produces one temporary file.
    • On completion, atomically renames it to the final output file.
    • If multiple executions race, the filesystem’s atomic rename ensures only one execution’s data survives.

Locality

GFS stores each input data block with multiple replicas across the cluster. The master exploits this by scheduling each map task on a machine that already holds a replica of its input, so workers read from local disk rather than the network.

This optimization reduces network bandwidth during the Map phase. However, the Reduce phase always requires remote reads, since intermediate data must be fetched from Map workers scattered across the cluster.

Task Granularity

MMM and RRR should be much larger than the number of worker machines:

  • Improves dynamic load balancing — idle workers can quickly pick up remaining tasks
  • Speeds up recovery — a failed worker’s tasks are spread across many machines

Practical bounds on MMM and RRR:

Resource Cost
Scheduling O(M+R)O(M + R)O(M+R) decisions
Master memory O(M×R)O(M \times R)O(M×R) state

In practice:

  • RRR is constrained by the user (determines the number of output files)
  • MMM is chosen so each task processes 16 MB to 64 MB of input data

Backup Tasks

A straggler — a machine that takes unusually long to finish — can delay the entire job.

Why stragglers occur: a bad disk, CPU contention from other processes, or a machine stuck in error-recovery mode can all cause one worker to run 10× slower than its peers.

When a MapReduce operation is close to completion, the master schedules backup executions of all remaining in-progress tasks. The task is marked complete when either the primary or backup execution finishes. This typically adds only a few percent to the total resource usage but can cut end-to-end latency significantly.

Refinements

Partitioning Function

Users specify RRR (the number of reduce tasks). Intermediate data is partitioned across reduce tasks using a partitioning function on the key.

  • Default: hash(key) mod R — generally well-balanced
  • Custom: e.g., hash(Hostname(urlkey)) mod R — groups all URLs from the same host into one output file

Ordering Guarantees

Within a given partition, intermediate key/value pairs are processed in increasing key order, making it easy to generate a sorted output file per partition.

Combiner Function

An optional function that performs partial merging of intermediate data on the Map worker before sending it over the network. This reduces shuffle traffic.

  • Typically uses the same code as the Reduce function
  • Key difference: Combiner output goes to an intermediate file (forwarded to Reduce tasks); Reduce output goes to the final output file

Example: In word counting, instead of shipping <the, 1> a hundred times, the Combiner locally sums them to <the, 100> — 100× less data over the network.

Input and Output Types

The library supports multiple input formats:

  • “text” mode: each line is a key/value pair (key = byte offset, value = line contents)
  • Custom types: implement a simple reader interface
  • Output types are similarly extensible

Side-effects

Map/Reduce operators can produce auxiliary output files as additional side-effects.

  • Writers must make side-effects atomic and idempotent — write to a temp file, then atomically rename it
  • No cross-file atomic two-phase commits — tasks producing multiple output files with cross-file consistency requirements must be deterministic

Skipping Bad Records

User code bugs can cause Map/Reduce to crash deterministically on certain records.

  • Each worker installs a signal handler to catch segmentation faults and bus errors
  • On crash, the worker sends the sequence number of the offending record to the master via UDP
  • If the master sees more than one failure on the same record, it marks that record to be skipped on the next re-execution

Local Execution

A sequential local implementation runs all MapReduce work on a single machine.

  • Facilitates debugging, profiling, and small-scale testing
  • Compatible with standard debuggers (e.g., gdb)

Status Information

The master runs an internal HTTP server exporting status pages:

  • Computation progress: tasks completed, bytes processed, processing rates
  • Links to stderr and stdout files generated by each task
  • Which workers have failed and which tasks they were processing

Counters

A facility for counting occurrences of various events across all workers.

  • Counter values are piggybacked on heartbeat pings and aggregated by the master
  • The master deduplicates counter updates to avoid double-counting from re-executed tasks
  • Some counters are maintained automatically (e.g., number of input/output key/value pairs)
  • Useful for sanity checks (e.g., verify that output pairs == input pairs for a bijective operation)

Lecture

Context: multi-hour computations on multi-terabyte data-sets

  • only practical with 1000s of computers
    • e.g. build search index, or sort, or analyze structure of web

Goal: easy for non-specialist programmers

  • programmer just defines Map and Reduce functions.
    • often simple sequential code
  • MR manages, and hides, all aspects of distribution.
    • MR is a framework / library
    • application is just Map() / Reduce()

Abstract View of A MapReduce Job

Input1 -> Map -> a,1 b,1
Input2 -> Map -> 	 b,1
Input3 -> Map -> a,1 	c,1
				 |   |  |
				 |   |  | -> Reduce -> c,1
				 |   |-----> Reduce -> b,2
				 |---------> Reduce -> a,2
  1. Input is (already) split into MMM pieces
  2. MR calls Map() for each input split, produces list of k,v pairs
    • intermediate data
    • each Map() call is a task
  3. When Maps are done,
    • MR gathers all intermediate v’s for each k,
    • and passes each key + values to a Reduce call
  4. Final output is set of <k,v> pairs from Reduce() s

Word Count

Map(d) {
	chop d into words
	for each word w
		emit(w, "1")
}

Reduce(k, v[]) {
	emit(len(v[]))
}

Scales

NNN worker computers (might) get NNNx throughput.

  • Maps()s can run in parallel, since they don’t interact.
  • Same for Reduce()s.

Thus more computers -> more throughput

Hide Complexity

  • Sending map+reduce code to servers
  • Tracking which tasks have finished
  • Shuffling intermediate data from Maps to Reduces
  • Balancing load over servers
  • Recovering from crashed servers

To get these benefits, MapReduce restricts applications:

  • Only one pattern (Map -> shuffle -> Reduce).
  • No interaction or state (other than via intermediate output).
  • Only batch: no real-time or streaming processing.

Details

GFS (Google File System)

Input and output are stored on the GFS cluster file system

  • MR needs huge parallel input and output throughput.
  • GFS splits files over many servers, many disks, in 64 MB chunks
  • Maps read in parallel
  • Reduces write in parallel
  • GFS replicates data on 2 or 3 servers, for fault tolerance

Output

  • MR writes Map() output to local disk
  • MR splits into files by hash(key) mod R
  • Each “hash bucket” contains multiple keys
  • The map workers all hash the same way

The Shuffle

  • Each Reduce task processes one hash bucket
  • MR fetches each Reduce tasks’ bucket from every Map worker
  • Merge, sort by key, call Reduce() for each key
  • Each Reduce task writes a separate output file on GFS

Coordinator (Master)

The Coordinator manages all the steps in a job.

  • Tracks state of each task
  • Hands out tasks to worker machines

Limitation

In 2004 were limited by network speed. MR send over the network:

  • Maps read input from GFS.
  • Reduces fetch Map intermediate output.
  • Often as large as input, e.g. for sorting.
  • Reduces write output files to GFS.

Optimise

MR minimize network use:

  • Coordinator tries to run each Map task on GFS server that stores its input.
  • All computers run both GFS and MR workers
  • So Map input is usually read from GFS data on local disk, not over network.
  • Intermediate data goes over network just once.
  • Map worker writes to local disk.
  • Reduce workers read from Map worker disks over the network.
  • (Storing it in GFS would require at least two trips over the network.)

Balance

Why Need Balance

  • If one server has more work than others, or is slower, then other servers will lie idle (wasted) at the end, waiting.
  • So ideally MR divides work so that all workers finish at same time.
  • But tasks vary in size, and computers vary in speed.

Solution

Many more tasks than worker machines.

  • Coordinator hands out new tasks to workers who finish previous tasks.
  • So faster servers do more tasks than slower ones.
  • And slow servers are given less work, reducing impact on total time.

Fault tolerance?

We want MR framework to hide failures.

  • Coordinator re-runs just the failed Map()s and Reduce()s.

Suppose MR runs a Map task twice, one Reduce sees first run’s output, but another Reduce sees the second run’s output?

The two Map executions had better produce identical intermediate output.

Map and Reduce should be pure deterministic functions:

  • They are only allowed to look at their arguments/input.
  • No state, no file I/O, no interaction, no external communication, no random numbers.
  • Programmer is responsible for ensuring this determinism.

Other Failures/Problems

What if the coordinator gives two workers the same Map() task?

  • Perhaps the coordinator incorrectly thinks one worker died.
  • It will tell Reduce workers about only one of them.

What if the coordinator gives two workers the same Reduce() task?

  • they will both try to write the same output file on GFS!
  • atomic GFS rename prevents mixing; one complete file will be visible.

What if a single worker is very slow – a “straggler”?

  • perhaps due to flakey hardware.
  • coordinator starts a second copy of last few tasks.

What if a worker computes incorrect output, due to broken h/w or s/w?

  • MR assumes “fail-stop” CPUs and software.

What if the coordinator crashes?
