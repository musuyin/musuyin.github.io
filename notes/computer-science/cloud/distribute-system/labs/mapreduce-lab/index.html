Lab1: MapReduce

2026-05-12

#分布式#MIT6824#MapReduce

理解主线

先用顺序版本确认 Map、排序分组与 Reduce 的数据契约，再把任务分给 Worker。实验的关键是 Coordinator 如何跟踪状态、检测超时、重派任务，并避免过期结果污染最终输出。

Introduction

The code provides a sequential MapReduce implementation.

Code

package main

//
// simple sequential MapReduce.
//
// go run mrsequential.go wc.so pg*.txt
//

import "fmt"
import "6.5840/mr"
import "plugin"
import "os"
import "log"
import "io/ioutil"
import "sort"

// for sorting by key.
type ByKey []mr.KeyValue

// for sorting by key.
func (a ByKey) Len() int           { return len(a) }
func (a ByKey) Swap(i, j int)      { a[i], a[j] = a[j], a[i] }
func (a ByKey) Less(i, j int) bool { return a[i].Key < a[j].Key }

func main() {
    if len(os.Args) < 3 {
       fmt.Fprintf(os.Stderr, "Usage: mrsequential xxx.so inputfiles...\n")
       os.Exit(1)
    }

    mapf, reducef := loadPlugin(os.Args[1])

    //
    // read each input file,    // pass it to Map,    // accumulate the intermediate Map output.    //    intermediate := []mr.KeyValue{}
    for _, filename := range os.Args[2:] {
       file, err := os.Open(filename)
       if err != nil {
          log.Fatalf("cannot open %v", filename)
       }
       content, err := ioutil.ReadAll(file)
       if err != nil {
          log.Fatalf("cannot read %v", filename)
       }
       file.Close()
       kva := mapf(filename, string(content))
       intermediate = append(intermediate, kva...)
    }

    //
    // a big difference from real MapReduce is that all the    // intermediate data is in one place, intermediate[],    // rather than being partitioned into NxM buckets.    //
    sort.Sort(ByKey(intermediate))

    oname := "mr-out-0"
    ofile, _ := os.Create(oname)

    //
    // call Reduce on each distinct key in intermediate[],    // and print the result to mr-out-0.    //    i := 0
    for i < len(intermediate) {
       j := i + 1
       for j < len(intermediate) && intermediate[j].Key == intermediate[i].Key {
          j++
       }
       values := []string{}
       for k := i; k < j; k++ {
          values = append(values, intermediate[k].Value)
       }
       output := reducef(intermediate[i].Key, values)

       // this is the correct format for each line of Reduce output.
       fmt.Fprintf(ofile, "%v %v\n", intermediate[i].Key, output)

       i = j
    }

    ofile.Close()
}

// load the application Map and Reduce functions
// from a plugin file, e.g. ../mrapps/wc.so
func loadPlugin(filename string) (func(string, string) []mr.KeyValue, func(string, []string) string) {
    p, err := plugin.Open(filename)
    if err != nil {
       log.Fatalf("cannot load plugin %v", filename)
    }
    xmapf, err := p.Lookup("Map")
    if err != nil {
       log.Fatalf("cannot find Map in %v", filename)
    }
    mapf := xmapf.(func(string, string) []mr.KeyValue)
    xreducef, err := p.Lookup("Reduce")
    if err != nil {
       log.Fatalf("cannot find Reduce in %v", filename)
    }
    reducef := xreducef.(func(string, []string) string)

    return mapf, reducef
}

Phase

  1. Load plugin: initialize Map and Reduce functions from a .so plugin file.
  2. Map phase: read each input file, pass content to Map, collect all intermediate KeyValue pairs.
  3. Sort: sort all intermediate pairs by key.
  4. Reduce phase: for each distinct key, call Reduce on all its values, write result to output file.

In the sequential version, all intermediate data is gathered in one place — no need to route keys to specific workers.

Distributed MapReduce

Job

Your job is to implement a distributed MapReduce, consisting of two programs, the coordinator and the worker. There will be just one coordinator process, and one or more worker processes executing in parallel. In a real system the workers would run on a bunch of different machines, but for this lab you’ll run them all on a single machine. The workers will talk to the coordinator via RPC. Each worker process will, in a loop, ask the coordinator for a task, read the task’s input from one or more files, execute the task, write the task’s output to one or more files, and again ask the coordinator for a new task. The coordinator should notice if a worker hasn’t completed its task in a reasonable amount of time (for this lab, use ten seconds), and give the same task to a different worker.

We have given you a little code to start you off. The “main” routines for the coordinator and worker are in main/mrcoordinator.go and main/mrworker.go; don’t change these files. You should put your implementation in mr/coordinator.go, mr/worker.go, and mr/rpc.go.

Details

Intermediate File File Routing

In the distributed version, multiple Reduce workers run in parallel, and the same key must always go to the same Reduce worker.

This is achieved with the hash function in worker.go:

// use ihash(key) % NReduce to choose the reduce task number
func ihash(key string) int {
    h := fnv.New32a()
    h.Write([]byte(key))
    return int(h.Sum32() & 0x7fffffff)
}
  • Map workers do not send intermediate data to the Coordinator.
  • Map workers write intermediate data directly to local files, partitioned by ihash(key) % NReduce.

Intermediate File Name Convention

Files are named mr-X-Y where:

  • X = Map task number
  • Y = Reduce task number (= ihash(key) % NReduce)

Intermediate Flie Count

With M Map tasks and N Reduce tasks:

  • Each Map worker writes N intermediate files (one per Reduce bucket).
  • Total intermediate files = M × N.

Files to Implement

File What to implement
mr/rpc.go RPC message structs (task request/reply, etc.)
mr/coordinator.go Task distribution, state tracking, crash recovery
mr/worker.go Request tasks from Coordinator, run Map/Reduce, write output
Role Responsibility
Coordinator Manages all tasks in a job. Tracks task state, hands out tasks to workers.
Worker Executes Map or Reduce tasks assigned by the Coordinator.

Communication: Via Unix domain socket (RPC over HTTP), not TCP.

RPC

Constants

const (
    StatusOK   = 0  // got a task, proceed
    StatusWait = 1  // no task available yet, retry later
    StatusDone = 2  // all done, worker should exit
)

const (
    TaskMap    = 0
    TaskReduce = 1
)

RPC 1: Ask for Task

type AskArgs struct{}  // worker has nothing to send

type AskReply struct {
    Status   int    // see status constants above
    Type     int    // TaskMap or TaskReduce
    Index    int    // task number (used in filename: mr-X-Y)
    Filename string // input file, only meaningful for Map tasks
    NReduce  int    // always included, needed by Map worker for ihash()
}

Worker logic after receiving reply:

  1. Check Status first
  2. If StatusOK → read Type, Index, Filename and execute task
  3. If StatusWait → sleep briefly and retry
  4. If StatusDone → exit

RPC 2: Report Completion

type FinishArgs struct {
    Type  int  // TaskMap or TaskReduce
    Index int  // which task finished
}

type FinishReply struct{}  // no response needed

Key Design Decisions

Decision Reason
AskArgs is empty Worker has nothing to identify itself; Coordinator tracks timing internally
NReduce always included Simpler than conditionally setting it only for Map tasks
FinishReply is empty If the RPC succeeds, the Coordinator received it
Filename left empty for Reduce Simpler than using *string; worker ignores it when Type == TaskReduce

Coordinator

Coordinator’s Role

The Coordinator is a passive server。

  • It never contacts workers.
  • Workers drive all progress by calling RPCs on the Coordinator.
  • The Coordinator only maintains state and responds to requests.

Task State Machine

graph LR
	A[TaskUndo]-->B[TaskProcessing]
	B[TaskProcessing]-->C[TaskDone]
	B[TaskProcessing]-->|timeout| A[TaskUndo]
const (
    TaskUndo = iota   // not yet assigned
    TaskProcessing    // assigned to a worker
    TaskDone          // completed
)

const (
    TaskMap    = 0
    TaskReduce = 1
)

Data Structure

Task Struct
type Task struct {
    Index     int
    Filename  string    // only used by Map tasks
    Status    int
    StartTime time.Time
}

A single Task type is shared by both Map and Reduce — Filename is left empty for Reduce tasks.

Coordinator Struct
type Coordinator struct {
    mu          sync.Mutex
    mapTasks    []Task
    reduceTasks []Task
    nReduce     int
}

No cached flags or counters — all phase state is derived by scanning the task arrays when needed.

RPC Handlers

AskTask
Lock
  1. Scan mapTasks for TaskUndo → assign it, spawn timeout goroutine, return StatusOK
  2. Count TaskDone map tasks
     - If count < total → some maps still running → return StatusWait
  3. All maps done → scan reduceTasks for TaskUndo → assign it, spawn timeout goroutine, return StatusOK
  4. All reduce tasks assigned or done → return StatusWait
Unlock (via defer)

Key rules:

  • Lock is held only briefly (no sleeping inside lock)
  • Goroutine is spawned after state update, outside the lock
  • reply fields are set directly (reply.Status = ...), never reply = &AskReply{...}

Timeout Goroutine (spawned per assigned task)
sleep 10 seconds
Lock
  if task.Status != TaskDone → task.Status = TaskUndo
Unlock

The task pointer (&c.mapTasks[i]) is passed into the goroutine so it modifies the original, not a copy.

FinishTask
Lock
  if task.Status == TaskProcessing → task.Status = TaskDone
Unlock

The TaskProcessing check prevents a stale/crashed worker from incorrectly marking a re-assigned task as done.

Done

Scans reduceTasks and returns true only when all are TaskDone. Called periodically by mrcoordinator.go to decide when to exit.

Key Design Decisions

Decision Reason
One sync.Mutex on Coordinator Protects all shared state; simpler than per-task locks
No defer + manual unlock mix Would cause double-unlock panic; use defer only
Recompute phase state each time Avoids cached flags going out of sync with task array
Goroutine spawned outside lock Goroutine re-acquires lock itself; lock is never held during sleep
FinishTask checks TaskProcessing Prevents stale worker reports from corrupting re-assigned task state
reply fields set directly RPC framework holds original pointer; replacing it has no effect

Common Pitfalls

  • for _, task := range slice gives a copy — use index (slice[i]) to modify in place
  • Spawning goroutine inside lock — goroutine tries to re-acquire same lock → deadlock
  • reply = &AskReply{} — replaces local pointer only, RPC caller sees no change
  • No status set at end of AskTask — default Status=0 equals StatusOK, confusing the worker

Worker

Worker’s Role

The Worker is stateless.

  • It doesn’t know in advance whether it will run Map or Reduce tasks.
  • It drives all progress by repeatedly asking the Coordinator for work, executing whatever task it receives, then reporting completion.

Main Loop

loop:
    call AskTask RPC
    if reply == nil    → Coordinator is gone, exit
    if StatusWait      → sleep 1s, retry
    if StatusDone      → exit
    if StatusOK:
        switch Type:
            TaskMap    → dealMap()
            TaskReduce → dealReduce()
        call FinishTask RPC

The same worker process can execute both Map and Reduce tasks across its lifetime.

Map Task (dealMap)

Steps
  1. Read input file content from disk
  2. Call mapf(filename, content) to get []KeyValue
  3. Partition output into NReduce buckets using ihash(key) % NReduce
  4. Write each bucket to an intermediate file atomically

Intermediate File Naming
mr-X-Y
  X = Map task index
  Y = ihash(key) % NReduce  (which Reduce task this key belongs to)

Atomic Write Pattern

Write to a temp file first, then rename — prevents corrupt partial files if the worker crashes mid-write:

ofile, _ := os.CreateTemp("", fmt.Sprintf("mr-%d-%d-*", mapIndex, bucket))
// ... write data ...
ofile.Close()
os.Rename(ofile.Name(), fmt.Sprintf("mr-%d-%d", mapIndex, bucket))

os.Rename is atomic on Unix — readers always see either the complete old file or the complete new file.

Why atomic writes are safe with duplicate tasks

If two workers are assigned the same Map task (one timed out), both produce identical output (deterministic mapf). The second rename simply overwrites the first — no corruption.

Intermediate File Format

JSON-encoded []KeyValue per file. JSON handles keys/values with any content safely (no ambiguity from spaces).

Reduce Task (dealReduce)

Steps
  1. Find all intermediate files for this Reduce index using Glob
  2. Decode each file into []KeyValue and merge into one slice
  3. Sort by key
  4. Group consecutive equal keys, call reducef(key, values)
  5. Write output atomically to mr-out-Y

Finding Input Files
filepath.Glob(fmt.Sprintf("mr-[0-9]*-%d", reduceIndex))

Important: The pattern must use [0-9]* (not *) for the Map index part. A plain * would also match files like mr-worker-jobcount-12345-0 written by some test plugins into the same directory, causing JSON decode failures.

Output File
mr-out-Y   (Y = Reduce task index)

Key Design Decisions

Decision Reason
Worker is stateless Task type decided per-iteration by Coordinator reply
nil reply → exit In this lab, dial failure means Coordinator has exited
Buckets in memory before writing Avoids opening/closing NReduce files repeatedly per key
JSON encoding for intermediate files Handles any key/value content; no ambiguity from spaces
os.CreateTemp for temp filenames Guarantees unique names; avoids collision between concurrent workers
Glob pattern mr-[0-9]*-%d Prevents matching non-intermediate files written by test plugins

Common Pitfalls

  • Glob pattern too broad (mr-*-%d) — accidentally matches plugin-created files, causing JSON decode failures
  • Writing directly to final filename — crashed worker leaves corrupt partial file; use temp + rename
  • Not closing file before rename — data may not be flushed to disk
  • log.Fatal on dial error — kills worker when Coordinator exits normally; use return false instead

Run & Test

cd src
make mr
