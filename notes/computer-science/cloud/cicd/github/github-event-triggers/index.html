Github Trigger

2026-09-01

#待处理

理解主线

GitHub 事件可以触发 Actions，也可以通过 Webhook 交给外部 App。两条路径都需要把事件识别、认证权限、幂等处理与结果回写分别设计。

这类工具的核心可以概括成一句话：GitHub 负责发事件，外部自动化服务接住事件并调用 GitHub API 回写结果。

以 PR-bot 自动生成 PR 说明并发评论为例，通常流程是：

开发者创建 / 更新 PR
        ↓
GitHub 产生 pull_request 事件
        ↓
触发 GitHub Actions，或向机器人服务发 Webhook
        ↓
机器人读取 PR 的标题、描述、diff、提交记录
        ↓
生成说明文字
        ↓
调用 GitHub API，在该 PR 下创建 Comment

“自动触发”主要有两种常见方式。

  1. GitHub Actions

仓库里放一个工作流文件，例如 .github/workflows/pr-bot.yml，声明：

on:
  pull_request:
    types: [opened, synchronize, reopened]
  • opened：新建 PR
  • synchronize：向现有 PR 推送新提交
  • reopened：重新打开 PR

GitHub 检测到事件后，会启动一个临时 Runner 执行工作流。工作流拿到 GitHub 自动注入的 GITHUB_TOKEN，然后通过 gh 命令或 GitHub API 创建评论。

例如 API 的本质是：

POST /repos/{owner}/{repo}/issues/{pr_number}/comments

请求体：

{
  "body": "机器人生成的 PR 摘要……"
}

GitHub 将 PR 的讨论区也视为 issue 评论的一种，所以这个接口能直接往 PR Conversation 里发评论。工作流中的令牌需要具备 pull-requests: write 或 issues: write 权限。

  1. GitHub App / 外部 Bot + Webhook

更成熟的 PR-bot 通常不是在 Action 内完成，而是一个长期运行的服务，可能部署在云函数、容器或自建服务器上。

仓库安装 GitHub App 后，App 订阅 pull_request 事件。GitHub 在 PR 创建或更新时，会向服务的 Webhook URL 发一个 HTTP POST，请求里包含：

  • PR 编号、标题、提交者
  • PR 的 base/head 分支
  • 仓库信息
  • 触发动作，例如 opened、synchronize

服务先校验 Webhook 签名，避免伪造请求；接着用 GitHub App 的私钥换取短期 installation token，再调用 GitHub API：

  • 获取 PR 内容：GET /repos/{owner}/{repo}/pulls/{pull_number}
  • 获取文件变更：GET /repos/{owner}/{repo}/pulls/{pull_number}/files
  • 新增评论：POST /repos/{owner}/{repo}/issues/{issue_number}/comments
  • 更新机器人之前的评论：PATCH /repos/{owner}/{repo}/issues/comments/{comment_id}

实际产品往往会“更新同一条评论”而不是每次推送都新增一条，避免讨论区被刷屏。机器人会保存它发出的 comment_id，或者扫描已有评论找自己的标记，例如 <!-- pr-bot-summary -->。

Jenkins 的原理与此类似，只是它更通用：它是一个长期运行的自动化调度器，不仅服务 GitHub。

GitHub PR / Push 事件
        ↓ Webhook
Jenkins 接收事件
        ↓
匹配对应 Job / Multibranch Pipeline
        ↓
拉取仓库代码
        ↓
按 Jenkinsfile 执行构建、测试、部署
        ↓
通过 GitHub API 回写状态、评论或检查结果

Jenkins 和 GitHub 的交互一般包括：

  • GitHub → Jenkins：Webhook 通知 Jenkins 有 push、PR 创建或 PR 更新。
  • Jenkins → GitHub：用 Token、Deploy Key 或 GitHub App 身份拉取代码。
  • Jenkins → GitHub：通过 API 创建 commit status 或 Check Run，例如显示 PR 的“测试通过 / 构建失败”。
  • Jenkins → GitHub：可选地发布 PR 评论、报告链接、代码扫描结果等。

其中 Jenkinsfile 是放在仓库里的流水线定义，例如：

pipeline {
  agent any

  stages {
    stage('测试') {
      steps {
        sh 'npm test'
      }
    }
  }
}

当 Jenkins 收到 GitHub Webhook 后，它会找到这个 PR 对应的代码版本，检出代码并执行 Jenkinsfile。测试结束后，GitHub PR 页面上常见的绿色勾、红叉、Required checks，本质上就是 Jenkins 或其他 CI 工具回写给 GitHub 的状态。

常见组件可以这样区分：

组件 主要职责 与 GitHub 的典型交互
GitHub Actions GitHub 内置 CI/CD 执行器 GitHub 事件直接触发工作流
Jenkins 自建、可高度定制的自动化平台 Webhook 触发，API 回写状态
GitHub App 以“应用身份”接入 GitHub 的机器人 订阅事件、调用 API
Webhook GitHub 主动通知外部系统的机制 把事件 HTTP POST 到指定地址
GitHub API 读写 GitHub 对象的接口 评论、标签、状态、合并 PR 等
Token / App Token 调用 API 的身份与权限凭证 决定机器人能做哪些操作

所以，PR-bot 的“生成文字”只是中间一步；真正让它出现在 PR 评论区的是：拿着有权限的身份凭证，调用 GitHub 的评论 API。而“自动发生”的根源，是 GitHub 的事件机制——GitHub Actions 是平台内置的事件消费者，Jenkins 和机器人服务则通常通过 Webhook 成为外部事件消费者。

复习与应用

沿一次 PR 更新比较 Actions 和外部 Bot：谁接收事件、谁取得令牌、谁写评论，以及重复通知如何避免产生重复输出。
