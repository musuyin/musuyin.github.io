2026-08-07

理解主线

声明式 Jenkinsfile 先定义执行位置与全局约束，再按 stages 组织步骤，post 负责结束后的动作。阅读时区分环境变量、构建参数与 Groovy 脚本作用域。

A Jenkinsfile (Declarative Pipeline syntax) is built from the following components.

Top Level

Library imports (@Library)

Optional. Loads shared Groovy libraries that provide reusable steps.

@Library('some-lib') _

The trailing _ is required when loading multiple libraries without importing a specific class.

pipeline block

The root block. Everything lives inside it.

pipeline {
    agent ...
    options { ... }
    parameters { ... }
    environment { ... }
    stages { ... }
    post { ... }
}

Required Fields

agent

Where the pipeline runs. Must be declared.

  • agent any — run on any available Jenkins node
  • agent { label 'linux' } — run on a node with that label
  • agent none — no global agent; each stage declares its own

stages → stage → steps

The actual work. stages contains one or more stage blocks, each with a steps block.

stages {
    stage('Build') {
        steps {
            sh 'make build'
        }
    }
}

Common Optional Fields

options

Pipeline-level behavior settings:

  • skipDefaultCheckout() — don’t auto-checkout SCM at start
  • timestamps() — prefix all log lines with timestamps
  • timeout(time: 30, unit: 'MINUTES') — abort if pipeline exceeds limit
  • disableConcurrentBuilds() — prevent parallel runs of the same job

parameters

User-supplied inputs when triggering a build. Accessed via params.NAME.

  • string(name: 'X', defaultValue: '', description: '...')
  • booleanParam(...), choice(...), password(...)

environment

Declares env vars available to all stages. Can read Jenkins credentials:

environment {
    MY_VAR = 'value'
    MY_SECRET = credentials('credentialId')
}

post

Runs after all stages, based on build result:

  • always, success, failure, unstable, cleanup
post {
    failure { mail to: '...', subject: 'Build failed' }
    cleanup { cleanWs() }
}

Inside steps

Built-in steps

  • sh 'command' — run shell command (Linux/Mac)
  • bat 'command' — run shell command (Windows)
  • echo 'message'
  • checkout scm — check out source code
  • sleep(60) — wait N seconds
  • timeout(time: 5, unit: 'MINUTES') { ... }
  • withCredentials([...]) { ... } — inject secrets into a block
  • readJSON(text: '...') — parse JSON string
  • error('message') — fail the build immediately

script block

Escapes into free-form Groovy when declarative syntax isn’t enough:

steps {
    script {
        def x = sh(script: 'echo hello', returnStdout: true).trim()
        echo x
    }
}

Stage Modifiers (optional, per-stage)

stage('Deploy') {
    when { branch 'main' }           // conditional execution
    agent { label 'deploy-node' }    // override agent for this stage
    parallel {                       // run sub-stages in parallel
        stage('A') { steps { ... } }
        stage('B') { steps { ... } }
    }
}

Structure Skeleton

pipeline
├── agent
├── options          (optional)
├── parameters       (optional)
├── environment      (optional)
├── stages
│   └── stage(s)
│       ├── when     (optional)
│       ├── agent    (optional, overrides top-level)
│       └── steps
│           └── sh / script / withCredentials / ...
└── post             (optional)

Minimal Working Example

pipeline {
    agent any
    stages {
        stage('Hello') {
            steps {
                echo 'Hello, World!'
            }
        }
    }
}

Function Origin: Standard Jenkins vs. Shared Libraries

Every function/step call in a Jenkinsfile comes from one of three sources.

Jenkins Declarative Pipeline syntax (built into Jenkins core)

These are keywords of the Declarative Pipeline DSL itself — not function calls, but structural syntax:

Keyword Role
pipeline Root block
agent Execution target
options Pipeline-level settings
parameters / string Build parameter definitions
stages / stage / steps Stage structure
post Post-build actions
script Escape hatch into Groovy
when / parallel Stage control flow

Standard Jenkins plugins (pre-installed on most Jenkins instances)

These look like function calls but ship with Jenkins or its standard plugin bundle — no @Library needed:

Function Plugin What it does
checkout scm Git Plugin Check out the SCM source configured for the job
sh(...) Pipeline: Nodes and Processes Run a shell command
echo Pipeline core Print a log message
sleep(N) Pipeline core Wait N seconds
timeout(...) Pipeline core Abort if a block exceeds a time limit
error('msg') Pipeline core Fail the build immediately
withCredentials([...]) Credentials Binding Plugin Inject secrets into a block
usernamePassword(...) Credentials Binding Plugin Credential binding type
readJSON(text: ...) Pipeline Utility Steps Plugin Parse a JSON string into an object
cleanWs(...) Workspace Cleanup Plugin Delete the workspace
deleteDir() Pipeline core Delete current directory
skipDefaultCheckout() Pipeline core Option: skip auto-checkout
timestamps() Timestamper Plugin Option: add timestamps to log
disableConcurrentBuilds(...) Pipeline core Option: prevent concurrent runs
env / params Pipeline core Built-in variable objects

Shared library functions (loaded via @Library)

These are developer-defined steps provided by the three libraries imported at the top of this Jenkinsfile. Without those @Library imports, these calls would fail:

Function Library What it does
setupPipelineEnvironment(...) piper-lib / piper-lib-os Initialises Piper pipeline context, sets GitHub org/repo metadata, loads config
cloneRepository(...) haas-jenkins-lib Clones a specific GitHub repo/branch into a named subdirectory
dockerExecute(...) piper-lib-os Runs a closure inside a Docker container with the specified image

Quick rule of thumb

If the call needs a @Library import to work → it’s library-defined (developer code).
If it works in any plain Jenkins pipeline → it’s standard.
