Jenkins

2026-08-12

#Cloud#Jenkins#CI/CD#DevOps#面试

理解主线

Jenkins 编排 CI/CD，把代码变更转为可重复执行的 Pipeline。Job、Stage、Step、Agent 和 Jenkinsfile 分别描述任务、阶段、动作、运行位置和流水线定义，先明确这些对象再看部署插件。

什么是 CI/CD

CI/CD 是现代软件开发的核心流程，解决“代码写完后如何安全、快速地到达生产”的问题。

缩写 全称 做什么
CI Continuous Integration 持续集成：代码合并后自动构建、测试
CD Continuous Delivery/Deploy 持续交付/部署：自动将通过测试的代码发布

没有 CI/CD 之前：

  • 开发各自写代码，合并时一堆冲突
  • 手动运行测试，容易漏跑
  • 手动登录服务器部署，容易出错、无法回溯

有了 CI/CD：

代码提交
    │
    ▼ 自动触发
构建（Build）→ 单元测试 → 集成测试 → 打包镜像
    │
    ▼ 通过后
自动部署到 staging → （人工确认）→ 自动部署到 prod

Jenkins 是什么

Jenkins 是最主流的开源 CI/CD 自动化服务器，负责编排和执行整个 Pipeline。

类比：Jenkins 是“工厂的流水线控制中心”——代码变更进来，它按顺序触发各道工序（构建/测试/部署），任何一道失败就停线告警。

核心概念：

概念 说明
Job / Pipeline 一个自动化任务，描述要执行哪些步骤
Jenkinsfile 用代码定义 Pipeline 的配置文件，存在 Git 仓库里
Stage Pipeline 的一个阶段（Build / Test / Deploy）
Step Stage 内的具体操作（执行 shell 命令、调用插件等）
Agent 执行 Pipeline 的机器（Jenkins Master 或 Worker）
Trigger 触发条件（PR 提交、代码合并、定时任务等）

Jenkinsfile：Pipeline as Code

Jenkinsfile 是 Jenkins 的核心——用代码定义流水线，和应用代码一起存在 Git 里，版本可追踪。

基本结构（Declarative Pipeline）

pipeline {
    agent any   // 在任意可用 Agent 上运行

    environment {
        IMAGE_TAG = "v${BUILD_NUMBER}"  // 内置变量
    }

    stages {
        stage('Build') {
            steps {
                sh 'docker build -t myapp:${IMAGE_TAG} .'
            }
        }

        stage('Test') {
            steps {
                sh 'go test ./...'
            }
        }

        stage('Push Image') {
            steps {
                sh 'docker push myregistry/myapp:${IMAGE_TAG}'
            }
        }

        stage('Deploy to Staging') {
            steps {
                sh 'helm upgrade --install myapp ./chart -f values-staging.yaml --set image.tag=${IMAGE_TAG}'
            }
        }

        stage('Deploy to Prod') {
            when {
                branch 'main'  // 只有 main 分支才部署到生产
            }
            steps {
                input message: '确认部署到生产？'  // 人工确认
                sh 'helm upgrade --install myapp ./chart -f values-prod.yaml --set image.tag=${IMAGE_TAG}'
            }
        }
    }

    post {
        failure {
            slackSend message: "Pipeline 失败：${env.JOB_NAME} #${BUILD_NUMBER}"
        }
        success {
            echo 'Pipeline 成功'
        }
    }
}

PR 触发 vs merge 触发

生产中最常见的触发模式：

开发者推送 PR
    │
    ▼ Jenkins 自动触发
    CI Pipeline（只跑构建 + 测试，不部署）
    → 结果作为 GitHub/GitLab Check 显示在 PR 上
    │
    ▼ Code Review 通过 + 合并到 main
    CD Pipeline（构建 → 测试 → 部署 staging → 部署 prod）

这正是 setup-account 项目的模式：PR 触发 terraform plan，merge 触发 terraform apply。

完整 Cloud Native CI/CD 流程

结合之前学的所有工具，完整流程如下：

开发者 git push / PR
        │
        ▼ Jenkins / GitHub Actions 触发
┌─────────────────────────────────────┐
│             CI 阶段                  │
│  1. 代码检出（git checkout）          │
│  2. 编译（mvn build / go build）     │
│  3. 单元测试（junit / go test）      │
│  4. 代码扫描（SonarQube / lint）     │
│  5. 构建 Docker 镜像                 │
│  6. 推送镜像到 ECR / Harbor          │
└──────────────┬──────────────────────┘
               │ 通过后触发
┌──────────────▼──────────────────────┐
│             CD 阶段                  │
│  7. helm upgrade（更新 K8s 部署）    │
│     → 使用新镜像 tag                 │
│     → 滚动更新，零停机               │
│  8. 冒烟测试 / 集成测试              │
│  9. 部署到 prod（人工或自动）        │
└─────────────────────────────────────┘
        │
        ▼ Prometheus + Grafana
    监控新版本的指标、告警

Jenkins vs GitHub Actions：本质差异

表面上看只是语法不同（Groovy DSL vs YAML）、运行机器不同（自托管 vs 云托管），但背后有几个架构层面的根本差异。

差异一：托管模式 → 决定能访问什么

这是最核心的差异，直接影响能做什么事。

维度 Jenkins（自托管） GitHub Actions（云托管）
运行位置 跑在你自己的服务器/K8s 集群里 跑在 GitHub 云上的 Runner（微软 Azure）
访问内部系统 原生可以：直接连内网 DB、私有 Vault、内部 K8s 默认不行：Runner 在公网，看不到内网
数据离境 所有日志、制品留在自己的机器上 日志、制品存储在 GitHub 的云上
合规/审计 完全自控 依赖 GitHub 的合规认证

这就是为什么 SAP 用 Jenkins 而不是 GitHub Actions：

setup-account 的 Pipeline 需要访问 SAP 内部的 Vault 实例、私有 AWS 账号、内部 K8s 集群——这些都在 SAP 内网，GitHub 云上的 Runner 根本连不到。Jenkins 跑在 SAP 自己的基础设施上，天然可以访问这一切。

GitHub Actions 云 Runner
    × 无法访问 → SAP 内部 Vault
    × 无法访问 → 私有 AWS 账号
    × 无法访问 → SAP 内部 K8s

Jenkins（跑在 SAP 内网）
    ✓ 直接访问 → SAP 内部 Vault
    ✓ 直接访问 → 私有 AWS 账号（通过内部 IAM）
    ✓ 直接访问 → SAP 内部 K8s

注：GitHub Actions 也支持 Self-hosted Runner（把 GitHub 的 Runner Agent 装在自己服务器上），这样就能访问内网——但这样就失去了“无需维护服务器”的优点，变成了一个更难用的 Jenkins。

差异二：插件架构 → 决定能扩展什么

维度 Jenkins GitHub Actions
扩展单元 Plugin（Java，跑在 Jenkins 进程内） Action（Docker 容器或 JS 脚本）
生态规模 1800+ 插件，历史积累深厚 Marketplace 上数万个 Action
深度集成能力 Plugin 可修改 Jenkins 内部行为 Action 相互隔离，无法影响 Runner 本身
维护负担 插件版本冲突是经典痛点 Action 版本锁定，相对稳定

Jenkins Plugin 可以做一些 GitHub Actions 做不到的事：比如动态修改 Pipeline 的执行逻辑、在 Stage 之间共享 Java 对象、与 Jenkins Master 深度交互。

差异三：Pipeline 编排能力 → 决定能写多复杂的流程

Jenkins 的 Pipeline 用 Groovy 写，本质是编程语言，可以写循环、条件、函数、异常处理：

// Jenkins：动态生成并行 Stage
def landscapes = ['hc-eu10', 'hc-us10', 'hc-ap11']
def parallelStages = landscapes.collectEntries { name ->
    ["Deploy ${name}": {
        stage("Deploy ${name}") {
            sh "terraform apply -chdir=${name}"
        }
    }]
}
parallel parallelStages   // 动态并行，Stage 数量运行时决定

// Jenkins：人工确认 + 超时
stage('Deploy to Prod') {
    timeout(time: 30, unit: 'MINUTES') {
        input message: '确认部署到生产？', ok: '确认'
    }
    sh 'helm upgrade ...'
}

GitHub Actions 的 YAML 是声明式配置，逻辑能力有限：

# GitHub Actions：矩阵是静态的，运行前必须已知
strategy:
  matrix:
    landscape: [hc-eu10, hc-us10, hc-ap11]   # 必须写死，不能动态生成

# 人工确认需要配置 Environment Protection Rules，不能在 YAML 里直接写 input

一句话对比： Jenkins 的 Pipeline 是“写程序”，GitHub Actions 的 Workflow 是“填配置”。复杂编排（动态并行、条件分支、运行时决策）Jenkins 更强；简单直接的 CI（push → build → test）GitHub Actions 更轻量。

差异四：与代码仓库的耦合度

GitHub Actions 是 GitHub 内置功能，对 GitHub 事件的感知是原生的：

on:
  pull_request:        # PR 的各种事件（open/sync/close）
  push:
    branches: [main]
  release:
    types: [published] # Release 发布时触发
  schedule:
    - cron: '0 9 * * 1-5'

Jenkins 需要通过 Webhook + 插件 才能感知 GitHub 事件，配置更繁琐，且有延迟。

反过来，Jenkins 不绑定任何特定 Git 平台，可以对接 GitHub / GitLab / Bitbucket / SVN 等任意代码仓库，而 GitHub Actions 只能用于 GitHub 仓库。

选择总结

用 Jenkins 当：
    ✓ 需要访问内部网络（内网 DB、私有 K8s、企业 Vault）
    ✓ 需要复杂 Pipeline 编排（动态并行、运行时决策）
    ✓ 合规要求数据不出企业
    ✓ 使用非 GitHub 的代码仓库（GitLab / 内部 Git）
    ✓ 已有大量 Jenkins 插件/基础设施投入

用 GitHub Actions 当：
    ✓ 代码在 GitHub 上，与 PR/Issue/Release 深度集成
    ✓ 不想维护 CI 服务器
    ✓ 开源项目（公共 Runner 免费）
    ✓ Pipeline 逻辑相对简单
    ✓ 快速启动，零运维成本

Jenkins vs GitHub Actions vs ArgoCD

面试常问“为什么用 Jenkins 而不是其他工具”，或者“它们各自的定位”：

工具 定位 特点
Jenkins 通用 CI/CD 服务器 老牌、插件生态最丰富、自托管、高度可定制
GitHub Actions 托管在 GitHub 的 CI/CD 无需维护服务器、与 GitHub PR 深度集成
GitLab CI GitLab 内置 CI/CD 与 GitLab 仓库无缝集成
ArgoCD GitOps 持续部署（CD 专用） 持续监听 Git，自动同步到 K8s，不做 CI
Tekton K8s 原生 CI/CD（CRD 定义） Pipeline 以 K8s 资源形式运行

关键区别：

  • Jenkins / GitHub Actions：既做 CI（构建/测试）又做 CD（部署触发）
  • ArgoCD：只做 CD，不构建代码，只负责把 Git 里的 Helm Chart/YAML 同步到 K8s
  • 生产中常见的组合：Jenkins（CI）+ ArgoCD（CD），两者解耦

GitOps：CD 的进化

GitOps 是 CI/CD 在 K8s 时代的最佳实践：

Git 仓库是唯一的事实来源（Single Source of Truth），K8s 的实际状态应始终与 Git 中声明的状态一致。

传统 CD（Push 模式）：
Jenkins → 主动 kubectl apply / helm upgrade → K8s

GitOps（Pull 模式）：
Jenkins → 更新 Git 仓库中的镜像 tag
ArgoCD 持续监听 Git → 发现差异 → 自动 sync 到 K8s

GitOps 的优点：

  • 所有变更有 Git 记录，可回滚
  • K8s 状态由 ArgoCD 持续维护，即使集群重建也自动恢复
  • 开发者只需 PR，不需要直接操作 K8s

SAP 实践：setup-account 的 Jenkins Pipeline

setup-account 的 Jenkinsfile 是真实生产 CI/CD 的绝佳例子，体现了以下工程实践：

PR 提交
    │
    ▼ Jenkins 检测变更文件路径
    │  只对受影响的 Landscape 触发（智能选择）
    ▼
terraform plan
    → 输出 +创建 ~修改 -删除 的资源预览
    → 结果 Comment 到 PR
    │
    ▼ Code Review 通过，合并到 master
    │
    ▼ master Pipeline
terraform apply
    → 最多 20 个 Landscape 并行执行
    → 结果上传 Sirius（合规审计）
    → 失败发 Slack 告警

工程亮点：

实践 做法 意义
智能 Pipeline 选择 分析变更文件路径，只跑受影响 Lane 避免每次 PR 跑全量，大幅提速
Plan 结果回 PR terraform plan 输出作为 PR Comment 人工审查变更，防止误操作
并行执行 最多 20 个 Landscape 同时 apply 缩短大规模变更的总耗时
合规审计 结果上传 Sirius 满足 SAP 内部合规要求
Slack 告警 失败即通知 快速感知问题，缩短 MTTR

面试高频问题

Q：CI 和 CD 的区别？ CI（持续集成）指代码合并后自动触发构建和测试，快速发现集成问题；CD（持续交付/部署）指通过 CI 后将构建产物自动部署到环境——交付（Delivery）需人工确认最终上线，部署（Deploy）全程自动。

Q：Jenkinsfile 的作用？ Jenkinsfile 将 Pipeline 配置以代码形式存在 Git 仓库里（Pipeline as Code），使 CI/CD 流程可版本化、可审查、可复现，避免 Jenkins 页面手动配置导致的“配置漂移”。

Q：Jenkins 和 ArgoCD 如何配合？ Jenkins 负责 CI 部分（构建代码、跑测试、打镜像），CD 部分将新镜像 tag 更新到 Git 仓库的 Helm values 文件；ArgoCD 持续监听该 Git 仓库，发现 tag 变化后自动同步到 K8s。两者分工：Jenkins 生产制品，ArgoCD 持续同步状态。

Q：什么是 GitOps？有什么优点？ GitOps 是以 Git 为唯一事实来源的 CD 实践，K8s 集群状态由 ArgoCD/Flux 持续与 Git 保持一致（Pull 模式）。优点：所有变更有审计记录可回滚；集群重建后应用自动恢复；开发者通过 PR 操作，不直接接触生产 K8s。

Q：如何实现零停机部署？ K8s 的滚动更新（Rolling Update）机制：helm upgrade 触发 Deployment 更新时，K8s 先启动新版本 Pod，等其 Ready 后再逐步终止旧版本 Pod，全程保持服务可用。配合 readinessProbe 确保新 Pod 真正就绪后才接受流量。

Q：如果一次部署出了问题，如何快速恢复？ 三种方案：① helm rollback <release> <revision> 回滚到上一个 Helm Release 版本；② GitOps 场景下在 Git 仓库 revert commit，ArgoCD 自动同步回旧版本；③ K8s Deployment 本身支持 kubectl rollout undo deployment/<name>。生产优先用 Helm rollback 或 GitOps revert，因为有完整记录。

复习与应用

给一次构建画出 Controller 排队、Agent 执行和结果回写过程；解释交付到可发布状态与自动部署到生产之间的门禁区别。
