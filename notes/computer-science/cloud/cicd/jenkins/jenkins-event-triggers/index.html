Jenkins-Trigger

2026-08-31

#待处理

理解主线

Webhook 只通知事件发生；多分支扫描、发现规则和 Jenkinsfile 决定是否构建以及构建哪个 revision。理解失败时先定位是事件未到、Job 未发现，还是构建已经开始但执行失败。

Jenkins 本身不会持续盯着 Git 仓库的每个变化。通常是 Git 平台（GitHub、GitLab、Bitbucket 等）在发生事件后，主动通过 Webhook 通知 Jenkins；Jenkins 再根据 Job 的配置、分支规则和仓库中的 Jenkinsfile 决定是否创建一次构建、构建哪个提交、执行哪些步骤。

一条 branch push 并创建 PR 后的完整链路

假设开发者向 feature/login 推送代码，随后创建一个合并到 main 的 PR：

开发者 git push / 创建 PR
          │
          ▼
GitHub / GitLab 产生 push、pull_request（或 merge_request）事件
          │  HTTP POST（Webhook）
          ▼
Jenkins 的 Webhook 接口
          │
          ▼
Multibranch Pipeline / Organization Folder 接收事件并扫描仓库
          │
          ├─ 根据规则判断：这个分支或 PR 是否值得构建
          ├─ 找到该版本中的 Jenkinsfile
          └─ 为分支或 PR 对应的 Job 排队一次构建
                    │
                    ▼
              Agent 拉取指定 revision，按 Jenkinsfile 执行
                    │
                    ▼
        测试、构建、制品发布；结果回写到 PR / Commit（状态检查）

Git 平台如何通知 Jenkins：Webhook

在 GitHub/GitLab 仓库设置中配置 Jenkins 的 Webhook 地址后，平台会对相关事件发起 HTTP 请求。常见事件包括：

  • push：向某分支推送了提交。
  • pull_request（GitHub）/ merge_request（GitLab）：PR/MR 被创建、更新源分支、关闭或重新打开。
  • 有些插件还能处理评论触发、标签创建等事件。

Webhook 的价值是近实时且主动通知：无需 Jenkins 定时轮询仓库。请求通常会带签名密钥（Webhook secret），Jenkins 或插件用它验证请求确实来自 Git 平台。

如果没有 Webhook，也可以配置“轮询 SCM”（例如每 5 分钟查一次仓库）或定时触发；但前者延迟更高、会产生无效请求，通常优先使用 Webhook。

注意：Webhook 只负责“告诉 Jenkins 仓库有变化”，并不直接定义构建命令。构建逻辑来自 Jenkins Job 配置和 Jenkinsfile。

Jenkins 如何知道是哪个 Job：Job 类型与仓库匹配

最常用的做法是 Multibranch Pipeline（多分支流水线）。一个 Multibranch Pipeline 指向一个仓库，并配置 GitHub Branch Source、GitLab Branch Source 等“分支来源”插件。它会发现仓库中的分支和 PR，并为符合条件的对象自动创建子 Job，例如：

my-service
├── main
├── feature%2Flogin
└── PR-42

因此，同一个仓库里的 main、feature/login 和 PR #42 可以各自有独立构建记录和状态。Webhook 到达后，Jenkins 根据仓库 URL、组织/项目名等信息定位对应的 Multibranch Pipeline，再对相关分支/PR 做增量扫描。

另一种较旧或较简单的方式是普通 Pipeline Job：它通常固定监听一个仓库/分支，借助 Git 插件、GitHub/GitLab 插件的触发器接收 Webhook。它适合固定分支构建；当分支和 PR 较多时，Multibranch Pipeline 的管理体验通常更好。

Jenkins 如何判断“要不要构建”

Webhook 到达并不等于每次都一定执行。以 Multibranch Pipeline 为例，Jenkins 会依据配置过滤和判断：

  1. 事件是否属于目标仓库：仓库来源、凭据和 Webhook 配置必须能够匹配。
  2. 分支是否被发现策略接受：例如仅构建 main、release/*，忽略已关闭或已合并 PR 的源分支。
  3. PR 是否被发现策略接受：可选择构建 PR 的源分支 HEAD、与目标分支的模拟合并结果，或两者都构建。
  4. 对应 revision 是否已经构建过：如果扫描结果没有新的提交或 PR 版本，通常不会重复排队。
  5. 仓库该 revision 中是否有 Jenkinsfile：没有时，默认不会有可执行的 Pipeline 定义（也可由 Job 使用固定脚本路径或内联脚本）。
  6. Jenkinsfile 中的条件是否允许某个阶段执行：即使 Pipeline 已启动，某些 stage 仍可以按分支、PR、变更文件等条件跳过。

PR 到底构建哪个代码版本

这点很关键。PR #42 从 feature/login 合并到 main 时，常见策略有：

策略 Jenkins 检出的代码 用途
PR HEAD feature/login 当前提交 验证开发者实际推送的代码
合并结果 将 PR 临时与 main 合并后的结果 提前发现与目标分支集成后的冲突或测试失败
两者 分别构建以上两个版本 要求严格，但资源消耗更多

“合并结果”往往是 Git 平台提供的临时 merge ref，或由插件在构建中生成。它不代表把代码真正合并进了 main。

如果 PR 的源分支再次 push，Git 平台会再次发出 PR 更新事件（并通常也会有 push 事件）。Jenkins 识别到 PR 的新 revision 后，便会重新构建，并将最新结果回写为 PR 的状态检查。许多团队还会开启“新构建开始时取消旧构建”，避免过期提交占用构建资源。

Jenkinsfile 如何决定具体执行内容

Jenkinsfile 是与代码一起版本管理的流水线定义，通常放在仓库根目录。Jenkins 找到它后，通过 Pipeline 引擎执行其中定义的阶段和命令。一个简化的声明式 Pipeline 如下：

pipeline {
  agent any

  options {
    disableConcurrentBuilds(abortPrevious: true)
  }

  stages {
    stage('Checkout') {
      steps {
        checkout scm
      }
    }

    stage('Test') {
      steps {
        sh 'npm ci'
        sh 'npm test'
      }
    }

    stage('Build image') {
      when { branch 'main' }
      steps {
        sh 'docker build -t registry.example.com/my-service:${BUILD_NUMBER} .'
      }
    }

    stage('Deploy production') {
      when { branch 'main'; not { changeRequest() } }
      steps {
        sh './deploy-production.sh'
      }
    }
  }
}

这里的行为是：所有被发现的分支/PR 都会跑测试；只有 main 才构建镜像和部署生产。changeRequest() 用来识别 PR/MR 构建，所以即便某些平台把 PR 显示为面向 main 的构建，也可明确阻止它部署生产。

除了 branch 和 changeRequest()，声明式 Pipeline 还常用：

  • when { changeset 'docs/**' }：只有匹配文件发生变化时运行阶段。
  • when { tag 'v*' }：只在符合模式的 Git tag 构建中运行。
  • when { expression { ... } }：使用 Groovy 表达式实现更复杂判断。
  • input：在部署前等待人工确认。

Jenkins 的基本组成

概念 作用
Controller（控制器，旧称 Master） 提供 Web UI、保存配置与构建记录、调度任务；不宜承担重型构建。
Agent（执行节点） 真正执行 checkout、测试、打包、部署等工作，可是虚拟机、容器或 Kubernetes Pod。
Job Jenkins 中可执行任务的配置单位，如 Freestyle、Pipeline、Multibranch Pipeline。
Pipeline 把构建、测试、发布等过程编排为可追踪的步骤。
Jenkinsfile Pipeline 的代码化定义，通常随业务代码放在仓库中。
Stage / Step Stage 是展示给人的阶段（如 Test、Deploy）；Step 是具体动作（如 sh、checkout）。
Plugin 为 Jenkins 提供 Git 平台集成、凭据、容器、通知等能力；需控制数量并及时维护。
Credential 安全保存的 token、SSH key、密码、证书等；构建中通过 ID 引用，不能写死在仓库。
Artifact 构建产物，如 JAR、镜像、测试报告；可归档、上传至制品库或传给下游任务。
Executor Agent 上可并行执行构建的槽位；槽位不足时构建会排队。

常见 Job 类型

  • Freestyle Project：在 UI 中配置源码、Shell、构建后操作等，入门简单，但复杂流程难以版本化。
  • Pipeline：用 Jenkinsfile 或 UI 中的 Pipeline Script 描述流程，适用于 CI/CD 的主流方式。
  • Multibranch Pipeline：自动发现仓库中含 Jenkinsfile 的分支和 PR，适合持续开发的 Git 仓库。
  • Organization Folder：扫描一个 GitHub Organization 或 GitLab Group 下多个仓库，为每个含 Jenkinsfile 的仓库创建 Multibranch Pipeline。

一次构建的典型生命周期

触发（Webhook / 定时 / 手动）
  → 排队（等待合适的 Agent 和 Executor）
  → 检出指定 commit 或 PR merge ref
  → 依赖安装与静态检查
  → 单元测试 / 集成测试
  → 打包、构建镜像、归档制品
  → 部署到测试或生产环境
  → 上报结果（Git 平台、IM、邮件、制品库）

每一步的日志、耗时、失败位置和制品都可以在 Jenkins 的 Build 页面查看。Pipeline 支持失败后从某个 stage 重新执行（具体能力取决于脚本和插件），也支持并行 stage、条件执行和人工审批。

与 GitHub / GitLab 集成时的最低配置

以 Multibranch Pipeline 为例，需要准备：

  1. 安装并配置对应的分支来源插件：GitHub Branch Source 或 GitLab Branch Source 等。
  2. Jenkins 中配置凭据：推荐使用权限最小化的 App / Project Access Token 或 token；至少应能读取仓库、读取 PR 信息、回写 commit/PR 状态。
  3. 创建 Multibranch Pipeline：配置仓库来源、仓库选择方式和凭据。
  4. 设置 Branch Sources 的发现行为：例如发现所有分支、仅发现未合并 PR、PR 使用合并结果构建等。
  5. 仓库设置 Webhook：指向 Jenkins 提供的地址，并订阅 push 与 PR/MR 事件；配置 secret。
  6. 将 Jenkinsfile 提交到仓库：路径一般为根目录 Jenkinsfile，也可在 Job 中改为其他路径。
  7. 首次 Scan / 索引仓库：让 Jenkins 建立已有分支和 PR 对应的子 Job；之后由 Webhook 增量更新。

不同插件的 Webhook URL、事件名称和 UI 字段略有不同，因此应以团队实际使用的 Git 平台插件文档为准。

为什么有时 push 了却没有运行：排查顺序

  1. Git 平台的 Webhook delivery 是否成功：查看 HTTP 状态码、响应体与重试记录。
  2. Jenkins 是否可被 Git 平台访问：公网地址、反向代理、TLS 证书、网络策略和 Jenkins URL 配置都可能影响回调。
  3. Webhook 事件是否订阅正确：push 与 PR/MR 事件通常都需要。
  4. Jenkins 系统日志和 Multibranch 扫描日志：确认插件是否收到并识别了事件。
  5. Branch / PR discovery 规则：分支或 PR 可能被过滤，或已关闭、已合并。
  6. Jenkinsfile 路径与语法：目标 revision 中是否存在文件、能否被读取和解析。
  7. 构建是否正在排队或被限流：检查 Agent 在线状态、label、executor、并发限制和 quiet period。
  8. 凭据权限：凭据可能只能读代码，不能读取 PR 元数据或回写检查结果。

实践建议

  • 用 Multibranch Pipeline + Jenkinsfile 管理分支和 PR，避免为每个分支手工创建 Job。
  • PR 默认只做校验；生产部署应限制在受保护的目标分支或 tag，并配合审批。
  • 构建明确检出触发事件对应的 revision，不要用“当前分支最新代码”替代，确保结果可复现。
  • 凭据使用 Jenkins Credentials 管理，按最小权限授权；不要把 token、密码写进 Jenkinsfile 或日志。
  • 对依赖、镜像和制品使用缓存与专门的制品仓库；构建机器尽量无状态。
  • 通过 Git 平台的 required status checks / merge checks，把 Jenkins 的成功结果作为 PR 合并条件。
  • 定期升级 Jenkins LTS 与插件，清理不再使用的插件，并给 Controller 做配置与构建记录备份。

一句话总结

Git 平台的 Webhook 告诉 Jenkins“发生了什么”；Multibranch Pipeline 的发现规则决定“是否为这个分支或 PR 建构建”；Jenkinsfile 决定“这次构建具体执行什么”。

复习与应用

对一次 feature push 和 PR 事件逐步说明 Job 的创建与排队；检查重复构建是否来自多条触发路径。
