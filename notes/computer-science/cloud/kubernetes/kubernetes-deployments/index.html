Kubernetes Deployment

2026-03-24

#Cloud#Kubernetes

理解主线

Deployment 控制 ReplicaSet，ReplicaSet 控制 Pod。发布过程中，新旧副本按 maxSurge 与 maxUnavailable 的约束变化，Readiness 决定后端何时可接流量。

学习目标

学完本章后，应当能够：

  • 解释 Deployment、ReplicaSet 与 Pod 的三级控制关系。
  • 计算 maxSurge、maxUnavailable 对发布容量和可用副本的影响。
  • 观察发布进度，识别 Pending、探针失败与 ProgressDeadlineExceeded。
  • 根据用户侧 SLI 决定继续、暂停或回滚，而不是只看 rollout status。

每次修改 Pod template 都会产生一个新 ReplicaSet。滚动发布本质上是新旧 ReplicaSet 在容量约束下此消彼长，Readiness 决定新 Pod 何时能承接流量。

概念

ReplicaSet 是一种 Pod 控制器，持续维持符合条件的 Pod 副本数达到期望值。

Deployment 是更高层的声明式控制器：Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod。

图：Deployment 滚动发布期间新旧 ReplicaSet 的扩缩容、发布观测与回滚关系。

  • 用户向 API Server 提交 Deployment 的期望状态，例如镜像、Pod 模板和副本数。
  • Deployment Controller 通过 Reconcile 控制循环创建或调整 ReplicaSet。
  • ReplicaSet Controller 再通过独立的 Reconcile 控制循环创建或删除 Pod，使实际副本数收敛到期望值。
  • Deployment 并不直接启动容器；Pod 调度完成后，由目标 Node 上的 Kubelet 调用容器运行时启动容器。

ReplicaSet

ReplicaSet 作为 Pod 控制器，具备以下能力：

  • 自愈。
  • 确保所需数量的 Pod 可用。
  • 提供容错能力。
  • 可用于扩缩容 Pod。
  • 依赖 Pod 模板。
  • 无需直接创建 Pod。
  • 通常由 Deployment 使用。

Deployment

Deployment 通过以下方式管理 Pod：

  • 通过 ReplicaSet 管理 Pod。
  • 扩/缩容 Deployment 会改变其活动 ReplicaSet 的期望副本数，随后由 ReplicaSet 协调 Pod 数量。
  • 滚动更新会创建新的 ReplicaSet，逐步扩容新版本、缩容旧版本。
  • 提供发布历史和回滚功能。
  • 通过 selector 与 Pod 模板标签建立归属关系；Kubernetes 还会添加 pod-template-hash 标签以区分 ReplicaSet 版本。
  • 所谓“零停机”不是天然保证：还依赖正确的 Readiness Probe、滚动更新策略、足够的集群容量以及应用自身的优雅启动和终止能力

一个 Deployment 可以对应多个 ReplicaSet，但在稳定状态下，通常只有最新的 ReplicaSet 持有 Pod，旧 ReplicaSet 会缩容到 0。

关系是：

Deployment
├── ReplicaSet revision 1 → 0 个 Pod
├── ReplicaSet revision 2 → 0 个 Pod
└── ReplicaSet revision 3 → 多个 Pod
                         ├── Pod
                         ├── Pod
                         └── Pod

所以一个 ReplicaSet 管理多个相同模板的 Pod，不是一个 ReplicaSet 对应一个 Pod。

例如：

spec:
  replicas: 3

稳定状态下通常是：

Deployment
└── ReplicaSet
    ├── Pod 1
    ├── Pod 2
    └── Pod 3

ReplicaSet 的职责就是确保符合其 Pod 模板的 Pod 数量始终等于期望副本数。删除其中一个 Pod 后，ReplicaSet 会再创建一个。

为什么会有多个 ReplicaSet

每次修改 Deployment 的 spec.template，例如修改镜像：

spec:
  template:
    spec:
      containers:
      - name: app
        image: app:v2

Deployment 都会创建一个新的 ReplicaSet。旧 ReplicaSet 默认不会立即删除，而是保留用于查看发布历史和回滚。

app:v1 → ReplicaSet A
app:v2 → ReplicaSet B
app:v3 → ReplicaSet C

旧 ReplicaSet 通常显示：

DESIRED   CURRENT   READY
0         0         0

Deployment 默认通过 revisionHistoryLimit 保留最多 10 个旧 ReplicaSet：

spec:
  revisionHistoryLimit: 10

滚动更新时不止一个 ReplicaSet 有 Pod

Deployment 正在滚动更新时，新旧 ReplicaSet 会同时持有 Pod：

ReplicaSet v1 → 2 个旧 Pod
ReplicaSet v2 → 2 个新 Pod

随后逐渐变为：

ReplicaSet v1 → 0 个 Pod
ReplicaSet v2 → 4 个 Pod

Pod 数量的变化由以下参数控制：

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 1

因此，“只有一个 ReplicaSet 有 Pod”只是发布完成后的稳定状态。在滚动更新、回滚或发布异常期间，多个 ReplicaSet 都可能有正在运行的 Pod。

还可以这样记：

Deployment 管理版本和发布过程，ReplicaSet 管理某个版本的多个 Pod，Pod 负责实际运行容器。

具体所有权关系是：

Deployment
    │ ownerReferences
    ▼
ReplicaSet
    │ ownerReferences
    ▼
多个 Pod

kubectl get rs 看到的多个 ReplicaSet，就是 Deployment 历次 Pod 模板版本留下的发布记录。

创建 Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
  labels:
    app: my-nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-nginx
  template:
    metadata:
      labels:
        app: my-nginx
    spec:
      containers:
      - name: frontend
        image: nginx:alpine
        ports:
        - containerPort: 80
        resources:
          requests:
            memory: "64Mi"
            cpu: "100m" #100
          limits:
            memory: "128Mi"
            cpu: "250m"

kubectl

创建

# 使用 `--filename` 或 `-f` 创建 Deployment
kubectl create -f [yaml_name.yaml]
# 创建 Deployment 或应用变更
kubectl apply -f [yaml_name.yaml]
# 希望后续使用 `kubectl apply`
kubectl create -f [yaml_name.yaml] --save-config

kubectl apply 更常用；kubectl create 则会在资源已存在时失败，避免意外覆盖既有资源。

查询

kubectl get deployment
# 显示标签
kubectl get deployment --show-labels
# 获取带指定标签的 Deployment
kubectl get deployment -l app=[label_name]

删除

kubectl delete deployment [deployment_name]

扩缩容

kubectl scale deployment [deployment_name] --replicas=[number]
# 使用 YAML 文件
kubectl scale -f [yaml_name.yaml] --replicas=[number]

也可以在 YAML 中声明 replicas：

spec:
  replicas: 3
  selector:
    tier: frontend

零停机发布

零停机发布旨在将软件更新部署到生产环境时不影响终端用户。

常见策略

  • 滚动更新（Rolling Update）
  • 蓝绿发布（Blue-Green Deployment）
  • 金丝雀发布（Canary Deployment）
  • 回滚（Rollback）

滚动发布

更新 Deployment 的 Pod 模板时，Deployment Controller 会创建新的 ReplicaSet，并依据 maxSurge 和 maxUnavailable 逐步扩容新 ReplicaSet、缩容旧 ReplicaSet。只有通过 Readiness Probe 的新 Pod 才应接收流量。

安全发布与回滚

spec:
  minReadySeconds: 30
  progressDeadlineSeconds: 600
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 25%

maxUnavailable: 0 适合副本数较少且不能降低在线副本数的服务，但前提是集群有额外容量；资源紧张时新副本可能 Pending，发布会停滞。

kubectl rollout status deployment/<name> -n <ns> --timeout=10m
kubectl rollout history deployment/<name> -n <ns>
kubectl rollout undo deployment/<name> -n <ns> --to-revision=<revision>

发布前明确基线与停止条件（错误率、P99、可用副本数）；发布中观察新旧版本、Readiness、5xx 和资源饱和度；回滚后验证核心 SLI 回归，而不是只看命令成功。

发布卡住 Runbook

kubectl get deployment,replicaset,pod -n <ns> -l app=<app>
kubectl describe deployment/<name> -n <ns>
kubectl rollout status deployment/<name> -n <ns> --timeout=5m
kubectl get events -n <ns> --sort-by=.lastTimestamp
  1. 比较 replicas、updatedReplicas、readyReplicas 与 availableReplicas。
  2. 新 Pod 未创建时检查 ResourceQuota、准入策略和控制器事件。
  3. 新 Pod Pending 时检查资源、调度约束和 PVC。
  4. 新 Pod Running 但未 Ready 时检查探针、配置和依赖。
  5. 若核心 SLI 越过停止线，先暂停或回滚，再保留失败 Pod 和日志分析根因。
kubectl rollout pause deployment/<name> -n <ns>
kubectl rollout undo deployment/<name> -n <ns>

实践与验收

  • 以 3 个副本部署应用，设置 maxUnavailable: 0、maxSurge: 1，观察新旧 ReplicaSet 数量变化。
  • 发布一个 Readiness 永远失败的版本，确认旧版本仍服务且发布停滞。
  • 查看 revision 历史并回滚，验证镜像、可用副本及请求成功率恢复。
  • 记录发布前基线、停止条件、操作时间线和发布后观察窗口。

生产基线

  • 镜像使用不可变版本或 digest，Pod template 变更可审计。
  • 正确配置 Readiness、资源请求、优雅终止、滚动策略和峰值容量。
  • 关键服务至少两个副本并跨故障域分散；维护保护见 高可用与发布保护。
  • 发布系统具备暂停、回滚和 SLI 门禁，回滚步骤经过演练。
