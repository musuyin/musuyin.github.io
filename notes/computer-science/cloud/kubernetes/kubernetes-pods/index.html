Kubernetes Pod

2026-03-10

#Cloud#Kubernetes

理解主线

Pod 是调度和替换的基本单位，控制器负责副本持续存在。故障判断要联合 phase、容器状态、Condition、事件和日志，不能只解释 kubectl 的 STATUS 显示。

学习目标

学完本章后，应当能够：

  • 解释 Pod 与容器、Node、控制器之间的关系，以及 Pod 为什么是可替换而非可修复的实例。
  • 区分 Pod phase、容器状态、Condition 和事件，不只凭 STATUS 一列判断故障。
  • 正确选择 Startup、Readiness 与 Liveness Probe，并理解错误探针可能放大故障。
  • 根据事件、当前日志、上一次容器日志和退出码定位 Pending、CrashLoopBackOff、OOMKilled 等问题。

Pod 是共享网络与存储命名空间的一组容器，也是 Kubernetes 调度和故障替换的最小单位；真正维持副本的是控制器，而不是 Pod 自己。

概念

图：Pod 从 Pending、Running 到终止状态的主要分支，以及探针、容器重启和控制器替代 Pod 的边界。

Pod 是 Kubernetes 应用的基本执行单元。

  • 它是 Kubernetes 对象模型中可创建和部署的最小、最简单单元。
  • Pod 为容器提供运行环境，将应用的不同组成部分（服务器、缓存、API、数据库等）组织在一起。
  • 同一 Pod 的容器共享网络命名空间和挂载卷，但默认不共享进程或内存命名空间。
  • 通常通过 Deployment 等工作负载控制器增加 Pod 副本，以实现水平扩缩容。
  • Pod 对象不会被“复活”：Pod 被删除或失效后，控制器可能创建一个具有新 UID、IP 和生命周期的新 Pod 作为替代
  • 容器异常时，Kubelet 会根据 restartPolicy 在同一个 Pod 内重启容器；Node 故障或 Pod 被驱逐时，Deployment、StatefulSet 等控制器才会在合适的 Node 上创建替代 Pod

网络

  • Pod 内的 Container 共享同一个网络命名空间（同一 IP 与端口空间）。
  • Pod 内的 Container 使用相同的本地回环网络接口（localhost）。
  • 同一 Pod 内的 Container 进程必须绑定不同端口。
  • 不同 Pod 中的 Container 可以复用相同端口。

Pod 不会跨多个 Node。

kubectl

创建

  1. kubectl run
  2. 使用 YAML 文件执行 kubectl create/apply
# 使用镜像创建独立 Pod
kubectl run [pod_name] --image=[image_name:image_version]

现代版本的 kubectl run 默认创建独立 Pod，不会创建 Deployment。生产工作负载通常使用 Deployment YAML 或 kubectl create deployment。

暴露端口

默认情况下，Pod 和容器只能在 Kubernetes 集群内部访问。

kubectl port-forward：将容器端口临时转发到本地。

kubectl port-forward [pod_name] [external_port:internal_port]

删除

删除独立创建的 Pod 后，Pod 不会自动重建：

kubectl delete pod [pod_name]

如果 Pod 由 Deployment、StatefulSet、DaemonSet、Job 等控制器管理，控制器发现实际副本数少于期望值后，会创建一个新的替代 Pod。此时若要停止 Deployment 管理的工作负载，应删除 Deployment 或将副本数缩容为 0：

kubectl delete deployment [deployment_name]
kubectl scale deployment [deployment_name] --replicas=0

Pod 健康检查

Kubernetes 通过 Probe（探针）判断 Pod 中容器的健康状态。

Probe 是 kubelet 定期对容器执行的诊断检查。

Probe 作用
Liveness Probe 判断容器是否仍然存活；连续失败达到阈值后，Kubelet 终止该容器，并根据 restartPolicy 决定是否重启
Readiness Probe 判断容器当前是否可以接收流量；失败时 Pod 会从对应 Service 的 EndpointSlice 中移除，但容器不会因此自动重启
Startup Probe 保护启动较慢的容器；在其成功前，Liveness 和 Readiness 检查不会生效

Pod 级别的 restartPolicy 默认为 Always，作用对象是 Pod 内的容器。容器重启通常发生在原 Pod 内，并不等于删除并重建 Pod。

检查方式

  • ExecAction：在容器内执行命令。
  • TCPSocketAction：对容器 IP 的指定端口进行 TCP 检查。
  • HTTPGetAction：向容器发送 HTTP GET 请求。

探针与资源配置示例

spec:
  containers:
  - name: app
    image: example/app:1.0.0
    resources:
      requests: {cpu: "250m", memory: "256Mi"}
      limits: {cpu: "1", memory: "512Mi"}
    startupProbe:
      httpGet: {path: /healthz, port: 8080}
      failureThreshold: 30
      periodSeconds: 5
    readinessProbe:
      httpGet: {path: /readyz, port: 8080}
      periodSeconds: 5
    livenessProbe:
      httpGet: {path: /healthz, port: 8080}
      periodSeconds: 10
  • readinessProbe 应反映“能否安全接流”，不要只检查进程存在。
  • 慢启动应用优先使用 startupProbe，避免 liveness 在初始化期间反复重启容器。
  • OOMKilled、频繁重启和 CPU throttling 都不能仅靠“调大 limit”处理；需结合应用内存、GC、并发与流量判断。

CrashLoopBackOff 排查

kubectl describe pod/<pod> -n <ns>
kubectl logs pod/<pod> -n <ns> --previous
kubectl get pod/<pod> -n <ns> -o jsonpath='{.status.containerStatuses[*].state}'

依次确认退出码、上一次容器日志、环境变量/挂载配置、探针路径及依赖连通性；不要把删除 Pod 当作根因修复。

  • Success：成功
  • Failure：失败
  • Unknown：未知
apiVersion: v1
kind: Pod
metadata:
  name: my-nginx
  labels:
    app: nginx
    rel: stable
spec:
  containers:
  - name: my-nginx
    image: nginx:alpine
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "300m"
    ports:
    - containerPort: 80
    livenessProbe:
      httpGet:
        path: /index.html
        port: 80
      initialDelaySeconds: 15
      timeoutSeconds: 2 # Default is 1
      periodSeconds: 5 # Default is 10
      failureThreshold: 1 # Default is 3
    readinessProbe:
      httpGet:
        path: /index.html
        port: 80
      initialDelaySeconds: 3
      periodSeconds: 5 # Default is 10
      failureThreshold: 1 # Default is 3
  • httpGet：检查 80 端口的 /index.html。
  • initialDelaySeconds：初始化后等待 15 秒再开始检查。
  • timeoutSeconds：单次检查 2 秒后超时。
  • periodSeconds：每 5 秒检查一次。
  • failureThreshold: 连续失败达到该次数后，当前 Probe 才被判定为失败
    • Liveness 失败会触发容器终止与重启流程
    • Readiness 失败只会停止接收 Service 流量

资源定义

apiVersion: v1
kind: Pod
metadata:
  name: test
spec:
  containers:
  - name: test
    image: nginx:alpine
  • apiVersion：Kubernetes API 版本。
  • kind：Kubernetes 资源类型。
  • metadata：Pod 的元数据。
  • spec：Pod 的规格/蓝图。
    • 包含将在 Pod 中运行的容器信息。

创建

使用 YAML 文件：

kubectl create -f [yaml_name.yaml] --dry-run --validate=true
# 若 Pod 已存在，该命令会报错
kubectl create -f [yaml_name.yaml]

更新

若资源不存在则创建；若存在则按 YAML 将变更应用到 Pod。

kubectl apply -f [yaml_name.yaml]

如后续希望使用 kubectl apply：

kubectl create -f [yaml_name.yaml] --save-config

--save-config 会将资源配置保存到 annotations 中。

也可以使用 kubectl edit / kubectl patch 对 Pod 进行原地、非中断式修改。

删除

使用创建该 Pod 的 YAML 文件删除它：

kubectl delete -f [yaml_name.yaml]

YAML 基础

  • YAML 由映射（map）和列表（list）组成。
  • 缩进具有语义。
  • 始终使用空格，不使用 Tab。
key: value
map:
  key1: value
  key2:
    subKey: value
list:
  - item1
  - item2
listMap:
  - map1: value
    map1p: value
  - map2: value
    map2p: value

YAML 核心结构

K8s 所有资源（Pod/Deployment/Service 等）的 YAML 配置遵循统一核心结构，分为 4 个基础段：

apiVersion: v1 # API 版本（必选）
kind: Pod	   # 资源类型（必选）
metadata:	   # 资源元数据（必选）
  name: my-nginx
  labels:
    app: nginx
    rel: stable
spec:		   # 资源规格（必选，不同资源类型字段不同）
  containers:
  - name: my-nginx
    image: nginx:alpine
    ports:
    - containerPort: 80
    resources: {}

常用命令：

# 基础命令
kubectl create -f nginx.pod.yml --save-config
kubectl describe pod [pod-name]
kubectl apply -f nginx.pod.yml
kubectl exec -it [pod-name] -- sh
kubectl edit -f nginx.pod.yml
kubectl delete -f nginx.pod.yml

# 进入容器：
kubectl exec -it [pod-name] -- sh

核心通用属性详解

apiVersion

API 版本

取值示例 适用资源类型 说明
v1 Pod/Service/Namespace/ConfigMap/Secret 核心基础资源的稳定版本
apps/v1 Deployment/StatefulSet/DaemonSet 应用工作负载相关资源
batch/v1 Job/CronJob 批处理任务相关资源
networking.k8s.io/v1 Ingress/NetworkPolicy 网络相关资源

kind

资源类型

取值 中文名称 核心作用
Pod 最小部署单元 运行容器的最小载体
Deployment 无状态部署 管理 Pod 副本、自动重启、滚动更新
Service 服务发现 暴露 Pod 网络访问、负载均衡
Namespace 命名空间 资源逻辑隔离
ConfigMap 配置映射 存储非敏感配置数据
Secret 密钥 存储敏感数据（密码/令牌等）
StatefulSet 有状态部署 管理有状态应用（固定网络标识、持久化存储）
DaemonSet 守护进程 集群所有/指定 Node 上运行一个 Pod 副本
Job 一次性任务 执行完成后终止的任务
CronJob 定时任务 按时间规则重复执行 Job
Ingress 入口规则 集群外部访问集群内服务的规则

metadata

资源元数据

metadata:
  name: string               # 资源名称（必选，同一命名空间内唯一）
  namespace: string          # 所属命名空间（可选，默认 default）
  labels:                    # 标签（可选，键值对，用于资源筛选/关联）
    key1: value1
    key2: value2
  annotations:               # 注解（可选，键值对，存储非标识性元数据）
    key1: value1
  uid: string                # 唯一标识（自动生成，无需配置）
  • labels 核心用途：Service 关联 Pod、Deployment 管理 Pod、资源筛选（kubectl get pods -l key=value）
  • annotations 典型场景：存储资源描述、运维备注、第三方工具配置

metadata 不是容器的运行配置，而是 Kubernetes 用来“识别、查找和管理资源”的信息。它主要被 Kubernetes 控制面、控制器和 kubectl 使用，所以业务代码里通常看不到。

以 Pod 为例：

metadata:
  name: my-nginx
  namespace: demo
  labels:
    app: nginx
    version: v1
  annotations:
    maintainer: musuyin

各字段的作用：

  • name：资源名称。执行 kubectl get pod my-nginx -n demo 时已经在使用它。
  • namespace：资源所在的逻辑空间。demo/my-nginx 和 default/my-nginx 是两个不同对象。
  • labels：可被筛选和关联的标签，是真正参与系统行为的 metadata。
  • annotations：提供给控制器或工具的附加配置，不能用于 selector。
  • uid：API Server 自动生成的唯一身份。Pod 删除后即使创建同名 Pod，UID 也不同。
  • ownerReferences：记录 Pod 由哪个 ReplicaSet 等对象创建，用于级联删除和垃圾回收。
  • finalizers：要求控制器完成清理后，资源才能真正删除。

最典型的实际使用是 Service 根据 labels 找 Pod：

apiVersion: v1
kind: Pod
metadata:
  name: my-nginx
  labels:
    app: nginx
spec:
  containers:
  - name: nginx
    image: nginx
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx

这里的关联关系是：

Pod metadata.labels.app = nginx
                ↓ 匹配
Service spec.selector.app = nginx
                ↓
流量发送给该 Pod

Deployment 中则要注意三个不同位置：

metadata:
  name: nginx                 # 标识 Deployment 自身
  labels:
    app: nginx
spec:
  selector:
    matchLabels:
      app: nginx              # ReplicaSet 用来匹配 Pod
  template:
    metadata:
      labels:
        app: nginx            # 创建出来的 Pod 获得这个标签
  • name 和 namespace 被 API、kubectl 隐式使用。
  • labels 被 Service、Deployment、NetworkPolicy 等资源使用。
  • annotations 通常由 Ingress、监控、Service Mesh 等控制器读取。
  • metadata 默认不会进入容器；若程序需要读取，可以通过 Downward API 注入。

故障排查 Runbook

kubectl get pod/<pod> -n <ns> -o wide
kubectl describe pod/<pod> -n <ns>
kubectl logs pod/<pod> -n <ns> --all-containers
kubectl logs pod/<pod> -n <ns> --all-containers --previous
kubectl get pod/<pod> -n <ns> -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\t"}{.state.waiting.reason}{"\t"}{.lastState.terminated.reason}{"\t"}{.lastState.terminated.exitCode}{"\n"}{end}'

按阶段缩小范围：

  • 一直 Pending：先看 Scheduler 事件，再查 requests、taint、亲和性与 PVC。
  • ImagePullBackOff：核对镜像名、标签或 digest、Registry 网络与拉取凭据。
  • CrashLoopBackOff：查看 --previous 日志、退出码、命令参数、配置和启动探针。
  • Running 但未 Ready：检查 Readiness Probe、依赖和应用监听地址。
  • OOMKilled：确认容器内存峰值与 limit，再修复内存使用或重新评估资源，不要只反复重启。

实践与验收

  • 创建一个启动命令必然失败的 Pod，通过上一次日志与退出码找出原因。
  • 配置错误的 Readiness Probe，验证 Pod 可以 Running 但不会进入 Service 后端。
  • 配置很小的内存 limit 触发 OOM，记录 lastState.terminated.reason。
  • 删除由 Deployment 管理的 Pod，观察旧 Pod 消失且新 UID 的 Pod 被创建。

验收标准：能够区分“容器重启”和“Pod 被替换”，并在不先删除现场的情况下收集事件、日志、状态和资源声明。

生产基线

  • 应用由合适的控制器管理，不直接运行孤立 Pod。
  • 配置 requests，并按风险决定 limits；监控重启、OOM、CPU throttling 与 Pending 时长。
  • 三类探针只检查各自语义，Liveness 不依赖容易抖动的外部服务。
  • 支持 SIGTERM 和优雅退出，调试所需权限与工具受控。
