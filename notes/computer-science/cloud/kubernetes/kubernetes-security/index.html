Kubernetes 安全基线

2026-08-13

#Kubernetes#Security#SRE

理解主线

按 API 身份与授权、准入、工作负载、网络和数据建立纵深防御。Namespace 是管理边界，安全效果需要 RBAC、运行时限制、网络策略与秘密管理共同提供。

学习目标

学完本章后，应当能够：

  • 从 API 访问、工作负载、网络、供应链和数据五个层面建立纵深防御。
  • 为人和 ServiceAccount 设计最小权限 RBAC，并识别可间接提权的高风险权限。
  • 使用 Restricted 风格的 SecurityContext、Pod Security Admission 与 NetworkPolicy。
  • 设计镜像验证、Secret 保护、审计检测和安全事件响应流程。

心智模型：安全不是单个开关，而是假设某一层会失守后，其他层仍能限制影响范围并留下可调查证据。

安全模型

图：从镜像供应链、API 准入、工作负载身份、运行时、网络和密钥到检测响应的纵深防御体系。

Kubernetes 安全至少包含四层：

层次 主要控制
API 访问 身份认证、RBAC、准入控制、审计
工作负载 ServiceAccount、SecurityContext、Pod Security Admission
网络 NetworkPolicy、入口 TLS、控制面网络隔离
供应链与数据 镜像签名/扫描、Secret 加密与外部密钥系统

Namespace 只是管理边界，不等于安全边界；多租户环境还需考虑独立 Node、沙箱运行时甚至独立集群。

RBAC

RBAC 的四个核心对象：

  • Role：Namespace 范围权限。
  • ClusterRole：集群范围权限，也可被 RoleBinding 引用后限制在某 Namespace 使用。
  • RoleBinding：在一个 Namespace 中绑定权限。
  • ClusterRoleBinding：在全集群绑定权限。
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: config-reader
  namespace: production
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  resourceNames: ["app-config"]
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: api-config-reader
  namespace: production
subjects:
- kind: ServiceAccount
  name: api
  namespace: production
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: config-reader

最小权限原则：

  • 避免 resources: ["*"]、verbs: ["*"] 和不必要的 ClusterRoleBinding。
  • create pods、pods/exec、读取 Secret、创建 RoleBinding、impersonate 等可能间接获取更高权限，应重点审计。
  • 不要通过把用户加入 system:masters 解决日常授权问题。
  • 将人类身份与工作负载身份分开，优先使用短期凭据。
kubectl auth can-i get secrets --as=system:serviceaccount:production:api -n production
kubectl auth can-i --list --as=system:serviceaccount:production:api -n production

ServiceAccount

每个 Namespace 都有 default ServiceAccount，但业务应使用专用 ServiceAccount。若 Pod 不需要访问 Kubernetes API，关闭自动挂载 Token：

apiVersion: v1
kind: ServiceAccount
metadata:
  name: api
  namespace: production
automountServiceAccountToken: false
---
apiVersion: v1
kind: Pod
metadata:
  name: api
  namespace: production
spec:
  serviceAccountName: api
  automountServiceAccountToken: false
  containers:
  - name: api
    image: example/api@sha256:<digest>

现代 Kubernetes 默认使用有期限、与 Pod 绑定的投射 Token。不要依赖长期 ServiceAccount Token Secret，也不要将 Token 导出后长期复用。

SecurityContext

SecurityContext 控制 Pod/容器运行时权限。面向普通 Linux 应用的推荐基线：

spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: api
    image: example/api@sha256:<digest>
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
      runAsUser: 10001
      runAsGroup: 10001

还应避免：

  • privileged: true。
  • hostNetwork、hostPID、hostIPC。
  • 不必要的 hostPath 和设备挂载。
  • 增加 SYS_ADMIN、NET_ADMIN 等高风险 capability。
  • 以 root 运行，或允许写入根文件系统。

确需特权的 CNI、CSI、监控等系统组件应使用独立 Namespace、专用 Node、精确 RBAC 和额外审计。

Pod Security Admission

Pod Security Standards 定义三个级别：

  • privileged：不限制，适合受信任的系统组件。
  • baseline：阻止已知的高风险配置。
  • restricted：更严格的加固基线，适合普通应用。

Pod Security Admission 使用 Namespace label 执行 enforce、audit、warn：

kubectl label namespace production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/audit-version=latest \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/warn-version=latest

上线顺序建议：先对现有 Namespace 启用 warn/audit 并修复，再启用 enforce。生产环境可以将版本固定到集群版本，升级时评估标准变化后再更新，而不是无条件使用 latest。

NetworkPolicy

安全基线采用 Namespace 默认拒绝，再按业务流量放行：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]

需要显式允许：

  • 到集群 DNS 的 UDP/TCP 53。
  • 来自 Ingress/Gateway Controller 的入口流量。
  • 必要的数据库、消息队列、身份服务和外部 API。
  • 监控抓取和日志发送。

NetworkPolicy 通常只控制 L3/L4，不能代替应用认证、TLS 或 API 授权；并确认所用 CNI 支持策略执行。

镜像与供应链安全

  • 使用不可变 digest：image@sha256:...，避免生产使用 latest。
  • 从受控 Registry 拉取，限制 Node 到公共 Registry 的出口。
  • 在 CI 中扫描 OS 包与语言依赖漏洞，定义严重级别和修复 SLA。
  • 生成 SBOM，保存镜像构建来源和签名，使用准入策略验证来源、签名和允许仓库。
  • 使用最小基础镜像、多阶段构建、非 root 用户，不把 shell/调试工具带进不需要它们的生产镜像。
  • Registry 凭据使用 imagePullSecrets 或云工作负载身份，并定期轮换。

镜像扫描只能发现已知问题，不能替代代码审查、运行时限制和网络隔离。

Secret 与外部密钥管理

Kubernetes Secret 的 Base64 不是加密。基础要求：

  • API Server 到 etcd 启用 TLS，Secret 在 etcd 中启用 encryption at rest。
  • RBAC 限制读取 Secret、创建可挂载 Secret 的 Pod、exec 和调试容器权限。
  • Git 中只存密钥引用或加密后的声明，不存明文/Base64 Secret。
  • 建立轮换、审计、吊销和泄露响应流程。

External Secrets Operator、Secrets Store CSI Driver 等是生态组件，不是 Kubernetes 核心内置功能。典型流程是工作负载通过集群身份从 Vault 或云 KMS/Secret Manager 获取密钥，减少长期密钥落入 Git 和人工操作。

选型时明确：

  • 是否将外部密钥同步为 Kubernetes Secret；同步后仍受 Kubernetes Secret 的安全边界约束。
  • 密钥如何轮换，应用是 reload、重启还是支持双凭据并存。
  • 外部密钥系统不可用时，新 Pod 和现有 Pod 的行为。
  • Controller/CSI Driver 自身的权限、审计和高可用。

安全检查命令

# RBAC 与身份
kubectl get serviceaccount,role,rolebinding -A
kubectl get clusterrolebinding
kubectl auth can-i --list -n <ns>

# Pod 权限与镜像
kubectl get pod -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{.spec.serviceAccountName}{"\t"}{range .spec.containers[*]}{.image}{" "}{end}{"\n"}{end}'

# Namespace 安全标签与网络策略
kubectl get namespace --show-labels
kubectl get networkpolicy -A

安全事件 Runbook

  1. 保存时间线、审计日志、受影响身份、Pod、Node、镜像 digest 和网络连接证据。
  2. 控制影响：撤销/轮换凭据，隔离工作负载或 Node；避免先删除所有证据。
  3. 识别攻击路径：入口 → Pod 权限 → ServiceAccount/RBAC → Secret → Node/控制面。
  4. 从可信镜像和配置重建，不在疑似被入侵容器内“修复”。
  5. 验证持久化机制、横向移动和数据访问范围。
  6. 恢复后补充准入策略、检测、Runbook 与演练。

生产基线

  • 默认拒绝、最小权限、专用 ServiceAccount、无 API 需求则不挂载 Token。
  • 普通应用满足 Restricted 标准，使用非 root、默认 seccomp、只读根文件系统并删除 capabilities。
  • Namespace 默认拒绝网络，出口采用允许列表。
  • 镜像固定 digest、扫描、签名并限制来源。
  • Secret 启用静态加密，优先对接外部密钥系统并自动轮换。
  • 启用 Kubernetes Audit Log，并为高风险 RBAC、Secret 读取、exec、特权 Pod 和准入拒绝告警。

实践与验收

  • 创建只能读取一个指定 ConfigMap 的 ServiceAccount，并用 kubectl auth can-i 验证正反权限。
  • 在测试 Namespace 先启用 Restricted 的 warn/audit，再修复工作负载并切换 enforce。
  • 配置入站、出站默认拒绝策略，只开放应用所需流量。
  • 检查镜像 digest、ServiceAccount Token、特权配置与 Secret 读取权限，形成审计记录。
  • 桌面推演一次凭据泄露：保全证据、隔离、轮换、重建、验证和复盘。

复习与应用

选一个 ServiceAccount，检查它能创建什么、能读取什么、是否可能间接提权，再检查运行中的 Pod 实际使用了哪些权限。
