Kubernetes Service

2026-03-24

#Cloud#Kubernetes

理解主线

Service 给动态 Pod 集合提供稳定访问入口，selector 和就绪状态影响后端集合，具体数据面负责转发。端口与后端关系必须联合 EndpointSlice 查看。

学习目标

学完本章后，应当能够：

  • 解释 Service、EndpointSlice、Pod Readiness 与 kube-proxy/数据面的关系。
  • 区分 port、targetPort、nodePort 和 containerPort，避免端口映射混淆。
  • 根据访问范围选择 ClusterIP、NodePort、LoadBalancer 或 ExternalName。
  • 从调用方逐跳验证 DNS、ClusterIP、EndpointSlice 与 Pod 端口，定位无后端和连接失败。

Service 是稳定的服务地址和后端集合抽象。它不启动 Pod，也不会修复应用；selector 与 Readiness 决定 EndpointSlice 中有哪些可接流量的后端。

概念

Service 为访问一个或多个 Pod 提供统一入口。

图：集群内外请求经 DNS、Ingress/Gateway、Service、EndpointSlice 到 Ready Pod 的链路，以及 CNI 与 NetworkPolicy 所处位置。

不能依赖 Pod IP：

  • Pod 是短暂的（ephemeral），生命周期可能很短。
  • Pod IP 地址可能发生变化。
  • Pod 可以水平扩缩容，每个 Pod 都有自己的 IP 地址。
  • Pod 在被调度后才获得 IP，客户端无法预先获知该地址。

Service 的作用

  • Service 为调用方屏蔽 Pod IP。
  • 在四层（TCP/UDP/SCTP）将流量负载均衡到就绪的后端 Pod。
  • 带 selector 的 Service 通过标签选择 Pod；控制面会将合格后端记录在 EndpointSlice 对象中。
  • API Server 分配 Service 的 ClusterIP。
    • 在传统实现中，kube-proxy 监听 Service 和 EndpointSlice，并在每个 Node 上维护 iptables、IPVS 或 nftables 转发规则；它不是创建一台真实的代理服务器。
  • Service 通常是相对稳定的 API 对象，但仍然可以被修改或删除；ClusterIP 在 Service 生命周期内保持稳定。
  • Service 不直接“绑定”Pod。Pod 是否成为后端取决于标签选择器、Readiness 状态以及对应的 EndpointSlice。

调用 Service

Service 使用标签（label）关联 Pod。

Service 类型

Service 可按以下方式定义：

Type Role
ClusterIP 在集群内部 IP 上暴露服务（默认）；适用于微服务间调用
NodePort 在每个 Node 的 IP 上以静态端口暴露服务；适用于本地学习和测试
LoadBalancer 申请外部 IP 作为服务负载均衡器；云环境中通常由云厂商提供
ExternalName 将 Service 映射到一个 DNS 名称；较少使用

ClusterIP Service

  • Service 的 ClusterIP 仅在集群内部暴露，无法从集群外直接路由访问。
  • 集群内能访问 Service 网络的数据面组件通常都可访问 ClusterIP，并不只限于 Pod。
  • ClusterIP 为一组动态变化的 Pod 后端提供稳定的虚拟 IP 与 DNS 名称。

NodePort Service

  • 在每个 Node 的 IP 上通过静态端口暴露 Service。
  • 从端口范围中分配端口（默认 30000-32767）。
  • 每个 Node 都会转发该端口的流量。

LoadBalancer Service

  • 将 Service 暴露到集群外部。
  • 适合与云厂商负载均衡器结合使用。
  • 通常会同时创建 NodePort 和 ClusterIP Service。
  • 每个 Node 转发分配端口的流量。

  • LoadBalancer Service 通常工作在四层，按 IP、端口、TCP/UDP 转发。
  • Ingress 工作在七层，理解 HTTP/HTTPS，可以按域名和路径路由。

而且 Ingress 自己不能直接接收流量，必须部署 Ingress Controller。Ingress Controller 通常又通过一个 LoadBalancer Service 暴露到集群外。

互联网
   │
   ▼
云 LoadBalancer
   │
   ▼
Ingress Controller
   │ 根据域名、路径路由
   ├── user-service
   ├── order-service
   └── payment-service

ExternalName Service

  • ExternalName Service 为集群内服务名提供一个外部 DNS 名称别名。
  • CoreDNS 通常为该 Service 返回 CNAME 记录；它不会创建 ClusterIP、EndpointSlice，也不会转发或代理任何流量。
  • 客户端最终直接连接解析得到的外部地址，因此协议、TLS 证书中的主机名以及部分 HTTP Host 头场景需要额外注意。
  • 修改 externalName 可以切换目标域名，而无需修改调用方配置。

创建 Service

端口转发

使用 kubectl port-forward 将本地端口转发到 Pod 端口。

# 本地监听 8080 端口并转发到 Pod 的 80 端口
kubectl port-forward pod/[pod_name] 8080:80
# 本地监听 8080 端口并转发到 Deployment 的 Pod
kubectl port-forward deployment/[deployment_name] 8080
# 本地监听 8080 端口并转发到 Service 的 Pod
kubectl port-forward service/[service_name] 8080

kubectl port-forward 主要用于临时调试，不是生产流量入口。生产环境通常根据需求使用 Service、Ingress 或 Gateway API；Service 是否直接暴露到集群外取决于其类型及底层基础设施。

YAML

服务连接

metadata:
  name: frontend # Service 名称；每个 Service 都会获得 DNS 记录

...
metadata:
  name: backend

frontend Pod 可通过 backend:port 访问 backend Pod。

NodePort

apiVersion: v1
kind: Service
metadata:
 name: nginx-nodeport
spec:
 type: NodePort
 selector:
    app: my-nginx
 ports:
 - port: 80
   targetPort: 80
   nodePort: 31000	# optionally set NodePort value (defaults between 30000-32767)

ClusterIP

apiVersion: v1
kind: Service
metadata:
 name: nginx-clusterip
spec:
 type: ClusterIP
 selector:
    app: my-nginx
 ports:
 - port: 8080
   targetPort: 80

LoadBalancer

apiVersion: v1
kind: Service
metadata:
 name: nginx-loadbalancer
spec:
 type: LoadBalancer
 selector:
    app: my-nginx
 ports:
  - name: "80"
    port: 80
    targetPort: 80

  - name: "443"
    port: 443
    targetPort: 443

ExternalName

apiVersion: v1
kind: Service
metadata:
 name: external-service # 其他 Pod 可使用该 FQDN 访问外部服务
spec:
 type: ExternalName # 将类型设为 ExternalName
 externalName: api.musuyin.com # DNS CNAME 目标；Service 不代理流量

kubectl

kubectl create -f [yaml_name.yaml]
kubectl apply -f [yaml_name.yaml]
kubectl delete -f [yaml_name.yaml]

# 进入 Pod 并测试 URL。若 Pod 内有多个容器，增加 `-c [container-name]` 指定容器。
kubectl exec [pod_name] -- curl -s http://podIP:port

Service 无法访问排查

# selector 是否选择到 ready 后端
kubectl get svc/<service> -n <ns> -o yaml
kubectl get pods -n <ns> -l <key>=<value> --show-labels
kubectl get endpointslice -n <ns> -l kubernetes.io/service-name=<service> -o yaml

# 从集群内验证 DNS 和 TCP/HTTP
kubectl run netcheck -n <ns> --rm -it --restart=Never --image=busybox:1.36 -- nslookup <service>

排查顺序：Service selector → Pod labels → Pod readiness → EndpointSlice → DNS → NetworkPolicy / 端口协议。EndpointSlice 没有 ready 地址时，优先检查标签和 Readiness，不要先怀疑 kube-proxy。

还应从同一调用方环境分别访问 Service 和 Pod IP：若 Pod IP 成功而 Service 失败，重点检查 Service/EndpointSlice 与数据面；两者都失败，重点检查应用监听、端口和网络策略。

实践与验收

  • 创建 Deployment 与 ClusterIP Service，从临时 Pod 通过短域名访问服务。
  • 故意写错 selector，观察 EndpointSlice 无后端并按 Runbook 修复。
  • 故意写错 targetPort，比较 DNS 正常、端点存在但连接失败的现象。
  • 让 Readiness Probe 失败，确认对应 Pod 不作为普通就绪后端接收流量。

验收标准：看到“Service 不通”时，能够明确回答失败发生在名称解析、后端发现、Service 转发、Pod 网络还是应用端口，而不是直接删除 Pod。

生产基线

  • Service selector 使用稳定业务标签，端口有名称且协议明确。
  • 入口服务限制 externalTrafficPolicy 等配置的变更范围，并评估客户端 IP、健康检查与流量分布。
  • 对空 EndpointSlice、连接错误和入口延迟建立监控。
  • NodePort 不作为默认公网暴露方案；外部入口与网络策略见 网络进阶。
