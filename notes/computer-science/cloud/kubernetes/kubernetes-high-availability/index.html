Kubernetes 高可用与发布保护

2026-08-13

#Kubernetes#SRE#Availability

理解主线

冗余只有在故障域独立、剩余容量足够、流量切换正确时才形成高可用。PDB、拓扑约束、探针与优雅终止保护不同环节，必须通过发布和维护演练组合验证。

学习目标

学完本章后，应当能够：

  • 从故障域、容量、发布、维护和依赖角度评估可用性，而不只看副本数。
  • 正确组合 PDB、Topology Spread、滚动策略、探针与优雅终止。
  • 解释自愿中断与非自愿中断，并判断 PDB 能保护和不能保护什么。
  • 安全执行 Node drain、发布回滚与故障演练，并用 SLI 验证结果。

心智模型：高可用是端到端属性。副本只有在彼此独立、能承接流量、容量足够且维护流程安全时，才真正形成冗余。

高可用的边界

图：一次安全滚动发布从新 Pod 启动、探针验证、SLI 门禁到旧 Pod 优雅终止，以及 PDB、故障域和容量保护的位置。

高可用不是“副本数大于 1”这么简单。应用需要同时承受：

  • Pod/容器故障。
  • Node、机架或可用区故障。
  • 滚动发布与配置变更。
  • 节点维护、升级和自动缩容等自愿中断。
  • 依赖、存储、网络与控制面故障。

生产设计应从错误预算和恢复目标出发，明确所需副本、故障域、容量余量、数据一致性和降级策略。

PodDisruptionBudget

PDB 限制通过 Eviction API 发起的自愿中断同时影响多少副本，例如 kubectl drain 和部分节点自动缩容。它不能阻止 Node 宕机等非自愿中断，也不能阻止直接删除 Pod/Deployment。

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api
  namespace: production
spec:
  minAvailable: 2
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: api

对 3 副本服务，minAvailable: 2 表示 Eviction API 正常情况下只允许同时中断 1 个可用副本。

重要边界：

  • PDB 不控制 Deployment/StatefulSet 自身的滚动更新，发布可用性由工作负载更新策略控制。
  • 副本数为 1 且 minAvailable: 1 会阻止正常 drain，除非接受中断、先扩容或强制操作。
  • PDB selector 必须与工作负载标签一致。
  • AlwaysAllow 允许 drain 驱逐异常 Pod，避免坏 Pod 永久卡住节点维护。
kubectl get pdb -A
kubectl describe pdb/api -n production
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server

优雅终止

Pod 删除时的典型过程：

  1. API 对象获得 deletionTimestamp，EndpointSlice 开始反映终止状态。
  2. kubelet 执行容器的 preStop hook（若配置）。
  3. kubelet 向容器主进程发送终止信号，通常为 SIGTERM。
  4. 应用停止接收新流量、完成在途请求、刷新数据并退出。
  5. 超过 terminationGracePeriodSeconds 后，剩余进程会被强制终止。

preStop 的执行时间包含在终止宽限期内，因此宽限期必须覆盖 hook 和应用退出时间。

spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: api
    image: example/api:1.0.0
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 10"]
    readinessProbe:
      httpGet:
        path: /readyz
        port: 8080

应用侧必须捕获 SIGTERM，并依次执行：Readiness 失败 → 停止接受新连接 → 等待在途请求 → 关闭依赖连接 → 退出。单纯 sleep 只能给外部负载均衡传播留时间，不能代替应用的优雅关闭。

多副本与故障域分布

副本集中在同一 Node 或 Zone 不能抵御对应故障。Topology Spread Constraints 可按 Node 和 Zone 分散 Pod：

spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: api
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: api
  • Zone 级 DoNotSchedule 提供硬保护，但可用 Zone 或容量不足时会 Pending。
  • Node 级 ScheduleAnyway 作为软分散，可提高资源紧张时的可调度性。
  • 多可用区部署还必须评估存储拓扑、跨区延迟、流量费用以及云负载均衡健康检查。

滚动发布保护

spec:
  replicas: 4
  minReadySeconds: 30
  progressDeadlineSeconds: 600
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    spec:
      terminationGracePeriodSeconds: 60
      containers:
      - name: api
        readinessProbe:
          httpGet:
            path: /readyz
            port: 8080

发布前计算峰值容量：replicas + maxSurge 必须能被集群容纳。maxUnavailable: 0 只保证 Deployment 期望的可用副本策略，不能保护应用免受错误配置、依赖故障或新版本逻辑错误。

发布门禁至少包含：

  • 新版本可用副本数和 Readiness。
  • 请求量、错误率、P95/P99 延迟。
  • CPU throttling、内存、OOM、重启和连接池。
  • 关键业务成功率与依赖错误。
  • 明确的停止、回滚条件与观察窗口。

HPA 与滚动发布

HPA 和 Deployment 同时修改容量时，需要避免控制环互相干扰：

  • HPA 管理副本数时，发布清单不应由其他工具频繁重写 .spec.replicas。
  • minReplicas 至少覆盖故障和发布期间的冗余要求。
  • HPA 使用 CPU 利用率时，新 Pod 的 requests 必须合理；启动阶段的 CPU 峰值可能触发过度扩容。
  • 发布的 maxSurge 加上 HPA 的快速扩容会突然需要大量 Node 容量。
  • 缩容设置稳定窗口，避免发布后指标波动造成副本抖动。
  • readiness 失败的 Pod 不接流量，剩余 Pod 利用率上升又可能触发 HPA；需监控这一反馈链。

节点维护 Runbook

# 1. 检查 Node 上工作负载、PDB 和可替代容量
kubectl get pod -A --field-selector spec.nodeName=<node> -o wide
kubectl get pdb -A
kubectl get nodes

# 2. 停止新 Pod 调度
kubectl cordon <node>

# 3. 预演并执行 drain
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=15m

# 4. 维护完成后恢复调度
kubectl uncordon <node>

--delete-emptydir-data 会删除该 Node 上 Pod 的 emptyDir 数据；使用前必须确认数据是临时的。不要默认使用 --force 或绕过 PDB，除非已确认影响并进入经批准的应急流程。

高可用验收清单

  • 至少两个副本，并确认每个副本可独立提供服务。
  • 跨 Node/Zone 分散，故障域标签可靠。
  • Readiness、Startup、Liveness 语义正确。
  • PDB 与维护策略一致，不阻塞正常运维。
  • SIGTERM、preStop 和终止宽限期经过压测验证。
  • 滚动策略与集群峰值容量匹配。
  • HPA 最小/最大副本、扩缩行为和指标链已验证。
  • 完成 Pod 删除、Node drain、Zone 故障和回滚演练。
  • 有状态服务额外验证 quorum、复制、备份与恢复。

实践与验收

  • 删除一个 Pod，验证剩余容量、替代速度与用户侧 SLI。
  • 发送 SIGTERM，记录流量摘除、在途请求完成和进程退出时间。
  • 预演并执行一次 Node drain，确认 PDB、DaemonSet、emptyDir 和可替代容量。
  • 发布一个无法 Ready 的版本，验证滚动策略不会让服务低于允许容量并完成回滚。
