Kubernetes 可观测性与告警

2026-08-13

#Kubernetes#Observability#SRE

理解主线

指标揭示总体趋势，日志保存事件细节，Trace 连接跨服务路径。用稳定上下文关联信号，再从用户 SLI 定义告警；采集更多数据不自动提高定位速度。

学习目标

学完本章后，应当能够：

  • 说明 Metrics、Logs、Traces 各自回答什么问题，以及如何通过上下文关联。
  • 为服务使用 RED、为资源使用 USE，避免高基数和语义含糊的指标。
  • 从用户旅程定义 SLI/SLO、计算错误预算并设计多窗口燃烧率告警。
  • 编写可执行 Runbook，让告警包含影响、验证、止损、升级和恢复标准。

心智模型：监控告诉你预先定义的问题是否发生，可观测性帮助从系统输出推断未知内部状态；最终目标不是收集更多数据，而是更快发现用户影响并安全恢复。

可观测性模型

图：Metrics、Logs、Traces 从信号源进入各自存储，再汇聚到 Dashboard、SLI/SLO、告警和事故响应的链路。

Kubernetes 可观测性包含指标、日志和 Trace 三类信号，事件与审计日志提供重要补充。信号必须通过 cluster、namespace、workload、pod、node、version 等稳定维度关联。

应用/控制面/Node
├── Metrics → 时序数据库 → Dashboard / Alert / Autoscaling
├── Logs    → 日志后端   → 查询 / 告警 / 审计
└── Traces  → Trace 后端 → 跨服务调用链与性能分析

Prometheus 指标体系

Prometheus 的核心设计意义（面试角度）

为什么需要 Prometheus？

在 Kubernetes 中，需要了解：

  • Pod 占用了多少 CPU、内存？
  • 应用处理了多少请求？成功率怎么样？
  • 磁盘快满了吗？网络延迟多高？

但是传统的“查询方式”行不通：

问题 1：实时值波动太大，无法决策
  查询一次 Pod 内存用量：500MB
  1 秒后再查：800MB
  1 秒后再查：300MB（GC 了）
  → 无法判断"这个 Pod 需要多少内存"

问题 2：大量指标数据难以存储和查询
  集群中有 1000 个 Pod × 10 个指标 = 10000 条数据
  每秒采集一次 → 每秒 10000 条数据
  一天 = 86400 秒 × 10000 = 860 亿条数据
  → 需要专门的时序数据库

问题 3：需要历史数据做趋势分析和告警
  今天 CPU 80% 告警？需要对比过去一周的趋势
  "内存在快速增长吗？还是正常波动？"
  → 需要存储历史数据，计算趋势

Prometheus 解决方案（Pull + TimeSeries）：

┌─────────────────────────────────────────────────────┐
│  Prometheus 的核心架构                               │
│                                                     │
│  ┌─ Scraper（定时拉取）                             │
│  │  每 15 秒 → kubelet /metrics                      │
│  │          → App /metrics                          │
│  │          → node_exporter /metrics                │
│  │                                                  │
│  ├─ 时间序列存储（TSDB）                            │
│  │  metric_name{label1="v1", label2="v2"} →        │
│  │  [时间点1: 值1] [时间点2: 值2] ...               │
│  │                                                  │
│  ├─ PromQL 查询引擎                                 │
│  │  rate(http_requests_total[5m])                   │
│  │  → 计算最近 5 分钟的平均请求速率                 │
│  │                                                  │
│  └─ 告警规则引擎                                    │
│     if 条件 > 阈值 then 触发告警                     │
│                                                     │
│  结果：Dashboard / 告警 / HPA 触发                  │
└─────────────────────────────────────────────────────┘

Prometheus vs 其他监控系统对比：

特性 Prometheus 传统日志聚合（ELK） 云厂商 API
采集方式 Pull（主动拉） Push（被动推） Push（API 调用）
时序支持 原生支持 需要额外组件 支持但收费
查询语言 PromQL（强大） SQL 查询 受限
告警能力 内置告警规则 需要 ElastAlert 需要额外配置
集群友好 Kubernetes 原生 通用但不专用 厂商锁定
成本 开源免费 开源但存储贵 按量计费（贵）

核心优势：Pull 模式（Prometheus 独特）

Push 模式（日志系统常用）：
  应用 → 主动推送日志 → 日志服务器
  
  问题：
  ├─ 应用崩溃了，无法推送日志 → 看不到崩溃原因
  ├─ 网络卡顿，日志堆积在应用内存 → OOM
  └─ 应用需要知道日志服务器的地址 → 耦合

Pull 模式（Prometheus）：
  Prometheus ← 主动拉取 ← 应用的 /metrics 端口
  
  优势：
  ├─ 应用崩溃了，Prometheus 看不到 /metrics
  │   → 立即触发"采集失败"告警 → 发现故障
  ├─ Prometheus 服务器挂了，应用照常工作
  │   → Prometheus 恢复后继续采集 → 无缝恢复
  └─ 应用不需要知道 Prometheus 在哪 → 完全解耦

Prometheus 实现原理

采集机制（Scrape）

核心流程：

Prometheus 服务器（周期性，默认 15 秒）
  │
  ├─ 1. 读取 scrape_configs（告诉 Prometheus 去哪采集）
  │  例如：
  │    - job_name: kubernetes-pods
  │      kubernetes_sd_configs:
  │      - role: pod
  │
  ├─ 2. 服务发现（Service Discovery）
  │  通过 Kubernetes API 发现所有 Pod
  │  → 动态获取 Pod IP、Port、Label
  │
  ├─ 3. 发起 HTTP GET 请求
  │  GET http://10.1.2.3:8080/metrics
  │
  ├─ 4. 解析 Prometheus 格式的响应
  │  http_requests_total{method="GET", path="/"} 1234
  │  http_request_duration_seconds_bucket{...} 0.05
  │
  └─ 5. 存入时序数据库
     按 (metric_name, labels, timestamp) 作为 key

应用暴露 /metrics 的例子：

$ curl http://app:8080/metrics

# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET", path="/api/users", status="200"} 1024
http_requests_total{method="GET", path="/api/users", status="500"} 5

# HELP http_request_duration_seconds HTTP request latency
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{path="/api/users", le="0.1"} 800
http_request_duration_seconds_bucket{path="/api/users", le="0.5"} 950
http_request_duration_seconds_bucket{path="/api/users", le="+Inf"} 1024

时序数据库（TSDB）

存储结构：

Prometheus 不是关系数据库，而是时序数据库：

Metric：http_requests_total
├─ Dimension 1（标签组合）：{method="GET", status="200"}
│  ├─ [时间 t1, 值 100]
│  ├─ [时间 t2, 值 105]
│  ├─ [时间 t3, 值 110]
│  └─ [时间 t4, 值 115]
│
└─ Dimension 2（标签组合）：{method="POST", status="201"}
   ├─ [时间 t1, 值 50]
   ├─ [时间 t2, 值 52]
   └─ ...

每条时间序列是一条直线的数据点序列，适合时间相关的查询和告警

PromQL 查询语言

常见查询示例：

# 1. 瞬时值（现在这一刻的值）
http_requests_total

# 2. 范围查询（最近 5 分钟）
http_requests_total[5m]

# 3. 速率计算（关键！把累计值变成速率）
rate(http_requests_total[5m])
→ 计算最近 5 分钟的平均每秒请求数

# 4. 按标签聚合
sum by (path) (http_requests_total)
→ 按 path 分组求和

# 5. 错误率
sum by (path) (rate(http_requests_total{status=~"5.."}[5m]))
/ sum by (path) (rate(http_requests_total[5m]))
→ 每个路径的 5xx 错误率

# 6. 按百分位数计算（用于延迟分析）
histogram_quantile(0.95, 
  rate(http_request_duration_seconds_bucket[5m]))
→ 95% 的请求延迟不超过多少秒

告警规则

告警规则引擎的流程：

alert.yml (告警规则文件):
  - alert: HighErrorRate
    expr: rate(http_requests_total{status=~"5.."}[5m]) > 0.05
    for: 5m
    annotations:
      summary: "High error rate detected"

Prometheus 告警规则引擎（每分钟检查一次）：
  1. 计算 expr（PromQL 表达式）
  2. 如果结果 > 0（True），进入"待命状态"（Pending）
  3. 持续 for 时间（5 分钟）仍然 True，则触发告警
  4. 告警发送给 Alertmanager
  
  优势：
  ├─ for 时间防止瞬时尖峰误报
  ├─ 自动消除告警（当 expr 变 False）
  └─ 支持告警分组、路由、合并、去重

数据源

Kubernetes 组件通常以 Prometheus 格式暴露 /metrics。常见数据源：

数据源 主要内容
应用 /metrics 请求、错误、延迟和业务指标
kubelet/cAdvisor 容器 CPU、内存、文件系统、网络
kube-state-metrics Deployment、Pod、PVC 等 API 对象状态
node_exporter Node 操作系统与硬件指标
API Server/Scheduler/Controller 控制面请求、队列、延迟和错误
metrics-server 轻量资源指标，主要供 kubectl top、HPA/VPA 使用

metrics-server 不是长期监控存储，也不能代替 Prometheus。kube-state-metrics 反映 Kubernetes 对象状态，不直接采集容器资源使用量。

指标设计

指标设计

  • Counter：只增不减，如请求总数；使用 rate() 计算速率。
  • Gauge：可增可减，如队列长度和当前连接数。
  • Histogram：记录延迟/大小分布，适合计算分位数与 SLO。
  • 标签只使用有界集合。不要将 user ID、request ID、完整 URL 等高基数字段作为标签。
  • 记录单位和语义，例如秒使用 _seconds、字节使用 _bytes、累计值使用 _total。

RED 与 USE

面向请求型服务使用 RED：

  • Rate：请求率。
  • Errors：错误率。
  • Duration：延迟分布。

面向 Node、CPU、磁盘、连接池等资源使用 USE：

  • Utilization：利用率。
  • Saturation：饱和度/排队程度。
  • Errors：错误数量或速率。

Kubernetes 工作负载还需关注期望副本、可用副本、Pending、重启、OOMKilled、CPU throttling、PVC 与 EndpointSlice。

日志采集

应用优先把结构化日志写到 stdout/stderr。Node 上通常运行 DaemonSet 日志 Agent，读取容器日志并转发到独立后端；Kubernetes 本身不提供集群级日志存储。

推荐字段：

{
  "timestamp": "2026-08-13T10:00:00+08:00",
  "level": "error",
  "service": "checkout-api",
  "version": "1.8.2",
  "trace_id": "...",
  "request_id": "...",
  "message": "dependency timeout",
  "dependency": "payment"
}

要求：

  • 不记录密码、Token、Cookie、身份证号等敏感信息。
  • 明确日志保留、索引、冷热分层和访问权限。
  • Node 配置日志轮转，防止 /var/log 写满。
  • 多行堆栈在采集端正确合并；格式变更向后兼容。
  • 对 kubelet、容器运行时、控制面和 Kubernetes Audit Log 分别采集。
kubectl logs pod/<pod> -n <ns> --all-containers --since=30m
kubectl logs pod/<pod> -n <ns> -c <container> --previous
journalctl -u kubelet --since "30 min ago"

Tracing

分布式 Trace 用于定位一次请求跨多个服务、队列和数据库的耗时与错误。应用应传播 W3C Trace Context，并把 trace_id 写入结构化日志，实现日志与 Trace 互跳。

常见链路：应用通过 OpenTelemetry SDK/自动探针产生 Span → OpenTelemetry Collector 接收、采样和处理 → Trace 后端存储与分析。

采样策略：

  • 常规流量使用概率或基于速率采样控制成本。
  • 错误、慢请求和关键交易提高保留概率，可采用 tail sampling。
  • 采样、脱敏和保留策略必须考虑个人信息和合规。

Trace 不能代替指标告警；指标发现异常，Trace 解释单次请求发生了什么，日志提供详细上下文。

SLI、SLO 与错误预算

  • SLI：可测量的服务质量指标。
  • SLO：在时间窗口内对 SLI 的目标。
  • Error Budget：允许不满足目标的比例，用于平衡可靠性和变更速度。

例如 30 天可用性 SLO 为 99.9%，错误预算约为 0.1%。请求型 API 的 SLI 应从用户视角定义：

可用性 SLI = 成功且满足有效性条件的请求数 / 有效请求总数
延迟 SLI   = 延迟低于阈值的请求数 / 有效请求总数

不要直接用“Pod Running”作为服务可用性 SLI；Pod 正常不代表请求成功。

常用 SLI：

类型 示例
HTTP API 非预期 5xx 比例、P99 延迟达标比例
异步任务 在承诺时间内完成的任务比例、积压时长
数据服务 成功读写比例、复制延迟、数据新鲜度
Kubernetes 平台 API 请求成功率、Pod 启动延迟、调度成功率

告警设计

告警应基于用户影响、趋势和可行动性，而不是看到任何异常指标就报警。

级别 含义 处理方式
P1 大面积不可用、数据安全风险、错误预算快速燃烧 立即通知值班，启动事故响应
P2 核心功能明显降级或即将耗尽关键容量 值班及时处理
P3 局部异常、冗余下降、需要工作时间处理 工单/白天处理
Info 变更、扩缩容、短暂自愈事件 记录或看板，不呼叫值班

对 SLO 推荐多窗口、多燃烧率告警：短窗口发现快速故障，长窗口捕获持续缓慢退化。容量类告警要预测“多久耗尽”，并排除短暂尖峰。

容易产生噪声的告警：单个 Pod 重启一次、CPU 短时 90%、Deployment 发布期间短暂副本变化、已自动恢复且无用户影响的瞬态错误。

基础告警矩阵

告警 关键验证 Runbook 入口
API 5xx/延迟燃烧 版本、入口、依赖、可用副本 发布/依赖/容量排障
Pod CrashLoopBackOff 退出码、previous 日志、探针、配置 Pod 崩溃排障
Pod Pending Scheduler 事件、request、taint、PVC 调度排障
OOMKilled limit、working set、GC、流量 内存容量排障
CPU throttling limit、使用率、延迟 CPU 配额排障
Node NotReady Node condition、kubelet、网络、运行时 Node 故障排障
PVC 容量不足 使用率、增长率、扩容能力 存储扩容 Runbook
EndpointSlice 无就绪后端 selector、Readiness、发布状态 Service 排障
CoreDNS 错误/高延迟 CoreDNS、上游 DNS、网络策略 DNS 排障
CronJob 失败/未执行 调度、并发、Job/Pod 日志 批任务排障

Runbook 模板

每条可呼叫告警必须附带：

# 告警名称

## 用户影响

哪些用户、功能和区域受到影响。

## 立即确认

Dashboard、查询、近期变更和影响范围。

## 止损操作

可安全执行的回滚、扩容、降级和流量切换步骤。

## 深入排查

按优先级排列的命令、日志、指标和判定分支。

## 验证恢复

SLI 回归阈值、稳定观察窗口和积压清理确认。

## 升级与沟通

何时升级到谁，事故频道和状态通知要求。

## 证据与复盘

保存时间线、变更、日志、指标和最终根因。

通用首轮排障

kubectl get pods -A -o wide
kubectl get events -A --sort-by=.lastTimestamp
kubectl get nodes
kubectl top nodes
kubectl top pods -A --containers
kubectl rollout history deployment/<name> -n <ns>
kubectl describe pod/<pod> -n <ns>
kubectl logs pod/<pod> -n <ns> --all-containers --previous

先确认用户影响和近期变更，再按应用 → 工作负载 → Node → 控制面逐层缩小范围。事件会过期，事故期间及时保存关键输出与时间线。

生产基线

  • 每个服务至少有 RED、容量、依赖和发布 Dashboard。
  • Node/容器按 USE 方法覆盖，控制面监控 API Server、etcd、Scheduler、Controller 和 CoreDNS。
  • 日志集中存储并与指标、Trace 通过稳定字段关联。
  • 核心服务定义用户视角 SLI/SLO、错误预算和多窗口燃烧率告警。
  • 每条 P1/P2 告警有责任人、Runbook、验证标准，并定期演练。
  • 可观测系统自身具备高可用、容量、丢数、采集延迟和成本监控。

实践与验收

  • 为一个 HTTP API 采集请求率、错误率与延迟分布，并制作 RED Dashboard。
  • 定义 30 天可用性 SLO，计算允许失败量与当前错误预算消耗。
  • 制造高错误率，验证告警表达式、通知路由、静默和恢复通知。
  • 从告警跳转到日志和 Trace，利用 request/trace ID 还原一次失败请求。
  • 请未参与配置的人只依据 Runbook 完成首轮排障，记录缺失步骤。

验收标准：告警必须代表可行动的问题；Dashboard、查询、日志字段和 Runbook 能共同缩短发现与恢复时间。
