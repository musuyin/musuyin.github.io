Kubernetes 工作负载进阶

2026-08-13

#Kubernetes#Workload#SRE

理解主线

控制器承诺不同的身份、调度与完成语义：StatefulSet 维持稳定身份，DaemonSet 维持节点覆盖，Job 跟踪完成，CronJob 定时创建任务。先判断业务需要的语义，再选择 kind。

学习目标

学完本章后，应当能够：

  • 按无状态、有状态、节点常驻、一次性和周期性任务选择控制器。
  • 解释 StatefulSet 的稳定身份、Headless Service、独立 PVC 与顺序语义。
  • 控制 Job/CronJob 的重试、并发、超时、历史保留和失败处理。
  • 排查 DaemonSet 未覆盖节点、Job 不完成和 CronJob 未触发等问题。

心智模型：控制器的区别不只是 YAML 的 kind，而是它承诺维持哪一种运行语义。先明确身份、完成条件与调度范围，再选择控制器。

控制器选择

图：根据无状态、有状态、节点 Agent、一次性和周期性任务选择合适的工作负载控制器。

控制器 适用场景 核心特征
Deployment 无状态常驻服务 Pod 可互换、滚动发布方便
StatefulSet 数据库、队列等有状态服务 稳定序号、网络身份和独立存储
DaemonSet 日志、监控、CNI、CSI 等节点 Agent 每个符合条件的 Node 运行一份
Job 一次性批处理 运行到成功完成
CronJob 周期性批处理 按 Cron 调度创建 Job

StatefulSet

StatefulSet 为 Pod 提供稳定身份，例如 db-0、db-1，并可通过 volumeClaimTemplates 为每个 Pod 创建独立 PVC。删除或缩容 StatefulSet 默认不会自动删除 PVC，避免意外丢失数据，也意味着需要单独治理遗留卷。

StatefulSet 通常需要一个 Headless Service（clusterIP: None）提供稳定 DNS：

<pod>.<service>.<namespace>.svc.cluster.local
apiVersion: v1
kind: Service
metadata:
  name: db
  namespace: production
spec:
  clusterIP: None
  selector:
    app: db
  ports:
  - name: client
    port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: production
spec:
  serviceName: db
  replicas: 3
  selector:
    matchLabels:
      app: db
  updateStrategy:
    type: RollingUpdate
  template:
    metadata:
      labels:
        app: db
    spec:
      terminationGracePeriodSeconds: 60
      containers:
      - name: db
        image: example/db:1.0.0
        ports:
        - containerPort: 5432
        readinessProbe:
          tcpSocket:
            port: 5432
        resources:
          requests:
            cpu: 500m
            memory: 1Gi
          limits:
            memory: 2Gi
        volumeMounts:
        - name: data
          mountPath: /var/lib/db
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: fast
      resources:
        requests:
          storage: 100Gi

有状态服务发布

  • 发布前确认应用自身的集群成员变更、主从切换、Schema 兼容和备份恢复机制。
  • RollingUpdate 默认按逆序逐个更新 Pod；前一个 Pod Ready 后才继续。
  • partition 可暂时只更新高序号 Pod，便于人工金丝雀验证。
  • podManagementPolicy: Parallel 只改变扩缩容时的顺序保证，应确认应用允许并行启动/终止。
  • Kubernetes 只管理 Pod 与存储对象，不理解数据库 quorum、复制延迟或数据一致性。
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 2

StatefulSet 排障

kubectl rollout status statefulset/db -n production
kubectl get pod,pvc -n production -l app=db
kubectl describe statefulset/db -n production
kubectl describe pod/db-0 -n production
kubectl logs pod/db-0 -n production --all-containers --previous

若滚动更新卡住，检查目标序号 Pod 的 Readiness、PVC 挂载、应用成员状态与事件；不要为了继续发布而直接删除生产 PVC。

DaemonSet

DaemonSet 的核心设计意义

为什么需要 DaemonSet？

在 Kubernetes 中，有一类工作负载是节点级的 Agent——它们不是应用本身，而是基础设施的一部分，每个 Node 都需要一份。典型场景：

问题场景：
日志采集工具（Fluent Bit）需要在每个 Node 上运行，收集该 Node 的容器日志
监控 Agent（Node Exporter）需要在每个 Node 上收集 CPU、内存、磁盘等指标
网络插件（CNI）需要在每个 Node 上配置网络栈
存储插件（CSI Node Plugin）需要在每个 Node 上挂载磁盘

朴素方案（行不通）：

如果用 Deployment 部署这类 Agent，会遇到的问题：

Deployment 是全局级的副本控制，它会说：
  "我要创建 5 个副本，Kubernetes 随意调度到任意 Node"

结果：
  - 某些 Node 上多个 Fluent Bit 实例，浪费资源
  - 某些 Node 上 0 个实例，该 Node 的日志无法采集
  - 新加 Node 时需要手动更新副本数
  - 删除 Node 时副本漂移到其他 Node，造成重复采集

Kubernetes 解决方案（DaemonSet）：

┌─────────────────────────────────────────────────────┐
│  DaemonSet Controller（Node 级的工作负载调度器）      │
│  ↓                                                   │
│  监听 Node 的加入与删除                              │
│  ↓                                                   │
│  ┌─ Node-1 ─→ 创建 Pod（自动匹配）                  │
│  ├─ Node-2 ─→ 创建 Pod（自动匹配）                  │
│  ├─ Node-3 ─→ 创建 Pod（自动匹配）                  │
│  └─ Node-4 ─→ 创建 Pod（自动匹配）                  │
│                                                     │
│  新加 Node-5 → 自动创建 Pod                        │
│  删除 Node-3 → 自动删除对应 Pod                    │
└─────────────────────────────────────────────────────┘

DaemonSet vs Deployment 的根本差异：

维度 Deployment DaemonSet
粒度 全局副本数 每个 Node 一份
扩展方式 手动改 replicas 自动跟随 Node 加减
调度逻辑 标准调度器 Node 级亲和性（必须）
使用场景 无状态应用服务 节点级基础设施组件
Pod 位置 分散在任意 Node 明确知道在哪个 Node

DaemonSet 的核心职责：

  1. 自动覆盖：无需指定副本数，每个符合条件的 Node 自动一份
  2. 节点感知：新 Node 加入时自动创建 Pod，Node 删除时自动清理 Pod
  3. 选择性部署：通过 label selector、affinity、taint/toleration 精确控制哪些 Node 应该运行

类比理解（面试好用）：

DaemonSet 就像“安装在每个派出所的监控摄像头”。

  • Deployment 是中央调度中心说“我要 5 台摄像头”，然后随意放在各地，可能某个派出所 3 台、某个派出所 0 台。
  • DaemonSet 是自动规则：“每个派出所都要安 1 台”。新派出所开张自动装上，派出所关闭自动拆掉。无需中央干预。

这样日志采集、监控、网络配置这些“基础设施工作”就不用运维手动维护了——系统自动保证每个 Node 都有一份。

没有 DaemonSet 会怎样：

  • 运维要手动计算 Node 数量，设置 Deployment replicas
  • 每次扩缩容集群都要改配置，容易出错
  • 新 Node 加入时日志采集有延迟，需要人工干预
  • 某些 Node 可能因为资源或亲和性限制而没有 Agent，导致监控盲点

DaemonSet

DaemonSet 确保每个符合 selector、affinity 和 taint/toleration 条件的 Node 运行一个 Pod，适合节点级 Agent，例如日志采集、Node Exporter、CNI 和 CSI 节点插件。

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
  namespace: observability
spec:
  selector:
    matchLabels:
      app: node-agent
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 10%
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      serviceAccountName: node-agent
      priorityClassName: system-node-critical
      tolerations:
      - operator: Exists
      containers:
      - name: agent
        image: example/node-agent:1.0.0
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            memory: 256Mi

tolerations: [{operator: Exists}] 权限很宽，只应供确实要覆盖所有 Node 的关键 Agent 使用。普通节点 Agent 应精确选择 Node 并按需容忍 taint。

kubectl get daemonset -A
kubectl describe daemonset/node-agent -n observability
kubectl get pod -n observability -l app=node-agent -o wide

重点比较 DESIRED、CURRENT、READY、AVAILABLE。某个 Node 缺少 Pod 时，检查 Node label、taint、资源、亲和性和 DaemonSet 事件。

Job

Job 负责将任务运行到成功完成。任务应尽可能幂等，因为节点故障、控制器重试等情况下可能重复执行。

apiVersion: batch/v1
kind: Job
metadata:
  name: report-20260813
  namespace: batch
spec:
  backoffLimit: 3
  activeDeadlineSeconds: 1800
  ttlSecondsAfterFinished: 86400
  podFailurePolicy:
    rules:
    - action: FailJob
      onExitCodes:
        containerName: report
        operator: In
        values: [42]
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: report
        image: example/report:1.0.0
        resources:
          requests:
            cpu: 250m
            memory: 256Mi
          limits:
            memory: 512Mi
  • backoffLimit 限制失败重试次数。
  • activeDeadlineSeconds 限制整个 Job 的运行时长，优先级高于重试。
  • ttlSecondsAfterFinished 自动清理已完成 Job 及其依赖对象。
  • podFailurePolicy 可按退出码或 Pod condition 选择立即失败、忽略或继续计入重试；示例中的退出码 42 会直接将 Job 判为失败。
  • restartPolicy 只能是 Never 或 OnFailure；排障更偏向使用 Never，便于保留每次失败 Pod 的状态和日志。

CronJob

CronJob 按计划创建 Job。调度可能在特殊情况下发生重复或错过，因此任务必须幂等，并在业务侧使用唯一键、锁或去重表保证副作用安全。

apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
  namespace: batch
spec:
  schedule: "0 2 * * *"
  timeZone: "Asia/Shanghai"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 600
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: backup
            image: example/backup:1.0.0

concurrencyPolicy：

  • Allow：允许同一 CronJob 的任务并发，默认值。
  • Forbid：上一次未结束时跳过本次启动。
  • Replace：新任务替换仍在运行的旧任务。

生产环境应显式设置 timeZone、并发策略、超时和历史保留数量。备份任务还必须独立验证备份可恢复，而非只看 Job 为 Complete。

定时任务失败 Runbook

# CronJob 是否被暂停，调度和上次执行时间是否正确
kubectl get cronjob/<name> -n <ns> -o wide
kubectl describe cronjob/<name> -n <ns>

# 按创建时间查看派生 Job 与 Pod
kubectl get job -n <ns> --sort-by=.metadata.creationTimestamp
kubectl get pod -n <ns> -l job-name=<job>
kubectl describe job/<job> -n <ns>
kubectl logs job/<job> -n <ns> --all-containers

# 查看事件
kubectl get events -n <ns> --sort-by=.lastTimestamp

按以下顺序判断：

  1. Cron 表达式、timeZone、.spec.suspend 和 startingDeadlineSeconds。
  2. concurrencyPolicy 是否因旧任务未完成而跳过新任务。
  3. Job 是否因配额、调度、拉取镜像、挂载或权限失败而没有启动。
  4. 容器退出码、日志、超时和 backoffLimit。
  5. 外部依赖和任务幂等性；修复后再决定是创建临时 Job 还是等待下一周期。

从 CronJob 手动创建一次性 Job：

kubectl create job --from=cronjob/<cronjob> <manual-job-name> -n <ns>

生产基线

  • 所有控制器配置 requests、探针、终止时间和可观测标签。
  • StatefulSet 在发布前验证备份、复制、quorum、Schema 兼容和回滚步骤。
  • 节点 Agent 设置精确权限、资源上限、更新预算和覆盖率告警。
  • Job/CronJob 明确幂等性、超时、重试、并发策略、历史清理和失败告警。
  • 关键任务记录业务完成指标，例如“备份可恢复时间”，不能仅依赖 Kubernetes 状态。

实践与验收

  • 发布 StatefulSet，验证 Pod 名称、DNS 与 PVC 在 Pod 重建后保持稳定关联。
  • 创建只运行在指定标签 Node 上的 DaemonSet，观察标签和 taint 对覆盖范围的影响。
  • 创建成功与失败的 Job，比较 backoffLimit、activeDeadlineSeconds 和退出码。
  • 创建带时区、禁止并发和历史保留限制的 CronJob，检查其派生 Job。

验收标准：面对新需求时能说明为何选择某控制器，以及其更新、扩缩容、失败重试和数据安全风险。
