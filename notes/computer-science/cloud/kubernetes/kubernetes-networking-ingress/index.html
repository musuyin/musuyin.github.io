CNI and Ingress

2026-08-13

#Kubernetes#Network#SRE

理解主线

沿客户端 → DNS → 入口 → Service → EndpointSlice → Pod 建立请求链路。CNI、服务发现、数据面和入口控制器分别负责不同段，网络策略还会叠加独立的允许条件。

学习目标

学完本章后，应当能够：

  • 沿客户端、DNS、入口、Service、EndpointSlice 和 Pod 网络解释完整请求链路
  • 区分 CNI、CoreDNS、Service 数据面、Ingress 与 Ingress Controller 的职责
  • 解释服务如何通过稳定名称发现动态变化的 Pod
  • 区分 LoadBalancer Service、Ingress 与 Gateway API 的适用场景
  • 编写默认拒绝并按最小范围放行的 NetworkPolicy
  • 用分层验证法定位 DNS、路由、策略、入口和应用端口故障

Kubernetes 网络不是一个组件，而是一条协作链。排障时应逐层验证，不能把所有连通性问题都归因于 CNI。

网络全景

Kubernetes 网络可以分成以下层次：

层次 主要对象或组件 解决的问题
Pod 网络 CNI、Pod IP Pod 如何获得地址并跨 Node 通信
服务发现 Service、EndpointSlice、CoreDNS 调用方如何稳定发现动态 Pod
Service 数据面 kube-proxy、iptables、IPVS 或 eBPF ClusterIP 流量如何转发到后端 Pod
网络隔离 NetworkPolicy、支持策略的 CNI 哪些来源能够访问哪些 Pod
南北向入口 LoadBalancer、Ingress、Gateway API 集群外流量如何进入集群

默认网络模型要求：

  • 每个 Pod 拥有集群范围内可路由的独立 IP
  • Pod 可以直接与其他 Pod 通信，不需要应用层 NAT
  • Node 上的组件可以访问该 Node 上的 Pod

具体如何分配地址、跨 Node 路由、封装数据包及执行 NetworkPolicy，由 CNI 实现决定。

南北向与东西向流量

  • 南北向流量：集群外部与集群内部之间的流量，例如浏览器访问集群中的 Web 服务
  • 东西向流量：集群内部服务之间的流量，例如 Order Service 调用 Payment Service
互联网用户
    │ 南北向
    ▼
LoadBalancer
    ▼
Ingress Controller
    ▼
Service
    │ 东西向
    ▼
Pod ──────────► 另一个 Service ──► Pod

南北向通常关注公网地址、TLS、域名和七层路由；东西向通常关注服务发现、低延迟、重试边界和网络隔离。

CNI

CNI（Container Network Interface）是一套容器网络插件规范。创建 Pod Sandbox 时，容器运行时调用 CNI 插件完成网络配置。

CNI 通常负责：

  • 为 Pod 创建网络接口并接入网络命名空间
  • 通过 IPAM 为 Pod 分配和回收 IP
  • 配置路由、隧道、网桥或 eBPF 数据面
  • 在插件支持时执行 NetworkPolicy

CNI 不负责：

  • 将 Service DNS 名解析为 ClusterIP，这是 CoreDNS 的职责
  • 根据 Service selector 维护后端列表，这是控制器和 EndpointSlice 的职责
  • 根据 HTTP Host 或 Path 路由，这是 Ingress Controller 或 Gateway Controller 的职责

不同实现可能采用不同数据面：

  • Overlay：通过 VXLAN 等隧道封装跨 Node 流量
  • Underlay 或路由模式：让底层网络直接学习 Pod 网段
  • eBPF：在内核中实现路由、Service 转发和策略执行，例如 Cilium

CNI 检查

kubectl get nodes -o wide
kubectl get pods -n kube-system -o wide
kubectl describe node/<node>
kubectl get events -A --sort-by=.lastTimestamp

只有一个 Node 异常时，优先检查该 Node 上的 CNI DaemonSet Pod、路由、网卡和 kubelet；所有 Node 都异常时，再检查 CNI 控制器、地址池、集群路由和近期配置变更。

Service 与集群内通信

Pod IP 会随重建而变化，调用方不应硬编码 Pod IP。Service 为一组 Pod 提供稳定的虚拟地址和端口，EndpointSlice 保存当前可用的后端 Pod 地址。

apiVersion: v1
kind: Service
metadata:
  name: payment
  namespace: production
spec:
  selector:
    app: payment
  ports:
  - name: grpc
    port: 50051
    targetPort: grpc

Service 通过 selector 匹配 Pod 的 label：

metadata:
  labels:
    app: payment

控制器根据匹配结果维护 EndpointSlice。Service 自身不启动进程，也不会创建 Pod。

CoreDNS 与服务发现

Service 创建后，集群 DNS 会为它提供稳定名称：

<service>.<namespace>.svc.<cluster-domain>

例如：

payment.production.svc.cluster.local
  • 同一 Namespace 可以使用短名称 payment
  • 跨 Namespace 可以使用 payment.production
  • 完整名称为 payment.production.svc.cluster.local
  • cluster.local 是常见默认值，但集群可以修改它

CoreDNS 只负责名称解析。调用方之所以知道 payment 这个名字，是因为服务依赖由系统设计确定，并通过环境变量、ConfigMap 或 Helm values 等配置传入应用。

RPC 地址可以拆成：

协议 + Service DNS 名称 + Service 端口 + RPC 方法

例如应用配置：

env:
- name: PAYMENT_RPC_ADDRESS
  value: payment.production.svc.cluster.local:50051

集群内请求链路

Order Pod
    │ 查询 payment.production
    ▼
CoreDNS
    │ 返回 payment Service 的 ClusterIP
    ▼
Service ClusterIP:50051
    │ kube-proxy 或 eBPF 根据 EndpointSlice 选择后端
    ▼
Payment Pod IP:targetPort

Service ClusterIP 在 Service 生命周期内稳定，后端 Pod 可以扩缩容或重建。对于无头 Service（clusterIP: None），DNS 通常返回后端 Pod 地址，由客户端或上层协议完成发现和负载均衡。

Service 抽象通常工作在四层。iptables、IPVS 或 eBPF 的转发不等同于理解 HTTP 语义的反向代理。

Service 类型

类型 可访问范围 典型用途
ClusterIP 集群内部 服务之间通信，默认类型
NodePort Node IP 的固定端口 测试或作为外部负载均衡器的下游入口
LoadBalancer 集群外部 通过云或基础设施负载均衡器暴露一个 Service
ExternalName DNS CNAME 将集群内名称映射到外部域名

LoadBalancer Service 的 Kubernetes 抽象通常提供四层 TCP/UDP 转发。不同云实现可以通过扩展能力提供更多功能，但不应把这些实现细节当成 Service API 的通用保证。

DNS 排障

kubectl exec -n <ns> <pod> -- cat /etc/resolv.conf
kubectl exec -n <ns> <pod> -- nslookup <service>.<namespace>
kubectl get svc/<service> -n <namespace> -o wide
kubectl get endpointslice -n <namespace> -l kubernetes.io/service-name=<service>
kubectl get deploy,pod,svc -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system deploy/coredns
kubectl get configmap/coredns -n kube-system -o yaml

排查顺序：Pod 的 /etc/resolv.conf → kube-dns Service → CoreDNS EndpointSlice → CoreDNS Pod → Corefile → 上游 DNS。

常见原因：

  • Service 名或 Namespace 写错
  • Service 存在，但 selector 没有匹配到 Ready Pod
  • CoreDNS Pod 未就绪或资源不足
  • NetworkPolicy 阻止到 DNS 的 UDP/TCP 53 流量
  • 上游 DNS 不可用，此时通常只有外部域名解析失败
  • ndots 和 search domain 产生额外查询，造成解析延迟

Ingress

Ingress 用于声明 HTTP/HTTPS 七层路由，例如根据 Host 和 Path 将请求转发到不同 Service。

必须区分两个概念：

  • Ingress：存储期望路由规则的 Kubernetes API 对象，本身不处理网络流量
  • Ingress Controller：监听 Ingress 对象，将规则转换为 NGINX、Envoy、HAProxy 或云负载均衡器配置，并实际处理流量

如果集群没有安装匹配的 Ingress Controller，只创建 Ingress 对象不会产生可用入口。

Ingress 与 LoadBalancer Service

二者经常组合使用，而不是互相替代：

公网 DNS
    │ api.example.com → 外部 IP
    ▼
LoadBalancer Service
    ▼
Ingress Controller
    │ 根据 Host、Path、TLS 等规则
    ▼
ClusterIP Service
    ▼
Pod
对比项 LoadBalancer Service Ingress
主要层级 通常是四层 七层 HTTP/HTTPS
路由依据 IP、端口、协议 Host、Path，部分实现还支持 Header 等
后端范围 通常暴露一个 Service 一个入口可以路由到多个 Service
TLS 取决于负载均衡器实现 常用于统一 TLS 终止和证书管理
实现依赖 云控制器或基础设施 LB 实现 必须安装 Ingress Controller
适用场景 TCP、UDP 或单个服务直接暴露 多个 HTTP/HTTPS 服务共享入口

标准 Ingress 主要面向 HTTP/HTTPS。gRPC 基于 HTTP/2，能否正确代理取决于 Ingress Controller 的支持和配置；任意 TCP/UDP 转发通常需要 Controller 专有配置或其他 API。

Ingress 示例

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: application
  namespace: production
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - api.example.com
    secretName: api-tls
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /users
        pathType: Prefix
        backend:
          service:
            name: user
            port:
              number: 80
      - path: /orders
        pathType: Prefix
        backend:
          service:
            name: order
            port:
              number: 80

这段配置只声明：

  • api.example.com/users 转发到 user Service
  • api.example.com/orders 转发到 order Service
  • 使用 api-tls Secret 中的证书处理 HTTPS
  • 由 nginx IngressClass 对应的 Controller 实现

公网 DNS 还需要将 api.example.com 指向 Ingress Controller 的外部 IP。这个 DNS 记录可以人工管理，也可以由 ExternalDNS 等控制器自动维护，但不是 Ingress API 自己创建的。

Ingress Controller 的具体数据路径取决于实现：有的经过 Service ClusterIP，有的直接读取 EndpointSlice 并连接 Pod。概念上，Ingress 的后端仍然通过 Service 名称声明。

Ingress 排障

kubectl get ingressclass
kubectl describe ingress/application -n production
kubectl get svc,endpointslice -n production
kubectl get pods,svc -A

重点确认：

  • ingressClassName 是否对应正在运行的 Controller
  • 外部 DNS 是否指向正确的外部 IP
  • Host 和 Path 是否与请求匹配
  • 后端 Service 和端口是否存在
  • EndpointSlice 是否包含 Ready 后端
  • TLS Secret 是否存在且证书域名匹配
  • Controller 日志是否报告配置、证书或上游连接错误

反向代理

反向代理代表后端服务器接收客户端请求，客户端只知道代理地址，不需要知道真实后端实例。

客户端 → 反向代理 → 后端服务

Ingress Controller 是典型的 HTTP 反向代理。它可以终止 TLS、读取 Host 和 Path、选择后端并建立新的上游连接。

Service 的 ClusterIP 转发通常是四层负载均衡或 NAT，不应简单等同于七层反向代理。Service Mesh 中的 Envoy Sidecar 或节点代理则可能承担东西向七层代理、mTLS、重试和可观测性等职责。

Gateway API

Ingress API 已稳定但功能冻结。Gateway API 通过 CRD 和具体 Controller 提供更强的表达能力以及更清晰的角色边界。

资源 常见负责人 作用
GatewayClass 平台团队 声明由哪个 Controller 实现网关
Gateway 基础设施团队 定义监听地址、端口、协议和 TLS
HTTPRoute 等 Route 应用团队 定义 Host、Path、权重和后端 Service

Gateway API 不是 Kubernetes 安装后的默认数据面，需要安装 CRD 和匹配的 Gateway Controller。

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: public
  namespace: gateway-system
spec:
  gatewayClassName: example-gateway-class
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    tls:
      mode: Terminate
      certificateRefs:
      - name: public-tls
    allowedRoutes:
      namespaces:
        from: All
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web
  namespace: production
spec:
  parentRefs:
  - name: public
    namespace: gateway-system
  hostnames:
  - web.example.com
  rules:
  - backendRefs:
    - name: web
      port: 80

跨 Namespace 的 Route 必须满足 Gateway 的 allowedRoutes；跨 Namespace 引用后端或证书时，还可能需要目标 Namespace 中的 ReferenceGrant。排障时重点查看资源的 status.conditions。

kubectl get gatewayclass,gateway -A
kubectl get httproute -A
kubectl describe gateway/public -n gateway-system
kubectl describe httproute/web -n production

NetworkPolicy

NetworkPolicy 用于限制 Pod 的入站和出站连接。它是允许列表模型，并且需要 CNI 支持策略执行。

  • 没有任何策略选择某个 Pod 的某个方向时，该方向默认不隔离
  • 一旦有策略选择该 Pod 的某个方向，只允许所有适用策略规则的并集
  • 多条 NetworkPolicy 是叠加关系，不存在规则顺序和显式拒绝规则

Namespace 默认拒绝

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress

启用默认拒绝后，必须显式放行 DNS、入口 Controller、监控和业务依赖。下面只允许带 access=frontend 标签的 Namespace 中、带 app=web 标签的 Pod 访问 API：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-from-frontend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          access: frontend
      podSelector:
        matchLabels:
          app: web
    ports:
    - protocol: TCP
      port: 8080

namespaceSelector 与 podSelector 位于同一个 from 条目时是 AND；写成两个独立条目时是 OR。

NetworkPolicy 中的 Ingress 表示进入 Pod 的流量方向，与七层路由对象 kind: Ingress 不是同一个概念。

端到端请求链路

集群内部调用

应用配置中的 Service 名称
    → CoreDNS 解析 ClusterIP
    → Service 数据面选择 EndpointSlice 后端
    → NetworkPolicy 判断是否允许
    → CNI 将数据包送到目标 Pod
    → 应用监听 targetPort 并处理请求

集群外部访问

公网域名
    → 公网 DNS 解析外部 IP
    → LoadBalancer 将连接送入集群
    → Ingress Controller 终止 TLS 并匹配 Host/Path
    → 后端 Service 或 EndpointSlice
    → NetworkPolicy 与 CNI
    → Pod

端到端网络排障

先判断故障范围：只有一个调用方、一个 Namespace、一个 Node，还是整个集群都失败。然后从离应用最近的后端开始逐层验证。

检查 Pod 与 EndpointSlice

kubectl get pod -n <ns> -l <selector> -o wide
kubectl get svc/<service> -n <ns> -o yaml
kubectl get endpointslice -n <ns> -l kubernetes.io/service-name=<service>

如果 EndpointSlice 为空，优先检查 Service selector、Pod labels、Readiness Probe 和 Service 端口，不要先重启 CoreDNS。

检查 DNS

kubectl exec -n <source-ns> <source-pod> -- nslookup <service>.<ns>

能解析只证明名称到地址成立，不证明端口、策略和后端应用可用。

分别测试 Service 和 Pod

kubectl exec -n <source-ns> <source-pod> -- wget -S -O- http://<service>.<ns>:<port>/healthz
kubectl exec -n <source-ns> <source-pod> -- wget -S -O- http://<pod-ip>:<target-port>/healthz
  • Pod IP 可达、Service 不可达：重点检查 Service 端口映射和 Service 数据面
  • Pod IP 不可达：重点检查应用监听地址、NetworkPolicy、CNI 路由和 Node 网络
  • Service 可达、Ingress 不可达：重点检查公网 DNS、LoadBalancer、IngressClass、路由规则、TLS 和 Controller 日志

检查策略与入口

kubectl get networkpolicy -A
kubectl describe ingress -n <ns>
kubectl get gateway,httproute -A

面试回答

CNI 负责让 Pod 获得 IP 并实现 Pod 网络；CoreDNS 将稳定的 Service 名称解析为 ClusterIP；Service 和 EndpointSlice 把流量转发到动态 Pod；NetworkPolicy 限制允许的通信；LoadBalancer 将外部连接带入集群；Ingress Controller 根据 Ingress 声明执行 HTTP/HTTPS 路由。排障时应沿 DNS、Service、EndpointSlice、策略、CNI 和应用端口逐层验证。

复习与应用

用一次外部超时解释如何逐跳缩小范围；NetworkPolicy 生效前要确认哪些实现和选择器条件？
