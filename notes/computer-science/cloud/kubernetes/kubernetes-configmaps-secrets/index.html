Kubernetes ConfigMap 与 Secret

2026-03-25

#Cloud#Kubernetes

理解主线

配置更新有三个独立状态：API 对象改变、内容进入容器、应用重新读取。环境变量和卷投射的更新语义不同，Secret 的 Base64 编码也不等于加密或授权。

学习目标

学完本章后，应当能够：

  • 区分 ConfigMap 与 Secret 的适用范围，并理解 Base64 不等于加密。
  • 选择环境变量或 Volume 投射方式，说明变更何时能被容器和应用感知。
  • 设计可审计、可灰度、可回滚的配置发布和密钥轮换流程。
  • 从对象引用、键名、挂载、应用 reload 与 RBAC 多层定位配置故障。

ConfigMap/Secret 只是 API 中的配置来源。配置“对象已更新”、文件“已投射”和应用“已重新加载”是三个不同状态，必须分别验证。

ConfigMap 概念

ConfigMap 用于存储配置数据，并将其提供给容器。

图：ConfigMap、Kubernetes Secret 和外部密钥系统向应用交付配置/密钥，以及环境变量与 Volume 两种生效路径。

  • 提供向容器注入配置数据的方式。
  • 可存储完整文件或键值对。
    • 以文件形式存储时，键是文件名，值是文件内容。
    • 内容可以是 JSON、XML、键值对等。

Pod 可通过以下方式使用 ConfigMap：

  • 环境变量（键值对）。
  • ConfigMap Volume（以文件方式访问）。

创建 ConfigMap

# 从 ConfigMap 清单创建
kubectl create -f [yaml_name.yaml]
# 使用配置文件中的数据创建 ConfigMap
kubectl create configmap [cm_name] --from-file=[file_path]
# 从环境变量文件创建 ConfigMap
kubectl create configmap [cm_name] --from-env-file=[file_path]
# 从单个数据值创建 ConfigMap
kubectl create configmap [cm_name] --from-literal=[key]=[value]

配置变更与密钥轮换

配置的生效语义

  • 通过 环境变量 注入的 ConfigMap/Secret，不会自动更新到已运行的容器，通常需要滚动重启工作负载。
  • 通过 volume 投射的 ConfigMap/Secret 会在 kubelet 同步后更新文件，但应用是否自动 reload 取决于应用本身；使用 subPath 挂载时不会自动更新。
  • 生产配置变更要有版本记录、灰度范围、验证指标和回滚版本；不要直接修改后假设所有 Pod 已生效。
# 变更后安全触发滚动重启，并观察发布状态
kubectl rollout restart deployment/<name> -n <ns>
kubectl rollout status deployment/<name> -n <ns> --timeout=10m

密钥安全检查

  • 为业务 ServiceAccount 授予最小化的 get/list Secret 权限；避免使用默认 ServiceAccount。
  • 密钥轮换应支持新旧凭据短暂并存，并在应用切换和验证后吊销旧凭据。
  • 禁止用 kubectl get secret -o yaml 的输出直接粘贴到工单、日志或代码仓库；调试输出应脱敏。

文件中的键值对

# 使用文件中的数据创建 ConfigMap
kubectl create configmap [cm_name] --from-file=[file_path]

环境变量文件

# 使用文件中的数据创建环境变量 ConfigMap
kubectl create configmap [cm_name] --from-env-file=[file_path]

使用 ConfigMap

kubectl

# 获取 ConfigMap
kubectl get cm [cm_name] -o yaml
kubectl describe cm [cm_name]

选择键作为环境变量

仅加载 Pod 所需的键。

将所有键作为环境变量

可使用 envFrom 将 ConfigMap 的所有键值加载为环境变量。

挂载到容器（Volume）

每个键会转换为一个文件，值写入该文件中。

Secret 概念

Secret 是包含少量敏感数据（如密码、令牌或密钥）的对象。

  • Kubernetes 可以存储密码、令牌、密钥和证书等敏感信息。
  • Secret 可以避免把敏感数据直接固化进容器镜像或普通应用配置，但 Secret 对象本身仍需严格保护。
  • Pod 可以将 Secret 作为文件或环境变量使用。
  • Kubelet 只会获取调度到本 Node 的 Pod 所需的 Secret。
  • Secret Volume 使用内存文件系统向容器投射数据，避免将该 Volume 内容持久化到节点磁盘；但 Secret API 对象仍存储在 etcd 中。

Secret 最佳实践：

  • 启用 API Server 的 encryption at rest，确保 Secret 写入 etcd 前经过静态加密；Kubernetes 默认并不保证 Secret 在 etcd 中已加密。
  • 严格限制 etcd、Secret API、Pod 创建权限，并遵循最小权限 RBAC。
  • 为 API Server 到 etcd、以及 etcd 节点之间的通信启用 TLS。
  • YAML/JSON 中 data 字段的 Base64 只是可逆编码，不是加密；不要将明文或 Base64 Secret 提交到 Git。
  • 优先使用外部密钥管理系统及其 CSI Driver/Operator，并建立密钥轮换、审计和吊销机制。
  • 通过环境变量注入的 Secret 可能出现在进程环境、调试输出或崩溃信息中；文件挂载通常更便于权限控制和轮换。

创建 Secret

kubectl

# 创建 Secret 并安全存储在 Kubernetes 中
kubectl create secret generic [secret_name] --from-literal=[key]=[value]
# 从文件创建 Secret
kubectl create secret generic [secret_name] --from-file=[key]=[value]
# 从密钥对创建 TLS Secret
kubectl create secret tls [secret_name] --cert=path/to/tls.cert --key=path/to/tls.key

YAML

Secret manifest 的 data 字段使用 Base64 编码只是为了安全传输二进制内容，并不提供保密性。任何获得 manifest 或 Secret API 读取权限的人都可以轻易解码，因此不要在仓库中保存真实密钥。也可使用 stringData 输入明文，由 API Server 转换为 data，但这同样不改变其安全边界。

使用 Secret

查看 Secret 键

# 获取 Secret
kubectl get secrets
# 获取指定 Secret 的 YAML
kubectl get secrets db-passwords -o yaml

环境变量

Volume

每个键会转换为一个文件，值写入该文件中。

示例

apiVersion: v1
kind: ConfigMap
metadata:
  labels:
    app: mongo-secrets-env
  name: mongo-secrets-env
data:
  MONGODB_DBNAME: codeWithDan
  MONGO_INITDB_ROOT_USERNAME: admin

---

kind: StorageClass
apiVersion: storage.k8s.io/v1
metadata:
  name: local-storage
provisioner: kubernetes.io/no-provisioner
# 回收策略作用于 PV，而非 StorageClass 本身。
# 使用此 StorageClass 创建的 PV/PVC 会继承这里设置的回收策略。
reclaimPolicy: Retain
volumeBindingMode: WaitForFirstConsumer

---

# 注意：本地存储 PV 虽可使用，但更推荐 NFS、云存储等更可靠的方案。
# 此示例用于 Docker Desktop Kubernetes；其环境仅支持单个 Node。
# https://kubernetes.io/blog/2018/04/13/local-persistent-volumes-beta/
apiVersion: v1
kind: PersistentVolume
metadata:
  name: mongo-pv
spec:
  capacity:
    storage: 1Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  # StorageClass has a reclaim policy default so it'll be "inherited" by the PV
  # persistentVolumeReclaimPolicy: Retain
  storageClassName: local-storage
  hostPath:
    path: /private/tmp/data/db
    type: DirectoryOrCreate
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values:
          - docker-desktop

---

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mongo-pvc
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: local-storage
  resources:
    requests:
      storage: 1Gi

---

apiVersion: apps/v1
kind: StatefulSet
metadata:
  labels:
    app: mongo
  name: mongo
spec:
  serviceName: mongo
  replicas: 1
  selector:
    matchLabels:
      app: mongo
  template:
    metadata:
      labels:
        app: mongo
    spec:
      volumes:
      - name: mongo-volume
        persistentVolumeClaim:
          claimName: mongo-pvc
        # 仅作示例；此处实际使用环境变量
      - name: secrets
        secret:
          secretName: db-passwords
      containers:
      - env:
        - name: MONGODB_DBNAME
          valueFrom:
            configMapKeyRef:
              key: MONGODB_DBNAME
              name: mongo-secrets-env
        - name: MONGO_INITDB_ROOT_USERNAME
          valueFrom:
            configMapKeyRef:
              name: mongo-secrets-env
              key: MONGO_INITDB_ROOT_USERNAME
        # 从 Secret 读取密码
        - name: MONGO_INITDB_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-passwords
              key: db-password
        image: mongo
        name: mongo
        ports:
        - containerPort: 27017
        resources: {}
        volumeMounts:
        - name: mongo-volume
          mountPath: /data/db
        # 仅作示例；此处实际使用环境变量
        - name: secrets
          mountPath: /etc/db-passwords
          readOnly: true

配置故障 Runbook

kubectl describe pod/<pod> -n <ns>
kubectl get configmap/<name> -n <ns> -o yaml
kubectl get deployment/<name> -n <ns> -o yaml
kubectl rollout status deployment/<name> -n <ns>

涉及 Secret 时避免把值输出到终端、日志或工单。依次确认：

  1. Pod 模板引用的对象名称和键是否存在。
  2. 环境变量或挂载路径是否与应用读取位置一致。
  3. 各 Pod 的 template revision 是否一致，旧 Pod 是否仍在运行。
  4. Volume 文件是否已更新，应用是否支持 reload；subPath 是否阻止自动更新。
  5. 密钥新旧版本是否处于兼容窗口，依赖端是否已接受新凭据。

实践与验收

  • 分别用环境变量和 Volume 注入同一 ConfigMap，更新后比较生效行为。
  • 使用不存在的键制造 Pod 创建错误，通过事件定位并修复。
  • 设计双凭据轮换：发布新凭据、验证应用切换、吊销旧凭据并确认无失败请求。
  • 使用 kubectl auth can-i 验证业务 ServiceAccount 不能读取无关 Secret。

生产基线

  • 配置和密钥有责任人、版本、校验和、变更记录与回滚方式。
  • Secret 在 etcd 中启用静态加密，读取权限最小化，禁止明文进入 Git 和日志。
  • 优先采用外部密钥系统和短期工作负载身份；轮换失败有告警与恢复方案。
  • 对需要重启才能生效的配置，通过受控 rollout 更新并观察核心 SLI。
