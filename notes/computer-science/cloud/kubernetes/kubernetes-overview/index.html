Kubernetes 概览

2026-03-10

#Cloud#Kubernetes

理解主线

Kubernetes 以 API 对象连接多个控制循环。提交配置只是写入期望状态，真正的资源创建、调度与启动由不同组件异步推进，排障时要找停在哪一步。

学习目标

学完本章后，应当能够：

  • 用“声明期望状态 → 控制器持续协调 → 系统逐步收敛”解释 Kubernetes 的工作方式。
  • 说清 API Server、etcd、Scheduler、Controller Manager、Kubelet 与容器运行时的职责边界。
  • 使用 kubectl 查看资源、事件和日志，并判断故障更可能位于应用、Node 还是控制面。
  • 理解本地单节点环境与生产高可用集群的差异，不把实验结论直接套用到生产。

Kubernetes 不是远程执行命令的工具，而是一组围绕 API 对象运行的控制循环。用户声明“想要什么”，各组件协作把“现在是什么”逐步变成期望状态。

特性

Kubernetes 是一个开源系统，用于自动化部署、扩缩容和管理容器化应用。

Kubernetes 提供了一个可弹性运行分布式系统的框架

  • 服务发现与负载均衡（Service Discovery / Load Balancing）
  • 存储编排（Storage Orchestration）
  • 自动发布与回滚（Rollouts / Rollbacks）
  • 自愈（Self-healing）
  • Secret 与配置管理
  • 水平扩缩容（Horizontal Scaling）

基础架构

Kubernetes Cluster=N Control Plane Nodes+M Worker Nodes(N,M≥1)\text{Kubernetes Cluster} = N\ \text{Control Plane Nodes} + M\ \text{Worker Nodes} \quad (N,M\geq1)Kubernetes Cluster=N Control Plane Nodes+M Worker Nodes(N,M≥1)

图：从期望状态提交到控制面 Reconcile，再到 Worker Node 执行的完整控制链路。

现代 Kubernetes 更推荐使用 Control Plane（控制面），而不是 Master。生产环境通常部署 3 个或更多奇数个控制面节点，以保证 etcd 和控制面的高可用。

Pod 与容器

  • 一个 Pod 中可有多个 Container
  • 一个 Node 中也可有多个 Pod

核心构成

  • Service：为 Pod 提供稳定访问入口和服务发现。
  • Deployment：声明式管理无状态应用的部署与发布。

使用 kubectl 与集群交互

  • etcd: Kubernetes 的一致性键值存储，持久化集群 API 对象和控制面状态，是集群事实数据的主要存储位置
  • API Server: 控制面的统一入口，负责 API 请求的认证、鉴权、准入校验与持久化；kubectl、控制器、Scheduler 和 Kubelet 都通过它读写集群状态
  • Controller Manager: 运行 Deployment、ReplicaSet、Node 等控制器，持续比较期望状态与实际状态，并通过 Reconcile 控制循环推动系统收敛
  • Scheduler: 监听尚未绑定 Node 的 Pod，经过过滤和评分后选择合适的 Node；它只负责调度决策，不负责启动容器

kubectl 并不是把命令逐级转发给 Controller Manager。它向 API Server 提交期望状态，随后各控制面组件通过监听 API 对象异步协作。

节点（Node）

  • Kubelet: 每个 Node 上的节点代理，向 API Server 注册 Node，并根据 PodSpec 调用容器运行时管理 Pod 中的容器
  • Container Runtime: 通过 CRI 运行和管理容器，例如 containerd、CRI-O
  • CNI/IPAM: 为 Pod 配置网络接口、路由并分配 Pod IP；具体能力由所使用的 CNI 插件提供
  • Kube-Proxy: 监听 Service 和 EndpointSlice，在 Node 上维护转发规则，实现 Service ClusterIP/NodePort 到后端 Pod 的四层转发；它不负责分配 Pod IP

使用场景

  • 在本地模拟生产环境
  • 从 Docker Compose 迁移到 Kubernetes
  • 创建端到端测试环境
  • 验证应用能否正确扩缩容
  • 验证 Secret 与配置是否正确生效
  • 构建性能测试场景
  • 构建工作负载场景（CI/CD 等）
  • 学习如何使用发布策略
  • 协助 DevOps 创建资源并排查问题

部署方式

  1. minikube
  2. Docker Desktop
  3. kubeadm
  4. kind

kubectl

命令 作用
kubectl version 查看版本
kubectl cluster-info 查看集群信息
kubectl get all 获取 Pod、Deployment、Service 等资源信息
kubectl get pods 仅获取 Pod 信息
kubectl run [pod-name] --image=[image-name] 创建独立 Pod
kubectl port-forward [pod] [ports] 将本地端口转发到 Pod
kubectl expose 为 Deployment/Pod 暴露端口
kubectl create [resource] 创建资源
kubectl apply [resource] 创建或修改资源

可以为 kubectl 设置别名

Windows:

Set-Alias -Name k -Value kubectl

Mac/Linux

alias k="kubectl"

Web UI Dashboard（Mac）

旧版原生 Dashboard 已经弃用，现使用 Headlamp

安装后即可直接查看本地运行的集群。

故障排查

日志

# 查看 Pod 中容器的日志
kubectl logs [pod_name]
# 查看 Pod 内指定容器的日志
kubectl logs [pod_name] -c [container_name]
# 查看上一次运行的容器日志
kubectl logs -p [pod_name]
# 持续输出 Pod 日志
kubectl logs -f [pod_name]
# 持续观察资源变化
kubectl get pod [pod_name] --watch

查看资源详情

# 查看 Pod 详情
kubectl describe pod [pod_name]
# 以 YAML 格式查看 Pod
kubectl get pod [pod_name] -o yaml
# 以 YAML 格式查看 Deployment
kubectl get deployment [deployment_name] -o yaml

进入容器 Shell

kubectl exec -it [pod-name] -- sh

集群级故障的首轮判断

现象 首先检查 常见方向
多个命名空间的 Pod 同时异常 API Server、Node 状态、kubectl get events -A 控制面、网络、节点池或镜像仓库
新 Pod 长期 Pending kubectl describe pod、节点可分配资源与 taint 资源不足、污点容忍、PVC 未绑定、调度约束
单节点 Pod 集中异常 kubectl describe node、节点条件和 kubelet 日志 DiskPressure、MemoryPressure、网络或运行时异常

排障时先确认影响面和近期变更，避免直接重启节点；恢复后再保存事件、日志和时间线用于复盘。

实践与验收

  1. 使用 kind、minikube 或 Docker Desktop 准备一个练习集群。
  2. 执行下列命令，分别找到控制面组件、Node 和普通工作负载：
kubectl cluster-info
kubectl get nodes -o wide
kubectl get pods -A -o wide
kubectl get events -A --sort-by=.lastTimestamp
  1. 创建一个 nginx Pod，观察从对象创建到获得 Pod IP 的过程，再删除它。
  2. 验收时应能回答：Scheduler 为何不启动容器、Kubelet 为何不决定副本数、etcd 故障为何会影响整个控制面。

生产操作前还应确认当前 context，防止误操作集群：

kubectl config current-context
kubectl config get-contexts
