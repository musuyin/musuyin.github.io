Kubernetes 调度与资源治理

2026-08-13

#Kubernetes#Scheduling#Autoscaling#SRE

理解主线

调度、扩缩容和配额共享资源声明，却解决不同问题：能放哪里、需要多少、谁可以创建。requests 同时影响放置和部分扩缩容判断，limits 则约束运行时资源使用。

学习目标

学完本章后，应当能够：

  • 解释 requests 如何影响调度与 HPA，limits 如何影响节流和 OOM。
  • 使用 Quota、LimitRange、PriorityClass、亲和性、污点与容忍实现资源治理。
  • 区分 HPA、VPA 与 Node Autoscaling 的控制对象，识别控制环冲突。
  • 根据 Scheduler 事件系统排查 Pending，而不是盲目增加 Node。

心智模型：调度解决“这个 Pod 能放在哪里”，扩缩容解决“需要多少 Pod 或 Node”，配额与优先级解决“资源紧张时谁可以使用”。这些控制环共享 requests，错误配置会互相放大。

治理目标

图：业务指标触发 HPA、Scheduler 判断可调度性、Cluster Autoscaler 扩 Node，以及 VPA、Quota、PDB 等约束的反馈链。

资源治理要同时解决四个问题：

  1. 谁可以在什么范围创建资源。
  2. Pod 至少需要多少资源、最多能使用多少资源。
  3. Pod 应该调度到哪些 Node，以及故障域如何分布。
  4. 负载与 Node 容量如何随需求变化。

Namespace

Namespace 用于划分资源名称和管理边界，适合按环境、团队或租户组织资源。Namespace 本身不提供完整安全隔离，还需结合 RBAC、ResourceQuota、LimitRange、NetworkPolicy 和 Pod Security Admission。

生产环境避免长期把业务部署到 default，并为资源明确 Namespace：

kubectl create namespace production
kubectl config set-context --current --namespace=production

requests 与 limits

Request 和 Limit 的核心设计意义

为什么需要 request 和 limit？

在集群中，同一个 Node 上运行多个 Pod，需要解决两个问题：

问题 1：调度器如何判断这个 Pod 能否放在某个 Node 上？
  - 不能只看当前实时使用量（实时值波动太大）
  - 需要一个"预期需要量"来做调度决策

问题 2：一个 Pod 用了多少资源是"超限"？该如何处理？
  - Pod 是否能临时突增使用资源（短时间峰值）
  - 长期超用应该如何处理（限制还是驱逐）

Request 与 Limit 分工：

┌─────────────────────────────────────────────────────┐
│  Pod 资源管理的三个阶段                              │
│                                                     │
│  调度阶段（Request）                               │
│  ├─ Scheduler 看 request 值                         │
│  ├─ 检查 Node 剩余容量是否 ≥ request               │
│  └─ 决定能否放这个 Pod                              │
│                                                     │
│  运行阶段（Limit）                                 │
│  ├─ 容器实际使用资源 < limit                        │
│  │  └─ 正常运行，允许临时突增（CPU 可争抢，内存）  │
│  ├─ 容器实际使用资源 ≈ limit                        │
│  │  └─ 可能被限流（CPU throttling）或驱逐（内存）  │
│  └─ 单位时间被驱逐/限流的次数                       │
│     └─ 是告警信号（需要提高 limit 或加 Pod）       │
└─────────────────────────────────────────────────────┘

关键概念对比：

维度 Request Limit
定义 Pod 预期需要多少资源 Pod 最多能用多少资源
发生时机 调度时（Scheduler 决策） 运行时（Kubelet enforcement）
作用角色 Scheduler 的可调度性判断 Kubelet 的资源隔离
CPU 超过 不触发调度决策 被 CFS throttling（限流）
内存超过 不触发调度决策 Pod 被 OOMKilled（驱逐）
建议关系 limit ≥ request（通常 1.5-2 倍） limit ≥ request

类比理解（面试好用）：

Request 和 Limit 就像“航空公司的座位管理”：

  • Request = 你提前购票时说“我需要一个座位”，航空公司据此确认是否能接待你

    • 航空公司看 request 来决定是否给你分配座位（调度决策）
    • 航空公司不会说“你这趟航班只坐了 0.5 个座位，让你分享一个”
    • Request 影响的是整体规划

  • Limit = 上飞机后，你最多能占用 1 个座位，不能占 1.5 个

    • 如果你超过座位（比如 limit 定为 1 个座位，你想占 1.2 个）
    • 乘务员会制止你（内存超 limit → OOMKilled；CPU 超 limit → 限流）
    • Limit 影响的是运行时的隔离

错用会怎样：

Request 偏低：
  ┌──────────────────────────────┐
  │ Node 可用：5GB 内存            │
  │ Pod1: request=1GB, limit=3GB  │
  │ Pod2: request=1GB, limit=3GB  │
  │ Pod3: request=1GB, limit=3GB  │
  │ （Scheduler 都允许）           │
  │                              │
  │ 实际运行：                     │
  │ Pod1 用 2GB, Pod2 用 2GB       │
  │ Pod3 要 2GB → 内存不足！       │
  │ Pod3 被 OOMKilled             │
  └──────────────────────────────┘
  
  原因：Request 不能真实反映需求，导致过度装箱


Request 偏高：
  ┌──────────────────────────────┐
  │ Node 可用：5GB 内存            │
  │ Pod1: request=2GB, limit=4GB  │
  │ Pod2: request=2GB, limit=4GB  │
  │ Pod3: request=2GB, limit=4GB  │
  │ （第 3 个 Pod Pending）        │
  │                              │
  │ 实际只用 1GB×3 = 3GB          │
  │ 但 2GB×3 = 6GB > 5GB，无法调度  │
  │ 浪费了 Node 容量，误导扩容     │
  └──────────────────────────────┘

  原因：Request 过高导致资源浪费、假扩容

详细对比表

配置 调度/运行语义
CPU request Scheduler 计算 Node 是否可容纳 Pod；HPA 的 CPU 利用率通常也以它为分母
Memory request Scheduler 预留容量的重要依据，也影响 Pod QoS
CPU limit 超过时通常被 CFS throttling，不会因此直接 OOM
Memory limit 超过时容器可能被 OOMKilled

调度决策的核心逻辑

Scheduler 主要依据 request 而非实时使用量调度。request 偏低会导致过度装箱和节点压力；偏高会造成资源浪费、Pod Pending，并误导节点自动扩缩容。

Pod QoS 分为 Guaranteed、Burstable、BestEffort。节点资源压力下，QoS 较低且超用 request 的 Pod 通常更容易被驱逐，但 QoS 不是业务优先级替代品。

kubectl top pod -A --containers
kubectl get pod/<pod> -n <ns> -o jsonpath='{.status.qosClass}{"\n"}'
kubectl describe node/<node>

设定建议

Request 的设定：

  • 基于历史实际使用量的 P50/P95
  • 加上启动峰值和业务增长率预留
  • 定期审查和调整（不是一成不变）

Limit 的设定：

  • 通常是 request 的 1.5-2 倍
  • 给予容器处理突发流量的余地
  • 防止单个 Pod 吃掉整个 Node 的资源

LimitRange

LimitRange 在单个 Namespace 中约束或默认化容器、Pod、PVC 的 request/limit。

apiVersion: v1
kind: LimitRange
metadata:
  name: container-defaults
  namespace: production
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    default:
      cpu: 1
      memory: 1Gi
    min:
      cpu: 10m
      memory: 32Mi
    max:
      cpu: 4
      memory: 8Gi

默认值只是安全网，不能代替基于真实负载测量的容量规划。

ResourceQuota

ResourceQuota 限制 Namespace 的资源总量或对象数量。若配额追踪 CPU/内存 requests 或 limits，新建 Pod 通常必须显式设置相关字段，或由 LimitRange 注入默认值。

apiVersion: v1
kind: ResourceQuota
metadata:
  name: production-quota
  namespace: production
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "200"
    persistentvolumeclaims: "50"
    services.loadbalancers: "5"
kubectl describe resourcequota -n production
kubectl describe limitrange -n production

PriorityClass 与抢占

PriorityClass 表示 Pod 的调度优先级。当高优先级 Pod 无法调度时，Scheduler 可能抢占低优先级 Pod。错误使用高优先级会把普通业务变成“不可驱逐对象”，加剧故障。

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: business-critical
value: 100000
globalDefault: false
description: 仅用于经过评审的核心在线服务
  • 平台预先定义少量等级，不允许团队随意创建极高值。
  • system-cluster-critical、system-node-critical 保留给集群关键组件。
  • 抢占对 PDB 的遵守是 best effort，不能把 PDB 当成绝对保护。

Node 选择与亲和性

nodeSelector 与 Node Affinity

nodeSelector 是简单的精确标签匹配；Node Affinity 支持 In、NotIn、Exists 等表达式，并分为硬约束与软偏好。

spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node.kubernetes.io/instance-type
            operator: In
            values: [memory-optimized]
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values: [zone-a]

硬约束过多会制造无法调度的 Pod，也会限制节点自动扩缩容的选择空间。业务偏好尽量使用 preferred，只有硬件、合规或存储约束才使用 required。

Pod 亲和性与反亲和性

  • Pod Affinity：让相关 Pod 靠近，减少网络延迟。
  • Pod Anti-Affinity：让相同应用分散，降低单一故障域影响。
  • topologyKey 决定 Node、Zone 等故障域，常用 kubernetes.io/hostname 和 topology.kubernetes.io/zone。

严格反亲和性在资源紧张或故障域不足时会导致 Pending。对于多副本均匀分布，通常优先使用 Topology Spread Constraints。

Taint 与 Toleration

Taint 作用于 Node，Toleration 作用于 Pod。Toleration 只表示 Pod 可以容忍该污点，并不保证一定调度到该 Node；若要专用节点，通常同时配置 Node Affinity。

kubectl taint nodes <node> dedicated=gpu:NoSchedule
kubectl describe node/<node> | grep -A3 Taints
spec:
  tolerations:
  - key: dedicated
    operator: Equal
    value: gpu
    effect: NoSchedule
  nodeSelector:
    dedicated: gpu

常见 effect：

  • NoSchedule：新 Pod 不会调度，已运行 Pod 不受影响。
  • PreferNoSchedule：尽量避免调度，是软限制。
  • NoExecute：不容忍的已有 Pod 也会被驱逐；可用 tolerationSeconds 延迟驱逐。

HPA

HorizontalPodAutoscaler 自动修改 Deployment、StatefulSet 等可扩缩对象的副本数，不适用于 DaemonSet。资源指标通常来自 Metrics API，自定义/外部指标需要相应 Adapter。

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 3
  maxReplicas: 20
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Percent
        value: 100
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60

CPU averageUtilization 是相对 CPU request 的百分比。未设置 request 会使相应 Pod 的 CPU 利用率无法计算。HPA 与手工设置 .spec.replicas 可能相互覆盖，应明确唯一控制方。

kubectl get hpa -A
kubectl describe hpa/api -n production
kubectl top pod -n production
kubectl get apiservice | grep metrics

VPA

VerticalPodAutoscaler 根据历史与实时使用量建议或调整容器 requests。VPA 不随 Kubernetes 核心默认安装，需要额外部署其组件与 CRD。

常见模式：

  • Off：只生成建议，适合先做容量分析。
  • Initial：只在 Pod 创建时应用建议。
  • Recreate/Auto：可能需要重建 Pod 才能调整资源，使用前评估中断。

CPU/内存型 HPA 与 VPA 同时控制相同资源时可能产生反馈冲突。常见组合是 VPA 先用 Off 生成建议，HPA 按业务指标扩副本；或者明确拆分各自控制的指标。

Node Autoscaling / Cluster Autoscaler

节点自动扩缩容与 HPA 解决的问题不同：HPA 创建更多 Pod，节点自动扩缩容为无法调度的 Pod 提供 Node，并在容量空闲时合并 Node。

Cluster Autoscaler 基于预配置 Node Group 增减 Node。它主要依据 Pending Pod 的 request、调度约束和 Node Group 模板判断是否扩容，不以实际 CPU 使用率直接扩 Node。

完整链路：

业务指标升高 → HPA 增加副本 → 新 Pod 因容量不足 Pending
→ Cluster Autoscaler 扩 Node → Scheduler 放置 Pod
→ 负载下降、HPA 缩副本 → 空闲 Node 被安全合并

PDB、Local PV、严格亲和性、安全 Pod、不可驱逐注解等都可能阻止缩容。生产环境必须对扩容失败、云配额不足和 Pending 时长告警。

Pending 排障 Runbook

kubectl describe pod/<pod> -n <ns>
kubectl get events -n <ns> --sort-by=.lastTimestamp
kubectl get nodes -L topology.kubernetes.io/zone,node.kubernetes.io/instance-type
kubectl describe node/<node>
kubectl get resourcequota,limitrange -n <ns>
kubectl get hpa -n <ns>

按 Scheduler 事件分类：

  • Insufficient cpu/memory：检查 request、Node 可分配量与扩容器。
  • untolerated taint：检查 taint/toleration，避免盲目添加 Exists。
  • didn't match Pod's node affinity/selector：核对 Node 标签与硬约束。
  • didn't match pod anti-affinity：检查副本数与可用故障域。
  • unbound immediate PersistentVolumeClaims：转到 PVC/StorageClass 排障。
  • ResourceQuota 拒绝创建：查看 admission 返回信息与配额使用量。

生产基线

  • 每个 Namespace 配置责任人、RBAC、Quota、LimitRange 和成本标签。
  • requests 根据 P50/P95 用量、启动峰值和 SLO 定期校准；内存 limit 留出合理峰值与 GC 空间。
  • 核心服务使用至少两个故障域，避免不必要的硬亲和性。
  • HPA 设置最小冗余、最大成本边界、缩容稳定窗口和扩容失败告警。
  • VPA 先以建议模式观察；节点自动扩缩容必须演练云配额不足、Node 启动失败和安全缩容。

实践与验收

  • 为练习 Namespace 设置 LimitRange 与 ResourceQuota，观察未声明资源和超额创建的结果。
  • 用不可满足的 node affinity 或未容忍 taint 制造 Pending，再通过事件修复。
  • 对 CPU 负载配置 HPA，确认指标、requests、期望副本和实际副本变化一致。
  • 制造 HPA 扩容后 Pod Pending，判断瓶颈在指标、工作负载还是 Node 容量。

验收标准：看到 Pending 或扩容失效时，能够用证据区分资源不足、约束冲突、配额拒绝、指标缺失与节点扩容失败。
