Kubernetes 集群运维

2026-08-13

#Kubernetes#kubeadm#etcd#SRE

理解主线

集群运维同时维护组件版本、证书和一致性。升级与恢复先确认前置条件，再分批执行；etcd 状态、业务卷和外部依赖需要分别备份与验证。

学习目标

学完本章后，应当能够：

  • 解释 kubeadm 高可用控制面、API Server 入口与 etcd quorum 的关系。
  • 执行集群健康检查、证书检查、Node 加入/退出和逐级版本升级。
  • 安全备份 etcd，并在隔离环境验证恢复、RPO 与 RTO。
  • 在控制面、etcd、kubelet、容器运行时和网络之间定位集群级故障。

心智模型：集群运维是在维护一组有版本偏差约束、证书时限和一致性要求的分布式组件。备份、升级和节点维护都必须先验证前置条件，再分批执行并保留回退路径。

kubeadm 集群架构

图：高可用 kubeadm 控制面、API Server 负载均衡、etcd quorum，以及备份、证书和逐级升级的运维关系。

kubeadm 用于引导和维护符合 Kubernetes 约定的集群，但不会替你安装 CNI、监控、日志、备份和完整生命周期平台。

典型控制面组件：

  • kube-apiserver：API 入口，负责认证、鉴权、准入和对象读写。
  • kube-controller-manager：运行控制循环，使实际状态收敛到期望状态。
  • kube-scheduler：为未绑定 Node 的 Pod 选择 Node。
  • etcd：保存 Kubernetes API 对象和控制面状态。
  • kubelet：在每个 Node 上管理 Pod；控制面组件在 kubeadm 集群中通常以 Static Pod 运行。

kubeadm 管理的 Static Pod manifest 通常位于：

/etc/kubernetes/manifests/
├── etcd.yaml
├── kube-apiserver.yaml
├── kube-controller-manager.yaml
└── kube-scheduler.yaml

kubelet 监视该目录，文件变化会触发对应 Static Pod 重建。不要直接无备份地修改 manifest；集群配置应保留为代码并经过评审。

高可用拓扑

拓扑 特点 适用场景
Stacked etcd 每个控制面 Node 同时运行 etcd，部署简单、故障域耦合 常见 kubeadm HA 集群
External etcd etcd 与控制面 Node 分离，故障域与扩缩容独立，运维更复杂 有独立 etcd 运维能力的场景

高可用控制面通常在 API Server 前放置负载均衡器，并部署奇数个 etcd 成员。增加 etcd 成员不等于提高性能，成员数和拓扑应遵循 etcd 官方建议。

日常健康检查

kubectl cluster-info
kubectl get --raw='/readyz?verbose'
kubectl get nodes -o wide
kubectl get pods -n kube-system -o wide
kubectl get events -A --sort-by=.lastTimestamp

控制面还应监控：

  • API Server 请求成功率、延迟、inflight request 与 429/5xx。
  • etcd leader、成员健康、磁盘 fsync/commit 延迟、DB 大小与剩余空间。
  • Scheduler 调度延迟、Pending Pod 和失败原因。
  • Controller workqueue 深度、重试和 leader election。
  • 证书剩余有效期、Node 心跳和 kubelet 状态。

etcd 备份

etcd 是控制面事实数据存储。备份必须加密、限制访问、异地保存并定期做完整恢复演练。

在可访问本地 etcd 证书和端点的控制面 Node 上，可以使用类似命令创建快照；证书路径和端点以实际 manifest 为准：

ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /secure-backup/etcd-snapshot.db

etcdutl --write-out=table \
  snapshot status /secure-backup/etcd-snapshot.db

备份计划至少记录：

  • 集群标识、Kubernetes/etcd 版本、创建时间和操作者。
  • 快照校验结果、文件哈希、加密方式和保留周期。
  • /etc/kubernetes/ 中 PKI、kubeconfig、manifest 与 kubeadm 配置的安全备份。
  • 外部依赖：CNI、CSI、Ingress/Gateway、CRD/Operator 和云资源声明。

etcd 快照只包含 Kubernetes API 数据，不包含 PV 中的业务数据；业务数据需要独立一致性备份。

etcd 恢复

恢复 etcd 是破坏性灾难恢复操作，会改变集群控制面状态。必须在维护窗口或事故指挥下执行，先保护现有数据目录并确认恢复点。

恢复原则：

  1. 停止所有 API Server，避免恢复期间继续读写 etcd。
  2. 使用与快照兼容的 etcd 版本和 etcdutl 恢复到新的、空的数据目录。
  3. 对多成员 etcd 按恢复方案配置成员名称、peer URL 与初始集群。
  4. 修改 Static Pod manifest 指向恢复后的数据目录/集群。
  5. 启动 etcd、验证成员健康，再启动 API Server 和其他控制面组件。
  6. 验证 API 对象、Node、关键工作负载、存储和外部控制器。

单成员示意命令，参数必须按实际集群修改：

etcdutl --data-dir=/var/lib/etcd-restored \
  snapshot restore /secure-backup/etcd-snapshot.db

etcd v3.5 之后恢复推荐使用 etcdutl，不要把旧教程中的 etcdctl snapshot restore 直接用于生产。恢复演练必须在隔离环境完成，并记录 RTO、RPO 与验证结果。

证书管理

# 检查 kubeadm 管理证书的过期时间
kubeadm certs check-expiration

# 按需续期，生产执行前先备份 /etc/kubernetes
kubeadm certs renew all

注意：

  • kubeadm 在控制面升级时通常会续期证书；是否启用取决于升级参数。
  • HA 集群需要在每个控制面 Node 上执行相应续期。
  • 续期后需要让使用证书的控制面组件重启，并更新分发在外部的 kubeconfig。
  • kubeadm certs renew 使用现有证书属性，若要修改 SAN 等内容，需要按新的 kubeadm 配置重新生成证书。
  • 外部 CA、外部 etcd 或企业 PKI 场景应采用对应流程，不能机械套用上述命令。

证书过期常表现为 x509: certificate has expired or is not yet valid。同时检查系统时间、NTP、客户端 kubeconfig 和控制面证书，不要只续期单个文件。

Node 扩容

# 在控制面生成短期 join 命令
kubeadm token create --print-join-command

# 新 Node 完成内核、容器运行时、kubelet/kubeadm 和网络前置配置后执行 join
kubeadm join <control-plane-endpoint>:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

# 控制面验证
kubectl get nodes -o wide
kubectl describe node/<new-node>

扩容前确认 Kubernetes 版本偏差、容器运行时、cgroup driver、内核模块、时间同步、DNS、镜像仓库、CNI MTU、安全组和 Node 标签/taint。

Node 缩容与维护

kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=15m
kubectl delete node <node>

随后才能在目标 Node 执行 kubeadm reset 并释放底层主机。kubeadm reset 会清理 kubeadm 管理的本地状态，是破坏性操作；它不会自动完整清理所有 CNI 规则、iptables/IPVS 和用户数据，应按所用发行版/CNI 的卸载流程处理。

删除 Node 前确认：

  • PDB、StatefulSet、Local PV 和 emptyDir 数据影响。
  • 关键服务在其余故障域仍有足够容量。
  • Node 上没有未被控制器管理的裸 Pod 或重要静态数据。
  • 云负载均衡、监控、CMDB 和自动扩缩容组状态会同步更新。

版本升级

升级必须查看当前版本对应的 Version Skew Policy 和 kubeadm 官方升级指南。通常按次要版本逐级升级，并遵循以下顺序：

  1. 阅读 Release Notes、弃用 API 和组件兼容矩阵。
  2. 备份 etcd、/etc/kubernetes/、集群配置与关键业务数据，并验证恢复路径。
  3. 在预生产执行升级和回滚演练。
  4. 升级第一台控制面 Node：先 kubeadm，再执行 kubeadm upgrade apply，随后 kubelet/kubectl。
  5. 逐台升级其他控制面 Node，验证 etcd quorum 与 API 可用性。
  6. 逐台 cordon/drain 并升级 Worker Node，保持最小服务容量。
  7. 验证系统组件、CNI/CSI、Ingress/Gateway、监控、CRD/Operator 和核心 SLI。
  8. 观察稳定后清理升级备份并更新资产、Runbook 和版本基线。
kubeadm upgrade plan
kubectl get nodes
kubectl get pods -A
kubectl get --raw='/readyz?verbose'

禁止同时升级 Kubernetes、操作系统、容器运行时、CNI 和业务大版本；多个变量会显著增加回滚和归因难度。

控制面故障排查

kubectl 无法连接 API Server

# 从客户端确认地址、证书和网络
kubectl config view --minify
kubectl cluster-info
curl --cacert <cluster-ca.crt> https://<control-plane-endpoint>:6443/livez

# 在控制面 Node 检查 kubelet、容器运行时和 Static Pod
systemctl status kubelet
journalctl -u kubelet --since "30 min ago"
crictl ps -a
crictl logs <kube-apiserver-container-id>
ls -l /etc/kubernetes/manifests

判断：

  • 负载均衡地址失败但单个 API Server 正常：检查 LB、健康检查和安全组。
  • API Server 容器反复退出：检查证书、manifest 参数、端口、etcd 连通性和磁盘。
  • 所有 API Server 都无法访问 etcd：检查 etcd quorum、证书、磁盘空间和网络。

API 可用但对象不收敛

kubectl get lease -n kube-system
kubectl get pods -n kube-system
kubectl describe pod/<scheduler-or-controller-pod> -n kube-system
crictl logs <container-id>
  • 新 Pod 不调度：检查 Scheduler、Pending 事件和 admission webhook。
  • Deployment 副本不恢复：检查 Controller Manager leader、workqueue 和权限。
  • API 请求卡住：检查不可用 admission webhook、APIService、etcd 延迟和 API Server inflight request。

Node 大面积 NotReady

优先判断是否为控制面误报、网络分区、证书/时间问题、CNI 故障或统一配置变更。不要同时重启全部 Node；保留一个故障样本用于证据采集，分批恢复并持续观察业务 SLI。

变更与灾备基线

  • 所有集群配置、版本、插件和证书责任人可追踪，控制面变更走评审和维护窗口。
  • etcd 自动备份、加密异地保存，至少按季度执行隔离恢复演练。
  • 证书剩余有效期提前告警，避免依赖人工记忆。
  • Node 与控制面逐台维护，遵守 PDB 和容量水位，不同时破坏同一故障域。
  • 升级前有兼容性检查、预生产演练、回退标准和稳定观察窗口。
  • 控制面、etcd、CNI、CSI、DNS 与入口组件都有 Runbook 和值班告警。

实践与验收

  • 完成一次日常健康检查并保存基线：API、组件、Node、系统 Pod、事件与容量。
  • 创建 etcd 快照，校验状态，在隔离环境恢复并验证关键 API 对象。
  • 检查全部证书到期时间，形成提前轮换和告警计划。
  • 对一个 Worker Node 执行 cordon、drain、维护验证与 uncordon。
  • 在测试集群按官方顺序完成一个小版本升级，记录兼容性、观察项和回退点。

验收标准：不仅命令执行成功，还应证明 API、工作负载、网络、存储和核心 SLI 恢复，并留下时间线和证据。
