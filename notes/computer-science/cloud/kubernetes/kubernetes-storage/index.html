Kubernetes Storage

2026-03-24

#Cloud#Kubernetes

理解主线

把存储分成需求、供给和挂载三个环节：PVC 描述需求，PV 表示存储资源，StorageClass 与 CSI 参与供应和接入。Pod 的启动故障可能只是存储链路问题的外在表现。

学习目标

学完本章后，应当能够：

  • 解释 Volume、PV、PVC、StorageClass 与 CSI 的职责及绑定链路。
  • 根据数据生命周期和访问方式选择临时存储或持久存储。
  • 读懂访问模式、回收策略、绑定模式和扩容能力对业务的影响。
  • 排查 PVC Pending、Volume Attach/Mount 失败和磁盘空间不足，并避免误删数据。

Pod 只声明“挂载哪个 PVC”，PVC 描述存储需求，StorageClass/CSI 负责供应，PV 代表实际存储。任何一层不匹配，都可能表现为 Pod 无法启动。

概念

Volume 用于为 Pod 和容器保存数据与状态。

图：Pod 引用 PVC、PVC 绑定 PV、StorageClass/CSI 动态供给并最终挂载到底层存储的完整路径。

  • 一个 Pod 可以挂载多个 Volume。
  • 容器通过 mountPath 访问 Volume。

存储类型

  • Volumes
  • PersistentVolumes
  • PersistentVolumeClaims
  • StorageClasses

Volume

  • Volume 引用一个存储位置。
  • 名称必须唯一。
  • Volume 挂载到 Pod，其生命周期是否与 Pod 绑定取决于 Volume 类型。
  • Volume Mount 通过名称引用 Volume，并定义 mountPath。

Volume 类型

  • emptyDir：用于存储临时数据的空目录，生命周期与 Pod 相同；适合在同一 Pod 的容器之间共享文件（临时存储）。
  • hostPath：将 Pod 挂载到 Node 的文件系统。
  • Network File System（NFS）：将 NFS 共享目录挂载到 Pod。
  • configMap/secret：让 Pod 访问 Kubernetes 资源的特殊 Volume 类型。
  • persistentVolumeClaim：为 Pod 提供更持久、且屏蔽底层细节的存储选择。
  • cloud：集群范围的云存储。

emptyDir Volume

apiVersion: v1
kind: Pod
metadata:
  name: nginx-alpine-volume
spec:
  containers:
  - name: nginx
    image: nginx:alpine
    volumeMounts:
      - name: html
        mountPath: /usr/share/nginx/html
        readOnly: true
  - name: html-updater
    image: alpine
    command: ["/bin/sh", "-c"]
    args:
      - while true; do date >> /html/index.html;sleep 10; done
    volumeMounts:
      - name: html
        mountPath: /html
  volumes:
  - name: html
    emptyDir: {} # 生命周期与 Pod 绑定

# kubectl port-forward nginx-alpine-volume 8080:80

PersistentVolume 与 PersistentVolumeClaim

PersistentVolume（PV）是由管理员提供的集群范围存储单元，生命周期独立于 Pod。

PersistentVolumeClaim（PVC）是对存储单元（PV）的申请。

  • PersistentVolume 是依赖网络附加存储（NAS）的集群范围存储资源。
  • 通常由集群管理员提供。
  • 即使 Pod 被重新调度到其他 Node，也仍可供其使用。
  • 依赖 NFS、云存储或其他存储提供方。
  • 通过 PersistentVolumeClaim 与 Pod 关联。

PVC/PV 的核心设计意义

为什么要设计 PVC/PV 这一层抽象？

在 PVC/PV 出现之前，开发者需要直接指定底层存储细节（NFS 服务器地址、云存储 bucket 名等），这导致两个问题：

  1. 耦合度高：应用 YAML 与基础设施紧密耦合，迁移集群或更换存储提供方需要修改所有应用配置
  2. 权限混乱：开发者需要知道集群的底层存储拓扑，这原本应该是运维的职责

PVC/PV 解决方案（声明式分离）：

┌─────────────────────────────────────────────────────┐
│  开发者（应用开发）                                  │
│  ↓                                                   │
│  "我需要 10Gi 可读写存储"  ← PVC（只声明需求）     │
│                                                     │
├─────────────────────────────────────────────────────┤
│  Kubernetes 管理平面                                │
│  ↓                                                   │
│  自动绑定 PVC 到可用的 PV  ← 运维不用介入          │
│                                                     │
├─────────────────────────────────────────────────────┤
│  运维/集群管理员                                    │
│  ↓                                                   │
│  "我提供 100Gi NFS 存储"  ← PV（具体存储资源）     │
└─────────────────────────────────────────────────────┘

关键优势：

角度 好处
开发者 只需关心“我需要多少存储、访问模式”，不用关心底层是 NFS/EBS/Azure Disk
运维 统一管理 PV 资源，开发者申请时自动绑定，不用逐个配置存储挂载
可移植性 同一个应用 YAML（含 PVC）可以跑在不同集群（AWS/Azure/内网 NFS），只需运维提供对应的 PV
生命周期 PV 独立于 Pod，Pod 删除后存储保留，新 Pod 仍可绑定同一 PVC 使用旧数据

类比理解（面试好用）：

PVC/PV 就像“餐厅点菜系统”：顾客（Pod）说“我要份 200g 牛排”（PVC），厨房（运维）准备好 50 份 200g 牛排（PV），系统自动分配一份给这个顾客。顾客不关心牛排从哪来，厨房也不关心每个顾客的具体需求，通过这层抽象双方都轻松了。

PersistentVolume 工作流程

  1. 创建网络存储资源（NFS、云存储等）。
  2. 定义 PV 并提交到 Kubernetes API。
  3. 创建 PVC。
  4. Kubernetes 将 PVC 绑定到 PV。
  5. Pod 的 Volume 引用 PVC。

StorageClass

StorageClass（SC）是一种存储模板，可用于动态供给存储。

  • 用于定义不同等级的存储。
  • 充当存储模板。
  • 支持动态创建 PersistentVolume。
  • 无需预先创建 PV。

StorageClass 的核心设计意义（面试角度）

为什么需要 StorageClass？

在 StorageClass 出现之前，存储供给流程是手动的：

运维需要做的：
1. 在云上创建存储资源（EBS volume、NFS share）
2. 手动创建 PV 对象，指定这个存储资源的详细信息
3. 等待开发者提交 PVC 申请
4. 人工确认是否绑定

这导致几个问题：

  • 扩展性差：每次申请存储都需要运维手动介入
  • 配置复杂：PV 需要写很多云厂商特定的参数（provisioner、parameters）
  • 不够灵活：无法根据不同业务需求灵活选择存储等级（SSD vs HDD、高性能 vs 成本优化）

StorageClass 解决方案（动态供给）：

┌──────────────────────────────────────────────────────┐
│  运维：定义一次 StorageClass 模板                     │
│  ↓                                                    │
│  "名为 fast-ssd 的存储"                              │
│  provisioner: ebs.csi.aws.com                        │
│  parameters: type: gp3, iops: 3000                   │
│                                                      │
├──────────────────────────────────────────────────────┤
│  开发者：每次创建 PVC 时只需引用 StorageClass      │
│  ↓                                                    │
│  PVC:                                                │
│    storageClassName: fast-ssd                        │
│    storage: 20Gi                                     │
│                                                      │
├──────────────────────────────────────────────────────┤
│  Kubernetes 自动化：                                 │
│  ↓                                                    │
│  K8s 看到 PVC → 查找 fast-ssd SC                    │
│  → 调用 ebs.csi.aws.com provisioner                 │
│  → 在 AWS 上创建 20Gi gp3 EBS volume                 │
│  → 自动创建 PV → 自动绑定 PVC                       │
└──────────────────────────────────────────────────────┘

关键优势：

维度 效果
自动化 从 PVC 申请到 PV 创建全自动，无需人工介入
参数化 SC 定义一次，PVC 可重复使用，减少重复配置
多等级 同一集群可以有多个 SC（fast-ssd、standard-hdd、high-throughput），满足不同应用需求
云无关 SC 的 provisioner 负责与云 API 对接，应用 YAML 不变
按需创建 PV 不需要预先创建，PVC 申请时动态创建，充分利用资源

面试类比：

StorageClass 就像“云厂商的模板库”。运维在 AWS 上定义一个“SSD 存储模板”，指定了磁盘类型、IOPS、加密方式等参数。之后开发者每次需要存储时，只需说“给我按 SSD 模板创建 20Gi 存储”，K8s 会自动调用 AWS API 创建对应的 EBS volume 并绑定到 PVC，完全自动化，无需人工操作。

StorageClass 工作流程

  1. 创建 StorageClass（运维定义一次）。
  2. 开发者创建引用该 SC 的 PVC。
  3. Kubernetes 监测到 PVC 并调用 SC 的 provisioner。
  4. Provisioner 在底层存储系统创建存储资源（AWS EBS、Azure Disk 等）。
  5. K8s 自动创建对应的 PV 并绑定到 PVC。
  6. Pod 的 Volume 引用 PVC 进行挂载。

StorageClass 核心参数

参数 说明 例子
provisioner 存储供给器，决定如何在哪个平台创建存储 ebs.csi.aws.com（AWS）、kubernetes.io/azure-disk（Azure）、pd.csi.storage.gke.io（GCP）
parameters 云厂商特定的参数 AWS: type: gp3, iops: 3000；Azure: cachingmode: ReadWrite, kind: Managed
reclaimPolicy PVC 删除后 PV 的回收策略 Retain（保留）、Delete（删除）、Recycle（回收，过时）
volumeBindingMode PV 何时绑定到 PVC Immediate（立即）、WaitForFirstConsumer（等待 Pod 调度）
allowVolumeExpansion 是否允许扩容 true 或 false

SRE：存储故障排查与生产检查

# PVC 长期 Pending：先确认 StorageClass、事件与可匹配 PV
kubectl get pvc,pv,storageclass -n <ns>
kubectl describe pvc/<claim> -n <ns>

# Pod 挂载失败：查看 Pod 事件与 CSI 相关 Pod（名称随环境不同）
kubectl describe pod/<pod> -n <ns>
kubectl get events -n <ns> --sort-by=.lastTimestamp
现象 优先判断 处理方向
PVC Pending StorageClass 是否存在、provisioner 是否工作、容量/访问模式是否匹配 修复 SC/CSI、容量或 PVC 规格，不要直接删 PVC
FailedMount Secret/ConfigMap/PVC 是否存在、CSI 与节点是否健康 根据事件定位对象、权限或节点插件
磁盘即将写满 文件系统使用率、应用日志增长、PVC 扩容能力 清理前确认保留策略；评估在线扩容和应用是否支持

生产环境避免把业务数据放在 hostPath；明确 reclaimPolicy（删除 PVC 后数据是否保留）、备份恢复目标以及故障演练频率。删除 PV/PVC 前必须确认数据生命周期与关联工作负载。

实践与验收

  • 创建动态供应的 PVC，确认 PVC 与 PV 的 StorageClass、容量和访问模式匹配。
  • 引用不存在的 StorageClass，观察 PVC Pending 事件并修复。
  • 删除并重建使用同一 PVC 的 Pod，确认数据是否仍在。
  • 在隔离环境演练 PVC 扩容，并同时验证文件系统和应用是否识别新容量。
  • 执行一次真实恢复验证，而不只确认“备份任务成功”。

验收时应能解释：ReadWriteOnce 表示卷可被单个 Node 读写挂载，不等同于只能被一个 Pod 使用；具体并发能力仍取决于驱动、访问模式和应用一致性要求。

生产基线

  • 关键数据使用受支持的 CSI 驱动、加密存储和合适的 StorageClass。
  • 明确容量告警、扩容流程、快照/备份策略、RPO、RTO 和恢复责任人。
  • Retain 与 Delete 的选择经过数据所有者确认，危险删除受权限和流程保护。
  • 多可用区场景评估卷拓扑、故障切换时间、跨区限制和 WaitForFirstConsumer。
