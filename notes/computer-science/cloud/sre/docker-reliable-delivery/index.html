Docker 与可靠交付

2026-09-30

#SRE#Docker#Delivery

理解主线

容器可靠性来自清晰的交付与数据边界：镜像提供固定程序，卷保存持久数据，健康检查和优雅停止决定运行行为。Compose 组织关系，但应用仍需处理依赖故障。

学习目标

学完本章后，应当能够：

  • 解释镜像层、容器可写层、Volume 和网络在故障与数据恢复中的边界。
  • 构建体积受控、非 root、可追溯且可复现的镜像。
  • 使用 Docker Compose 编排应用、代理和依赖，并正确处理启动顺序与健康状态。
  • 排查容器退出、OOM、磁盘增长、网络不通和数据丢失。

SRE 视角：容器不是轻量虚拟机，也不会自动带来可靠性。可靠性来自不可变交付、资源边界、持久化设计、健康语义、观测和恢复流程。

运行边界

  • 镜像是只读模板；容器可写层随容器删除而消失。
  • Volume 生命周期独立于容器，适合持久数据；Bind Mount 与宿主路径强耦合。
  • 容器共享宿主内核，Namespace 提供隔离，cgroup 提供资源统计与限制。
  • 容器内 PID 1 需要正确转发信号并回收子进程。
  • EXPOSE 只声明元数据，发布端口需要 -p 或 Compose ports。
docker inspect <container>
docker stats --no-stream
docker top <container>
docker diff <container>
docker system df -v

Dockerfile 生产实践

FROM python:3.13-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /wheels -r requirements.txt

FROM python:3.13-slim
RUN useradd --system --uid 10001 --create-home app
WORKDIR /app
COPY --from=builder /wheels /wheels
RUN pip install --no-cache-dir /wheels/* && rm -rf /wheels
COPY --chown=app:app . .
USER 10001
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz')"]
CMD ["python", "-m", "myapp"]

关键原则：

  • 固定基础镜像版本；生产可进一步固定 digest。
  • 使用多阶段构建，不携带编译器和无关工具。
  • .dockerignore 排除 Git、密钥、缓存和测试产物。
  • 依赖版本锁定，在 CI 中生成 SBOM 并扫描漏洞。
  • 不在 ARG、ENV 或镜像层中写入真实密钥。
  • 以非 root 用户运行，根文件系统尽可能只读。

镜像标签是可变指针。部署记录必须能追溯 commit、构建流水线和镜像 digest。

Compose 交付

services:
  app:
    image: registry.example/myapp@sha256:<digest>
    env_file: .env
    restart: unless-stopped
    init: true
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz')"]
      interval: 30s
      timeout: 3s
      retries: 3
    volumes:
      - app-data:/var/lib/myapp
    networks: [backend]
    read_only: true
    tmpfs: [/tmp]

  nginx:
    image: nginx:1.28-alpine
    depends_on:
      app:
        condition: service_healthy
    ports:
      - "443:443"
    networks: [backend]

volumes:
  app-data:

networks:
  backend:

depends_on 只能表达编排启动关系；即使等待健康，运行期间依赖仍可能失败，应用必须配置连接超时、重试和降级。

数据与日志

  • 数据库和上传文件使用明确命名的 Volume，并纳入备份。
  • 不依赖容器可写层保存数据。
  • 应用优先写 stdout/stderr，由日志驱动收集并设置轮转。
  • Docker 日志、未使用镜像和构建缓存可能耗尽宿主磁盘，应监控 /var/lib/docker。
docker volume ls
docker volume inspect <volume>
docker inspect -f '{{.LogPath}}' <container>
docker system df

执行 docker system prune 或 docker compose down -v 前必须列出将删除的对象；-v 会删除数据卷。

健康、停止与资源

健康检查应快速、稳定，验证实例是否能服务，但不要因为短暂外部依赖抖动反复重启整个应用。

docker stop --time 30 <container>
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' <container>
docker events --since 30m

应用捕获 SIGTERM，停止接收新请求、完成在途工作、刷新数据后退出。设置内存限制时监控 OOM；CPU 限制可能引起 throttling 和延迟上升。

故障排查 Runbook

容器持续退出

docker compose ps -a
docker logs --tail 200 <container>
docker inspect -f '{{json .State}}' <container>
docker inspect -f '{{json .Config.Healthcheck}}' <container>

检查退出码、OOM、命令/入口点、配置、权限和依赖。不要只设置无限重启。

容器间网络不通

docker network inspect <network>
docker exec <client> getent hosts <service>
docker exec <client> sh -c 'nc -vz <service> <port>'
docker exec <server> ss -lntp

Compose 网络内使用服务名和容器端口，不要使用宿主发布端口互连。确认应用监听 0.0.0.0 而非仅 127.0.0.1。

重建后数据丢失

检查实际 Mount、Volume 名称、Compose project name 和宿主路径。先停止写入并保护残留卷，不要反复 down -v。

实践与验收

  • 为练习服务创建多阶段、非 root Dockerfile，并记录镜像 digest。
  • 用 Compose 启动应用、Nginx 和持久化依赖，一条命令完成部署。
  • 重建容器，确认 Volume 数据保留；再从备份恢复到新 Volume。
  • 制造错误启动命令、OOM、健康检查失败和服务名解析错误并排查。
  • 执行优雅停止，确认请求排空和退出时间符合预期。

生产基线

  • 镜像不可变、可追溯、经过漏洞扫描，不包含密钥并以非 root 运行。
  • 容器设置健康检查、停止宽限期、资源边界和日志轮转。
  • 数据只存入已纳管 Volume 或外部存储，备份与恢复经过验证。
  • Compose 配置和 .env.example 进入 Git，真实 .env 权限受控且不提交。
