进程、资源与日志排障

2026-09-30

#SRE#Linux#Troubleshooting#systemd

理解主线

从 systemd Unit 追到进程与端口，再用日志和资源指标解释行为。资源利用率只是线索，用户影响、排队和饱和度才帮助判断是否形成瓶颈。

学习目标

学完本章后，应当能够：

  • 从 systemd Unit、进程、线程、端口和日志之间建立对应关系。
  • 根据 CPU、内存、I/O、磁盘与文件描述符证据定位资源瓶颈。
  • 正确使用 SIGTERM、超时和重启策略，避免用 kill -9 掩盖问题。
  • 把简单 HTTP 服务作为可恢复、可观测、受资源约束的系统服务运行。

SRE 视角：资源使用率高不一定是故障，真正需要关注的是用户影响、饱和度、排队、错误以及增长趋势。先证明瓶颈在哪，再采取行动。

从服务到进程

排障链路通常是：

systemd Unit → 主进程 PID → 子进程/线程 → socket → 文件与依赖 → 日志
systemctl status myapp
systemctl show myapp -p MainPID,ActiveState,SubState,Result
ps -o pid,ppid,user,stat,%cpu,%mem,etime,cmd -p <pid>
pstree -ap <pid>
ls -l /proc/<pid>/fd
tr '\0' '\n' </proc/<pid>/environ

读取进程环境时可能接触密钥，不要把完整输出粘贴到工单。STAT 中 D 常表示不可中断 I/O 等待，Z 表示已退出但父进程尚未回收的僵尸进程。

信号与优雅停止

  • SIGTERM：请求应用清理并退出，是服务停止的默认选择。
  • SIGHUP：传统上用于 reload，但是否支持由应用定义。
  • SIGKILL：内核立即终止，应用无法清理；只作为最后手段。
  • SIGSTOP/SIGCONT：暂停和继续进程，可用于受控实验。

停止服务前确认在途请求、后台任务、数据刷新和依赖连接。若 SIGTERM 超时，应保留线程栈、日志和资源状态，再决定是否强杀。

systemd 服务设计

[Unit]
Description=Practice HTTP service
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=myapp
Group=myapp
WorkingDirectory=/opt/myapp
EnvironmentFile=/etc/myapp/myapp.env
ExecStart=/opt/myapp/venv/bin/python -m myapp
Restart=on-failure
RestartSec=5s
TimeoutStopSec=30s
KillSignal=SIGTERM
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ReadWritePaths=/var/lib/myapp
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
sudo systemd-analyze verify /etc/systemd/system/myapp.service
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
systemctl status myapp
journalctl -u myapp -f

Restart=always 可能让配置错误进入无限重启并压垮依赖，应结合启动限速与告警。应用自身也要提供健康端点，进程存在不代表服务可用。

日志与 journalctl

journalctl -u myapp --since '30 min ago' --no-pager
journalctl -u myapp -p warning..alert
journalctl _PID=<pid>
journalctl -k --since today
journalctl --disk-usage

日志应包含 UTC 时间、级别、服务、版本、请求或 Trace ID、操作结果与错误类型。不得记录密码、Token、完整支付信息等敏感数据。

日志排查时先限定：时间窗口、主机、服务版本、请求标识和错误类型。不要从海量日志中只搜索一个模糊关键词。

资源诊断框架

使用 USE 方法检查资源：

  • Utilization：资源忙碌比例。
  • Saturation：等待队列或无法立即获得资源的工作量。
  • Errors：设备、内核或应用报告的错误。

CPU

uptime
mpstat -P ALL 1
pidstat -u -t 1
top -H -p <pid>

Load Average 包含可运行任务以及部分不可中断等待任务，不等于 CPU 使用率。CPU 很低但 load 很高时，应检查 I/O 等待和 D 状态进程。

内存

free -h
vmstat 1
cat /proc/meminfo
journalctl -k | grep -i -E 'oom|out of memory|killed process'
pidstat -r 1

Linux 会把空闲内存用于缓存，free 很小不一定内存不足。关注 available、持续 swap、major page fault、OOM 和业务延迟。

磁盘与 I/O

df -hT
df -i
iostat -xz 1
pidstat -d 1
sudo du -xhd1 /var | sort -h

空间、inode 和 I/O 延迟是不同问题。磁盘使用率接近 100% 不总是故障，但高延迟、队列增长和应用超时通常表明饱和。

文件描述符与连接

cat /proc/<pid>/limits
ls /proc/<pid>/fd | wc -l
lsof -p <pid>
ss -s
ss -lntp

FD 泄漏常表现为计数持续增长，最终出现 Too many open files。提高限制只能暂时缓解，仍要定位未关闭的文件或连接。

故障排查 Runbook

服务无法启动

systemctl status myapp
journalctl -u myapp -b --no-pager
systemctl cat myapp
systemd-analyze verify /etc/systemd/system/myapp.service
sudo -u myapp /opt/myapp/venv/bin/python -m myapp
ss -lntp

依次检查 Unit 语法、运行用户权限、文件路径、环境配置、端口冲突和依赖可用性。

服务响应缓慢

  1. 先确认错误率、延迟和影响范围。
  2. 对比故障前后的发布、流量和依赖变化。
  3. 查看 CPU、运行队列、内存、swap、I/O 延迟、FD 和连接池。
  4. 区分应用计算、主机资源、数据库或外部依赖。
  5. 先限流、扩容、回滚或降级恢复服务，再做深入分析。

服务反复重启

systemctl show myapp -p NRestarts,Result,ExecMainStatus
journalctl -u myapp --since '1 hour ago'
coredumpctl list myapp

保留首次失败原因。自动重启是恢复机制，不是根因修复。

实践与验收

  • 将练习 HTTP 服务注册为非 root systemd 服务并设置开机启动。
  • 验证 SIGTERM 可以停止接收请求、完成在途请求并在超时内退出。
  • 制造端口冲突、错误配置和无权限目录，分别从 journal 找出原因。
  • 制造 CPU、内存、磁盘 I/O 和 FD 压力，记录 USE 证据与用户侧表现。
  • 停止服务后确认 systemd 自动恢复，并验证告警不会因重启而丢失。

生产基线

  • 服务使用独立用户、最小文件权限和 systemd 沙箱能力。
  • 有明确启动、停止、reload、健康检查和依赖超时语义。
  • 资源限制来自压测与历史数据，并为饱和、OOM、磁盘和 FD 设置监控。
  • 日志结构化、可关联、有限流和轮转，敏感信息脱敏。
