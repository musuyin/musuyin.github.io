服务部署与数据保护

2026-09-30

#SRE#Deployment#Backup

理解主线

交付和恢复需要把程序、配置、密钥、可变数据与日志分别管理。一次发布有回退路径，一次备份有恢复验证，才形成可依赖的操作流程。

学习目标

学完本章后，应当能够：

  • 将程序、配置、密钥、可变数据和日志分离管理。
  • 设计可验证、可回滚、影响范围明确的服务变更流程。
  • 配置 HTTPS、日志轮转、最小权限和数据库备份。
  • 用恢复演练验证备份，并量化 RPO 与 RTO。

SRE 视角：部署成功不是“进程已启动”，备份成功也不是“文件已生成”。两者都必须从用户请求和恢复结果验证。

服务资产分类

资产 示例 管理原则
程序 二进制、包、静态资源 不可变版本，可重建、可回滚
配置 端口、特性开关、依赖地址 版本化、校验、环境差异明确
密钥 密码、Token、TLS 私钥 不进 Git，最小权限，可轮换
数据 数据库、上传文件 持久化、备份、恢复和一致性验证
日志 应用、访问、审计日志 轮转、保留、脱敏、集中检索

推荐路径示例：程序位于 /opt/myapp/releases/<version>，稳定软链接指向当前版本；配置位于 /etc/myapp；数据位于 /var/lib/myapp；日志交给 journald 或 /var/log/myapp。

变更与发布流程

  1. 明确变更目的、影响范围、负责人和维护窗口。
  2. 备份必要状态，确认回退版本与回退命令。
  3. 在测试环境验证配置语法、迁移兼容性和健康检查。
  4. 小范围执行，观察错误率、延迟、资源和业务成功率。
  5. 达到停止条件则回滚；稳定窗口通过后再扩大范围。
  6. 记录版本、时间、操作、验证结果和异常。
sha256sum artifact.tar.gz
nginx -t
systemd-analyze verify myapp.service
curl -fsS http://127.0.0.1:8000/healthz

健康检查至少区分：

  • Liveness：进程是否陷入不可恢复状态。
  • Readiness：实例当前能否接收流量。
  • 深度检查：依赖是否可用，通常供诊断而非高频重启判断。

配置与环境变量

环境变量适合少量启动配置，但可能出现在进程环境、崩溃信息或调试输出中。复杂配置使用权限受控的文件；密钥优先从密钥系统在运行时获取。

变更配置后分别验证：

  • 文件内容是否正确落地。
  • 服务是否读取了新版本。
  • reload 或 restart 是否成功。
  • 用户侧行为和核心指标是否符合预期。

配置发布要么原子替换，要么写新文件后切换软链接，避免进程读取到半写入内容。

日志轮转

若应用直接写文件，可使用 logrotate：

/var/log/myapp/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 myapp adm
    sharedscripts
    postrotate
        systemctl kill -s HUP myapp.service || true
    endscript
}

确认应用是否会在 HUP 后重新打开日志。使用 copytruncate 可能丢失少量日志，并非首选。轮转后检查磁盘、文件所有者、应用写入和日志采集 Agent。

数据库备份策略

先明确：

  • 需要保护哪些数据库和外部文件。
  • 可接受丢失多久的数据，即 RPO。
  • 可接受多久恢复服务，即 RTO。
  • 备份是逻辑备份、物理备份、快照还是持续日志归档。
  • 备份时如何保证事务一致性。
  • 密钥、备份介质和生产故障是否隔离。

遵循 3-2-1 思路：至少三份副本、两种介质、一份异地或独立故障域。实际方案还要考虑加密、访问控制、不可变保留和删除保护。

备份不等于恢复

恢复演练应在隔离环境执行：

  1. 选择明确时间点和备份版本。
  2. 校验备份文件和解密能力。
  3. 恢复数据库及外部文件。
  4. 启动同版本或兼容版本应用。
  5. 执行业务级校验，例如记录数、关键查询和抽样校验和。
  6. 记录实际数据缺口和恢复耗时，比较 RPO/RTO。

TLS 与密钥

  • 私钥只允许服务用户或代理读取，通常为 600 或受控组权限。
  • 证书自动续期，至少提前数周告警。
  • reload 前验证新证书链、域名和有效期。
  • 轮换数据库密码时允许新旧凭据短暂共存，应用切换验证后再吊销旧值。
  • 禁止把真实 .env、数据库导出和私钥提交到 Git。

故障排查 Runbook

发布后服务不可用

systemctl status myapp nginx
journalctl -u myapp -u nginx --since '20 min ago'
ss -lntp
curl -sv http://127.0.0.1:8000/healthz
curl -sv https://<host>/healthz

比较本机应用、代理入口和外部请求，查看变更 diff。若越过停止条件，先回滚程序和配置，再调查。

磁盘即将写满

df -hT
df -i
du -xhd1 /var | sort -h
lsof +L1
journalctl --disk-usage

先限制增长源并保护数据库。不要未经确认删除 /var/lib 数据或仍在使用的日志。

恢复后数据不一致

停止向错误实例继续写入；保存恢复步骤、备份元数据和应用版本。检查恢复时间点、事务日志、时区、外部文件以及数据库 schema 兼容性。

实践与验收

  • 按程序、配置、密钥、数据、日志分类部署练习服务。
  • 配置 Nginx 访问/错误日志、HTTPS 与自动续期测试。
  • 配置日志轮转并验证轮转后服务仍持续写日志。
  • 实现每日数据库备份、校验、保留和失败告警。
  • 删除一份测试数据，在隔离目录或实例恢复并记录实际 RPO/RTO。
  • 发布一份错误配置，按停止条件回滚并验证用户请求恢复。

生产基线

  • 发布物不可变且可追溯，配置变更经过审查，密钥独立管理。
  • 数据备份加密、异地、受访问控制，并定期进行业务级恢复验证。
  • 日志有容量上限和保留策略，磁盘空间与 inode 均有告警。
  • 发布与恢复 Runbook 明确负责人、停止条件、回退步骤和验证指标。
