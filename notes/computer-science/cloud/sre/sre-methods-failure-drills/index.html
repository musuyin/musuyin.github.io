SRE 方法与故障演练

2026-09-30

#SRE#SLO

理解主线

SRE 用用户目标约束可靠性工作：SLI 提供观测，SLO 定义目标，错误预算连接变更与风险。故障演练验证假设和恢复路径，复盘再把证据转为具体改进。

学习目标

学完本章后，应当能够：

  • 从用户旅程定义 SLI、SLO 和错误预算，并说明其决策用途。
  • 组织事件响应，明确指挥、操作、沟通和记录职责。
  • 区分触发因素、根因、促成条件和影响放大因素。
  • 设计有假设、有护栏、可中止并能产生改进行动的故障演练。

SRE 视角：可靠性不是追求绝对不故障，而是在成本、功能速度与用户体验之间建立可度量的目标，并持续改善发现、恢复和预防能力。

SLI、SLO 与 SLA

  • SLI：实际测量的可靠性指标。
  • SLO：SLI 在时间窗口内的内部目标。
  • SLA：对外协议，可能包含责任或赔偿，通常应比内部 SLO 宽松。

从用户旅程定义 SLI

以 HTTP API 可用性为例：

good events = 满足业务成功条件的有效请求
total events = 应计入 SLO 的所有有效请求
availability SLI = good events / total events

必须明确：

  • 测量位置在客户端、边缘、代理还是应用。
  • 哪些状态码和业务结果算成功。
  • 客户端取消、无效请求、计划维护是否计入。
  • 低流量或无流量时如何解释。
  • 数据延迟、缺失和重放如何处理。

延迟 SLI 通常使用“低于阈值的请求比例”，比只看平均值更能对应用户体验，例如 99% 的有效请求在 300 ms 内完成。

错误预算

若 30 天可用性 SLO 为 99.9%，错误预算为 0.1%。按连续时间粗略换算约 43.2 分钟，但基于请求的 SLI 应按失败请求比例计算，不能直接等同停机时间。

错误预算用于决策：

  • 预算充足：可以承担合理变更风险。
  • 消耗过快：收紧发布、优先修复可靠性问题。
  • 预算耗尽：按既定政策暂停高风险变更，但保留安全和紧急修复通道。

不要把 SLO 当作考核个人的工具，否则团队会隐藏故障或操纵指标。

燃烧率

燃烧率表示错误预算消耗速度：

burn rate = 实际错误比例 / 允许错误比例

燃烧率为 1 表示按预算刚好消耗；大于 1 表示若持续下去会提前耗尽。告警应结合短窗口与长窗口：短窗口快速发现严重故障，长窗口过滤短暂噪声。

事件响应

事件生命周期：

检测 → 分级 → 响应组织 → 止损 → 恢复 → 验证 → 沟通 → 复盘

较大事件明确角色：

  • Incident Commander：设定优先级、分配任务和做决策。
  • Operations：执行排障和恢复操作。
  • Communications：同步用户、管理层和相关团队。
  • Scribe：记录时间线、假设、命令和结果。

一人可兼任多个角色，但必须明确谁负责什么。事件中建立单一沟通频道和权威状态记录，避免多人无协调地同时修改系统。

首轮响应

  1. 确认告警有效及用户影响。
  2. 定义范围、开始时间、严重级别和事件负责人。
  3. 检查近期变更，建立最可能假设。
  4. 优先使用已验证的回滚、扩容、限流、故障切换或降级。
  5. 每项操作记录预期、执行人、时间和结果。
  6. 以核心 SLI 的稳定恢复结束事件，而不是以某条命令成功结束。

复盘

无责复盘关注系统为什么允许错误发生并扩大，而不是寻找“犯错的人”。建议结构：

  • 摘要与用户影响。
  • 检测方式和响应方式。
  • 精确时间线。
  • 触发因素、根因、促成条件与影响放大因素。
  • 哪些措施有效，哪些没有。
  • 行动项、负责人、优先级和截止时间。

好的行动项具体、可验证并改变系统，例如“为证书剩余 30/14/7 天配置告警并演练续期”，而不是“以后更加小心”。

变更风险

按影响范围、可逆性、复杂度、新颖性、观察能力和执行时间评估风险。降低风险的方法：

  • 减少单次变更内容。
  • 自动检查和同行评审。
  • canary、分批和维护窗口。
  • 预先验证回滚与数据兼容性。
  • 设置停止条件和稳定观察窗口。
  • 高风险变更安排明确负责人和实时沟通。

变更冻结不能替代修复系统性风险；紧急变更同样需要记录和事后审查。

故障演练设计

演练不是随机破坏。每次应包含：

  • 假设：例如“单个应用进程停止时，systemd 会在 30 秒内恢复，用户成功率不低于 99%”。
  • 稳态指标：成功率、延迟、队列、资源和数据一致性。
  • 故障注入：停止进程、错误代理端口、依赖延迟、磁盘压力或凭据失效。
  • 护栏：允许环境、最大影响、观察人、停止阈值和立即恢复命令。
  • 结果：假设是否成立、发现了什么缺口、如何跟踪行动项。

先在本地和测试环境执行，再逐步接近生产；没有成熟观测和中止能力时不应直接开展生产演练。

事件 Runbook 模板

# 告警或事件名称

## 用户影响

## 立即确认

## 安全止损

## 深入排查

## 恢复验证

## 升级与沟通

## 证据保留

Runbook 写决策和证据，不只罗列命令；注明命令在哪台主机、哪个环境执行，以及潜在副作用。

实践与验收

  • 为练习服务定义可用性和延迟 SLI，明确 good/total event 与数据源。
  • 定义 30 天 SLO，计算错误预算并写出预算策略。
  • 模拟服务停止、Nginx 上游错误或依赖延迟，完整记录响应时间线。
  • 由另一人按 Runbook 完成首轮响应，收集文档缺口。
  • 完成无责复盘，为每个行动项指定负责人、期限和验证方式。
  • 复测同一故障，确认检测时间和恢复时间改善。

生产基线

  • 核心用户旅程有少量、稳定、可解释的 SLO。
  • 告警基于用户影响或错误预算消耗，并与事件等级和 Runbook 关联。
  • 值班职责、升级路径、沟通模板和事件权限提前准备。
  • 复盘行动项进入正常工程计划并跟踪关闭，定期演练关键恢复路径。
