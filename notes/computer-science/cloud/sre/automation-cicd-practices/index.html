自动化与 CI/CD 实践

2026-09-30

#SRE#Automation#Ansible#CI/CD

理解主线

自动化先固化边界，再放大执行效率。幂等、锁、超时、退出码和逐环境晋级共同限制重复或部分失败的影响，不能只检查流水线是否为绿色。

学习目标

学完本章后，应当能够：

  • 判断操作是否适合自动化，并把手工步骤改造成可重复、可观测的流程。
  • 用幂等、超时、重试、锁和退出码提升 Bash/Python 自动化可靠性。
  • 使用 Ansible 管理主机状态、配置变更、Handler 和敏感变量。
  • 设计构建一次、逐环境晋级、可暂停和可回滚的 CI/CD 流水线。

SRE 视角：自动化会同时放大效率和错误。只有边界、验证、停止条件、审计和回退都明确时，自动化才会降低运维风险。

自动化前先标准化

适合自动化的任务通常高频、规则稳定、输入输出明确且可验证。开始前写清：

  • 前置条件和支持的平台版本。
  • 输入参数、默认值与合法范围。
  • 期望状态和成功验证。
  • 失败模式、影响范围和回滚方式。
  • 并发执行与中断后的行为。
  • 日志、指标和审计信息。

先在单台测试主机验证，再使用 canary、批次和并发上限扩大范围。

幂等与错误处理

幂等不是“命令不会报错”，而是重复执行后系统仍处于同一目标状态。

反例：每次都向配置文件追加一行。正确做法是使用模板生成完整配置，写入临时文件，语法校验后原子替换。

set -Eeuo pipefail
timeout 30s some-command

retry() {
  local attempt
  for attempt in 1 2 3; do
    "$@" && return 0
    sleep $((attempt * 2))
  done
  return 1
}

只重试临时性、幂等的失败，并设置总体截止时间和抖动；认证失败、配置错误和数据校验失败不应盲目重试。

Python 更适合结构化数据、API、并发和复杂测试。无论语言，都应使用结构化日志、异常分类、非零退出状态和单元测试。

Ansible 实践

- name: Deploy practice service
  hosts: app
  become: true
  serial: 1
  max_fail_percentage: 0
  tasks:
    - name: Render configuration
      ansible.builtin.template:
        src: myapp.conf.j2
        dest: /etc/myapp/myapp.conf
        owner: root
        group: myapp
        mode: "0640"
        validate: /usr/local/bin/myapp --check-config %s
      notify: Reload myapp

    - name: Ensure service is running
      ansible.builtin.systemd_service:
        name: myapp
        enabled: true
        state: started

    - name: Verify health
      ansible.builtin.uri:
        url: http://127.0.0.1:8000/healthz
        status_code: 200

  handlers:
    - name: Reload myapp
      ansible.builtin.systemd_service:
        name: myapp
        state: reloaded
  • 使用模块表达状态，少用不可判定变更的 shell。
  • Handler 只在配置变更时触发。
  • 使用 --check --diff 预览，但注意并非所有模块完全支持 check mode。
  • Inventory 划分环境和故障域，限制目标主机模式。
  • 密钥使用 Vault 或外部密钥系统，日志用 no_log 保护敏感字段。

CI/CD 流水线

推荐阶段：

代码检查 → 单元/集成测试 → 构建一次 → 扫描与签名
→ 测试环境部署 → 冒烟测试 → 审批/策略门禁
→ 小流量生产 → SLI 观察 → 扩大或回滚

关键原则：

  • 同一不可变制品在环境间晋级，不在生产重新构建。
  • 每次部署记录 commit、制品 digest、配置版本、操作者和时间。
  • 流水线凭据短期化、权限最小化，受保护分支和环境需要审批。
  • 数据库迁移优先向后兼容，采用 expand/contract，避免应用回滚后 schema 不兼容。
  • 部署成功以用户侧 SLI 和冒烟测试为准，不以 SSH 命令退出码为准。

安全发布与回滚

发布前定义：

  • 基线：当前错误率、延迟、流量和资源。
  • 停止线：哪些指标达到何值立即暂停。
  • 观察窗口：需要稳定多久。
  • 回滚：程序、配置和数据库分别如何处理。
  • 责任人：谁执行、谁批准、谁沟通。

自动回滚适合信号明确且回滚安全的场景。若数据库迁移不可逆或外部副作用明显，应自动暂停并由人工决策。

自动化故障 Runbook

重复执行产生副作用

停止扩大执行范围，保存目标列表和运行日志。比较执行前后状态，检查追加写、非唯一资源、时间戳命名和非幂等 API。

部分主机成功

ansible-playbook deploy.yml --limit <canary> --check --diff
ansible-playbook deploy.yml --limit <failed-hosts>

不要在未知状态下直接全量重跑。先确定任务是否原子、哪些主机已变更以及重试是否安全。

流水线绿色但服务异常

检查流水线是否只验证进程而未验证请求；关联制品 digest、配置、数据库迁移、流量和 SLI。越过停止线时先回滚或降级。

实践与验收

  • 用脚本或 Ansible 安装 Docker、部署 Compose 服务并完成健康验证。
  • 连续执行两次，第二次除必要检查外应无额外变更。
  • 制造依赖下载超时、配置校验失败和目标主机不可达，确认非零退出和清晰错误。
  • 建立 CI：测试、构建镜像、扫描并输出 digest。
  • 建立测试部署与冒烟测试，模拟生产 canary、停止线和回滚。

生产基线

  • 自动化变更默认支持预览、限制目标、分批执行、超时和停止。
  • 制品、配置和部署记录可追溯，凭据最小权限且不出现在日志。
  • 流水线有并发控制，避免同一环境被多个发布同时修改。
  • 回滚与数据库兼容性经过演练，发布后使用 SLI 验收。
