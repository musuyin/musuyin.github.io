Linux 与 Shell 运维实践

2026-09-30

#SRE#Linux#Shell

理解主线

运维 Shell 的重点是可控地改变系统：确认身份与路径，理解退出码和重定向，再处理锁、日志、错误与重试。脚本成功退出应与预期系统状态对应。

学习目标

学完本章后，应当能够：

  • 在不使用 root 直接登录的前提下管理用户、权限和 SSH 访问。
  • 从文件、权限、进程环境与系统日志中收集故障证据。
  • 编写具备错误处理、日志、锁和保留策略的幂等 Shell 脚本。
  • 在执行删除、覆盖、权限修改前识别影响范围并设计回退方式。

SRE 视角：不需要重新背诵所有 Linux 命令，而要理解命令看到的是哪一层状态、输出能否作为证据，以及操作失败或重复执行时会发生什么。

文件系统中的运维边界

排障时先知道数据通常位于哪里：

路径 SRE 常见用途 风险
/etc 系统和服务配置 修改错误可能导致服务无法启动
/var/log 持久化日志 日志失控会耗尽磁盘
/var/lib 服务状态和持久数据 不应当作普通缓存清理
/run PID、socket 等运行时状态 重启后通常消失
/tmp 临时文件 可能被定期清理，不适合保存数据
/proc 内核导出的进程与系统状态 是运行状态视图，不是普通磁盘文件
/sys 设备和内核对象状态 写操作可能直接改变系统行为

先确认文件系统与挂载点，不要只看目录：

findmnt
findmnt -T /var/lib/myapp
df -hT
df -i
lsblk -f

df 显示文件系统整体使用量，du 统计可见目录中的文件。文件已删除但仍被进程打开时，du 下降而 df 不下降，可用 lsof +L1 定位。

权限、身份与最小授权

Linux 权限需要同时考虑：所有者、组、mode、ACL、父目录执行权限以及进程实际身份。

id <user>
namei -l /var/lib/myapp/data.db
stat /var/lib/myapp/data.db
getfacl /var/lib/myapp/data.db
sudo -l -U <user>
  • 文件的 r/w/x 分别表示读取、修改和执行。
  • 目录的 x 表示可以穿越目录，w 表示可以创建或删除目录项。
  • chmod 644 为所有者读写、组和其他用户只读；它不适合包含私钥的文件。
  • SSH 私钥通常使用 600，.ssh 目录通常使用 700。
  • 服务使用独立系统用户，不共享个人账号，不授予交互 Shell 和多余 sudo 权限。

不要用 chmod 777 解决权限问题。正确做法是确认哪个进程身份需要哪种访问，再通过所有者、组、ACL 或服务配置授予最小权限。

SSH 访问基线

推荐：个人账号 + 公钥认证 + 必要时 sudo，禁止共享 root 凭据。

ssh-keygen -t ed25519 -a 100
ssh-copy-id <user>@<host>
ssh -v <user>@<host>
sshd -T | grep -E 'passwordauthentication|permitrootlogin|pubkeyauthentication'

生产变更 SSH 配置时：

  1. 保留当前已登录会话。
  2. 使用 sshd -t 检查语法。
  3. reload 而不是直接重启。
  4. 从新终端验证登录成功后再退出旧会话。

主机密钥告警意味着远端身份发生变化，也可能是中间人攻击。核对变更记录和可信指纹，不要习惯性删除 known_hosts 条目。

管道、重定向与退出状态

command >file       # 覆盖标准输出
command >>file      # 追加标准输出
command 2>error.log # 单独写标准错误
command >all.log 2>&1
producer | consumer

管道默认退出码常来自最后一个命令。脚本应开启 pipefail，避免前序命令失败却被误判成功：

#!/usr/bin/env bash
set -Eeuo pipefail
trap 'printf "failed at line %s\n" "$LINENO" >&2' ERR

使用变量时默认加双引号：rm -- "$file"。删除命令使用 -- 防止以 - 开头的路径被解释为参数。

面向运维的 Shell 脚本

可靠脚本至少具备：

  • 参数和依赖检查。
  • 明确退出码，错误写入 stderr。
  • 临时文件清理与信号处理。
  • 重复执行结果稳定。
  • 并发锁，避免两个任务同时修改同一状态。
  • 可读日志，但不输出密码和 Token。
  • --dry-run 或预览能力，危险操作有边界检查。

备份脚本示例

#!/usr/bin/env bash
set -Eeuo pipefail

source_dir=${1:?usage: backup.sh SOURCE BACKUP_DIR}
backup_dir=${2:?usage: backup.sh SOURCE BACKUP_DIR}
retention_count=${RETENTION_COUNT:-7}
lock_file=/tmp/myapp-backup.lock

exec 9>"$lock_file"
flock -n 9 || { echo "backup already running" >&2; exit 75; }

[[ -d "$source_dir" ]] || { echo "source does not exist" >&2; exit 66; }
mkdir -p -- "$backup_dir"

stamp=$(date -u +%Y%m%dT%H%M%SZ)
tmp=$(mktemp "$backup_dir/.backup-${stamp}.XXXXXX")
final="$backup_dir/backup-${stamp}.tar.gz"
trap 'rm -f -- "$tmp"' EXIT

tar -C "$(dirname "$source_dir")" -czf "$tmp" "$(basename "$source_dir")"
tar -tzf "$tmp" >/dev/null
mv -- "$tmp" "$final"
mapfile -d '' backups < <(
  find "$backup_dir" -maxdepth 1 -type f -name 'backup-*.tar.gz' \
    -printf '%T@ %p\0' | sort -zrn
)
for entry in "${backups[@]:$retention_count}"; do
  old_file=${entry#* }
  printf 'deleting old backup %s\n' "$old_file"
  rm -- "$old_file"
done
printf 'created %s\n' "$final"

保留策略不等于备份策略。还要验证目标介质故障隔离、访问权限、完整性、恢复步骤、RPO 和 RTO。

常见故障 Runbook

Permission denied

id
namei -l <path>
stat <path>
getfacl <path>
mount | grep ' <mountpoint> '

区分文件 mode、父目录权限、只读挂载、SELinux/AppArmor 和服务沙箱限制。不要先放宽到 777。

No space left on device

df -hT
df -i
sudo du -xhd1 /var | sort -h
sudo lsof +L1

可能是空间耗尽、inode 耗尽或已删除文件仍被占用。先控制日志增长和业务影响，再清理已确认可删除的数据。

脚本在 cron 中失败

检查工作目录、PATH、环境变量、权限、时区、Shell 类型与输出去向。脚本使用绝对路径或显式初始化环境，不依赖交互式 shell 配置。

实践与验收

  • 创建普通运维用户，通过 ed25519 密钥登录，并验证其只能执行批准的 sudo 命令。
  • 完成备份脚本，支持并发锁、原子写入、压缩包校验和保留最近七天。
  • 连续执行脚本两次，确认不会覆盖有效备份或误删最新文件。
  • 从备份恢复到新目录，比较文件数量和校验和。
  • 模拟 inode 耗尽或打开后删除文件，使用对应证据定位。

验收标准：能够解释每个高风险命令的影响范围；脚本失败时返回非零状态、留下可定位日志，并且已有有效数据不被破坏。

生产基线

  • 禁止共享账号和 root 远程直登，使用个人身份、短期授权和审计。
  • 配置、脚本进入版本控制，密钥使用专用系统管理。
  • 定时任务设置超时、锁、失败告警和日志保留。
  • 删除和权限变更先预览对象，关键数据有备份与恢复验证。

复习与应用

让备份脚本连续运行两次、在缺少权限时运行一次，检查输出、退出码和残留文件是否符合设计。
