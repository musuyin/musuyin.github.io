网络与 Web 链路排障

2026-09-30

#SRE#Network#HTTP#Troubleshooting

本文以通过 TCP 的 HTTPS 请求为例，从客户端的失败现象出发，用命令输出定位故障所在的一跳。网络与运维学习路径提供同主题的入口。需要回顾协议时，可先读DNS 解析机制和TCP 连接管理。

故障现场速查

一次请求通常依次经过 DNS 解析、本地路由与网关、TCP 建连、TLS 握手和 HTTP 交互，再由负载均衡器或反向代理将请求转给应用。应用还可能等待数据库或外部依赖。

  1. 从受影响的客户端复现，记录域名、端口、请求路径、失败时间和影响范围。记下每条命令的执行位置，客户端、代理与应用主机的网络视角可能不同。
  2. 找到最早出现异常的阶段。下表提供各层的起点，详细命令和判断依据见后续小节。
  3. 沿出错的一跳对比两端证据。将结论落到失败层、失败方向、时间窗口与影响范围，再决定要查哪一段路径或哪一个服务。
观察到的现象 检查位置和命令 下一步看什么
域名不解析或返回旧地址 受影响的客户端运行 dig +short <host> 地址异常时用完整 dig 输出检查响应码、Resolver 和 TTL
端口连接失败 发起连接的一端运行 ip route get <ip> 和 nc -vz -w 3 <ip> <port> 路由是否正确，端口是拒绝、超时还是重置
TLS 握手或证书验证失败 客户端运行 openssl s_client，显式传入 SNI 域名、有效期、证书链、系统时间与信任库
请求缓慢或返回 HTTP 错误 客户端运行 curl -sv --max-time 10 https://<host>/healthz 请求是否获得响应，耗时卡在哪个阶段，响应来自哪一跳
怀疑代理或上游应用异常 对应的服务端运行 ss -lntp 和 journalctl 监听地址、应用是否收到请求，以及代理等待上游的耗时

按层验证请求

下列命令用于 Linux 环境。执行前将尖括号中的占位符替换为现场的域名、解析器、地址或端口，并选择相应主机。resolvectl 适用于使用 systemd-resolved 的环境，journalctl -u 中的服务名应与实际 systemd 单元一致。

DNS 解析与客户端选址

dig +short <host>
dig example.com
dig +trace example.com
dig @<resolver> example.com A
dig @<resolver> example.com AAAA
getent ahosts example.com
resolvectl query example.com

记录 DNS 响应码、记录值、TTL、使用的 Resolver、查询耗时，以及客户端实际选择 IPv4 还是 IPv6。dig +trace 用于沿委派链检查，getent ahosts 可用于对照系统解析结果。

  • NXDOMAIN 表示 DNS 响应认为查询的名称不存在。SERVFAIL 表示解析失败，可继续检查解析链或 DNSSEC。
  • 解析配置已更新却仍访问旧地址时，检查 TTL、本地和递归缓存，以及变更传播情况。
  • dig 成功而应用仍失败时，确认应用是否使用不同的 Resolver、缓存或代理环境。

路由选择与路径可达性

ip addr
ip route
ip route get <destination-ip>
ip route get <ip>
ping -c 3 <ip>
traceroute <ip>
tracepath <ip>

ip route get 可显示内核为目标地址选择的出口接口和源地址。ICMP 可能被过滤，ping 失败时应独立验证 TCP 可达性。ping 成功只提供 ICMP 往返证据，仍需检查服务端口与 HTTP 响应。

TCP 建连与服务监听

在发起连接的一端检查目标端口，并按需请求 HTTP 健康检查接口。

nc -vz -w 3 <ip> <port>
nc -vz -w 3 <host> <port>
curl --connect-timeout 3 http://<host>:<port>/healthz

在目标主机确认监听地址、端口和连接状态。

ss -lntp
ss -nt state established
TCP 现象 常见排查方向
Connection refused 连接被主动拒绝，检查目标端口是否监听，以及路径上的防火墙是否主动拒绝
Connection timed out 检查路由、路径上的丢包与防火墙，以及目标服务是否响应
Connection reset 检查对端或中间设备主动终止连接的原因
本机可访问，远端不可访问 检查是否只监听 loopback，以及防火墙、安全组与 NAT

监听 127.0.0.1 的服务只能从本机访问。0.0.0.0 表示监听所有本地 IPv4 地址，远端访问仍受防火墙和网络策略控制。

必要时抓包确认 SYN、SYN-ACK 和重传。抓包可能包含业务数据和凭据，应在授权范围内限定过滤条件、采集时间与文件权限。

sudo tcpdump -ni any host <ip> and port <port>

TLS 握手与证书校验

openssl s_client -connect <host>:443 -servername <host> </dev/null
openssl s_client -connect example.com:443 -servername example.com </dev/null
curl -vI https://example.com/
curl --resolve example.com:443:<ip> https://example.com/

检查证书域名、有效期、证书链、SNI、协议版本、系统时间和客户端信任库。--resolve 将指定域名和端口临时绑定到指定 IP，URL 中的域名仍用于 HTTP Host 和 TLS SNI。对比正常解析与固定 IP 的结果，有助于区分 DNS 选址与 TLS 或服务故障。

仅在受控诊断中使用 curl -k。该选项会跳过证书身份验证，修复后用正常校验的客户端重新验证。

HTTP 响应与请求耗时

curl -sv --max-time 10 https://<host>/healthz
curl -sv --connect-timeout 3 --max-time 10 https://example.com/healthz
curl -sS -o /dev/null -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} code=%{http_code}\n' https://example.com/

curl -w 输出从请求开始到 DNS 解析完成、TCP 建连完成、TLS 握手完成、收到首字节和请求结束的时间。直接发起一次新建连接且无重定向的请求时，可以对比相邻时间点，判断耗时集中在哪个阶段。

响应 常见排查方向
4xx 检查请求内容、认证、授权或限流
502 检查代理能否连接上游并获得有效响应
503 检查是否没有可用后端，或服务是否过载、处于维护中
504 检查代理等待上游是否超时，再定位上游的处理或依赖耗时

确认响应由代理还是应用返回。用请求 ID 和时间窗口关联代理日志、应用日志、请求耗时、上游耗时及依赖指标，再判断根因。

代理与应用日志

journalctl -u nginx --since '15 min ago'
journalctl -u myapp --since '15 min ago'

在对应主机上按失败时间窗口查日志，同时查看代理的访问日志和错误日志。结合上游地址和服务端监听检查，将「代理连接不上应用」与「应用收到请求后报错或超时」分开。可参考按 systemd 服务和时间筛选日志。

Nginx 反向代理配置与验证

实验配置片段

示例假设上游服务监听 127.0.0.1:8000，Nginx 接收 example.test 的 HTTPS 请求。实验环境需要让客户端能够访问该域名对应的测试地址，并为 listen 443 ssl 准备与域名匹配的测试证书及私钥。示例保留代理相关配置，TLS 证书配置由实验环境提供。

upstream practice_app {
    server 127.0.0.1:8000;
    keepalive 32;
}

server {
    listen 443 ssl;
    server_name example.test;

    location / {
        proxy_pass http://practice_app;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Request-ID $request_id;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
    }
}

示例使用 Host、X-Forwarded-For 和 X-Forwarded-Proto 将主机名、客户端地址链和原请求协议传给应用。X-Request-ID 用于对照代理和应用的日志。

配置生效与回归检查

  1. 运行 sudo nginx -t 检查配置。
  2. 检查通过后，运行 sudo systemctl reload nginx 重载服务。
  3. 运行 journalctl -u nginx --since '10 min ago' 检查重载日志，重新请求健康检查接口，并对照代理和应用日志核对响应及请求 ID。

超时需要覆盖外层代理、应用和依赖。将预算逐层收紧，或明确每层的超时预算，避免外层结束请求后内层仍在消耗资源。重试用于幂等请求，并应限制次数、设置退避和总体截止时间，防止重试风暴。

生产基线

  • DNS 变更前考虑 TTL、回退和双栈影响，监控关键域名的解析与到期。
  • 为 TLS 证书配置自动续期和提前告警，最小化私钥访问权限。
  • 代理与应用统一请求 ID，记录状态码、请求耗时和上游耗时。
  • 检查上游健康状态，验证后端不可用时代理的行为。
  • 配置连接、读取、写入和总体超时，根据容量规划重试、连接池与限流。

故障演练与验收

  • 为本地 HTTP 服务配置 Nginx 和测试 TLS 证书。
  • 使用 curl -w 记录 DNS、连接、TLS、首字节与总耗时。
  • 分别制造错误域名、未监听端口、过期或域名不匹配证书、应用 500 和代理上游超时，记录各自的失败证据。
  • 修改 Nginx 上游端口触发 502，从访问日志和错误日志定位。
  • 用 tcpdump 观察一次正常 TCP 握手和一次连接重传，仅采集实验流量。

通过标准是能用一条证据指出失败的层与方向，说明证据来自哪个位置和时间窗口，并说清下一步检查什么。

复习

  • dig 返回了正确的 IP，应用仍连接旧地址。还要比较哪些解析结果和缓存？如何固定目标 IP，同时保留 HTTP Host 和 TLS SNI？
  • 同一端口分别出现拒绝、超时与重置。每种现象应该先查监听、路径还是连接终止方？
  • 代理返回 504。怎样用请求 ID、日志和上游耗时判断请求在哪一跳等待？
