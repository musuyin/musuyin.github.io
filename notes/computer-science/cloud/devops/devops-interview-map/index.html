DevOps 面试知识地图

2026-10-13

#DevOps#Kubernetes#面试

理解主线

这份地图以初级 DevOps 岗位的基础解释与排障能力为主线。按优先级先建立 Linux、网络、容器与 Kubernetes 的职责图，再用证据、止损和恢复验证把概念转成面试回答。

目标岗位：以 Kubernetes 和云基础设施为主要工作环境的初级 DevOps Engineer。学习顺序采用广度优先：先能解释每个主干领域的基本原理、观察信号和排障入口，再深入 Kubernetes 高级能力。

使用方式

  • P0：高频基础，面试前必须能独立解释并完成基本排障。
  • P1：工程实践，应能说明为什么使用、如何验证以及失败时如何回滚。
  • P2：进阶辨析，理解边界和常见取舍即可，不优先记忆冷门实现细节。
  • 回答结构：先给结论，再说原理，然后给证据和命令，最后说明修复、验证与预防措施。
  • 排障结构：确认影响范围 → 最近变更 → 分层收集证据 → 提出并验证假设 → 缓解 → 根因修复 → 复盘。

Linux 系统与服务运行 P0

核心概念与原则

  • Linux 运维的主线是用户与权限、文件系统、进程、服务、资源、日志和信号。
  • 进程拥有 PID、父子关系、环境变量、文件描述符和退出码；线程共享进程的大部分资源。
  • systemd 负责服务生命周期和依赖关系，journalctl 提供集中日志入口。
  • CPU 高、内存不足、磁盘空间不足、inode 耗尽和文件描述符耗尽是不同故障，必须用对应证据区分。
  • 先观察再修改；先缓解影响，再处理根因；所有变更都要有验证方法。

延伸：Linux 与 Shell 运维实践、进程、资源与日志排障

常见面试问题

  • chmod 644 和 chmod 755 分别表示什么？sudo 与切换到 root 有什么区别？
  • 进程和线程有什么区别？僵尸进程与孤儿进程是什么？
  • Load Average 表示什么？它为什么不能直接等同于 CPU 使用率？
  • 内存中的 used、available、buffer/cache 如何理解？Swap 一定是坏事吗？
  • 服务启动失败、端口被占用或磁盘写满时如何排查？
  • SIGTERM 与 SIGKILL 有什么区别？为什么应优先优雅终止？

实战排障场景

  • 服务无法启动：检查 systemctl status、单元配置、日志、依赖、权限、端口和退出码。
  • 主机响应缓慢：先区分 CPU、内存、I/O、网络还是进程数问题，再定位具体进程。
  • 磁盘告警：同时检查容量和 inode，定位增长目录及已删除但仍被进程占用的文件。
  • Permission denied：从执行用户、目录逐级权限、所有者、挂载参数和安全模块逐层判断。

  • 长期使用 root 运行服务，或用 chmod 777 掩盖权限设计问题。

网络、DNS、HTTP 与 TLS P0

核心概念与原则

  • 请求链路通常经过 DNS 解析、路由、TCP 建连、TLS 握手、HTTP 交换和应用处理。
  • IP 与子网决定地址范围，路由表决定下一跳，NAT 改写地址，防火墙或安全组决定是否放行。
  • TCP 提供可靠字节流；UDP 无连接、开销低；端口标识主机上的网络服务。
  • DNS 将域名解析为记录，缓存和 TTL 会影响变更生效时间。
  • HTTP 状态码只是应用层结果；连接拒绝、超时、证书错误和 HTTP 5xx 属于不同层。

延伸：网络与 Web 链路排障

常见面试问题

  • TCP 三次握手和四次挥手解决什么问题？
  • Connection refused 与 Connection timed out 有何区别？
  • DNS 解析过程是什么？A、AAAA、CNAME 和 TTL 分别是什么？
  • 正向代理与反向代理有什么区别？四层和七层负载均衡如何区分？
  • HTTPS 如何建立信任？证书链、SNI 和主机名校验是什么？
  • 502、503、504 通常分别提示什么方向？

实战排障场景

  • 域名不可访问：按 DNS → 路由 → TCP 端口 → TLS → HTTP → 后端依赖的顺序定位。
  • 只有部分客户端失败：比较 DNS 缓存、IPv4/IPv6、代理、MTU、区域和证书信任差异。
  • 请求偶发超时：检查负载均衡后端健康、连接池、重传、上游延迟和资源饱和。
  • TLS 失败：确认系统时间、证书有效期、SAN、证书链和服务端 SNI 配置。

  • 为排障长期关闭防火墙、TLS 校验或证书验证。
  • 抓包前不缩小主机、端口和时间范围，得到大量无关流量。

Git 与 CI/CD P0

核心概念与原则

  • Git 管理提交图和分支引用；工作区、暂存区、本地仓库与远端仓库是不同状态。
  • CI 负责持续集成，包括构建、静态检查和测试；CD 负责可交付或自动部署。
  • 同一份不可变制品应逐环境晋级，避免在生产环境重新构建。
  • 流水线必须快速失败、保留证据、保护凭据，并明确人工审批和回滚边界。
  • 缓存用于加速，可以重建；制品是流水线交付结果，需要版本和保留策略。

延伸：自动化与 CI/CD 实践、GitHub Actions、GitLab CI、Jenkinsfile

常见面试问题

  • merge 与 rebase 有什么区别？什么时候不能随意 rebase？
  • CI 和 CD 分别解决什么问题？一条基础流水线有哪些阶段？
  • 缓存与制品有什么区别？为什么镜像标签不应只使用 latest？
  • 如何保护生产环境凭据？如何限制谁能触发生产部署？
  • 蓝绿、滚动和金丝雀发布的取舍是什么？
  • 部署失败如何回滚？数据库变更如何保持向前和向后兼容？

实战排障场景

  • 流水线偶发失败：先判断代码、环境、依赖源、并发竞争还是测试不稳定。
  • 构建成功但部署失败：核对制品版本、仓库权限、部署参数、集群权限和运行时事件。
  • 新版本异常：确认影响范围，停止继续发布，根据兼容性回滚应用或关闭功能开关。
  • 凭据泄漏：吊销并轮换凭据，检查使用记录和影响范围，再清理历史与补上扫描。

容器与 OCI 镜像 P0

核心概念与原则

  • 容器是受 namespaces、cgroups 和安全边界约束的宿主机进程，不是轻量虚拟机。
  • 镜像由只读分层和元数据组成，容器在其上增加可写层；持久数据不应依赖容器可写层。
  • OCI 定义镜像与运行时标准；Kubernetes 通常通过 CRI 使用 containerd 或 CRI-O。
  • Dockerfile 应可复现、分层合理、使用精确基础镜像、最小权限并支持优雅终止。
  • 构建时秘密不能通过 ARG 或镜像层长期保留，应使用构建系统的秘密挂载能力。

延伸：Docker、Docker 与可靠交付

常见面试问题

  • 镜像和容器有什么区别？容器与虚拟机有什么区别？
  • namespaces 与 cgroups 分别解决什么问题？
  • ENTRYPOINT 与 CMD 有什么区别？为什么 PID 1 很重要？
  • 多阶段构建有什么价值？如何减小镜像并提高安全性？
  • volume 与 bind mount 有什么区别？容器删除后数据是否存在？
  • 镜像 tag 与 digest 有何不同？如何保证部署内容不可变？

实战排障场景

  • 容器启动后立刻退出：检查主进程、命令参数、退出码、架构和运行时日志。
  • 镜像拉取失败：检查名称、tag/digest、仓库网络、认证、限流和节点磁盘。
  • 本地可运行但集群失败：比较 CPU 架构、用户权限、环境变量、文件路径和只读文件系统。
  • 容器无法优雅退出：确认 PID 1 是否转发信号、应用是否处理 SIGTERM、宽限期是否足够。

Kubernetes 架构与声明式模型 P0

核心概念与原则

  • API Server 是集群 API 入口；etcd 保存集群状态；Scheduler 负责绑定节点；Controller 持续调谐；kubelet 在节点执行 Pod 期望状态。
  • Kubernetes 使用声明式 API：用户提交期望状态，控制器通过 reconciliation loop 使实际状态逐步接近期望状态。
  • Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod；Service 为一组动态 Pod 提供稳定访问入口。
  • Namespace 提供逻辑隔离边界，但不是完整安全边界；权限和网络隔离还需要 RBAC、NetworkPolicy 等。
  • metadata、spec 与 status 分别表达身份、期望状态和观察到的状态。

延伸：Kubernetes Overview、Pod、Kubernetes 面试题

常见面试问题

  • 控制平面与工作节点有哪些主要组件？各自负责什么？
  • 从提交 Deployment 到 Pod 运行，中间经过哪些组件？
  • 什么是 reconciliation loop？声明式与命令式操作有何区别？
  • Pod、ReplicaSet、Deployment、StatefulSet、DaemonSet、Job 如何选择？
  • spec 与 status 为什么分开？OwnerReference 有什么作用？
  • Namespace 能隔离哪些资源，不能隔离哪些风险？

实战排障场景

  • kubectl 无法访问集群：检查 context、凭据、API Server 地址、网络和证书。
  • Deployment 副本不足：沿 Deployment → ReplicaSet → Pod → Event 查找阻塞点。
  • 对象反复恢复旧值：检查控制器、GitOps reconciliation、准入策略和字段管理者。
  • 节点 NotReady：检查节点条件、kubelet、容器运行时、磁盘与到控制平面的网络。

Kubernetes 工作负载与应用生命周期 P0

核心概念与原则

  • Pod 是最小调度单元，同一 Pod 内容器共享网络命名空间和声明的卷。
  • Init Container 在应用容器前依次完成；Sidecar 承担辅助能力，但会增加资源与生命周期复杂度。
  • startup probe 判断是否完成启动，liveness probe 决定是否重启，readiness probe 决定是否接收流量。
  • 优雅终止涉及 Endpoint 摘除、SIGTERM、preStop 和 terminationGracePeriodSeconds。
  • ConfigMap 适合非敏感配置；Secret 只是 Kubernetes 资源类型，不代表默认已加密或适合在 Git 中明文保存。

Kubernetes Service、DNS 与入口流量 P0

核心概念与原则

  • CNI 为 Pod 配置网络；Kubernetes 网络模型通常要求 Pod 间可直接寻址，具体实现由插件决定。
  • Service 通过 selector 关联后端，EndpointSlice 记录实际可用端点，ClusterIP 提供稳定虚拟地址。
  • kube-proxy 可用 iptables 或 IPVS 实现 Service 转发；部分 CNI 使用 eBPF 替代传统路径。
  • CoreDNS 提供集群内服务发现；短域名解析受 Namespace 和 Pod 的 DNS 搜索域影响。
  • Ingress 或 Gateway API 描述七层入口规则，真正处理流量的是对应控制器和负载均衡实现。

Kubernetes 调度、资源与存储 P0

核心概念与原则

  • Scheduler 先过滤不满足条件的节点，再对候选节点评分，最终通过绑定确定 nodeName。
  • requests 用于调度和资源保障；limits 用于运行时约束。CPU 超限通常被节流，内存超限可能触发 OOMKill。
  • QoS 分为 Guaranteed、Burstable 和 BestEffort，影响节点压力下的驱逐顺序，但不是绝对的可用性保证。
  • nodeSelector/affinity 表达吸引，taint/toleration 表达排斥；拓扑分布约束用于控制副本分散。
  • PV 表示存储资源，PVC 表示声明，StorageClass 定义动态供应，CSI 对接具体存储实现。

Kubernetes 系统化故障排查 P0

核心概念与原则

  • 先确认对象、Namespace、context、时间范围和影响范围，避免在错误集群排查。

核心概念与原则

弹性、高可用与成本意识 P2

核心概念与原则

  • 高可用依赖多副本、故障域分散、健康检查、容量余量、数据层设计和依赖可用性。
  • PodDisruptionBudget 限制自愿中断期间同时不可用的副本数量，不保证 Pod 永不宕机。
  • 扩容存在启动延迟和依赖瓶颈；缩容需要考虑连接排空、任务完成和存储。
  • 成本优化应从 requests 利用率、闲置资源、存储、网络出口和托管服务费用入手，不能以牺牲 SLO 为代价。

实战排障场景

  • HPA 不扩容：检查指标、target、requests、最小/最大副本和 HPA condition。
  • 扩容后仍然超时：检查数据库、连接池、队列、外部 API、负载均衡和节点容量。
  • 节点维护无法驱逐 Pod：检查 PDB、单副本工作负载、本地存储和终止宽限期。
  • 成本突然上升：按计算、存储、网络和托管服务拆分，并关联最近变更和自动扩缩容事件。

典型追问

  • CPU 使用率低但请求延迟高，HPA 应使用什么指标？
  • minAvailable: 100% 为什么可能阻塞节点维护？
  • 多副本都在同一节点上，节点故障时会怎样？
  • 使用 Spot/Preemptible 节点时，工作负载需要具备哪些特性？

常见误区与错误

  • 认为 HPA 能自动解决所有性能问题，忽略下游瓶颈。
  • 把 PDB 当成强可用性保证，忽略非自愿中断。
  • requests 远高于实际使用却只关注节点数量，不做工作负载级归因。
  • 为降低成本取消冗余、备份或容量余量，却没有评估 SLO 风险。

综合场景串联

发布后用户收到 502

  1. 确认影响范围、开始时间与最近发布，判断是否需要暂停或回滚。
  2. 从 Ingress/Load Balancer 确认 502 的产生层和后端健康。
  3. 检查 Service selector、EndpointSlice、Pod readiness 和 targetPort。
  4. 检查应用是否监听正确地址与端口，以及新旧版本日志差异。
  5. 直接从集群内访问 Pod IP 和 Service，逐层缩小问题。
  6. 修复后验证真实用户路径、错误率和延迟，并保留发布与恢复时间线。

Pod 反复重启

  1. 查看 describe 中的 Last State、Reason、Exit Code 和 Event。
  2. 使用 kubectl logs --previous 获取上一次容器日志。
  3. 区分应用崩溃、OOMKilled、liveness 失败、配置缺失和依赖不可用。
  4. 对比 requests/limits、探针和最近配置变更。
  5. 修复后观察 restart count、内存趋势、readiness 和请求成功率。

Pod 一直 Pending

  1. 从 FailedScheduling 事件读取调度器给出的明确原因。
  2. 检查 requests 与节点 allocatable，而不是只看瞬时使用率。
  3. 检查 taint/toleration、node affinity、拓扑分布和端口冲突。
  4. 如果涉及 PVC，检查绑定、StorageClass、CSI 和可用区。
  5. 修复后确认 Pod 已绑定节点、卷已挂载并通过 readiness。

私有集群中的应用无法访问云 API

  1. 在 Pod 内分别验证 DNS、路由、TCP/TLS 和 HTTP 返回。
  2. 检查私有子网默认路由、NAT 或私有 Endpoint。
  3. 检查云防火墙、NetworkPolicy 和代理配置。
  4. 如果返回 401/403，确认实际工作负载身份、权限和 Token 有效期。
  5. 避免通过写入长期 Access Key 绕过问题，修复身份或网络设计。

面试自检清单

  • 能否在两分钟内解释代码从提交到 Kubernetes 对外服务的完整路径？
  • 能否不靠猜测，给出 Linux 服务故障和 Pod 故障的证据顺序？
  • 能否明确区分 DNS、TCP、TLS、HTTP 和应用层失败？
  • 能否说明 requests、limits、QoS、HPA 和节点容量之间的关系？
  • 能否解释 Service、EndpointSlice、Ingress Controller 和 Load Balancer 各自职责？
  • 能否说明云 IAM、Kubernetes RBAC 和应用权限不是同一个层次？
  • 能否区分构建制品、版本晋级、GitOps 调谐与运行时验证？
  • 能否给每个修复配套验证命令，并说明回滚与残余风险？
  • 遇到没有实操过的平台或工具时，能否诚实说明边界并用已掌握的通用原理回答？
