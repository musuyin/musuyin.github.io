Gardener

2026-08-12

#Cloud#Gardener#Kubernetes#面试

理解主线

Gardener 用声明式资源管理 Kubernetes 集群的生命周期。Garden 接收管理意图，Seed 承载托管控制面，Shoot 是用户集群；区分这三层才能说明故障影响和运维职责。

什么是 Gardener

Gardener 是 SAP 开源的多云 Kubernetes 集群生命周期管理系统，核心思想是：

用 Kubernetes 来管理 Kubernetes（Kubernetes-native cluster management）

没有 Gardener 时，在多个云上（AWS/GCP/Azure/阿里云）管理成百上千个 K8s 集群，需要：

  • 为每个云写不同的自动化脚本
  • 手动处理集群创建、版本升级、节点扩缩、故障修复
  • 没有统一的 API 和操作界面

Gardener 提供一套统一的声明式 API，像操作 K8s 资源一样操作集群本身：创建一个 Shoot 对象 = 创建一个 K8s 集群。

核心架构：用 K8s 管理 K8s

Gardener 的天才设计在于：它把“管理集群”这件事本身，也用 K8s 的方式来实现。

Garden Cluster（管理平面，运行 Gardener 组件）
├── Seed Cluster（种子集群，每个云区域一个）
│   ├── 运行被管集群的控制平面组件（API Server / etcd / Scheduler）
│   └── Gardenlet（在 Seed 上运行，管理 Shoot 的生命周期）
└── Shoot Cluster（用户的 K8s 集群，仅含 Worker Node）

关键设计：Shoot 集群的控制平面不在 Shoot 自己的节点上运行，而是作为 Pod 跑在 Seed 集群里。这样控制平面与工作负载完全隔离，Shoot 的节点出问题不影响控制平面。

三层架构详解

Garden Cluster（花园集群）

  • 整个 Gardener 系统的大脑
  • 运行 Gardener API Server、Controller Manager 等核心组件
  • 存储所有 Shoot、Seed、CloudProfile 等自定义资源（CRD）
  • 用户/运维通过操作这里的资源来管理所有集群

Seed Cluster（种子集群）

  • 每个云厂商/区域部署一个 Seed
  • 负责托管 Shoot 集群的控制平面（控制平面以 Pod 形式运行在 Seed 上）
  • 运行 Gardenlet：类比 K8s 的 Kubelet，负责监听 Garden Cluster 的 Shoot 资源变更并执行
Seed Cluster 上托管的控制平面（针对某个 Shoot）：
├── kube-apiserver Pod
├── etcd Pod
├── kube-scheduler Pod
└── kube-controller-manager Pod

Shoot Cluster（芽集群）

  • 用户实际使用的 K8s 集群
  • 只包含 Worker Node，没有控制平面节点
  • Worker Node 上运行 Kubelet，连接到 Seed 上的 API Server

核心资源（CRD）

Gardener 将集群管理抽象为 K8s 自定义资源：

资源 说明
Shoot 用户的 K8s 集群定义（节点数/规格/K8s 版本/云厂商/网络配置）
Seed 种子集群注册信息（在哪个云/区域，能托管哪些 Shoot）
CloudProfile 云厂商能力描述（支持的机器类型/镜像/K8s 版本列表）
Project 命名空间级别的资源隔离，管理一组 Shoot

创建一个集群就是创建一个 Shoot 对象：

apiVersion: core.gardener.cloud/v1beta1
kind: Shoot
metadata:
  name: student-mgmt-cluster
  namespace: garden-team-a
spec:
  cloudProfileName: aws          # 使用 AWS 云
  region: eu-west-1
  secretBindingName: aws-creds   # 云账号凭证
  kubernetes:
    version: "1.28"              # K8s 版本
  provider:
    type: aws
    workers:
      - name: worker-pool
        machine:
          type: m5.xlarge        # 节点规格
        minimum: 2               # 最少节点数
        maximum: 10              # 最多节点数（自动扩缩容）
  networking:
    type: calico
    pods: 100.96.0.0/11
    services: 100.64.0.0/13

kubectl apply -f shoot.yaml → Gardener 自动在 AWS eu-west-1 创建一个完整的 K8s 集群。

Gardenlet

Gardenlet 是运行在每个 Seed 上的组件，类比关系：

K8s 概念 Gardener 概念
Node Seed Cluster
Kubelet（管理 Node 上的 Pod） Gardenlet（管理 Seed 上的 Shoot 控制平面）
kube-apiserver Gardener API Server

Gardenlet 的职责：

  • 监听 Garden Cluster 中 Shoot 资源的变化
  • 在 Seed 上创建/更新/删除对应的控制平面 Pod
  • 执行 Shoot 的生命周期操作（创建/升级/休眠/删除）
  • 上报 Shoot 健康状态回 Garden Cluster

核心能力

能力 说明
多云统一管理 AWS / GCP / Azure / 阿里云 / OpenStack，统一 API
集群生命周期管理 创建、升级、扩缩容、休眠、删除，全自动化
控制平面与工作负载隔离 控制平面跑在 Seed，Worker 节点故障不影响 API Server
集群休眠（Hibernation） 非工作时间自动关闭 Worker 节点，节省成本
系统组件自动管理 自动安装 CoreDNS、CNI、CSI、kube-proxy 等
扩展机制（Extensions） 通过 CRD + Controller 扩展支持新云厂商或自定义行为

Gardener vs Terraform vs Cluster API

对比项 Terraform Cluster API Gardener
定位 通用 IaC，管所有云资源 K8s 原生集群管理标准 企业级多云集群管理平台
控制平面隔离 无 可选 原生支持（Seed 托管）
集群休眠 无 无 原生支持
多集群规模 一般 中等 大规模（SAP 生产管理数千集群）
学习曲线 中 中 高
适用场景 基础设施全栈 标准化集群 API 大规模多云 K8s 平台

Gardener 在 SAP 的实践

SAP 用 Gardener 管理其云平台（SAP BTP / Kyma）上的数千个客户 K8s 集群：

  • 客户创建一个 K8s 集群 = 在 Gardener 中创建一个 Shoot
  • SAP 在多个云（AWS/Azure/GCP/阿里云）都部署了 Seed
  • 控制平面统一托管在 Seed，客户只看到 Worker 节点
  • 版本升级、节点修复全部自动化，无需人工介入

面试高频问题

Q：Gardener 是什么？解决了什么问题？ Gardener 是 SAP 开源的多云 K8s 集群生命周期管理系统，用“Kubernetes 管理 Kubernetes”的思路，通过统一的声明式 API（Shoot CRD）管理多个云上的集群创建、升级、扩缩容和删除，解决了大规模多云集群运维的复杂性。

Q：Shoot / Seed / Garden Cluster 各是什么？

  • Garden Cluster：管理平面，存储所有 Shoot/Seed 资源，是 Gardener 的大脑
  • Seed Cluster：每个云区域一个，托管 Shoot 集群的控制平面（控制平面以 Pod 形式运行在 Seed 上）
  • Shoot Cluster：用户实际使用的 K8s 集群，只含 Worker Node，控制平面在 Seed 上

Q：为什么要把控制平面放在 Seed 上，而不是 Shoot 自己的节点上？ 隔离控制平面与工作负载。Shoot 的 Worker 节点跑用户应用，节点故障或资源耗尽不会影响控制平面（API Server/etcd）的可用性。同时便于统一管理：一个 Seed 可以托管多个 Shoot 的控制平面，提升资源利用率。

Q：Gardenlet 和 Kubelet 有什么类比关系？ Kubelet 是 K8s 中运行在每个 Node 上、负责管理该 Node 上 Pod 的 Agent。Gardenlet 是运行在每个 Seed 上、负责管理该 Seed 托管的所有 Shoot 控制平面的 Agent——Seed 对应 Node，Shoot 控制平面对应 Pod，Gardenlet 对应 Kubelet。

Q：Gardener 和 Terraform 的分工？ 两者可以互补。Terraform 管底层云资源（VPC、IAM、云账号）；Gardener 管 K8s 集群生命周期（在这些云资源之上创建和维护集群）。也可以单独使用 Gardener（它自己会调用云 API 创建节点），或用 Terraform 创建完基础设施后再交给 Gardener 管理集群。

Q：Kubelet 是什么？

Kubelet 是运行在每个 Worker Node 上的 Agent，是 K8s 节点侧的核心组件。

职责：

  • 向 API Server 注册本节点，上报节点状态（CPU/内存/磁盘）
  • 监听 API Server，获取调度到本节点的 Pod 描述（PodSpec）
  • 调用 Container Runtime（containerd）创建/启动/停止容器
  • 执行健康检查（liveness/readiness probe），汇报 Pod 状态
  • 挂载 Volume、注入 ConfigMap/Secret 到容器
API Server
    │  下发 PodSpec（这个 Node 要跑哪些 Pod）
    ▼
Kubelet（每个 Node 上运行）
    │  调用 Container Runtime
    ▼
容器（实际运行的进程）
    │  状态上报
    └──────────────────→ API Server

Kubelet 是“Node 和集群控制平面之间的桥梁”：控制平面决定 调度什么，Kubelet 负责 执行和汇报。

Q：Kubelet 和 Gardenlet 的类比与区别？

两者都是“Agent”角色，遵循相同的设计模式：监听上层控制器的期望状态 → 在本地执行 → 上报实际状态。

对比项 Kubelet Gardenlet
运行位置 每个 Worker Node 每个 Seed Cluster
监听目标 K8s API Server（PodSpec） Garden Cluster（Shoot CRD）
管理对象 Node 上的容器/Pod Seed 上的 Shoot 控制平面
本质类比 Node 的执行者 Seed 的执行者
上报内容 Node/Pod 健康状态 Shoot 集群健康状态

一句话：Kubelet 让一台机器加入 K8s 集群；Gardenlet 让一个 Seed 集群加入 Gardener 体系，两者解决的是同一类问题，只是层级不同。

Q：如何精确理解 Gardener 三层架构的职责边界？

Seed Cluster 本身是一个 K8s 集群（基础设施），“监听 Garden Cluster 并管理 Shoot”这件事是由跑在 Seed 上的 Gardenlet 完成的，不是 Seed Cluster 自身有这个能力。

Garden Cluster（大脑）
│  存储 Shoot CRD、Seed 注册信息、CloudProfile、Project
│  运维人员在这里 kubectl apply shoot.yaml
│
│  ← Gardenlet 主动 Watch（不是 Garden 推送）
▼
Seed Cluster（基础设施，每个云/区域一个，如 AWS-eu01、Azure-jp02）
│  上面跑着：
│  ├── Gardenlet（Agent，负责把 Garden 的意图落地到 Seed）
│  └── Shoot 控制平面 Pod（kube-apiserver/etcd/scheduler，每个 Shoot 一套）
│
│  Shoot Worker Node 连接 Seed 上的 API Server
▼
Shoot Cluster（用户集群，仅有 Worker Node）
│  用户只能操作这里（部署 Pod/Service/Deployment）
│  完全感知不到 Garden Cluster 的存在
└── Worker Node（运行 Kubelet，连接 Seed 上的 kube-apiserver）

隔离的本质：用户拿到的 kubeconfig 指向 Seed 上的 kube-apiserver，而不是 Garden Cluster。所以用户天然访问不到 Garden Cluster 的任何资源——这个隔离不是靠额外的权限控制，而是架构上就分开了。Gardenlet 是唯一知道 Garden 和 Seed 两侧的组件，充当翻译和执行者。

Q：Gardener 在业界的普及程度如何？值得学吗？

普及程度：小众但精准。

Gardener 在整个业界的使用面不广，教程和社区资源远少于 Terraform、Helm 等主流工具。主要原因是：

  • 它解决的是大规模多云集群管理问题，受众本身就是少数大型云平台团队
  • SAP 主导开发，生态主要集中在 SAP 体系和少数欧洲企业云场景

已知的主要使用方：SAP（BTP/Kyma）、Deutsche Telekom、Beeline 等。

但对于 SAP Cloud Engineer 面试，它是核心考点，不是加分项。

理由：

  1. SAP 的云产品（BTP、Kyma Runtime）底层就是 Gardener 驱动的，技术面大概率深问
  2. 简历上有 Gardener 实习经验，面试官会预设你懂这套体系
  3. 业界懂 Gardener 的人极少，这是稀缺性优势，不是普通八股

更重要的价值：迁移能力。

Gardener 背后的设计思想——用 K8s 扩展机制（CRD + Controller）管理复杂的基础设施生命周期——是整个 Cloud Native 生态的核心范式。理解了 Gardener 的架构：

  • 能快速理解 Cluster API（CNCF 标准，与 Gardener 思路相近）
  • 理解 Operator 模式（K8s 生态最重要的扩展方式）
  • 面试时能讲出“我理解大规模集群管理的工程权衡”，而不只是“我会用 kubectl”

复习与应用

沿创建 Shoot 追踪资源和控制器，解释 Worker 故障与 Seed 故障影响为何不同。原文区域拓扑示意是教学布局，不应视为所有部署的固定约束。
