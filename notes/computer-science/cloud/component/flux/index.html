Flux

2026-09-10

#Cloud#Kubernetes#GitOps#Flux

理解主线

Flux 让配置来源持续驱动集群收敛：Source 产生版本化制品，控制器读取并应用目标状态，状态条件反馈调谐结果。理解漂移修复比只记住“提交后部署”更关键。

Flux 是什么

Flux 是一套运行在 Kubernetes 集群内的 GitOps 持续交付工具。它持续读取 Git、OCI Registry、Helm Repository 等配置来源，将其中声明的目标状态与集群实际状态对比，并通过 Kubernetes API 把两者重新同步。

可以把它概括为：

Git 中的 Kubernetes 配置
          │
          ▼
Flux 拉取、校验并生成版本化制品（artifact）
          │
          ▼
Flux 调用 Kubernetes API 执行 reconcile
          │
          ▼
集群实际状态持续收敛到 Git 声明的期望状态

这正是 GitOps 的 Pull 模式落地：CI 负责构建、测试并更新 Git；Flux 在集群内部负责拉取并部署。因此，CI 不必持有集群管理员 kubeconfig，部署权限留在集群边界内。

Flux 的目标不只是“Git 有新提交时部署一次”，而是持续 reconciliation（调谐）：

  • Git 中配置变更后，Flux 应用新状态；
  • 人工用 kubectl 修改受 Flux 管理的资源后，Flux 会发现漂移并恢复 Git 中的定义；
  • 资源创建失败或尚未就绪时，Flux 会记录失败原因，并在下一次调谐继续尝试。

Flux 在 GitOps 中的位置

一条典型的交付链路如下：

应用代码仓库
   │ CI：测试、构建镜像、推送镜像
   ▼
配置 Git 仓库
   │ PR：把镜像 tag 或 Kubernetes 配置提交并审核
   ▼
Flux（运行在目标 Kubernetes 集群）
   │ Pull：拉取配置并调用 Kubernetes API
   ▼
Deployment / Service / Ingress / Helm Release

Flux 管理的是部署配置的期望状态，而不是构建应用镜像。镜像构建、单元测试、镜像扫描仍属于 CI；将通过验证的镜像版本写入配置仓库，以及由 Flux 部署该版本，属于 CD。

与传统 Push 式 CD 相比，最重要的差异是部署动作的发起方：

对比项 Push 式 CD Flux 的 Pull 式 GitOps
谁连接 Kubernetes API CI 系统 集群内的 Flux Controller
集群凭证位置 CI 平台的 Secret 集群内 ServiceAccount / RBAC
状态漂移 通常需要额外检测 Controller 持续调谐
审计入口 CI 日志与部署脚本 Git 提交、PR、Flux 事件
回滚方式 再执行一套部署步骤 回滚 Git 提交，Flux 自动收敛

Kubernetes 原生的工作方式

Flux 不是一个常驻的“部署脚本”。它使用 Kubernetes 的 API 扩展机制：安装后会注册 CRD，并用 Controller 监听这些自定义资源。你在 Git 中声明 Flux CR，Controller 将其状态写回 .status.conditions，因此可以像查看 Deployment 一样查看调谐结果。

最常见的资源关系是：

GitRepository
  └── 表示从哪个 Git 仓库、分支、目录获取配置
        │
        ▼
Kustomization
  └── 表示从制品中的哪个路径构建、校验并应用资源
        │
        ▼
Kubernetes 资源
  └── Deployment、Service、ConfigMap、Namespace 等

注意：GitRepository 和 Kustomization 是 Flux CRD；后者首字母大写。目录中的 kustomization.yaml 则是 Kustomize 的配置文件，两者不是同一个对象。

控制器分工

Flux 是多个专职 Controller 的组合，而非单一二进制程序。常用组件如下：

Controller 主要职责 常见 CRD
source-controller 从 Git、OCI、Helm Repository、Bucket 拉取内容，生成可复用的 artifact GitRepository、OCIRepository、HelmRepository、Bucket
kustomize-controller 基于 artifact 构建和应用 Kustomize 清单，处理依赖、健康检查、垃圾回收 Kustomization
helm-controller 安装、升级、测试、回滚 Helm Chart HelmRelease
notification-controller 将 Flux 事件发送到 GitHub、Slack、Webhook 等 Provider Alert、Provider、Receiver
image-reflector-controller 扫描镜像仓库中的标签与摘要 ImageRepository、ImagePolicy
image-automation-controller 按镜像策略更新 Git 中的镜像引用并提交 ImageUpdateAutomation

前两个 Controller 构成最小 GitOps 闭环。Helm、通知和镜像自动化在需要这些能力时再加入。

核心概念

Source

Source 是 Flux 可消费的配置来源。source-controller 定期拉取来源内容，生成带 revision 的 artifact。后续 Controller 不直接访问 Git，而是消费该 artifact，这让下载、缓存和版本追踪职责保持集中。

GitRepository 常用字段：

  • spec.url：仓库地址；
  • spec.ref：分支、Tag 或 Commit；
  • spec.interval：轮询间隔；
  • spec.secretRef：访问私有仓库的认证 Secret；
  • spec.verify：提交或 Tag 签名验证。

Kustomization

Flux Kustomization 描述“从某个 Source 的某个路径，将哪些资源以什么策略应用到集群”。常用字段：

  • spec.sourceRef：引用 GitRepository 等 Source；
  • spec.path：artifact 内的清单目录；
  • spec.prune：删除 Git 中已移除、但曾由该对象管理的资源；
  • spec.wait / spec.healthChecks：等待指定工作负载就绪；
  • spec.dependsOn：声明另一个 Kustomization 必须先成功；
  • spec.serviceAccountName：以指定 ServiceAccount 的权限应用资源；
  • spec.interval：定期调谐间隔。

prune: true 很关键：它让 Git 的“删除”也成为期望状态的一部分。启用前必须明确该 Kustomization 的管理边界，避免将不属于它的资源纳入清理范围。

HelmRelease

当工作负载以 Helm Chart 交付时，使用 HelmRelease。它引用 HelmRepository 或 OCIRepository 中的 Chart，并用 values 或 valuesFrom 提供配置；helm-controller 负责把 Helm 的安装、升级和失败处理纳入调谐循环。

Flux 与 Helm 并不冲突：Helm 负责 Chart 的模板化和 Release 生命周期，Flux 负责让 HelmRelease 的声明持续与 Git 保持一致。

最小实战

下面的示例将一个 Git 仓库中的 Nginx Deployment 交给 Flux 管理。假设 Flux 已安装到 flux-system 命名空间，目标仓库为 https://github.com/example/platform-config，使用 main 分支。

仓库目录：

platform-config/
├── clusters/
│   └── dev/
│       ├── source.yaml
│       └── apps.yaml
└── apps/
    └── nginx/
        ├── deployment.yaml
        ├── service.yaml
        └── kustomization.yaml

先声明配置来源：

# clusters/dev/source.yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: platform-config
  namespace: flux-system
spec:
  interval: 1m
  url: https://github.com/example/platform-config
  ref:
    branch: main

再声明 Flux 要应用的路径：

# clusters/dev/apps.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: nginx
  namespace: flux-system
spec:
  interval: 10m
  path: ./apps/nginx
  prune: true
  sourceRef:
    kind: GitRepository
    name: platform-config
  wait: true
  timeout: 2m

被部署应用使用普通 Kubernetes 清单：

# apps/nginx/kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml
# apps/nginx/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
  namespace: default
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
# apps/nginx/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx
  namespace: default
spec:
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80

将 source.yaml 和 apps.yaml 应用到集群后，Flux 会拉取仓库、构建 apps/nginx 并创建 Nginx 资源：

kubectl apply -f clusters/dev/source.yaml
kubectl apply -f clusters/dev/apps.yaml

实际生产环境一般用 flux bootstrap 将 Flux 组件及同步入口一并提交进仓库。例如 GitHub 场景：

flux check --pre
flux bootstrap github \
  --owner=example-org \
  --repository=platform-config \
  --branch=main \
  --path=clusters/dev \
  --personal=false

该命令会安装 Flux，并在指定 Git 路径创建同步所需的 flux-system 清单。之后应以 Git 提交变更，而不是手动修改集群中的受管资源。

从提交到部署的调谐过程

以修改 deployment.yaml 中 nginx:1.27 为例：

  1. 开发者提交 Pull Request，更新镜像 tag。
  2. 审核通过后，配置变更合并到 main。
  3. source-controller 在轮询周期内发现新 commit，拉取并生成新的 artifact。
  4. kustomize-controller 发现 GitRepository revision 更新，从 artifact 的 ./apps/nginx 读取清单。
  5. Controller 调用 Kubernetes API，更新 Deployment。
  6. wait: true 让 Controller 等待工作负载就绪；结果写入 Kustomization.status.conditions。
  7. 后续人工修改副本数或镜像时，下一轮调谐会重新应用 Git 中的清单。

interval 决定轮询上限。通过 Webhook Receiver 可以在 Git 推送时更快触发 Source 更新，但 Webhook 是加速机制，持续调谐仍是 Flux 保证一致性的基础。

常用命令与排障

# 检查 Flux 组件与 Kubernetes 前置条件
flux check

# 查看 Git Source 的最新 revision 与就绪状态
flux get sources git -A

# 查看 Kustomization 的调谐状态
flux get kustomizations -A

# 查看 HelmRelease 的状态
flux get helmreleases -A

# 立即请求重新拉取 Git Source
flux reconcile source git platform-config -n flux-system

# 立即请求重新应用 Kustomization，并先同步其 Source
flux reconcile kustomization nginx -n flux-system --with-source

# 查看 Controller 日志
flux logs --level=error -A

# 直接查看 Kubernetes 状态条件和事件
kubectl describe kustomization nginx -n flux-system

排障按依赖方向进行：先确认 Source 是否 Ready，再确认 Kustomization 或 HelmRelease 是否 Ready，最后检查目标资源。

现象 优先检查 常见原因
GitRepository 未就绪 flux get sources git -A、source-controller 日志 仓库地址、分支、认证 Secret、网络连通性或签名验证失败
Kustomization 未就绪 kubectl describe kustomization path 不存在、YAML 无效、缺少 CRD、RBAC 拒绝或依赖尚未成功
已显示应用成功但工作负载不可用 Deployment/Pod 事件与日志 镜像拉取失败、探针失败、资源配额不足、应用自身配置错误
Git 删除了资源但集群仍存在 Kustomization.spec.prune 与对象归属 未启用 prune，或资源未由该 Kustomization 管理
人工修改总被恢复 Git 提交与 Kustomization 状态 这是持续调谐的正常结果；应通过 Git 修改期望状态

安全与多租户

Flux 的安全边界应围绕“最小权限”和“Git 是变更入口”设计：

  • 给 Flux 访问 Git 的 Deploy Key 或 Token 只授予读取配置仓库所需的权限；
  • 将写入 Kubernetes 的权限限制在专用 ServiceAccount 的 RBAC 范围内；
  • 使用 Kustomization.spec.serviceAccountName 让不同团队以不同权限调谐资源；
  • 将团队的 Source、Kustomization 和业务资源划分到相应 Namespace；
  • 使用 SOPS 等方案加密 Git 中的 Secret，避免明文密钥进入版本库；
  • 通过 Git 分支保护、PR 审核、提交签名与 Flux Source 验证建立变更审计链。

Flux 支持任意数量的 Git 仓库。多团队共用一个集群时，平台团队可以管理 Flux 安装与集群级资源，业务团队只管理被授权 Namespace 下的 Source 和 Kustomization；这样既保持 GitOps 自助交付，也不把 cluster-admin 权限扩散给每条 CI 流水线。

Flux、Argo CD 与 Helm 的关系

工具 核心定位 典型使用方式
Flux Kubernetes 原生、Controller 驱动的 GitOps 工具集 用 CRD 声明 Source 和调谐策略，偏向 Git 声明与 CLI 工作流
Argo CD GitOps 持续交付平台 用 Application 管理同步，提供较完整的 Web UI
Helm Kubernetes 包管理器 用 Chart 模板化和发布应用，可由 Flux 或 Argo CD 驱动

Flux 与 Argo CD 解决的是同一层问题，通常选择其一作为集群的 GitOps 控制平面；Helm 解决的是 Chart 打包与渲染问题，常作为两者管理的应用交付格式。

入门时的实践原则

  • 将集群配置与应用代码分仓，或者至少分目录和分支管理；
  • 让 Git 默认分支的内容始终代表可部署、可审计的期望状态；
  • 以小的 Kustomization 划分管理边界，基础设施、CRD、业务应用按依赖拆分；
  • 用 dependsOn 明确 CRD、Namespace、基础设施与业务工作负载的先后关系；
  • 在 Kustomization 上启用健康检查或 wait，把“资源已提交”与“应用已就绪”区分开；
  • 从只读 Git 拉取和人工提交镜像 tag 开始，确认审计与 RBAC 边界后再启用镜像自动更新。

面试高频问题

Q：Flux 的核心价值是什么？

Flux 将 Git 中的声明式配置持续调谐到 Kubernetes 集群。它把部署权限放在集群内、把变更历史放在 Git 中，并能自动修复实际状态相对期望状态的漂移。

Q：Flux 为什么比 CI 直接执行 kubectl apply 更符合 GitOps？

CI Push 部署需要把集群凭证交给 CI 平台，并且通常只在流水线运行时部署一次。Flux 在集群内 Pull 配置，CI 无需持有集群高权限凭证；Flux Controller 会持续比较并收敛状态。

Q：GitRepository、Kustomization 和 kustomization.yaml 分别是什么？

GitRepository 是描述 Git 来源的 Flux CR；Kustomization 是描述从来源的哪个路径应用资源的 Flux CR；小写文件 kustomization.yaml 是 Kustomize 的资源组合清单。

Q：prune: true 的作用和风险是什么？

它会删除已不在 Git 期望状态中、且属于该 Kustomization 管理的资源，实现声明式删除。风险在于管理边界定义错误时可能误删受管资源，因此应按应用或基础设施单元拆分 Kustomization。

Q：Flux 如何实现多租户？

通过 Namespace 隔离、每租户的 Git Source 与 Kustomization、以及 serviceAccountName 配合 RBAC 限制调谐权限。租户能部署其 Namespace 内的资源，但无法借助 Flux 获得集群级权限。

总结

Flux 是 Kubernetes 内的 GitOps 调谐控制平面。它把 Git、OCI 或 Helm 等配置来源转换为 Kubernetes API 上的持续期望状态：Source Controller 负责获取版本化配置，Kustomize 或 Helm Controller 负责应用配置，状态、事件和权限都遵循 Kubernetes 原生模型。

入门时抓住一条主线即可：GitRepository 指向配置来源，Kustomization 指向应用路径，Controller 持续让集群收敛到 Git 的状态。

复习与应用

人工改动受管资源后会发生什么？顺着 Source → Kustomization/HelmRelease → 资源 Ready 检查失败位置。
