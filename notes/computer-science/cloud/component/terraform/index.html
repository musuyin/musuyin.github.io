Terraform

2026-08-12

#Cloud#Terraform#IaC#面试

理解主线

Terraform 通过 Provider 管理外部资源，用配置表达目标，用 State 建立资源映射，plan 展示预期变更。真正执行前要理解哪些变化原地更新，哪些会替换资源。

什么是 Terraform

Terraform 是 HashiCorp 开源的基础设施即代码（IaC，Infrastructure as Code）工具。

它解决什么问题？

没有 Terraform 之前，创建云资源（虚拟机、数据库、网络、K8s 集群）需要：

  • 手动在云控制台点击操作（容易出错，无法复现）
  • 写各云厂商自己的脚本（AWS CLI / gcloud / az，各不相同）
  • 没有版本控制，不知道谁改了什么

Terraform 的做法：用代码描述你想要的基础设施，Terraform 负责把它变成现实。

写 .tf 文件（声明期望状态）→ terraform plan（预览变更）→ terraform apply（执行创建/修改）

类比理解：

场景 工具 作用
管理应用部署 Kubernetes YAML 声明期望的应用状态
管理基础设施 Terraform HCL 声明期望的云资源状态

K8s 管的是“应用层”（Pod/Service），Terraform 管的是“基础设施层”（服务器/网络/云数据库/K8s 集群本身）。

核心概念

HCL（配置语言）

Terraform 使用 HCL（HashiCorp Configuration Language）编写配置文件，扩展名为 .tf。

# 创建一个 AWS EC2 实例
resource "aws_instance" "web_server" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = {
    Name = "student-mgmt-server"
  }
}

Resource（资源）

Resource 是 Terraform 管理的最小单元，代表一个云基础设施对象。

resource "<provider>_<type>" "<local_name>" {
  # 配置参数
}
  • aws_instance：AWS EC2 虚拟机
  • google_container_cluster：GKE K8s 集群
  • azurerm_kubernetes_cluster：AKS K8s 集群
  • aws_s3_bucket：AWS S3 存储桶

Provider

Provider 是对接各云厂商 API 的插件，告诉 Terraform“去哪个云上操作”。

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

常用 Provider：AWS、GCP、Azure、Kubernetes、Helm（是的，Helm 也有 Terraform Provider）。

State（状态文件）

terraform.tfstate 是 Terraform 最重要的文件，记录了当前实际部署的资源状态。

.tf 文件（期望状态）+ terraform.tfstate（实际状态）→ terraform plan 计算差异 → apply 执行变更
  • State 默认存本地，生产环境必须存远端（Remote State），如 S3、GCS、Terraform Cloud
  • State 文件包含敏感信息，不能提交到 Git
# 远端 State 配置示例（存到 S3）
terraform {
  backend "s3" {
    bucket = "my-terraform-state"
    key    = "prod/student-mgmt/terraform.tfstate"
    region = "us-east-1"
  }
}

Module（模块）

Module 是可复用的 Terraform 配置包，类比 Helm Chart——封装一组资源，通过变量参数化。

# 调用一个 VPC 模块
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"

  name = "student-mgmt-vpc"
  cidr = "10.0.0.0/16"
}

Variable（变量）

# variables.tf
variable "environment" {
  type    = string
  default = "dev"
}

variable "replica_count" {
  type    = number
  default = 2
}

# 引用变量
resource "aws_instance" "web" {
  instance_type = var.environment == "prod" ? "t3.medium" : "t2.micro"
}

核心工作流

terraform init     # 初始化，下载 Provider 插件
      │
terraform plan     # 预览变更（不实际执行），输出 +创建 ~修改 -删除
      │
terraform apply    # 执行变更，更新 state 文件
      │
terraform destroy  # 销毁所有资源（危险！）

terraform plan 输出示例：

+ aws_instance.web_server will be created    # + 表示新建
~ aws_security_group.sg will be updated      # ~ 表示修改
- aws_s3_bucket.old will be destroyed        # - 表示删除

Plan: 1 to add, 1 to change, 1 to destroy.

Terraform vs 手动操作 vs Ansible

对比项 手动控制台 Ansible Terraform
版本控制 无 有 有
幂等性 无 有（部分） 有（声明式）
多云支持 各自操作 有限 原生支持
定位 - 配置管理（在已有机器上装软件） 基础设施编排（创建机器本身）
状态追踪 无 无 有（state 文件）

Terraform 管“有没有这台机器”，Ansible 管“这台机器上装了什么软件”。两者互补，不冲突。

实际场景：用 Terraform 创建 K8s 集群

# 在 GCP 上创建一个 GKE 集群
resource "google_container_cluster" "primary" {
  name     = "student-mgmt-cluster"
  location = "us-central1"

  initial_node_count = 3

  node_config {
    machine_type = "e2-medium"
    disk_size_gb = 50
  }
}

# 输出 kubeconfig 所需信息
output "cluster_endpoint" {
  value = google_container_cluster.primary.endpoint
}

然后用 Helm 往这个集群里部署应用——Terraform 负责创建集群，Helm 负责往集群里部署应用，两者分工清晰。

Terraform（基础设施层）→ 创建 K8s 集群、网络、数据库
      ↓
Helm（应用层）→ 往集群里部署应用、中间件

面试高频问题

Q：Terraform 是什么？解决了什么问题？ Terraform 是基础设施即代码工具，用 HCL 声明式描述云资源（服务器、网络、K8s 集群等），通过 plan/apply 工作流实现版本化、可复现的基础设施管理，支持多云统一操作。

Q：State 文件的作用是什么？为什么要存到远端？ State 记录 Terraform 当前管理的实际资源状态，是计算“期望状态 vs 实际状态”差异的基础。本地 State 在团队协作时会产生冲突，且容易丢失；远端 State（S3/GCS）支持加锁（防止并发 apply）和共享，是生产必选。

Q：Terraform 和 Helm 的关系？各管什么层？ 两者分工互补。Terraform 管基础设施层（创建 K8s 集群本身、云网络、云数据库、IAM 权限），Helm 管应用层（往已有的 K8s 集群里部署应用）。典型流程：Terraform 创建集群 → Helm 部署应用。

Q：terraform plan 和 terraform apply 的区别？ plan 只计算并预览变更（会创建/修改/删除哪些资源），不实际执行，用于 Review；apply 真正执行变更并更新 state 文件。生产环境标准流程是：plan 输出结果人工确认后再 apply。

Q：什么是幂等性？Terraform 如何保证？ 幂等性指多次执行同一操作结果相同。Terraform 通过声明式配置 + state 对比保证：如果资源已存在且与 .tf 描述一致，apply 不做任何操作；只对存在差异的资源执行变更。

Q：Terraform 管什么，不管什么？

Terraform 管 Terraform 不管
云服务器（CPU / 内存 / 磁盘规格） Pod / Deployment / Service（这是 K8s / Helm 的职责）
网络（VPC / 子网 / 防火墙规则） 容器内的应用配置
K8s 集群本身（Node 数量 / 节点规格 / 版本） 应用的业务逻辑
云数据库（MySQL / Redis 实例的规格、存储大小）
IAM 权限 / 存储桶 / DNS 等云资源

一句话：Terraform 管“有什么机器/资源”，Helm/K8s 管“机器上跑什么应用”。

Q：修改 Terraform 重建集群后，需要重新跑 Helm 吗？可以让 Terraform 自动触发 Helm？

有三种方案，复杂度递增：

方案一：手动分步执行（最常见）

terraform apply   # 重建/修改集群
      ↓
helm upgrade      # 手动重新部署应用

集群重建后 Helm Release 会丢失，需要手动重跑。简单直接，适合小团队。

方案二：Terraform 内嵌 Helm Provider（自动触发）

Terraform 有官方的 Helm Provider，可以把 Helm Release 也声明为 Terraform 资源，terraform apply 一次性完成“建集群 + 部署应用”：

# 先创建 K8s 集群
resource "google_container_cluster" "primary" {
  name               = "my-cluster"
  initial_node_count = 3
}

# 再用 Helm Provider 部署应用（depends_on 保证顺序）
resource "helm_release" "student_mgmt" {
  depends_on = [google_container_cluster.primary]

  name       = "student-mgmt"
  chart      = "./mychart"
  values     = [file("values-prod.yaml")]
}

优点：一条命令全搞定；缺点：Terraform state 既管基础设施又管应用，职责混杂，集群频繁变更时 Helm 也会被反复触发。

方案三：GitOps（生产主流）

用 ArgoCD 或 Flux 持续监听 Git 仓库，集群重建后自动重新同步 Helm Chart，无需手动操作：

Git 仓库（Helm Chart + values）
      │
      ▼ ArgoCD 持续监听
      自动 helm apply → K8s 集群
Terraform（管集群）←→ ArgoCD（管应用）
两者解耦，各自独立，集群重建后 ArgoCD 自动恢复应用

实践建议：

场景 推荐方案
个人项目 / 小团队 方案一（手动分步）或方案二（Helm Provider）
生产环境 / 多团队 方案三（GitOps，Terraform + ArgoCD）
SAP / 大型云平台 方案三，配合 Gardener 管理集群生命周期
