Helm

2026-08-12

#Cloud#Kubernetes#Helm

理解主线

Helm 把模板与 values 渲染为资源，并按 Release 管理安装、升级与回滚。Chart、values、渲染结果和运行中的资源是四种不同对象；排障时逐层核对，不能只看 values 文件。

Helm 的工作主线

Helm 将 Chart 模板和配置值转换为 Kubernetes 资源，并管理安装、升级和回滚。Flux 等 GitOps 工具持续获取期望配置，再调用 Helm 或直接应用渲染结果。

GitOps 把期望部署状态保存在版本化来源中，由控制器持续调谐。调谐是读取期望状态、检查实际状态、执行必要变更的循环。

flowchart TD
    A[Chart 模板与依赖] --> C[Helm 渲染]
    B[默认值与环境 Values] --> C
    C --> D[Kubernetes 资源清单]
    D --> E[Helm 安装或升级]
    E --> F[Kubernetes API]
    E --> G[Release 历史记录]
    F --> H[Deployment 等控制器]
    H --> I[Pod 与应用]

Helm 不调度 Pod，也不构建应用镜像。Kubernetes 控制器、调度器和节点组件执行资源对应的运行行为。

本文的独立 Helm 行为以 Helm 3 为基线，Flux 示例使用 HelmRelease v2。不同版本的参数和功能需对照已安装版本。Flux 笔记介绍 Flux 的整体结构。

什么是 Helm

Helm 是 Kubernetes 的包管理器，类比关系：

生态 包管理器 包
Linux apt / yum .deb / .rpm
Node.js npm package
Kubernetes Helm Chart

没有 Helm 时，部署一个应用需要手动维护多个 YAML 文件（Deployment、Service、Ingress、ConfigMap…），版本升级、多环境配置、回滚都很繁琐。Helm 把这些文件打包成一个 Chart，一条命令完成安装/升级/回滚。

核心概念

Chart

Chart 是 Helm 的包，包含一组描述 K8s 资源的模板文件。

mychart/
├── Chart.yaml          # Chart 元信息（名称、版本、描述）
├── values.yaml         # 默认配置值
├── templates/          # K8s YAML 模板（用 Go template 语法）
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   └── _helpers.tpl    # 公共模板片段
└── charts/             # 依赖的子 Chart

Values

values.yaml 存放 Chart 的默认配置，模板中通过 {{ .Values.xxx }} 引用。

# values.yaml
replicaCount: 3
image:
  repository: nginx
  tag: "1.25"
service:
  type: ClusterIP
  port: 80
# templates/deployment.yaml（模板引用）
spec:
  replicas: {{ .Values.replicaCount }}
  containers:
    - image: {{ .Values.image.repository }}:{{ .Values.image.tag }}

部署时可通过 --set 或 -f 覆盖默认值，实现多环境配置复用。

Release

每次 helm install 都会创建一个 Release，即 Chart 在集群中的一次具体部署实例。

  • 同一个 Chart 可以安装多次，每次是不同的 Release（不同名称）
  • Release 记录了安装历史，支持版本回滚
Chart + 合并后的 Values → Kubernetes 资源清单
Helm 安装或升级这些资源，并记录 Release 与 revision

Repository

存放 Chart 的远程仓库，类似 npm registry 或 Docker Hub。

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo bitnami/mysql

核心命令

# 安装
helm install <release-name> <chart> [-f values.yaml] [--set key=value]
helm install student-mgmt ./mychart -f prod-values.yaml

# 升级（Chart 或 Values 变更时）
helm upgrade <release-name> <chart> [-f values.yaml]
helm upgrade student-mgmt ./mychart --set image.tag=v2.0

# 回滚
helm rollback <release-name> [revision]
helm rollback student-mgmt 1        # 回滚到第 1 个版本

# 查看
helm list                            # 列出所有 Release
helm status <release-name>          # 查看 Release 状态
helm history <release-name>         # 查看版本历史

# 卸载
helm uninstall <release-name>

# 渲染模板（不实际部署，用于调试）
helm template <release-name> <chart> [-f values.yaml]

# 打包
helm package ./mychart               # 生成 mychart-0.1.0.tgz

多环境配置实践

Helm 最大的价值之一：同一套模板，不同环境用不同 Values。

mychart/
├── values.yaml           # 默认值（通用）
├── values-dev.yaml       # 开发环境覆盖
└── values-prod.yaml      # 生产环境覆盖
# values-prod.yaml
replicaCount: 5
resources:
  limits:
    cpu: "1"
    memory: "512Mi"
helm install student-mgmt ./mychart -f values-prod.yaml

Helm vs 直接 kubectl apply

对比项 kubectl apply Helm
配置管理 多个独立 YAML，难以统一管理 一个 Chart，Values 集中管理
多环境 可结合 Kustomize overlays 管理 用 Values 文件覆盖默认配置
升级/回滚 无应用级 Release 历史；Deployment 有自己的 rollout 历史 helm upgrade / helm rollback
依赖管理 无 Chart 可声明依赖其他 Chart
复用性 可复用清单或 Kustomize bases Chart 可发布到仓库供他人使用

面试高频问题

Q：Helm 是什么？解决了什么问题？ Helm 是 K8s 的包管理器。解决了手动维护多个 YAML 文件繁琐、多环境配置复用困难、无法追踪版本历史和回滚的问题。

Q：Chart、Release、Repository 的关系？ Chart 是模板包（含 YAML 模板 + 默认 Values），Repository 是存放 Chart 的远端仓库，Release 是 Chart 安装到集群后的具体运行实例。同一个 Chart 可创建多个 Release（不同配置）。

Q：如何实现多环境部署？ 同一套 Chart 模板，为每个环境维护一个 Values 文件（values-dev.yaml、values-prod.yaml），通过 helm install -f values-prod.yaml 覆盖默认值，无需修改模板本身。

Q：Helm upgrade 和 helm rollback 怎么工作？ helm upgrade 渲染新的 Chart 和 Values，并更新已有 Release 的资源。Deployment 的 Pod 模板变化后，Kubernetes 才按更新策略替换 Pod；只改 ConfigMap 不一定触发重启。升级尝试通常产生新的 revision 记录，失败状态也可能写入历史。helm rollback 根据历史 revision 恢复资源配置，并产生新的 revision。

Q：Helm 和 Spring Boot 配置体系的类比？

两者设计思路高度一致：

Spring Boot Helm 作用
application.yaml values.yaml 默认配置
application-dev.yaml values-dev.yaml 环境特定覆盖
--spring.profiles.active=prod -f values-prod.yaml 启动时选择配置
@Value("${xxx}") / @ConfigurationProperties {{ .Values.xxx }} 将配置值注入到目标
Java 类字段（JVM 运行时） K8s YAML 模板（部署资源定义） 被注入的目标

核心相同点：配置与代码/模板分离，同一套模板，通过切换配置文件适配不同环境。

差异点：Spring Boot 注入发生在程序运行时（JVM 加载），注入目标是内存中的字段值；Helm 注入发生在部署阶段（helm install 渲染模板），注入目标是 K8s 资源的 YAML 定义，渲染完成后才提交给 K8s。

Q：实践中应该改 Helm values.yaml 还是 Spring Boot application.yaml？

一种常见做法是让 application.yaml 保持通用，把环境差异交给部署配置。下面用环境变量作为 Helm 与应用之间的配置传递方式。

完整的配置流转链路是：

Helm values.yaml
      │
      ▼ helm install 渲染
K8s ConfigMap / Secret
      │
      ▼ K8s 注入到 Pod
环境变量（env vars）
      │
      ▼ Spring Boot 读取
application.yaml 中的 ${ENV_VAR} 占位符
      │
      ▼
JVM 运行时字段

各层职责划分：

配置层 放什么 示例
application.yaml 应用级固定配置、结构定义、用 ${} 占位 连接池大小、日志格式、超时时间默认值
Helm values.yaml 环境差异化的部署参数 副本数、镜像 tag、数据库地址、资源限制
K8s ConfigMap/Secret 由 Helm 渲染生成，注入到 Pod 环境变量 DB_URL、REDIS_HOST、API_KEY

实际代码示例：

# application.yaml（固定，随代码一起打包进镜像）
spring:
  datasource:
    url: ${DB_URL}           # 占位符，从环境变量读取
    username: ${DB_USER}
  redis:
    host: ${REDIS_HOST:localhost}  # 冒号后是本地开发默认值
server:
  port: 8080
logging:
  level:
    root: INFO
# Helm values-prod.yaml（环境差异，不进镜像）
env:
  DB_URL: jdbc:mysql://prod-db.internal:3306/student
  DB_USER: prod_user
  REDIS_HOST: prod-redis.internal
# Helm Deployment 模板片段（渲染后才是普通 Kubernetes YAML）
env:
  - name: DB_URL
    value: {{ .Values.env.DB_URL }}
  - name: DB_USER
    valueFrom:
      secretKeyRef:           # 敏感值从 Secret 读取
        name: db-secret
        key: username

核心原则：

  • 建议让 application.yaml 保存结构和默认值，将环境差异放在部署时提供的配置中
  • 环境配置可通过环境变量、挂载文件或外部配置服务提供；敏感值宜引用已有 Secret，避免写入普通 Values 或 Git
  • 这样镜像本身是环境无关的，同一个镜像可以部署到 dev/staging/prod，只换 Helm values

Helm 一次部署内部发生什么

以 helm upgrade --install student-mgmt ./mychart -n apps -f values-prod.yaml 为例：

  1. Helm 使用当前 kubeconfig 连接 Kubernetes API。--install 表示 Release 不存在时执行安装。
  2. Helm 读取 Chart、子 Chart 和默认 Values。需要的依赖应先通过 helm dependency build 准备。
  3. Helm 合并配置：Chart 默认值、各个 -f 文件、--set 参数。相同键通常由后面的配置覆盖，列表通常整体替换。
  4. Helm 用 Go template 渲染 templates/，产生 Deployment、Service 等资源清单。
  5. Helm 执行适用的安装或升级 Hook，并创建、更新或删除相应资源。普通资源变更不构成数据库式原子事务。
  6. Helm 保存 Release 记录，包括 Chart、配置、清单、revision 和操作状态。Helm 3 默认把记录保存为 Release 所在命名空间内的 Secret。
  7. Kubernetes 根据新资源状态启动、更新或终止 Pod。Helm 是否等待就绪，取决于命令参数和操作类型。

Helm 3 的 CLI 自身执行上述操作，不需要集群内的 Tiller 服务。Release 是部署及其历史记录，不等于某一个 Pod。

Chart version 是包版本；appVersion 是描述性应用版本，不会自动指定镜像。镜像版本由模板读取的 Values 或模板内容决定。Release revision 则是该安装实例的操作历史编号。

# 本地检查，不连接集群执行部署
helm dependency build ./mychart
helm lint ./mychart -f values-prod.yaml
helm template student-mgmt ./mychart -n apps -f values-prod.yaml

# Helm 3：部署并等待常见工作负载就绪；失败时尝试清理或回滚
helm upgrade --install student-mgmt ./mychart \
  -n apps --create-namespace -f values-prod.yaml \
  --wait --atomic --timeout 5m

# 查看声明、实际使用的配置及历史
helm get manifest student-mgmt -n apps
helm get values student-mgmt -n apps --all
helm history student-mgmt -n apps

helm template 只渲染清单，不创建 Release 历史，也不能单独证明集群会接受资源。--wait 检查部分 Kubernetes 就绪条件，不证明业务请求成功。

--atomic 不能撤销数据库迁移或外部系统变更。Helm 回滚恢复历史资源配置，不恢复数据库、持久卷数据或已发生的外部副作用。

Helm 默认不持续运行。命令结束后，人工修改资源不会自动触发 Helm 再次部署。Chart 中 crds/ 的自定义资源定义也有特殊生命周期：Helm 通常安装缺失定义，但不自动升级或删除它们，需要另行规划。

Pull 模式到底拉取什么

Pull 模式描述的是部署控制器主动获取期望状态。控制器通常运行在目标集群内；CI 不必直接调用目标集群 API。

开发者 → CI 测试、构建镜像 → 推送镜像到 Registry
开发者或自动化 → 更新配置 Git 中的镜像引用 → 审核并合并
Flux → 拉取配置 Git 和 Chart 来源 → 调用 Kubernetes API
节点容器运行时 → 拉取应用镜像 → 启动容器

这里有三个独立的获取过程：Flux 拉取部署配置，source-controller 获取 Chart，节点拉取应用镜像。Git 更新、Chart 更新和镜像更新不是同一件事。

仅推送新镜像不会自动部署。如果 Git 仍引用旧版本，Flux 继续维护旧版本。使用可变标签可能让不同 Pod 获取不同内容；生产环境宜固定明确版本或镜像摘要。

CI 可以只持有镜像仓库写权限和配置 Git 写权限。Flux 需要来源读取凭证及 Kubernetes 写权限，节点需要镜像读取权限。Pull 改变凭证位置，不自动限制权限；仍需配置角色访问控制（RBAC）和 Git 审核规则。首次安装 Flux 与创建同步入口仍需要有集群权限的操作者。

Flux 如何驱动 Helm

Flux 使用自定义资源定义（CRD）扩展 Kubernetes API。HelmRelease 是声明期望部署的自定义资源；它与 Helm 保存的 Release 记录是两个对象。

对象或组件 职责
GitRepository 声明部署配置所在的 Git 来源，source-controller 拉取并生成带版本的 artifact（制品）
Flux Kustomization 从 Git artifact 的指定目录构建并应用资源，包括 HelmRelease 和 Chart 来源对象
HelmRepository 声明传统 HTTP Helm 仓库；source-controller 获取仓库索引
HelmChart 声明要获取或打包的 Chart，source-controller 生成 Chart artifact
OCIRepository 从开放容器倡议（OCI）Registry 获取 artifact，也可承载 Chart
helm-controller 消费 HelmRelease 与 Chart artifact，通过 Helm SDK 执行安装、升级及配置的失败处理

Flux Kustomization 是 Kubernetes 对象；目录内的 kustomization.yaml 是 Kustomize 的组合配置。两者用途不同。

flowchart TD
    G[配置 Git] --> S[source-controller]
    S --> A[Git artifact]
    A --> K[kustomize-controller]
    K --> R[HelmRelease]
    K --> P[HelmRepository]
    P --> S
    R --> C[生成 HelmChart 对象]
    C --> S
    H[Chart 仓库] --> S
    S --> T[Chart artifact]
    T --> HC[helm-controller 使用 Helm SDK]
    R --> HC
    HC --> API[Kubernetes API 与 Release 历史]
    API --> W[Kubernetes 控制器与 Pod]

上图使用传统 HelmRepository 路径。现代 Flux 还支持通过 HelmRelease.spec.chartRef 直接引用 OCIRepository 或 HelmChart，具体能力取决于已安装的 CRD 和控制器版本。

一次 Values 变更的过程：

  1. 开发者在 Git 的 HelmRelease 中把 replicaCount 从 2 改为 3，审核后合并。
  2. source-controller 定期检查 Git，或收到通知后提前拉取，生成新的 Git artifact。
  3. kustomize-controller 应用新 HelmRelease。Chart 来源与版本没有变化时，可以复用已有 Chart artifact。
  4. helm-controller 读取新 Values，用 Helm SDK 渲染并升级对应 Release。它不需要执行本机的 helm CLI。
  5. Kubernetes 更新 Deployment，创建第三个 Pod。helm-controller 按配置检查结果并写入状态条件。
  6. 后续调谐处理新的配置变化、可用的 Chart 更新，以及启用后的资源漂移检测。

Source 和 HelmRelease 各有自己的 interval。来源新 artifact 和对象变更可以提前触发调谐，所以间隔不是固定部署延迟，也不保证在该时间内完成部署。Webhook 只负责加速触发，控制器仍主动拉取内容。

Flux 与 Helm 的最小配置示例

以下示例仅用于说明关系，未在集群运行。假设 Flux 的 source、kustomize、helm 控制器及相应 CRD 已安装，并有权限创建示例资源。Git URL 是占位地址，必须替换。

配置仓库结构：

platform-config/
└── apps/
    └── podinfo/
        ├── kustomization.yaml
        ├── repository.yaml
        └── release.yaml

由已有 bootstrap 入口管理下面的 GitRepository 与 Flux Kustomization，或者先由有权限的操作者创建它们。只把文件提交到尚未被 Flux 同步的目录，不会启动同步。

# GitRepository：配置来源
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: platform-config
  namespace: flux-system
spec:
  interval: 1m
  url: https://github.com/example/platform-config
  ref:
    branch: main
# Flux Kustomization：从配置来源应用指定目录
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: podinfo
  namespace: flux-system
spec:
  interval: 5m
  path: ./apps/podinfo
  prune: true
  wait: true
  timeout: 5m
  sourceRef:
    kind: GitRepository
    name: platform-config
# apps/podinfo/kustomization.yaml：普通 Kustomize 文件
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - repository.yaml
  - release.yaml
# apps/podinfo/repository.yaml：Chart 来源
apiVersion: source.toolkit.fluxcd.io/v1
kind: HelmRepository
metadata:
  name: podinfo
  namespace: flux-system
spec:
  interval: 5m
  url: https://stefanprodan.github.io/podinfo
# apps/podinfo/release.yaml：安装目标与配置
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: podinfo
  namespace: flux-system
spec:
  interval: 5m
  timeout: 5m
  releaseName: podinfo
  targetNamespace: apps
  chart:
    spec:
      chart: podinfo
      version: '6.9.2'
      sourceRef:
        kind: HelmRepository
        name: podinfo
        namespace: flux-system
      interval: 5m
  install:
    createNamespace: true
    remediation:
      retries: 3
  upgrade:
    remediation:
      retries: 3
      strategy: rollback
  driftDetection:
    mode: enabled
  values:
    replicaCount: 2

version 固定示例 Chart 版本，使用前应确认仓库仍提供它及其兼容性。targetNamespace 是工作负载目标命名空间。此例未设置 storageNamespace，Helm Release 历史默认保存在 HelmRelease 所在的 flux-system，不是 apps。

将 values.replicaCount 改为 3 并提交 Git，Flux 会升级 Release。也可通过 valuesFrom 引用 HelmRelease 同命名空间内的 ConfigMap 或 Secret；这些来源依次合并，内联 values 通常最后覆盖，targetPath 有特殊覆盖行为。需要即时响应引用对象变更时，按 Flux 文档配置 watch 标签。

示例显式启用 driftDetection.mode: enabled，用于检查并纠正实际资源相对 Helm 保存清单的漂移。持续调谐 HelmRelease 本身，不等于默认持续修复所有 Helm 工作负载的人工修改。若水平自动扩缩容器（HPA）管理副本数，应避免同时由 Chart 强制管理该字段，或配置漂移忽略规则。

版本更新、失败与回滚

变更或故障 Flux 与 Helm 的行为
修改 HelmRelease Values helm-controller 使用新配置执行升级
修改固定 Chart 版本 source-controller 获取对应 Chart，helm-controller 执行升级
使用 Chart 版本范围，如 6.x 新匹配版本可能触发升级，即使配置 Git 没有新提交
Chart 存在 Git 内且只改模板 使用 GitRepository 来源时，检查 reconcileStrategy: Revision；默认 ChartVersion 策略通常需要增加 Chart 版本
人工改 Deployment 启用 HelmRelease 漂移检测后，controller 可恢复受管字段
仓库临时不可访问 新版本同步失败；已有 Pod 通常继续运行，不能据此确认新的期望状态已部署
安装或升级失败 状态条件和事件记录错误；重试、卸载或回滚取决于 remediation 配置，不是所有错误都会无限重试
Git 删除 HelmRelease 上层 Kustomization 启用 prune 后可删除对象，helm-controller 通常通过 finalizer 卸载 Release；保留规则和特殊资源生命周期仍需检查

长期回滚应把 Git 中的 Chart 版本或 Values 恢复到已知可用配置。Helm 的失败自动回滚是即时恢复措施，不能替代修正仍然失败的 Git 期望状态。

不要长期同时用人工 Helm 命令和 Flux 管理同一个 Release。人工回滚后，Flux 后续升级可能再次应用 Git 声明的版本。紧急操作可以先暂停 HelmRelease，再修正 Git 并恢复调谐。

flux suspend helmrelease podinfo -n flux-system
# 处理故障并将期望配置修正到 Git 后恢复
flux resume helmrelease podinfo -n flux-system
flux reconcile helmrelease podinfo -n flux-system --with-source

暂停 HelmRelease 不会暂停上层 Kustomization。若 Git 明确声明 spec.suspend: false，上层可能重新应用它；持久暂停也应纳入 Git 管理。

Argo CD 等组件如何使用 Helm

使用方式 谁获取配置 Helm 的角色 谁管理应用生命周期与漂移
本机或 CI 执行 Helm 操作者或 CI 渲染、安装、升级，保存 Helm Release 历史 Helm 只在命令运行时操作；不持续检查漂移
Flux HelmRelease source-controller 获取 Git 与 Chart artifact helm-controller 通过 Helm SDK 管理真实 Release Flux 持续调谐；Helm 资源漂移修复需相应配置
Argo CD Application 使用 Helm Chart Argo CD 获取 Git 或 Chart 来源 通常运行 helm template 生成清单 Argo CD 应用与跟踪资源；自动纠偏需启用 selfHeal
Flux 应用预先渲染的 YAML Flux 获取 Git 中的静态清单 Helm 只在生成文件时使用 kustomize-controller 管理资源，不创建 Helm Release 历史

Argo CD 通常不执行 helm install 或 helm upgrade，所以 helm list 不会显示这类 Application 的 Helm Release。它的同步历史、健康状态和回滚由 Argo CD 管理。

Argo CD 可自动拉取并比较来源，但应用新状态需要手动同步或启用 automated sync。恢复人工修改需要 selfHeal: true，删除已移除的受管资源需要 prune: true。Pull 并不等于默认开启所有自动化行为。

Argo Workflows 与 Argo CD 是不同组件。Argo Workflows 执行提交的任务 DAG（有向无环图），可在步骤中调用 Helm；它本身不是持续拉取并调谐 Git 的部署控制器。

如何确认部署成功

沿依赖方向检查，避免把“已拉取”误判为“业务成功”：

  1. 确认 GitRepository 的 revision 是目标 commit，Chart 来源可用。
  2. 确认 Kustomization 已应用对应 revision。
  3. 确认 HelmRelease 状态对应最新对象 generation，实际 Chart 版本与 Values 符合预期。
  4. 确认 Deployment 的更新完成，Pod 镜像与就绪探针符合预期。
  5. 执行一条真实业务请求，检查结果及必要的下游状态。
flux get sources git -A
flux get sources helm -A
flux get sources chart -A
flux get kustomizations -A
flux get helmreleases -A
kubectl describe helmrelease podinfo -n flux-system
flux logs --level=error -A

# 本例的 Release 存储命名空间为 flux-system
helm status podinfo -n flux-system
helm get values podinfo -n flux-system --all
helm history podinfo -n flux-system
kubectl rollout status deployment/podinfo -n apps --timeout=5m
kubectl get pods -n apps

Ready 是控制器定义的检查结果。它不能替代业务验收，也不能保证数据库迁移、外部权限或依赖服务均正确。
