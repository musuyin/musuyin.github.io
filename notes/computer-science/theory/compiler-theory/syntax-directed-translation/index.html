语法制导的语义计算

2026-05-01

#编译原理

阅读线索

语法制导翻译在文法结构上附加属性与动作。先区分综合属性和继承属性，再用依赖关系确定求值顺序，并理解语义栈如何配合归约。

语法制导翻译概述

语法分析阶段产出的只是“句子是否合法”，而编译器还需要理解句子的含义并生成中间代码。语法制导翻译（Syntax-Directed Translation，SDT）将语义规则嵌入到文法的产生式中，在语法分析的同时完成语义计算。

基本思想

在每条产生式 A→αA \rightarrow \alphaA→α 上附加语义规则（Semantic Rule）或语义动作（Semantic Action）：

  • 语义规则：计算属性值的等式（用于属性文法）
  • 语义动作：嵌入产生式中间的可执行代码片段（用于翻译方案）

类比：文法规则是“语法骨架”，语义规则是“给骨架填肉”——语法告诉我们结构，语义告诉我们含义。

编译器的工作流程

源程序
  ↓ 词法分析
单词符号序列
  ↓ 语法分析（+ 语义分析）
语法树 / 中间代码
  ↓ 代码优化
优化后中间代码
  ↓ 目标代码生成
目标程序

语法制导翻译处于语法分析 + 语义分析 + 中间代码生成阶段。

属性文法

什么是属性文法

属性文法（Attribute Grammar）是在上下文无关文法的基础上，为每个文法符号附加属性（Attribute），并为每个产生式附加语义规则来计算这些属性值。

形式定义：属性文法 A=(G,V,F)A = (G, V, F)A=(G,V,F)，其中：

  • GGG：上下文无关文法
  • VVV：属性集合，每个文法符号关联若干属性
  • FFF：语义规则集合，每条规则形如“属性 = 表达式”

综合属性与继承属性

属性分为两类，核心区别是信息在分析树上的流动方向。

综合属性（Synthesized Attribute）

定义：由该节点的子节点属性计算得到，信息自底向上流动。

规律：对于产生式 A→X1X2⋯XnA \rightarrow X_1 X_2 \cdots X_nA→X1​X2​⋯Xn​，AAA 的综合属性由右部 X1,…,XnX_1, \ldots, X_nX1​,…,Xn​ 的属性计算得到。

类比：像层层汇报——每个子节点先算好自己的值，然后“上报”给父节点，父节点汇总后得到自己的值。

特点：

  • 终结符只有综合属性（由词法分析器给出，如 digit.lexval）
  • 适合自底向上（LR）分析，归约时计算

示例：计算表达式的值

文法：

E→E1+TE→TT→T1∗FT→FF→(E)F→digit \begin{aligned} E &\rightarrow E_1 + T \\ E &\rightarrow T \\ T &\rightarrow T_1 * F \\ T &\rightarrow F \\ F &\rightarrow (E) \\ F &\rightarrow \mathbf{digit} \end{aligned} EETTFF​→E1​+T→T→T1​∗F→F→(E)→digit​

每个节点有属性 .val 表示表达式的值，语义规则：

产生式 语义规则 说明
E→E1+TE \rightarrow E_1 + TE→E1​+T E.val=E1.val+T.valE.\text{val} = E_1.\text{val} + T.\text{val}E.val=E1​.val+T.val 父节点由两个子节点计算
E→TE \rightarrow TE→T E.val=T.valE.\text{val} = T.\text{val}E.val=T.val 直接传递
T→T1∗FT \rightarrow T_1 * FT→T1​∗F T.val=T1.val×F.valT.\text{val} = T_1.\text{val} \times F.\text{val}T.val=T1​.val×F.val 父节点由两个子节点计算

所有的 .val 都是综合属性——每个节点的值由它的子节点计算，信息从叶节点向根节点流动。

分析树上的计算过程（输入 3 + 4 * 5）：

            E.val=23          ← 第5步：3 + 20 = 23
           /        \
       E.val=3    T.val=20    ← 第4步：4 * 5 = 20
          |        /    \
       T.val=3  T.val=4  F.val=5
          |        |        |
       F.val=3  F.val=4  digit(5) ← 第1步：叶节点取词法值
          |        |
       digit(3) digit(4)

计算顺序：叶节点 → 中间节点 → 根节点，严格自底向上。

继承属性（Inherited Attribute）

定义：由该节点的父节点或左兄弟节点的属性计算得到，信息自顶向下（或从左到右）流动。

规律：对于产生式 A→X1X2⋯XnA \rightarrow X_1 X_2 \cdots X_nA→X1​X2​⋯Xn​，XjX_jXj​ 的继承属性由 AAA 的属性，或 X1,…,Xj−1X_1, \ldots, X_{j-1}X1​,…,Xj−1​ 的属性计算得到。

类比：像上级下发任务——父节点先确定好某个“上下文信息”（比如类型），然后把这个信息“下发”给子节点，子节点拿着这个信息去做自己的事。

特点：

  • 开始符号没有继承属性
  • 适合自顶向下（LL）分析，展开时传递
  • 兄弟节点不能直接互相读取属性，必须通过父节点中转

示例：变量声明的类型传播

文法：处理声明语句 int a, b

D→T LT→int ∣ realL→L1, id ∣ id \begin{aligned} D &\rightarrow T\ L \\ T &\rightarrow \mathbf{int}\ |\ \mathbf{real} \\ L &\rightarrow L_1,\ \mathbf{id}\ |\ \mathbf{id} \end{aligned} DTL​→T L→int ∣ real→L1​, id ∣ id​

问题：LLL 负责处理变量名列表（a, b），但类型信息（int）在兄弟节点 TTT 里，LLL 自己不知道变量是什么类型。

解决：用继承属性 L.in 把类型从 TTT 经由父节点 DDD 传给 LLL。

分析树结构：

        D
       / \
      T   L
   (int)   └── ...

TTT 和 LLL 是兄弟，LLL 无法直接读取 T.typeT.\text{type}T.type。只有父节点 DDD 同时看得到两者，所以由 DDD 的语义规则完成“中转”：

语义规则：

计算过程（以 int a, b 为例）：

步骤1：T 识别出 int → T.type = integer        （综合，自底向上）
步骤2：D 读取 T.type，赋给 L.in              （继承，父→子）
        L.in = integer
步骤3：L 展开为 L₁, id(a)，把 L.in 传给 L₁  （继承，父→子）
        L₁.in = integer
步骤4：L  用 L.in 注册 id(a)                 （使用继承属性）
        addtype(a, integer)
步骤5：L₁ 用 L₁.in 注册 id(b)               （使用继承属性）
        addtype(b, integer)

L.in 就像一张“任务单”——父节点填好类型，子节点拿着任务单去注册符号表。

综合属性 vs 继承属性对比

综合属性 继承属性
来源 子节点 父节点或左兄弟节点
信息流向 自底向上 ↑ 自顶向下 ↓（或从左到右 →）
计算时机 归约时（LR 分析） 展开时（LL 分析）
典型用途 计算表达式的值、类型推导 传递上下文信息、类型分发
终结符 只有综合属性 不能有继承属性
开始符号 可以有综合属性 没有继承属性

一个节点可以同时有两种属性：比如 LLL 节点，L.in 是继承属性（从父节点获得类型），同时也可以有综合属性（如 L.count 统计变量个数，由子节点计算得到）。

属性文法的求值

依赖图

依赖图（Dependency Graph）表示属性之间的计算依赖关系：

  • 节点：分析树中每个属性实例
  • 边：a→ba \rightarrow ba→b 表示计算 bbb 需要先有 aaa

对依赖图进行拓扑排序，即得到属性的合法计算顺序。

循环依赖：若依赖图有环，则属性文法无法求值——说明语义规则设计有问题。

注释分析树

在分析树的每个节点旁标注属性值，称为注释分析树（Annotated Parse Tree）。

S-属性文法与 L-属性文法

实际实现中，不同的属性类型对应不同的分析策略。

S-属性文法

定义：只包含综合属性的属性文法。

求值方式：自底向上，可以在 LR 分析的归约阶段直接计算，十分高效。

实现：将属性值保存在分析栈中，归约时计算新属性。

S-属性文法是最简单的情况，适合用 Yacc/Bison 等工具实现。

L-属性文法

定义：属性的计算满足如下限制——对于产生式 A→X1X2⋯XnA \rightarrow X_1 X_2 \cdots X_nA→X1​X2​⋯Xn​，XjX_jXj​ 的继承属性只依赖于：

  1. AAA 的继承属性
  2. X1,X2,⋯ ,Xj−1X_1, X_2, \cdots, X_{j-1}X1​,X2​,⋯,Xj−1​ 的综合属性或继承属性（只看左边的兄弟）

含义：信息流从左到右，从上到下——与 LL 分析（自顶向下，从左到右）的方向一致。

关系：S-属性文法⊂L-属性文法\text{S-属性文法} \subset \text{L-属性文法}S-属性文法⊂L-属性文法

属性文法类型 含属性类型 适合的分析方法
S-属性文法 只有综合属性 自底向上（LR）
L-属性文法 综合 + 有限制的继承 自顶向下（LL）或深度优先遍历

遍历分析树进行语义计算

属性文法定义了“属性如何计算”，但没有规定计算顺序。实际执行时，需要按照依赖关系遍历分析树，保证每个属性在被使用前已经算好。

依赖图与计算顺序

依赖图（Dependency Graph）描述属性之间的先后依赖关系：

  • 每个节点的每个属性实例是依赖图的一个顶点
  • 若计算属性 bbb 需要用到属性 aaa，则连一条有向边 a→ba \rightarrow ba→b

对依赖图进行拓扑排序，得到的顺序就是合法的属性计算顺序。

循环依赖：若依赖图中存在环（aaa 依赖 bbb，bbb 又依赖 aaa），则属性文法无法求值，说明语义规则设计有误。

三种遍历策略

策略一：自底向上遍历（仅综合属性）

适用于 S-属性文法（只有综合属性）。

方法：对分析树做后序遍历（Post-order）——先访问所有子节点，再处理当前节点。

后序遍历顺序：左子树 → 右子树 → 根节点

原因：综合属性由子节点计算，后序遍历保证子节点先于父节点处理，依赖关系天然满足。

示例：计算 3 + 4 * 5 的值

后序遍历顺序：digit(3) → F → T → digit(4) → F → T → digit(5) → F → T → E → E

每次到达一个节点，其子节点的 .val 已全部算好，直接代入语义规则即可。

策略二：深度优先遍历（综合 + 继承属性）

适用于 L-属性文法（含有限制的继承属性）。

方法：对分析树做深度优先、从左到右的遍历，在访问每个节点时：

  1. 进入节点前：计算该节点的继承属性（此时父节点和左兄弟已处理，信息已就绪）
  2. 递归访问子节点（从左到右）
  3. 离开节点后：计算该节点的综合属性（此时所有子节点已处理完毕）
访问节点 X：
  1. 计算 X 的继承属性（依赖父/左兄弟，已就绪）
  2. 从左到右递归访问 X 的每个子节点
  3. 计算 X 的综合属性（依赖子节点，已就绪）

为什么 L-属性文法适合这种遍历：L-属性文法规定继承属性只依赖父节点和左边的兄弟，深度优先从左到右遍历时，访问 XjX_jXj​ 前，X1,…,Xj−1X_1, \ldots, X_{j-1}X1​,…,Xj−1​ 已处理完毕，继承属性的来源恰好都已就绪。

示例：处理声明 int a, b

访问 D：
  访问 T(int)：
    T 无继承属性
    T.type = integer（综合属性，叶节点直接得到）
  访问 L：
    计算 L.in = T.type = integer（继承属性，T 已处理完毕）
    访问 L₁：
      计算 L₁.in = L.in = integer（继承属性，L 已处理）
      访问 id(b)：addtype(b, integer)
    访问 id(a)：addtype(a, integer)

策略三：多遍扫描

若属性文法既不是 S-属性文法也不是 L-属性文法（继承属性依赖右兄弟或其他复杂情况），单次遍历无法保证依赖关系，需要多遍扫描分析树：

  • 第一遍：计算能算的属性
  • 第二遍：利用第一遍的结果计算更多属性
  • ……直到所有属性计算完毕

代价高，实际编译器尽量避免，通常通过重新设计语义规则将属性文法转化为 L-属性文法。

三种策略对比

策略 适用文法 遍历方式 代价
自底向上（后序） S-属性文法 一遍，后序遍历 最低
深度优先（前序+后序） L-属性文法 一遍，深度优先从左到右 较低
多遍扫描 一般属性文法 多遍 高

文法和语义规则同前，分析树：

            D

语法制导翻译方案

语法制导翻译方案（Syntax-Directed Translation Scheme，SDT Scheme）是在产生式右部嵌入语义动作的扩展文法。

语义动作是夹在文法里的代码钩子，语法分析走到哪、代码就在哪执行，用来完成类型检查、符号表操作、代码生成等语义工作

语义动作的位置

语义动作是用 { ... } 括起来的代码，可以放在产生式右部的任意位置：

E→E1+T { print("+") } E \rightarrow E_1 + T\ \{\ \text{print}("+")\ \} E→E1​+T { print("+") }
E→T E \rightarrow T E→T
T→T1∗F { print("∗") } T \rightarrow T_1 * F\ \{\ \text{print}("*")\ \} T→T1​∗F { print("∗") }
T→F T \rightarrow F T→F
F→(E) F \rightarrow (E) F→(E)
F→digit { print(digit.lexval) } F \rightarrow \mathbf{digit}\ \{\ \text{print}(\mathbf{digit}.\text{lexval})\ \} F→digit { print(digit.lexval) }

上面的翻译方案对输入 3 * 4 + 5 后序输出：3 4 * 5 +（逆波兰表达式）

语义动作的执行时机

  • 语义动作在它左边的所有文法符号都匹配/归约后立即执行
  • 在 LL 分析中：从左到右执行
  • 在 LR 分析中：归约时执行产生式末尾的语义动作

后缀翻译方案

后缀翻译方案：所有语义动作都在产生式右部末尾，适合 LR 分析直接实现。

E→E1+T { E.val=E1.val+T.val } E \rightarrow E_1 + T\ \{\ E.\text{val} = E_1.\text{val} + T.\text{val}\ \} E→E1​+T { E.val=E1​.val+T.val }

若语义动作不在末尾，需要引入标记非终结符（Marker Nonterminal）来模拟中间动作。

中间代码

中间代码（Intermediate Code）是编译器在前端（分析）和后端（代码生成）之间的“通用语言”，与具体机器无关。

为什么需要中间代码

  • 可移植性：前端 → 中间代码，中间代码 → 多种目标平台
  • 优化方便：在中间代码层面做优化，比直接优化目标代码更简单
  • 模块化：前后端解耦，mmm 种语言 × nnn 种平台只需 m+nm+nm+n 个模块

三地址码

三地址码（Three-Address Code）是最常见的中间代码形式，每条指令最多三个操作数：

x=y op z x = y\ \text{op}\ z x=y op z

其中 xxx、yyy、zzz 是变量名、常量或编译器生成的临时变量（如 t1,t2,…t_1, t_2, \ldotst1​,t2​,…）。

三地址码的常见形式

形式 含义
x=y op zx = y\ \text{op}\ zx=y op z 二元运算
x=op yx = \text{op}\ yx=op y 一元运算（取反、类型转换等）
x=yx = yx=y 赋值
goto LLL 无条件跳转到标号 LLL
if x relop yx\ \text{relop}\ yx relop y goto LLL 条件跳转
param xxx 函数调用参数
call p, np,\ np, n 调用过程 ppp，nnn 个参数
return xxx 函数返回
x=y[i]x = y[i]x=y[i] 数组读取
x[i]=yx[i] = yx[i]=y 数组写入
x=&yx = &amp;yx=&y，x=∗yx = *yx=∗y，∗x=y*x = y∗x=y 地址/指针操作

示例：翻译 a = b * -c + b * -c

t1 = minus c      // -c
t2 = b * t1       // b * (-c)
t3 = minus c      // -c（未优化时重复计算）
t4 = b * t3       // b * (-c)
t5 = t2 + t4      // b*(-c) + b*(-c)
a  = t5

四元式

四元式（Quadruple）是三地址码的一种表示方式：

(op, arg1, arg2, result) (\text{op},\ \text{arg1},\ \text{arg2},\ \text{result}) (op, arg1, arg2, result)
编号 op arg1 arg2 result
(0) minus c — t1
(1) * b t1 t2
(2) minus c — t3
(3) * b t3 t4
(4) + t2 t4 t5
(5) = t5 — a

三元式

三元式（Triple）省略了 result 字段，用指令编号直接引用：

(op, arg1, arg2) (\text{op},\ \text{arg1},\ \text{arg2}) (op, arg1, arg2)

三元式更紧凑，但不方便移动指令（因为引用用了编号），优化困难。

间接三元式：用一个额外的指令序列列表来支持指令重排。

逆波兰表达式

逆波兰表达式（Reverse Polish Notation，RPN）也叫后缀表达式，将运算符写在操作数后面：

  • 中缀：a+b×ca + b \times ca+b×c
  • 后缀：a b c × +a\ b\ c\ \times\ +a b c × +

优点：不需要括号，求值只需一个栈，适合简单表达式的翻译。

控制流语句的翻译

控制流（如 if-else、while）需要生成跳转指令，核心是确定跳转的目标地址。

布尔表达式的翻译

布尔表达式有两种翻译方式：

  1. 数值表示：true 用 1，false 用 0，和算术表达式类似
  2. 跳转方式（更常用）：布尔值体现在跳转目标上，不生成临时变量

跳转方式的关键属性：

  • E.true：EEE 为真时跳转的目标标号
  • E.false：EEE 为假时跳转的目标标号

这两个属性是继承属性，由父节点（if、while 语句）传入。

回填技术

问题背景

在单遍扫描的翻译中，生成跳转指令时目标地址还未确定（还没扫描到标号的定义处）。

例如：生成 if a < b goto ? 时，还不知道“真”分支的入口地址。

回填（Backpatching）的思路

  1. 生成跳转指令时，暂时留空目标地址（填 0 或 -）
  2. 用链表记录所有待填写的跳转指令
  3. 当目标地址确定后，回头填写所有相关指令

关键属性与函数

  • B.truelist：BBB 为真时需要跳转、但目标尚未确定的指令编号列表
  • B.falselist：BBB 为假时需要跳转、但目标尚未确定的指令编号列表
  • S.nextlist：语句 SSS 之后需要跳转到下一条指令、但目标尚未确定的指令编号列表

辅助函数：

  • makelist(i)：创建只含指令 iii 的列表
  • merge(p1, p2)：合并两个链表
  • backpatch(p, i)：将列表 ppp 中所有指令的跳转目标填写为 iii

布尔表达式的回填翻译方案

产生式 语义动作
B→B1 or M B2B \rightarrow B_1\ \mathbf{or}\ M\ B_2B→B1​ or M B2​ backpatch(B₁.falselist, M.quad)；B.truelist = merge(B₁.truelist, B₂.truelist)；B.falselist = B₂.falselist

B→E1 relop E2B \rightarrow E_1\ \text{relop}\ E_2B→E1​ relop E2​ emit('if E₁ relop E₂ goto _')；emit('goto _')；B.truelist = makelist(nextquad)；B.falselist = makelist(nextquad+1)

总结

概念 核心要点
综合属性 自底向上，由子节点计算，适合 LR 分析
继承属性 自顶向下，由父/左兄弟计算，适合 LL 分析
S-属性文法 只含综合属性，最简单
L-属性文法 含有限继承属性，信息从左到右流动
三地址码 中间代码主流形式，最多三个操作数
四元式 三地址码的表格表示，便于优化
回填技术 解决单遍扫描中跳转目标未知的问题

步骤 18（r1r_1r1​：S→(L)S \rightarrow (L)S→(L)）： 弹出 3 个符号（)))、LLL=1、(((），计算 S.num=1+1=2S.\text{num}=1+1=2S.num=1+1=2，查 GOTO(0,S)=1，压入状态 1 和 SSS（语义值 2）。
