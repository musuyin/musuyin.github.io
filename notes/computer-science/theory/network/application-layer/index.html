#计算机网络

阅读线索

应用层定义进程交换的消息与规则。HTTP、邮件与 DNS 服务于不同应用需求，选择 TCP 或 UDP 时则要对应可靠性、时延等要求。

应用层协议原理

网络应用体系结构

客户/服务器（C/S）

  • 服务器：7×24 小时在线，拥有固定 IP/域名，用大量服务器实现可扩展性
  • 客户机：间歇性接入，可能使用动态 IP，不与其他客户机直接通信

P2P（对等）

  • 没有永远在线的服务器，任意节点间可直接通信
  • 优点：高度可伸缩；缺点：难于管理，节点 IP 可能变化

混合结构

示例 Napster：文件传输用 P2P，文件搜索用 C/S（中央服务器索引）

应用进程通信

  • 套接字（Socket）：进程通过套接字发送/接收消息，相当于应用层与传输层之间的“门”
  • 进程寻址：IP 地址 + 端口号（如 HTTP 服务器：端口 80，邮件服务器：端口 25）

应用层协议

协议定义了消息的类型（请求/响应）、语法（字段格式）、语义（字段含义）和规则（何时发送/响应）。

分为公开协议（RFC 定义，如 HTTP、SMTP）和私有协议（如多数 P2P 应用）。

应用对传输层服务的需求

应用类型 数据丢失 带宽要求 时延要求
文件传输、Email 不可丢失 弹性 宽松
网络电话/视频 可容忍少量 有最低要求 严格（<几百 ms）
网络游戏 可容忍少量 弹性 严格

TCP vs UDP 提供的服务

特性 TCP UDP
连接 面向连接（需握手） 无连接
可靠性 可靠传输 不可靠
流量控制 有 无
拥塞控制 有 无
时延/带宽保障 不提供 不提供

Web 应用与 HTTP

概述

  • Web 页面由多个对象（HTML、图片、脚本等）组成，基础是一个 HTML 文件（含对其他对象的引用链接）
  • 对象通过 **URL（Uniform Resource Locator）**寻址：scheme://host:port/path
  • HTTP 使用 C/S 结构：浏览器（客户端）向 Web 服务器（端口 80）发请求，服务器响应
  • HTTP 是无状态协议：服务器不记录客户端的历史请求

HTTP 连接类型

非持久性连接（HTTP 1.0）

  • 每个 TCP 连接只传输一个对象
  • 响应时间 = 2 RTT + 文件传输时间（1 RTT 建立 TCP + 1 RTT 请求+响应）
  • 缺点：每个对象都需建立 TCP 连接，开销大

持久性连接（HTTP 1.1 默认）

  • 一个 TCP 连接可传输多个对象
方式 特点
无流水（串行） 收到响应后才发下一个请求，每个对象耗时约 1 RTT
带流水（并行） 遇到引用对象立即发出请求，理想情况约 1 RTT 获取所有对象

HTTP 消息格式

请求报文

GET /index.html HTTP/1.1\r\n        ← 请求行
Host: www.example.com\r\n           ← 首部行
Connection: keep-alive\r\n
...
\r\n                                ← 空行（分隔首部和主体）

常见方法：

方法 说明
GET 请求获取对象
POST 提交数据（如表单），数据在消息体中
HEAD 只获取首部，不获取对象（测试用）
PUT 上传文件到指定 URL
DELETE 删除指定 URL 的文件

响应报文

HTTP/1.1 200 OK\r\n                  ← 状态行
Content-Length: 1234\r\n             ← 首部行
...
\r\n
<HTML>...</HTML>                     ← 对象内容

常见状态码：

状态码 含义
200 OK 请求成功
301 Moved Permanently 永久重定向
400 Bad Request 请求语法错误
404 Not Found 对象不存在
505 HTTP Version Not Supported 不支持的 HTTP 版本

Cookie 技术

HTTP 无状态，但可用 Cookie 跟踪用户身份。

四个组件：

  1. HTTP 响应消息中的 Set-Cookie 头部
  2. HTTP 请求消息中的 Cookie 头部
  3. 保存在客户端的 Cookie 文件（浏览器管理）
  4. 服务器端后台数据库

Web 缓存（代理服务器）

Web 缓存在不访问原始服务器的前提下满足客户端请求，减少响应时间和机构流量。

工作方式：

  1. 浏览器将请求发给缓存服务器
  2. 若对象在缓存中 → 直接返回
  3. 若不在缓存中 → 缓存服务器向原始服务器请求，缓存并返回给客户端

条件 GET（If-Modified-Since）：缓存先向服务器确认对象是否更新，未更新则服务器返回 304 Not Modified，避免重复传输。

FTP 文件传输

FTP（File Transfer Protocol）使用两条 TCP 连接：

  • 控制连接（端口 21）：传输命令（持久，带外信令）
  • 数据连接（动态建立）：传输文件（传完即关闭）

服务器维护“状态”（当前目录、认证信息等），是有状态协议（与 HTTP 不同）。

电子邮件（Email）

三个核心组件

  1. 用户代理（User Agent）：邮件客户端，读写发收邮件
  2. 邮件服务器（Mail Server）：存储用户邮箱，管理发送队列
  3. SMTP（Simple Mail Transfer Protocol）：在邮件服务器之间传送邮件

SMTP

  • 使用 TCP，服务器端口 25
  • 是推协议：发送方主动将邮件推送给接收方邮件服务器
  • 要求 7 位 ASCII 编码（非 ASCII 内容需用 MIME 扩展编码）
  • 三个阶段：握手 → 传送消息 → 关闭连接
  • 邮件结束标记：CRLF.CRLF（只含一个句点的单独一行）

HTTP vs SMTP

特性 HTTP SMTP
方向 拉协议（客户从服务器拉取） 推协议（服务器主动推送）
字符限制 无 7 位 ASCII（需 MIME 扩展）
多媒体 每个对象单独封装 所有对象放在同一报文

邮件访问协议

SMTP 用于发送和服务器间传递，收件用以下协议从邮件服务器取回邮件：

协议 端口 特点
POP3 110 简单，将邮件下载到本地，服务器可选保留或删除，无状态
IMAP 143 功能强，在服务器上管理邮件，有状态，支持文件夹
HTTP 80 基于 Web 的邮件（如 Gmail），收发都用 HTTP

DNS（域名解析系统）

作用

将域名（如 www.example.com）解析为 IP 地址（如 1.2.3.4）。

DNS 是一个多层命名服务器构成的分布式数据库 + 应用层协议，不使用集中式是为了避免单点失效、流量瓶颈和维护问题。

DNS 提供的服务

  • 域名 → IP 地址翻译
  • 主机别名（CNAME）
  • 邮件服务器别名（MX）
  • 负载均衡（一个域名对应多个 IP）

DNS 层级结构

根域名服务器
    └── 顶级域名服务器（TLD）：.com, .org, .cn, ...
            └── 权威域名服务器：各组织自己维护
  • 本地域名服务器：每个 ISP 有一个，作为默认服务器，将查询代理给层级系统

查询方式

  • 迭代查询：被查询服务器返回下一级服务器地址，由本地服务器逐步查询
  • 递归查询：将解析任务交给所联系的服务器，由它负责最终解析

本地服务器缓存 DNS 查询结果，超时删除（TTL 控制），减少根服务器访问频率。

DNS 资源记录（RR）

格式：(name, value, type, ttl)

type name value
A 主机域名 IP 地址
NS 域 权威域名服务器的主机域名
CNAME 别名 真实域名
MX 邮件服务器别名 邮件服务器主机名

DNS 报文格式

查询和回复报文格式相同，头部包含：

  • Identification：16 位查询标号，回复使用相同标号匹配
  • Flags：标志位（查询/回复、期望递归、递归可用、权威回答）

P2P 文件分发

C/S 与 P2P 分发时间对比

设文件大小 FFF，服务器上行带宽 usu_sus​，有 NNN 个客户端，各下行带宽 did_idi​：

  • C/S：TC/S≥max⁡{NF/us,F/min⁡idi}T_{C/S} \geq \max{NF/u_s, F/\min_i d_i}TC/S​≥max{NF/us​,F/mini​di​}（随 N 线性增长）
  • P2P：TP2P≥max⁡{F/us,F/min⁡idi,NF/(us+∑ui)}T_{P2P} \geq \max{F/u_s, F/\min_i d_i, NF/(u_s + \sum u_i)}TP2P​≥max{F/us​,F/mini​di​,NF/(us​+∑ui​)}（增长更缓慢）

BitTorrent

  • tracker：跟踪参与 torrent 的节点
  • torrent：交换同一文件的节点组，文件划分为 256KB 的 chunk

关键策略：

  • 稀缺优先：优先下载最少节点拥有的 chunk，避免 chunk 垄断
  • tit-for-tat（以牙还牙）：优先向给自己发送速率最快的 4 个邻居上传（每 10s 重评），每 30s 随机解锁一个其他节点（乐观解锁）

P2P 索引

类型 特点
集中式索引 中央服务器维护节点内容清单，单点失效、性能瓶颈
泛洪式查询（Gnutella） 完全分布式，查询广播转发，带宽消耗大
层次式覆盖网络 超级节点管理子节点内容，综合两者优点

Socket 编程

Socket API 概述

Socket 是应用进程与传输层之间的接口，通过 IP + 端口号标识通信端点。

关键 API 函数

函数 用途
socket() 创建套接字
bind() 绑定本地 IP 和端口
listen() 服务器置于监听状态（仅 TCP）
accept() 接受连接请求，创建新套接字（仅服务器 TCP）
connect() 客户端发起连接（TCP）或指定服务器地址（UDP）
send()/recv() TCP 套接字收发数据
sendto()/recvfrom() UDP 套接字收发数据（含地址信息）
closesocket() 关闭套接字

TCP vs UDP Socket 调用流程

TCP Server:                    TCP Client:
socket() → bind() →           socket() →
listen() → accept()  ←───── connect()
↕ recv()/send()                ↕ send()/recv()
closesocket()                  closesocket()
UDP Server:                    UDP Client:
socket() → bind() →           socket() →
recvfrom() ←─────────────── sendto()
sendto() ──────────────────→ recvfrom()

面试追问：HTTP、SSE 与 WebSocket

SSE 和 WebSocket 有何区别

SSE（Server-Sent Events）是服务器通过一个保持不断开的 HTTP 响应，以 text/event-stream 格式单向推送事件；浏览器原生 EventSource 支持自动重连和 Last-Event-ID。它适合通知、日志流、AI 输出流。WebSocket 先经 HTTP Upgrade 握手，随后成为独立的全双工帧协议，客户端和服务端均可随时发消息，适合聊天室、协作编辑、实时游戏。

维度 SSE WebSocket
通信方向 服务端 → 客户端 双向全双工
协议与载荷 HTTP 流、文本事件 独立帧协议，可传文本/二进制
重连 浏览器内建 应用自行实现
代理兼容性 与普通 HTTP 接近 要求代理正确转发 Upgrade

WebSocket 是否和 HTTP 使用相同端口

通常是。ws:// 默认 80、wss:// 默认 443，分别对应 HTTP 和 HTTPS；端口不是协议专属资源，TCP 端口由传输层复用。服务端先依据监听端口和 HTTP 请求中的 Upgrade: websocket 区分协议，因此可在 443 上让 HTTPS 与 WSS 共用反向代理入口。也可显式使用任意未占用端口。

SSE 是否基于 HTTP/1.1；WebSocket 支持 HTTP/2/3 吗

SSE 是 HTTP 语义，不限定 1.1：在 HTTP/1.1 用 chunked 的长响应；在 HTTP/2/3 是一个持续的数据流。实践中要关闭代理缓冲并定期发心跳。

经典 WebSocket 的 Upgrade 只适用于 HTTP/1.1。HTTP/2 用 RFC 8441 的 extended CONNECT，HTTP/3 用 RFC 9220 的 extended CONNECT；是否可用取决于浏览器、CDN、代理和服务端是否都支持。不要把“HTTP/2 天然支持 WebSocket”当成事实。

从输入 URL 到页面渲染

  1. 浏览器解析 URL，查浏览器/系统缓存、hosts 和 DNS，获得 IP；HTTPS 还会校验证书链并协商 TLS。
  2. 客户端经路由、ARP/ND 找到下一跳，完成 TCP 三次握手；HTTP/3 则在 QUIC 上完成加密握手。
  3. 浏览器发送 HTTP 请求；CDN、WAF、负载均衡或 Nginx 常先接收，再反向代理到应用实例。应用访问缓存、数据库等，返回响应。
  4. 浏览器校验缓存和响应头，解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，合成 render tree，随后 layout、paint、composite；JS 可能阻塞解析或触发后续请求与重排。

HTTP 版本的演进

版本 关键能力 主要局限/改进
1.0 短连接 每个资源重复握手
1.1 持久连接、Host、chunked 管线化实践少，同一连接仍队头阻塞
2 二进制分帧、多路复用、HPACK、流优先级 共用一个 TCP 连接，丢包会阻塞所有流
3 HTTP 语义跑在 QUIC/UDP 上，独立流避免 TCP 层队头阻塞，TLS 1.3、连接迁移 UDP 可能受网络设备限制，CPU 开销更高

域名解析到的 IP 是否就是后台服务器

通常不是。域名可先解析到 CDN Anycast/边缘节点、四层/七层负载均衡或 WAF 的 VIP；再由其按健康检查、权重、路径、灰度规则转到内网应用实例。这样隐藏源站、抗攻击并实现弹性扩缩。

正向代理和反向代理

正向代理代表客户端访问外网，目标站知道代理而未必知道真实用户，常用于出网控制、匿名或跨网访问。反向代理代表服务端接收公网请求，客户端只面向代理，常做 TLS 终止、路由、负载均衡、缓存、限流和 WAF。Nginx 常作为反向代理；项目回答应如实说明实际使用的 proxy_pass、负载均衡、静态资源、HTTPS、WebSocket Upgrade、限流或缓存配置，不能泛称“都用过”。

网络字节顺序

TCP/IP 使用**大端（Big-Endian）**字节序作为网络标准，需要在本地字节序和网络字节序之间转换：

函数 转换方向
htons() 主机 → 网络（16 位）
ntohs() 网络 → 主机（16 位）
htonl() 主机 → 网络（32 位）
ntohl() 网络 → 主机（32 位）
