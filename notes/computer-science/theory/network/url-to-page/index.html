从浏览器输入 URL 到请求返回

2026-10-13

#计算机网络#Interview

阅读线索

一次网页访问跨越 URL 解析、DNS、邻居发现、传输和安全握手、HTTP 及浏览器处理。缓存、协议版本和已有连接会改变路径，应按条件说明哪些阶段实际发生。

问题边界

经典面试题：在浏览器地址栏输入一个 URL 并按下回车，到页面显示出来，发生了什么？

这个过程不是一条永远固定的流水线。浏览器可能直接命中缓存、复用已有连接、经过代理或 VPN，也可能使用 HTTP/1.1、HTTP/2 或 HTTP/3。回答时应先讲主链路，再补充分支：

解析 URL
    → 检查本地缓存与现有连接
    → DNS 解析域名
    → 根据路由表选择下一跳
    → ARP 或 NDP 获得下一跳链路层地址
    → 建立 TCP 与 TLS，或建立 QUIC 连接
    → 发送 HTTP 请求
    → 数据封装并经过交换机、路由器和 NAT 转发
    → CDN、负载均衡器或服务器处理请求
    → 返回 HTTP 响应
    → 浏览器解析资源并渲染页面
    → 复用或关闭连接

本文主要解释计算机网络链路。浏览器渲染只保留理解整个闭环所需的内容。

URL 解析与本地决策

假设输入：

https://www.example.com:443/products?id=42#detail

浏览器首先解析 URL：

  • Scheme：https，决定使用 HTTPS
  • Host：www.example.com，用于 DNS 查询、HTTP Host 或 :authority 以及 TLS SNI
  • Port：显式指定为 443；未指定时，HTTP 默认 80，HTTPS 默认 443
  • Path：/products
  • Query：id=42
  • Fragment：detail，只在浏览器本地使用，不会发送给服务器

地址栏同时也是搜索框。浏览器会先判断输入的是 URL、搜索关键词还是自定义协议。对于 HTTPS 站点，HSTS 缓存或 HSTS Preload List 还可能在发送网络请求前将 http 升级为 https。

可能提前结束的分支

真正访问网络前，浏览器可能检查：

  • Service Worker 是否拦截请求并返回本地响应
  • HTTP 缓存中是否存在仍然新鲜的响应
  • 是否已有可复用的 HTTP/1.1 Keep-Alive、HTTP/2 或 HTTP/3 连接
  • 是否配置了系统代理、浏览器代理、PAC、VPN 或安全软件

如果缓存可以直接使用，请求可能不需要 DNS 和建连。缓存需要重新验证时，浏览器仍会发出条件请求，例如携带 If-None-Match 或 If-Modified-Since；服务器可以返回 304 Not Modified。

DNS 域名解析

网络层负责根据 IP 地址转发，不能直接使用 www.example.com。浏览器需要先获得目标 IP 地址。

典型查询路径

浏览器 DNS 缓存
    → 操作系统 DNS 缓存与 hosts 文件
    → Stub Resolver
    → 递归 DNS 解析器
    → 根 DNS
    → 顶级域 DNS
    → 权威 DNS

实际实现会因浏览器、操作系统和 DoH 配置而不同，但核心角色不变：

  • Stub Resolver：终端上的轻量解析器，把查询交给递归解析器
  • Recursive Resolver：代表客户端完成后续查询并缓存结果，通常由运营商、企业或公共 DNS 提供
  • Root Server：告诉解析器 .com 等顶级域服务器在哪里
  • TLD Server：告诉解析器 example.com 的权威 DNS 在哪里
  • Authoritative Server：返回该域名的最终记录或下一段 CNAME

DNS 返回什么

常见记录包括：

  • A：IPv4 地址
  • AAAA：IPv6 地址
  • CNAME：将一个域名指向另一个域名，CDN 场景常见
  • HTTPS 或 SVCB：可以携带可用协议、替代端点等连接提示，但支持情况取决于客户端和部署

DNS 响应带有 TTL，各级缓存可以在 TTL 内复用结果。CDN 可能根据解析器位置、EDNS Client Subnet、健康状态和负载返回不同边缘节点地址；返回的 IP 也可能是 Anycast 地址。

DNS 解决“域名对应哪个地址”，不会告诉浏览器业务 URL 的 Path。协议和默认端口通常来自 URL；普通网页访问也不会依赖 SRV 记录发现端口。

DNS 使用的传输协议

  • 传统 DNS 通常先使用 UDP 53，开销小
  • 响应被截断、数据较大或执行特定操作时，可以使用 TCP 53
  • DoT 在 TLS 中传输 DNS，常用 TCP 853
  • DoH 把 DNS 放入 HTTPS，通常使用 443

当同时获得 IPv6 和 IPv4 地址时，浏览器常使用类似 Happy Eyeballs 的策略并发或错峰尝试，避免某个协议栈不可用导致长时间等待。

本地网络与下一跳

获得目标 IP 后，操作系统根据路由表进行最长前缀匹配，决定：

  • 使用哪个网络接口
  • 目标是否位于本地子网
  • 下一跳是目标主机还是默认网关

如果目标在公网，主机通常只需要知道默认网关的链路层地址，而不是远端服务器的 MAC 地址。

ARP 与 NDP

在以太网或 Wi-Fi 局域网中：

  • IPv4 使用 ARP，根据下一跳 IPv4 地址查询 MAC 地址
  • IPv6 使用 Neighbor Discovery Protocol，根据下一跳 IPv6 地址发现链路层地址

典型 IPv4 ARP 过程：

主机广播：谁拥有网关 IP 192.168.1.1？
网关单播：192.168.1.1 对应 MAC aa:bb:cc:dd:ee:ff
主机将结果写入 ARP 缓存

之后主机才能把 IP 包封装成发往网关 MAC 地址的链路层帧。

DHCP 通常在设备接入网络时就已经为主机提供 IP、子网掩码、默认网关和 DNS 服务器，不是每次输入 URL 都重新执行。

NAT

家庭、企业网络和移动网络经常使用 NAT。出口网关会把私网五元组映射为公网地址和端口：

192.168.1.10:52000 → 203.0.113.10:40001

返回报文到达公网端口后，NAT 设备根据状态表把它还原并转发给内部主机。运营商还可能再执行一层 CGNAT。

建立传输连接

浏览器根据已知协议、缓存的 Alt-Svc 信息、DNS 提示和服务端能力选择连接方式：

  • HTTP/1.1 和 HTTP/2 通常运行在 TCP 之上
  • HTTPS 还要在 TCP 之上完成 TLS
  • HTTP/3 运行在 QUIC 之上，QUIC 基于 UDP 并内置 TLS 1.3

如果已有满足证书和连接合并条件的连接，浏览器可以复用连接，不必每次重新握手。

TCP 三次握手

客户端选择一个临时源端口，与服务器 IP 和端口组成连接四元组：

源 IP、源端口、目标 IP、目标端口

三次握手过程：

客户端 → 服务端：SYN，seq=x
服务端 → 客户端：SYN + ACK，seq=y，ack=x+1
客户端 → 服务端：ACK，ack=y+1

握手完成以下事情：

  • 双方确认发送和接收路径可用
  • 同步双方初始序列号
  • 协商 MSS、窗口扩大、SACK、时间戳等 TCP 选项
  • 服务端为连接分配必要状态

两次握手无法让服务端确认客户端已经收到自己的初始序列号，也更难排除历史重复连接请求造成的错误状态，因此 TCP 使用三次握手。

TCP 可靠传输

连接建立后，TCP 通过以下机制提供可靠、有序的字节流：

  • Sequence Number：标记字节位置
  • ACK：确认已经收到的数据
  • Retransmission：超时或快速重传丢失数据
  • Sliding Window：接收方通过窗口进行流量控制
  • Congestion Control：发送方根据拥塞窗口控制进入网络的数据量
  • Checksum：发现传输中的比特错误

流量控制保护接收方，拥塞控制保护网络，两者不能混为一谈。

TLS 安全连接

HTTPS 会在 HTTP 数据传输前完成 TLS 握手。以 TLS 1.3 为主线：

ClientHello
  - 支持的 TLS 版本与密码套件
  - Key Share
  - SNI：目标域名
  - ALPN：在 TCP 上通常协商 http/1.1 或 h2

ServerHello
  - 选择的参数与 Key Share
  - Certificate
  - CertificateVerify
  - Finished

客户端验证证书并发送 Finished
双方开始使用会话密钥传输加密数据

证书验证

浏览器主要检查：

  • 证书链能否连接到本地信任的根 CA
  • 证书中的域名是否与访问域名匹配
  • 证书是否在有效期内
  • 证书用途、签名和算法是否符合安全策略
  • 根据浏览器策略检查吊销信息，例如 OCSP 或 CRL

证书证明公钥与域名身份的绑定。真正加密业务数据的是握手协商出的对称会话密钥，因为对称加密更适合大量数据传输。

SNI 与 ALPN

  • SNI 让同一个 IP 上的服务器知道客户端要访问哪个域名，从而选择正确证书和虚拟主机
  • ALPN 用于协商应用层协议，例如 TCP 上的 h2、http/1.1，或 QUIC 上的 h3

现代加密 ClientHello 机制可以保护部分握手元数据，但是否可用取决于客户端、DNS 和服务端部署，不能假设所有 HTTPS 都隐藏了 SNI。

TLS 会话恢复

客户端可以使用会话票据恢复 TLS 会话，减少握手成本。TLS 1.3 的 0-RTT 可以提前发送数据，但早期数据存在重放风险，只适合服务端明确允许的幂等操作。

HTTP/3 与 QUIC

HTTP/3 不执行 TCP 三次握手。QUIC 基于 UDP，在用户态同时完成传输参数协商与 TLS 1.3 握手。

QUIC 的主要特点：

  • 连接通常用 Connection ID 标识，网络地址变化时可以支持连接迁移
  • 每个 Stream 独立排序，一个 Stream 丢包不会像 HTTP/2 over TCP 那样阻塞其他 Stream 的交付
  • 加密是协议的一部分，不能运行明文 HTTP/3
  • 拥塞控制和可靠传输仍然存在，只是由 QUIC 而不是 TCP 实现

首次连接通常仍需要约一个 RTT 建立安全连接；恢复连接可能使用 0-RTT。UDP 被网络阻断时，浏览器通常会回退到 HTTP/2 或 HTTP/1.1，但具体回退策略由客户端实现决定。

发送 HTTP 请求

连接可用后，浏览器构造 HTTP 请求。HTTP/1.1 的逻辑形式例如：

GET /products?id=42 HTTP/1.1
Host: www.example.com
User-Agent: ...
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=...
Connection: keep-alive

请求包含：

  • Method：例如 GET、POST
  • Target：Path 和 Query，不包含 Fragment
  • Headers：Host、内容协商、缓存条件、Cookie、追踪信息等
  • Body：POST、PUT 等请求可能携带；是否存在由方法语义和业务协议决定

HTTP/2 和 HTTP/3 不再以这种文本行格式在线路上传输，而是使用二进制帧；它们仍然表达相同的 Method、Scheme、Authority、Path、Headers 和 Body 语义。

数据封装与网络转发

HTTP/1.1 或 HTTP/2 使用 HTTPS 时，数据自上而下封装：

HTTP Message
    ↓
TLS Record
    ↓
TCP Segment
    ↓
IP Packet
    ↓
Ethernet 或 Wi-Fi Frame
    ↓
物理信号

HTTP/3 的封装路径不同：

HTTP/3 Frame
    ↓
QUIC Packet，使用 TLS 1.3 派生的密钥加密
    ↓
UDP Datagram
    ↓
IP Packet
    ↓
Ethernet 或 Wi-Fi Frame

QUIC 使用 TLS 1.3 完成握手和密钥协商，但应用数据不会先封装成传统 TLS Record 再放入 UDP。

接收端按照相反方向解封装。

各层地址的作用

层次 主要标识 作用
应用层 域名、URL、HTTP Host 标识站点和资源
传输层 TCP 或 UDP 端口 标识主机上的进程或 Socket
网络层 IPv4 或 IPv6 地址 跨网络选择路径并转发
链路层 MAC 地址 在当前链路交付给下一跳

MAC 地址通常每一跳都会变化；IP 地址通常端到端保持不变，但经过 NAT 时可能被改写。

交换机与路由器

  • 交换机根据目标 MAC 地址和 MAC 地址表，在同一二层网络中转发帧
  • 路由器移除收到的链路层首部，检查目标 IP，根据路由表选择下一跳
  • IPv4 路由器递减 TTL，IPv6 路由器递减 Hop Limit；减为 0 时丢弃报文并通常返回 ICMP 超时消息
  • 路由器为下一段链路重新封装新的链路层帧

Internet 上的实际路径由多个自治系统组成。域间主要通过 BGP 传播可达前缀，自治系统内部再使用自己的路由协议和转发表。请求与响应不保证经过完全相同的路径。

MTU 与 MSS

  • MTU 是链路层一次可承载的最大网络层报文大小，以太网常见值为 1500 字节，但并非固定保证
  • TCP MSS 表示 TCP Segment 中可承载的最大应用数据，通常在握手时协商
  • TCP 会按 MSS 分段，尽量避免 IP 分片
  • IPv6 路由器不会在途中分片，端点依赖 Path MTU Discovery 调整报文大小

如果 ICMP 被错误阻断，Path MTU Discovery 可能失败，出现小请求正常、大请求卡住等问题。

服务端接收与处理

请求到达目标 IP 后，不一定直接进入源站应用。常见链路是：

CDN 或边缘节点
    → DDoS 防护与 WAF
    → 四层或七层负载均衡器
    → 反向代理或 API Gateway
    → 应用服务器
    → 缓存、数据库或下游服务

不同组件可能终止并重新建立连接：

  • CDN 可以直接返回已缓存内容
  • 四层负载均衡器根据 IP、端口和连接信息选择后端
  • 七层负载均衡器或反向代理可以读取 Host、Path、Header 和 Cookie
  • TLS 可以在边缘、负载均衡器或应用服务器终止；后续链路是否再次加密取决于部署

在服务器主机上，网卡接收帧并触发内核网络栈处理。内核根据目标端口找到监听 Socket，把有序字节交给进程；应用解析 HTTP、执行鉴权和业务逻辑，最终生成响应。

返回 HTTP 响应

HTTP/1.1 响应的逻辑形式例如：

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: br
Cache-Control: max-age=300
Content-Length: ...
Set-Cookie: session=...; Secure; HttpOnly

<html>...</html>

响应包含：

  • Status Code：例如 200、301、304、404、500
  • Headers：内容类型、长度或分块信息、压缩、缓存、Cookie、安全策略等
  • Body：HTML、JSON、图片或其他资源

服务器可能压缩响应。HTTP/1.1 可以使用 Content-Length 或 Chunked Transfer Encoding 界定消息；HTTP/2 和 HTTP/3 使用帧边界，不使用 HTTP/1.1 的 Chunked 编码。

响应数据经过与请求相同的分层封装，但网络路径不一定对称。TCP 接收端根据序列号重组乱序数据、确认已收数据并触发必要重传；HTTP/1.1 和 HTTP/2 的 HTTPS 流量由 TLS 解密，HTTP/3 流量由 QUIC 解密和重组；HTTP 层最终获得完整响应语义。

浏览器解析与页面加载

浏览器收到 HTML 后开始流式解析，不一定等完整 HTML 下载结束才工作：

HTML → DOM
CSS → CSSOM
DOM + CSSOM → Render Tree
    → Layout
    → Paint
    → Composite

解析 HTML 时发现 CSS、JavaScript、图片、字体等资源，浏览器会继续发起请求。这些请求通常复用已有 HTTP/2 或 HTTP/3 连接并并发使用多个 Stream；HTTP/1.1 则可能使用多个连接缓解队头阻塞。

JavaScript 可能修改 DOM 和 CSSOM，也可能阻塞 HTML 解析。DNS Prefetch、Preconnect、Preload 等提示可以提前执行解析、建连或资源加载，但不会改变各网络协议本身的职责。

连接复用与关闭

页面完成不代表连接立即关闭：

  • HTTP/1.1 默认可以保持连接以处理后续请求
  • HTTP/2 和 HTTP/3 通常在一个连接上复用多个 Stream
  • 空闲超时、服务端策略、网络变化或错误可能关闭连接

TCP 正常关闭通常需要四次挥手，因为两个方向的字节流可以独立关闭：

主动方 → 被动方：FIN
被动方 → 主动方：ACK
被动方 → 主动方：FIN
主动方 → 被动方：ACK

主动关闭方通常进入 TIME_WAIT，主要用于让旧连接中的延迟报文在网络中消失，并在最后一个 ACK 丢失时重新发送 ACK。异常关闭可以发送 RST。QUIC 使用自己的连接关闭帧和超时机制，不执行 TCP 四次挥手。

HTTP 版本对比

特性 HTTP/1.1 HTTP/2 HTTP/3
传输基础 TCP TCP QUIC over UDP
数据格式 文本首部 二进制帧 二进制帧
多路复用 不支持真正的单连接多路复用 支持 支持
Header 压缩 无标准动态压缩 HPACK QPACK
队头阻塞 HTTP 请求及 TCP 层 TCP 丢包会影响连接内所有 Stream 丢包通常只阻塞相关 Stream
TLS HTTP 可明文，HTTPS 使用 TLS 浏览器实践中通常使用 TLS TLS 1.3 内置且必须使用
连接迁移 不支持 不支持 Connection ID 支持地址变化后的迁移

HTTP/2 的多路复用解决了 HTTP/1.1 应用层队头阻塞，但没有消除 TCP 层队头阻塞。HTTP/3 把独立 Stream 的可靠传输放入 QUIC，降低一个 Stream 丢包对其他 Stream 的影响。

面试回答模板

浏览器首先解析 URL，确定协议、域名、端口和资源路径，并检查 Service Worker、HTTP 缓存和可复用连接。如果需要访问网络，就通过浏览器、操作系统和递归 DNS 缓存查询域名，必要时递归解析到权威 DNS，获得 A 或 AAAA 地址。

操作系统根据路由表选择网络接口和下一跳，在局域网中使用 ARP 或 IPv6 NDP 获得下一跳 MAC 地址。HTTP/1.1 和 HTTP/2 通常先进行 TCP 三次握手；HTTPS 随后完成 TLS 握手，校验证书、通过密钥交换得到对称会话密钥，并用 ALPN 协商 HTTP 版本。如果使用 HTTP/3，则通过基于 UDP 的 QUIC 同时完成传输和 TLS 1.3 建连。

浏览器构造 HTTP 请求。HTTP/1.1 和 HTTP/2 的 HTTPS 数据依次封装为 TLS Record、TCP Segment、IP Packet 和链路层 Frame；HTTP/3 则封装为加密的 QUIC Packet、UDP Datagram、IP Packet 和链路层 Frame。交换机按 MAC 转发，路由器按目标 IP 和路由表逐跳转发，出口可能执行 NAT。服务端前面可能存在 CDN、WAF、负载均衡器和反向代理，最终应用处理请求并生成 HTTP 响应。

响应沿网络返回后，传输层完成可靠传输和重组，TLS 解密，HTTP 层解析状态码、首部和 Body。浏览器解析 HTML 和 CSS、加载子资源并完成布局、绘制与合成。连接通常会保留并复用，而不是每个资源都重新握手。

常见追问

DNS 已经获得 IP，为什么还需要 Host 和 SNI

一个 IP 可以承载多个域名：

  • TLS 握手发生在 HTTP 请求之前，SNI 帮助服务器选择证书
  • TLS 建立后，HTTP Host 或 HTTP/2、HTTP/3 的 :authority 帮助服务器选择虚拟主机和路由

ARP 查询的是服务器 MAC 吗

只有服务器与客户端处于同一二层网络时才查询服务器 MAC。访问公网服务器时，客户端通常查询默认网关的 MAC。路由器每经过一跳都会重新封装链路层帧。

为什么 DNS 正常不代表网站可用

DNS 成功只证明域名能解析为地址。TCP 端口、防火墙、TLS 证书、HTTP 路由、负载均衡器、服务器进程和后端依赖仍然可能失败。

HTTPS 能隐藏哪些信息

HTTPS 加密 HTTP Path、Query、Header 和 Body，但通常不能完全隐藏目标 IP。传统 TLS ClientHello 中的 SNI 也可能可见；加密 ClientHello 可改善这一点，但不是所有环境都支持。流量大小、时间和连接行为等侧信道仍然可观察。

Cookie 位于哪一层

Cookie 是 HTTP 应用层机制。浏览器根据域名、Path、Secure、SameSite 等规则决定是否在请求 Header 中携带 Cookie；TLS 只负责保护传输内容，不理解 Cookie 的业务含义。

TCP 粘包是不是数据丢失

不是。TCP 提供没有消息边界的字节流，一次读取可能得到半条、恰好一条或多条应用消息。应用协议必须通过长度字段、分隔符或固定长度自行划分消息边界。HTTP 已经定义了自己的消息和帧边界。

Ping 通为什么 HTTP 仍然不通

Ping 使用 ICMP，只能证明某种 IP 可达性。HTTP 还依赖目标 TCP 或 QUIC 端口、防火墙策略、TLS、应用监听和七层路由。反过来，禁用 ICMP 的主机也可能正常提供 HTTP 服务。

排障工具

分层验证

# DNS
dig www.example.com A
dig www.example.com AAAA

# TCP、TLS 与 HTTP 详细过程
curl -v https://www.example.com/

# 绕过 DNS，将域名临时绑定到指定 IP，同时保留 SNI 和 Host
curl -v --resolve www.example.com:443:203.0.113.10 https://www.example.com/

# 查看证书链、SNI 和 ALPN
openssl s_client -connect www.example.com:443 -servername www.example.com -alpn h2

# 查看本机监听和连接
ss -antp

# 观察路径
traceroute www.example.com

# 抓取并分析报文，接口和过滤条件应按环境调整
tcpdump -i <interface> -nn host <ip> and port 443

工具结果需要分层解释：

  • dig 成功：DNS 基本正常，不证明端口可达
  • TCP 建连失败：检查路由、ACL、防火墙、监听端口和负载均衡器
  • TCP 成功但 TLS 失败：检查 SNI、证书链、域名、时间和协议兼容性
  • TLS 成功但 HTTP 错误：检查 Host、Path、认证、反向代理和应用逻辑
  • 首个 HTML 成功但页面异常：继续检查子资源、缓存、CORS、JavaScript 和浏览器控制台
