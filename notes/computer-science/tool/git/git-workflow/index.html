Git Workflow

2026-09-02

#Git

这篇笔记从主干开分支开始，说明如何提交变更、同步主干、检查 PR，以及如何用 reflog 找回误操作前的提交。示例假定远程名为 origin，主干为 main，功能分支为 feature/example。

从主干开分支并创建 PR

  1. 检查工作区。确认手头的修改已妥善保存后，更新远程跟踪引用，再从 origin/main 创建功能分支。

    git status --short --branch
git fetch origin
git switch -c feature/example origin/main

  2. 完成修改和测试后，暂存需要提交的文件。将示例中的 example.txt 换成实际文件路径，用 git diff --cached 检查待提交内容。

    git add -- example.txt
git diff --cached
git commit -m "feat: add example"

  3. 首次推送时用 -u 设置上游分支。然后在 GitHub 创建 PR，目标分支选 main，来源分支选 feature/example。

    git push -u origin feature/example

手头的任务仍有未提交修改，又需要从主干开始另一项工作时，可以用 Git Worktree 在独立目录中继续。

把主干更新同步到功能分支

先确认当前在功能分支上，且暂存区和工作区干净。运行 git fetch origin 更新 origin/main，再按分支是否已被共享选择一种方式。

方式 命令 对提交历史的影响 适用场景
merge git merge origin/main 保留已有提交及其 ID。两侧分叉时通常生成合并提交，可快进时只需移动分支指针。 多人使用或已有其他分支依赖的功能分支。
rebase git rebase origin/main 将待重放的功能提交逐个应用到新基点。实际重放生成的提交有新的 ID。 尚未共享的分支，或由自己维护、团队允许改写的分支。

只要有人基于原提交继续开发，即使功能分支平时只有一人推送，重写历史也需要先协调。团队要求线性历史时，按约定整理个人分支和提交 PR。两种操作都可能冲突。处理完毕后，检查工作区和变更，重新运行相关测试。Git merge 文档，Git rebase 文档

处理同步冲突

用 git status 找出冲突文件，修改后用 git add -- example.txt 暂存，将示例文件名换成实际路径。合并用 git merge --continue 结束。重放用 git rebase --continue 继续，后续提交仍可能停下来要求处理冲突。决定撤销这次操作时，按刚才选用的方式运行 git merge --abort 或 git rebase --abort。Git merge 文档，Git rebase 文档

用交互式 rebase 整理提交

如果最近三个提交都是当前功能分支上可改写的线性提交，可以用 git rebase -i HEAD~3 打开待办列表。最早的提交保留 pick，需要合入前一个提交的后续项改为 squash 或 fixup。squash 会让你编辑合并后的提交说明，普通 fixup 沿用前一个提交的说明。Git rebase 文档

推送已经重写的分支

从未推送过的分支直接首次推送。如果已推送分支的远端顶端提交已不在新历史中，普通推送会因无法快进而被拒绝。只在确认功能分支允许重写、且远端提交都已纳入检查后，用 --force-with-lease 更新该分支。主干按团队的合并流程更新。

下面的命令适用于 Bash。先确认当前分支为 feature/example。重写前更新远程跟踪引用、记录远端顶端的提交 ID，并检查它是否有当前分支未包含的提交。如果 git log 输出了提交，先核对并整合这些改动，再重新检查。

git fetch origin
expected=$(git rev-parse --verify origin/feature/example)
git log --oneline HEAD.."$expected"

重写完成并验证后，在同一 Shell 使用先前记录的预期值推送。远端分支在此期间若已经指向另一提交，Git 会拒绝此次更新。

git push --force-with-lease="refs/heads/feature/example:$expected" origin HEAD:refs/heads/feature/example

省略预期值的 git push --force-with-lease origin feature/example 会用本地远程跟踪引用作为预期值。后台运行的 git fetch 可能刷新该引用，让命令接受尚未人工核对的远端提交。Git push 文档

检查 PR 的提交与文件差异

rebase 会改变实际重放的提交 ID。提交变少时，检查是否有提交被 squash 合并，或与主干上的补丁等价而在重放时被跳过。仅凭提交 ID 改变，无法判断某项改动是否还在 PR 中。Git rebase 文档

确认 PR 选对来源和目标分支，推送了预期版本。再核对 Commits 和 Files changed。前者用于检查提交历史，后者用于审查此次 PR 引入的文件改动。若本地 HEAD 与 PR 的来源分支顶端一致，且目标为最新的 origin/main，可在本地对照下面的输出。三点差异比较合并基点到功能分支顶端的内容。GitHub 分支比较文档

git fetch origin
git log --oneline origin/main..HEAD
git diff origin/main...HEAD

用 reflog 找回误操作前的提交

reflog 记录本地引用最近指向过的提交，可用于找回误 rebase 或误 reset 前的状态。先看 git reflog，再用 git show 核对对应的提交。下例假定已确认 HEAD@{2} 是需要找回的条目。创建救援分支即可先保留该提交。Git reflog 文档

git reflog
git show 'HEAD@{2}'
git branch rescue/before-rebase 'HEAD@{2}'

如果还要把当前本地功能分支移回该提交，先确认分支、保存需要的未提交修改，并为当前提交另建备份分支。git reset --hard rescue/before-rebase 会同时更新当前分支、暂存区和工作区，丢弃已跟踪文件的未提交修改，还可能覆盖阻挡写入的未跟踪文件。Git reset 文档
